RESTful API Design: A Practical Reference

What REST actually specifies, how to apply it correctly, where it fits well, and where other approaches are more appropriate. For frontend developers who consume, evaluate, and occasionally design HTTP APIs.

Reference guide
~30 min read
For developers working with HTTP APIs

REST is the dominant architectural style for HTTP APIs, but it is frequently misunderstood, inconsistently applied, and sometimes the wrong tool for the job. This document covers what REST actually specifies, how to apply it correctly, where it fits well, and where other approaches are more appropriate. It is written for frontend developers who encounter REST daily but want to move beyond cargo-culted conventions and understand the reasoning behind the rules.

Background

REST was defined in a doctoral dissertation. Understanding where it came from explains why it looks the way it does.

REST (Representational State Transfer) was defined by Roy Fielding in his doctoral dissertation at UC Irvine in 2000. It is an architectural style — a set of constraints on how components in a distributed system communicate — not a protocol, specification, or standard. Fielding derived REST by identifying the properties desirable in a large-scale hypermedia system (like the web) and working backward to the constraints that produce them.

REST is applied on top of HTTP. HTTP already provides the transport, method semantics, status codes, headers, and caching mechanisms that REST relies on. A RESTful API is one that uses these mechanisms in the way they were intended, rather than tunneling everything through a single endpoint or overloading method semantics.

The Richardson Maturity Model

The Richardson Maturity Model characterizes how RESTful a given API is across four levels:

Level 0
HTTP as a Tunnel

Single endpoint, all operations via POST. HTTP is used purely as a transport mechanism, ignoring its method semantics entirely. SOAP and XML-RPC are the canonical examples.

Level 1
Resources

Multiple resources identified by different URLs, but a single HTTP method (usually POST) for all operations. The domain is decomposed into nouns but the verb layer is ignored.

Level 2
HTTP Verbs

Resources and correct HTTP method semantics. This is what most people mean when they say "REST API." GET retrieves, POST creates, PUT/PATCH updates, DELETE removes.

Level 3
Hypermedia Controls

Responses include links to available actions (HATEOAS). Clients discover transitions from the response rather than having them hard-coded. Rarely implemented in practice.

What to target in practice

Most production APIs target Level 2. This document focuses on Level 2 design and notes where Level 3 concepts are relevant. Reaching Level 2 consistently and correctly is harder than it looks — most "REST APIs" in the wild are actually Level 1 with some GET requests sprinkled in.

REST Compared to Other API Designs

REST is not the only way to design an HTTP API, and it is not always the best fit.

Understanding the alternatives makes it easier to choose the right tool and to recognize where REST's model imposes unnecessary friction.

REST vs. RPC (Remote Procedure Call)

RPC-style APIs expose operations rather than resources. Rather than POST /orders/42/cancel, an RPC API might expose POST /cancelOrder with {"orderId": 42} in the body. gRPC is a modern, strongly-typed RPC framework that uses Protocol Buffers over HTTP/2.

RPC is a natural fit when the domain is operation-heavy rather than resource-heavy: financial transactions, data processing pipelines, internal service-to-service communication where network overhead matters. REST's resource model adds friction in these contexts without a compensating benefit. The practical difference for a frontend developer is that RPC APIs tend to have more predictable, strongly-typed contracts (especially gRPC with generated clients), but less convention — every API defines its own operation names and structures.

REST vs. GraphQL

GraphQL is a query language and runtime developed by Meta and open-sourced in 2015. Rather than multiple resource-specific endpoints, a GraphQL API exposes a single endpoint through which clients issue typed queries and mutations.

GraphQL Strengths
Client-specified shape

The client declares exactly which fields it wants. This eliminates over-fetching (too much data) and under-fetching (multiple round trips to assemble a view). Strongly typed schema enables build-time validation.

GraphQL Tradeoffs
Single endpoint

All operations go through one URL (POST /graphql). HTTP caching does not apply naturally. Server complexity is higher, and introspection exposes the full API surface to any consumer.

GraphQL fits well when the frontend has highly variable data requirements — particularly with multiple clients (web, mobile, third-party) that need different shapes of the same data.

REST vs. tRPC

tRPC is a TypeScript-first framework that generates end-to-end type-safe APIs without a schema definition step. It is RPC-style: the server defines procedures, and the client calls them with full type inference. It requires both client and server to be TypeScript.

tRPC is well-suited to full-stack TypeScript applications where the same team owns both ends. It is not appropriate for public APIs or multi-language environments.

REST remains the right default for public-facing APIs, APIs consumed by heterogeneous clients, and situations where HTTP-level caching and tooling compatibility matter. The other approaches solve specific problems that REST handles awkwardly.

Architectural Constraints

Fielding defined six constraints. Taken together, they produce scalability, visibility, reliability, and portability.

Uniform Interface

The uniform interface constraint is what most distinguishes REST from other architectural styles. It requires that all interaction between components happen through a standardized interface — in practice, HTTP with resource-based URLs. It has four sub-constraints:

  • Identification of resources — Every resource is identified by a stable URI. The resource itself (e.g., a database row) is separate from its representation (the JSON response).
  • Manipulation of resources through representations — Clients interact with resources by exchanging representations. A client that holds a representation of a resource has enough information to modify or delete it.
  • Self-descriptive messages — Each message includes enough information to describe how it should be processed. The Content-Type header is the mechanism for this.
  • Hypermedia as the engine of application state (HATEOAS) — Responses include links to available transitions. Rarely implemented at Level 2; worth understanding conceptually.

The practical implication is that URLs should identify resources (nouns), not operations (verbs). The operation is expressed by the HTTP method.

Statelessness

Each request from client to server must contain all the information necessary to process the request. The server does not store client session state between requests. Any session state lives on the client.

This constraint enables horizontal scaling — any server instance can handle any request — and makes individual requests easier to reason about and log. The cost is that some information must be repeated on every request (authentication credentials, preferences, etc.).

Statelessness ≠ no server state

Statelessness does not mean the server has no state. Resource state (the data in the database) is stored server-side. Session state (who is making the request, what they have in a shopping cart) must not be.

Client–Server

The client and server are separate concerns with a well-defined interface between them. The server manages resources and business logic; the client manages the user interface and user state. Neither knows the internal implementation of the other. This separation means the client and server can evolve independently as long as the interface contract is maintained.

Layered System

A client cannot tell whether it is connected directly to the origin server or to an intermediary (a load balancer, CDN, caching proxy, or API gateway). Intermediaries can be inserted transparently. This constraint is what makes CDN caching, API gateways, and reverse proxies work without changes to clients.

Cacheability

Every response must explicitly declare itself as cacheable or non-cacheable. HTTP provides the mechanisms: Cache-Control, ETag, Last-Modified, Expires, and conditional request headers (If-None-Match, If-Modified-Since). Cacheable responses can be stored and reused by clients, intermediaries, or CDNs, reducing latency and server load.

Code on Demand Optional

Servers can extend client functionality by transferring executable code — JavaScript in a browser being the canonical example. This constraint is optional and rarely relevant in API design contexts.

Resource Modeling

Resource modeling is the most consequential design decision in a REST API. Getting it right makes the API predictable.

Resources Are Nouns, Not Verbs

A resource is a thing, not an action. URLs identify resources; HTTP methods express the action.

# Correct
GET /orders/42
POST /orders
DELETE /orders/42
# Incorrect — verbs in URLs
GET /getOrder?id=42
POST /createOrder
POST /deleteOrder

If you find yourself putting a verb in a URL, that is a signal to reconsider the resource model. Often there is an implicit noun: a cancellation is a resource; a report is a resource; a session is a resource.

URL Structure and Hierarchy

URL hierarchy should reflect containment or ownership relationships between resources. A resource nested under another is a sub-resource.

/users/9/orders # Orders belonging to user 9
/orders/42/items # Line items within order 42
/orders/42/items/7 # A specific line item

Nesting should be kept to two levels in most cases. Deep hierarchies produce long, fragile URLs and often indicate that the resource model is too tightly coupled to a particular access pattern. A resource may be accessible via multiple URLs, but it should have a single canonical URL.

Identifiers

Resource identifiers should be opaque, stable, and not expose internal implementation details. UUIDs or other non-sequential identifiers are preferable to auto-incrementing database IDs, which reveal record counts and are easier to enumerate.

/orders/a3f9b2c1-4d5e-6f7a-8b9c-0d1e2f3a4b5c # Preferred
/orders/42 # Acceptable, but exposes sequence

Granularity

Overly coarse resources return unnecessary data on every request; overly fine resources require many requests to assemble a useful view. Consider the access patterns of your clients. If every view that shows an order also shows the customer name, returning the customer name inline in the order response is reasonable. For public APIs, sparse fieldsets (?fields=id,name,status) are a useful middle ground.

HTTP Semantics

HTTP methods have defined semantics. Deviating from them breaks caching, idempotency guarantees, and the assumptions of any intermediary.

Methods

GET Retrieve a resource. Safe (no side effects) and idempotent (repeated calls produce the same result). Must not modify state. Responses may be cached.
POST Submit data for processing. Neither safe nor idempotent. Used for creating resources where the server assigns the identifier, and for operations that do not fit other methods.
PUT Replace a resource entirely. Idempotent: repeated calls produce the same result. The client provides the complete representation. If the resource does not exist, it may be created.
PATCH Apply a partial update. Not idempotent by default (though specific patch formats can be). The request body contains instructions for modifying the resource, not the full replacement.
DELETE Remove a resource. Idempotent in effect: the server state after repeated calls is the same. A second DELETE on an already-deleted resource may return 204 (treating "already gone" as success) or 404 — both are valid; be consistent across your API.
HEAD Identical to GET but returns only headers. Useful for checking whether a resource exists or has been modified without transferring the body.

PATCH formats

PATCH semantics require that the request body describe changes to apply, not the full resource. Two standard formats cover most cases.

JSON Merge Patch (RFC 7396) is a simple overlay: fields present overwrite the existing value, fields set to null are deleted, fields absent are unchanged. Use Content-Type: application/merge-patch+json.

PATCH /orders/42 JSON Merge Patch 
// Only "status" changes. All other fields are untouched.
{ "status": "cancelled", "cancellation_reason": "Customer request" }

Merge Patch is easy to read and implement, but cannot set a field to null without deleting it.

JSON Patch (RFC 6902) is an array of typed operations (add, remove, replace, move, copy, test) that can precisely express any mutation. Use Content-Type: application/json-patch+json.

PATCH /orders/42 JSON Patch 
[
  { "op": "replace", "path": "/status",              "value": "cancelled" },
  { "op": "add",     "path": "/cancellation_reason", "value": "Customer request" }
]

JSON Patch supports a test operation that aborts the entire patch if a precondition fails. For most APIs, Merge Patch is sufficient; use JSON Patch when you need conditional or complex atomic updates.

Status Codes

Use the most specific applicable status code. Generic codes (200, 400, 500) are acceptable when no more specific code fits, but they discard information the client could use.

2xx — Success

200OK — Request succeeded. Used for GET, PUT, PATCH responses and POST responses that return the resource.
201Created — A resource was created. Must include a Location header pointing to the new resource.
202Accepted — Request received but processing is not complete. Used for asynchronous operations.
204No Content — Request succeeded; no response body. Common for DELETE and PATCH responses when the updated resource is not returned.

3xx — Redirection

301Moved Permanently — Resource has a new canonical URL. Clients should update bookmarks.
304Not Modified — Conditional GET; cached version is current. No body returned.

4xx — Client Error

400Bad Request — The request is malformed or contains invalid syntax.
401Unauthorized — Authentication is required and was not provided, or credentials are invalid. (The name is misleading: this code means unauthenticated.)
403Forbidden — The client is authenticated but does not have permission. Do not use 404 to obscure the existence of a resource unless the security requirement demands it.
404Not Found — The resource does not exist at this URL.
405Method Not Allowed — The resource exists but does not support this HTTP method. The response must include an Allow header listing the supported methods.
409Conflict — The request conflicts with the current state of the resource. Used for duplicate creation, optimistic concurrency conflicts.
410Gone — The resource existed and has been permanently removed. Prefer over 404 when the removal is intentional.
422Unprocessable Entity — The request is syntactically valid but semantically incorrect. Used for validation errors.
429Too Many Requests — Rate limit exceeded. Should include a Retry-After header.

5xx — Server Error

500Internal Server Error — Unhandled server-side failure.
503Service Unavailable — Server is temporarily unable to handle requests. Should include a Retry-After header.

Headers

Request headers clients should send:

  • Content-Type — The media type of the request body. Typically application/json.
  • Accept — The media type(s) the client can handle. The server uses this for content negotiation.
  • Authorization — Authentication credentials. Commonly Bearer <token> for JWT-based auth.
  • If-None-Match — ETag value from a previous response; triggers a 304 if unchanged.
  • If-Modified-Since — Timestamp from a previous response; triggers a 304 if unchanged.

Response headers servers should send:

  • Content-Type — The media type of the response body.
  • Location — URI of a newly created resource (on 201) or the polling URL for an async operation (on 202).
  • ETag — A version identifier for the response. Clients use this for conditional requests and optimistic concurrency.
  • Cache-Control — Caching instructions. At minimum, set no-store on responses that must not be cached.
  • Retry-After — How long to wait before retrying, used with 429 and 503.
  • X-RateLimit-Limit / X-RateLimit-Remaining / X-RateLimit-Reset — Rate limit status. Widely adopted by convention; not yet standardised (an IETF draft proposes a standard RateLimit header).
Rate limit design

Send rate limit headers on every response, not only on 429. This lets clients back off proactively. A 429 response should always include Retry-After. Distinguish per-user and global limits if both apply.

Error Response Format

Inconsistent error formats across an API create unnecessary client-side complexity. RFC 9457 (Problem Details for HTTP APIs) defines a standard format:

JSON 
{
  "type": "https://example.com/problems/insufficient-stock",
  "title": "Insufficient stock",
  "status": 422,
  "detail": "Requested quantity 5 exceeds available stock of 2 for item SKU-9981.",
  "instance": "/orders/42/items/7"
}

Respond with Content-Type: application/problem+json so clients can identify the format. The type URI should resolve to documentation. The title is a stable human-readable summary — it should not change between occurrences. The detail is specific to this occurrence. Additional members may be added freely; a common extension is an errors array for field-level validation failures.

RFC 9457 supersedes RFC 7807

RFC 9457 (2023) replaces RFC 7807. Both describe the same structure; 9457 is a minor clarifying revision. References to "Problem Details" or RFC 7807 in older code refer to the same concept.

Optimistic Concurrency

ETags let multiple clients modify the same resource safely, without locking.

When multiple clients may update the same resource concurrently, last-write-wins produces silent data loss. Optimistic concurrency detects conflicts without holding locks: the server issues a version token (ETag) with every response, and the client must present that token on modification requests. If the resource has changed since the client last fetched it, the server rejects the update with 412 Precondition Failed.

HTTP 
# 1. Fetch — server returns a version token
GET /orders/42
→ 200 OK
ETag: "v3"

# 2. Update — send the token in If-Match
PATCH /orders/42
If-Match: "v3"
→ 200 OK  (token matched, update applied)
ETag: "v4"

# If another client updated first, the token no longer matches
PATCH /orders/42
If-Match: "v3"
→ 412 Precondition Failed

On a 412, the client should re-fetch the resource, present the conflict to the user, and ask them to re-confirm or merge. If-Match: * means "update only if the resource exists at all, regardless of version." The ETag value should be opaque — a hash or row version, not a timestamp, which has resolution and clock-skew issues.

Idempotency Keys

POST is not idempotent by definition. Idempotency keys give you the property anyway.

When a client sends a POST and the connection drops before a response arrives, it cannot know whether the server processed the request. Retrying risks creating a duplicate. Idempotency keys solve this: the client generates a unique token per logical operation and includes it in the request. If the server receives a second request with the same token, it returns the result of the first without re-executing the operation.

HTTP 
POST /payments
Idempotency-Key: "a3f9b2c1-4d5e-6f7a-8b9c-0d1e2f3a4b5c"
Content-Type: application/json

{ "amount": 9900, "currency": "SEK", "card_token": "tok_xyz" }

The server stores the key and result for a defined period (commonly 24 hours). Repeated requests with the same key return the cached result immediately. The header name Idempotency-Key is the de facto convention (used by Stripe, Adyen, and most payment providers), though not yet an HTTP standard. Use it for any operation where duplicate execution would be harmful: payments, order creation, and account actions.

Keys must be client-generated

Generate a fresh UUID per logical attempt before sending the request — not from a prior response. If the key comes from the server, the round-trip to fetch it has the same network-failure problem you are trying to solve.

CORS

Browsers enforce a same-origin policy. CORS is the mechanism servers use to opt in to cross-origin requests.

A browser blocks JavaScript from reading responses to requests that cross origins (scheme + host + port), unless the server explicitly permits it via CORS headers. This is a browser security constraint — curl and server-to-server calls are unaffected.

A simple request (GET, HEAD, or POST with a basic content type) is sent directly — the browser checks the response headers to decide whether to expose the result to JavaScript. Any other method, a custom header, or a JSON Content-Type triggers a preflight: the browser first sends an OPTIONS request to ask permission before sending the real request.

HTTP 
# Preflight — browser asks before sending the real request
OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

→ 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
Response headerPurpose
Access-Control-Allow-OriginWhich origin(s) are permitted. Use a specific origin, not *, when credentials are involved.
Access-Control-Allow-MethodsHTTP methods the browser may use.
Access-Control-Allow-HeadersRequest headers the browser may include. Must list every custom header the client sends.
Access-Control-Allow-CredentialsSet to true to allow cookies and the Authorization header. Requires a specific (non-wildcard) origin.
Access-Control-Max-AgeHow long to cache the preflight result, in seconds. Reduces round-trips on frequent requests.
Access-Control-Expose-HeadersNon-standard response headers to expose to JavaScript (ETag, Location, custom headers are hidden by default).
Do not combine * with credentials

If your API uses cookies or an Authorization header, you cannot use Access-Control-Allow-Origin: *. Browsers reject this combination. Reflect the specific incoming Origin value (after validating it against an allowlist) instead.

Versioning

No versioning strategy is universally correct. The three common approaches each make different tradeoffs.

URL Path Versioning

https://api.example.com/v2/orders

Visible, easy to route at the infrastructure level, and simple to test in a browser or curl. The version is explicit in every request log. The cost is that URLs are no longer "pure" resource identifiers — the version prefix is infrastructure metadata, not part of the resource's identity. This is the most common approach in practice and is a reasonable default.

Request Header Versioning

API-Version: 2

URLs remain clean and canonical. The cost is that the version is invisible in logs that only record URLs, cannot be tested directly in a browser address bar, and infrastructure routing on version requires header inspection.

Content Negotiation

Accept: application/vnd.example.api+json; version=2

The most technically correct approach — versioning is about the representation, not the resource, and Accept is the appropriate mechanism for negotiating representations. Also the least commonly adopted, due to tooling support and developer familiarity.

Versioning Considerations

  • Version the entire API surface, not individual endpoints.
  • Maintain previous versions for a documented deprecation period.
  • Communicate deprecation timelines via response headers (Deprecation, Sunset) and documentation.
  • Additive changes (new fields, new optional parameters) generally do not require a version increment if you follow Postel's law: be conservative in what you send, liberal in what you accept.

Breaking vs non-breaking changes

A breaking change causes a correctly-implemented existing client to fail or produce wrong results. Non-breaking changes can ship without a version bump, provided clients are written defensively.

ChangeBreaking?Notes
Add optional response fieldNoClients must ignore unknown fields.
Add optional request parameterNoExisting clients omit it; behaviour unchanged.
Relax validation (accept more values)NoPreviously valid requests still succeed.
Remove a response fieldYesClients reading that field break.
Remove or rename an endpointYesUse 301/410 with a migration window.
Add a required request fieldYesExisting clients that omit it get 400.
Change a field's typeYesEven if the value is semantically equivalent (e.g. number → string).
Narrow validation (reject previously valid values)YesPreviously valid requests now fail.
Change a status codeYesClients checking for exact codes break.

OpenAPI

OpenAPI is the de facto standard for describing REST APIs. In 2026, you will encounter it in almost every professional API context.

OpenAPI (formerly Swagger) is a machine-readable specification format for HTTP APIs, written in YAML or JSON. A document describes every endpoint, its parameters, request and response schemas, authentication requirements, and expected status codes. OpenAPI 3.1 (released 2021) is the current version; it aligns fully with JSON Schema, resolving a long-standing incompatibility in 3.0.

openapi.yaml OpenAPI 3.1 
openapi: "3.1.0"
info:
  title: Orders API
  version: "2"
paths:
  /orders/{id}:
    get:
      summary: Retrieve an order
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string, format: uuid }
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Order" }
        "404": { description: Not found }

Design-first vs code-first

In a design-first workflow the OpenAPI document is written before implementation. Teams agree on the contract, generate mocks for frontend development, and can spot breaking changes in pull request diffs before any code ships. This is preferable for public or partner-facing APIs.

In a code-first workflow the spec is generated from the implementation via decorators or runtime introspection. The spec is always in sync but the design is constrained by what was easy to code. This works well for internal APIs where the same team controls both sides.

TypeScript client generation

Tools like Hey API generate fully-typed TypeScript clients directly from an OpenAPI spec — typed parameters, response bodies, and error types — eliminating an entire class of integration bugs without hand-written types or manual sync with the server team.

Pagination, Filtering, and Sorting

Collections should always be paginated. Returning unbounded result sets creates performance, memory, and timeout issues on both ends.

Pagination

Offset pagination uses a numeric offset and limit:

GET /orders?offset=40&limit=20

Simple to implement and allows random access to any page. The failure mode is instability: if items are inserted or deleted between pages, a client paginating sequentially may skip or duplicate records. Also expensive at large offsets — the database must scan and discard all preceding rows.

Cursor pagination uses an opaque pointer to the last seen item:

GET /orders?cursor=eyJpZCI6NDJ9&limit=20

Stable under insertion and deletion, and performs consistently at any position. The tradeoff is that it does not allow random page access — clients must paginate sequentially. The cursor should be opaque to the client; its internal structure is an implementation detail.

Pagination metadata

Include at minimum the total count, the cursor or offset for the next page, and whether more results exist. Conveying this via response headers (Link per RFC 5988, X-Total-Count) keeps the response body clean; embedding it in a response envelope is also common and more explicit.

Filtering

Filtering is expressed via query parameters. Consistency within an API matters more than any particular syntax:

GET /orders?status=pending
GET /orders?created_after=2024-01-01&created_before=2024-06-30
GET /orders?status=pending,processing # multiple values
GET /orders?total_gte=100&total_lte=500 # range

Unsupported filter parameters should return a 400 rather than being silently ignored.

Sorting

Two conventions are common:

GET /orders?sort=created_at&order=desc # explicit direction parameter
GET /orders?sort=-created_at # prefix: - for desc, no prefix for asc
GET /orders?sort=-created_at,id # multi-field with prefix notation

Sorting on non-indexed fields should be restricted or rate-limited, as it can produce expensive queries.

Handling Non-Resource Operations

REST's resource model maps cleanly to CRUD operations but produces friction for action-oriented, bulk, and asynchronous operations.

State Transitions

Operations that transition a resource from one state to another can be modeled as either a direct update or a sub-resource.

Direct update — the client sends the target state:

HTTP 
PATCH /orders/42
Content-Type: application/json

{ "status": "cancelled" }

Sub-resource — the transition itself is treated as a resource:

HTTP 
POST /orders/42/cancellations

The sub-resource approach is more expressive when transitions have their own attributes (a cancellation reason, a timestamp) or when you want to record a history of transitions.

Bulk Operations

No standard convention exists for bulk operations. The common approaches are a batch endpoint that accepts an array of operations, or collection-level operations that match a filter:

HTTP 
POST /orders/batch
Content-Type: application/json

{
  "operations": [
    { "method": "DELETE", "id": "42" },
    { "method": "DELETE", "id": "43" }
  ]
}

Clarify whether operations are atomic (all succeed or all fail) or non-atomic (partial success is possible), and what the response format looks like for partial failures.

Asynchronous Operations

For operations that take significant time, respond immediately with 202 Accepted and provide a way for the client to check progress:

HTTP 
# Client creates the report
POST /reports
→ 202 Accepted
   Location: /reports/jobs/f3a9b2c1

# Client polls the job resource
GET /reports/jobs/f3a9b2c1
→ 200 OK
   { "status": "processing", "progress": 0.42 }

GET /reports/jobs/f3a9b2c1
→ 200 OK
   { "status": "complete", "result": { "href": "/reports/2024-q4" } }

When the job is complete, the response points to the result resource. This pattern is REST-native and works without webhooks or real-time infrastructure.

Search and Computation

For simple search, a GET with query parameters is idiomatic and allows caching:

GET /products?q=running+shoes&category=footwear

For complex queries — full-text search with ranking, facets, and multiple compound filters — request bodies are more practical. A POST to a dedicated endpoint is acceptable:

HTTP 
POST /products/search
Content-Type: application/json

{
  "query": "running shoes",
  "filters": { "category": "footwear", "price_lte": 150 },
  "facets": ["brand", "size"],
  "sort": "-relevance"
}

The tradeoff with POST is that it is not cacheable. For read-heavy search APIs where caching is important, encoding the query as a GET parameter (potentially base64-encoded JSON) preserves cacheability at the cost of readability.

Real-Time Updates

REST has no native mechanism for server-initiated messages. The appropriate tools are:

  • Server-Sent Events (SSE) — unidirectional server-to-client streaming over HTTP. Suitable for live feeds, notifications, and progress updates. Reconnects automatically.
  • WebSockets — bidirectional connection. Suitable for collaborative editing, chat, and high-frequency two-way communication.
  • Webhooks — the server pushes events to a client-provided URL. Suitable for asynchronous integration between systems. See security note below.

Polling (repeated GET requests) is a valid fallback when real-time infrastructure is not available, particularly with conditional requests (If-None-Match) to minimize response bodies on unchanged resources.

Webhook security

A webhook receiver is a publicly accessible endpoint that accepts POST requests from a third party. Without verification, any party can POST to it and trigger your logic. Two properties are required for production webhook integrations.

Payload signature verification. The sender signs each payload with a shared secret using HMAC-SHA256 and includes the signature in a request header (commonly X-Signature-256 or Webhook-Signature). The receiver recomputes the signature and rejects the request if it does not match.

verify-webhook.ts TypeScript 
import { createHmac, timingSafeEqual } from 'node:crypto';

function verifyWebhook(
  rawBody: Buffer,
  signature: string,   // from X-Signature-256 header
  secret: string
): boolean {
  const expected = createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');
  // timingSafeEqual prevents timing-based signature oracles
  return timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(expected)
  );
}

Event idempotency. Network issues mean a webhook may be delivered more than once. Each event should carry a unique ID. The receiver should record processed event IDs and discard duplicates before acting on them.

Always verify before acting

Respond with 200 OK immediately after verification, before any processing. Senders typically retry on non-2xx responses — do expensive work asynchronously to avoid spurious retries from timeouts.

Design Checklist

A reference checklist for evaluating or reviewing a REST API design.

Resource and URL design
URLs use nouns, not verbs
URL hierarchy reflects containment, not operations
Resources have stable, opaque identifiers
Collections and individual resources behave consistently
HTTP semantics
HTTP methods are used according to their defined semantics
GET requests have no side effects
PUT and DELETE requests are idempotent
Status codes are specific and accurate (not generic 200 for everything)
201 Created responses include a Location header
202 Accepted responses include a Location pointing to a job resource
Headers and caching
Content-Type is set on all requests and responses with a body
Cacheable responses include appropriate Cache-Control and ETag headers
Non-cacheable responses are explicitly marked Cache-Control: no-store
Error handling
Error responses follow a consistent format (RFC 9457 recommended)
Validation errors identify the specific fields and constraints violated
4xx errors are not returned for server-side failures
5xx errors do not expose internal implementation details
Versioning and evolution
Versioning strategy is defined and applied consistently
Additive changes are non-breaking (no version increment required)
Deprecated endpoints communicate sunset timelines via headers or documentation
Pagination and collections
All collection endpoints are paginated
Pagination style (offset vs. cursor) is consistent across the API
Pagination metadata includes total count and next-page pointer
Filtering and sorting parameters are documented
Non-resource operations
Bulk and async endpoints document atomicity behavior
Async operations return 202 with a Location header
Real-time requirements are handled outside REST (SSE, WebSockets, webhooks)
Webhooks verify payload signatures (HMAC-SHA256) and handle duplicate events idempotently
Concurrency and safety
Resources that may be concurrently modified carry ETag headers
Modification requests that must be conflict-safe use If-Match
Non-idempotent POST operations that must survive retries accept an Idempotency-Key
CORS
CORS headers are present on all endpoints accessed from browsers
Access-Control-Allow-Origin is not wildcard when credentials are used
Access-Control-Expose-Headers lists any non-standard response headers clients need to read
Description
An OpenAPI 3.1 document describes all endpoints, schemas, and authentication
The spec is linted (e.g. with Spectral) and validated against the implementation
