Web Application Networking: From Browser to Backend

The infrastructure between a user's browser and your application code: what each layer does, why it exists, and what it means for security, scalability, and application design.

Conceptual overview
~14 min read
Architecture
June 2026

Introduction

A browser makes a request. Application code handles it. Between those two events is a chain of infrastructure that shapes how fast the application responds, how it behaves under load, whether it stays up when a server fails, and what attack surface it presents to the internet.

This article explains the components in that chain: what each one does, why it exists, and what decisions it requires from you as an architect. The goal is not to configure these components but to understand them well enough to choose the right ones, place them correctly, and know how they interact with application design.

The Request Path

A request rarely travels directly from a browser to an application server. The components along the path each have a specific job, and understanding those jobs is where architectural clarity starts.

The journey starts with DNS, which resolves the hostname to an IP address before any connection is established. The browser then opens a TCP connection and performs a TLS handshake to the destination, which is often a CDN edge or load balancer rather than the origin server. If a CDN is present, it receives the request first and serves cached content when possible. Otherwise, it forwards the request to the origin. A WAF, often integrated with the CDN, reverse proxy, or load balancer, inspects HTTP requests for malicious traffic. Network firewalls control which connections are allowed to reach the infrastructure. A reverse proxy or API gateway terminates TLS, routes requests, and handles cross-cutting concerns such as authentication, rate limiting, and logging. A load balancer distributes requests across multiple application instances. The application servers execute the business logic, communicating with databases and internal services as needed.

The sections below examine each layer. The four components that cause the most confusion (firewall, reverse proxy, load balancer, and API gateway) are compared first.

Four Core Components

Firewalls, reverse proxies, load balancers, and API gateways each have a distinct primary job. Products often combine multiple roles, which is why the distinctions matter more at the concept level than at the product level.

Firewall

A firewall controls which network connections are permitted. Traditional firewalls operate at the network layer (IP addresses) and transport layer (ports and protocols), allowing or denying traffic based on source address, destination address, port number, and protocol. At this level, a firewall has no knowledge of HTTP or your application's behavior. Modern next-generation firewalls (NGFW) can additionally inspect traffic at the application layer, applying policies based on application type or threat signatures, but the core role is the same: the firewall is a boundary enforcer that decides whether a connection is allowed before any application code runs.

A firewall is how you express rules like "the database accepts connections only from the application servers, not from the internet." If a connection does not match a permitted rule, it is dropped at the boundary.

Reverse Proxy

A reverse proxy sits in front of one or more backend servers, accepting connections on their behalf and forwarding each request onwards. From the client's perspective, it is always talking to the proxy. The actual application servers are not directly reachable. The value of this arrangement is that cross-cutting concerns can be handled at the proxy rather than repeated in every backend: TLS can be terminated there, responses can be cached and compressed, headers can be rewritten, and requests can be routed to entirely different applications based on the URL path. That last point is worth making concrete: a single domain can send /login to an authentication service and /my-account to a profile service, with the proxy directing each request to the right backend. The client sees one address. The proxy decides what runs behind it. These things can also be done within application code, but a reverse proxy lets you centralize them for all backends without changing the applications themselves.

Nginx is the canonical standalone reverse proxy. Every load balancer, CDN, and API gateway also behaves as a reverse proxy in the sense that it intercepts connections and forwards them. The term names a behavior more than a specific product type.

Load Balancer

A load balancer's primary job is to prevent any single server from being overloaded. It distributes incoming traffic across a pool of application instances so capacity scales horizontally: when demand grows you add more instances, and when one fails its health check the load balancer removes it from rotation and traffic continues to the healthy ones automatically.

Load balancers operate at either Layer 4 (TCP connections) or Layer 7 (HTTP requests). A Layer 4 load balancer distributes connections based on IP address and port without reading HTTP. A Layer 7 load balancer understands HTTP, which enables it to also perform reverse proxy functions such as routing by hostname or path, and TLS termination. Most web application load balancers today operate at Layer 7. AWS Application Load Balancer, GCP Load Balancing, and Azure Application Gateway all work this way. The useful distinction to keep in mind: a load balancer's defining goal is distributing load across instances, while a reverse proxy's defining goal is intercepting and augmenting individual requests. In practice, many products do both.

API Gateway

An API gateway is a reverse proxy with application-level policies built in. It sits in front of backend services and enforces cross-cutting concerns centrally: authentication and authorization, rate limiting, routing by API version or path, analytics, and developer-facing features like API key management. Where a general-purpose reverse proxy is neutral about what flows through it, an API gateway is opinionated about API traffic specifically.

The practical benefit is that these concerns are handled once at the gateway rather than duplicated across every service. Individual services receive already-authenticated requests and can focus on domain logic.

Why these overlap in practice

An AWS Application Load Balancer is both a load balancer and a reverse proxy. An Nginx instance can serve as a reverse proxy, load balancer, and static file server simultaneously. The distinctions above are conceptual: they describe a primary job and what the component needs to see to do it. When evaluating a product, ask which of these jobs it covers and whether it covers them well.

At the Edge: CDN and WAF

The components furthest from your application handle the highest request volumes and provide the first lines of defense.

A CDN (Content Delivery Network) is a global network of servers positioned close to users in major population centers. The purpose is latency: a user in Frankfurt connecting to a CDN point-of-presence in Frankfurt gets a response in single-digit milliseconds rather than the 150+ milliseconds a round trip to a US data center would take. For dynamic content that cannot be cached, the CDN still helps: it terminates TLS at the edge node (eliminating the round-trip cost of the handshake) and routes the remaining connection over the CDN's own high-capacity network backbone to the origin.

The CDN is not just a performance tool. It is the first security layer many applications have. A WAF (Web Application Firewall) positioned at the edge inspects HTTP requests for SQL injection patterns, XSS payloads, path traversal attempts, and known bot signatures. DDoS protection also lives here: a volumetric attack large enough to saturate a single data center's network connection is absorbed across the CDN's aggregate capacity in hundreds of edge locations. The application servers never see the traffic.

What you put at the edge determines what reaches your infrastructure at all. Cache TTL decisions, which response headers are forwarded, and where TLS terminates all have direct consequences for application behavior and security posture.

Load Balancers and Application Design

Horizontal scaling sounds simple: add more servers and distribute traffic. The complication is state stored in process memory.

A load balancer distributes incoming requests across a pool of application instances. When one instance fails its health check, traffic moves to the remaining healthy ones. When demand grows, new instances join the pool. This is horizontal scaling, the standard approach to availability and capacity in modern web applications. It does create one challenge: user sessions.

The problem surfaces as soon as user sessions are involved. A user logs in, and server A creates a session record in memory. Their next request goes to server B. Server B has no knowledge of that session. The user appears to be logged out.

The workaround is session stickiness: the load balancer routes all requests from the same user to the same server. It works in the short term, but it creates exactly the kind of fragility horizontal scaling is meant to eliminate. If server A crashes, every session pinned to it is lost. Load distribution becomes uneven. Deployments require careful session migration.

The right answer is designing the application to be stateless. Session data lives in a shared external store (Redis is the most common choice) rather than in process memory. Every server can then handle any request, because session state is not local. The load balancer routes freely. Servers can be added, removed, or restarted without disrupting user sessions.

Health checks are the other critical piece. A load balancer continuously probes each instance on a dedicated endpoint to verify it is ready to serve traffic. An instance that fails health checks is removed from rotation automatically. The endpoint should verify actual readiness, not just that the process is running. An instance that has started but not yet finished loading configuration or warming up a cache should fail its health check until it is genuinely ready.

TLS Termination

HTTPS is encrypted from the browser to wherever TLS terminates. That point is usually not your application server, and where it is matters.

TLS is almost always terminated at a reverse proxy or load balancer rather than at the application server itself. After that point, traffic travels as plain HTTP over the internal network. This is practical: certificates are managed in one place, application servers are simpler, and offloading TLS reduces CPU overhead on application instances.

The diagram above illustrates a key constraint: any component that needs to inspect or modify HTTP content must be the TLS termination point, or must sit downstream of it. A WAF checking for injection patterns, an API gateway enforcing authorization, or an L7 load balancer routing by path all require access to decrypted HTTP. If the traffic arriving at that component is still an encrypted TLS stream, it cannot see inside it. A traditional network firewall is the exception: it operates on IP addresses and port numbers rather than HTTP content, so it can allow or block HTTPS connections without decrypting them.

One consequence of reverse proxy termination is that the application server no longer sees the original client IP. It receives only the proxy's IP. The reverse proxy injects the real client address as the X-Forwarded-For header. Application code that uses this for rate limiting, geo-blocking, or fraud detection must handle it carefully: a misconfigured proxy that does not strip existing values allows clients to spoof their address by injecting their own X-Forwarded-For before the proxy appends the real one.

Network Zones

Not everything should be reachable from the internet. Placing components in the right zone is one of the most effective security controls available.

In cloud infrastructure, network segmentation is implemented through subnets within a VPC (Virtual Private Cloud). Components are placed in public or private subnets based on whether they need to accept inbound connections from the internet.

Public subnets hold components that accept inbound internet traffic: load balancers, CDN origin connections, and NAT gateways. These have public IP addresses. Private subnets hold application servers and internal services that should only be reachable from inside the network. They have no public IP and are not routable from the internet. The data tier goes further still: databases accept connections only from application servers in the private subnet.

This layering is the network implementation of defense in depth. An attacker who compromises a component in the public subnet still faces firewall boundaries before reaching private instances. A misconfigured load balancer does not automatically expose the database. Compromising the database requires compromising an application server first.

Application servers in private subnets still need outbound internet access for third-party API calls, OS package updates, and similar. A NAT gateway in the public subnet provides this: private instances route outbound traffic through it, but inbound connections from the internet cannot traverse NAT. The asymmetry is intentional.

Service-to-Service Communication

Traffic between services inside your network has a different character from traffic entering it. It still needs its own security and reliability controls.

In a single-service application, the only traffic worth thinking about is inbound. In a multi-service architecture, most of the traffic volume is internal: service A calls service B, which calls a payment provider, which writes to a database. This internal traffic is sometimes called east-west, to distinguish it from north-south traffic that crosses the perimeter.

East-west traffic is often assumed to be safe because it never leaves the private network. That assumption is reasonable in some cases and dangerous in others. An attacker who gains access to one compromised instance inside the perimeter has free movement if there are no controls on internal traffic. Mutual TLS (mTLS) is the standard response: every service presents a certificate, and services only accept connections from other services with valid, trusted certificates. Both ends authenticate each other, and traffic is encrypted at every hop.

A service mesh handles mTLS and reliability concerns centrally, without touching application code. The mesh takes care of certificates, retries, timeouts, and traffic metrics across all services. Whether that infrastructure is worth the operational overhead depends on scale. For smaller deployments, applying mTLS at the application level or enforcing it at the network boundary may be sufficient.

A circuit breaker is a reliability pattern worth understanding regardless of whether you run a mesh. When a downstream service starts failing or responding slowly, a circuit breaker stops sending it new traffic immediately rather than letting requests queue up waiting for timeouts that will never succeed. After a short recovery window it sends a probe request, and if that succeeds normal traffic resumes. This prevents a single degraded service from causing cascading failures across the system.

Persistent Connections

HTTP's request-response model covers most use cases. When the server needs to push data to the browser unprompted, the model needs to change.

Standard HTTP is strictly client-initiated. The browser asks. The server answers. This is sufficient for the vast majority of web application interactions. But some patterns require the server to deliver data to the client without waiting for a request: a live dashboard updating in real time, a collaborative document where other users' edits appear instantly, a notification that arrives as it happens rather than when the user next refreshes.

WebSockets upgrade an HTTP connection to a persistent, full-duplex channel. Either side can send messages at any time. The connection stays open for the session's duration, making WebSockets the right choice when the browser also sends frequent messages to the server: live collaboration, real-time gaming, trading interfaces.

Server-Sent Events (SSE) are simpler: a persistent, one-way stream from server to browser over a normal HTTP connection. The browser cannot push over the same channel, but it can make separate HTTP requests. SSE handles many real-time use cases without the added complexity of WebSockets, and the browser's EventSource API includes built-in reconnection logic.

The infrastructure implications of both are significant. Persistent connections are long-lived, which changes capacity planning fundamentally. A server handling 10,000 short HTTP requests per second and a server holding 10,000 open WebSocket connections have entirely different resource profiles. Load balancers must be configured to support long-lived connections. Many WebSocket problems in production trace back to a proxy closing idle connections on a timeout shorter than the client's reconnection interval. Session affinity is often needed: a client reconnecting to a different backend loses any in-memory state the original instance held, which circles back to the statelessness discussion from the load balancing section.

Networking infrastructure shapes application design in ways that are easy to underestimate. Stateless servers, external session stores, TLS termination strategy, subnet placement: none of these are operational details to sort out at deployment time. They are architectural decisions that become expensive to change once an application is in production.
