Web Application Networking: From Browser to Backend

The infrastructure between a user's browser and the application code: what each layer does, why it exists, and what it means for security, scalability, and application design.

Conceptual overview
~14 min read
Architecture
June 2026

Introduction

Between a browser and application code sits a chain of infrastructure: CDN edges, firewalls, load balancers, API gateways, and more. Most requests pass through several of them before a line of application code runs.

This article covers what those components are and what they do. It starts with the full request path from browser to database, then works through each layer in turn: CDN and WAF at the edge, TLS termination, load balancing, and the security boundaries that divide public from private infrastructure. The second half covers patterns that live closer to the application: how services talk to each other, how the three main models for persistent browser connections differ, and how to think about which components a given application actually needs.

The Request Path

A request rarely travels directly from a browser to an application server. The components along the path each have a specific job, and understanding those jobs is where architectural clarity starts.

A typical production request path starts with DNS: the client looks up the hostname to find the IP address it should connect to. That address often belongs to a CDN edge rather than the origin server. The CDN terminates TLS and serves cached content when it can. Requests that can't be served from cache are inspected by the WAF before being forwarded to the origin. A perimeter firewall controls which connections are allowed through to the internal network. A reverse proxy in the public subnet is the first application-layer component: it routes each request by path, sending page requests to web servers in the private subnet and API traffic to an API gateway that handles authentication and rate limiting before passing requests to a set of load-balanced service instances.

The sections below examine each layer in turn. A comparison of the four components that cause the most confusion (firewall, reverse proxy, load balancer, and API gateway) follows after the individual deep-dives.

At the Edge: CDN and WAF

For most users, geography is the biggest source of latency. A CDN puts the application's front door close to where users actually are.

A CDN (Content Delivery Network) is a global network of servers positioned close to users in major population centers. Originally, the purpose was to serve static files (images, stylesheets, scripts) from a server near the user instead of routing every request to a central origin. A user in Stockholm connecting to a CDN point-of-presence in Stockholm gets a cached response in single-digit milliseconds rather than the 150+ milliseconds a round trip to a US data center would take.

How CDN routing works

When a CDN is configured for a domain, the domain's DNS record is pointed at the CDN's infrastructure. The CDN runs its own authoritative nameservers, which respond to each DNS query with the IP address of the nearest edge node, selected by geographic location or network proximity. The browser ends up connecting to a server a few milliseconds away with no awareness that the origin is elsewhere.

Modern CDNs do considerably more than cache files. For dynamic content that cannot be cached, the CDN terminates TLS at the nearest edge node and routes the remaining connection to the origin over the CDN's own high-capacity backbone, reducing latency even when nothing is served from cache. CDNs also terminate HTTP/2 and HTTP/3 connections from clients, even when the origin only speaks HTTP/1.1. Many providers now offer edge compute (small functions that run at the edge node itself, before the request reaches the origin) as well as on-the-fly image and video optimization such as format conversion and resizing.

The CDN is also the first security layer many applications have. A WAF (Web Application Firewall) positioned at the edge inspects each HTTP request and blocks those that match known attack patterns: SQL injection, XSS payloads, path traversal attempts, and known bot signatures. Blocked requests are dropped before they reach the origin, logged, and answered with a 403. DDoS protection works on the same principle at a larger scale: a volumetric attack large enough to saturate a single data center's network connection is absorbed across the CDN's aggregate capacity in hundreds of edge locations, and the application servers never see the traffic.

Not all WAFs are CDN-integrated. In on-premises and regulated environments, a WAF is commonly deployed as a dedicated appliance (products like F5 and Imperva) sitting inline in the traffic path between the perimeter firewall and the internal network, independent of any CDN.

Protecting the origin

A CDN that provides WAF and DDoS protection is only effective if attackers cannot bypass it by connecting directly to the origin. If the origin's IP address is publicly discoverable, traffic sent directly to it skips the CDN entirely, along with all the security controls at the edge. The fix is to configure the origin's firewall to accept inbound traffic only from the CDN provider's published IP ranges, and to avoid exposing the origin IP in DNS records, error messages, or email headers. Without this, the CDN is security theater.

Load Balancers and Application Design

Horizontal scaling sounds simple: add more servers and distribute traffic. The complication is state stored in process memory.

A load balancer distributes incoming requests across a pool of application instances. When one instance fails its health check, traffic moves to the remaining healthy ones. When demand grows, new instances join the pool. This is horizontal scaling, the standard approach to availability and capacity in modern web applications.

A problem surfaces as soon as user sessions are involved. A user logs in, and server A creates a session record in memory. Their next request goes to server B. Server B has no knowledge of that session. The user appears to be logged out.

The solution is stateless application design. Session data lives in a shared external store (Redis is the most common choice) rather than in process memory. Any server can then handle any request because session state is not tied to a specific instance. The load balancer routes freely, and servers can be added, removed, or restarted without disrupting active sessions.

How requests are distributed across instances is controlled by the balancing algorithm.

Balancing algorithms
  • Round robin cycles through the instance pool in sequence. It works well when requests are similar in cost. Most cloud load balancers use this as the default.
  • Least connections routes each new request to whichever instance currently has the fewest active connections. This adapts better to variable workloads where some requests take much longer than others.
  • IP hashing uses a hash of the client's IP address to select the destination instance, so the same client consistently reaches the same server. It is not a substitute for stateless design: corporate users behind a NAT gateway all share a single IP, routing the entire office to one instance.
  • Weighted balancing assigns each instance a capacity weight, giving more traffic to instances with more resources. Useful when the pool contains machines of different sizes.

Health checks are the second major capability of a load balancer. The load balancer continuously probes each instance on a dedicated endpoint, and any instance that fails is removed from rotation automatically. A liveness check tests whether the process is still running, and a failure triggers a restart. A readiness check tests whether the instance is ready to accept traffic, and a failure pulls it from rotation without restarting it. An instance can be live but not ready: it may have started but not yet connected to its database, loaded required configuration, or completed a cache warmup.

Load balancers operate at either Layer 4 (TCP connections) or Layer 7 (HTTP requests). These layer numbers come from the OSI networking model: Layer 3 is the network layer (IP routing), Layer 4 is the transport layer (TCP and UDP connections), and Layer 7 is the application layer (HTTP, DNS, and other application protocols). A component described as L3/L4 sees IP addresses, ports, and connection state. An L7 component also sees the HTTP content inside those connections.

A Layer 4 load balancer distributes connections based on IP address and port without reading HTTP. A Layer 7 load balancer understands HTTP, which enables it to also perform reverse proxy functions such as routing by hostname or path, and TLS termination. Most web application load balancers today operate at Layer 7. AWS Application Load Balancer, GCP Load Balancing, and Azure Application Gateway all work this way.

TLS Termination

HTTPS is encrypted from the browser to wherever TLS terminates. That point is usually not the application server, and where it is matters.

TLS is almost always terminated at a reverse proxy or load balancer rather than at the application server itself. After that point, traffic travels as plain HTTP over the internal network. This is practical: certificates are managed in one place, application servers are simpler, and offloading TLS reduces CPU overhead on application instances. The trade-off is that internal traffic is unencrypted. If an attacker gains access to the internal network, they can read traffic between the load balancer and application servers. A WAF checking for injection patterns, an API gateway enforcing authorization, or an L7 load balancer routing by path all require access to decrypted HTTP. If the traffic arriving at that component is still an encrypted TLS stream, it cannot see inside it. A traditional network firewall is the exception: it operates on IP addresses and port numbers rather than HTTP content, so it can allow or block HTTPS connections without decrypting them.

Client IP address after termination

One consequence of reverse proxy termination is that the application server no longer sees the original client IP. It receives only the proxy's address. The proxy injects the client's real IP into an X-Forwarded-For header, which accumulates every address in the chain: X-Forwarded-For: client-ip, proxy-ip. Application code that reads the first value in this header is reading client-controlled data. A client can set any value it likes before the proxy appends to it. The correct approach is to trust only the rightmost IP added by a proxy the application explicitly trusts, or to have the proxy strip all incoming X-Forwarded-For headers and set the value fresh from the real connection. Some setups use a dedicated X-Real-IP header that only the proxy can set, which avoids the chain ambiguity entirely.

Firewall

A firewall controls which network connections are permitted. Traditional firewalls operate at the network layer (IP addresses) and transport layer (ports and protocols), allowing or denying traffic based on source address, destination address, port number, and protocol. At this level, a firewall has no knowledge of HTTP or the application's behavior. Modern next-generation firewalls (NGFW) can additionally inspect traffic at the application layer, applying policies based on application type or threat signatures, but the core role is the same: the firewall is a boundary enforcer that decides whether a connection is allowed before any application code runs.

A firewall is how you express rules like "the database accepts connections only from the application servers, not from the internet." If a connection does not match a permitted rule, it is dropped at the boundary.

Reverse Proxy

The name makes more sense once you understand what a forward proxy is. A forward proxy works on behalf of the client: a corporate proxy or VPN sits in front of the user, makes outbound requests on their behalf, and the destination server sees the proxy's address rather than the original client's. A reverse proxy is the mirror image. It works on behalf of the server. Clients connect to the proxy's address, and the actual backend servers are not directly reachable from outside.

A reverse proxy sits in front of one or more backends, accepting connections on their behalf and forwarding each request onwards. The value of this arrangement is that cross-cutting concerns can be handled at the proxy rather than repeated in every backend: TLS can be terminated there, responses can be cached and compressed, headers can be rewritten, and requests can be routed to entirely different applications based on the URL path. That last point is worth making concrete: a single domain can send /login to an authentication service and /my-account to a profile service, with the proxy directing each request to the right backend. The client sees one address. The proxy decides what runs behind it. These things can also be done within application code, but a reverse proxy lets you centralize them for all backends without changing the applications themselves.

Nginx and Caddy are the most common standalone reverse proxies. Every load balancer, CDN, and API gateway also behaves as a reverse proxy in the sense that it intercepts connections and forwards them. The term names a behavior more than a specific product type.

API Gateway

An API gateway is a reverse proxy with application-level policies built in. It sits in front of backend services and enforces cross-cutting concerns centrally: authentication and authorization, rate limiting, routing by API version or path, analytics, and developer-facing features like API key management. Where a general-purpose reverse proxy is neutral about what flows through it, an API gateway is opinionated about API traffic specifically.

The practical benefit is that these concerns are handled once at the gateway rather than duplicated across every service. Individual services receive already-authenticated requests and can focus on domain logic.

Why these overlap in practice

An AWS Application Load Balancer is both a load balancer and a reverse proxy. An Nginx instance can serve as a reverse proxy, load balancer, and static file server simultaneously. The distinctions above are conceptual: they describe a primary job and what the component needs to see to do it. When evaluating a product, ask which of these jobs it covers and whether it covers them well.

Network Zones

Not everything should be reachable from the internet. Placing components in the right zone is one of the most effective security controls available.

In cloud infrastructure, network segmentation is implemented through subnets within a VPC (Virtual Private Cloud). Components are placed in public or private subnets based on whether they need to accept inbound connections from the internet.

Public subnets hold components that accept inbound internet traffic: load balancers, CDN origin connections, and NAT gateways. These have public IP addresses. Private subnets hold application servers and internal services that should only be reachable from inside the network. They have no public IP and are not routable from the internet. The data tier goes further still: databases accept connections only from application servers in the private subnet.

In traditional on-premises architecture, this intermediate zone between the internet and the internal network was called a DMZ (demilitarized zone). A DMZ sits between two firewalls: one facing the internet, one facing the internal network. Public-facing servers such as web servers and reverse proxies live in the DMZ, isolated from internal systems even if compromised. The cloud VPC model achieves the same thing with public and private subnets and security group rules, but the underlying principle is identical: public-facing components are separated from internal ones by a firewall boundary, and no direct path from the internet to the internal network exists.

This layering is the network implementation of defense in depth. An attacker who compromises a component in the public subnet still faces firewall boundaries before reaching private instances. A misconfigured load balancer does not automatically expose the database. Compromising the database requires compromising an application server first.

Application servers in private subnets still need outbound internet access for third-party API calls, OS package updates, and similar. A NAT gateway in the public subnet provides this: private instances route outbound traffic through it, but inbound connections from the internet cannot traverse NAT. The asymmetry is intentional.

Service-to-Service Communication

Traffic between services inside the network has a different character from traffic entering it. It still needs its own security and reliability controls.

In a single-service application, the only traffic worth thinking about is inbound. In a multi-service architecture, most of the traffic volume is internal: service A calls service B, which calls a payment provider, which writes to a database. This internal traffic is sometimes called east-west, to distinguish it from north-south traffic that crosses the perimeter.

East-west traffic is often assumed to be safe because it never leaves the private network. That assumption is reasonable in some cases and dangerous in others. An attacker who gains access to one compromised instance inside the perimeter has free movement if there are no controls on internal traffic. Mutual TLS (mTLS) is the standard response: every service presents a certificate, and services only accept connections from other services with valid, trusted certificates. Both ends authenticate each other, and traffic is encrypted at every hop.

A service mesh handles mTLS and reliability concerns centrally, without touching application code. The mesh takes care of certificates, retries, timeouts, and traffic metrics across all services. The traditional approach injects a sidecar proxy container alongside each service instance to intercept its traffic. A newer model uses eBPF to enforce the same policies at the Linux kernel level, with no sidecar process at all. Whether either model is worth the operational overhead depends on scale. For smaller deployments, applying mTLS at the application level or enforcing it at the network boundary may be sufficient.

Circuit breaker

A circuit breaker is a reliability pattern worth understanding regardless of whether you run a mesh. When a downstream service starts failing or responding slowly, a circuit breaker stops sending it new traffic immediately rather than letting requests queue up waiting for timeouts that will never succeed. After a short recovery window it sends a probe request, and if that succeeds normal traffic resumes. This prevents a single degraded service from causing cascading failures across the system.

Persistent Connections

HTTP's request-response model covers most use cases. When the server needs to push data to the browser unprompted, the model needs to change.

Standard HTTP is strictly client-initiated. The browser asks. The server answers. This is sufficient for the vast majority of web application interactions. But some patterns require the server to deliver data to the client without waiting for a request: a live dashboard updating in real time, a collaborative document where other users' edits appear instantly, a notification that arrives as it happens rather than when the user next refreshes.

WebSockets upgrade an HTTP connection to a persistent, full-duplex channel. Either side can send messages at any time. The connection stays open for the session's duration, making WebSockets the right choice when the browser also sends frequent messages to the server: live collaboration, real-time gaming, trading interfaces.

Server-Sent Events (SSE) are simpler: a persistent, one-way stream from server to browser over a normal HTTP connection. The browser cannot push over the same channel, but it can make separate HTTP requests. SSE handles many real-time use cases without the added complexity of WebSockets, and the browser's EventSource API includes built-in reconnection logic.

The infrastructure implications of both are significant. Persistent connections are long-lived, which changes capacity planning fundamentally. A server handling 10,000 short HTTP requests per second and a server holding 10,000 open WebSocket connections have entirely different resource profiles. Load balancers must be configured to support long-lived connections. Many WebSocket problems in production trace back to a proxy closing idle connections on a timeout shorter than the client's reconnection interval. The WebSocket protocol includes ping/pong frames for keepalives: the server sends a ping on a regular interval, the client responds with a pong, and the proxy sees traffic and leaves the connection open. Configuring the proxy's idle timeout to exceed the ping interval resolves most of these issues. Session affinity is often needed: a client reconnecting to a different backend loses any in-memory state the original instance held, which circles back to the statelessness discussion from the load balancing section.

Deciding What You Need

These layers do not all appear in every architecture. The right set depends on the problems you actually face, not on what a complete diagram looks like.

A monolithic application with moderate traffic often needs nothing more than Nginx or Caddy acting as a reverse proxy in front of the application: it terminates TLS, compresses responses, and keeps the application server's IP off the public internet. That is enough for many deployments.

The moment you need multiple instances of the same application, a load balancer becomes necessary. The trigger is less about raw traffic volume than about resilience: even at modest load, two instances behind a load balancer means the application survives a single server failure without going down.

An API gateway becomes valuable when authentication, rate limiting, and API versioning turn into cross-cutting concerns shared by multiple services. In a monolith, those concerns live in the application code. In a system with independent services, each team implementing the same authentication logic produces fragility and inconsistency. The gateway enforces these policies once at the entry point, and services downstream receive requests that have already been authenticated and validated.

Most production systems at scale end up combining layers rather than choosing one. A CDN sits at the edge absorbing cache hits and DDoS traffic. An API gateway handles authentication and routing. Load balancers distribute requests across service instances. In some deployments, a lightweight reverse proxy runs alongside each service for internal TLS and compression. None of these layers is redundant with the others because each one handles a category of problem the others cannot. The layers cooperate rather than compete, and the architecture you need is the one with layers up to and including the problems you actually have.

Key Takeaways

A firewall controls network access, not application behavior. It allows or denies connections based on IP address, port, and protocol before any HTTP is parsed.

A load balancer's primary job is distributing traffic across a pool of instances for availability and capacity. It spreads requests so no single server becomes a bottleneck, and when an instance fails its health check the load balancer stops routing to it automatically.

A reverse proxy handles header manipulation and path-based routing to different applications. It also handles TLS termination, caching, and compression.

An API gateway is a reverse proxy with application-level policy built in. Authentication, rate limiting, routing by API version, and usage tracking are enforced centrally at the gateway.

A CDN terminates TLS at the edge, close to users. Cache hits never reach the origin. WAF inspection and DDoS absorption happen here, across aggregate capacity that no single data center can match.

Network zones implement defense in depth. Internet-facing components live in the public subnet. Application servers live in a private subnet with no public IP. Each zone boundary is a firewall rule.
