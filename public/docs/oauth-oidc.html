The Engineer's Guide to OAuth 2.0 & OIDC

Two specifications quietly run the login button on nearly every app you use. Here's what's actually happening behind it — the actors, the tokens, the endpoints, and the attacks they're designed to stop.

A field guide
~22 min read
For developers building real auth

If you've ever clicked "Sign in with Google" and wondered what happens between that click and landing back on the app, logged in, you've already met OAuth 2.0 and OpenID Connect. They're two of the most widely deployed specifications on the internet, and also two of the most widely misunderstood — partly because they were designed by committee over more than a decade, and partly because most of us learn them by copy-pasting a working example rather than reading the RFCs. This guide walks through both specs from the ground up: who the actors are, what each token is for, how the most common flow actually works end to end, and which mistakes turn a textbook-correct implementation into a security hole. By the end you should be able to read an OAuth library's source code and know exactly what it's doing and why.

Roles & Actors

Every OAuth conversation, no matter how complex, is really just four parties talking to each other in a fixed pattern.

Before any of the redirects and tokens make sense, it helps to fix the cast of characters firmly in your head, because the entire specification is written in terms of these four roles, and almost every security property in OAuth exists to keep one of them from impersonating or deceiving another.

Resource Owner
The User

The human (or in machine-to-machine cases, the system) who actually owns the protected data. The resource owner is the one who decides whether to grant or deny access, and critically, they authenticate directly with the authorization server — never with the client app. This is the whole point of OAuth: the app asking for access never sees the resource owner's password.

Client
Your Application

The application requesting access on the user's behalf — a web app, a single-page app, a mobile app, a CLI tool, or a background service. The client receives tokens once the user has granted access, but it is never supposed to see the user's credentials at any point. How much the spec trusts a given client depends heavily on whether it's "public" or "confidential," a distinction covered later on.

Authorization Server
The Auth Server (IdP)

The system that authenticates the user, captures their consent, and issues tokens. In the identity world this is usually called an Identity Provider, or IdP. Auth0, Okta, Keycloak, Google Identity, and Azure AD/Entra ID are all examples. This is the component most teams choose to outsource rather than build, because getting it wrong is expensive.

Resource Server
The API

The server that actually hosts the protected data — the Google Drive API, a payments API, or your own backend. Its only real job in this story is to accept an access token on incoming requests, validate it, and decide whether the scopes attached to that token permit the requested operation.

It's worth sitting with the distinction between the last two roles for a moment, because in small setups they often live on the same physical server and that can blur the conceptual line. The authorization server's entire responsibility is issuing tokens; the resource server's entire responsibility is consuming them. A single company might run both, or might use a third-party authorization server (like Auth0) in front of their own resource server (their own API) — both architectures are completely normal.

Authorization vs Authentication

OAuth 2.0 is, at its core, an authorization framework — it exists to answer the question "what is this app allowed to do on the user's behalf?" Read the original RFC and you'll notice it never actually defines who the user is; identity simply isn't OAuth's job.

OIDC was built specifically to close that gap. It layers authentication on top of OAuth's authorization mechanics, answering "who is this user, exactly?" by introducing a new artifact: the ID token. This is also why you'll sometimes hear OIDC described as "OAuth 2.0 plus an identity layer" rather than a competing standard — it reuses OAuth's flows almost entirely and just adds a few extra pieces.

Tokens

Three tokens, three jobs. Confusing them is the single most common source of OAuth bugs.

If there's one mental model worth memorizing from this entire guide, it's this: the access token is for machines, the ID token is for your app, and the refresh token is for staying logged in quietly. Mixing these up — for instance, sending an ID token to an API, or treating an access token as proof of identity — is responsible for a surprising share of real-world OAuth bugs.

Access Token
API Credential

The credential you attach to every API request, typically as Authorization: Bearer <token>. It's intentionally short-lived — usually minutes to a couple of hours — so that if one leaks, the damage window is small. It may be a JWT that the resource server can verify locally, or an opaque string that requires a call back to the authorization server to validate. Either way, its only job is proving the bearer has permission for a given set of scopes.

ID Token
Identity Proof (OIDC)

Always a JWT, and always meant for your application to consume directly rather than forward anywhere. It carries claims about who just authenticated — a stable subject identifier, maybe an email or name — and its presence is what turns a plain OAuth exchange into an OIDC login. A useful rule of thumb: if you're tempted to send a token to an API, it should be the access token, never the ID token.

Refresh Token
Silent Re-auth

A long-lived credential — days, weeks, sometimes months — that the client exchanges for a fresh access token once the old one expires, without bothering the user to log in again. Because it lives so much longer than the other tokens, it's also the most sensitive one to leak, and the spec treats it accordingly: it should never be sent to a resource server, and it should never end up in a place JavaScript can read it.

Token Lifetimes (relative)

Lifetimes vary by provider, but the relative ordering below is close to universal, and it's a useful intuition to carry around: the shorter-lived a token is, the more freely it can be passed around; the longer-lived it is, the more carefully it needs to be guarded.

JWT vs Opaque Access Tokens

One detail that trips people up: the spec never actually mandates a token format. An access token can be a self-contained JWT that any resource server can verify on its own using a public key, or it can be a short, meaningless-looking opaque string that only the authorization server knows how to interpret. Opaque tokens require the resource server to call back to the authorization server's introspection endpoint on every request to check validity — slower, but it means a token can be instantly revoked. JWTs are faster to validate locally but, by nature, can't be revoked before they expire unless you build a separate denylist. Many production systems use JWTs for access tokens precisely because that local-validation speed matters at API scale, while accepting the tradeoff that revocation isn't instant.

Don't decode access tokens in your client code

Even when an access token happens to be a JWT, treat it as opaque from the client's perspective. Its format and contents are a contract between the authorization server and the resource server, not something your frontend should depend on or parse. Use the ID token for identity information instead.

Scopes

Scopes are how OAuth implements the principle of least privilege — they let a client ask for exactly what it needs, nothing more.

A scope is simply a string that names a unit of access. When your app sends the user to the authorization server, it lists the scopes it wants, and the consent screen the user sees is essentially a human-readable translation of that list — "this app wants to see your name and email" is the scope profile email rendered for a person rather than a machine. Once granted, the requested scopes get baked into the access token, and it's the resource server's job to check, on every request, that the token actually carries the scope required for that operation.

OIDC Standard Scopes

OIDC defines a small set of standard scopes so that identity providers don't all invent their own conventions for "give me the user's email." These are worth memorizing since you'll see them in nearly every integration:

openid
The scope that turns a plain OAuth request into an OIDC request. Required to receive an ID token at all — without it, you just get OAuth's access token and nothing more.
profile
Name, picture, website, locale, birthdate, and similar non-sensitive profile fields.
email
The user's email address along with whether it has been verified.
address
The user's physical mailing address, when the provider stores one.
phone
Phone number and its verification status.
offline_access
Tells the server you'd like a refresh token back, so the user doesn't need to log in again every time their access token expires.

Beyond these standard ones, real applications almost always define their own custom scopes shaped around their own API — things like read:orders or admin:users. Designing good scopes is really an exercise in API design: think in terms of the operations a client should be allowed to perform, then name a scope for each meaningful grouping of those operations rather than handing out blanket access.

Scopes are not a substitute for fine-grained authorization

Scopes tell you what categories of action a token is allowed to attempt — they're a coarse-grained gate. They generally don't express "can this user edit this specific document." That kind of fine-grained, resource-level authorization is usually handled separately, inside your application logic, after the scope check has already passed.

Grant Types

A grant type is just a recipe — the specific sequence of requests a client follows to walk away with tokens.

OAuth defines several of these recipes because "getting a token" looks completely different depending on what kind of client you're building. A web app with a logged-in human in front of it has very different constraints than a cron job with no user at all, or a smart TV with no keyboard. Picking the wrong grant type for your situation is one of the most common OAuth mistakes, so it's worth understanding what each one was actually designed for before reaching for it.

Recommended for most apps

Authorization Code + PKCE

This is the workhorse flow, and almost certainly the one you should reach for unless you have a specific reason not to. The user is redirected away to the authorization server, where they authenticate and consent, and is then redirected back carrying a short-lived authorization code rather than a token. That code is then traded for actual tokens through a separate, back-channel request — one that never touches the browser. PKCE sits alongside this exchange specifically to stop that authorization code from being usable by anyone other than the client that requested it, even if it gets intercepted along the way.

Use when: you're building a web app with a backend, a single-page app, or a mobile app — essentially any flow where a real human is sitting in front of a browser or device.

Machine-to-machine

Client Credentials

There's no user anywhere in this flow — it's the client authenticating as itself, using its own client_id and client_secret, to get an access token that represents the application's own identity rather than any person's. It's the simplest grant in the spec because there's no redirect, no consent screen, and no browser involved at all; it's a single back-channel request.

Use when: you have background jobs, microservices, or daemons that need to call an API with no user context attached — a nightly batch job pulling data from a partner API is the textbook case.

// POST /token (back-channel)
grant_type=client_credentials
&client_id=my-service
&client_secret=••••••••
&scope=read:reports
Input-constrained devices

Device Authorization Grant

Designed for devices that have no convenient way to handle a browser redirect — think smart TVs, CLI tools, or IoT devices with no keyboard. Instead of opening a browser on the device itself, it displays a short code and a URL. The user picks up their phone or laptop, visits that URL, types in the code, and authenticates there instead, while the original device quietly polls the token endpoint in the background until that approval comes through.

Use when: you're building a CLI tool (this is exactly how gh auth login works), a smart TV app, or any other device without a practical way to render a full browser-based login screen.

Deprecated

Implicit Flow

This was OAuth's original answer for single-page apps, back before PKCE existed: rather than returning a code that gets exchanged for tokens, the authorization server returned the access token directly in the URL fragment, as in #access_token=.... It seemed reasonable at the time, but tokens sitting in a URL turn out to leak in all sorts of mundane ways — browser history, referrer headers sent to third-party scripts, and server access logs all end up holding a live credential.

Do not use

Use Authorization Code + PKCE for SPAs instead — it solves the same problem without exposing tokens in the URL. The implicit flow has been formally dropped from the OAuth 2.1 draft specification.

Avoid

Resource Owner Password Credentials

In this grant, the client itself collects the user's username and password through its own form and sends them straight to the token endpoint. It quietly defeats the entire premise of OAuth, which is that the client app should never see the user's actual credentials. It also makes multi-factor authentication and social login effectively impossible to support, since the auth server never gets to show its own login UI.

Only for legacy migration

About the only legitimate use case left is a temporary bridge while migrating an existing system that already stores user passwords directly. For any new system, Authorization Code + PKCE is the right choice.

Grant Type Comparison

Laid side by side, the deciding factors usually come down to two questions: is a human present to authenticate, and can the client be trusted with a secret? Answer those two and the right grant type tends to fall out naturally.

Grant Type User present? Client secret needed? Recommended?
Auth Code + PKCE Yes No (PKCE replaces it) Yes
Client Credentials No Yes For M2M
Device Code Yes (on another device) No For devices
Implicit Yes No Deprecated
ROPC Yes (password exposed) Sometimes Avoid

Endpoints

Every authorization server exposes the same small handful of URLs. Learn these four and you can read any OAuth integration.

One of the nicer things about OAuth and OIDC is that despite the dozens of providers out there, they all converge on the same basic set of endpoints, doing the same basic jobs. Once you've worked with one provider's /authorize and /token endpoints, you've effectively worked with all of them — the parameter names and behavior are remarkably consistent across vendors. Click each one below to expand it.

GET /.well-known/openid-configuration Discovery document ▶

This is usually the very first request your application makes, and it's worth starting every integration here. It returns a single JSON document listing the URLs of every other endpoint, the scopes and claims the provider supports, the signing algorithms it uses, and a number of other capability flags. Fetch it once on startup, cache the result, and resolve every other endpoint from it rather than hardcoding URLs — providers do occasionally restructure their infrastructure, and discovery is what insulates your app from that.

// Returned JSON includes:
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "userinfo_endpoint": "https://auth.example.com/userinfo",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "scopes_supported": ["openid", "profile", "email"],
  "id_token_signing_alg_values_supported": ["RS256"]
}
GET /authorize Authorization endpoint — browser redirect ▶

This is the endpoint the user's browser actually navigates to — never something your code calls with fetch(). It needs to be a genuine, full browser navigation because the authorization server has to render its own login UI, set its own cookies, and possibly redirect through a federated identity provider of its own. Trying to call it programmatically defeats the entire security model, since the whole point is that the user is interacting directly with a server they (hopefully) trust, on a domain the client app can't tamper with.

Key Parameters

  • client_idIdentifies your app to the auth server.required
  • redirect_uriWhere to send the user after auth. Must match an allow-list on the server.required
  • response_typeAlways code for auth code flow.required
  • scopeSpace-separated scopes. Include openid for OIDC.required
  • stateRandom value to prevent CSRF. Must be verified when the callback arrives.required
  • code_challengeSHA-256 hash of your PKCE code verifier.required (PKCE)
  • code_challenge_methodAlways S256. Never use plain.required (PKCE)
  • nonceRandom value embedded in the ID token to prevent replay attacks.optional (OIDC)
  • promptnone (silent), login (force re-login), consent (force re-consent), select_account.optional
  • max_ageMax seconds since last user authentication. Forces re-auth if exceeded.optional
POST /token Token endpoint — back-channel fetch ▶

Where the actual tokens get issued — by exchanging an authorization code for tokens after a login, or later by exchanging a refresh token for a fresh access token. Crucially, this call happens server-to-server, in the back channel, never from code running in the browser. Keeping it server-side means the response — including any client secret used to authenticate the request — never passes through the user's browser, where it could end up in history, dev tools, or a malicious extension's view.

  • grant_typeauthorization_code, refresh_token, or client_credentials.required
  • codeThe authorization code from the redirect callback.required (code flow)
  • redirect_uriMust exactly match what was sent to /authorize.required (code flow)
  • code_verifierThe original random PKCE value. Server hashes and compares to stored challenge.required (PKCE)
  • client_idYour app's identifier.required
  • client_secretSecret for confidential clients. Never include in browser code.confidential only
  • refresh_tokenUsed when grant_type=refresh_token.refresh only
GET /.well-known/jwks.json JSON Web Key Set — public keys for JWT verification ▶

The authorization server signs JWTs with a private key it never shares — but it publishes the matching public keys here, in a standard format called a JSON Web Key Set. Your resource server fetches this once and caches it, then uses it to verify the signature on every JWT it sees, locally, with no network call required per request. Each key carries a kid (key ID), and that's how a verifier matches an incoming token to the right public key — it's also how providers can rotate signing keys over time without breaking already-issued tokens.

{
  "keys": [{
    "kty": "RSA",
    "kid": "key-id-2024",    // match to token header's "kid"
    "use": "sig",
    "alg": "RS256",
    "n": "...base64url modulus...",
    "e": "AQAB"
  }]
}
POST /revoke Revocation endpoint — back-channel fetch ▶

The counterpart to issuing tokens is being able to take them back, and that's what this endpoint is for. Call it with a refresh token (or, on some providers, an access token) when a user logs out, and the authorization server invalidates it immediately rather than waiting for it to expire naturally. This matters most for refresh tokens, since they otherwise stay valid for a long time — a proper "log out everywhere" feature is really just a call to this endpoint.

PKCE — Proof Key for Code Exchange

A clever cryptographic handshake that turns a stealable authorization code into something useless to anyone but you.

PKCE — pronounced "pixie" — exists to solve a very specific problem: how do you prove that whoever is redeeming an authorization code is the exact same client that originally requested it, when that client has no secret it can use to prove its identity? The trick is to generate a secret on the fly, for that one login attempt only, and only ever reveal it at the very last step.

1
Generate code_verifier

A cryptographically random 43–128 character string. Stays in the client. Never sent to the auth server directly.

↓
2
Hash it → code_challenge

code_challenge = BASE64URL(SHA256(code_verifier))
This hash is sent to the auth server in the /authorize request.

↓
3
Auth server stores the challenge

It ties the code_challenge to the authorization code it issues. The challenge is a commitment — you can't back-compute the verifier from it.

↓
4
Token exchange: send the verifier

POST to /token with code_verifier. The server hashes it and checks it matches the stored challenge. If not, it rejects the request.

Notice the asymmetry baked into this design: the hash of the secret travels in the open, in a URL, where it could plausibly be observed. The secret itself only ever appears once, in the back-channel request to the token endpoint, which is a far more controlled environment. That ordering is the whole trick — by the time anyone could intercept the code from step three, the verifier needed to redeem it was never exposed alongside it.

Why this stops code theft

An attacker who intercepts the code in the redirect URL doesn't have the code_verifier — it was never in a URL. They'd need to break SHA-256 to derive it from the challenge. That's computationally infeasible.

It's also worth knowing that while PKCE was originally specified as a mitigation for public clients — apps that can't hold a secret — modern guidance, including the emerging OAuth 2.1 spec, recommends using it everywhere, even for confidential server-side clients that do have a client secret. It's cheap to implement and closes off an entire class of attack, so there's little reason not to use it universally.

Client Types

Not all OAuth clients can be trusted equally — and the spec splits them into two categories precisely so it can treat them differently.

The single question that determines which category a client falls into is simple: can this application keep a secret from the end user it's running on, or in front of? A server-side app's code runs somewhere the user can never inspect, so it can hold a real secret. Anything running on the user's own device or in their own browser — a JavaScript bundle, a native mobile binary, a CLI tool — can always be decompiled, inspected, or read directly, so it cannot.

Confidential Client
Can keep a secret

Server-side apps where code runs in a trusted environment. Can safely store a client_secret. Examples: Express, Django, Rails, Spring Boot apps.

Public Client
Cannot keep a secret

Code runs on the user's device — they could inspect it. Cannot use a client secret. Use PKCE instead. Examples: SPAs, React/Vue apps, mobile apps, CLIs.

This distinction is also why PKCE exists at all: it was designed to give public clients a way to prove their requests are legitimate without needing a secret they're structurally incapable of protecting. A confidential client authenticates itself to the token endpoint with its client secret; a public client authenticates the specific transaction with PKCE instead.

Client secrets in frontend code

If you embed a client_secret in a JavaScript bundle, it's not secret — anyone can find it in DevTools. Public clients must use PKCE, and no client secret.

State Parameter & CSRF

A single random string is all that stands between your login flow and a class of attack that links the wrong account to the wrong session.

The state parameter looks almost too simple to matter — it's just an opaque random value you generate, send along with the authorization request, and check still matches when the user comes back. But that simple round trip is exactly what defeats a CSRF attack against the OAuth flow itself: it proves that the browser completing the login is the same browser that initiated it.

// Before redirect: generate and store
const state = crypto.randomUUID();
sessionStorage.setItem('oauth_state', state);
// Include in /authorize URL

// In callback handler: verify
const returnedState = new URLSearchParams(location.search).get('state');
if (returnedState !== sessionStorage.getItem('oauth_state')) {
  throw new Error('CSRF attack detected — state mismatch');
}
sessionStorage.removeItem('oauth_state'); // use once
Attack without state

Without state, an attacker could trick a victim into completing an OAuth flow that logs them into the attacker's account, then steal their session actions (payment, data entry). Always verify state on every callback.

That last scenario is worth spelling out, because it's not always obvious why it's dangerous: imagine an attacker starts an OAuth login flow themselves, captures the resulting authorization code, and then tricks a victim into visiting the callback URL with the attacker's code attached. If the app never checks state, it happily logs the victim in as the attacker — and anything the victim subsequently does, like linking a payment method or uploading a sensitive file, ends up associated with the attacker's account instead of their own. Verifying state, generated fresh per attempt and tied to the user's own browser session, closes that gap entirely.

What OIDC Adds to OAuth 2.0

OIDC doesn't replace anything in OAuth — it's a small, deliberate set of additions layered on top.

If you already understand OAuth's authorization code flow, you essentially already understand OIDC's login flow too — the redirects, the back-channel token exchange, PKCE, the state parameter, all of it carries over unchanged. What OIDC contributes is a handful of new, standardized pieces bolted onto that same foundation, all aimed at one goal: letting the client walk away knowing exactly who just logged in, in a way that's portable across providers. You opt into all of it simply by including the openid scope in your authorization request.

ID Token
A JWT about the user

Returned alongside the access token. Contains who the user is: their subject identifier, email, name. Your app reads this — it does not send it to APIs.

UserInfo Endpoint
Fetch more claims

An authenticated GET endpoint that returns user profile data. Use it when you need claims that aren't in the ID token, or want fresh data.

Nonce
Replay protection

A random value sent in /authorize, embedded in the ID token. Your app verifies it matches, preventing an old token from being replayed.

Discovery
Auto-configuration

OIDC standardizes the /.well-known/openid-configuration endpoint so clients can auto-discover all endpoints and capabilities without hardcoding URLs.

It's this last point — standardization — that's arguably OIDC's biggest practical contribution. Plain OAuth 2.0 leaves a lot of room for interpretation: providers were free to invent their own ways of representing user profile data, their own discovery mechanisms, their own conventions for everything beyond the bare authorization mechanics. OIDC pins all of that down, which is exactly why a single OIDC client library can talk to Google, Microsoft, Okta, and a dozen other providers with barely any provider-specific code.

JWT & ID Token Anatomy

A JWT is just three pieces of JSON, base64-encoded and glued together — but each piece carries a very specific job.

JSON Web Tokens look intimidating as a long string of seemingly random characters, but they're built from nothing more exotic than JSON. Split on the two dots and you get three Base64URL-encoded segments: a header describing how the token is signed, a payload containing the actual claims, and a signature that lets anyone holding the right public key verify the first two segments haven't been tampered with since they were issued.   "aud": "my-app",                 // Audience — must match your client_id
  "exp": 1735689600,              // Expiry (Unix timestamp) — reject if in the past
  "iat": 1735686000,              // Issued At — when the token was created

  "name": "Jane Doe"              // From 'profile' scope
}
Signature
// RSA-SHA256 signature over (base64url(header) + "." + base64url(payload))
// Signed with the auth server's PRIVATE key.
// Verified with the auth server's PUBLIC key from /jwks.json.
// If ANY byte of header or payload changes, signature verification fails.
// This makes JWTs tamper-evident without a database lookup.

The header and payload are only Base64URL-encoded, not encrypted — anyone can decode them and read the claims inside without any key at all, which is why a JWT is described as tamper-evident rather than confidential. The signature is what actually does the protective work: it's computed over the exact bytes of the encoded header and payload, so changing even a single character anywhere in either one — say, swapping "sub": "user_123" for someone else's ID — invalidates the signature and any honest verifier will reject the token outright.

ID Token Validation Checklist

Decoding a JWT and trusting its contents are two very different things, and skipping validation is one of the most common ways teams accidentally build an authentication bypass. A library can do the cryptographic verification for you, but it still needs to be told what to check — every item below should be confirmed before you treat the claims inside as true.

Always validate these — never trust a JWT you didn't verify

✔ iss matches your expected auth server
✔ aud contains your client_id
✔ exp is in the future
✔ iat is not too far in the past
✔ nonce matches what you sent (if used)
✔ Signature verified with the correct public key from JWKS
✔ alg header matches an algorithm you accept (reject none!)

Claims

Claims are the actual statements a token makes — and OIDC standardizes the most important ones so providers don't reinvent them.

Every key-value pair inside a JWT's payload is technically a "claim" — the spec borrows the term from the broader world of identity assertions, where a claim is simply a statement one party makes about another. OIDC defines a baseline set that any compliant provider should expose consistently, which is exactly what lets you write one piece of code that pulls a user's name and email regardless of whether they signed in with Google, Okta, or a custom IdP.

sub
Unique identifier for the user at this issuer. Use as your primary user key — never email (email can change).
iss
Issuer URL. The auth server that issued this token.
aud
Audience. The client(s) this token is intended for.
exp
Expiration time (Unix timestamp). Reject tokens past this time.
iat
Issued At. When the token was created.
email
User's email. Check email_verified before trusting it.
email_verified
Boolean. Whether the auth server has verified the email.
name
Full display name.
picture
URL to profile photo.
locale
BCP 47 language tag, e.g. en-US.
nonce
Replay protection value — verify it matches what you sent.
at_hash
Hash of the access token. Binds the ID token to a specific access token.

The sub claim deserves a special callout, because it's one of the most common sources of subtle bugs in real systems: it's tempting to use a user's email address as their primary key in your own database, since it feels stable and human-readable, but email addresses change, get recycled, or get re-verified under a different identity over time. The sub claim is specifically designed to be a permanent, opaque identifier for one user at one issuer, and that's what you should be storing as your foreign key, with email treated as just another mutable profile field.

UserInfo Endpoint

The ID token is a snapshot taken at login. Sometimes you need to know what's true right now instead.

An OIDC-specified endpoint returning fresh profile data for the currently authenticated user. Call it with a Bearer access token (must include the openid scope). It exists as a separate call rather than just stuffing everything into the ID token because ID tokens are meant to stay reasonably small and are only minted at login time, while profile data — a changed display name, a newly uploaded avatar — can drift over the course of a long session.

// Frontend or backend fetch — requires a valid access token
const res = await fetch('https://auth.example.com/userinfo', {
  headers: { 'Authorization': `Bearer ${accessToken}` }
});
const user = await res.json();
// { sub, email, name, picture, ... }
ID token vs UserInfo

The ID token is a snapshot at login time. The UserInfo endpoint returns the current state. If you show the user's avatar and it might change, call UserInfo. For simply establishing identity at login, the ID token is enough.

Token Storage

Where you put a token after you receive it matters just as much as how you got it in the first place.

A surprising amount of real-world OAuth insecurity has nothing to do with the protocol flow itself and everything to do with what happens after tokens land in the browser. The honest answer to "where should I store this?" is "it depends on what kind of attack you're most worried about" — every storage location trades off resistance to one attack class against resistance to another, so it's worth understanding the table below as a set of tradeoffs rather than a single right answer.

LocationXSS Safe?CSRF Safe?Verdict
localStorage No — any JS can read it Yes Avoid for tokens
sessionStorage No — any JS can read it Yes Acceptable for PKCE state only
HttpOnly Cookie Yes — JS can't read it No — requires CSRF tokens Best for session tokens
In-memory (JS var) Yes — lost on tab close Yes Good for access tokens in SPAs
Server session Yes Yes (with SameSite cookies) Best overall

The pattern to notice is that localStorage and sessionStorage are convenient precisely because any JavaScript on the page can read and write them — and that's also exactly why they're dangerous, because any JavaScript on the page includes a malicious script injected through an XSS vulnerability anywhere in your app's dependency tree. HttpOnly cookies flip that tradeoff: the browser will send them automatically with requests, but no script, malicious or otherwise, can ever read their contents directly.

Best practice: BFF pattern

Use a Backend for Frontend (BFF) — your server handles the OAuth flow and stores tokens. The browser only gets a session cookie. Tokens never touch the browser's storage, eliminating the entire XSS token theft surface.

Common Attacks & Mitigations

Most OAuth vulnerabilities aren't flaws in the specification — they're implementations that quietly skip a step the spec assumes you'll do.

It's worth approaching this section as a list of "what happens if you skip the boring part," because that's genuinely what most of these come down to. PKCE, state validation, careful token storage, and signature verification can all feel like ceremony when you're just trying to get a login button working — but each one exists because someone, somewhere, shipped a version without it and got burned.

ATTACK Authorization Code Interception ▶

An attacker intercepts the code in the redirect URI (via referrer headers, browser history, or a malicious app registering the same custom URI scheme).

Mitigation: PKCE

PKCE binds the code to the verifier. An intercepted code is useless without the verifier, which was never transmitted in the vulnerable channel.

ATTACK CSRF / Open Redirect ▶

Attacker initiates an OAuth flow and tricks the victim into completing it, linking the victim's identity to the attacker's account.

Mitigation: state parameter

Validate state on every callback. The attacker can't forge a valid state value because it's stored in the victim's browser session.

ATTACK Token Theft via XSS ▶

A Cross-Site Scripting vulnerability lets an attacker run JavaScript that reads tokens from localStorage or sessionStorage and exfiltrates them.

Mitigation: HttpOnly cookies + BFF

Store tokens server-side. Issue the browser an HttpOnly session cookie — JS cannot access it regardless of XSS. Combine with SameSite=Strict or SameSite=Lax for CSRF protection.

ATTACK JWT Algorithm Confusion (alg:none) ▶

An attacker crafts a token with "alg":"none" and no signature. Naive verifiers that trust the alg header accept it as valid.

Mitigation: allowlist algorithms

Never use the alg field in the token header to decide how to verify — always specify the expected algorithm in your verifier code. Reject none always. Prefer RS256 over HS256 for multi-party scenarios.

ATTACK Open Redirect via redirect_uri ▶

If an authorization server validates redirect_uri loosely — say, only checking that it starts with the right domain — an attacker can register a lookalike path and trick the server into sending a freshly issued authorization code straight to an attacker-controlled endpoint instead of the legitimate app.

Mitigation: exact-match redirect URI allowlists

Authorization servers should require the redirect_uri sent at login to exactly match one pre-registered for that client — no wildcards, no prefix matching. This is configuration on the auth server side, but it's worth understanding as a client developer, since it's why you register your callback URLs ahead of time rather than passing them freely.

ATTACK ID Token Replay Without a Nonce ▶

Without a nonce, a previously issued, still-unexpired ID token could in principle be captured and replayed by an attacker to impersonate a login session, since nothing ties that specific token to a specific, fresh authorization request.

Mitigation: nonce verification

Generate a fresh, random nonce for every authorization request, store it client-side, and verify the value embedded in the returned ID token matches it exactly before trusting the token. This is the same one-time-use pattern as state, just scoped specifically to the ID token rather than the whole flow.

Refresh Tokens & Rotation

The mechanism that lets users stay logged in for weeks without ever re-typing a password — and the part that needs the most careful handling.

Refresh tokens solve a real tension in the design of short-lived access tokens: you want access tokens to expire quickly so a leaked one does limited damage, but you don't want users re-authenticating every hour either. A refresh token is the answer — a long-lived credential that, kept safely on the server, can be silently traded for a brand-new access token whenever the old one runs out, with the user never noticing a thing.

// POST /token — refresh grant (back-channel, server-side)
const res = await fetch('https://auth.example.com/token', {
  method: 'POST',
  body: new URLSearchParams({
    grant_type:    'refresh_token',
    refresh_token: storedRefreshToken,
    client_id:     'my-app',
    client_secret: process.env.CLIENT_SECRET,
  })
});
const { access_token, refresh_token } = await res.json();
// store new refresh_token — old one is now invalid (rotation)

Because that long lifetime is also what makes a refresh token dangerous if it's ever stolen, modern providers layer two additional protections on top of the basic exchange, both worth understanding even if you're using a library that implements them for you under the hood:

Refresh Token Rotation
Single-use refresh tokens

Each time a refresh token is used, a new one is issued and the old one invalidated. If a stolen token is used, the legitimate user's next refresh fails — alerting you to the theft.

Refresh Token Families
Reuse detection

Servers track "families" of rotated tokens. If an already-used token is presented (indicating theft), the entire family is revoked — logging out all devices for that user.

The elegance of rotation is that it converts theft from a silent, invisible problem into a detectable event: under normal operation, every refresh token gets used exactly once before being replaced, so if your server ever sees the same refresh token presented twice, that's a strong signal something has gone wrong — either an attacker has a copy, or a client retried a request it shouldn't have. Treating that signal as a reason to revoke the entire token family, rather than just rejecting the one bad request, is what turns detection into actual containment.

Refresh token storage

Refresh tokens are as sensitive as passwords. Store them server-side only (database or encrypted store). Never in localStorage, never in the browser. Treat exposure of a refresh token as equivalent to account compromise.

That's the shape of OAuth 2.0 and OIDC in practice: four roles, three tokens, one well-trodden flow, and a handful of small but load-bearing details — PKCE, state, nonce, rotation — that exist because each one closes a specific, real attack. Most of the libraries you'll use handle these mechanics for you, but knowing what they're doing under the hood is what lets you debug a broken integration, audit someone else's implementation, or make an informed call the day a library doesn't quite fit your situation.
