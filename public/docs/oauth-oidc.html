The Engineer's Guide to OAuth 2.0 & OIDC

Two specifications quietly run the login button on nearly every app you use. Here's what's actually happening behind it: the actors, the tokens, the endpoints, and the attacks they're designed to stop. Updated for 2026.

A field guide
~22 min read
For developers building real auth
Updated June 2026

If you've ever clicked "Sign in with Google" and wondered what happens between that click and landing back on the app, logged in, you've already met OAuth 2.0 and OpenID Connect. They're two of the most widely deployed specifications on the internet, and also two of the most widely misunderstood. This guide walks through both specs from the ground up: who the actors are, what each token is for, how the most common flow actually works end to end, and which mistakes turn a textbook-correct implementation into a security hole. It also covers what's new in 2026: OAuth 2.1 consolidation, DPoP sender-binding, PAR, and the emerging challenges of authorizing AI agents. By the end you should be able to read an OAuth library's source code and know exactly what it's doing and why.

Roles & Actors

Every OAuth conversation, no matter how complex, is really just four parties talking to each other in a fixed pattern.

Before any of the redirects and tokens make sense, it helps to fix the cast of characters firmly in your head, because the entire specification is written in terms of these four roles, and almost every security property in OAuth exists to keep one of them from impersonating or deceiving another.

Resource Owner
The User

The human (or in machine-to-machine cases, the system) who actually owns the protected data. The resource owner is the one who decides whether to grant or deny access, and critically, they authenticate directly with the authorization server, never with the client app. This is the whole point of OAuth: the app asking for access never sees the resource owner's password.

Client
Your Application

The application requesting access on the user's behalf: a web app, a single-page app, a mobile app, a CLI tool, or a background service. The client receives tokens once the user has granted access, but it is never supposed to see the user's credentials at any point. In 2026, this increasingly includes AI agents acting autonomously on a user's behalf.

Authorization Server
The Auth Server (IdP)

The system that authenticates the user, captures their consent, and issues tokens. In the identity world this is usually called an Identity Provider, or IdP. Auth0, Okta, Keycloak, Google Identity, and Microsoft Entra ID are all examples. This is the component most teams choose to outsource rather than build, because getting it wrong is expensive.

Resource Server
The API

The server that actually hosts the protected data: the Google Drive API, a payments API, or your own backend. Its only real job in this story is to accept an access token on incoming requests, validate it, and decide whether the scopes attached to that token permit the requested operation.

Authorization vs Authentication

OAuth 2.0 is, at its core, an authorization framework: it exists to answer the question "what is this app allowed to do on the user's behalf?" Read the original RFC and you'll notice it never actually defines who the user is. Identity simply isn't OAuth's job.

OIDC was built specifically to close that gap. It layers authentication on top of OAuth's authorization mechanics, answering "who is this user, exactly?" by introducing a new artifact: the ID token. This is also why you'll sometimes hear OIDC described as "OAuth 2.0 plus an identity layer" rather than a competing standard. It reuses OAuth's flows almost entirely and just adds a few extra pieces.

Tokens

Three tokens, three jobs. Confusing them is the single most common source of OAuth bugs.

If there's one mental model worth memorizing from this entire guide, it's this: the access token is for machines, the ID token is for your app, and the refresh token is for staying logged in quietly. Mixing these up (sending an ID token to an API, or treating an access token as proof of identity) is responsible for a surprising share of real-world OAuth bugs.

Access Token
API Credential

The credential you attach to every API request, typically as Authorization: Bearer <token>. Intentionally short-lived, usually minutes to a couple of hours. It may be a JWT the resource server verifies locally, or an opaque string requiring an introspection call. Either way, its only job is proving the bearer has permission for a given set of scopes.

ID Token
Identity Proof (OIDC)

Always a JWT, always meant for your application to consume directly rather than forward anywhere. It carries claims about who just authenticated (a stable subject identifier, maybe an email or name), and its presence is what turns a plain OAuth exchange into an OIDC login. Never send this to an API; that's the access token's job.

Refresh Token
Silent Re-auth

A long-lived credential (days, weeks, sometimes months) that the client exchanges for a fresh access token once the old one expires, without bothering the user to re-authenticate. Because it lives so much longer, it's also the most sensitive one to leak. It should never be sent to a resource server, and should never end up where JavaScript can read it.

Token Lifetimes (relative)

Lifetimes vary by provider, but the relative ordering below is close to universal. The shorter-lived a token is, the more freely it can be passed around; the longer-lived it is, the more carefully it needs to be guarded.

JWT vs Opaque Access Tokens

The spec never mandates a token format. An access token can be a self-contained JWT that any resource server can verify using a public key, or it can be a short opaque string that only the authorization server knows how to interpret. Opaque tokens require a call to the introspection endpoint on every request. This is slower, but tokens can be instantly revoked. JWTs are faster to validate locally but can't be revoked before expiry unless you build a separate denylist. Many production systems use JWTs for access tokens precisely because local-validation speed matters at API scale, while accepting that revocation isn't instant.

Don't decode access tokens in your client code

Even when an access token happens to be a JWT, treat it as opaque from the client's perspective. Its format and contents are a contract between the authorization server and the resource server, not something your frontend should depend on. Use the ID token for identity information instead.

Scopes

Scopes are how OAuth implements the principle of least privilege. They let a client ask for exactly what it needs, nothing more.

A scope is simply a string that names a unit of access. When your app sends the user to the authorization server, it lists the scopes it wants, and the consent screen is essentially a human-readable translation of that list. Once granted, the requested scopes get baked into the access token, and the resource server checks, on every request, that the token carries the scope required for that operation.

OIDC Standard Scopes

OIDC defines a small set of standard scopes so that identity providers don't all invent their own conventions for "give me the user's email." These are worth memorizing since you'll see them in nearly every integration:

openid
Turns a plain OAuth request into an OIDC request. Required to receive an ID token at all. Without it, you get only an access token.
profile
Name, picture, website, locale, birthdate, and similar non-sensitive profile fields.
email
The user's email address along with whether it has been verified.
address
The user's physical mailing address, when the provider stores one.
phone
Phone number and its verification status.
offline_access
Requests a refresh token back, so the user doesn't need to log in again every time their access token expires.

Beyond these standard ones, real applications almost always define their own custom scopes shaped around their API, things like read:orders or admin:users. Designing good scopes is really an exercise in API design: think in terms of the operations a client should be allowed to perform, then name a scope for each meaningful grouping of those operations rather than handing out blanket access.

Scopes are not a substitute for fine-grained authorization

Scopes tell you what categories of action a token is allowed to attempt. They're a coarse-grained gate. They generally don't express "can this user edit this specific document." That kind of fine-grained, resource-level authorization is usually handled separately, inside your application logic, after the scope check has already passed.

Grant Types

A grant type is just a recipe: the specific sequence of requests a client follows to walk away with tokens.

OAuth defines several of these recipes because "getting a token" looks completely different depending on what kind of client you're building. A web app with a logged-in human in front of it has very different constraints than a cron job with no user at all, or a smart TV with no keyboard. Picking the wrong grant type for your situation is one of the most common OAuth mistakes.

Recommended for most apps

Authorization Code + PKCE

This is the workhorse flow, and almost certainly the one you should reach for unless you have a specific reason not to. The user is redirected away to the authorization server, where they authenticate and consent, and is then redirected back carrying a short-lived authorization code rather than a token. That code is then traded for actual tokens through a separate, back-channel request that never touches the browser. PKCE sits alongside this exchange specifically to stop that authorization code from being usable by anyone other than the client that requested it, even if it gets intercepted along the way.

Use when: you're building a web app with a backend, a single-page app, or a mobile app: essentially any flow where a real human is sitting in front of a browser or device. In OAuth 2.1, PKCE is required for all authorization code flows regardless of client type.

Machine-to-machine

Client Credentials

There's no user anywhere in this flow. It's the client authenticating as itself, using its own client_id and client_secret (or a private key JWT), to get an access token that represents the application's own identity rather than any person's. It's the simplest grant in the spec: a single back-channel request, no redirect, no consent screen, no browser.

Use when: you have background jobs, microservices, or daemons that need to call an API with no user context attached. A nightly batch job pulling data from a partner API is the textbook case. Also heavily used by AI agents calling APIs on a pre-authorized basis.

// POST /token (back-channel)
grant_type=client_credentials
&client_id=my-service
&client_secret=••••••••
&scope=read:reports
Input-constrained devices

Device Authorization Grant

Designed for devices that have no convenient way to handle a browser redirect (smart TVs, CLI tools, or IoT devices with no keyboard). Instead of opening a browser on the device itself, it displays a short code and a URL. The user picks up their phone or laptop, visits that URL, types in the code, and authenticates there instead, while the original device quietly polls the token endpoint in the background until approval comes through.

Use when: you're building a CLI tool (this is exactly how gh auth login works), a smart TV app, or any other device without a practical way to render a full browser-based login screen. Increasingly also used for headless AI agent authorization.

Deprecated

Implicit Flow

This was OAuth's original answer for single-page apps, back before PKCE existed: rather than returning a code that gets exchanged for tokens, the authorization server returned the access token directly in the URL fragment, as in #access_token=.... It seemed reasonable at the time, but tokens sitting in a URL turn out to leak in all sorts of mundane ways: browser history, referrer headers sent to third-party scripts, and server access logs all end up holding a live credential.

Do not use — removed in OAuth 2.1

Use Authorization Code + PKCE for SPAs instead. It solves the same problem without exposing tokens in the URL. The implicit flow has been formally removed from the OAuth 2.1 specification.

Avoid

Resource Owner Password Credentials

In this grant, the client itself collects the user's username and password through its own form and sends them straight to the token endpoint. It quietly defeats the entire premise of OAuth, which is that the client app should never see the user's actual credentials. It also makes multi-factor authentication and social login effectively impossible to support.

Removed in OAuth 2.1

ROPC has been formally dropped from OAuth 2.1. The only legitimate use case left is a temporary bridge while migrating an existing system that already stores user passwords directly. For any new system, Authorization Code + PKCE is the right choice.

OAuth 2.1 — What's New 2026

OAuth 2.1 is not a new protocol. It's a curated consolidation of a decade of security best practices into a single, tighter document.

OAuth 2.1 folds the most important security best practices and several extensions into one coherent specification, removing the footguns that experience has shown developers tend to stumble into. If your implementation already follows current best practices, you're probably already compliant with 2.1. The key changes are:

PKCE — Mandatory
Required for all auth code flows

Previously PKCE was specifically recommended for public clients. In OAuth 2.1 it's required for every client using the authorization code grant, confidential clients included. PKCE is now table stakes.

Implicit & ROPC — Removed
Two grants eliminated

The implicit flow and Resource Owner Password Credentials grant are no longer part of the specification. If you encounter code that still uses them, that's a clear signal the implementation needs updating.

Redirect URI
Exact-match only

OAuth 2.1 mandates exact-match redirect URI comparison: no wildcards, no prefix matching. This closes off a class of authorization code redirect attacks that loose matching enabled.

Refresh Token Rotation
Default, not optional

Refresh token rotation is now the expected default for public clients. Sender-constrained refresh tokens (tied to a specific client via DPoP or mTLS) are the recommended approach for confidential clients.

Is my app OAuth 2.1 compliant?

Check four things: (1) you're using Authorization Code + PKCE, (2) you've dropped Implicit and ROPC, (3) your redirect URIs are registered exactly, and (4) you're rotating refresh tokens. If all four are true, you're effectively already compliant. 2.1 codifies existing best practice rather than introducing new requirements.

Endpoints

Every authorization server exposes the same small handful of URLs. Learn these four and you can read any OAuth integration.

GET /authorize Authorization endpoint — browser redirect ►

The endpoint where the browser flow begins. The client redirects the user here, the authorization server authenticates them and shows a consent screen, then redirects back to the client with an authorization code attached. This is the only endpoint that speaks directly to the user. Every other endpoint in OAuth is a back-channel machine-to-machine call.

  • response_typeAlways code for the authorization code flow.Required
  • client_idIdentifies your application to the authorization server.Required
  • redirect_uriWhere to send the user back with the code. Must exactly match a pre-registered URI in OAuth 2.1.Required
  • scopeSpace-separated list of permissions your app is requesting. Include openid for OIDC.Required
  • stateA random value you generate, stored client-side, and verified on return. Defeats CSRF attacks against the login flow.Required
  • code_challengeThe SHA-256 hash of your PKCE code_verifier. Required in OAuth 2.1.Required
  • code_challenge_methodShould always be S256. Never use plain.Required
  • nonceOIDC-specific. A random value embedded in the returned ID token to prevent replay attacks.OIDC
  • request_uriPAR-specific. Replaces all other params with a reference to a pushed request object. See PAR section below.PAR
POST /token Token endpoint — back-channel fetch ►

The endpoint where authorization codes get redeemed for actual tokens, and where refresh tokens get exchanged for new access tokens. Everything here happens as a direct server-to-server (or SPA-to-server) request, not a browser redirect, which is why this endpoint never exposes tokens in a URL. If you're using DPoP, your JWT proof header is bound to this endpoint.

  • grant_typeOne of: authorization_code, refresh_token, client_credentials, or the device code URN.Required
  • codeThe authorization code from the /authorize callback. One use only. It expires in seconds.auth_code only
  • code_verifierThe PKCE secret you generated before the redirect. The server hashes it and checks it against the stored challenge.PKCE required
  • redirect_uriMust exactly match the URI used in /authorize. Just a validation parameter, not a new redirect.Required
  • client_idYour application's identifier. Confidential clients authenticate here with a secret or private key JWT.Required
GET /.well-known/openid-configuration Discovery endpoint — auto-configuration ►

OIDC's discovery endpoint. Returns a JSON document listing every endpoint, supported algorithm, scope, and capability of this authorization server. This is how a client library can talk to Google, Okta, and Keycloak with no provider-specific code. It just reads this document and configures itself. Every modern OIDC provider exposes this URL. Use it rather than hardcoding endpoint URLs in your config.

GET /.well-known/jwks.json JWKS endpoint — public keys for JWT verification ►

The JSON Web Key Set endpoint. Returns the authorization server's current public keys in a standardized format. When you receive a JWT, your library fetches this document to find the right key, identified by the kid claim in the JWT header, and uses it to verify the signature. Most libraries cache this document and only re-fetch when they encounter an unknown key ID.

POST /revoke Revocation endpoint — back-channel fetch ►

The counterpart to issuing tokens is being able to take them back. Call it with a refresh token (or, on some providers, an access token) when a user logs out, and the authorization server invalidates it immediately rather than waiting for it to expire naturally. This matters most for refresh tokens. A proper "log out everywhere" feature is really just a call to this endpoint.

PKCE — Proof Key for Code Exchange

A clever cryptographic handshake that turns a stealable authorization code into something useless to anyone but you.

PKCE (pronounced "pixie") exists to solve a very specific problem: how do you prove that whoever is redeeming an authorization code is the exact same client that originally requested it, when that client has no secret it can use to prove its identity? The trick is to generate a secret on the fly, for that one login attempt only, and only ever reveal it at the very last step.

1
Generate code_verifier

A cryptographically random 43–128 character string. Stays in the client. Never sent to the auth server directly.

↓
2
Hash it → code_challenge

code_challenge = BASE64URL(SHA256(code_verifier))
This hash is sent to the auth server in the /authorize request.

↓
3
Auth server stores the challenge

It ties the code_challenge to the authorization code it issues. The challenge is a commitment: you can't back-compute the verifier from it.

↓
4
Token exchange: send the verifier

POST to /token with code_verifier. The server hashes it and checks it matches the stored challenge. If not, the request is rejected.

Why this stops code theft

An attacker who intercepts the code in the redirect URL doesn't have the code_verifier. It was never in a URL. They'd need to break SHA-256 to derive it from the challenge. That's computationally infeasible.

While PKCE was originally specified as a mitigation for public clients, OAuth 2.1 requires it everywhere, even for confidential server-side clients that do have a client secret. It's cheap to implement and closes off an entire class of attack, so there's little reason not to use it universally.

Pushed Authorization Requests (PAR) 2026

PAR flips the authorization flow. Instead of stuffing everything in a URL, you push the parameters to the server first and get back a reference.

Pushed Authorization Requests address a subtle weakness in the standard authorization code flow: all your authorization parameters travel in the browser's URL, where they can be logged, intercepted, or tampered with. PAR moves those parameters to a back-channel POST first.

1
Client POSTs parameters to /par

All authorization parameters (scope, redirect_uri, PKCE challenge, etc.) are sent as a back-channel POST, authenticated with client credentials. No browser involved yet.

↓
2
Server returns a request_uri

The server stores the parameters and returns a short-lived, one-time-use request_uri reference — an opaque token that stands in for the full parameter set.

↓
3
Browser redirect uses only the request_uri

The redirect to /authorize carries just client_id and request_uri. All the sensitive parameters are already safely stored on the server side.

Why PAR matters in 2026

PAR is now mandatory in FAPI 2.0 (Financial-grade API) and strongly recommended as a general security best practice. It's also a prerequisite for Rich Authorization Requests (RAR), which allow structured authorization data (like specifying exactly which bank accounts a fintech app may access) rather than flat scope strings. If you're building high-security or regulated applications, PAR is no longer optional.

Client Types

Not all OAuth clients can be trusted equally. The spec splits them into two categories precisely so it can treat them differently.

The single question that determines which category a client falls into is simple: can this application keep a secret from the end user it's running on, or in front of? A server-side app's code runs somewhere the user can never inspect, so it can hold a real secret. Anything running on the user's own device or in their own browser can always be decompiled, inspected, or read directly, so it cannot.

Confidential Client
Can keep a secret

Server-side apps where code runs in a trusted environment. Can safely store a client_secret or use private_key_jwt for stronger client authentication. Examples: Express, Django, Rails, Spring Boot apps.

Public Client
Cannot keep a secret

Code runs on the user's device; anyone can inspect it. Cannot use a client secret. Use PKCE instead. Examples: SPAs, React/Vue apps, mobile apps, CLIs. In 2026, AI agent runtimes on user devices also fall into this category.

Client secrets in frontend code

If you embed a client_secret in a JavaScript bundle, it's not secret. Anyone can find it in DevTools. Public clients must use PKCE, and no client secret. For server-side clients, prefer private_key_jwt over shared secrets wherever your auth server supports it. It's phishing-resistant and doesn't require secret rotation.

State Parameter & CSRF

A single random string is all that stands between your login flow and a class of attack that links the wrong account to the wrong session.

The state parameter looks almost too simple to matter. It's just an opaque random value you generate, send along with the authorization request, and check still matches when the user comes back. But that simple round trip is exactly what defeats a CSRF attack against the OAuth flow itself: it proves that the browser completing the login is the same browser that initiated it.

// Before redirect: generate and store
const state = crypto.randomUUID();
sessionStorage.setItem('oauth_state', state);
// Include in /authorize URL

// In callback handler: verify
const returnedState = new URLSearchParams(location.search).get('state');
if (returnedState !== sessionStorage.getItem('oauth_state')) {
  throw new Error('CSRF attack detected — state mismatch');
}
sessionStorage.removeItem('oauth_state'); // use once
Attack without state

Without state, an attacker could trick a victim into completing an OAuth flow that logs them into the attacker's account, then steal their session actions (payment, data entry). Always verify state on every callback.

What OIDC Adds to OAuth 2.0

OIDC doesn't replace anything in OAuth. It's a small, deliberate set of additions layered on top.

If you already understand OAuth's authorization code flow, you essentially already understand OIDC's login flow too. The redirects, the back-channel token exchange, PKCE, the state parameter, all of it carries over unchanged. What OIDC contributes is a handful of new, standardized pieces bolted onto that same foundation, all aimed at one goal: letting the client walk away knowing exactly who just logged in, in a way that's portable across providers. You opt into all of it simply by including the openid scope in your authorization request.

ID Token
A JWT about the user

Returned alongside the access token. Contains who the user is: their subject identifier, email, name. Your app reads this. It does not send it to APIs.

UserInfo Endpoint
Fetch more claims

An authenticated GET endpoint that returns user profile data. Use it when you need claims that aren't in the ID token, or want fresh data since login.

Nonce
Replay protection

A random value sent in /authorize, embedded in the ID token. Your app verifies it matches, preventing an old token from being replayed.

Discovery
Auto-configuration

OIDC standardizes the /.well-known/openid-configuration endpoint so clients can auto-discover all endpoints and capabilities without hardcoding URLs.

It's this last point, standardization, that's arguably OIDC's biggest practical contribution. Plain OAuth 2.0 leaves a lot of room for interpretation: providers were free to invent their own ways of representing user profile data. OIDC pins all of that down, which is exactly why a single OIDC client library can talk to Google, Microsoft, Okta, and a dozen other providers with barely any provider-specific code.

JWT & ID Token Anatomy

A JWT is just three pieces of JSON, base64-encoded and glued together. Each piece carries a very specific job.

JSON Web Tokens look intimidating as a long string of seemingly random characters, but they're built from nothing more exotic than JSON. Split on the two dots and you get three Base64URL-encoded segments: a header describing how the token is signed, a payload containing the actual claims, and a signature that lets anyone holding the right public key verify the first two segments haven't been tampered with. ID Token Claims

Claims are the key-value pairs inside the payload. Each one carries a specific, standardized piece of information about the user or the token itself.

iss
Issuer — the URL of the authorization server. Validate it matches what you expect.
sub
Subject — the user's stable, unique ID. Use this as your primary key, not email.
aud
Audience — must contain your client_id. Reject tokens issued for someone else.
exp
Expiry — Unix timestamp. Reject any token whose exp is in the past.
iat
Issued At — when the token was created. Useful for detecting stale tokens.
nonce
Replay protection value — verify it matches what you sent in /authorize.
at_hash
Hash of the access token. Binds the ID token to a specific access token.
email_verified
Boolean. Don't trust the email claim for authentication unless this is true.

The sub claim deserves a special callout: it's tempting to use a user's email address as their primary key in your database, since it feels stable and human-readable, but email addresses change, get recycled, or get re-verified under a different identity over time. The sub claim is specifically designed to be a permanent, opaque identifier for one user at one issuer. Store this as your foreign key, with email treated as just another mutable profile field.

UserInfo Endpoint

The ID token is a snapshot taken at login. Sometimes you need to know what's true right now instead.

An OIDC endpoint that returns fresh profile data for the authenticated user. Call it with a Bearer access token that includes the openid scope. The ID token is a snapshot taken at login — if the user has since changed their display name or avatar, the UserInfo endpoint reflects the current state.

// Frontend or backend fetch — requires a valid access token
const res = await fetch('https://auth.example.com/userinfo', {
  headers: { 'Authorization': `Bearer ${accessToken}` }
});
const user = await res.json();
// { sub, email, name, picture, ... }
ID token vs UserInfo

The ID token is a snapshot at login time. The UserInfo endpoint returns the current state. If you show the user's avatar and it might change, call UserInfo. For simply establishing identity at login, the ID token is enough.

DPoP — Demonstrating Proof of Possession 2026

Bearer tokens are stolen all the time. DPoP makes a stolen token useless because the thief can't prove they hold the private key that bound it.

DPoP solves a fundamental weakness of Bearer tokens: anyone who obtains a Bearer token can use it. DPoP cryptographically binds an access token to a specific private key held by the client, so even a captured token can't be replayed by an attacker who doesn't hold that key.

🔑
Client generates a key pair

An ephemeral public/private key pair is created by the client. The public key will be embedded in tokens; the private key never leaves the client.

📸
Client sends a DPoP proof JWT to /token

A short-lived JWT signed by the private key, containing the HTTP method, URI, and a timestamp. Proves the client holds the private key right now.

✅
Auth server binds the access token to the public key

The issued access token contains a cnf.jkt claim: a thumbprint of the client's public key. The token is now "sender-constrained."

🔒
API verifies DPoP proof on every request

The client attaches both the access token and a fresh DPoP proof JWT to each API call. The resource server verifies the proof's signature matches the key thumbprint in the token. A stolen token without the private key is useless.

// API request with DPoP — two headers required
fetch('https://api.example.com/data', {
  headers: {
    'Authorization': `DPoP ${accessToken}`,  // Note: DPoP, not Bearer
    'DPoP': await createDPoPProof({
      htu: 'https://api.example.com/data',
      htm: 'GET',
      privateKey,
    }),
  }
});
DPoP adoption in 2026

DPoP is mandatory in FAPI 2.0 and supported by major identity providers including Okta, Auth0, and Microsoft Entra ID. For most web apps, the BFF pattern achieves similar protection by keeping tokens off the browser entirely. For SPAs that must hold tokens client-side, DPoP is the strongest mitigation available.

Token Storage

Where you put a token after you receive it matters just as much as how you got it in the first place.

A surprising amount of real-world OAuth insecurity has nothing to do with the protocol flow itself and everything to do with what happens after tokens land in the browser. Every storage location trades off resistance to one attack class against resistance to another:

Best practice: BFF pattern

Use a Backend for Frontend (BFF): your server handles the OAuth flow and stores tokens server-side. The browser only gets a session cookie. Tokens never touch the browser's storage, eliminating the entire XSS token theft surface. In 2026, this is the strongly recommended architecture for any app that can support a server component.

Common Attacks & Mitigations

Most OAuth vulnerabilities aren't flaws in the specification. They're implementations that quietly skip a step the spec assumes you'll do.

PKCE, state validation, careful token storage, and signature verification can all feel like ceremony when you're just trying to get a login button working. Each one exists because someone, somewhere, shipped a version without it and got burned.

ATTACK Authorization Code Interception ►

An attacker intercepts the code in the redirect URI (via referrer headers, browser history, or a malicious app registering the same custom URI scheme).

Mitigation: PKCE (+ PAR)

PKCE binds the code to the verifier. An intercepted code is useless without the verifier, which was never transmitted in the vulnerable channel. PAR goes further by removing all parameters from the browser URL entirely.

ATTACK CSRF / Open Redirect ►

Attacker initiates an OAuth flow and tricks the victim into completing it, linking the victim's identity to the attacker's account.

Mitigation: state parameter

Validate state on every callback. The attacker can't forge a valid state value because it's stored in the victim's browser session.

ATTACK Token Theft via XSS ►

A Cross-Site Scripting vulnerability lets an attacker run JavaScript that reads tokens from localStorage or sessionStorage and exfiltrates them.

Mitigation: HttpOnly cookies + BFF (+ DPoP)

Store tokens server-side. Issue the browser an HttpOnly session cookie. JS cannot access it regardless of XSS. Combine with SameSite=Strict or SameSite=Lax for CSRF protection. If tokens must be in the browser, use DPoP to sender-bind them so a stolen token can't be replayed.

ATTACK JWT Algorithm Confusion (alg:none) ►

An attacker crafts a token with "alg":"none" and no signature. Naive verifiers that trust the alg header accept it as valid.

Mitigation: allowlist algorithms

Never use the alg field in the token header to decide how to verify. Always specify the expected algorithm in your verifier code. Reject none always. Prefer RS256 or ES256 over HS256 for multi-party scenarios.

ATTACK Open Redirect via redirect_uri ►

If an authorization server validates redirect_uri loosely (only checking that it starts with the right domain), an attacker can register a lookalike path and redirect a freshly issued authorization code to an attacker-controlled endpoint.

Mitigation: exact-match redirect URI allowlists

Authorization servers must require the redirect_uri sent at login to exactly match one pre-registered for that client. No wildcards, no prefix matching. This is now mandatory in OAuth 2.1.

ATTACK ID Token Replay Without a Nonce ►

Without a nonce, a previously issued, still-unexpired ID token could be captured and replayed by an attacker to impersonate a login session.

Mitigation: nonce verification

Generate a fresh, random nonce for every authorization request, store it client-side, and verify the value embedded in the returned ID token matches it exactly before trusting the token.

ATTACK Mix-Up Attack (multi-IdP) ►

In a multi-IdP setup, an attacker tricks the client into sending an authorization code issued by a legitimate IdP to a malicious IdP's token endpoint, or vice versa.

Mitigation: iss parameter + PAR

An iss parameter in the authorization response lets clients verify which server issued the response. PAR also significantly reduces this risk by tying the request to a specific server before the redirect happens.

Refresh Tokens & Rotation

The mechanism that lets users stay logged in for weeks without re-typing a password, and the part that needs the most careful handling.

Refresh tokens solve a real tension in the design of short-lived access tokens: you want access tokens to expire quickly so a leaked one does limited damage, but you don't want users re-authenticating every hour either. A refresh token is the answer: a long-lived credential that, kept safely on the server, can be silently traded for a brand-new access token whenever the old one runs out, with the user never noticing.

// POST /token — refresh grant (back-channel, server-side)
const res = await fetch('https://auth.example.com/token', {
  method: 'POST',
  body: new URLSearchParams({
    grant_type:    'refresh_token',
    refresh_token: storedRefreshToken,
    client_id:     'my-app',
    client_secret: process.env.CLIENT_SECRET,
  })
});
const { access_token, refresh_token } = await res.json();
// store new refresh_token — old one is now invalid (rotation)
Refresh Token Rotation
Single-use refresh tokens

Each time a refresh token is used, a new one is issued and the old one invalidated. If a stolen token is used, the legitimate user's next refresh fails, alerting you to the theft. Required in OAuth 2.1 for public clients.

Refresh Token Families
Reuse detection

Servers track "families" of rotated tokens. If an already-used token is presented (indicating theft), the entire family is revoked, logging out all devices for that user. This turns detection into containment.

Refresh token storage

Refresh tokens are as sensitive as passwords. Store them server-side only (database or encrypted store). Never in localStorage, never in the browser. Treat exposure of a refresh token as equivalent to account compromise.

Agentic & AI Authorization 2026

When an AI agent acts on a user's behalf (booking flights, sending emails, querying databases) the authorization model gets more complex.

By 2026, AI agents and LLM-based assistants are a real authorization use case that existing OAuth flows weren't quite designed for. The core challenge: a user delegates authority to an agent, and that agent may need to call many APIs, run for a long time, spawn sub-agents, or operate without the user being present at all. Standard OAuth handles the initial delegation well, but the devil is in the details.

Delegation Problem
Who is acting — user or agent?

When an agent calls an API, the API needs to know both who authorized the action (the user) and which agent is acting. Token Exchange allows creating a derived token that chains both identities, creating an auditable delegation trail.

Scope Minimization
Least privilege for agents

Agents should receive narrow, task-scoped tokens rather than broad user-level access. Rich Authorization Requests allow structured, resource-specific authorization data, e.g. "access only this Google Doc" rather than "access all Drive files."

Long-lived Sessions
Agents that outlive a login session

An agent running an hours-long task needs refresh tokens and robust rotation. Consider time-boxing agent authority: issue tokens with a max lifetime matching the expected task duration rather than allowing indefinite access.

Human in the Loop
Step-up auth for sensitive actions

Even a pre-authorized agent should trigger step-up authentication for high-impact actions (sending money, deleting data). OIDC's max_age and acr parameters let resource servers demand fresh user authentication when the stakes are high.

Watch out: token laundering via agents

If your agent framework accepts tokens as inputs and passes them to other services, validate the chain carefully. An attacker-controlled agent could present a legitimate user token to escalate privileges. Always verify iss, aud, and scope at every hop, and consider mTLS or DPoP binding throughout the chain.

FAPI & High-Security Profiles 2026

FAPI 2.0 is what OAuth looks like when the stakes are high enough that every optional best practice becomes mandatory.

The Financial-grade API Security Profile (FAPI 2.0), published by the OpenID Foundation, takes the OAuth security best practices and turns them into a strict, auditable profile. It was designed for open banking but is increasingly adopted for any regulated API — healthcare, government, payments. If you're building to this profile, you will be using all of the following:

PAR
Pushed Authorization Requests — mandatory. All authorization parameters travel back-channel.
DPoP or mTLS
Sender-constrained tokens — mandatory. Plain Bearer tokens are not permitted.
RAR
Rich Authorization Requests for structured, resource-specific access data.
private_key_jwt
Client authentication via signed JWTs rather than shared secrets.
PKCE S256
Mandatory for all authorization code flows. plain is not acceptable.
Exact redirect URIs
Pre-registered, exact-match. No wildcards, no prefix matching, no exceptions.
Should I care about FAPI if I'm not in fintech?

FAPI 2.0 is a useful benchmark even if you're not building a regulated API. Its requirements represent a curated list of the most impactful security controls. Think of it as a security checklist rather than a compliance obligation. The components most worth adopting broadly are PAR (removes parameters from browser URLs), DPoP (stops token replay), and private_key_jwt (eliminates shared secret management).

That's the shape of OAuth 2.0 and OIDC in 2026: four roles, three tokens, one well-trodden flow, and a growing stack of security enhancements (PKCE, state, nonce, rotation, DPoP, PAR), each closing a specific, real attack. Most libraries handle these mechanics for you, but knowing what they're doing is what lets you debug a broken integration, audit an existing implementation, authorize an AI agent safely, or make an informed call the day a library doesn't quite fit your situation.
