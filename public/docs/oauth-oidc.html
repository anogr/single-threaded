OAuth 2.0 & OIDC

Every important concept, explained clearly — from tokens to threat models.

Roles & Actors

OAuth defines four parties. Every flow is just these four talking to each other.

Resource Owner
The User

The human (or system) who owns the data. They grant or deny access. They authenticate to the Auth Server — never to the client app.

Client
Your Application

The app requesting access on the user's behalf. Could be a web app, SPA, mobile app, or CLI. It receives tokens but should never see the user's password.

Authorization Server
The Auth Server (IdP)

Issues tokens after authenticating the user and getting consent. Examples: Auth0, Okta, Keycloak, Google Identity, Azure AD.

Resource Server
The API

The server hosting the protected data (e.g. Google Drive API, your own backend). It validates incoming access tokens before serving data.

Authorization vs Authentication

OAuth 2.0 is an authorization framework — it answers "what is this app allowed to do?" It says nothing about who the user is.
OIDC adds authentication on top — it answers "who is this user?" by introducing the ID token.

Tokens

Three types of token exist in OAuth/OIDC. Each has a distinct job.

Access Token
API Credential

Sent with every API call. Short-lived (minutes–hours). Proves the client has permission for certain scopes. Usually a JWT, sometimes opaque.

ID Token
Identity Proof (OIDC)

A JWT that proves who the user is. Contains claims like sub, email, name. For your app to consume — not to send to APIs.

Refresh Token
Silent Re-auth

Long-lived (days–months). Used to get new access tokens without re-prompting the user. Must be stored securely. Never sent to resource servers.

Scopes

Scopes are strings that define what access the client is requesting. The user sees them on the consent screen. The auth server encodes them into the access token. The resource server checks them.

OIDC Standard Scopes

openid
Required to trigger OIDC. Returns an ID token with a sub claim.
profile
Name, picture, website, locale, birthdate, etc.
email
Email address and whether it's verified.
address
Physical mailing address.
phone
Phone number and verification status.
offline_access
Requests a refresh token for long-lived access.
Custom Scopes

Real-world apps define their own scopes: read:orders, write:invoices, admin:users. Scope design is API design — think in terms of what operations the client needs permission to perform.

Grant Types

A grant type is the mechanism by which a client obtains tokens. Use the right one for your context.

Recommended for most apps

Authorization Code + PKCE

The user is redirected to the auth server, authenticates, then redirected back with a short-lived authorization code. The code is exchanged back-channel for tokens. PKCE prevents the code from being stolen in transit.

Use when: Web apps with a backend, SPAs, mobile apps — any flow where a human user is present.

Machine-to-machine

Client Credentials

No user involved. The client authenticates directly with its client_id + client_secret and gets an access token. Pure machine-to-machine.

Use when: Background jobs, microservices, daemons, cron tasks calling APIs with no user context.

// POST /token (back-channel)
grant_type=client_credentials
&client_id=my-service
&client_secret=••••••••
&scope=read:reports
Input-constrained devices

Device Authorization Grant

For devices with no browser (Smart TVs, CLIs, IoT). The device shows a code and a URL. The user visits the URL on their phone/computer, enters the code, and the device polls until it gets a token.

Use when: CLI tools (like gh auth login), smart TVs, printers, anything without a usable browser.

Deprecated

Implicit Flow

Tokens were returned directly in the URL fragment (#access_token=...) — no code exchange step. This was designed for SPAs before PKCE existed. Now considered insecure because tokens in URLs leak via browser history, referrer headers, and server logs.

Do not use

Use Authorization Code + PKCE for SPAs instead. The implicit flow has been removed from the OAuth 2.1 draft spec.

Avoid

Resource Owner Password Credentials

The client collects the user's username and password and sends them directly to the token endpoint. This breaks the core OAuth promise — the user's password is exposed to the client app, and you can't use MFA or social login.

Only for legacy migration

The only valid use case is migrating an existing system that already stores user passwords. For all new systems, use Authorization Code + PKCE.

Endpoints

Auth servers expose a standard set of endpoints. Discovery makes finding them automatic.

GET /.well-known/openid-configuration Discovery document ▶

Returns a JSON document listing all other endpoint URLs, supported scopes, signing algorithms, and capabilities. Always start here — hard-coding endpoint URLs is fragile. Fetch this once on startup and cache it.

// Returned JSON includes:
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "userinfo_endpoint": "https://auth.example.com/userinfo",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "scopes_supported": ["openid", "profile", "email"],
  "id_token_signing_alg_values_supported": ["RS256"]
}
GET /authorize Authorization endpoint — browser redirect ▶

The user's browser is redirected here. The auth server authenticates the user and gets consent. This is never called as a fetch() — it must be a full browser navigation so the auth server can set its own cookies and show its UI.

Key Parameters

  • client_idIdentifies your app to the auth server.required
  • redirect_uriWhere to send the user after auth. Must match an allow-list on the server.required
  • response_typeAlways code for auth code flow.required
  • scopeSpace-separated scopes. Include openid for OIDC.required
  • stateRandom value to prevent CSRF. Must be verified when the callback arrives.required
  • code_challengeSHA-256 hash of your PKCE code verifier.required (PKCE)
  • code_challenge_methodAlways S256. Never use plain.required (PKCE)
  • nonceRandom value embedded in the ID token to prevent replay attacks.optional (OIDC)
  • promptnone (silent), login (force re-login), consent (force re-consent), select_account.optional
  • max_ageMax seconds since last user authentication. Forces re-auth if exceeded.optional
POST /token Token endpoint — back-channel fetch ▶

Called server-to-server (back-channel) to exchange a code for tokens, or to refresh an access token. Never called from the browser directly — that would expose tokens to browser history and extensions.

  • grant_typeauthorization_code, refresh_token, or client_credentials.required
  • codeThe authorization code from the redirect callback.required (code flow)
  • redirect_uriMust exactly match what was sent to /authorize.required (code flow)
  • code_verifierThe original random PKCE value. Server hashes and compares to stored challenge.required (PKCE)
  • client_idYour app's identifier.required
  • client_secretSecret for confidential clients. Never include in browser code.confidential only
  • refresh_tokenUsed when grant_type=refresh_token.refresh only
GET /.well-known/jwks.json JSON Web Key Set — public keys for JWT verification ▶

Returns the auth server's public keys. Your resource server fetches these to verify the signatures of JWTs. Keys are cached locally and only re-fetched when a token arrives signed with an unknown key ID (kid).

{
  "keys": [{
    "kty": "RSA",
    "kid": "key-id-2024",    // match to token header's "kid"
    "use": "sig",
    "alg": "RS256",
    "n": "...base64url modulus...",
    "e": "AQAB"
  }]
}

PKCE — Proof Key for Code Exchange

PKCE prevents authorization code interception attacks. Even if an attacker intercepts the code in the redirect, they can't use it without the code_verifier that was never sent over the network in a form they could capture.

1
Generate code_verifier

A cryptographically random 43–128 character string. Stays in the client. Never sent to the auth server directly.

↓
2
Hash it → code_challenge

code_challenge = BASE64URL(SHA256(code_verifier))
This hash is sent to the auth server in the /authorize request.

↓
3
Auth server stores the challenge

It ties the code_challenge to the authorization code it issues. The challenge is a commitment — you can't back-compute the verifier from it.

↓
4
Token exchange: send the verifier

POST to /token with code_verifier. The server hashes it and checks it matches the stored challenge. If not, it rejects the request.

Why this stops code theft

An attacker who intercepts the code in the redirect URL doesn't have the code_verifier — it was never in a URL. They'd need to break SHA-256 to derive it from the challenge. That's computationally infeasible.

Client Types

Confidential Client
Can keep a secret

Server-side apps where code runs in a trusted environment. Can safely store a client_secret. Examples: Express, Django, Rails, Spring Boot apps.

Public Client
Cannot keep a secret

Code runs on the user's device — they could inspect it. Cannot use a client secret. Use PKCE instead. Examples: SPAs, React/Vue apps, mobile apps, CLIs.

Client secrets in frontend code

If you embed a client_secret in a JavaScript bundle, it's not secret — anyone can find it in DevTools. Public clients must use PKCE, and no client secret.

State Parameter & CSRF

The state parameter is your CSRF protection for the OAuth flow.

// Before redirect: generate and store
const state = crypto.randomUUID();
sessionStorage.setItem('oauth_state', state);
// Include in /authorize URL

// In callback handler: verify
const returnedState = new URLSearchParams(location.search).get('state');
if (returnedState !== sessionStorage.getItem('oauth_state')) {
  throw new Error('CSRF attack detected — state mismatch');
}
sessionStorage.removeItem('oauth_state'); // use once
Attack without state

Without state, an attacker could trick a victim into completing an OAuth flow that logs them into the attacker's account, then steal their session actions (payment, data entry). Always verify state on every callback.

What OIDC Adds to OAuth 2.0

OpenID Connect (OIDC) is a thin layer on top of OAuth 2.0. You opt in by including the openid scope.

ID Token
A JWT about the user

Returned alongside the access token. Contains who the user is: their subject identifier, email, name. Your app reads this — it does not send it to APIs.

UserInfo Endpoint
Fetch more claims

An authenticated GET endpoint that returns user profile data. Use it when you need claims that aren't in the ID token, or want fresh data.

Nonce
Replay protection

A random value sent in /authorize, embedded in the ID token. Your app verifies it matches, preventing an old token from being replayed.

Discovery
Auto-configuration

OIDC standardizes the /.well-known/openid-configuration endpoint so clients can auto-discover all endpoints and capabilities without hardcoding URLs.

Header (decoded)
{
  "alg": "RS256",   // RS256 = RSA + SHA-256. Always verify this matches expected.
  "kid": "key-2024", // Key ID — look up in JWKS to find the right public key
  "typ": "JWT"
}
Payload — Claims (decoded)
{
  "iss": "https://auth.example.com", // Issuer — must match your auth server
  "sub": "user_123",               // Subject — stable unique user ID. Use as your user key.
  "aud": "my-app",                 // Audience — must match your client_id
  "exp": 1735689600,              // Expiry (Unix timestamp) — reject if in the past
  "iat": 1735686000,              // Issued At — when the token was created
  "nonce": "abc123",               // Must match nonce you sent in /authorize
  "email": "jane@example.com",     // From 'email' scope
  "email_verified": true,       // Don't trust unverified emails
  "name": "Jane Doe"              // From 'profile' scope
}
Signature
// RSA-SHA256 signature over (base64url(header) + "." + base64url(payload))
// Signed with the auth server's PRIVATE key.
// Verified with the auth server's PUBLIC key from /jwks.json.
// If ANY byte of header or payload changes, signature verification fails.
// This makes JWTs tamper-evident without a database lookup.

ID Token Validation Checklist

Always validate these — never trust a JWT you didn't verify

✔ iss matches your expected auth server
✔ aud contains your client_id
✔ exp is in the future
✔ iat is not too far in the past
✔ nonce matches what you sent (if used)
✔ Signature verified with the correct public key from JWKS
✔ alg header matches an algorithm you accept (reject none!)

Claims

Claims are the key-value pairs inside a JWT. Standard OIDC claims:

sub
Unique identifier for the user at this issuer. Use as your primary user key — never email (email can change).
iss
Issuer URL. The auth server that issued this token.
aud
Audience. The client(s) this token is intended for.
exp
Expiration time (Unix timestamp). Reject tokens past this time.
iat
Issued At. When the token was created.
email
User's email. Check email_verified before trusting it.
email_verified
Boolean. Whether the auth server has verified the email.
name
Full display name.
picture
URL to profile photo.
locale
BCP 47 language tag, e.g. en-US.
nonce
Replay protection value — verify it matches what you sent.
at_hash
Hash of the access token. Binds the ID token to a specific access token.

UserInfo Endpoint

An OIDC-specified endpoint returning fresh profile data for the currently authenticated user. Call it with a Bearer access token (must include the openid scope).

// Frontend or backend fetch — requires a valid access token
const res = await fetch('https://auth.example.com/userinfo', {
  headers: { 'Authorization': `Bearer ${accessToken}` }
});
const user = await res.json();
// { sub, email, name, picture, ... }
ID token vs UserInfo

The ID token is a snapshot at login time. The UserInfo endpoint returns the current state. If you show the user's avatar and it might change, call UserInfo. For simply establishing identity at login, the ID token is enough.

Token Storage

LocationXSS Safe?CSRF Safe?Verdict
localStorage No — any JS can read it Yes Avoid for tokens
sessionStorage No — any JS can read it Yes Acceptable for PKCE state only
HttpOnly Cookie Yes — JS can't read it No — requires CSRF tokens Best for session tokens
In-memory (JS var) Yes — lost on tab close Yes Good for access tokens in SPAs
Server session Yes Yes (with SameSite cookies) Best overall
Best practice: BFF pattern

Use a Backend for Frontend (BFF) — your server handles the OAuth flow and stores tokens. The browser only gets a session cookie. Tokens never touch the browser's storage, eliminating the entire XSS token theft surface.

Common Attacks & Mitigations

ATTACK Authorization Code Interception ▶

An attacker intercepts the code in the redirect URI (via referrer headers, browser history, or a malicious app registering the same custom URI scheme).

Mitigation: PKCE

PKCE binds the code to the verifier. An intercepted code is useless without the verifier, which was never transmitted in the vulnerable channel.

ATTACK CSRF / Open Redirect ▶

Attacker initiates an OAuth flow and tricks the victim into completing it, linking the victim's identity to the attacker's account.

Mitigation: state parameter

Validate state on every callback. The attacker can't forge a valid state value because it's stored in the victim's browser session.

ATTACK Token Theft via XSS ▶

A Cross-Site Scripting vulnerability lets an attacker run JavaScript that reads tokens from localStorage or sessionStorage and exfiltrates them.

Mitigation: HttpOnly cookies + BFF

Store tokens server-side. Issue the browser an HttpOnly session cookie — JS cannot access it regardless of XSS. Combine with SameSite=Strict or SameSite=Lax for CSRF protection.

ATTACK JWT Algorithm Confusion (alg:none) ▶

An attacker crafts a token with "alg":"none" and no signature. Naive verifiers that trust the alg header accept it as valid.

Mitigation: allowlist algorithms

Never use the alg field in the token header to decide how to verify — always specify the expected algorithm in your verifier code. Reject none always. Prefer RS256 over HS256 for multi-party scenarios.

Refresh Tokens & Rotation

Refresh tokens are long-lived credentials for getting new access tokens silently. They need careful handling.

// POST /token — refresh grant (back-channel, server-side)
const res = await fetch('https://auth.example.com/token', {
  method: 'POST',
  body: new URLSearchParams({
    grant_type:    'refresh_token',
    refresh_token: storedRefreshToken,
    client_id:     'my-app',
    client_secret: process.env.CLIENT_SECRET,
  })
});
const { access_token, refresh_token } = await res.json();
// store new refresh_token — old one is now invalid (rotation)
Refresh Token Rotation
Single-use refresh tokens

Each time a refresh token is used, a new one is issued and the old one invalidated. If a stolen token is used, the legitimate user's next refresh fails — alerting you to the theft.

Refresh Token Families
Reuse detection

Servers track "families" of rotated tokens. If an already-used token is presented (indicating theft), the entire family is revoked — logging out all devices for that user.

Refresh token storage

Refresh tokens are as sensitive as passwords. Store them server-side only (database or encrypted store). Never in localStorage, never in the browser. Treat exposure of a refresh token as equivalent to account compromise.
