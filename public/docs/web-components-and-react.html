Web Components from the Ground Up — and Wrapping Them in React

How custom elements, Shadow DOM, and HTML templates work at the platform level — and how to wrap them in first-class React components with TypeScript, refs, and proper event handling.

Deep dive
~25 min read
For React and platform developers
June 2026

There is a moment every team eventually hits: you have a component library built in React, your design system is humming along, and then someone asks whether it could work in the Vue project, or the legacy jQuery app, or the server-rendered Astro site that marketing just launched. The honest answer, usually, is no. Not without rewriting it.

Web Components are the platform's answer to that problem. They are not a framework. They are a collection of browser APIs that let you define custom, reusable HTML elements that work anywhere HTML works — in React, in Vue, in a plain HTML file, in an email renderer that supports custom elements. Understanding them is genuinely useful, even if you live in React all day, because knowing where your framework ends and the platform begins makes you a sharper developer.

In this post we will cover every major Web Component API, build a real BaseButton custom element step by step, and then write a first-class React wrapper around it — with proper TypeScript types, refs, hooks, and event handling.

A brief history

The idea of extending HTML with custom tags is nearly as old as the web itself. In 2011, Alex Russell and the Chrome team at Google published the first draft of what they called "Web Components" — a set of four related specifications: Custom Elements, Shadow DOM, HTML Templates, and HTML Imports. The ambition was enormous: a native component model for the web that required no build tools and no framework.

Browser vendors disagreed on the details for years. Firefox and Apple resisted parts of the v0 API. HTML Imports were eventually dropped entirely. The community moved on to v1 of the spec in 2016, and by 2020 all major browsers had shipped compatible implementations. Google's Polymer library, which had been the de facto way to use Web Components during the turbulent v0 era, gave way to lighter libraries like Lit, FAST, and Stencil. Today the APIs are stable, well-supported, and genuinely pleasant to use.

What did not change over that decade is the core motivation: a way to package behaviour, markup, and styles together in a self-contained unit, without depending on any particular framework to parse or execute it.

What they are — and what they are good at

Web Components are built on three browser APIs that can be used independently or together:

Custom Elements let you define a new HTML tag — say, <base-button> — backed by a JavaScript class. The browser upgrades any matching element in the DOM by instantiating your class and calling lifecycle hooks.

Shadow DOM attaches a private subtree to your element. Styles defined inside the shadow root do not leak out, and external styles do not bleed in, which makes your component genuinely encapsulated.

HTML Templates give you a <template> element whose content is parsed but not rendered. You clone from it to stamp out DOM cheaply and safely.

Web Components are strongest when the thing you are building needs to cross framework boundaries. A design system button, a date picker, a media player, a syntax highlighted code block — these are all good candidates. They are also a natural fit for teams that ship embeddable widgets, micro-frontends, or components that will outlive any particular framework choice.

They are less suited to application-level concerns: routing, global state, server data fetching. For those, use the framework that has already solved them well.

How they differ from React components

React components and Web Components look similar on the surface — both encapsulate markup, behaviour, and optionally styles — but they operate at completely different layers.

A React component is a JavaScript function or class that React's reconciler knows how to render. It only exists inside a React tree. Its lifecycle (useEffect, componentDidMount) is managed by React, not the browser. Passing data in means passing JS values as props. Responding to changes means re-rendering.

A custom element, by contrast, is a browser citizen. Its lifecycle is managed by the DOM itself. Data flows in through HTML attributes (strings) and JavaScript properties (any value). Its events are regular DOM events. React, Vue, or plain JavaScript can all interact with it through the same DOM APIs they use to interact with a <div>.

Key distinction

React manages a virtual DOM that eventually maps to real DOM. Custom elements are real DOM — the browser manages them directly. When you use a custom element inside a React tree, React still only sees an opaque DOM node; it has no awareness of the element's internal lifecycle or shadow DOM.

This is why wrapping a Web Component for use in React requires a little care: you need to manually bridge the gap between React's prop/event model and the DOM's attribute/property/event model.

Custom Elements

The entry point to Web Components is HTMLElement. Every custom element extends it, either directly or through one of the specialised subclasses like HTMLButtonElement. Custom element tag names must contain a hyphen — this is a parsing rule that reserves single-word names for future HTML elements.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  // The browser calls this once, when the class is first defined.
  constructor() {
    super(); // always first
  }
}

The super() call is non-negotiable: it sets up the element's prototype chain and associates the instance with the underlying DOM node. Leave it out and the browser throws a ReferenceError before you can do anything else.

Defining elements

Once you have a class, you register it with the Custom Elements registry using customElements.define. From that moment forward, every <base-button> in the document — including ones already in the DOM — will be upgraded.

base-button.ts TypeScript 
// Pass the tag name, then the class. The name must contain a hyphen.
customElements.define('base-button', BaseButton);

Registrations are permanent and global — you cannot undefine an element, and you cannot redefine the same name. In practice this means you need to guard against double-registration in module-heavy environments:

base-button.ts TypeScript 
if (!customElements.get('base-button')) {
  customElements.define('base-button', BaseButton);
}

Shadow DOM

Shadow DOM creates a separate DOM tree attached to your element. Code outside the component cannot query into it with document.querySelector, styles do not cross the boundary by default, and IDs inside the shadow root are scoped to it. This is real encapsulation — not naming conventions, not CSS Modules, not build-time transforms.

You attach a shadow root inside the constructor:

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;

  constructor() {
    super();
    // 'open' lets JS outside the element reach shadow internals
    // via element.shadowRoot. Use 'closed' to prevent that.
    this.shadow = this.attachShadow({ mode: 'open' });
  }
}

mode: 'open' is almost always what you want. Closed shadow roots are a footgun — they break accessibility tools and testing libraries without providing meaningful security, since motivated code can always get around them.

Setting CSS

Styles inside a shadow root are written as regular CSS but are completely scoped. The :host pseudo-class lets you style the custom element itself — the outer DOM node — from within the shadow. The modern approach uses Constructable Stylesheets, which lets multiple elements share a single parsed stylesheet object rather than injecting a <style> tag per instance.

base-button.ts TypeScript 
// Create once at module scope so all instances share one stylesheet
const sheet = new CSSStyleSheet();
sheet.replaceSync(`
  :host {
    display: inline-flex;
    align-items: center;
    justify-content: center;
    gap: 0.5em;
    font-family: inherit;
    cursor: pointer;
    border: none;
    border-radius: 6px;
    font-weight: 500;
    transition: opacity 0.15s, transform 0.1s;
  }

  :host([disabled]) {
    opacity: 0.45;
    pointer-events: none;
    cursor: not-allowed;
  }

  /* Variant: primary (default) */
  :host([variant="primary"]) button,
  :host(:not([variant])) button {
    background: #f0a500;
    color: #0d0f14;
  }

  /* Variant: secondary */
  :host([variant="secondary"]) button {
    background: transparent;
    border: 1.5px solid currentColor;
    color: #f0a500;
  }

  /* Variant: ghost */
  :host([variant="ghost"]) button {
    background: transparent;
    color: #c8ccd8;
  }

  /* Size */
  :host([size="sm"]) button { padding: 0.3em 0.75em; font-size: 0.8rem; }
  :host([size="md"]) button,
  :host(:not([size])) button { padding: 0.5em 1.1em; font-size: 0.9rem; }
  :host([size="lg"]) button { padding: 0.7em 1.5em; font-size: 1rem; }

  button {
    all: unset;
    width: 100%;
    cursor: inherit;
    display: inline-flex;
    align-items: center;
    justify-content: center;
  }
`);

class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    // Adopt the shared stylesheet
    this.shadow.adoptedStyleSheets = [sheet];
  }
}

CSS Custom Properties (variables) defined on :host or outside the component do cross the shadow boundary — this is intentional. It is the recommended way to expose a theming API from a Web Component: define --base-button-radius on :host, let consumers override it on the element or any ancestor.

HTML Templates

A <template> element's content is a DocumentFragment that is parsed by the HTML parser but never rendered. Cloning it is cheap — no re-parsing, no layout, no paint. The <slot> element inside a template is a placeholder for light DOM children, which lets consumers of your component write natural HTML inside the tag.

base-button.ts TypeScript 
const template = document.createElement('template');
template.innerHTML = `
  <button part="button">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

// Inside the constructor, clone and append:
this.shadow.appendChild(template.content.cloneNode(true));

The part attribute on the inner button is worth noting: it exposes a named part to the ::part() CSS pseudo-element, letting consumers style internals from outside the shadow root in a controlled way.

Building BaseButton — step by step

Now that the primitives are in place, let us build the component properly. We will cover lifecycle callbacks, observed attributes, properties, and events in sequence, ending with the full component.

Lifecycle callbacks

Custom elements have four lifecycle callbacks. Three of them matter in practice:

connectedCallback fires when the element is inserted into a document. This is the right place to attach event listeners, start observers, or render imperative content that depends on being in the DOM. Equivalent to a combination of React's useLayoutEffect and component mount.

disconnectedCallback fires when the element is removed from a document. Clean up event listeners and any external subscriptions here. Equivalent to the cleanup return of a React useEffect.

attributeChangedCallback fires when one of the element's observed attributes changes. More on this shortly.

The fourth — adoptedCallback — fires when the element is moved into a different document (via document.adoptNode). This is rare in practice; you will almost never need it.

A gotcha with connectedCallback

An element can be connected and disconnected multiple times — for example if it is moved in the DOM. Do not assume connectedCallback runs exactly once. Relatedly, you should always remove listeners in disconnectedCallback, even if you think the element is permanent.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;
  private innerButton: HTMLButtonElement | null = null;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    this.shadow.adoptedStyleSheets = [sheet];
    this.shadow.appendChild(template.content.cloneNode(true));
  }

  connectedCallback() {
    this.innerButton = this.shadow.querySelector('button');
    this.innerButton?.addEventListener('click', this.handleClick);
    this.syncDisabled();
    this.syncType();
  }

  disconnectedCallback() {
    this.innerButton?.removeEventListener('click', this.handleClick);
    this.innerButton = null;
  }
}

Observed attributes and attributeChangedCallback

Attributes on a custom element are strings — always. If you write <base-button disabled>, the attribute value is an empty string, not a boolean. The browser will only call attributeChangedCallback for attributes listed in the static observedAttributes array. If you do not list an attribute there, changes to it are silently ignored.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  // Tell the browser which attributes to watch
  static get observedAttributes(): string[] {
    return ['disabled', 'variant', 'size', 'type'];
  }

  attributeChangedCallback(
    name: string,
    _oldValue: string | null,
    newValue: string | null
  ) {
    switch (name) {
      case 'disabled':
        this.syncDisabled();
        break;
      case 'type':
        this.syncType();
        break;
    }
    // variant and size are read directly from the attribute in CSS
    // via :host([variant="…"]), so no JS sync needed for those.
  }

  private syncDisabled() {
    if (this.innerButton) {
      this.innerButton.disabled = this.hasAttribute('disabled');
    }
  }

  private syncType() {
    if (this.innerButton) {
      const t = this.getAttribute('type') ?? 'button';
      this.innerButton.type = t as HTMLButtonElement['type'];
    }
  }
}

Notice that attributeChangedCallback may fire before connectedCallback. This can happen when the element is parsed from HTML — attributes are processed first. The sync methods guard against a null innerButton for exactly this reason.

Properties and upgrading them

Attributes are a limited surface: they only accept strings, and they are part of the HTML serialisation. For richer data — booleans, numbers, objects — you expose JavaScript properties on the element class. Properties and attributes should mirror each other for the common cases, using a pattern sometimes called "attribute/property reflection":

base-button.ts TypeScript 
type Variant = 'primary' | 'secondary' | 'ghost';
type Size    = 'sm' | 'md' | 'lg';
type BtnType = 'button' | 'submit' | 'reset';

class BaseButton extends HTMLElement {
  // Expose a boolean `disabled` property that mirrors the attribute
  get disabled(): boolean {
    return this.hasAttribute('disabled');
  }
  set disabled(value: boolean) {
    value
      ? this.setAttribute('disabled', '')
      : this.removeAttribute('disabled');
  }

  get variant(): Variant {
    return (this.getAttribute('variant') ?? 'primary') as Variant;
  }
  set variant(value: Variant) {
    this.setAttribute('variant', value);
  }

  get size(): Size {
    return (this.getAttribute('size') ?? 'md') as Size;
  }
  set size(value: Size) {
    this.setAttribute('size', value);
  }

  get type(): BtnType {
    return (this.getAttribute('type') ?? 'button') as BtnType;
  }
  set type(value: BtnType) {
    this.setAttribute('type', value);
  }
}

There is a subtle problem here called the property upgrade timing issue. If someone sets myButton.disabled = true using JavaScript before the custom element class has been defined and the element upgraded, the property assignment goes to the raw DOM node as a plain expando — not through your setter. When the upgrade eventually happens, your setter never fires.

The fix is to check for and apply any pre-upgrade expando properties in connectedCallback:

base-button.ts TypeScript 
private upgradeProperty(prop: keyof this) {
  if (Object.prototype.hasOwnProperty.call(this, prop)) {
    const value = this[prop];
    delete this[prop]; // remove the expando
    this[prop] = value;  // re-set through the class setter
  }
}

connectedCallback() {
  this.upgradeProperty('disabled');
  this.upgradeProperty('variant');
  this.upgradeProperty('size');
  this.upgradeProperty('type');
  // ... rest of setup
}

Custom events

Web Components communicate outward through DOM events. The convention is to dispatch a CustomEvent with a namespaced name — prefixing with the component name prevents collisions. Setting composed: true is required when an event originates within a shadow tree and must cross the shadow boundary. It is not strictly necessary when dispatching from the host element itself.

base-button.ts TypeScript 
// Type the detail payload for consumers
interface BaseButtonClickDetail {
  originalEvent: MouseEvent;
  variant: Variant;
  disabled: boolean;
}

private handleClick = (e: MouseEvent) => {
  // Prevent the native click from propagating out of the shadow
  e.stopPropagation();

  const detail: BaseButtonClickDetail = {
    originalEvent: e,
    variant: this.variant,
    disabled: this.disabled,
  };

  this.dispatchEvent(
    new CustomEvent<BaseButtonClickDetail>('base-button:click', {
      detail,
      bubbles:  true,
      composed: true, // cross the shadow boundary
    })
  );
};

// Arrow function stored as a class field so `this` is always bound,
// and so the exact same reference can be removed in disconnectedCallback.

The arrow function stored as a class field is important. If you used a regular method reference (this.handleClick), each call to addEventListener and removeEventListener would need the same bound reference — a common source of listener leaks.

The full component

Putting it all together, here is the complete BaseButton:

base-button.ts TypeScript 
type Variant = 'primary' | 'secondary' | 'ghost';
type Size    = 'sm' | 'md' | 'lg';
type BtnType = 'button' | 'submit' | 'reset';

export interface BaseButtonClickDetail {
  originalEvent: MouseEvent;
  variant: Variant;
  disabled: boolean;
}

// ── Shared stylesheet ──────────────────────────────────
const sheet = new CSSStyleSheet();
sheet.replaceSync(`
  :host {
    display: inline-flex;
    align-items: center;
    justify-content: center;
    font-family: inherit;
    cursor: pointer;
    border-radius: var(--base-button-radius, 6px);
  }
  :host([disabled]) { opacity: 0.45; pointer-events: none; }
  :host([variant="primary"]) button,
  :host(:not([variant])) button { background: #f0a500; color: #0d0f14; }
  :host([variant="secondary"]) button {
    background: transparent; border: 1.5px solid #f0a500; color: #f0a500;
  }
  :host([variant="ghost"]) button { background: transparent; color: #c8ccd8; }
  :host([size="sm"]) button { padding: 0.3em 0.75em; font-size: 0.8rem; }
  :host(:not([size])) button,
  :host([size="md"]) button { padding: 0.5em 1.1em; font-size: 0.9rem; }
  :host([size="lg"]) button { padding: 0.7em 1.5em; font-size: 1rem; }
  button {
    all: unset; cursor: inherit; width: 100%;
    display: inline-flex; align-items: center; justify-content: center;
    font-weight: 500; border-radius: inherit; gap: 0.5em;
  }
`);

// ── Template ───────────────────────────────────────────
const template = document.createElement('template');
template.innerHTML = `
  <button part="button">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

// ── Element class ──────────────────────────────────────
export class BaseButton extends HTMLElement {
  static readonly tagName = 'base-button';

  static get observedAttributes() {
    return ['disabled', 'variant', 'size', 'type'] as const;
  }

  private shadow: ShadowRoot;
  private innerButton: HTMLButtonElement | null = null;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    this.shadow.adoptedStyleSheets = [sheet];
    this.shadow.appendChild(template.content.cloneNode(true));
  }

  // ── Lifecycle ──────────────────────────────────────────
  connectedCallback() {
    this.upgradeProperty('disabled');
    this.upgradeProperty('variant');
    this.upgradeProperty('size');
    this.upgradeProperty('type');

    this.innerButton = this.shadow.querySelector('button');
    this.innerButton?.addEventListener('click', this.handleClick);
    this.syncAll();
  }

  disconnectedCallback() {
    this.innerButton?.removeEventListener('click', this.handleClick);
    this.innerButton = null;
  }

  attributeChangedCallback(
    name: string,
    _old: string | null,
    _next: string | null
  ) {
    if (name === 'disabled') this.syncDisabled();
    if (name === 'type') this.syncType();
  }

  // ── Properties ────────────────────────────────────────
  get disabled() { return this.hasAttribute('disabled'); }
  set disabled(v: boolean) {
    v ? this.setAttribute('disabled', '') : this.removeAttribute('disabled');
  }

  get variant(): Variant {
    return (this.getAttribute('variant') ?? 'primary') as Variant;
  }
  set variant(v: Variant) { this.setAttribute('variant', v); }

  get size(): Size {
    return (this.getAttribute('size') ?? 'md') as Size;
  }
  set size(v: Size) { this.setAttribute('size', v); }

  get type(): BtnType {
    return (this.getAttribute('type') ?? 'button') as BtnType;
  }
  set type(v: BtnType) { this.setAttribute('type', v); }

  // ── Private helpers ────────────────────────────────────
  private upgradeProperty(prop: keyof this) {
    if (Object.prototype.hasOwnProperty.call(this, prop)) {
      const value = this[prop];
      delete this[prop];
      this[prop] = value;
    }
  }

  private syncDisabled() {
    if (this.innerButton) this.innerButton.disabled = this.disabled;
  }

  private syncType() {
    if (this.innerButton)
      this.innerButton.type = this.type as HTMLButtonElement['type'];
  }

  private syncAll() {
    this.syncDisabled();
    this.syncType();
  }

  // ── Event handler ──────────────────────────────────────
  private handleClick = (e: MouseEvent) => {
    e.stopPropagation();
    this.dispatchEvent(
      new CustomEvent<BaseButtonClickDetail>('base-button:click', {
        detail: {
          originalEvent: e,
          variant: this.variant,
          disabled: this.disabled,
        },
        bubbles: true,
        composed: true,
      })
    );
  };
}

// ── Registration ───────────────────────────────────────
if (!customElements.get(BaseButton.tagName)) {
  customElements.define(BaseButton.tagName, BaseButton);
}

Wrapping BaseButton in React

React 19 (released December 2024) brought long-overdue improvements to custom element support. On the client, React now checks whether a prop name matches a property on the custom element instance, and if so, sets it as a JavaScript property rather than an HTML attribute. It also added declarative event listener support: you can pass on + the event name as a JSX prop and React will call addEventListener for you. These two changes mean that for simple use cases, dropping a custom element into a React tree just works.

React 19 property/attribute strategy

On the client, props matching a property on the custom element instance are set as JS properties; the rest become attributes. On the server (SSR), primitive props (string, number, true) render as attributes; non-primitive props are omitted to avoid hydration mismatches. This means complex props like objects still require the imperative ref approach when SSR is involved.

Despite these improvements, a typed wrapper component is still the right call for a design system. Using <base-button> bare in JSX gives you no TypeScript safety on props, no onButtonClick callback mapped to the right detail type, and no forwarded ref that the consumer can rely on. The wrapper layer is thin, but it converts a loosely-typed DOM element into a properly-typed React component.

In React 19, forwardRef is deprecated — ref is now a plain prop on function components. We write the wrapper accordingly.

TypeScript global declarations

Before writing the component, register the custom element with TypeScript so that document.querySelector('base-button') returns a typed BaseButton instance, and so JSX knows what props the bare tag accepts.

base-button.d.ts TypeScript 
import { BaseButton } from './base-button';

declare global {
  // Allows: document.querySelector('base-button') → BaseButton
  interface HTMLElementTagNameMap {
    'base-button': BaseButton;
  }

  // Allows JSX: <base-button ...> — use React.HTMLAttributes as the base,
  // then add the element's own props. 'ref' is handled by React itself.
  namespace React {
    namespace JSX {
      interface IntrinsicElements {
        'base-button': React.HTMLAttributes<BaseButton> & {
          variant?: BaseButton['variant'];
          size?: BaseButton['size'];
          type?: BaseButton['type'];
          disabled?: boolean;
        };
      }
    }
  }
}

Helper hooks

Three small hooks do the heavy lifting for the wrapper. They are generic enough to be reused across any custom element in your system.

useCustomElementProperty sets a DOM property imperatively whenever its value changes. This is useful for non-primitive props — objects, arrays, complex types — that React 19 would otherwise omit during SSR or fail to set correctly.

useCustomElementProperty.ts TypeScript 
import { RefObject, useEffect } from 'react';

export function useCustomElementProperty<
  El extends HTMLElement,
  K extends keyof El
>(
  ref: RefObject<El | null>,
  property: K,
  value: El[K]
): void {
  useEffect(() => {
    const el = ref.current;
    if (el !== null) {
      el[property] = value;
    }
  }, [ref, property, value]);
}

useCustomElementEvent subscribes to a DOM custom event on the element and calls a React callback, cleaning up automatically on unmount or when the handler reference changes. Even though React 19 can wire up on-prefixed JSX props to addEventListener, doing so via a hook keeps the event strongly typed against CustomEvent<D> and keeps the wrapper's internal logic explicit.

useCustomElementEvent.ts TypeScript 
import { RefObject, useEffect } from 'react';

export function useCustomElementEvent<
  El extends HTMLElement,
  D = unknown
>(
  ref: RefObject<El | null>,
  eventName: string,
  handler: ((e: CustomEvent<D>) => void) | undefined
): void {
  useEffect(() => {
    const el = ref.current;
    if (!el || !handler) return;

    const listener = (e: Event) =>
      handler(e as CustomEvent<D>);

    el.addEventListener(eventName, listener);
    return () => el.removeEventListener(eventName, listener);
  }, [ref, eventName, handler]);
}

useMergedRefs combines multiple refs into a single callback ref. This lets the wrapper hold an internal RefObject for imperative DOM access, while simultaneously forwarding a ref to the consumer — all without either ref interfering with the other.

useMergedRefs.ts TypeScript 
import { Ref, useCallback } from 'react';

type AnyRef<T> = Ref<T> | undefined | null;

export function useMergedRefs<T>(
  ...refs: AnyRef<T>[]
): (node: T | null) => void {
  // eslint-disable-next-line react-hooks/exhaustive-deps
  return useCallback((node: T | null) => {
    for (const ref of refs) {
      if (!ref) continue;
      if (typeof ref === 'function') {
        ref(node);
      } else {
        (ref as React.MutableRefObject<T | null>).current = node;
      }
    }
  }, refs); // stable as long as the refs array members don't change
}
Why useCallback here?

React calls a callback ref every render if its function identity changes, triggering unnecessary detach/re-attach cycles. useCallback memoises the merged ref so it only changes when the incoming refs themselves change. Note that the eslint exhaustive-deps rule would flag this — the disable comment is intentional since refs is a rest argument spread, not a stable array reference.

The wrapper component

With the hooks in place, the wrapper itself is straightforward. Since forwardRef is deprecated in React 19, we accept ref as a plain prop. The internal useRef is needed to drive the imperative hooks; useMergedRefs unifies it with whatever the consumer passes.

Button.tsx TypeScript · React 19 
import { useRef, Ref } from 'react';
import { BaseButton, BaseButtonClickDetail } from './base-button';
import { useCustomElementEvent } from './useCustomElementEvent';
import { useCustomElementProperty } from './useCustomElementProperty';
import { useMergedRefs } from './useMergedRefs';

export interface ButtonProps {
  variant?: BaseButton['variant'];
  size?: BaseButton['size'];
  type?: BaseButton['type'];
  disabled?: boolean;
  onButtonClick?: (detail: BaseButtonClickDetail) => void;
  children?: React.ReactNode;
  className?: string;
  style?: React.CSSProperties;
  // React 19: ref is a plain prop, no forwardRef needed
  ref?: Ref<BaseButton>;
}

export function Button({
  variant = 'primary',
  size = 'md',
  type = 'button',
  disabled = false,
  onButtonClick,
  children,
  className,
  style,
  ref: externalRef,
}: ButtonProps) {
  // Internal ref for imperative hooks
  const innerRef = useRef<BaseButton | null>(null);

  // Merge the internal ref with any ref the consumer passed in
  const mergedRef = useMergedRefs(innerRef, externalRef);

  // Set properties directly on the DOM element.
  // For primitives React 19 handles this via JSX, but doing it here
  // is explicit, SSR-safe, and works regardless of React version.
  useCustomElementProperty(innerRef, 'variant', variant);
  useCustomElementProperty(innerRef, 'size', size);
  useCustomElementProperty(innerRef, 'type', type);
  useCustomElementProperty(innerRef, 'disabled', disabled);

  // Subscribe to the custom event via the DOM — strongly typed.
  useCustomElementEvent<BaseButton, BaseButtonClickDetail>(
    innerRef,
    'base-button:click',
    onButtonClick ? (e) => onButtonClick(e.detail) : undefined
  );

  return (
    <base-button
      ref={mergedRef}
      class={className}
      style={style}
    >
      {children}
    </base-button>
  );
}

A few things worth pointing out. The JSX element uses class not className — it is a native element, not a React component, so React's aliasing does not apply. We still accept className as a prop and pass it through as class to give consumers the familiar React API.

No props for variant, size, type, or disabled appear on the JSX element itself. All four go through useCustomElementProperty via the ref, which means they set the DOM property directly and trigger the element's own setters. This sidesteps React 19's SSR/attribute ambiguity entirely and makes the prop-to-DOM mapping explicit and testable.

Using the wrapper looks exactly like any other React component:

App.tsx TypeScript · React 
import { useRef } from 'react';
import { Button } from './Button';
import { BaseButtonClickDetail } from './base-button';

function App() {
  const btnRef = useRef<BaseButton | null>(null);

  const handleClick = (detail: BaseButtonClickDetail) => {
    console.log('clicked', detail.variant);
  };

  return (
    <Button
      ref={btnRef}
      variant="primary"
      size="lg"
      onButtonClick={handleClick}
    >
      Save changes
    </Button>
  );
}

The BaseButton custom element owns rendering and its own lifecycle. The Button React wrapper owns the React integration surface. Neither knows too much about the other: you can evolve the component's internals — new slots, tweaked styles, additional properties — without touching the wrapper, and you can refine the wrapper's React patterns without touching the element class.

Web Components are not trying to compete with React. They live at a lower layer — the browser platform — and that is exactly what makes them useful as a foundation for design systems that need to outlast any particular framework. The wrapping pattern we built here is one you can apply to any custom element: three small generic hooks, one thin wrapper component, and you have a first-class React citizen with full TypeScript safety.

The APIs are stable, the browser support is universal, and the tooling — Lit, FAST, Stencil, or even vanilla as we did here — is mature. It is a good time to know how they work.
