The handshake
and the seal

Encryption keeps the data moving between a browser and a server private. Certificates prove that the server on the other end is actually who it claims to be. HTTPS bundles both together — and most of the confusion around it has nothing to do with encryption at all. It's the identity half that gets complicated, especially once private, company-internal services enter the picture.

HTTPS solves two separate problems

Most developers already have a working knowledge of symmetric and asymmetric encryption, and that's the easier half of this story. The harder half — the one certificates exist to solve — is identity.

Encryption

Stop anyone on the network — a coffee-shop Wi-Fi, a misconfigured proxy, a curious neighbor on the VPN — from reading the traffic passing between client and server. This is what most people mean when they say "HTTPS."

solved by symmetric + asymmetric crypto

Identity

Prove that the server on the other end of a connection is actually the one it claims to be, not something impersonating it. This depends entirely on certificates, and it's the part that causes the most confusion once internal, non-public services enter the picture.

solved by certificates + a chain of trust

Both problems get solved in a handful of round trips, before a single byte of the page loads. Here's the sequence.

Beyond privacy

Why HTTPS matters even with nothing to hide

Browsers don't only use connection security to decide whether to show a warning icon. A long list of capabilities are gated behind what's called a secure context, regardless of whether the page actually handles anything sensitive — they simply refuse to initialize over plain HTTP. localhost gets an exemption, covered below, but a plain internal hostname over HTTP does not. This is often the real reason an internal tool needs HTTPS in development: not because it's transmitting secrets, but because a feature it depends on won't run without one.

Where the warning actually comes from

Trust stores, and why internal certs get flagged

~150
root Certificate Authorities ship preinstalled in most operating systems and browsers. Public CAs like Let's Encrypt chain up to one of these, which is why their certificates "just work" with no warning.

Companies often run their own internal certificate authority for services that were never meant to be public. Those certificates are perfectly valid technically, but they're untrusted by browsers and tools like Node.js unless that internal CA's certificate has been explicitly added to the relevant trust store. A device that's never been told to trust it treats the certificate exactly like a self-signed one — same red triangle, same "connection is not private" page.

The fix isn't a different kind of certificate — it's distribution. Once an internal root CA's public certificate is installed into the trust store on every device that needs to reach those internal services, typically pushed out once via MDM or group policy, the warnings disappear.

Node.js

A second, separate trust store

Getting a CA trusted by the operating system fixes the browser — but Node.js doesn't read that same OS trust store by default. It ships with its own bundled list of root certificates. A Node script, an SSR process, or a test runner calling that same HTTPS endpoint can still fail with UNABLE_TO_VERIFY_LEAF_SIGNATURE or self signed certificate in chain, on a machine where the browser shows no warning at all.

NODE_EXTRA_CA_CERTS=/path/to/ca.pem node server.js

The tempting shortcut is NODE_TLS_REJECT_UNAUTHORIZED=0, which disables certificate verification entirely rather than fixing the underlying trust problem — fine for a five-second debug, risky to leave anywhere near a real environment.

Applying this

The practical playbook

Three different situations, three different answers. Most "why is this cert broken" confusion comes from mixing these up.

Local dev · Vite

Make the local machine trusted

mkcert creates a tiny local CA, installs it into the local trust store, then issues real certificates for localhost or any other local hostname — no warnings.

mkcert -install
mkcert localhost app.local
// vite.config.js
import fs from 'node:fs'

export default {
  server: {
    https: {
      key: fs.readFileSync('./localhost-key.pem'),
      cert: fs.readFileSync('./localhost.pem'),
    },
  },
}

Quicker but noisier: @vitejs/plugin-basic-ssl auto-generates a self-signed cert — the browser will still warn.

Shared internal envs

One CA, company-wide

Staging, QA, and internal tools shared across teams typically rely on a company-run internal CA, usually managed by a platform or IT team.

That CA issues certificates for *.internal.company.com-style domains, and its root certificate gets pushed to every employee device once.

If a warning shows up on one machine but not another, it's almost always a device missing that root certificate — not a broken deployment.

Production-style services

Let the edge handle it

A Node application usually shouldn't terminate TLS itself. A reverse proxy or load balancer placed in front holds the real certificate instead.

# nginx terminates TLS,
# proxies to Node in plain HTTP
listen 443 ssl;
ssl_certificate     app.crt;
ssl_certificate_key app.key;
location / {
  proxy_pass http://127.0.0.1:3000;
}

Node listens on plain HTTP behind it, inside the network boundary the proxy already secured.

Field notes

Things that trip people up

Expiry isn't optional

Automated certs often last 90 days, not a year. No exceptions for "1 second past expired." Automate renewal or it breaks silently, usually at the worst time.

SAN, not CN

Modern browsers ignore the old Common Name field entirely. If a hostname isn't listed in the Subject Alternative Name field, the certificate fails validation — even when the CN looks correct.

Mixed content

An https page calling an http API gets the request silently blocked. Common when a Vite dev server is https but proxies to a plain-http backend.

"Untrusted" ≠ "unencrypted"

A self-signed certificate still encrypts the connection fine. The warning is purely about identity verification — not about weaker encryption.

localhost gets a free pass

http://localhost is treated as a secure context automatically by browsers. app.internal.company.com gets no such exemption.

Check the whole chain

A server that sends only its leaf cert and forgets the intermediate will work in some browsers and fail in others, depending on what's cached.

HSTS remembers

Once a browser sees a Strict-Transport-Security header for a domain, it refuses plain HTTP for that domain again for the cached duration — no warning, just an automatic redirect or a hard failure. Some entries are even browser-preloaded and effectively permanent.

Certificate Transparency

Certificates from public CAs like Let's Encrypt get published to public CT logs by design. An internal-only hostname issued one of these becomes publicly searchable, even though the service behind it isn't reachable.

Wildcards aren't infinite

A certificate for *.internal.company.com covers exactly one subdomain level — not deeper nesting like api.app.internal.company.com, and not the bare domain itself.
