Browser Security: Attacks and Defenses

XSS, CSRF, clickjacking, and the HTTP headers that defend against them. Understanding how each attack works makes the defenses obvious.

Deep dive
~18 min read
Browser security
June 2026

Browsers enforce a set of security boundaries that web applications rely on, but those boundaries can be circumvented if an application makes certain mistakes. This article covers the most common browser-targeted attacks, what makes them possible, and the combination of application-level practices and HTTP headers that defend against them. The security principles article provides the conceptual background.

Cross-Site Scripting (XSS)

XSS lets an attacker inject JavaScript into a page viewed by other users. Once running in a victim's browser, that script has the same capabilities as any legitimate script on the page.

How it works

XSS occurs when an application takes untrusted data (from a user, a URL, a database) and outputs it into a page without escaping it. The browser then parses that data as markup and executes it.

There are three main forms. Stored XSS is the most severe: the malicious payload is saved to the database (in a comment, a profile name, a message) and injected into the page for every user who views it. Reflected XSS is delivered via a crafted URL; the server reflects the payload back in the response without storing it, and the attack typically requires tricking a victim into clicking a link. DOM-based XSS never reaches the server. The vulnerability is in client-side JavaScript that unsafely writes URL parameters or user input into the DOM.

What an attacker can do once JavaScript is executing in the victim's browser: read cookies (unless HttpOnly prevents it), steal tokens from localStorage, make authenticated API requests as the user, log every keystroke, redirect to a phishing page, or silently modify page content.

Defenses

The primary defense is output encoding: any untrusted data inserted into HTML must be escaped so that it cannot be interpreted as markup. The characters that matter most are <, >, &, ", and ': escaped, these become &lt;, &gt;, and so on. Modern frontend frameworks (React, Vue, Angular, Svelte) escape output by default. The danger is bypassing these protections deliberately (dangerouslySetInnerHTML in React, v-html in Vue, or raw innerHTML in vanilla JavaScript) without first sanitizing the input through a trusted library like DOMPurify.

HttpOnly cookies don't prevent XSS but meaningfully limit its impact. A cookie marked HttpOnly is not accessible to JavaScript. document.cookie won't include it. This means an XSS payload cannot steal session tokens stored in HttpOnly cookies, which removes the most common goal of XSS attacks. This is why session cookies should always be HttpOnly.

Content Security Policy (CSP) is a response header that tells the browser which content sources are legitimate. It is a second line of defense: it does not fix the underlying vulnerability, but it can prevent an injected script from executing or exfiltrating data.

# Only allow scripts from the same origin — no inline scripts
Content-Security-Policy: script-src 'self'
 
# Allow scripts from self and a CDN
Content-Security-Policy: script-src 'self' https://cdn.example.com
 
# Allow specific inline scripts using a nonce
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m9x'

A nonce is a random value generated per response and added to both the CSP header and any inline <script> tags you control. The browser only executes inline scripts whose nonce matches. An injected script has no nonce, so even if XSS occurs, the script is blocked. Nonces must be genuinely random and must change on every response. A predictable or reused nonce is no protection.

X-Content-Type-Options: nosniff prevents the browser from guessing content types. Without it, a browser might execute a response as JavaScript if the content looks like a script, even if the server declared it as a different type. This closes a subtle XSS vector where an attacker uploads a file that looks like JavaScript and tricks the browser into executing it.

X-Content-Type-Options: nosniff
CSP in report-only mode

Deploying a new CSP policy can break legitimate functionality if you've missed an allowed source. Content-Security-Policy-Report-Only sends the same policy but only reports violations instead of blocking them, letting you audit the impact before enforcement. Pair it with a report-uri or report-to directive to collect violations in your logging infrastructure.

Cross-Site Request Forgery (CSRF)

CSRF exploits the browser's automatic cookie behavior to make authenticated requests on a victim's behalf, without the victim knowing.

How it works

Browsers automatically attach cookies to every request sent to an origin, regardless of where that request originates. This means a page on attacker.com can trigger a request to bank.com, and the browser will include the victim's bank.com session cookie. If the bank's server sees a valid session cookie, it processes the request (the transfer, the password change, the data deletion) without any indication that it came from a third-party page.

A classic example

A user is logged into their bank. They visit a page containing a hidden form that points to https://bank.com/transfer with the attacker's account as the recipient. The form submits automatically on page load. The bank receives a POST with the user's session cookie and processes the transfer. The user never saw a form.

CSRF only works for state-changing operations (POST, PUT, DELETE). The same-origin policy prevents the attacker's page from reading the response, so it can't steal data, only trigger actions.

Defenses

The modern defense is the SameSite cookie attribute, covered in depth in the HTTP article. With SameSite=Strict, session cookies are never sent on cross-site requests. The browser simply won't attach them. SameSite=Lax (the browser default since around 2020) blocks cookies on cross-site subrequests like form submissions and XHR, but allows them on top-level navigations. Either setting prevents the classic CSRF scenario above.

CSRF tokens are the traditional defense and remain necessary when cookie-based auth is used on older browsers or when SameSite cannot be relied on. The server embeds a unique, unpredictable token in each form or response. Every state-changing request must include this token. Because the attacker's page cannot read content from the victim's origin (same-origin policy), it cannot obtain the token and therefore cannot forge a valid request.

Attack
How CSRF works

Attacker's page triggers a cross-origin request. Browser automatically sends the victim's cookies. Server sees a valid session and processes the request.

Defense
What stops it

SameSite=Strict or Lax cookies are not sent on cross-site requests, so the session cookie never arrives. CSRF tokens verify the request originated from a page the server rendered.

Clickjacking

The attacker makes the victim click something they didn't intend to, by overlaying a transparent version of the target site on top of their own page.

How it works

An attacker embeds the target site in a transparent <iframe> and positions it precisely over a button or link on their own page. The user sees the attacker's page and thinks they're clicking the attacker's button. They're actually clicking a "Confirm Transfer" or "Delete Account" button on the embedded site, while authenticated in that site's session.

Defenses

The defense is preventing your pages from being embedded in iframes you don't control. Two mechanisms do this.

X-Frame-Options is the older header. DENY prevents embedding anywhere; SAMEORIGIN only allows embedding in iframes on the same origin.

X-Frame-Options: DENY

The CSP frame-ancestors directive is more flexible and supersedes X-Frame-Options in modern browsers. It accepts a list of permitted embedding origins.

# No embedding allowed anywhere
Content-Security-Policy: frame-ancestors 'none'
 
# Only allow embedding within the same origin
Content-Security-Policy: frame-ancestors 'self'
 
# Allow a specific trusted partner site
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com

Set both headers for maximum compatibility: X-Frame-Options: DENY for older browsers and frame-ancestors 'none' in CSP for modern ones.

Protocol Downgrade Attacks

HTTPS prevents eavesdropping, but only if the browser uses it. On the first visit, an attacker on the same network can intercept the initial HTTP request before HTTPS kicks in.

How it works

SSL stripping is an attack where the attacker sits between the user and the server (on a café WiFi network, for example) and intercepts the initial HTTP request to a site. Instead of forwarding it to the server, the attacker communicates with the server over HTTPS themselves, then relays a plain HTTP version back to the victim. The user thinks they're talking to the real site; they're actually talking to the attacker. Since the victim's connection is HTTP, all their data is visible and modifiable.

This works because users typically type a domain name without an explicit https:// prefix, and the browser's first request is HTTP. Even if the server immediately redirects to HTTPS, that redirect traverses the attacker's connection first.

Defense: HSTS

HTTP Strict Transport Security (HSTS) instructs the browser to always use HTTPS for a domain (even if the user types HTTP) for a specified period. Once the browser has seen the HSTS header, it converts any HTTP request for that domain to HTTPS before sending it, bypassing any attacker in the middle.

Strict-Transport-Security: max-age=31536000; includeSubDomains

max-age is in seconds: 31536000 is one year. includeSubDomains applies the policy to all subdomains, which prevents an attacker from attacking a subdomain to compromise the main site via cookies. preload (an optional additional directive) opts the domain into browser preload lists.

The first-visit problem and preloading

HSTS solves the problem for returning visitors, but not the first visit. The browser hasn't yet received the HSTS header. The HSTS preload list is a list of domains that major browsers ship with, instructing them to always use HTTPS before the first request. Submitting to the preload list at hstspreload.org is free, but it is a significant commitment: removing a domain takes months and requires coordination with browser vendors. Only submit if you are certain every subdomain of your domain can serve HTTPS indefinitely.

Supply Chain Attacks

When you load a third-party script, you trust that it will always contain what you expect. If the CDN or the script provider is compromised, your users run malicious code.

How it works

Including a script from a CDN with a plain <script src="..."> tag means whatever that URL serves, your users execute. If the CDN is breached or the script provider's account is compromised, the injected code runs with full access to the page and can steal form inputs, session data, or anything else on the page. This happened to Polyfill.io in 2024, affecting hundreds of thousands of sites that trusted a shared CDN.

Defense: Subresource Integrity

Subresource Integrity (SRI) lets you specify the expected hash of a resource. The browser refuses to execute the script if its content doesn't match.

HTML 
<script
  src="https://cdn.example.com/library.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>

The hash is generated from the exact file content at the time you add the tag. SRI only works for static, versioned assets. It cannot protect dynamically updated scripts (where the URL stays the same but the content changes), because any legitimate update would also break the hash. For dynamically updated third-party scripts, the only reliable mitigation is to self-host a pinned version and update it manually.

Information Leakage

Browsers share information with third parties as a side effect of normal navigation. Two headers give servers control over what gets shared.

Referrer-Policy

When a user navigates from one page to another, or when a page loads a third-party resource, the browser sends a Referer header containing the current page's URL. This is useful for analytics, but it can also leak sensitive information: if your URLs contain user IDs, session tokens, or search terms, every third-party resource on the page receives that data.

# Send only the origin (not the full URL) for cross-origin requests
Referrer-Policy: strict-origin-when-cross-origin

strict-origin-when-cross-origin is the browser default in modern browsers. It sends the full URL for same-origin requests (useful for internal analytics) and only the origin for cross-origin ones (no path, no query string). For pages that are genuinely sensitive, no-referrer sends nothing at all.

Permissions-Policy

Permissions-Policy controls which browser features a page and its embedded content can access: camera, microphone, geolocation, payment APIs, and others. A page that doesn't use the camera can declare that explicitly, which means a compromised third-party script embedded in the page cannot activate it even if it tries.

# Disable camera and microphone for this page and all iframes
Permissions-Policy: camera=(), microphone=()

An empty value () disables the feature entirely. (self) allows it for the page itself but not for embedded iframes. This header matters most for pages that embed third-party iframes or advertising. Restricting permissions limits what those third parties can do regardless of their own code.
