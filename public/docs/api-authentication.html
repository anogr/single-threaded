API Authentication: Tokens, Keys, and Sessions

Sessions, JWTs, refresh tokens, and API keys: the practical layer between authentication flows and running code.

Deep dive
~15 min read
Authentication
June 2026

The OAuth & OIDC article covers delegated authorization flows: how an application gets permission to act on a user's behalf. This article covers the layer underneath: what credentials actually look like, how they are validated, where they are stored, and the tradeoffs between different approaches. These decisions affect both security and architecture in ways that are hard to change later.

Authentication vs Authorization

Two concepts that are frequently conflated and almost as frequently implemented incorrectly.

Authentication establishes identity: who is making this request? It answers the question "are you who you claim to be?" through credentials: a password, a token, a certificate, a biometric. Authentication is binary: either the identity is established or it isn't.

Authorization establishes permission: given who you are, what are you allowed to do? It answers the question "do you have the right to perform this operation?" Authorization is always relative to an identity: you can't authorize someone you haven't authenticated. But authentication alone is not sufficient for authorization. A valid login doesn't mean you can access every resource.

Conflating the two is a common source of access control vulnerabilities. An application that checks "is this user logged in?" for every request but not "does this user own this resource?" has authenticated correctly but failed at authorization. The security principles article covers broken access control in more depth.

Sessions and Tokens

Two fundamentally different approaches to keeping a user authenticated across requests.

After a user logs in, every subsequent request needs to prove that they did. HTTP is stateless, so this proof must be carried in the request itself. There are two broad strategies.

Server-side sessions

The server creates a session record on login and returns an opaque session ID (a random string with no inherent meaning). The browser stores this ID (typically in a cookie) and sends it with every request. The server looks up the session ID in a store (a database or in-memory cache like Redis) to retrieve the associated user and their permissions.

Advantage
Easy to revoke

Deleting the session record immediately invalidates the session, everywhere. Logging out, detecting account compromise, or forcing re-authentication is instant and reliable.

Tradeoff
Shared state required

Every server instance must be able to look up any session. In a multi-server environment this requires a shared session store, which becomes a dependency to manage and a potential bottleneck.

Token-based authentication

The server encodes all necessary information (user ID, roles, expiry) directly into a signed token and returns it to the client. On subsequent requests, the client sends the token. The server validates the signature and reads the claims without consulting any external store. The server is stateless with respect to authentication.

Advantage
Stateless and scalable

Any server instance can validate a token independently. No shared session store is required. This makes token-based authentication a natural fit for microservices and horizontally scaled deployments.

Tradeoff
Difficult to revoke

A token is valid until it expires. Revoking a token before expiry requires either a revocation list (which every server must check, reintroducing shared state) or very short token lifetimes paired with refresh tokens.

JWT Structure

A JSON Web Token encodes identity claims and a cryptographic signature into a compact, URL-safe string.

A JWT consists of three base64url-encoded JSON objects separated by dots: a header, a payload, and a signature.

The header identifies the token type and signing algorithm. The payload contains claims: statements about the user and the token itself. Decoded, a typical payload looks like:

JSON — decoded payload 
{
  "sub": "user_123",          // subject — the user's ID
  "iss": "auth.example.com",  // issuer — who created this token
  "aud": "api.example.com",   // audience — who should accept it
  "exp": 1719489600,         // expiry — Unix timestamp
  "iat": 1719486000,         // issued at — when it was created
  "roles": ["editor"]       // custom claim — application-specific
}

The signature is computed over the header and payload using the server's private key (for RSA or ECDSA algorithms) or a shared secret (for HMAC). It allows any holder of the corresponding public key or shared secret to verify that the token hasn't been tampered with.

The payload is not encrypted

Base64url encoding is not encryption. It is reversible by anyone. The payload of a JWT is readable by anyone who intercepts the token. Never put passwords, secrets, or sensitive personal data in JWT claims. The signature prevents tampering, not reading.

JWT Validation

Accepting a JWT without fully validating it is as dangerous as accepting no authentication at all.

When a server receives a JWT, it must perform several checks before trusting any claim in it:

  1. Verify the signature. Compute the expected signature using the header's algorithm and the server's key, and compare it to the token's signature. If they don't match, the token has been tampered with or was not issued by a trusted party.
  2. Check exp. Reject the token if the current time is past the expiry timestamp. Allow a small tolerance (a few seconds) for clock skew between servers.
  3. Check iss. Verify the issuer is one you trust. This prevents tokens from one service being used at another.
  4. Check aud. Verify the audience matches your service. This prevents tokens intended for a different API from being accepted.

Most JWT libraries handle these checks if you pass the right options. The risk is misuse of the library: passing the wrong key, skipping validation options, or accepting the token's own claims about which algorithm to use.

JWT Pitfalls

JWTs are frequently misused. The most common mistakes share a theme: trusting the token before validating it.

Not validating the signature. This sounds too obvious to be a real mistake, but several high-profile incidents have involved JWT libraries that, depending on configuration, accepted tokens without verifying the signature. Always use a well-maintained library and check that signature verification is not disabled or configurable per-request.

The alg: none attack. Some early JWT implementations accepted a token that declared its algorithm as none, meaning no signature was needed. An attacker could set any claims they liked and the server would accept the token as valid. Modern libraries reject alg: none by default, but the lesson is to never accept the algorithm from the token itself. Specify the expected algorithm server-side.

Overly long expiry. A JWT that is valid for 30 days cannot be revoked if the user's account is compromised or deleted. Short-lived access tokens (15 minutes to 1 hour) paired with refresh tokens are the standard approach. The access token can't be revoked, but the damage is limited by its short lifetime.

Storing sensitive data in claims. As noted above, claims are readable by anyone who can intercept the token. Limit claims to identifiers and roles. Do not include personal data, permissions that shouldn't be visible, or anything you'd consider private.

Token Storage

Where you store a token determines what kind of attack can steal it. There is no option with no tradeoffs.

Browser-based applications must store authentication tokens somewhere the application can retrieve them to attach to API requests. The two main options are localStorage (or sessionStorage) and HttpOnly cookies, and they have opposite vulnerability profiles.

localStorage
Vulnerable to XSS

Any JavaScript running on the page can read localStorage. Even a small XSS vulnerability can exfiltrate the token to an attacker's server. The attacker then has the token and can use it from anywhere, independently of the browser session.

HttpOnly cookie
Vulnerable to CSRF

JavaScript cannot read an HttpOnly cookie, eliminating XSS-based token theft. However, cookies are sent automatically on cross-site requests, so an XSS-free application may still be vulnerable to CSRF unless SameSite is set correctly. See the browser security article.

The practical recommendation for most web applications is HttpOnly, Secure, SameSite=Strict cookies. This eliminates XSS-based token theft (cookie is not readable by scripts) and eliminates CSRF (cookie is not sent cross-site). The server sets the cookie on login. The browser attaches it automatically on every subsequent request.

Memory storage for SPAs

Some single-page applications store tokens in JavaScript memory (a module-level variable rather than any persistent storage). This prevents both XSS theft (nothing to steal from storage after a page refresh) and CSRF (not a cookie, not sent automatically). The downside is that the token is lost on page refresh, requiring silent re-authentication. This approach works well with refresh tokens and short-lived access tokens, and is increasingly the pattern recommended for SPAs that cannot use HttpOnly cookies (for example, because the API is on a different domain).

Refresh Tokens

Short-lived access tokens limit the damage if a token is stolen. Refresh tokens provide the mechanism to get new access tokens without asking the user to log in again.

The pattern works as follows: on login, the server issues two tokens: a short-lived access token (valid for 15 minutes to an hour) and a long-lived refresh token (valid for days or weeks). The application uses the access token for API calls. When the access token expires, the application presents the refresh token to a dedicated endpoint and receives a new access token.

If the access token is stolen, the attacker has a window of at most the token's lifetime before it expires. The refresh token is used less frequently and can be stored more carefully: in an HttpOnly cookie, or passed only over a secure server-to-server channel in mobile apps.

Refresh token rotation

A refresh token that never changes is almost as dangerous as a long-lived access token. Steal it once and you have persistent access. Refresh token rotation addresses this: every time the refresh token is used to obtain a new access token, the refresh token itself is also replaced. The old refresh token is immediately invalidated.

Rotation also enables theft detection. If an attacker steals a refresh token and uses it, the original token is invalidated. When the legitimate application later tries to use its (now invalidated) token, the server detects a reuse attempt (two parties are using what should be a single-use token) and can revoke the entire session.

API Keys

API keys are the simplest form of authentication: a shared secret that identifies a client. They work well for server-to-server communication but require careful handling.

An API key is a long random string issued by the server and shared with a specific client. The client presents it on every request. The server looks it up and determines what the client is allowed to do. Unlike user authentication, API keys typically identify an application or a team rather than an individual person.

Transmission

API keys must be sent in headers: either the Authorization header or a custom header like X-API-Key. They must never be sent as URL query parameters. Query parameters end up in server access logs, browser history, CDN logs, and Referer headers when the page links elsewhere, any of which can expose the key to unintended parties.

HTTP 
# Correct — key in header
GET /data
Authorization: Bearer sk_live_a3f9b2c1d4e5f6a7b8c9

# Wrong — key in URL (ends up in logs, browser history, Referer headers)
GET /data?api_key=sk_live_a3f9b2c1d4e5f6a7b8c9

Storage and rotation

API keys should be stored hashed on the server, just like passwords. If the database is breached, the raw keys are not exposed. The client sees the key once on creation. After that, the server only stores a hash. When comparing an incoming key to the stored hash, use a constant-time comparison to avoid timing attacks.

Keys should be rotatable without downtime: the client generates a new key, the server accepts both old and new for a brief overlap period, then the old key is revoked. Keys should be scoped to the minimum required permissions. A read-only key cannot be used to delete records even if it's stolen. And like any credential, keys should have a mechanism for emergency revocation if they're suspected compromised.

API keys in source code

Committing an API key to a public repository is one of the most common credential exposure incidents. Automated scanners watch public repositories for credential patterns and can begin abusing a key within minutes of it appearing. Use environment variables or a secrets manager, never hard-code credentials in source files, and add secret-scanning tools to your CI pipeline.
