React Server Components

How the server and client module graphs fit together, what crosses the boundary, and where the model pays off.

Andreas Ögren
~11 min read
Last updated July 2026

React Server Components (RSC) render in an environment separate from the client application. A framework may run them during a build or for each request. Their source and server-only dependencies are absent from the client bundle, while their rendered result is sent in the RSC payload.

The model also gives server components access to server-side resources, such as a database or filesystem, without exposing those resources to the browser. Client components remain responsible for state, event handlers, effects, and browser APIs.

This differs from traditional server-side rendering (SSR). SSR produces HTML for an initial load, then hydration attaches React to the client components represented in that HTML. A server component has no client implementation to hydrate. Its output can still surround and supply props to client components that do hydrate.

SSR and RSC therefore answer different questions. SSR determines how the first HTML is produced. RSC determines which modules need a client implementation at all. Frameworks commonly combine both on the initial request.

React 19 stabilised the application-facing Server Component APIs. The lower-level APIs used by framework and bundler authors still require version coordination. For application teams, RSC is consequently a framework capability rather than a feature enabled by importing one React API.

Server and Client Components

The boundary divides the module dependency graph, not every visual parent-child relationship.

In frameworks such as the Next.js App Router, pages and layouts are server components by default. A 'use client' directive creates an entry point into the client module graph. The marked module and its transitive imports are evaluated on the client, even when those imported files do not repeat the directive.

The render tree can cross that boundary more than once. A server component may render a client component. A server parent may also pass already-rendered server content through a client component's children or another JSX prop. The client module must not import and execute the server module itself; the server parent performs that composition.

Keep 'use client' at the narrowest useful entry points. State, effects, event handlers, and browser APIs require client evaluation. Pure formatting helpers and server-rendered presentation do not. The separate 'use server' directive marks Server Functions, not server components.

app/dashboard/page.tsx Server Component 
import { getAccountSummary } from '@/lib/data';
import { SpendingChart } from './spending-chart';

// no 'use client' directive: this file, and everything it does here, stays on the server
export default async function DashboardPage() {
  const summary = await getAccountSummary();  // runs on the server, never ships

  return (
    <section>
      <h1>Account overview</h1>
      {/* summary crosses into the client tree as a plain serialized prop */}
      <SpendingChart data={summary.monthlyTotals} />
    </section>
  );
}
app/dashboard/spending-chart.tsx Client Component 
'use client';

import { useState } from 'react';

export function SpendingChart({ data }: { data: number[] }) {
  const [range, setRange] = useState<'3m' | '12m'>('3m');
  return <Chart values={data} range={range} onRangeChange={setRange} />;
}

DashboardPage and its data-access module stay on the server. The serialised summary prop crosses into SpendingChart, whose module is part of the client bundle because the browser needs its state and event logic. A client module cannot import the database-backed page component. It can, however, receive server-rendered JSX from a server parent.

Props crossing the boundary must use React's supported serialisable types. The set includes primitives, plain objects, arrays, dates, maps, sets, promises, and server-function references. Arbitrary functions, class instances, DOM nodes, database connections, and file handles cannot cross. A normal onClick function must therefore be defined in client code.

RSC and route loaders

Both can fetch before client rendering, but they return different kinds of output.

Server-side data loading predates RSC. A route loader runs before a route renders and returns data to that route. The components that consume the data may still be part of a client bundle and hydrate after SSR.

Older pattern
Remix loaders, SvelteKit load

Runs on the server and returns data as a value. The whole page is still one tree, client-rendered or hydrated after SSR. No component-level server/client split.

RSC
Server components

Runs on the server and returns a serialized component tree with an explicit 'use client' boundary. Whole subtrees never reach the browser.

A server component returns rendered React output, references to client components, and serialised props. That lets the framework omit the server component's implementation from the browser. Data loading is useful inside that model, but it is not the defining feature.

Choose RSC when the module boundary itself is useful, not merely because data should load on the server. A loader is often easier to reason about when the application still wants one client component model. RSC adds import rules and serialisation constraints in exchange for keeping server-only rendering code out of the client bundle.

Suspense and Arrival Order

Suspense lets ready regions proceed without waiting for the slowest part of the route.

RSC frameworks can stream the component payload, and they commonly combine it with streaming SSR for the initial HTML. A Suspense boundary lets ready content proceed while a nested component waits. Separate boundaries can resolve independently.

On a product page, the title and price may be ready before reviews. A boundary around the reviews can show a fallback while the rest of the route is sent. A separate related-items boundary may finish first even when it appears later in the document.

Suspense handles waiting, not failure. Framework error boundaries determine how far a rejected render propagates. Place both kinds of boundary around a region only when the product can meaningfully display and recover that region independently.

Test focus and announcement order

Test focus preservation, meaningful fallback labels, and announcements for content that appears later. These concerns belong to streaming rather than RSC alone. Accessibility and Rendering Architecture covers them in depth.

Props vs. Client-Side Fetching

Server props can fill the initial render, while client subscriptions handle data that must keep changing.

A server component can fetch data before a client component renders and pass the result as a prop. The client component then begins with data instead of mounting, starting a request, and waiting through another round trip.

Server code can still create a waterfall. Awaiting one independent request before starting another serialises them. Start independent work together, or pass a promise to the boundary that should suspend on it. Keep sequential requests only when a later request needs an earlier result.

A prop is a snapshot from one server render. Framework navigation, refresh, or revalidation can request a new RSC payload. Data that must update while the route remains open may instead need a client subscription, polling, or a cache-aware query hook.

One hybrid uses the server result to seed a client query cache. TanStack Query supports this with dehydration and HydrationBoundary. The client hook starts with server-fetched data, then applies its own freshness and refetch rules.

app/dashboard/page.tsx Server Component 
import { dehydrate, QueryClient, HydrationBoundary } from '@tanstack/react-query';
import { SpendingChart } from './spending-chart';

export default async function DashboardPage() {
  const queryClient = new QueryClient();
  await queryClient.prefetchQuery({
    queryKey: ['spending', 'monthly'],
    queryFn: getMonthlyTotals,
  });

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <SpendingChart />
    </HydrationBoundary>
  );
}
app/dashboard/spending-chart.tsx Client Component 
'use client';

import { useQuery } from '@tanstack/react-query';

export function SpendingChart() {
  // seeded from the server prefetch, refetches like any other query after that
  const { data } = useQuery({
    queryKey: ['spending', 'monthly'],
    queryFn: getMonthlyTotals,
  });
  return <Chart values={data} />;
}

Use server props for request-time or build-time data that can wait for the next server render. Add a client cache only when the interface needs a continuing data lifecycle in the browser.

Client boundaries and islands

Both approaches limit client JavaScript, but they draw and operate the boundary differently.

A client component inside a server-rendered route resembles an island: only the interactive region needs its component code in the browser. Both models encourage narrow client boundaries around controls that need state or browser APIs.

The mechanisms are not interchangeable. Island frameworks can create separately hydrated roots with per-island loading policies. RSC frameworks preserve one React composition model and use the RSC payload for later navigation and reconciliation. Treat the comparison as design intuition, not as an implementation description.

Server Actions

Server Functions connect React actions to server-side work without a hand-written client request layer.

A Server Function is an asynchronous function marked with 'use server'. A compatible framework turns references to that function into calls back to the server. Arguments and return values must use supported serialisable types, and the function must treat every call as an untrusted network request.

A Server Function used through an action prop or called in an Action is commonly called a Server Action. Forms can pass a function to action or formAction, which removes the need for a hand-written client fetch call. The server function still needs authentication, authorisation, validation, and error handling.

Expected validation failures work well as typed return values, while unexpected failures can propagate to an error boundary. useActionState stores the latest returned value and exposes pending state, so field errors can be rendered without a second client state model.

app/dashboard/actions.ts Server Action 
'use server';

type ActionResult =
  | { ok: true }
  | { ok: false; fieldErrors: Record<string, string> };

export async function updateEmail(
  prevState: ActionResult,
  formData: FormData
): Promise<ActionResult> {
  const email = formData.get('email');
  if (typeof email !== 'string' || !email.includes('@')) {
    return { ok: false, fieldErrors: { email: 'Enter a valid email address.' } };
  }
  await db.user.update({ email });
  return { ok: true };
}
app/dashboard/email-form.tsx Client Component 
'use client';

import { useActionState } from 'react';
import { updateEmail } from './actions';

export function EmailForm() {
  const [state, formAction, pending] = useActionState(updateEmail, { ok: true });

  return (
    <form action={formAction}>
      <input name="email" type="email" />
      {state.ok === false && <p>{state.fieldErrors.email}</p>}
      <button disabled={pending}>Save</button>
    </form>
  );
}

useOptimistic provides a temporary value while an Action is pending. When the Action settles, the hook returns to the current base value unless the parent has supplied confirmed data. Display an error when a mutation fails, and make sure the base data is refreshed or updated after success.

Mutation and cache behaviour belong to the framework. In Next.js, a successful action may call revalidatePath or revalidateTag so later renders do not reuse stale cached data. That is a framework-specific form of the on-demand revalidation used for incremental static regeneration.

Operational Cost

Build-time, request-time, and client-time work have different costs; RSC does not make any of them disappear.

A server component can run once during a build or on a server for each request. Static work increases build time and cache storage. Dynamic work consumes server compute and keeps a response open while dependencies resolve. A serverless deployment may also add cold starts and invocation limits, but those are properties of the chosen platform rather than RSC itself.

Client components still ship, execute, and hydrate. Moving a large static shell to server components does not reduce the cost of an interactive chart inside it. Measure server latency, cache behaviour, RSC payload size, client bundle size, and hydration work together. The deployment trade-offs for SSR still apply to dynamic RSC rendering.

SEO and Social Sharing

Search and sharing benefits come from HTML and metadata in the initial response, not from the RSC payload alone.

RSC does not itself guarantee useful HTML or metadata. A framework must combine it with static rendering or SSR for the initial document. Once it does, route-specific content and metadata can arrive without requiring a crawler or link unfurler to execute the client bundle.

Next.js provides generateMetadata for this purpose. It can use the same cached data source as the page, although metadata remains a separate framework concern from the server/client component boundary.

Testing the Boundary

Coverage across the server/client boundary needs a framework-aware test environment.

Client components can still be tested in a browser-like component harness. Pure server-side helpers can be unit tested without React. Tests that cross the RSC serialisation boundary need framework support, and Next.js guidance prefers end-to-end coverage for async server components when unit tools do not support them. Testing Strategy covers how to balance those layers.

Security Note

Props cross a serialization boundary, not a security boundary

Data sent to a client component is visible to the user, even when it originated in a server component. Send only the fields the interface needs. Dynamic HTML still needs the sanitisation discipline covered in Browser Security. Every Server Function must also repeat authentication and authorisation checks because a client can invoke it as a network endpoint.

Next.js and Beyond

A framework-level contract now, rather than a single vendor's feature.

RSC is a React architecture implemented by frameworks and bundlers. Next.js App Router provides the most established application model for it, including routing, streaming, caching, metadata, and Server Functions. Other frameworks may make different choices around each of those concerns.

Evaluate the framework rather than an abstract checklist of React features. The useful questions are whether server-only modules meaningfully reduce client code, whether the serialisation boundary fits the data model, and whether the team can operate the resulting cache and deployment behaviour. A route loader and conventional SSR remain sound choices when those benefits do not justify the extra boundary.
