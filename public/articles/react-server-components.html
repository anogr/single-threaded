React Server Components

How the server/client boundary actually works, and when to pass data down instead of fetching it in the browser.

Deep dive
~22 min read
React architecture
July 2026

React Server Components (RSC) are a React feature that lets some components render only on the server, rather than in the browser. A component that never runs in the browser never has to ship its JavaScript there either, which cuts how much code a visitor downloads and speeds up how quickly the page becomes interactive. It also means that component can reach directly for resources that only make sense on a server, such as a database query, a file on disk, or a credential, without routing through a separate API layer just to get there.

That's a stronger guarantee than traditional server-side rendering (SSR) makes, streaming or otherwise. Traditional SSR always ends with the same handoff. The server renders a full component tree to HTML and ships the JavaScript for every one of those components alongside it. Then the browser re-runs them to attach event listeners and take over. That re-run is hydration, and it happens whether or not a given component ever does anything interactive. A footer that renders a copyright year still downloads its component code, still gets re-executed in the browser, still costs bytes and CPU time it arguably never needed to spend.

RSC removes that requirement for an entire category of components. A component marked as a server component runs once, on the server, and never ships its source or its logic to the client at all. It has no client-side existence, so there's nothing to hydrate and no client copy of it to reconcile against.

This article discusses that mechanical difference. Traditional SSR already answers where rendering happens. RSC answers a different question. It cares about which parts of a component tree exist on the client at all, and whether a project draws that line on purpose or lets it happen by accident.

The idea has a specific origin. In December 2020, members of the React team, Sebastian Markbåge, Andrew Clark, Dan Abramov, and Joe Savona among them, presented Server Components as a research direction. Dan Abramov framed the goal in that talk: "The future of React is not about rendering faster. It's about rendering less." Vercel, the company behind Next.js, worked with the React team on the implementation from early on, building the bundler integration that keeps server and client module graphs separate. Next.js's App Router became the first framework to ship a production version of the model, in 2022, well ahead of React itself, and remains the implementation most teams reach for today. React didn't mark server components stable until React 19, released in December 2024.

Server and Client Components

The line between server and client isn't a convention. It's an import restriction the framework enforces.

Every file in a server-components project defaults to being a server component. A component only becomes a client component by adding a 'use client' directive at the top of its file, and that directive doesn't just mark the one component. It marks a boundary. Everything the file exports, and everything imported into that component's render tree from there down, runs on the client from that point on. There's no way to import a server component into a client component's tree and have it quietly stay a server component. Once a tree crosses into 'use client', it's client all the way down.

That default inverts how React worked for most of its history. Before RSC, every component was implicitly a client component whether it needed to be or not. Adding 'use client' to a file that doesn't need it defeats the point of the new default. The discipline the model rewards is the opposite instinct. Leave a component on the server until something concrete forces it across the boundary: a state value, an event handler, a browser API.

A second directive, 'use server', marks something different: not a component, but a Server Function. A client component is allowed to call a Server Function directly, even though it executes on the server. The mutation-focused subset of Server Functions gets its own name, Server Actions, and its own section further down, enough of a topic on their own to deserve one.

app/dashboard/page.tsx Server Component 
import { getAccountSummary } from '@/lib/data';
import { SpendingChart } from './spending-chart';

// no 'use client' directive: this file, and everything it does here, stays on the server
export default async function DashboardPage() {
  const summary = await getAccountSummary();  // runs on the server, never ships

  return (
    <section>
      <h1>Account overview</h1>
      {/* summary crosses into the client tree as a plain serialized prop */}
      <SpendingChart data={summary.monthlyTotals} />
    </section>
  );
}
app/dashboard/spending-chart.tsx Client Component 
'use client';

import { useState } from 'react';

export function SpendingChart({ data }: { data: number[] }) {
  const [range, setRange] = useState<'3m' | '12m'>('3m');
  return <Chart values={data} range={range} onRangeChange={setRange} />;
}

The DashboardPage component above never ships to the browser. Its imports, its data-fetching call, the shape of the account summary itself, none of that is visible to the client. What crosses the boundary is the summary object, serialized into the response and handed to SpendingChart as a plain prop. SpendingChart is a genuine client component. It holds local state, responds to interaction, and its source code does ship, because the browser has to run it. The one-directional rule catches people in both directions. A client component can't import a server component and expect it to render inside its own tree (there's no server left to call once the response has already streamed down), and a server component that imports a client component doesn't make that import a server component either. The 'use client' file's boundary sticks.

That serialization is also where the boundary imposes a real constraint, not just a directional one. Only values React knows how to serialize can cross from server to client: plain objects, arrays, strings, numbers, dates, and a handful of other supported types, but not functions, class instances, or anything that closes over server-only state like a database connection or a file handle. A server component can't pass an onClick handler down as a plain prop, because a function reference has no meaning once it's supposed to run in a different runtime entirely. Server Functions are deliberately the one exception, covered in full further down. A function marked 'use server' can cross the boundary as a prop, but only because React replaces it with a reference the client can call back through, not the function's actual code.

Not Just "Fetches on the Server"

RSC is a specific mechanism, not a synonym for server-side data fetching in general.

It's tempting to describe RSC as "React finally lets you fetch data on the server" and leave it there, but that description also fits patterns that predate RSC by years and work nothing like it underneath. Remix's loader functions and SvelteKit's load functions both run exclusively on the server, both fetch data before a route renders, and both hand that data to the page as a plain, typed value. Neither one builds a serialized component tree, and neither has anything resembling a 'use client' boundary, because in both frameworks the whole page is still one tree once the data arrives, client-rendered or hydrated after SSR. A Remix loader answers "what data does this route need before it renders." RSC answers a different question: "which parts of this tree need to exist on the client at all."

Older pattern
Remix loaders, SvelteKit load

Runs on the server and returns data as a value. The whole page is still one tree, client-rendered or hydrated after SSR. No component-level server/client split.

RSC
Server components

Runs on the server and returns a serialized component tree with an explicit 'use client' boundary. Whole subtrees genuinely never reach the browser.

The two problems overlap in the data-fetching case, which is why the conflation is so common, but RSC is solving the second problem. The loader pattern was never trying to.

The distinction is more than terminology. A team that adopts Remix or SvelteKit gets server-side data fetching without ever touching a serialized component tree, without a 'use client' directive to reason about, and without a rule about which imports are safe to nest where. A team adopting RSC takes on the component-tree model deliberately, in exchange for the ability to keep genuinely inert content, such as layout chrome, static copy, and presentation logic, off the client entirely rather than shipping it as JavaScript that happens to render once and never update again. Neither approach is strictly newer or more advanced than the other. They're solving adjacent but different problems, and a team that only needs server-side data shouldn't feel obligated to adopt RSC's component model just because both get described, loosely, as "server-side React."

Suspense and Arrival Order

A server component can stream in long after the shell around it has already painted.

Server components stream to the client the same way streaming SSR does. Wrapped in a Suspense boundary, a slow part of the tree doesn't block the parts that are already ready. Nested boundaries resolve independently, each one streaming in as its own data arrives rather than waiting for the slowest sibling to finish. What's different from plain streaming SSR is what can live inside one of those boundaries. In ordinary streaming SSR, a boundary wraps a component that will eventually hydrate on the client. In RSC, a boundary can wrap a component that never ships to the client in any form. Only its rendered output streams in, later, once its data resolves.

A product page makes the effect concrete. The header, price, and title resolve almost immediately and stream first. A reviews section that has to aggregate ratings from a slower service might resolve well after that. A related-items strip pulling from a recommendation service might land somewhere in between. None of that has to match the order those sections appear in the document, because streaming delivers content in the order it becomes ready, not the order it's written in the markup.

Suspense only covers the waiting case, not the failure case, which is why streaming RSC code almost always pairs a Suspense boundary with an error boundary around the same region. If the reviews service times out entirely rather than just running slowly, the Suspense boundary has nothing to resolve into, and without an error boundary wrapping it, that failure can bubble up and take out more of the page than the one section that actually broke. Scoping both boundaries to the same region keeps a single slow or broken dependency contained. The rest of the page keeps working, and the failed section renders its own fallback instead of an unhandled error taking the whole tree down with it.

Test focus and announcement order

Streaming out of DOM order carries a real accessibility cost worth testing for specifically. If a screen reader announces new content in the order it arrives rather than the order it appears in the document, a boundary that resolves last can get announced after content that logically comes after it, which doesn't match how the page reads. And if focus was set on an element that a resolving Suspense boundary later replaces, that focus can silently land nowhere, leaving a keyboard or screen-reader user without a clear sense of where they are. Neither failure is unique to RSC. Both apply to any streaming SSR, but RSC's habit of wrapping more of a page in independent boundaries makes it more likely to show up. It's a narrow thing to test for, not a reason to avoid streaming. Broader SPA-versus-SSR accessibility questions, and streaming accessibility in general, are covered in Accessibility and Rendering Architecture.

Props vs. Client-Side Fetching

Passing data down avoids a fetch waterfall. It's only ever as fresh as the render that produced it.

A server component that fetches data and passes it down as props sidesteps a specific, common performance problem: the client-side fetch waterfall, where a component renders, fires a request, waits, then renders a child that fires its own request, each round trip adding to the time before anything useful appears. When a server component does that fetching before anything streams to the browser, the client tree receives already-resolved data as a prop and never has to fetch it at all for the initial render.

That doesn't mean a server component is automatically free of waterfalls of its own. Awaiting one data call and then starting the next only after it resolves recreates the exact problem, inside a single server component, that RSC is supposed to avoid at the client boundary. Starting independent fetches together, with Promise.all or by simply not awaiting a call until its result is actually needed further down the function, keeps a server component's own data fetching parallel instead of accidentally serial.

The tradeoff is staleness. Data passed down as a prop is a snapshot from the moment the server rendered, and it won't update again unless something re-renders that server component: a full navigation, a server action revalidating a route, or an explicit refresh in frameworks that support one. A dashboard number embedded as a prop is correct as of page load and then quietly frozen until the next render, which is fine for a lot of content and wrong for anything that needs to update while the visitor is still looking at it.

The pattern that settles this in practice treats server-side fetching as what fills the first paint, and a client-side cache as what handles everything after. TanStack Query's dehydrate and hydrate functions do exactly that. A server component runs a query, dehydrates the resulting cache into a serializable snapshot, and passes it down. A client component picks that snapshot back up with HydrationBoundary and gets a live query, complete with its own refetching, polling, and cache invalidation, seeded with data that was already there on first paint instead of starting from an empty cache and an unavoidable loading spinner.

app/dashboard/page.tsx Server Component 
import { dehydrate, QueryClient, HydrationBoundary } from '@tanstack/react-query';
import { SpendingChart } from './spending-chart';

export default async function DashboardPage() {
  const queryClient = new QueryClient();
  await queryClient.prefetchQuery({
    queryKey: ['spending', 'monthly'],
    queryFn: getMonthlyTotals,
  });

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <SpendingChart />
    </HydrationBoundary>
  );
}
app/dashboard/spending-chart.tsx Client Component 
'use client';

import { useQuery } from '@tanstack/react-query';

export function SpendingChart() {
  // seeded from the server prefetch, refetches like any other query after that
  const { data } = useQuery({
    queryKey: ['spending', 'monthly'],
    queryFn: getMonthlyTotals,
  });
  return <Chart values={data} />;
}

Server fetch for first paint, client cache for what happens after: that framing is closer to how the pattern gets used in practice than treating server props and client fetching as a binary choice between the two.

Client Components as Islands

A 'use client' component inside a server tree is an island by another name.

The earlier look at islands architecture describes Astro's model as small, independently hydrated pockets of interactivity dropped into an otherwise static or server-rendered page. A 'use client' component inside an RSC tree is the same shape: a server-rendered page with one deliberately marked region that ships JavaScript and hydrates, surrounded by server components that never do. The vocabulary differs. Astro calls the boundary a component island. React calls it a client component. The underlying bet is the same either way: ship JavaScript only where something genuinely needs to be interactive, and draw that boundary explicitly rather than by default. The two just arrive there from different starting points. Astro starts from zero JavaScript and opts components in. RSC starts from a component-tree model and opts specific branches out of the server.

One difference is worth naming so the analogy doesn't overreach. An Astro page with zero islands ships genuinely zero JavaScript framework runtime. An RSC page, even one with no 'use client' components anywhere, still needs React's client runtime present to handle navigation and any future interactive additions, because the framework doesn't know in advance that a route will stay purely static forever. The islands are comparable. The baseline they sit on top of isn't.

Server Actions

Mutations get the same treatment reads did. The framework decides which parts of the round trip actually need to run on the client.

Any Server Function, marked with 'use server' at the top of its own file or inline inside a server component, is callable directly from a client component as though it were local, even though the call crosses the network and executes on the server. React handles serializing the arguments and the return value automatically, so a plain form submission or button click doesn't need a hand-written API route or a manual fetch call underneath it.

A Server Function earns the more specific name Server Action when it's passed to a form's action prop, or called from inside a transition. Those are the two paths React and its frameworks build mutation tooling around. Not every Server Function qualifies. One that a component calls directly to only read data, the pattern covered earlier in this article, stays a Server Function and never becomes an action. The distinction matters because hooks like useActionState only make sense for the action shape, a function that reports pending state and a typed result back to whatever triggered it.

The pattern that has settled for handling validation is a typed result rather than a thrown exception. An action always returns a value with the same shape, { ok: true } on success or { ok: false, fieldErrors } on a validation failure, instead of throwing for the failure case the way early examples of the pattern did. That consistency is what lets useActionState render inline field errors straight from an action's return value, with no try/catch at the call site and no separate error state to keep in sync with the form.

app/dashboard/actions.ts Server Action 
'use server';

type ActionResult =
  | { ok: true }
  | { ok: false; fieldErrors: Record<string, string> };

export async function updateEmail(
  prevState: ActionResult,
  formData: FormData
): Promise<ActionResult> {
  const email = formData.get('email');
  if (typeof email !== 'string' || !email.includes('@')) {
    return { ok: false, fieldErrors: { email: 'Enter a valid email address.' } };
  }
  await db.user.update({ email });
  return { ok: true };
}
app/dashboard/email-form.tsx Client Component 
'use client';

import { useActionState } from 'react';
import { updateEmail } from './actions';

export function EmailForm() {
  const [state, formAction, pending] = useActionState(updateEmail, { ok: true });

  return (
    <form action={formAction}>
      <input name="email" type="email" />
      {state.ok === false && <p>{state.fieldErrors.email}</p>}
      <button disabled={pending}>Save</button>
    </form>
  );
}

useOptimistic pairs with this pattern for the immediate-feedback case, showing a predicted result while the action is still in flight. Its rollback behavior is narrower than it looks. The optimistic value only reverts automatically when the action throws. If an action follows the typed-result convention above and returns { ok: false, ... } instead of throwing, useOptimistic has no signal to roll back on, and the optimistic UI keeps showing the predicted state until something else, a fresh prop from the parent re-rendering, updates it. Teams that combine the typed-error pattern for useActionState with useOptimistic in the same form need to handle that gap explicitly, usually by deriving the optimistic reset from the action's returned state rather than relying on the hook's automatic behavior.

Server Actions commonly close the loop on the caching story covered elsewhere in this series. After updateEmail succeeds, a real implementation typically calls something like revalidatePath or revalidateTag so any cached server-rendered page still showing the old value gets marked stale immediately, the same on-demand revalidation covered as part of incremental static regeneration (ISR), just triggered from a mutation instead of a webhook.

Operational Cost

Moving rendering onto the server doesn't remove cost. It relocates cost into serverless economics specifically.

Server components shift rendering compute from the visitor's device to a function running per request, which means the usual serverless tradeoffs now apply to page rendering itself, not just to API routes. A function that hasn't run recently pays a cold start before the first byte goes out. A render that streams for several seconds while waiting on slow data holds memory for the whole duration, and enough concurrent slow renders can pressure a function's memory ceiling the same way any long-lived request would. The RSC model doesn't guarantee zero client-side JavaScript, either. A large subtree that's genuinely interactive still ships and hydrates like it always did, so time-to-interactive for that portion of the page doesn't automatically improve just because the tree around it is server-rendered. None of this is a performance-tuning concern so much as a capacity-planning one. Cold starts, concurrent render memory, and residual client bundle size are the numbers worth watching, and none of them show up in a single benchmark run.

Most serverless platforms also cap how long a single function invocation can run, which puts a hard ceiling on how long a streaming RSC response can stay open waiting on a slow dependency, a constraint that doesn't exist in the same way for a long-running origin server process. The edge-versus-origin tradeoff covered for plain SSR carries over here too, and it matters more for RSC than for a stateless API route. An edge runtime buys lower cold-start latency in exchange for less compute headroom, and a streaming render has to sustain its connection for the whole duration rather than finishing in one quick round trip.

SEO and Social Sharing

Metadata that a crawler never has to execute JavaScript to see is a direct, practical win.

Search engine optimization (SEO) depends on a crawler being able to read a page's metadata without running any JavaScript first, and that's exactly what server-first rendering delivers. Next.js's generateMetadata function, and its equivalents in other server-first frameworks, runs on the server and produces the actual <title>, description, and Open Graph tags a crawler or a social-media unfurler sees in the initial response, without either of them needing to execute a client bundle to find that information. That's the exact problem a pure client-rendered SPA has. A crawler that doesn't run the bundle sees an empty shell and whatever static meta tags happen to be hardcoded into the document, which is usually wrong for anything beyond the homepage. Server-first rendering doesn't just make metadata correct for SEO. It makes metadata correct for every route without a team having to reason about which crawlers execute JavaScript and which don't.

generateMetadata runs before the page component itself and can await the same data sources the page uses, so a product's title and price end up in both the visible page and its Open Graph tags from one shared fetch, rather than a separate metadata pipeline that quietly drifts out of sync with the page it's describing.

Testing the Boundary

A quick heads-up rather than a strategy. Server components need a different kind of test harness.

Server components don't run inside the kind of browser-like harness component tests are normally written against. jsdom and its equivalents simulate a DOM, not a server render pipeline with a serialization boundary running through the middle of it. That pushes a meaningful share of RSC-specific coverage, especially anything that crosses the server/client boundary, out of unit tests and into integration or end-to-end tests that actually run the framework's server and hit it with real requests. In practice that means leaning harder on Playwright or a similar end-to-end tool for anything that spans the boundary, and reserving component-level testing tools for the client components that can genuinely run in an isolated, browser-like environment on their own. The tradeoffs between unit, integration, and end-to-end coverage generally, and where the line should sit for a given team, belong to Testing Strategy. This is just the part specific to RSC.

Security Note

Props cross a serialization boundary, not a security boundary

Passing data from a server component to a client component as a prop crosses a serialization boundary, not a trust boundary. Nothing about that crossing sanitizes dynamic content on its own. If a value contains user-supplied HTML or script content, it still needs the same sanitization discipline covered in the cross-site scripting section of the browser security article. RSC doesn't add a new defense here, and it doesn't remove the need for an existing one.

Next.js and Beyond

A framework-level contract, increasingly, rather than a single vendor's feature.

React Server Components are a React-level mechanism, not a Next.js feature. The pieces underneath it, chiefly the bundler integration that keeps server and client module graphs separate, ship as standalone packages like react-server-dom-webpack that any framework can build on, and a few do. Waku is a minimal framework built specifically as an RSC runtime, with no Next.js underneath it at all. Next.js's App Router is still the flagship implementation of everything covered above, and for most teams evaluating RSC, it's also the only one mature enough to bet a production app on today. That gap is closing rather than settling permanently. Other frameworks, TanStack Start among them, are adopting compatible server and client component patterns rather than treating the model as a Next.js-only feature. Read as a contract, the model is a specific set of pieces: server components, an explicit client boundary, streaming with Suspense, and typed server actions. Together they're closer to where React itself is heading than a feature specific to one meta-framework, even though learning it in practice still means learning Next.js's implementation first.
