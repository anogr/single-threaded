React Server Components

How React keeps selected component code on the server while combining its output with interactive client components.

Andreas Ögren
~16 min read
Last updated July 2026

A React application often uses server data to produce interface elements that do not need state, event handlers, or browser APIs. Shipping their component modules makes the browser download and execute code that has no client-side responsibility.

React Server Components (RSC) let selected components render in an environment separate from the browser application. A framework may run them once during a build or for each request on the web server. Their source and server-only dependencies stay out of the browser bundle, while interactive component code for the browser still ships where the interface needs it.

This model is separate from server-side rendering (SSR). SSR determines how the browser receives the first HTML. RSC determines which component modules need a client implementation. A framework can combine RSC with static generation, SSR, streaming, or client navigation because RSC and those rendering strategies are separate architectural questions.

This article focuses on the server/client module boundary. HTML generation, streaming, and hydration are covered in Rendering Strategies.

Server and Client Components

A Server Component executes outside the browser, while a Client Component's module must ship to the browser when the interface needs state, effects, event handling, or browser APIs.

Execution Environments

A Server Component executes in the separate server environment chosen by the framework. It runs during a CI build or server render, returns React output, and then does not persist in memory as a mounted component. It cannot retain component state, register event handlers, or run client lifecycle logic such as effects.

Build-time execution does not require an application server after deployment. A framework can read static source data during the build and publish the generated output as static assets. Request-time execution instead needs a server environment for later renders and can use data from the current request. In both cases, “server” names the environment where the component module executes rather than one required deployment shape.

A Client Component belongs to the module graph sent to the browser. It can use state, effects, event handlers, context providers, and browser APIs. A framework may use its output when producing initial HTML, but the module still ships because React needs it for interaction in the browser.

The 'use client' Boundary

The 'use client' directive creates an entry point into the client module graph. The marked module and its transitive imports enter that graph even when those imported files do not repeat the directive. Frameworks such as the Next.js App Router treat pages and layouts as Server Components unless a client boundary changes the import path. React has no corresponding directive that marks a component as a Server Component. The 'use server' directive instead marks asynchronous server-side functions that client code can call.

The directive must appear at the beginning of its file before imports or other code. The client boundary begins where server code first imports a client-marked module. Repeating 'use client' in modules already below that boundary does not create another client subtree or change where the boundary begins.

Server Component and Client Component describe component usages rather than permanently labelling a function definition. An unmarked formatting helper or component with no environment-specific requirements can be evaluated on the server when server code imports it and in the browser when client code imports it. The same component definition can therefore have a Server Component usage through one import path and a Client Component usage through another. The import path determines which module graph contains each usage.

How the Client Module Graph Grows

The boundary follows the module dependency tree rather than the rendered parent-child tree. Every transitive dependency below it enters the client graph, including utilities and third-party packages as well as component modules. The 'use client' directive should therefore sit at the narrowest useful entry points. Modules reached only from the server graph stay out of the browser bundle.

A third-party component that uses client-only Hooks or browser APIs may need client execution even when its package does not include a directive. A small wrapper module can add 'use client', import and export that component, and become the entry point used by server code. The wrapper places the package in the client graph without moving the surrounding server modules across the boundary.

The module graph uses a DashboardWidget to make that transitive effect visible. Page reaches Sidebar through the server graph and reaches DashboardWidget through a client entry point. The widget's imports place Chart and Tooltip in the same client subtree.

Framework and Bundler Support

JavaScript does not create a client boundary when it encounters 'use client'. A compatible bundler must read the directive while it follows imports from a server entry point. When it reaches a client-marked module, the bundler creates a browser entry for that module and its transitive dependencies. During an RSC render, React represents the Client Component with a reference to the browser entry instead of executing its module as Server Component code. The reference identifies the browser entry at the Client Component's position in the React tree.

The framework decides when to execute the server graph and how the browser receives the rendered result and client modules. It may run Server Components during a build, run them for each request, or support both modes for different routes. The framework starts the RSC render, serves the browser bundles created from client entries, and connects navigation or refresh to later server renders. For the initial page load, a framework that supports SSR can turn the React tree into HTML before the browser hydrates the Client Components.

An application therefore needs an RSC integration rather than a React import or directive alone. The Next.js App Router provides one example. Its compiler separates the module graphs, its server renderer produces RSC results, and its router requests later renders during navigation.

The RSC Payload

React serialises the server-rendered tree together with references to the client modules and props needed to complete it.

The React Server Component payload, usually shortened to the RSC payload, represents the result of a Server Component render. It contains rendered Server Component output, references to the Client Component modules needed at particular positions, and the props passed into those Client Components.

The payload preserves the React tree without sending Server Component functions or their server-only dependencies to the browser. A Server Component can read a file, call a database, or import a formatting library, but the client receives the component's rendered result rather than that implementation.

A framework may use the payload when producing the initial HTML, but HTML generation and hydration are separate concerns covered in Rendering Strategies.

Later navigation or refresh can request another RSC payload without replacing the whole document. React reconciles the new server-rendered result with the existing tree, so Client Component state can remain when the same component stays in the same position. Routing, prefetching, caching, and the request that obtains the next payload belong to the framework.

Composition Across the Boundary

The module graph controls which component code can execute in the browser. A server parent can still place server-produced React output inside a Client Component without sending the Server Component module.

Passing Server-Rendered JSX

A Server Component can import an interactive Expandable Client Component and a non-interactive Article Server Component. The server parent returns <Expandable><Article /></Expandable>. The server executes Article and represents its result in the RSC payload, while Expandable receives that result through its children prop. In the browser, Expandable handles state and events, and React places the server-produced result in its child slot. The Expandable module never imports or executes the Article module.

Values passed from a Server Component to a Client Component must use React's supported serialisable types. These include primitives, plain objects, arrays, dates, maps, sets, and promises. React elements can cross as JSX slots. Ordinary functions, class instances, DOM nodes, database connections, and file handles cannot cross.

React context does not cross into Server Component execution. A Server Component can render a Client Component provider and pass server-rendered content through it, but the Server Components in that content cannot read the provider's client context. Server-side code should share request data through function arguments, cached data-access functions, or another server-owned mechanism.

Passing Serialised Data

The following account overview demonstrates the data-prop path rather than the JSX slot above. Its page reads account data on the server, passes serialisable monthly totals into an interactive spending chart, and keeps the data-access module out of the client graph.

app/account/page.tsx Server Component 
import { getAccountSummary } from '@/lib/data';
import { SpendingChart } from './spending-chart';

// Next.js treats this page entry as a Server Component.
export default async function AccountOverviewPage() {
  const summary = await getAccountSummary();  // data access runs on the server

  return (
    <section>
      <h1>Account overview</h1>
      {/* monthlyTotals crosses through the serialised data prop */}
      <SpendingChart data={summary.monthlyTotals} />
    </section>
  );
}
app/account/spending-chart.tsx Client Component 
'use client';

import { useState } from 'react';
import { SpendingBars } from './spending-bars';

export function SpendingChart({ data }: { data: number[] }) {
  const [range, setRange] = useState<'3m' | '12m'>('3m');
  return <SpendingBars values={data} range={range} onRangeChange={setRange} />;
}

AccountOverviewPage and its data-access module stay on the server. The serialised data prop carries summary.monthlyTotals into SpendingChart. The browser bundle contains SpendingChart and its SpendingBars dependency because both lie below the client boundary, while SpendingChart owns the range state and event logic. Unlike the earlier children slot, this example sends an array. Neither path lets a client module import the server-backed page.

Server Data Is a Render Snapshot

An async Server Component can resolve initial data during a build-time or request-time render, before the browser runs the application. The returned values form a snapshot for that render.

Resolving Initial Data During Rendering

An async Server Component starts a database or service read as part of rendering. When the component reaches await, React suspends that component's render until the promise settles and then resumes with the value. React includes the resulting component output in the RSC payload. The read can run while a framework builds static output or while it renders the route for a request. A framework may then use the RSC result to generate static HTML or request-time SSR HTML. The RSC render determines the component result, while SSR is the separate step that turns the tree into HTML.

A client-only SPA that loads initial data in useEffect follows the opposite sequence. The browser first downloads the application code and commits a render with an empty or loading state. The Effect runs after that commit and sends a request for the data. When the response updates component state, React renders the component again with the result. The initial data therefore arrives through a second browser-to-server request and causes a second client render after the application has started. A route loader, preloaded data, or a client cache can avoid this exact sequence, so the comparison applies specifically to fetching on mount in an Effect.

Reading during the Server Component render moves that initial request ahead of the server-produced tree. The browser can receive a tree that already contains the resolved value, and a Client Component can begin with the value in its serialised props instead of fetching the same data after mount. Those props are a snapshot of one server render. They do not subscribe the Client Component to later changes in the database or service.

Moving the read to the server changes where and when it starts, but it does not remove dependencies between reads. A child read that needs a parent result can only start after that result exists. Independent reads can start together. Moving data close to the renderer can reduce latency, but it cannot parallelise reads that depend on earlier results.

Promises and Suspense

A server render does not have to await every promise immediately. It can start lower-priority work, pass the promise to a Client Component, and let that component read the result with React's use API. When the consumer sits behind a Suspense boundary, that subtree can show its fallback while the rest of the page continues rendering. The Client Component is a synchronous function. React suspends it through use, rather than await, until the server-started promise resolves.

Refreshing the Snapshot

Framework navigation, refresh, or revalidation can request another RSC payload and supply a newer snapshot. Data that must keep changing while the route is open instead needs an explicit browser-side lifecycle, such as a subscription, polling, or a cache-aware query hook.

RSC does not define how long fetched data stays fresh. Request memoisation, persistent caches, invalidation, and route revalidation belong to the framework or data library. Server props suit data that can wait for the next server render, while a client cache suits an interface with a continuing browser-side data lifecycle.

RSC and Route Loaders

A route loader returns data to components, while RSC returns a React tree containing server-rendered output and references to client modules.

A route loader runs before a route renders and returns data to that route. The component modules that consume the value may still belong to the client bundle. A loader moves data access to the server without creating a Server Component module graph.

Route loader
Returns a data value

The route receives data, then its component modules render that data in their normal environment.

RSC
Returns rendered component output

The payload identifies Client Component modules and the serialised props they receive.

Data loading is useful inside RSC, but it is not the defining feature. The RSC payload lets the framework omit Server Component implementations from the browser while preserving their rendered positions in the React tree.

RSC fits when the module boundary itself removes meaningful client code or keeps server-only rendering logic close to its data. A loader is easier to reason about when the application still wants one client component model and only needs server-side data loading.

Server Functions and Actions

Server Functions let Client Components call asynchronous server code through a callable reference, which supports interactions that mutate server-side state.

Declaring Server Functions

A Server Function is an asynchronous function marked with 'use server'. A compatible framework replaces a reference to that function with a call back to the server, so client code can request the work without importing and executing the server module in the browser. Server Functions are designed for mutations of server-side state rather than data fetching. Initial data belongs in a Server Component render or an explicit client-side data lifecycle.

When 'use server' marks an individual asynchronous function, the directive must be the first statement in that function body. A Server Component can define such a function and pass the resulting reference to a Client Component. A file can instead place 'use server' before its imports at module level, which marks every exported asynchronous function as a Server Function. This module-level form is required when a Client Component imports a Server Function directly. In either form, client code receives a reference and the server executes the function body.

Actions and Interface State

An Action is a function whose work React coordinates with pending, error, and optimistic interface states. A Client Component can call a Server Function reference directly. A Server Function is a Server Action only when it is passed to an action or formAction prop, or called from an Action. Frameworks that implement Server Functions typically process Actions one at a time and do not cache their return values. Server Functions are therefore a poor data-loading API for reads that should run concurrently or reuse cached results. Form integration supplies the submitted FormData and can submit it without a hand-written client fetch call.

A Transition lets React track asynchronous work as a non-blocking interface update. React automatically invokes a Server Function passed to action or formAction within a Transition. When a Client Component calls a Server Function from a click or another event instead, the call should run inside an Action created with startTransition. Client code must await the returned promise to read its value, while useTransition can expose whether that work is pending.

The Network and Security Boundary

Calling a Server Function from client code sends a network request to the server. Its arguments and return value must use React's supported serialisable types, and the function must authenticate the user, authorize the operation, and validate the input like any other server endpoint.

Form Action Example

The following settings example uses the inline form path. SettingsPage defines updateEmail and passes its reference to the form's action prop. React supplies the submitted FormData, and the function requires the current user and validates the email before updating that user's record.

app/settings/page.tsx Server Component 
export default function SettingsPage() {
  async function updateEmail(formData: FormData) {
    'use server';
    const user = await requireUser();
    const email = formData.get('email');
    if (typeof email !== 'string' || !isValidEmail(email)) return;
    await db.user.update({ where: { id: user.id }, data: { email } });
  }

  return (
    <form action={updateEmail}>
      <input name="email" type="email" required />
      <button>Save</button>
    </form>
  );
}

updateEmail is a Server Action because the form receives its reference through the action prop. A Client Component can use useActionState to expose the latest returned state and whether an Action is pending. When useActionState receives a Server Function, React can show the returned state before hydration finishes, and frameworks can support form submission before the client bundle loads. Optimistic state can show the expected result while the request is pending. Cache invalidation tells the framework which server-rendered data needs a new snapshot after the mutation.

Security Across the Boundary

Serialisation controls which values can cross, while security controls which values and operations a user may access.

Authorizing Data Access

Server execution does not authorize a data read. Before reading a database or service record, server code must verify that the current user may access it. After that check, a Server Component should send only the fields the interface needs because every value passed to a Client Component reaches the user's browser and can be inspected.

Props cross a serialisation boundary, not a security boundary

Supported serialisation says that React can encode a value. It does not say that the user is authorized to receive that value.

Protecting the Module Boundary

Build-time checks can prevent a server-only data module from entering the client graph by accident. Next.js recognises import 'server-only' in modules that must never be imported by Client Components. Environment-variable filtering is not a substitute because an accidental client import can still expose logic or produce broken browser code.

A Client Component may import a module marked 'use server', but the bundler replaces that import with a Server Function reference. The server module does not execute in the browser. Each call still arrives as an untrusted network request, so authentication, authorization, validation, and any necessary abuse controls must protect the operation itself.

Protocol and Browser Security

RSC frameworks and their protocol packages need timely security updates because they decode network input. React's RSC security advisory records the affected packages and patched release lines.

Dynamic HTML rendered by any component creates a separate browser security concern and needs the sanitisation discipline covered in Browser Security.

When RSC Fits

The model is useful when its server boundary removes meaningful client work without creating disproportionate operational and testing costs.

Whether RSC fits depends partly on how the application divides work between the server and client. Build-time rendering increases build work, while request-time rendering consumes server compute and waits for data dependencies. Client Components still ship, execute, and hydrate. Teams therefore need to measure server latency, RSC payload size, client bundle size, and client work together rather than treat the server boundary as an automatic performance improvement.

Testing follows the same server-client boundary. Client Components fit a browser-like component harness, and pure server helpers fit ordinary unit tests. A test that renders across the RSC serialisation boundary needs framework support, so end-to-end coverage often carries more of that integration work. Testing Strategy explains how those layers divide responsibility.

The model pays off when server-only modules meaningfully reduce client code, direct server data access simplifies the application, and the serialisation boundary fits the data model. A route loader or conventional rendering strategy may fit better when those benefits do not justify the framework, cache, deployment, and testing responsibilities.
