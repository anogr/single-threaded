Accessibility as an Architecture Decision

Why early design decisions reduce remediation work, which standards matter, and how teams can make accessibility part of delivery.

Andreas Ögren
~11 min read
Last updated July 2026

Accessibility often enters a project as a checklist for the final audit. By then, the audit is examining components and interaction patterns that have already spread through the product. Each defect may be small, but correcting the underlying pattern can touch many screens.

The World Health Organization estimates that 1.3 billion people, or 16% of the global population, experience significant disability. Products also create similar barriers for people dealing with temporary injuries or difficult surroundings. Someone may be using one hand, reading a screen in glare, or trying to follow a video where audio is unavailable. The scale alone makes accessibility an architectural concern. Legal obligations add another reason, while the cost of changing a shared pattern explains why the timing matters.

Consider a design system that uses a real <button> for its button component. Every consumer starts with the element's native semantics and keyboard behavior. If the shared component begins with a styled <div> instead, each use inherits missing behavior that must later be restored and tested. Accessibility follows the familiar economics of architecture: a sound decision in a shared layer prevents repeated repair at its call sites.

Semantic HTML Does the Work

Native elements provide a dependable starting point because browsers already understand their meaning and basic interaction.

Browsers derive an accessibility tree from the document object model (DOM) and expose it through platform accessibility APIs. The two trees are related but not identical. Hidden or purely presentational elements may be omitted, while meaningful text and controls are represented in forms that assistive technology can use. Interactive objects can expose a role, an accessible name, and relevant state such as whether they are expanded or disabled. Two elements that look identical can therefore present very different information to a screen reader.

A native <button> is exposed with the button role and can take its accessible name from its contents. It also participates in sequential keyboard navigation and responds to Enter and Space without application code. Browsers provide default focus styling as well, although a design system may replace it with a clearer :focus-visible treatment. A styled <div> has none of those button behaviors. Authors must add the semantics and interaction themselves, then test the result across the browser and assistive-technology combinations they support.

The same principle extends beyond buttons. Opening a native <dialog> with showModal() places it in the top layer, makes the rest of the document inert, and gives the browser defined focus and Escape-key behavior. Authors still need a useful name, sensible initial focus, and a deliberate destination for focus when the dialog closes. For non-modal overlays, the Popover API handles top-layer placement and can provide light dismissal for popover="auto". It does not supply the keyboard model for a menu or the semantics of a tooltip, so those remain author responsibilities. A <details> and <summary> pair provides disclosure behavior without recreating it in JavaScript. Native features do not finish the accessibility work, but they reduce the amount of behavior a team must build and maintain.

What ARIA Is For

ARIA adds semantics that HTML cannot express on its own, but it does not implement a component's behavior.

Accessible Rich Internet Applications (ARIA) defines roles, states, and properties that browsers expose to assistive technology. Attributes such as aria-expanded can describe state that a tag does not convey, while roles support widgets such as tab lists and tree views that have no direct HTML equivalent. These additions change the semantic information exposed by an element. Keyboard handling and focus management remain the author's responsibility. A <div role="button"> may be announced as a button, but authors must still place it in the tab order and implement the expected Enter and Space interactions.

OrderButton.tsx TSX 
// The div still needs Enter and Space handlers.
<div role="button" tabIndex={0} onClick={submitOrder}>Submit order</div>

// The native element already has the expected keyboard behavior.
<button type="button" onClick={submitOrder}>Submit order</button>

The W3C's first rule of ARIA provides a useful default: use a native element when one already has the required semantics and behavior. ARIA becomes appropriate when the interface has no suitable HTML pattern or when native semantics need additional state or relationships.

Accessible-name calculation follows a defined algorithm whose sources vary by element. In broad terms, aria-labelledby takes precedence over aria-label, followed by native HTML naming mechanisms such as a form control's associated <label>. Some elements can derive a name from their contents, while attributes such as title serve only as fallbacks in relevant cases. The practical lesson is to prefer visible text and native labels. If a component duplicates visible wording in aria-label, later copy changes can leave sighted users reading one label while screen reader users hear another.

The Standards Landscape

WCAG provides the shared technical vocabulary, although each law or contract decides which version and conformance level applies.

The Web Content Accessibility Guidelines (WCAG) are the W3C standard for accessible web content. WCAG 2.2 is the current Recommendation and became ISO/IEC 40500:2025 in October 2025. Its success criteria are grouped into levels A, AA, and AAA, with each level including the ones below it. Many policies and regulations use Level AA as their target, although the named WCAG version differs. The W3C advises against requiring Level AAA across an entire site because some content cannot satisfy every AAA criterion.

WCAG 3.0 remains a Working Draft. The March 2026 draft explores core and supplemental requirements, assertions, and Bronze, Silver, and Gold conformance levels. Several parts of that model are still marked as undecided, so it is not a stable target for policy or procurement. Teams can follow its development without postponing work against the applicable WCAG 2 standard.

Regulation and Enforcement

Accessibility obligations depend on jurisdiction and sector, so architects need the applicable rule rather than a single global compliance claim.

In the European Union, the European Accessibility Act (EAA) applies to covered products placed on the market and covered consumer services provided after 28 June 2025. Its scope includes e-commerce, consumer banking, e-books, electronic communications, and parts of passenger transport. Member states implement and enforce the directive through national law, so obligations and remedies must be checked in the countries where a product is offered. The act is broader than rules limited to public-sector websites, but it does not cover every product, service, or piece of web content.

In the United States, a 2024 Department of Justice rule under Title II of the Americans with Disabilities Act (ADA) adopts WCAG 2.1 Level AA. The rule covers web content and mobile apps from state and local governments. An April 2026 interim final rule moved the compliance date to 26 April 2027 for entities with a population of at least 50,000. Smaller entities and special district governments have until 26 April 2028. Title III separately applies to covered businesses open to the public. The Department identifies WCAG as helpful guidance for web accessibility under Title III, but it has not adopted the Title II web rule as a technical standard for private businesses.

The Overlay Widget Shortcut

An overlay widget is a third-party script that attempts to alter an existing site at runtime, often through a control displayed in a corner of the page. Such software may change presentation or patch some detectable defects, but an automated layer cannot determine whether the site as a whole conforms to WCAG. The W3C is explicit that evaluation tools require human judgment and cannot establish accessibility on their own. In 2025, the US Federal Trade Commission finalized an order requiring accessiBe to pay one million dollars over deceptive claims that its automated product could make any website WCAG-compliant.

An overlay cannot establish conformance

A runtime patch does not repair inaccessible workflows, unclear content, or interactions that require human evaluation. It can also behave differently across browser and assistive-technology combinations. Treat an overlay like any other third-party script with a narrow, testable purpose. It cannot replace accessible source code, standards-based evaluation, or testing with the people who use the product.

Planning Accessibility as a System

Accessibility becomes easier to sustain when it is part of ordinary product decisions rather than a separate launch activity.

The first planning decision is the conformance target. WCAG 2.2 Level AA is a sensible product target when no governing rule requires a different version, and the W3C recommends adopting it over earlier WCAG 2 versions. The target then belongs in acceptance criteria, design review, and the definition of done for shared components. A reusable button or form field should be tested once at its source and again in representative product contexts. Centralizing the pattern does not remove page-level responsibilities, but it prevents every team from rebuilding the same interaction independently.

Practice
Put accessibility in the definition of done

A component without an appropriate accessible name or its expected keyboard interaction is unfinished. Recording that requirement before implementation gives reviewers a clear basis for rejecting the defect instead of postponing it to an unspecified audit.

Design tokens can support the same goal without pretending to guarantee it. A shared focus treatment and approved foreground-background pairs give components safer defaults. Motion utilities can provide reduced-motion variants for teams to reuse. Actual conformance still depends on how those tokens are combined in a component and how that component appears in context. UX Principles explains how contrast, spacing, and type fit into the wider token system.

Procurement extends the boundary beyond code the organization owns. A third-party component, embedded service, or customer-facing platform can introduce barriers into the final workflow. The Voluntary Product Accessibility Template (VPAT) is a standard template for producing an Accessibility Conformance Report. The completed report should identify its product version, evaluation methods, applicable standards, and known gaps. It is evidence to examine rather than a certification, and representative workflows still need testing before a purchasing decision.

Testing Accessibility

Automated scanning is a floor, not a substitute for a person using a keyboard and a screen reader.

Automated tools such as axe-core can find many mechanical defects quickly, but coverage figures depend on what is being counted. Deque reported that its automated rules could detect 57.38% of issues in a sample of first-time customer audits. That number is not a percentage of WCAG that a tool can certify. The W3C states the broader limit plainly: tools cannot check every aspect of accessibility, and human judgment remains necessary. A scanner may detect a missing alt attribute, but it cannot decide whether the supplied text serves the image's purpose in context.

A workable testing strategy combines automated checks, expert review, and evaluation with users. Automated scanning can run in continuous integration and during component development. Manual passes then examine keyboard operation, reading order, focus behavior, text alternatives, and the clarity of errors. Testing with disabled users adds evidence about whether complete workflows are usable, while WCAG evaluation checks the wider range of requirements that a small user sample cannot represent. Testing Strategy covers how these checks fit into the broader test suite.

A keyboard-only pass is an efficient place to begin manual testing. Move through the interface with Tab and Shift+Tab, operate controls with their expected keys, and confirm that focus stays visible and never becomes trapped. A screen reader pass examines a different layer: names, roles, states, reading order, errors, and dynamic announcements. Choose test combinations from the browsers, operating systems, and assistive technologies used by the product's audience. Results from one combination should not be generalized to all others because browsers and assistive technologies share responsibility for presenting the accessibility tree.

The architecture decision is therefore less about a special accessibility layer than about ownership. Shared components own their semantics and interaction. Product teams own the complete workflow and its content. The delivery process supplies automated checks, manual evaluation, and user feedback at the points where each is useful.
