Accessibility as an Architecture Decision

Why accessibility is cheaper to design in than to retrofit, what standards actually govern it, and how to plan for it before code gets written.

Deep dive
Andreas Ögren
~15 min read
Accessibility fundamentals
Last updated July 2026

Accessibility is usually discussed as a checklist to run through near launch. Treated that way, it behaves like one: a pile of fixes discovered late, against components that were never built to hold them.

An estimated 1.3 billion people, about 16% of the global population, experience a significant disability. That figure only counts conditions that meaningfully limit daily activity. It doesn't count the much larger group who hit a temporary or situational version of the same barrier: an arm in a cast, a phone screen washed out by sunlight, a hallway too noisy for audio to help, a new parent operating a laptop one-handed. Reach is the first reason accessibility belongs at the architecture level rather than the QA level. It's also, on its own, the least persuasive one to a team under deadline pressure, so this article covers the other two: what legally governs the decision, and why the cost of getting it right moves in one direction as a project ages.

That cost curve is the part worth internalizing before anything else. A component library that renders a real <button> instead of a styled <div> costs nothing extra to build correctly the first time. The same fix applied after three hundred product screens have copied the wrong pattern is a migration project. Accessibility isn't unusual in this respect. It follows the same shape as any architectural decision made once at the foundation versus repeated badly at every call site, just with a wider blast radius, because interactive components get reused more than almost anything else in a frontend codebase.

Semantic HTML Does the Work

Most of what accessibility requires isn't extra code. It's using the element the browser already built for the job instead of reconstructing it by hand.

Every browser exposes a parallel structure to assistive technology called the accessibility tree. It's built from the document object model (DOM) but isn't identical to it: purely decorative nodes get dropped, some elements are renamed or merged, and every node carries a computed role, an accessible name, and a state (expanded, checked, disabled, and so on). A screen reader doesn't read raw markup. It reads the accessibility tree, which is why two visually identical elements can behave completely differently for a screen reader user depending on what actually produced them.

A native <button> arrives in that tree with a role of "button" already set, an accessible name computed from its text content, keyboard operability (Enter and Space activate it, while Tab reaches and leaves it in the expected order), and a focus outline the browser manages on its own. None of that was written by whoever used the tag. It came from the browser's own implementation of the HTML specification, and it's consistent across every browser and every assistive technology that reads the accessibility tree. A <div> styled to look identical starts with none of it. Every one of those properties has to be added back by hand, and every one has to be kept in sync as the component evolves.

The same argument extends well past buttons. A native <dialog> element, opened with its showModal() method, comes with a focus trap, an inert background that keeps the rest of the page from receiving clicks or keystrokes while it's open, a backdrop, and Escape-to-close, all handled by the browser. The newer popover attribute covers the lighter case, a menu, a tooltip, a toast, with its own default focus handling and Escape binding, without going as far as a full modal focus trap. A <details>/<summary> pair gets an expandable disclosure with correct aria-expanded state management for free. In every one of these cases, the alternative is a JavaScript library or a hand-built component reimplementing behavior a 2026 browser already ships, and reimplementations are where accessibility regressions tend to live: a focus trap that doesn't quite trap, an escape key that's wired to one handler but not another added later. Reaching for the platform first is a real 2026 default, not a nostalgia argument for plain HTML.

What ARIA Is For

Accessible Rich Internet Applications attributes exist to patch a real gap in semantic HTML, not to replace it.

Accessible Rich Internet Applications (ARIA) is a set of HTML attributes, role, aria-label, aria-expanded, and dozens more, that let a component tell the accessibility tree things the tag alone can't express. A custom dropdown, a tab panel, or a live region that updates without a page reload all need ARIA because HTML doesn't have a native element for them. That's a legitimate and common need. What ARIA can't do is retroactively grant keyboard behavior, focus management, or any of the other free properties a native element carries. Adding role="button" to a <div> tells a screen reader to announce it as a button. It does nothing to make Enter or Space activate it, and nothing to put it in the expected tab order, both of which then have to be coded in by hand and kept correct for the life of the component.

button.html HTML 
<!-- Needs a manually added keydown handler for Enter and Space,
     and a manually added tabindex to enter the tab order at all -->
<div role="button" tabindex="0">Submit order</div>

<!-- Gets both behaviors from the browser, for free -->
<button>Submit order</button>

The rule the W3C's own authoring guidance leads with settles most day-to-day decisions on its own: don't use ARIA if a native element or attribute already does the job. Reach for it when the markup genuinely has no native equivalent, not as a default way to build a custom design system's components.

Worth knowing at a conceptual level, since it explains a class of bug that shows up constantly in component libraries: a screen reader computes an element's accessible name by checking a fixed order of sources, not by picking whichever one looks most convenient. An explicit aria-labelledby or aria-label wins if present, then visible label text associated through a <label> element or similar mechanism, then the element's own text content, and only as a last resort a title attribute, which most screen readers treat as a weak fallback rather than a primary name. A component that sets aria-label for one piece of visible text and then changes the visible text later, without updating the attribute, produces a real name mismatch: sighted users read one label, screen reader users hear another. That drift is a common, quiet source of accessibility bugs precisely because nothing about it fails visually.

The Standards Landscape

One standard governs almost every accessibility conversation in practice, with conformance levels that show up in law even when the underlying legislation never mentions the standard by name.

The Web Content Accessibility Guidelines (WCAG) are the W3C's technical standard for accessible web content, and version 2.2 is the current Recommendation as of 2026. It carries real international weight beyond the W3C's own endorsement: WCAG 2.2 was approved as ISO/IEC 40500:2025 in October 2025, giving it the same formal standing as an ISO specification in procurement and regulatory contexts. WCAG defines three conformance levels, A, AA, and AAA, each layering stricter criteria on the one below it. AA is the level that matters in practice, since it's the level named by essentially every law or regulation that references WCAG at all. Full AAA conformance is rare and, for some criteria, not achievable for all content by design.

A successor, WCAG 3.0, is in development and worth tracking without planning around yet. It proposes a graded outcome model in place of the current binary pass-or-fail criteria, closer to a maturity score than a checklist. As of a March 2026 working draft it listed 174 requirements and remained far from a stable, citable conformance model. Organizations should keep conforming to WCAG 2.2 and treat WCAG 3.0 as a multi-year horizon, not something worth deferring current work for.

Who Enforces This

Deadlines move, penalties vary by jurisdiction, but the direction has only gone one way: more regulators naming WCAG explicitly, not fewer.

In the European Union, the European Accessibility Act (EAA) has applied since 28 June 2025, and 2026 is the first full year national authorities are actively supervising against a deadline that has already passed. It reaches further than most government-only accessibility rules, covering private-sector e-commerce, banking, and other digital services sold into the EU, not just public bodies. Enforcement sits with member states individually rather than one central regulator, and the first test case is already underway: disability advocacy groups filed suits in France in November 2025 against four major retailers, with no ruling and no fines issued as of April 2026.

In the United States, a 2024 Department of Justice rule under Title II of the Americans with Disabilities Act (ADA) set WCAG 2.1 Level AA as the binding technical standard for state and local government web and mobile content. The original 2026 and 2027 compliance dates were pushed back a year by an April 2026 rule, to April 2027 for entities serving 50,000 people or more and April 2028 for smaller entities and special districts. The extension changes the timeline, not the destination. WCAG AA conformance is already the named target, and private-sector ADA litigation (which doesn't name a specific technical standard but treats WCAG conformance as the practical benchmark courts and plaintiffs point to) has been active for years independent of the Title II rule entirely.

The Overlay Widget Shortcut

One decision an architect gets asked to sign off on more often than any other in this space is whether to install an overlay widget, a third-party script layered on top of an existing site that promises to detect and patch accessibility issues automatically, usually with a floating badge in a corner of the page. Regulators and disability organizations are broadly aligned on the answer. The EU Commission has stated directly that overlay widgets don't satisfy EAA compliance. In the US, the Federal Trade Commission fined the largest overlay vendor, accessiBe, one million dollars in 2025 for falsely claiming its product could make any website WCAG-compliant within 48 hours.

An overlay is a signal, not a fix

Screen reader users report that overlays frequently interfere with the assistive technology they already use, rather than improving anything. And because a visible overlay badge is now a known pattern, its presence can read to a regulator or a plaintiff's lawyer as a marker that the underlying site was never built accessibly, the opposite of the intended signal. There's no substitute for the semantic HTML and testing practice covered in this article. An overlay bought instead of that work is a liability with a subscription fee attached.

Planning for It as a System

The teams that don't end up doing a costly retrofit are the ones that never treated accessibility as a separate deliverable in the first place.

The practical move is to fold an accessibility target, WCAG 2.2 AA in most cases, into the same place a performance budget or a security review gate already lives: a non-functional requirement checked at the component library level, not a separate audit scheduled near launch. A shared component library is the highest-leverage place to spend this effort, because a correct, accessible button, form field, and dialog built once and reused everywhere pays for itself on every screen that consumes it. Fixing the same gap independently in every product team that built its own version is the expensive path, and it's the default outcome if accessibility isn't a stated requirement of the shared library from the start.

Practice
Definition of done, not definition of launch-blocker

A component that ships without a correct accessible name or keyboard support isn't "incomplete but shippable with a follow-up ticket." Treating it as unfinished, the same way a component with no error state would be treated, is what keeps the gap from ever reaching production in the first place.

The same logic extends to a design system's shared tokens, not just its components. A focus-visible outline style, a minimum contrast ratio, and a motion-reduction fallback each belong at the token layer for the same reason a correct <button> belongs in the component library: solved once, inherited everywhere, instead of re-solved inconsistently by whichever team happens to build the next screen. A design system that ships accessible tokens by default makes the accessible choice the path of least resistance, which matters more in practice than any amount of documentation telling teams what the inaccessible choice would have been. UX Principles covers where a token system like that comes from in the first place, including why contrast belongs there alongside spacing and type.

There's also a vendor-facing side to this planning that architects run into directly: procurement. Buying a third-party component library, a widget, or an embedded tool exposes an organization to that vendor's accessibility gaps as if they were its own. A Voluntary Product Accessibility Template (VPAT), a standardized report a vendor fills out describing how its product conforms to WCAG, is the artifact procurement teams increasingly ask for before a contract is signed, and it's worth treating with the same scrutiny as a vendor security questionnaire. A vendor without one, or with one several major versions out of date, is a real signal worth weighing against the rest of the evaluation.

Testing Accessibility

Automated scanning is a floor, not a substitute for a person using a keyboard and a screen reader.

Automated tools like axe-core catch a real share of issues, and estimates of how much vary by methodology. Deque's own sampling against real, documented defects puts detectable coverage around 57%. Other estimates, testing against the full criteria set rather than a sample of already-known defects, put the automatable share lower, closer to 30 to 40%. Either number leaves a substantial remainder that needs human judgment: whether alt text actually describes an image rather than restating its filename, whether a form's focus order matches its visual reading order, whether an error message read aloud actually explains what to fix. A scanner can confirm an image has an alt attribute. It can't confirm the attribute says anything useful.

The workable shape for most teams is automated scanning wired into continuous integration as a regression floor, catching the mechanical failures (missing labels, insufficient contrast, invalid ARIA) before they merge, paired with a periodic manual pass using a keyboard alone and at least one screen reader. That manual pass is the part that actually catches the failures users report, and it's also the part most commonly skipped when accessibility is scheduled as a single pre-launch audit rather than an ongoing practice. Broader test-automation strategy, the pyramid of unit, integration, and end-to-end coverage, belongs to a dedicated testing article. What's specific to accessibility is that a green automated scan is a floor, never a ceiling.

A keyboard-only pass is the cheapest version of manual testing and catches a surprising share of real problems on its own: unplug the mouse, and try to reach and operate every interactive element on a page using only Tab, Shift+Tab, Enter, Space, and the arrow keys. Anything unreachable, anything that traps focus with no way out, and any focus outline invisible against its background shows up immediately, no assistive technology required. Layering a screen reader on top catches what the keyboard pass alone can't: whether announcements make sense, whether a form field's error gets read aloud when it appears, whether a live region interrupts at a reasonable moment instead of talking over whatever the user was already doing. Three tools cover the vast majority of real-world usage and are worth testing against directly rather than a longer list. NVDA is free and dominant among Windows screen reader users, VoiceOver is built into every Apple platform, and JAWS remains common in enterprise and government environments. None of the three behaves identically to the others on edge cases, which is itself the argument for testing with more than one.

None of this is really a separate discipline from good architecture. A component library that gets semantic HTML right, a design system that bakes in focus states and contrast at the token level, and a testing practice that treats a keyboard as a first-class input device are the same investments a team makes for maintainability and resilience generally. The population directly served by getting it right is larger than most teams assume. The group that benefits indirectly, from clearer error messages, larger touch targets, and captions on video, is larger still. The other half of the picture, how a team's choice of rendering strategy, streaming, and hydration changes what this work actually requires, is covered in Accessibility and Rendering Architecture.
