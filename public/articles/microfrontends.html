Microfrontends

Why splitting a frontend across teams creates shared-dependency problems, and the build-time vs. runtime tradeoffs, such as module federation.

Deep dive
~22 min read
Frontend architecture
July 2026

A retailer's frontend starts as one codebase because one team owns it. Two years and four teams later, the checkout flow, the product catalog, and the account settings pages are still living in that same repository, deployed together, tested together, and blocked on each other's release windows. The catalog team wants to ship a search redesign on Tuesday. The checkout team is mid-migration to a new payment provider and can't risk a release until Thursday. Because everything ships as one build, the catalog team waits, or the two teams coordinate a joint release train that neither of them actually wants to be on.

That's the problem microfrontends exist to solve: independent team ownership and independent deploy cadence, at the point where an organization has grown past the size where one frontend codebase and one release process still fit the teams building it. It's an organizational problem wearing an architectural costume. The technical question, how do several separately built pieces of UI end up as one coherent page in a browser, only matters because the organizational one came first. That the org chart drives the architecture rather than the reverse is the argument the stack fits the team article makes in full.

This is a different axis from the two questions the rest of this series has covered. Rendering strategy asks when and where a given page's HTML gets built. React Server Components asks which parts of a component tree need to exist on the client at all. Microfrontends ask who owns which piece of the product and how those pieces get stitched together without those teams having to release in lockstep. A single microfrontend remote still picks its own answer to the first two questions entirely on its own, which is one of the reasons this axis is worth treating separately rather than folding it into either of the earlier articles.

Build-Time Composition

The easiest way to combine several teams' code into one frontend is to combine it before anything ships.

Build-time composition means each team's UI code lives in its own package, often in its own repository, but all of those packages get resolved, compiled, and bundled together into a single deployable artifact before that artifact ever reaches a browser. A monorepo with shared build tooling is the common shape this takes: separate source trees, one build step, one output. Nothing about the browser knows or cares that the code came from three different teams. By the time it's running, it's a single application.

The advantage is real and worth taking seriously before dismissing this approach as the naive option. Because everything is compiled together, there's no possibility of a runtime version mismatch between one team's code and another's. Whatever combination of dependencies and component versions passed the test suite is exactly what ships, because testing and shipping happen against the same resolved build. There's no seam in production where two independently built pieces might turn out to be incompatible in a way nobody caught before users hit it.

The cost is the one that matters for the problem this article opened with. Combining everything at build time reintroduces the exact coordination the teams were trying to escape: a shared build, a shared release window, one broken package blocking everyone else's deploy. Martin Fowler's framing of this tradeoff has become the standard reference point in the microfrontends literature, and it reads best stated plainly rather than softened. A build-time composed frontend, no matter how cleanly its packages are separated internally, is a modular monolith with better manners. It's genuinely easier to work in day to day than a tangled single codebase, and it's still one release train. Teams that only need cleaner internal boundaries, not independent deploys, should stop here. This approach solves that problem well. Teams whose actual requirement is that the checkout team can ship without waiting on the catalog team need something that composes later than build time.

Runtime Composition

Composing in the browser, at request time, is what actually decouples the deploys.

Runtime composition means each team ships their own independently built and independently deployed bundle, and those bundles only come together once a browser requests the page. Nobody has to wait for anybody else's build to finish, because there isn't a shared build. The checkout team can deploy Thursday and the catalog team can deploy Tuesday, and the only coordination required between them is agreeing on the contract at the seam where their code meets, not the release calendar.

Module Federation, introduced in webpack 5, is the dominant mechanism for this today. The tooling around it has grown considerably, but the core idea hasn't changed: separately built applications can share code with each other at runtime rather than at bundle time. A host application declares which remote modules it needs and where to find them, a remote application declares which of its own modules it's willing to expose, and the actual loading and wiring happens in the browser when the host runs.

rspack.config.js (remote: checkout) Module Federation 
const { ModuleFederationPlugin } = require('@module-federation/enhanced/rspack');

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'checkout',
      exposes: { './CartSummary': './src/CartSummary' },
      shared: {
        react: { singleton: true, requiredVersion: '^19.0.0' },
        'react-dom': { singleton: true, requiredVersion: '^19.0.0' },
      },
    }),
  ],
};

The host side is the mirror image: a matching remotes entry pointing at the checkout team's deployed manifest, and an ordinary-looking import in the host's own code, const CartSummary = await import('checkout/CartSummary'), that resolves to code the host never bundled itself. The singleton: true line on react matters enough to earn its own section further down, it's the difference between the host and remote genuinely sharing one React instance and quietly loading two.

single-spa takes a lighter path to the same runtime-composition goal. Instead of a bundler plugin that rewrites how modules resolve, it relies on browser-native import maps and a small root-level orchestrator that decides which registered application should be active for the current route, then mounts and unmounts applications as the user navigates. Because it doesn't require a specific bundler, it's the more natural choice when the remotes being composed aren't all using the same build tool, or aren't all written in the same framework to begin with, a React shell mounting an Angular settings panel and a Vue reporting widget is squarely single-spa's home turf in a way it isn't Module Federation's.

A third option solves a narrower version of the problem, and it belongs before either of the runtime mechanisms above: Next.js Multi-Zones. A Multi-Zone setup doesn't share components or runtime state between zones at all, it splits an application into several distinct Next.js apps that live under one domain, with routing rules (typically at the reverse proxy or next.config level) deciding which zone serves which URL path. Moving between zones is a genuine full navigation, not a runtime composition. For a team whose actual requirement is "separate builds, separate deploys, separate teams" rather than "share a live component across two apps without a page reload," Multi-Zones solves that without touching Module Federation at all, and it's worth checking whether that's the real requirement before reaching for the heavier runtime-sharing mechanisms.

Web Components as a Composition Boundary

A remote shipped as a native custom element doesn't need the host to know or care what built it.

Module Federation and single-spa both compose JavaScript modules, which means the host and the remote are, at some level, speaking the same framework's language even when the tooling papers over the difference. Custom elements offer a third composition boundary that sidesteps that requirement entirely. A team builds their remote as a native custom element, whatever framework they used internally to build it, React, Svelte, plain JavaScript, and ships a single script that registers a tag like <checkout-cart-summary>. The host doesn't import a module, negotiate a shared dependency, or run a bundler plugin aware of the remote's existence. It drops a tag into its markup and the browser does the rest.

host page HTML 
<!-- host has no build-time knowledge of what CartSummary is built with -->
<script type="module" src="https://checkout.example.com/cart-summary.js"></script>

<section>
  <h2>Your cart</h2>
  <checkout-cart-summary user-id="{{ userId }}"></checkout-cart-summary>
</section>

The tradeoff mirrors the one that shows up everywhere in this article: less coupling in exchange for less sharing. A Web Components remote can't lean on the host's React context, its router, or a shared client-side cache the way a Module Federation remote sometimes can, because it's deliberately opaque to the host beyond its custom element interface and whatever attributes and events that interface exposes. What it buys back is genuine framework independence and a much smaller integration surface, no shared runtime version to negotiate, no bundler plugin both sides need to agree on. For a remote that's meant to be dropped into products the owning team doesn't control at all, a marketing site, a partner's storefront, a component this loosely coupled is often the more realistic choice than one that assumes a matching Module Federation host on the other end.

Sharing State Across Remotes

The default should stay loosely coupled, because the whole point was independent teams.

Once two remotes are running on the same page, something usually needs to pass between them. A user adds an item in the catalog remote and the checkout remote's cart badge needs to update. The default, and the option that keeps remotes genuinely independently deployable, is custom events or a small pub-sub layer sitting outside either remote's own code. The catalog remote dispatches an event describing what happened, the checkout remote listens for it and updates itself, and neither remote imports the other's state shape or knows the other exists beyond the shape of the event contract itself.

catalog remote JavaScript 
window.dispatchEvent(
  new CustomEvent('cart:item-added', {
    detail: { sku: 'SKU-1042', quantity: 1 },
    bubbles: true,
  })
);
checkout remote JavaScript 
window.addEventListener('cart:item-added', (event) => {
  updateBadgeCount(event.detail.quantity);
});

A shared state library, Zustand and Redux both show up here in practice, is a reasonable choice too, but it comes with a condition: it only makes sense when the remotes sharing that store are tightly co-owned by one team. The moment a shared store is imported by remotes owned by two different teams, the architecture has quietly recoupled exactly what runtime composition was supposed to decouple. Team B can no longer change its half of the store's shape without checking with team A, which is the lockstep-release problem from the build-time composition section showing up again, just at the state layer instead of the build layer.

URL and query parameters cover a third case of their own: cross-remote navigation context that needs to survive a full page load, not just a runtime event. A filter applied in the catalog remote that should still be active if the user bookmarks the page, or shares the link, or reloads the browser, belongs in the URL rather than in an in-memory event or a store, because it's the one state-sharing mechanism here that isn't scoped to a single page session.

Who Owns the Address Bar

The routing question is really an ownership question in disguise.

Routing-layer composition, Multi-Zones is the clearest current example, gives each remote genuine ownership of whole routes. Moving from /catalog to /checkout is a real navigation: a new document request, a new full page load, handled by whichever zone owns that path. Each team's remote is, from the browser's perspective, simply a separate application that happens to live under a shared domain and shared top-level navigation.

Client-side shell routing, single-spa's model, works the other way. One shell application owns the URL for the whole page, and remotes are mounted into regions of that page without a full navigation when the shell's router decides a given remote should be active. Moving between two areas of the product can feel instantaneous, because it's not a page load at all, it's the shell unmounting one remote and mounting another into the same DOM region.

The Current Tooling Landscape 2026

The practical path depends heavily on what a team is already building with.

Module Federation 2.0, shipped as @module-federation/enhanced, reached a stable release across the broader bundler ecosystem in early 2026, decoupling the runtime from webpack specifically. The same federation runtime now works across Rspack, Vite, and Rollup, not just webpack, with added TypeScript type sharing across federated boundaries and manifest-based host discovery so a host doesn't need remote URLs hardcoded at build time. For a team with an existing webpack investment, running Module Federation 2.0 on Rspack rather than plain webpack is currently the practical migration path: Rspack's webpack-compatible configuration API means most of an existing setup carries over directly, while builds run something like five to ten times faster.

Next.js complicates that picture rather than extending it. Turbopack, the default bundler in Next.js 16, does not support Module Federation. It's on the public roadmap and explicitly unshipped, which is a real gap for any team hoping to run Module Federation inside a Turbopack-built Next.js app today. The practical consequence is a growing divergence between Module Federation and Next.js's own architectural direction: teams building microfrontends on Next.js today are more often pointed toward Multi-Zones, single-spa, Astro islands, or a plain monorepo instead, several of which were never solving a genuine runtime-sharing problem to begin with and are better fits for teams whose real need was separate builds and separate teams.

Native Federation, maintained by the Angular Architects team, is the framework-agnostic alternative, relevant even outside the Angular ecosystem it originated in. It implements the same composition idea, remotes exposing modules a host can consume at runtime, but over native ECMAScript modules and browser import maps instead of a bundler-specific runtime. That makes it lighter than the webpack-derived Module Federation runtime and usable from any build tool that can emit standard ESM, at the cost of some of the manifest tooling and TypeScript-sharing convenience Module Federation 2.0 has built up around itself.

Zephyr sits a level above both, as a build and hosting layer rather than a federation mechanism of its own. It resolves shared dependencies and dedupes assets across a set of federated remotes even when those remotes were built with different bundlers, Webpack, Vite, Rspack, and Rollup among them, using content-addressed storage to avoid shipping the same dependency twice under two different bundlers' output. For an organization where different teams have already settled on different bundlers, which is common once a company reaches the size where microfrontends make sense at all, that cross-bundler resolution is often the more pressing problem than which single federation library to standardize on.

One more piece of the current landscape is where remotes run, not just how they're built. Hosting a remote's bundle from a Cloudflare Workers edge location, the same edge-versus-origin tradeoff covered for edge SSR in the rendering strategies article, buys the same lower cold-start latency for a federated remote's static assets that it buys for a rendered page, worth considering once a remote's origin location starts showing up in latency numbers for users far from wherever it's currently hosted.

CSS Isolation

A global stylesheet from one remote can silently override another remote's button styles, and nothing in the browser stops it by default.

CSS has no built-in module boundary. A stylesheet loaded by one remote applies to the entire document, not just the DOM nodes that remote rendered, which means an unscoped button { padding: 8px } rule from the catalog remote can quietly restyle the checkout remote's buttons too, with no error, no warning, and no obvious cause when someone finally notices the layout looks wrong. This is the actual failure case that makes CSS isolation worth planning for deliberately rather than discovering the hard way in production.

Hard isolation
Shadow DOM

Via Shadow DOM. Styles inside a shadow root can't leak out and page styles can't leak in, enforced by the browser itself, not by convention.

Soft isolation, build-time
CSS Modules / scoped hashing

Class names get hashed at build time so two remotes' .button classes can't collide, but a genuinely unscoped global rule still escapes.

Soft isolation, runtime
CSS-in-JS

Scoping happens at runtime instead of build time, useful when remotes are composed dynamically and never share a build step to hash classes against.

Shadow DOM is the only option on that list enforced by the platform rather than by discipline, which is part of why it pairs naturally with the Web Components composition boundary covered earlier, a remote already living inside a custom element gets shadow-root style isolation close to for free. CSS Modules and CSS-in-JS both depend on every remote actually using the convention consistently. One remote that ships a genuinely global stylesheet, intentionally or by mistake, defeats either approach for everyone sharing the page with it.

Shared Dependency Pitfalls

The React duplication bug is the one every team hits first, and it fails at runtime, not at build time.

Back in the Module Federation config example earlier, the shared entry for React carried a singleton: true flag. Leave that flag off, or leave it off in just one of the host or remote configs while the other has it, and Module Federation doesn't refuse to build. It builds cleanly, deploys cleanly, and then loads two separate copies of React into the same page at runtime, one bundled with the host and one bundled with the remote. React's hooks depend on a single module-level instance tracking which component is currently rendering, and two React copies means two of those instances, neither aware of the other. The result is usually Invalid hook call, thrown deep inside whichever component happened to call a hook from the "wrong" copy of React, with a stack trace that gives no hint that the actual cause is a missing singleton flag three files away.

browser console Runtime error 
Error: Invalid hook call. Hooks can only be called inside the body of a function component.
This could happen for one of the following reasons:
1. You might have mismatching versions of React and the renderer
2. You might be breaking the Rules of Hooks
3. You might have more than one copy of React in the same app

React is the version of this problem that surfaces loudest, because React happens to fail in a way that names itself in the error message. The underlying issue, dependency hoisting and version negotiation across independently built remotes, isn't specific to React at all. A shared date library, a shared design-system package, any dependency two remotes both import can drift out of sync the same way, sometimes loading two versions side by side, sometimes silently picking whichever version loaded first regardless of which remote actually asked for it. Module Federation's shared-scope negotiation exists specifically to manage this, matching version ranges where it can and falling back to separate instances where it can't, but a fallback to separate instances is exactly the silent-duplication failure above, just for a dependency that doesn't announce itself as loudly as React does.

Cross-origin requests add a second category of pitfall once remotes are actually served from different domains rather than different paths on the same one. A host on shell.example.com loading a remote's manifest and assets from checkout.example.com is a cross-origin request, subject to the same CORS preflight behavior covered in the HTTP article: the remote's server has to return the right Access-Control-Allow-Origin headers or the browser blocks the response before the host ever sees it, and if that remote's calls need to carry cookies or credentials, the CORS configuration has to explicitly allow that too, a plain wildcard origin isn't enough once credentials are involved. This connects directly to the next section, because the same cross-origin boundary that trips up asset loading is exactly where a shared auth session has to survive.

Shared Auth Context

Independently deployed remotes still need to agree on who's logged in.

A user shouldn't have to authenticate separately to the catalog remote and the checkout remote just because two different teams built and deployed them independently. The common solution is a session cookie scoped to a shared parent domain, example.com rather than checkout.example.com specifically, so every remote served under that domain receives the same session automatically. Where cookies aren't practical, typically because remotes genuinely live on unrelated domains, the shell instead holds the authenticated token and passes it down to each remote it composes, rather than each remote independently running its own login flow against the identity provider. Either way, the underlying token mechanics, what's actually inside that cookie or token and how it gets validated, are the same ones covered in the tokens section of the OAuth and OIDC article, this is a question of where that token lives and how it reaches each remote, not a different authentication model.

One narrow case deserves a specific mention: a remote that needs SharedArrayBuffer or runs WebAssembly requiring cross-origin isolation has to be served with COEP and COOP headers set correctly, and getting those headers wrong is a common way for an otherwise-working cross-origin microfrontend setup to break in a way that has nothing to do with CORS or auth at all. It's a narrow enough case that most microfrontend setups never hit it, but the symptom, isolated features failing silently or refusing to load, points here rather than back at the CORS or cookie configuration.

When It's Worth It

The org chart, not the codebase, is what determines whether any of this is worth the cost.

Team Topologies gives the clearest vocabulary for answering this, and it's worth borrowing directly rather than reaching for a vaguer "big org" justification. A stream-aligned team, one organized around a continuous flow of work toward a specific business domain, checkout, catalog, account, rather than around a technical layer, is the org shape microfrontends actually benefit. That team owns its slice end to end, including the decision to deploy it, and runtime composition is what lets that ownership extend all the way to production without waiting on anyone else's release calendar. An organization that hasn't actually organized itself into teams shaped like that doesn't get the benefit just by adopting the architecture, the deploy independence microfrontends promise only shows up if there's a team boundary in the first place for it to align with.

A shared design system is what keeps independently built remotes from drifting into a product that visibly looks like four different products stapled together. It's the contract, not a technical mechanism, that makes runtime composition tolerable at the UI level, consistent spacing, typography, and component behavior across remotes that share nothing else at build time. Skipping it is the single most common way a microfrontend migration produces a worse-looking product than the monolith it replaced, not because the architecture is wrong but because nothing was left to keep the visual language aligned once the teams stopped sharing a codebase.

CI/CD is where the operational reality of this tradeoff actually lands. Each remote gets its own pipeline, its own test suite, its own deploy schedule, which is the entire point, but it also means the one giant end-to-end suite that used to catch integration bugs across the whole product no longer has a single build to run against. Contract tests between the shell and each remote, verifying that a remote still exposes what the shell expects at the boundary, whatever that boundary is, a custom element's attributes, a federated module's exports, an event's payload shape, become the replacement. They're narrower than a full end-to-end suite and faster to run, but they only catch what's actually in the contract, which makes writing a contract that covers the seams that matter as important as the testing infrastructure itself.

Observability carries its own microfrontend-specific wrinkle: a single user-facing error can originate in a remote that a completely different team owns and monitors, which makes correlated tracing across independently deployed remotes, not just "everyone uses the same APM," the part that actually needs deliberate setup. The full depth of that belongs to a dedicated observability article rather than this one.

Worth it
Genuinely autonomous stream-aligned teams

Separate teams that need to deploy on separate schedules, own separate domains end to end, and would otherwise be blocked on each other's release windows.

Not worth it
Code organization within one team

If the real goal is cleaner internal boundaries rather than independent deploys, that's a module-boundary problem. Plain imports and a well-organized monorepo solve it without any of the runtime cost above.

Where the Boundary Sits

Two things to close on, because both are easy to conflate with material from earlier in this series. First, a microfrontend remote still makes its own choice from the full menu in the rendering strategies article, SSR, SSG, a plain SPA, whatever fits that team's product, entirely independently of how it gets composed into the larger page. Composition and rendering strategy are orthogonal decisions, and nothing about runtime composition constrains which one a given remote picks.

Second, the word "island" gets used loosely enough across this series that it's worth drawing the line explicitly. Astro's islands and a client component inside a server-rendered React tree are both a granularity-of-JavaScript decision made within a single page, by a single team, at build or render time. A federated microfrontend remote is a different unit of composition entirely: a separately built, separately deployed application boundary owned by a different team, composed at runtime rather than embedded in a single render pass. Both get called "islands" informally often enough that the resemblance is real, but they're solving different problems at different organizational scales, and treating them as the same mechanism is where the analogy stops holding.
