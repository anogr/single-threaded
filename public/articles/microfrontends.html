Microfrontends

How independent teams compose one product, and what they trade for separate builds and deployments.

Andreas Ögren
~13 min read
Last updated July 2026

A retailer's frontend may begin as one codebase owned by one team. As the product grows, checkout, catalog, and account work can move to separate teams while the application still ships as one build. A release in one area then depends on the readiness of every other area. The technical boundary no longer matches the ownership boundary.

Microfrontends align parts of the interface with teams that can build and deploy them independently. The architecture is justified by organizational autonomy, not by the size of the repository alone. Once that need exists, the technical problem is how separately produced interfaces form one coherent product. The Stack Fits the Team develops the relationship between team boundaries and system boundaries in full.

This decision is separate from rendering strategy and the Server and Client Component boundary. Those choices determine where markup and JavaScript execute. Microfrontends determine ownership and composition across independently delivered parts of the product. Each remote still chooses its own rendering model.

Build-Time Composition

The easiest way to combine several teams' code into one frontend is to combine it before anything ships.

Build-time composition keeps each team's interface in a separate package but resolves those packages into one deployable application. A monorepo often provides this shape through separate source trees and shared tooling. The browser receives one application and has no runtime knowledge of the team boundaries.

A shared build resolves dependency versions before release and tests the same combination that will ship. Integration failures are therefore visible before deployment rather than discovered when independently built artifacts meet in a browser. The model is often sufficient when teams need clear source ownership but can still coordinate releases.

The same shared build also preserves a shared release window. A broken package can block every team, and dependency updates land together. The result is a modular monolith with strong internal boundaries rather than an independently deployed system. It solves source organization well. Teams that need separate production releases must compose later.

Runtime Composition

Runtime composition lets independently built artifacts meet after deployment.

Runtime composition lets each team build and deploy its own artifact. The host discovers or loads those artifacts when serving or running the application. Release coordination moves from a shared build to explicit contracts at the seams between host and remotes.

Module Federation, introduced with webpack 5, implements this model for JavaScript modules. A remote declares modules it exposes, while a host declares how to locate and consume them. The federation runtime loads the remote and negotiates shared dependencies after the applications have been built separately.

rspack.config.ts (remote: checkout) TypeScript 
import { ModuleFederationPlugin } from '@module-federation/enhanced/rspack';

export default {
  plugins: [
    new ModuleFederationPlugin({
      name: 'checkout',
      exposes: { './CartSummary': './src/CartSummary' },
      shared: {
        react: { singleton: true, requiredVersion: '^19.0.0' },
        'react-dom': { singleton: true, requiredVersion: '^19.0.0' },
      },
    }),
  ],
};

The host points a remotes entry at the checkout manifest. An import such as await import('checkout/CartSummary') then resolves to code that was not part of the host build. The singleton: true setting asks the federation runtime to use one React instance across that boundary, which is examined later.

single-spa orchestrates applications rather than federating their module graphs. A root configuration decides which registered application is active for the current route and mounts or unmounts it during navigation. Import maps are a common way to resolve those applications, but single-spa does not require one bundler or framework. That makes it suitable for gradual migrations and deliberately mixed framework estates.

Next.js Multi-Zones solve a narrower problem at the routing layer. Several applications share a domain, while routing rules assign URL paths to zones. Navigation within a zone can remain client-side, but crossing between zones performs a full document navigation. This provides separate builds and deployments without sharing live components or in-memory state.

Web Components as a Composition Boundary

A remote shipped as a native custom element doesn't need the host to know or care what built it.

Custom elements provide a browser-defined composition boundary. A remote registers a tag such as <checkout-cart-summary>, regardless of the framework used inside it. The host loads the registration script and uses the element through attributes, properties, methods, slots, and events. No shared framework runtime is required at the interface.

host page HTML 
<!-- host has no build-time knowledge of what CartSummary is built with -->
<script type="module" src="https://checkout.example.com/cart-summary.js"></script>

<section>
  <h2>Your cart</h2>
  <checkout-cart-summary user-id="{{ userId }}"></checkout-cart-summary>
</section>

The boundary limits coupling by limiting what can be shared. A custom element does not automatically participate in the host's React context, router, or client cache. Integration must pass through its public element contract. That smaller surface suits remotes embedded in products the owning team does not control, although it requires deliberate API and accessibility design.

Sharing State Across Remotes

State exchange should preserve the independence that runtime composition created.

Remotes on the same page often need to exchange information. A catalog can publish that an item was added, and a checkout badge can react. Custom events or a small external event bus preserve independence when the event payload is versioned as a public contract. Neither remote needs to import the other's internal state shape.

catalog-events.ts TypeScript 
window.dispatchEvent(
  new CustomEvent('cart:item-added', {
    detail: { sku: 'SKU-1042', quantity: 1 },
    bubbles: true,
  })
);
checkout-events.ts TypeScript 
type CartItemAddedDetail = { sku: string; quantity: number };

window.addEventListener('cart:item-added', ((event: CustomEvent<CartItemAddedDetail>) => {
  updateBadgeCount(event.detail.quantity);
}) as EventListener);

A shared store can work when the participating remotes are deliberately co-owned. Across independent teams, the store becomes a shared implementation detail whose shape must change in coordination. That recreates release coupling at the state layer. Client State covers the ownership and placement questions behind that choice.

The URL handles navigation context that must survive a document load or be shareable. A catalog filter that should remain after refresh belongs in path or query state rather than an in-memory event. This also lets routing-layer composition pass context across a hard navigation.

Who Owns the Address Bar

Routing determines whether the shell or each application owns navigation.

Routing-layer composition gives each application ownership of whole paths. In a Multi-Zones setup, moving from /catalog to /checkout crosses an application boundary and loads a new document. The browser sees separate applications under one domain and shared navigation design.

Shell routing keeps one application in control of the URL. The shell activates remotes for the current route and mounts them into regions of the existing document. Navigation can preserve in-memory shell state, but every remote must follow the shell's routing contract.

The Current Tooling Landscape 2026

The practical path depends heavily on what a team is already building with.

Module Federation 2.0 is stable and supports integrations across webpack, Rspack, Vite, and the Rollup/Rolldown ecosystem. Its runtime and manifest model extend the original webpack feature with remote discovery, runtime plugins, and type-generation support. Rspack is a close fit for existing webpack configurations, while other integrations use their own build plugins.

Next.js follows a different path. Its Module Federation integration requires webpack, while Turbopack is the default bundler in Next.js 16. Teams that only need independently deployed route groups can use Multi-Zones without federating modules. A team that needs runtime component sharing must evaluate the webpack integration or choose a composition layer outside the default Next.js build.

Native Federation uses standard ES modules and import maps to load exposed modules at runtime. Although it originated in the Angular ecosystem, its runtime boundary remains independent of a particular bundler. The tooling model differs from Module Federation's shared scopes and generated type support.

Zephyr adds a deployment and asset-management layer for federated applications. It can publish manifests and coordinate assets produced by different bundlers. Teams with varied build systems can use that layer to create operational consistency above the federation runtime.

Remote assets also need an ordinary delivery strategy. A content delivery network can place static bundles closer to users, while server-rendered remotes inherit the data-location tradeoffs described for edge SSR. Federation does not remove HTTP caching, origin, or availability concerns.

CSS Isolation

A global stylesheet from one remote can silently override another remote's button styles, and nothing in the browser stops it by default.

An ordinary stylesheet applies across the document. An unscoped button { padding: 8px } rule from one remote can therefore restyle another remote without producing an error. Runtime independence needs a corresponding styling boundary, or the cascade becomes an undocumented integration surface.

Hard isolation
Shadow DOM

Via Shadow DOM. Styles inside a shadow root can't leak out and page styles can't leak in, enforced by the browser itself, not by convention.

Soft isolation, build-time
CSS Modules / scoped hashing

Class names are rewritten at build time so two remotes' local .button classes cannot collide. An unscoped global rule can still escape.

Soft isolation, runtime
CSS-in-JS

Scoping happens at runtime instead of build time, useful when remotes are composed dynamically and never share a build step to hash classes against.

Shadow DOM provides the strongest browser-enforced selector boundary and pairs naturally with custom elements. CSS Modules and generated classes prevent local name collisions but cannot contain an intentionally global selector. Whichever mechanism is chosen, the shell still needs shared tokens and component contracts to keep the product visually consistent.

Shared Dependency Pitfalls

The React duplication bug is the one every team hits first, and it fails at runtime, not at build time.

The earlier federation configuration marked React as a singleton. Without compatible sharing configuration, the host and remote may load separate React instances. A component rendered by one instance can then call hooks from another, producing React's Invalid hook call warning. The build can still succeed because the incompatibility appears only after the independently built artifacts are composed.

browser console Runtime error 
Error: Invalid hook call. Hooks can only be called inside the body of a function component.
This could happen for one of the following reasons:
1. You might have mismatching versions of React and the renderer
2. You might be breaking the Rules of Hooks
3. You might have more than one copy of React in the same app

The wider issue is dependency negotiation. Two remotes may request incompatible versions of a date library or design-system package. The federation runtime can satisfy compatible ranges from a shared scope or load separate versions when necessary. Separate copies may be harmless for pure utilities and dangerous for stateful singletons, so the sharing policy must reflect the dependency's semantics.

Serving remotes from another origin adds browser security rules. Module scripts and API requests must satisfy the relevant CORS mechanism. Credentialed requests require an explicit allowed origin and credential policy rather than a wildcard. These constraints affect asset loading and any shared authentication context.

Shared Auth Context

Independently deployed remotes still need to agree on who's logged in.

Authentication should remain a product-level concern even when teams deploy separately. Same-site applications can rely on a server-managed session and appropriately scoped cookies. Cross-origin composition needs a deliberate token-exchange or backend integration rather than passing long-lived credentials through arbitrary remotes. OAuth and OIDC covers the token and session mechanics. The microfrontend concern is preserving one trust boundary across several artifacts.

A remote that requires cross-origin isolation, for example to use SharedArrayBuffer, also depends on compatible Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers across the page. This requirement belongs to the document as a whole, so one incompatible resource can prevent isolation even when CORS and authentication are configured correctly.

When Microfrontends Fit

The org chart, not the codebase, is what determines whether any of this is worth the cost.

Microfrontends fit stream-aligned teams that own business capabilities such as checkout, catalog, or accounts from development through deployment. Runtime composition lets that ownership extend to the release boundary. If teams remain organized around technical layers or share one approval process, the architecture adds runtime seams without creating meaningful autonomy.

A shared design system provides the visual and behavioral contract across remotes. Tokens, components, accessibility rules, and version policy must remain consistent even when source code and releases do not. Without that governance, technical independence appears to users as inconsistent interaction and visual drift.

Independent pipelines also change testing. Each remote can verify its own behavior, while contract tests check the exports, element API, or event schema at integration boundaries. A smaller set of end-to-end tests should still exercise deployed combinations because contracts cannot capture every rendering and timing interaction. The test strategy must reflect the fact that no single build now represents the whole product.

Observability must identify the remote name, version, and owning team in shared logs and traces. A browser error can cross shell and remote boundaries, so correlation is more valuable than separate dashboards that cannot reconstruct one user journey.

Worth it
Autonomous stream-aligned teams

Separate teams that need to deploy on separate schedules, own separate domains end to end, and would otherwise be blocked on each other's release windows.

Not worth it
Code organization within one team

If the real goal is cleaner internal boundaries rather than independent deploys, that's a module-boundary problem. Plain imports and a well-organized monorepo solve it without any of the runtime cost above.

Composition Boundaries

A remote still chooses its own rendering strategy. It may use SSG, SSR, or client rendering regardless of whether the product composes at the route, element, application, or federated-module boundary. Composition determines ownership and integration. Rendering determines how one owned part produces its interface.

The word “island” can obscure that distinction. Astro islands divide client activation within one page, while a Client Component boundary controls which React modules enter the client graph. A federated remote is independently built, deployed, and owned. The boundaries can coexist, but they solve different problems.
