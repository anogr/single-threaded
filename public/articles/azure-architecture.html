Azure Architecture

Azure's resource model, core building blocks, and how its services map onto the equivalents in AWS and GCP.

Andreas Ögren
~17 min read
Last updated July 2026

Cloud Computing Fundamentals covers the categories every major cloud provider shares: compute, storage, networking, managed data, messaging, and identity, along with the service-model spectrum and the regional reliability model underneath all of them. That article closes its provider comparison with a promise to come back to Azure specifically. This is that companion piece.

Where the fundamentals article stays deliberately provider-agnostic, this one names names. It starts with Azure's resource model, the hierarchy of subscriptions and resource groups that has no clean equivalent anywhere else on this site. From there it works back through compute, storage, networking, managed data, messaging, and identity, this time as concrete Azure services rather than abstract categories. It covers Azure's regional reliability model and its infrastructure-as-code tooling, and closes with a direct lookup table mapping Azure's service names onto their closest AWS and GCP equivalents, for a reader arriving from either.

Azure's Resource Model

Every Azure resource lives inside a hierarchy with no real equivalent elsewhere on this site, and it comes first because almost everything later in this article gets organized by it.

Azure Resource Manager (ARM) is Azure's management layer, sitting underneath every way of interacting with the platform. Every resource gets created, updated, tagged, secured, and organized through ARM, whether the request comes from the Azure portal, the command-line interface, PowerShell, or a deployment tool like Bicep or Terraform. The rest of this section, and the deployment tooling covered later in this article, are really describing what gets managed through ARM and how.

A subscription is Azure's billing and access-control boundary, the container everything else in an Azure environment ultimately belongs to. A resource group is a grouping within a subscription for resources that are typically managed together as part of the same application or environment. That's not a hard guarantee that everything inside it shares one lifecycle, just the common case. A production web application's resource group might hold its App Service instance, its database, and its virtual network, created and usually torn down as one unit. A shared resource like a network referenced by several applications often lives in a resource group of its own instead, with a longer life than any one application using it.

Management groups sit above subscriptions. They let an organization apply a rule once, at the top of a hierarchy, and have it cascade down to every subscription and resource group underneath. Azure Policy is Azure's governance service for that first kind of rule, enforcing constraints like which resource types or regions are allowed. An RBAC role assignment does the same for permissions. AWS handles the same inheritance idea through organization-level service control policies applied above individual accounts, and GCP through folders sitting above projects. The mechanism differs, but the goal is the same across all three: govern many teams' worth of resources from a single point instead of configuring each one by hand.

Tags close out the resource model: key-value metadata attached to a resource, independent of where it sits in the subscription and resource group structure. A tag doesn't affect how a resource behaves. It's how a team answers a question like which department a resource's cost should be billed to, months after whoever created it has moved on.

Compute: VMs, App Service, Containers, and Functions

The same IaaS-to-serverless spectrum from the fundamentals article, in five concrete Azure products, ordered from the least abstracted to the most.

Azure Virtual Machines fill the IaaS end of the spectrum. There's nothing distinctive to add to the mapping here. It's the same virtual machine covered generically in the fundamentals article's compute section, an emulated computer with its own operating system that the customer configures and patches.

Azure App Service is Azure's flagship platform-as-a-service compute product, a concrete answer to the fundamentals article's abstract example of a managed application platform. Point it at application code or a container image, and it handles provisioning, scaling, and patching the host underneath, without the customer configuring a server directly.

Two managed-container options sit in the middle of the spectrum, narrower to broader. Azure Container Apps runs containers with built-in autoscaling, including scaling all the way down to zero instances when there's no traffic, without the customer managing a cluster directly. Azure Kubernetes Service (AKS) is Azure's managed Kubernetes offering, worth reaching for once a workload actually needs Kubernetes's full feature set rather than Container Apps's narrower one. What a container actually is, and how an orchestrator like Kubernetes schedules and scales one, is covered in full in Containers and Orchestration. This article only needs where AKS sits relative to Azure's other compute options.

Azure Functions closes out the spectrum at its serverless end, the same far end the fundamentals article described: no server management at all, in exchange for constraints like execution time limits and cold starts. One detail is distinctive enough to call out here. Bindings are declarative configuration that connect a function to a trigger or an output, such as a queue message, a blob upload, or an HTTP request, without hand-written code to wire the connection up. Azure Functions leans on bindings more than the other major providers lean on their own equivalents, though calling the underlying Azure SDK directly instead of using a binding is just as fully supported.

Storage: Blob, Disks, and Files

The same three access patterns from the fundamentals article, filled in with Azure's product names and one tiering detail specific to Azure.

Azure Blob Storage fills the object storage category, with one addition to the general tiering picture from the fundamentals article. Blob Storage splits pricing across four tiers rather than two: hot, cool, cold, and archive, each a step down in storage cost and a step up in retrieval latency from the one before it. The cold tier sits between cool and archive specifically for data accessed less often than hot but still needed faster than an archive retrieval allows.

Azure Data Lake Storage Gen2 is a variant of Blob Storage, not a separate product. It adds a hierarchical namespace and filesystem semantics on top of the same underlying object storage, the layer most Azure analytics workloads are actually built on, including the data-warehouse services covered in the next section.

Azure managed disks fill block storage, attached to a single virtual machine the same way the fundamentals article described generically. Azure Files fills file storage, a shared filesystem mountable over SMB or NFS from more than one machine at once.

Networking and Managed Data

The boundary Azure resources sit inside, how traffic reaches it, and the shapes managed data comes in once it's there.

Azure Virtual Network (VNet) fills the virtual-network category from the fundamentals article, divided into subnets the same way most providers divide theirs. A network security group (NSG) is the traffic-filtering mechanism attached to a subnet or a network interface, Azure's equivalent of a security group on another provider.

Traffic leaving a subnet can be steered by a handful of additional building blocks, listed here without detailing each one. A user-defined route overrides Azure's default routing to send traffic through a specific next hop instead. Azure Firewall is a managed network firewall for traffic leaving a VNet. A VPN Gateway or ExpressRoute connects a VNet back to on-premises infrastructure, over the public internet for a VPN Gateway or a private, dedicated circuit for ExpressRoute. Which of the two an organization reaches for usually comes down to how much bandwidth and latency guarantee the connection needs, not just whether a connection back to on-premises exists at all.

Azure Front Door and Application Gateway are Azure's edge and layer-seven load-balancing products. What each actually does once traffic arrives, a CDN, a web application firewall, a load balancer, is covered in full in Web Application Networking. This article only needs their Azure names. A private endpoint is one more piece of that model. It lets traffic reach a managed PaaS service like a database over the VNet instead of the public internet, relevant to the compliance and data-residency considerations the fundamentals article raised. Enough production Azure deployments turn off public access entirely and expose a managed service only through a private endpoint that this counts as the common case rather than the exception. Resolving that connection correctly usually depends on Azure DNS private zones, linked to the VNet the same way a public DNS zone backs an internet-facing service.

On the data side, Azure SQL Database fills the managed relational-database category. Azure SQL Managed Instance is a sibling product, offering near-full SQL Server engine compatibility for a lift-and-shift migration of an existing SQL Server workload. Azure SQL Database has a lighter, more PaaS-native footprint instead, better suited to something built for the cloud from the start. A team on an open-source engine has its own managed option too, Azure Database for PostgreSQL or MySQL, the portability angle the fundamentals article raised under lock-in.

Azure Cosmos DB fills managed NoSQL. One detail goes beyond the mapping. Multiple tunable consistency levels, and multi-region writes that stay active in more than one region at once, are both available as configuration choices, rather than something the customer has to build themselves.

Synapse and Fabric

Azure Synapse Analytics fills the managed data-warehouse category, Azure's established answer to the analytical, scan-heavy access pattern the fundamentals article distinguished from an operational database. It remains a supported, current product, not a deprecated one. But Microsoft now positions Microsoft Fabric as its primary platform for new, unified analytics work, describing it as the next generation built on what Synapse established. A reader evaluating analytics on Azure today should have both names in hand, not just the older one.

Messaging and Identity

Who talks to whom, who's allowed to do what, and where a credential actually lives.

Azure Service Bus fills the queue category from the fundamentals article: a queue for point-to-point delivery to exactly one consumer, or a topic within Service Bus for one-to-many delivery to multiple subscriptions at once. Azure Event Grid fills the broader publish/subscribe category, routing events from a source to any number of handlers for reactive, event-driven architectures. Azure Event Hubs gets a shorter mention. It's a high-throughput streaming-ingestion service for continuous event data, and its deeper mechanics belong to the event-driven architecture entry still to come in this site's backlog.

Azure Key Vault stores secrets, certificates, and encryption keys centrally, instead of scattered across application configuration files. Managed identities are what make that centralization actually secure in practice. A managed identity is assigned directly to a resource, such as a virtual machine, an App Service instance, or a function. It lets that resource authenticate to Key Vault and other Azure services with no credential embedded in its code or configuration at all. That's Azure's concrete implementation of the workload-identity pattern the fundamentals article named generically under least privilege.

Microsoft Entra ID, formerly Azure Active Directory, is Azure's identity and access-management system, worth one level more concrete than the fundamentals article's general definition. Entra ID is also an organization's directory service. That's the reason Azure integrates directly with an existing on-premises Active Directory, through a bridge called Entra Connect, or with an existing Microsoft 365 tenant. It's the specific mechanism behind the Microsoft-ecosystem integration strength the fundamentals article's provider comparison named without explaining how it actually works. Role-based access control (RBAC) is the permission model layered on top of the resource hierarchy from earlier in this article. Roles get assigned to an identity at the management group, subscription, or resource group level, inherited downward the same way policy is.

Regions, Availability Zones, and Paired Regions

The same physical reliability model from the fundamentals article, plus one reliability layer that's genuinely Azure's own.

Azure's regions and availability zones follow the same physical model the fundamentals article's figure already covers. A region is a geographic location with its own cluster of data centers, and an availability zone is an isolated failure domain within it. That figure doesn't need redrawing here. Azure adds one more layer on top of it.

Azure pairs each region with a specific partner region in the same geography, a relationship called a paired region. Azure sequences platform updates across a pair rather than rolling them out to both halves simultaneously, so an update-related issue in one region's rollout doesn't hit its pair at the same time. Some services also replicate data to the paired region automatically, for disaster recovery beyond what a single region's availability zones already provide.

Paired regions sit on top of availability zones, not in place of them. A workload still spreads across zones within a region for its baseline resilience. Pairing is the additional layer for the scenario where an entire region, not just one zone inside it, becomes unavailable.

Infrastructure as Code: ARM Templates, Bicep, and Terraform

Three ways to describe an Azure deployment declaratively, instead of clicking through the portal by hand.

This article's resource-model section already introduced Azure Resource Manager as the layer every deployment method ultimately goes through, so this section only needs to cover the formats used to describe a deployment to it. ARM templates are Azure's native declarative format: JSON documents describing the resources in a deployment, submitted to Resource Manager the same way a manual portal action ultimately is.

Bicep is a newer domain-specific language that compiles down to ARM JSON before it's submitted. It reads far more cleanly than a hand-written ARM template, and it doesn't require a separate state file the way Terraform does, since Resource Manager itself already tracks what a deployment created. A minimal Bicep resource declaration is compact enough to read at a glance:

main.bicep Bicep 
resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'mystorageaccount'
  location: resourceGroup().location
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}

Terraform, already introduced generically in CI/CD and DevOps, gets a shorter mention here for the same reason: it works across Azure, AWS, and GCP with the same tool and the same syntax. That's why a team already standardized on Terraform for a multi-cloud footprint might reach for it over Bicep even on a project that only touches Azure. The choice comes down to what a team is already organized around. Bicep suits a team fully committed to Azure that wants the platform-native tool. Terraform suits a team that values one tool across providers, or already has Terraform expertise in house.

Mapping Azure to AWS and GCP

The lookup table a reader arriving from another provider actually wants.

Every section above named an Azure service without dwelling on what the equivalent looks like on another provider. This table closes that gap in one place, plus one category not named earlier: observability. Azure Monitor is Azure's umbrella product for logs, metrics, and traces, the same three pillars a future observability article on this site will cover in full. It's included here for orientation, not explained in a dedicated section of its own. Row labels use the generic category rather than the Azure product name, "managed Kubernetes" as the row instead of "AKS." That keeps the table a comparison of equivalent categories, rather than implying the row is itself an Azure concept the other two columns are measured against.

Two of Azure Monitor's own sub-components matter here. Log Analytics is specifically its log-query component, and Application Insights is specifically its application-performance-monitoring component. Both, like Azure Monitor itself, are named here for orientation only, ahead of the fuller treatment the observability article in this site's backlog will eventually give them, CloudWatch and Cloud Monitoring included.

Treat this table as a starting orientation, not a claim that each row is functionally identical across providers. Consistency models, pricing structure, and operational limits differ underneath a matching label even when the row implies a clean swap. The queue and publish/subscribe rows are a clear example. GCP's Pub/Sub genuinely fills both roles with the same product. A subscription behaves like a queue when only one consumer reads it, and like a broadcast when several do, while Azure and AWS keep the two patterns in separate services. The infrastructure-as-code row is another. Infrastructure Manager isn't GCP's own competing template language the way Bicep and CloudFormation are to each other. It's a managed way to run the same multi-cloud Terraform covered earlier in this article, GCP leaning on that shared tool rather than maintaining a proprietary one of its own. The table's job is to get a reader oriented quickly, not to substitute for reading a service's own documentation before building on it.

When Azure Is the Right Fit

Earned from what this article actually covered, not a generic strengths list.

The fundamentals article's provider comparison named Azure's strength as Microsoft-ecosystem integration and enterprise AI adoption. Everything covered since then makes that claim more concrete. The resource hierarchy from earlier in this article scales governance cleanly for a large enterprise running many teams across many subscriptions. Entra ID simplifies hybrid identity specifically for an organization with an existing on-premises Active Directory or Microsoft 365 tenant, not just organizations in the abstract. App Service and Azure Functions reduce operational overhead for a team that doesn't want to run its own cluster, while AKS and Terraform support a team already organized around cloud-native, multi-provider tooling instead. Existing Microsoft licensing, or an existing .NET or Windows Server investment, reduces migration friction in a way that's easier to point to now than the fundamentals article's general phrase for it.

Azure's AI services fit the same pattern rather than sitting apart from it. Microsoft Foundry, renamed from Azure AI Foundry in late 2025, is Microsoft's unified AI platform. It builds on the same resource model, identity system, and networking covered throughout this article, instead of forming a separate platform bolted on alongside everything else.

One caution, stated plainly: existing Microsoft licensing is a reason to evaluate Azure seriously. It isn't a substitute for checking whether Azure's specific managed services actually fit the workload, the same caution the fundamentals article's own closing section raised about cloud providers generally. The provider-agnostic factors that article closed on, existing skills, and which managed services actually matter for the workload at hand, still apply on top of everything Azure-specific covered here.
