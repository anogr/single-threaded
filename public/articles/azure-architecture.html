Azure Architecture

How Azure organizes resources, which services fill each cloud role, and how they compare with AWS and Google Cloud.

Andreas Ögren
~12 min read
Last updated July 2026

Cloud Computing introduces the service models and building blocks shared by the major providers. This companion article applies those concepts to Azure. It uses Azure product names where the broader article uses categories such as compute, storage, networking, data, messaging, and identity.

Azure's resource hierarchy comes first because it supplies the scope for deployment, policy, access, and cost management. The sections that follow place concrete services inside that model, then cover regional resilience and infrastructure as code. A final mapping gives readers from AWS or Google Cloud a practical orientation without implying that similarly named products behave identically.

Azure's Resource Model

Management groups, subscriptions, resource groups, and resources form the scopes through which Azure is governed.

Azure Resource Manager (ARM) is the control plane used to create, update, organize, and secure Azure resources. Portal actions, command-line tools, PowerShell, Bicep, and Terraform all submit management requests through this layer. ARM also supplies the scope hierarchy on which Azure role-based access control and policy operate.

A subscription contains resources and provides a major scope for access and cost management. Its charges can roll up into a separate billing-account hierarchy, so a subscription is not always the top billing boundary. Within a subscription, a resource group collects resources that an organization wants to manage together. Application resources may share a group and lifecycle, while long-lived networks or other shared services often belong in groups of their own.

Management groups organize subscriptions into an inheritance hierarchy. Azure Policy assignments at a management-group scope can audit or restrict resources below it, while Azure role-based access control assignments grant permissions across the same descendants. AWS organizations and Google Cloud folders provide comparable governance scopes, although their account and project models differ from Azure subscriptions.

A tag adds key-value metadata to a resource for purposes such as ownership, environment, and cost allocation. Tags do not replace the hierarchy or change a resource's behavior. They provide a second way to group and report on resources that sit in different scopes.

Compute: VMs, App Service, Containers, and Functions

The same IaaS-to-serverless spectrum from the fundamentals article, in five concrete Azure products, ordered from the least abstracted to the most.

Azure Virtual Machines occupy the IaaS end of the compute spectrum. Azure operates the physical host and virtualization layer, while the customer configures and patches the guest operating system.

Azure App Service is a managed platform for web applications and APIs. It can deploy supported application runtimes or container images without exposing host management to the customer. Scaling still depends on the selected plan and configuration rather than happening automatically in every deployment.

Two managed-container options occupy the middle of the spectrum. Azure Container Apps runs containers behind a managed control plane and can scale many workloads to zero. Azure Kubernetes Service (AKS) exposes the Kubernetes API and its broader orchestration model while Azure manages the cluster control plane. The choice depends on whether the workload needs Kubernetes-specific control or can use the narrower Container Apps model. Containers and Orchestration explains the underlying mechanisms.

Azure Functions runs event-triggered code without guest operating-system management. Execution limits, scaling behavior, and cold-start characteristics depend on the hosting plan. Bindings declaratively connect a function to inputs and outputs such as HTTP requests, queues, and blobs. Code can use an Azure SDK directly when a binding does not expose the required behavior.

Storage: Blob, Disks, and Files

The same three access patterns from the fundamentals article, filled in with Azure's product names and one tiering detail specific to Azure.

Azure Blob Storage provides object storage. Its hot, cool, and cold access tiers remain online, with lower storage charges and higher access charges as data becomes less active. Archive is an offline tier that requires rehydration before a blob can be read. Minimum retention periods, availability, supported redundancy options, and retrieval costs also differ, so tier choice involves more than latency alone.

Azure Data Lake Storage Gen2 refers to Blob Storage accounts with a hierarchical namespace enabled. The namespace adds directory operations and access-control behavior suited to analytical workloads while retaining Blob Storage's object-storage foundation.

Azure managed disks fill block storage, attached to a single virtual machine the same way the fundamentals article described generically. Azure Files fills file storage, a shared filesystem mountable over SMB or NFS from more than one machine at once.

Networking and Managed Data

The boundary Azure resources sit inside, how traffic reaches it, and the shapes managed data comes in once it's there.

Azure Virtual Network (VNet) fills the virtual-network category from the fundamentals article, divided into subnets the same way most providers divide theirs. A network security group (NSG) is the traffic-filtering mechanism attached to a subnet or a network interface, Azure's equivalent of a security group on another provider.

Several services control traffic beyond a subnet. A user-defined route can direct traffic through a chosen next hop, while Azure Firewall filters traffic centrally. VPN Gateway connects networks through encrypted tunnels over the public internet. ExpressRoute uses a private connection supplied through a connectivity provider. Bandwidth, latency consistency, redundancy, cost, and security requirements all affect the choice between them.

Azure Front Door is a global edge-routing and content-delivery service that can add a web application firewall. Application Gateway is a regional layer-seven load balancer, also available with a web application firewall, but it is not a CDN. Web Application Networking covers those mechanisms in depth. A private endpoint assigns a private VNet address to a supported managed service through Azure Private Link. The service's public endpoint may need to be disabled separately, and private DNS must resolve its name to the private address for connected clients.

Azure SQL Database is a managed relational database based on SQL Server. Azure SQL Managed Instance exposes broader SQL Server compatibility and instance-level features, which can reduce changes during some migrations. Azure also provides managed PostgreSQL and MySQL services. Engine compatibility can improve application portability, although extensions, operating features, and service limits still differ.

Azure Cosmos DB is a distributed database service with several APIs and configurable consistency levels. It can replicate across regions and support writes in more than one region when configured for that mode. Those choices affect latency, availability, conflict handling, and cost, so multi-region capability does not remove application-level design decisions.

Synapse and Fabric

Azure Synapse Analytics combines data integration, SQL analytics, and Spark workloads. Microsoft Fabric is a separate software-as-a-service analytics platform that unifies several Microsoft data experiences around OneLake. Both products remain relevant, and their overlapping capabilities do not make them interchangeable. A selection should follow the workload, existing investments, and Microsoft's current product guidance.

Messaging and Identity

Who talks to whom, who's allowed to do what, and where a credential actually lives.

Azure Service Bus provides queues and topics for brokered messaging. Competing consumers receive messages from a queue, while topic subscriptions create separate delivery streams. Delivery can be repeated, so handlers should follow the service's settlement and idempotency model. Azure Event Grid routes discrete events to handlers, whereas Azure Event Hubs ingests high-volume event streams for consumers that track their own position.

Azure Key Vault stores secrets, certificates, and cryptographic keys. A managed identity gives an Azure resource an identity in Entra ID without placing a long-lived credential in application configuration. Azure can then issue tokens for Key Vault and other supported services. Authorization remains a separate step because the identity must still receive an appropriate role or access policy.

Microsoft Entra ID, formerly Azure Active Directory, is Microsoft's cloud identity and directory service. Microsoft 365 uses Entra ID, and organizations can synchronize or federate identities from on-premises Active Directory through Microsoft Entra Connect. Azure role-based access control (RBAC) grants Azure management and data-plane permissions to those identities. Assignments can begin at a management group, subscription, resource group, or individual resource and normally apply to descendants.

Regions, Availability Zones, and Paired Regions

Azure uses zones within regions and, for some services, predefined relationships between regions.

Azure's regions and availability zones follow the same physical model the fundamentals article's figure already covers. A region is a geographic location with its own cluster of data centers, and an availability zone is an isolated failure domain within it. That figure doesn't need redrawing here. Azure adds one more layer on top of it.

Some Azure regions have a designated partner in the same geography, forming a paired region. A small number of services use that relationship for geo-replication or disaster-recovery features. The relationship does not automatically replicate every resource, provide failover, or make a workload resilient.

Many regions are not paired and use availability zones as their primary local redundancy mechanism. Azure services can often replicate between regions that are not a predefined pair. A resilient design therefore starts with service capabilities and recovery requirements rather than assuming that a region pair supplies protection by default.

Availability zones and multiple regions address different failure scopes. A zone-redundant deployment can survive some failures within a region. A multi-region design can address regional loss, whether the selected regions form an Azure pair or not.

Infrastructure as Code: ARM Templates, Bicep, and Terraform

Three ways to describe an Azure deployment declaratively, instead of clicking through the portal by hand.

This article's resource-model section already introduced Azure Resource Manager as the layer every deployment method ultimately goes through, so this section only needs to cover the formats used to describe a deployment to it. ARM templates are Azure's native declarative format. They are JSON documents describing the resources in a deployment, submitted to Resource Manager the same way a manual portal action ultimately is.

Bicep is Azure's domain-specific language for Resource Manager deployments. The tooling translates Bicep into ARM template JSON before deployment. Bicep relies on Azure's control plane instead of maintaining a separate client-side state file, which distinguishes its operating model from Terraform. The following minimal declaration creates a storage account.

main.bicep Bicep 
resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'mystorageaccount'
  location: resourceGroup().location
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}

Terraform, introduced in CI/CD and DevOps, uses one workflow and configuration language across provider-specific plugins. Resource types and behavior still differ between Azure, AWS, and Google Cloud. Bicep offers the closest integration with Azure Resource Manager, while Terraform may fit an organization that already uses its workflow and state management across platforms.

Matching rows can still differ in consistency, delivery guarantees, pricing, and operational limits. Google Cloud Infrastructure Manager is another imperfect match because it deploys Terraform rather than defining a proprietary template language. When Azure Is the Right Fit

Earned from what this article covered, not a generic strengths list.

Azure deserves close consideration when an organization already depends on Microsoft identity, administration, or application platforms. Management groups and subscriptions provide governance scopes for many teams. Entra ID connects Azure access with Microsoft 365 and hybrid identity, while App Service and Functions offer managed compute for teams that do not need Kubernetes. AKS remains available when the workload and operating model justify that control.

Azure's AI services use the same governance foundations. Microsoft Foundry provides model access and tools for building and operating AI applications within Azure's resource, identity, and networking model. The precise data handling and network options depend on the models and services selected.

Existing Microsoft investments can lower integration and migration costs, but they do not settle the provider decision. The workload still needs a service-by-service fit, an operating model the team can sustain, and acceptable commercial terms. The provider-selection guidance remains the final test.
