Web Application Security

How web applications fail, and a framework for thinking about threats before they become incidents.

Andreas Ögren
~17 min read
Last updated July 2026

Security is adversarial thinking. Software that merely works is not enough, because it also has to keep working when someone is actively trying to make it fail.

Software is usually designed around what legitimate users are trying to accomplish. Attackers approach the same system differently. They alter parameters, replay requests, probe inputs, and test whether the server enforces the restrictions shown in the interface. Secure design accounts for both ways of using the application from the start.

Late security review can find defects, but it cannot cheaply repair every unsafe design decision. A login flow designed without abuse limits or recovery controls may need architectural changes rather than a patch. Security work therefore begins while authority, data flows, and failure behavior are still being designed.

The OWASP Top 10:2025 provides the structure for the failure modes below. It is an awareness document built from contributed data and community review, not a complete application-security standard. Its categories give teams a shared vocabulary, while the later principles and threat-modeling section show how to reason beyond a checklist. The articles on browser security and authentication own the detailed mechanisms in those areas.

The Web's Trust Model

The browser enforces boundaries. Understanding which boundaries, and why they exist, is the starting point for web security.

The browser and server enforce different trust boundaries. The same-origin policy restricts how one origin reads another origin's data. HTTPS authenticates the TLS endpoint and protects traffic in transit. Neither control decides whether an authenticated user may read a particular record. The HTTPS article covers transport, while the HTTP article owns the same-origin and CORS mechanisms.

Beyond transport, every request raises two separate questions. Authentication establishes which identity is making the request. Authorization decides whether that identity may perform the requested operation. An application can answer the first question correctly and still expose another user's records because it never asked the second.

Broken Access Control

Broken access control lets a caller read resources or perform actions beyond the authority their identity was granted.

An insecure direct object reference (IDOR) occurs when an application accepts a resource identifier without checking it against the caller's permissions. For example, GET /invoices/10042 may return an invoice to any authenticated user who can guess or obtain its identifier. The login is valid, but the record-level authorization is missing.

Hidden UI is not access control

If a button is hidden from unprivileged users but the underlying API endpoint accepts requests from anyone, the restriction exists only in the interface, not in the system. Removing a UI element does not prevent a direct API call. Authorization must be enforced on the server, for every request, regardless of what the client presents.

The same failure appears in other forms. A caller may change a role parameter, substitute another account ID, or send a write request to an endpoint exposed through a read-only interface. Each operation needs a server-side authorization check. A check during page load or a restriction in the UI cannot protect the API behind it.

A related case is when the application itself, not a logged-in user, becomes the actor whose access needs restricting. That's what happens with server-side request forgery, covered next.

Server-Side Request Forgery Part of Broken Access Control

Many legitimate features fetch a URL on a user's behalf. Link previews, remote profile images, and webhook checks all follow this pattern. The server can usually reach internal services that are inaccessible from the user's browser. Server-side request forgery (SSRF) abuses that reach by supplying a destination the feature was never meant to contact, such as an internal administration service or a cloud metadata endpoint.

The 2019 Capital One breach showed how SSRF can reach a cloud metadata service, obtain temporary credentials, and turn a URL-fetching flaw into access to stored customer data. Effective prevention needs controls at both the application and infrastructure layers:

  • Validate destination URLs against an allowlist of expected hosts rather than a blocklist.
  • Reject requests to private IP ranges and link-local addresses, including the cloud metadata range, unless a feature specifically needs them.
  • Don't follow redirects blindly, since a validated URL can redirect to an internal address after the check has already passed.
  • Harden the metadata service itself. On AWS, require IMDSv2 and configure its response hop limit for the workload. Its token exchange blocks many common open-proxy and SSRF primitives, but it remains defense in depth rather than permission to accept arbitrary destinations.

The web application networking article covers network segmentation as a second line of defense.

Security Misconfiguration

Correct software deployed incorrectly. The code itself has no flaw, but the environment around it is configured dangerously.

Security behavior is spread across framework settings, cloud policies, reverse proxies, feature flags, and deployment manifests. A safe application can still be exposed by one inconsistent environment. Common examples include:

  • Default credentials left unchanged on databases, admin panels, or network equipment.
  • Verbose error messages that expose stack traces, database schemas, or internal paths to users.
  • Unnecessary features or endpoints enabled in production that wouldn't be enabled in a consciously designed deployment.
  • Cloud storage buckets left publicly accessible.
  • Debug modes active in production environments.

Infrastructure as code and automated configuration management make environments reproducible and changes reviewable. A corrected definition can be applied consistently instead of relying on an operator to repeat the same manual fix. That discipline matters because security behavior increasingly depends on feature flags, environment variables, identity policies, and tenant-specific settings.

Error messages are a dual audience problem

Detailed error messages are valuable for debugging. They are also valuable to attackers, who use stack traces, table names, and file paths to understand a system's internals. The solution is to log details internally while showing generic messages to users. The two audiences need different information. The exceptional conditions section below covers the broader problem of error handling that this is one symptom of.

Software Supply Chain Failures

Modern applications depend on libraries, build tools, delivery pipelines, and deployment infrastructure. A compromise in that chain can reach every downstream application that trusts its output.

The narrowest version is a vulnerable dependency. Applications depend on both packages they selected and transitive packages selected by those dependencies. A disclosed flaw matters only when the affected component and vulnerable behavior reach the application, but teams first need an inventory before they can make that assessment. Log4Shell showed how difficult that discovery becomes when a library is embedded several layers down.

A supply-chain attack changes a trusted input rather than waiting for an accidental flaw. The SolarWinds compromise inserted malicious code into a vendor's build and update path. The 2025 Shai-Hulud npm campaign published malicious package versions that harvested credentials and used available npm tokens to publish further infected versions. Both attacks reached downstream users through ordinary trust in build or distribution systems.

Defenders need an inventory of what reached each build, including transitive dependencies absent from the top-level manifest. A software bill of materials (SBOM) records those components. Software composition analysis can compare the inventory with advisories, after which the team still has to assess reachability and exposure.

The build pipeline needs protection of its own. Require review for sensitive changes, keep CI/CD credentials narrowly scoped, and sign artifacts so downstream systems can verify their origin and integrity. Separation of duties can also prevent one compromised account from changing source and promoting the resulting artifact without another control intervening.

The same threat has a narrower, browser-specific form: a third-party script loaded at runtime from a CDN, where a compromise of that CDN runs attacker code directly in the user's page. The supply chain attacks section of the browser security article covers that case and Subresource Integrity, the browser-level defense against it.

Cryptographic Failures

Sensitive data that should be protected isn't. Often it's transmitted without encryption, stored incorrectly, or "protected" with algorithms that are no longer adequate.

Password storage is a familiar example of cryptographic failure. Plain-text storage turns a database breach into immediate credential disclosure. New systems should use a salted, adaptive password-hashing function such as Argon2id, with scrypt as an alternative where Argon2id is unavailable. OWASP treats bcrypt as a legacy choice. Fast general-purpose hashes such as MD5 and SHA-256 do not slow offline guessing enough for password storage.

The category is broader than passwords. It covers transmitting sensitive data over plain HTTP, storing credit card numbers or health data unencrypted at rest, and relying on outdated algorithms. The same category also covers encrypting data that should have been hashed, since encryption is reversible and password verification needs a transformation that isn't. The principle is to classify data by sensitivity and apply protection proportional to the risk of exposure.

Injection

Injection vulnerabilities happen when an application treats untrusted data as instructions. They have existed since the earliest web applications and remain among the most reliably damaging.

SQL injection is the canonical example. When user input is concatenated into a SQL query, an attacker can escape the intended value and alter the query structure.

find-user.ts TS — vulnerable 
// email can close the quoted value and add SQL syntax
const sql = `SELECT id, display_name FROM users
  WHERE email = '${email}'`
const result = await db.query(sql)

The fix is parameterized queries, which send the SQL structure separately from bound data values. The database driver handles each parameter as data for that statement rather than splicing it into SQL text.

find-user.ts TS — safe 
const sql = `SELECT id, display_name FROM users
  WHERE email = $1`
const result = await db.query(
  sql,
  [email],
)

The same principle, data becoming instructions, applies elsewhere. Command injection passes user input to a shell, and template injection evaluates it inside a template engine. Cross-site scripting renders untrusted input as HTML and executes it as JavaScript, which the browser security article covers.

Frameworks, object-relational mappers, and query builders make parameterized queries easier to use, but they do not eliminate injection. Risk returns whenever code constructs commands from strings, bypasses a safe abstraction, or sends untrusted data into another interpreter.

Insecure Design

Some vulnerabilities aren't bugs in the code. They're the predictable result of a design that never accounted for an adversary in the first place.

Insecure design describes missing or ineffective controls in the system's intended behavior. Correct implementation cannot supply a requirement that was never designed. A discount-code flow with no abuse limit and a public upload area with no content boundary can both work exactly as specified while remaining unsafe.

Design review should ask what authority a feature grants, how it can be automated, and which limits still hold when requests arrive in an unexpected order. The threat-modeling section turns those questions into a repeatable process.

Secure by design, not secure by review

A security review at the end of a project can catch implementation bugs, but it rarely fixes a flawed design without a rebuild. Secure by design means the default behavior of a system is the safe one: access denied unless granted, output encoded unless explicitly trusted, limits applied unless explicitly raised. Retrofitting that mindset after launch is far more expensive than starting with it.

Authentication Failures

Weak authentication mechanisms give attackers a foothold that strong application logic can't compensate for.

Credential stuffing tests username and password pairs from earlier breaches against another service. Password reuse makes the attack effective because credentials exposed by a forum may also unlock the user's email or workplace account. The requests can resemble ordinary login attempts. Rate limits, breached-password checks, anomaly detection, and stronger authentication address different parts of the attack.

Other common authentication failures:

  • No rate limiting on login attempts, which enables brute force.
  • Sessions that never expire.
  • Session tokens that are predictable or too short.
  • Not invalidating sessions on logout.
  • No way to revoke other sessions after credential reset or suspected compromise.

Multi-factor authentication (MFA) prevents a stolen password from being sufficient on its own. The protection depends on the second factor: one-time codes and push approvals can still be phished or socially engineered, while WebAuthn credentials resist phishing by binding authentication to the site's origin. Administrative and other high-impact accounts should require a phishing-resistant option where possible. The authentication article covers the underlying factors, sessions, and tokens.

Software or Data Integrity Failures

Data can carry reconstruction instructions as well as values. A parser that accepts both must not receive attacker-controlled input.

Insecure deserialization is the clearest example. Serialization converts an in-memory object into a format that can be stored or transmitted. Deserialization reconstructs it later.

Some native object formats can describe executable reconstruction behavior as well as data. Examples include Java serialization, Python's pickle, and PHP's unserialize. An attacker who can influence such a payload may trigger code while the application reconstructs the object.

The dangerous boundary may be a cookie, cache entry, file, or message from another service. A format does not become trustworthy because it arrived from another internal component.

Avoid native object serialization across an untrusted boundary. A data-only format such as JSON cannot directly encode executable object reconstruction, but its parsed structure still needs schema validation and safe handling. If a native serialization format is unavoidable inside a trusted boundary, authenticate its origin and integrity and keep user-controlled data out of that channel.

Security Logging and Alerting Failures

An attack that isn't logged never happened, as far as the system is concerned. An attack that's logged but never triggers an alert is barely better.

Preventive controls will sometimes fail, so the application also needs evidence of what happened. Record security-relevant events such as login attempts, permission changes, and high-value transactions with enough context to investigate them. Failures matter as much as successes because a pattern of denied requests may reveal an attack before one succeeds.

Logs become a detection control only when someone or something evaluates them. Alert on events that require action, such as repeated authorization failures, unexpected privilege changes, or a burst of recovery attempts. Thresholds need tuning so ordinary traffic does not bury the signals the team is expected to investigate.

Logs are also an attack surface

Logging passwords, tokens, or full payment-card numbers creates another copy of the data an attacker wants. Log content can also become an injection point. Log4Shell demonstrated the risk because vulnerable Log4j configurations could evaluate attacker-controlled lookup expressions in logged strings. Treat log fields as untrusted data, and separate useful diagnostic context from secrets that should never be persisted.

Mishandling of Exceptional Conditions

Software fails constantly in small ways, such as a null value where one wasn't expected, a network call that times out, or a downstream service that returns an error. What the system does in that moment is often where the real vulnerability lives.

An exceptional condition appears when a code assumption stops holding. A required field may be missing, a payment provider may time out, or the permissions service may be unreachable. None of these conditions is an attack by itself.

The vulnerability lies in the application's response. It might expose a stack trace, grant access after a failed permission check, or leave a multi-step transaction half-applied.

Consider a transfer with separate debit, credit, and ledger steps. A failure between steps can leave contradictory state or make a retry apply part of the operation twice. A single transactional boundary can roll back local database work. Distributed workflows instead need idempotency keys, explicit state transitions, compensating actions, and reconciliation. The secure rule is to preserve invariants and deny success until the system can prove the operation reached an accepted state.

The category also covers verbose error output, touched on under security misconfiguration. Handle expected failures near the operation that understands them, release resources, and map internal detail to a safe external response. A global handler remains the final boundary for unexpected exceptions, where it can record context without exposing a framework error page.

Security Principles

The failure modes above share common themes. The principles below are responses to those themes. They don't prevent every attack, but they limit damage and reduce the attack surface.

Principle
Defense in Depth

Don't rely on a single control. Server-side validation establishes the input contract, parameterized queries keep values out of SQL syntax, and restricted database permissions limit the damage if application code still fails. The layers address different failure points.

Principle
Least Privilege

Every component (a user account, a service, a database connection, an API key, a CI/CD credential) gets exactly the permissions it needs and no more. A background job that reads orders doesn't need write access to the user table. Least privilege limits the blast radius of any individual failure.

Principle
Fail Securely

When something goes wrong, the default should be to deny access, not grant it. An error in an authentication check should result in access denied, not access granted. Generic error messages to users, detailed logs for operators. If a security check or a multi-step operation cannot complete, assume the worst and roll it back rather than leaving it half-done.

Principle
Treat External Data as Untrusted

Validate data from users, third-party APIs, files, queues, and configuration at the boundary where it enters a trust domain. Sanitization is appropriate only when the application intentionally accepts a restricted language such as HTML. Output encoding still depends on the destination context.

Principle
Reduce Attack Surface

Every feature, endpoint, dependency, and open port is a potential entry point. Disable what isn't needed. Remove unused dependencies. Don't expose internal services to the public internet. The smallest possible attack surface is the easiest to defend.

Principle
Keep It Simple

Complexity is the enemy of security. The more complex a system, the harder it is to reason about its security properties and the more places there are for subtle errors. Prefer simple, well-understood patterns over clever custom solutions, especially for authentication and cryptography.

Threat Modeling

The most valuable security habit is asking "how could this go wrong?" before shipping a feature, not after an incident.

Threat modeling is a structured way to examine a design from an attacker's perspective before implementation fixes become expensive. Start by identifying the assets and trust boundaries, then trace how data and authority move through the system. For each path, ask what an attacker could read, alter, impersonate, or disrupt, and decide which controls will reduce that risk.

STRIDE is one vocabulary for categorizing threats. It does not estimate likelihood or business impact, so the team still has to prioritize findings against the assets and controls in the actual system.
