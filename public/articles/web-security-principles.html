Web Security: Principles and Pitfalls

How web applications fail, the principles that prevent it, and a framework for thinking about threats before they become incidents.

Deep dive
~18 min read
Security fundamentals
July 2026

Security is adversarial thinking. Software that merely works is not enough. It has to keep working even when someone is actively trying to make it fail.

Most software is designed with legitimate users in mind. Security failures happen because real systems are also interacted with by people who probe inputs for weaknesses, replay requests, modify parameters, and look for gaps between what the interface allows and what the server actually enforces. Building secure software means holding both models in mind simultaneously: the normal path and the adversarial one.

Security is also not a feature that can be added after the fact. A login system built without thinking about brute force, session fixation, or credential stuffing will require significant rework to harden. The most effective place to apply security thinking is during design, before the code is written.

This article covers the conceptual foundation: how web applications commonly fail, the principles that reduce that risk, and a habit of thinking about threats proactively. The section below on how applications fail is structured around the OWASP Top 10, the industry's reference list of the most critical web application security risks, current as of its 2025 revision. OWASP revises the list periodically as attack patterns shift, and it's the vocabulary most security discussions, audits, and tooling use, so the categories are worth knowing even without reading the source document. The articles on browser security and authentication fundamentals build on this foundation with specific mechanisms and defenses.

The Web's Trust Model

The browser enforces boundaries. Understanding which boundaries, and why they exist, is the starting point for web security.

Browsers are the primary security boundary for web applications. The same-origin policy prevents JavaScript on one origin from reading responses from another, which stops a malicious page from silently reading a user's email or bank balance through their existing session. HTTPS ensures the connection between browser and server cannot be read or modified in transit. These are the foundations; without them, every other security measure is built on sand. The HTTPS article covers the transport layer in depth, and the HTTP article covers the same-origin policy and CORS.

Beyond transport, every web application must answer two questions for every request. Authentication asks: who is this? It establishes identity by verifying that a request comes from who it claims to be from. Authorization asks: what are they allowed to do? It enforces permissions by deciding whether the authenticated identity has the right to perform the requested operation. The two are distinct operations. Failing at authentication lets strangers in. Failing at authorization lets legitimate users do things they shouldn't. Conflating the two (treating authentication as sufficient proof of authorization) is one of the most common sources of access control vulnerabilities.

How Web Applications Fail: Broken Access Control

An authenticated user accesses resources or performs actions they should not be permitted to. This is the most frequently occurring vulnerability class in modern web applications, present in some form in nearly every application tested.

The most common form is insecure direct object reference (IDOR): a resource identifier in a URL or request body that is not validated against the requesting user's permissions. A request like GET /invoices/10042 might return the invoice regardless of whether the requesting user owns it. The application authenticates the user but doesn't check whether they're authorized to see that specific record.

Hidden UI is not access control

If a button is hidden from unprivileged users but the underlying API endpoint accepts requests from anyone, the restriction exists only in the interface, not in the system. Removing a UI element does not prevent a direct API call. Authorization must be enforced on the server, for every request, regardless of what the client presents.

Other common forms include: users escalating their own privileges by modifying a role or admin parameter in a request, accessing another user's account by changing an ID, and performing write operations through an endpoint that only intended to support reads. The fix is consistent server-side authorization checks on every operation, not just on initial page load, and not only in the UI layer.

A related case is when the application itself, not a logged-in user, becomes the actor whose access needs restricting. That's what happens with server-side request forgery, covered next.

Server-Side Request Forgery Part of Broken Access Control

A server that fetches a URL on the user's behalf can be tricked into fetching a URL the user was never supposed to reach. Plenty of legitimate features work this way: fetching a profile picture from a link, previewing a shared URL, checking that a webhook endpoint exists. The server is trusted to reach places the user's own browser can't, most importantly the private network it runs inside. Server-side request forgery (SSRF) happens when an attacker supplies a URL pointing somewhere unintended instead, such as an internal admin panel or a cloud provider's metadata endpoint, which typically hands out temporary credentials to anything that asks from inside the network.

In the 2019 breach at Capital One, an SSRF vulnerability let an attacker query AWS's metadata service, retrieve temporary IAM credentials, and pull over 100 million customer records, all without the vulnerable feature ever touching a database directly. The fix:

  • Validate destination URLs against an allowlist of expected hosts rather than a blocklist.
  • Reject requests to private IP ranges and link-local addresses, including the cloud metadata range, unless a feature specifically needs them.
  • Don't follow redirects blindly, since a validated URL can redirect to an internal address after the check has already passed.

The web application networking article covers network segmentation as a second line of defense.

How Web Applications Fail: Security Misconfiguration

Correct software deployed incorrectly. The code has no flaw. The environment around it is configured dangerously.

Security misconfiguration is pervasive because the default configuration of many systems prioritizes convenience over security. Common examples:

  • Default credentials left unchanged on databases, admin panels, or network equipment.
  • Verbose error messages that expose stack traces, database schemas, or internal paths to users.
  • Unnecessary features or endpoints enabled in production that wouldn't be enabled in a consciously designed deployment.
  • Cloud storage buckets left publicly accessible.
  • Debug modes active in production environments.

Infrastructure-as-code and automated configuration management reduce this risk: if every environment is provisioned from the same checked-in definition, a misconfiguration gets fixed once and propagates everywhere. Manual configuration across environments is the most reliable path to "this works on staging but is dangerous in production." As applications lean more and more on configuration to control behavior (feature flags, environment variables, per-tenant settings) this category has only grown, and it now ranks among the most common failure modes found in testing.

Error messages are a dual audience problem

Detailed error messages are valuable for debugging. They are also valuable to attackers, who use stack traces, table names, and file paths to understand a system's internals. The solution is to log details internally while showing generic messages to users. The two audiences need different information. The exceptional conditions section below covers the broader problem of error handling that this is one symptom of.

How Web Applications Fail: Software Supply Chain Failures

Modern applications don't just depend on their own code. They depend on everything upstream of it: libraries, build tools, CI/CD pipelines, and the infrastructure that turns source into a running deployment. A compromise anywhere in that chain reaches every application downstream of it.

The narrowest version of this problem is a known vulnerability sitting in a dependency. A typical frontend application has hundreds of transitive dependencies: packages that are dependencies of dependencies, often several layers deep. The same is true on the backend. Most developers can name their direct dependencies, but very few know the full transitive tree. When a vulnerability is discovered in a widely-used library, it affects every application that includes it, directly or indirectly, whether or not the application uses the vulnerable feature. The Log4Shell vulnerability in late 2021 illustrated the scale of this risk: a critical remote code execution flaw in Log4j, a Java logging library so ubiquitous that hundreds of thousands of applications were affected, many without their teams realizing they depended on it at all.

The broader and more consequential concern is the supply chain itself being tampered with, rather than merely containing an old vulnerability. In the 2019/2020 SolarWinds breach, attackers compromised the build system of a network monitoring vendor and inserted malicious code into a routine software update, which was then installed by roughly 18,000 organizations, several of them government agencies. Nobody downloaded anything unusual. The trusted update mechanism was the attack. More recently, a self-propagating worm nicknamed Shai-Hulud spread through the npm registry by publishing malicious versions of popular packages that harvested credentials from developer machines and used them to automatically publish more infected packages in turn, reaching hundreds of package versions before it was stopped. Attacks like these target developer tooling and build infrastructure directly, on the assumption that compromising one link poisons everyone downstream of it.

Defending against this requires visibility into what's actually running, not just what's listed in a package.json or requirements.txt. A software bill of materials (SBOM) is an inventory of every component, direct and transitive, that makes up a piece of software, similar in spirit to a food label listing ingredients. Combined with software composition analysis tools (Dependabot, Snyk, OWASP Dependency-Track) that continuously check that inventory against newly disclosed vulnerabilities, an SBOM turns "are we exposed to this" from a guess into a query. Beyond dependency scanning, hardening the build pipeline itself matters just as much: requiring review before code merges, signing build artifacts so a tampered package can be detected, scoping CI/CD credentials narrowly, and not letting a single person push a change all the way to production without another person in the loop.

How Web Applications Fail: Cryptographic Failures

Sensitive data that should be protected isn't. Often it's transmitted without encryption, stored incorrectly, or "protected" with algorithms that are no longer adequate.

The most common practical failure is password storage. Passwords must never be stored in plain text. If the database is compromised, plain-text passwords expose every user's credentials immediately. Because people reuse passwords, this cascades into breaches on other services. The correct approach is a one-way hash designed specifically for passwords: bcrypt, Argon2, or scrypt. These are deliberately slow and include a salt, which makes precomputed attacks (rainbow tables) impractical. General-purpose fast hashes like MD5 and SHA-256 are not appropriate for passwords. Their speed becomes a liability when an attacker is running millions of guesses per second.

Beyond passwords: transmitting sensitive data over HTTP instead of HTTPS, storing credit card numbers or health data without encryption at rest, using outdated encryption standards, and encrypting data that should instead be hashed (encryption is reversible, passwords need irreversibility). The principle is to classify data by sensitivity and apply protection proportional to the risk of exposure.

How Web Applications Fail: Injection

Injection vulnerabilities happen when an application treats untrusted data as instructions. They have existed since the earliest web applications and remain among the most reliably damaging.

SQL injection is the canonical example. When user input is concatenated directly into a SQL query, an attacker can escape the intended context and modify the query itself. A login form that constructs its query like this:

SQL — vulnerable 
-- Input: username = "admin'--"
SELECT * FROM users WHERE username = 'admin'--' AND password = 'anything'
-- The -- comments out the password check. This logs in as admin with any password.

The fix is parameterized queries (also called prepared statements), which separate data from instructions at the database level. The query structure is compiled first. User input is passed as a parameter that can never be interpreted as SQL.

SQL — safe 
SELECT * FROM users WHERE username = $1 AND password_hash = $2
-- $1 and $2 are parameters — they cannot change the query structure

The same principle (data becoming instructions) applies elsewhere: command injection (user input passed to a shell), template injection (user input evaluated inside a template engine), and cross-site scripting (user input rendered as HTML and executed as JavaScript, covered in the browser security article).

Injection vulnerabilities are largely a solved problem in modern frameworks: ORMs and query builders use parameterized queries by default. They persist in legacy code and in places where developers bypass the safe abstraction, typically for convenience or to build dynamic queries.

How Web Applications Fail: Insecure Design

Some vulnerabilities aren't bugs in the code. They're the predictable result of a design that never accounted for an adversary in the first place.

Every other failure mode in this article describes an implementation mistake: a query built the wrong way, a check that's missing, a default left unchanged. Those are fixable by writing the code correctly. Insecure design is different. The code does exactly what it was built to do, and what it was built to do is unsafe. A password reset flow that emails the new password in plain text is working as designed. A discount code system with no limit on how many codes a single session can try is working as designed. A file upload feature that saves whatever it receives to a public directory is working as designed. No amount of careful coding rescues a design that never considered what an attacker would do with the feature.

This is why security has to enter the process during design, not as a review step before launch. A useful habit is to ask, for every feature, what happens if this input is malicious, what happens if this action is repeated a thousand times a second, and what's the worst thing a legitimate-looking request could do. The threat modeling section below gives this a more structured form, but the underlying habit is the same: treat the adversarial case as a normal case to design for, not an edge case to patch afterward.

Secure by design, not secure by review

A security review at the end of a project can catch implementation bugs, but it rarely fixes a flawed design without a rebuild. Secure by design means the default behavior of a system is the safe one: access denied unless granted, output encoded unless explicitly trusted, limits applied unless explicitly raised. Retrofitting that mindset after launch is far more expensive than starting with it.

How Web Applications Fail: Authentication Failures

Weak authentication mechanisms give attackers a foothold that strong application logic can't compensate for.

Credential stuffing is the most prevalent form of authentication attack today. Attackers use lists of username and password pairs leaked from previous breaches, of which there are billions in circulation, and test them against other services. It is effective because a significant proportion of users reuse passwords across sites. If a user's credentials were leaked from a breached forum, those same credentials may work on their bank, email, or workplace applications.

Other common authentication failures:

  • No rate limiting on login attempts, which enables brute force.
  • Sessions that never expire.
  • Session tokens that are predictable or too short.
  • Not invalidating sessions on logout.
  • Not invalidating all sessions when a password is changed.

Multi-factor authentication is the single most effective mitigation. An attacker who has a user's password still cannot authenticate if a second factor (a TOTP code, a push notification, a hardware key) is required. For high-value accounts and administrative access, MFA should be mandatory, not optional. Widespread adoption of standardized authentication frameworks has measurably reduced how often these failures show up in the wild, which is a rare piece of good news in this list. The authentication fundamentals article covers sessions, tokens, and the practical mechanics of implementing authentication.

How Web Applications Fail: Software and Data Integrity Failures

Not everything that arrives at an application is safe to trust just because it's shaped like ordinary data. Sometimes the format itself can carry instructions.

Insecure deserialization is the clearest example. Serialization converts an in-memory object into a format that can be stored or transmitted. Deserialization converts it back. Some serialization formats, including Java's native serialization, Python's pickle, and PHP's unserialize, can encode more than plain data: they can encode instructions for reconstructing arbitrary objects, including ones that execute code as a side effect of being reconstructed. If an application deserializes data from a source it doesn't fully control (a cookie, a cache entry, a message from another service) using one of these formats, an attacker who can influence that data can potentially get code to run the moment it's deserialized, without ever exploiting a separate bug.

Python — vulnerable 
# cookie value is attacker-controlled
import pickle
data = pickle.loads(request.cookies['session_data'])
# pickle.loads can execute arbitrary code embedded in the input
# before the application ever inspects the resulting object

The dependable fix is to avoid deserializing untrusted data in formats that support this at all. Cross a trust boundary (between the browser and the server, or between two services owned by different teams) using a data-only format like JSON, which has no mechanism for encoding executable behavior. If a native serialization format is unavoidable for internal use, never accept it from anything the user can influence, and validate the resulting structure strictly rather than trusting it implicitly. This is the same trust-boundary thinking behind the software supply chain failures covered above, just applied at the level of a single object instead of an entire dependency: both are cases of an application implicitly trusting the integrity of something it didn't create itself.

How Web Applications Fail: Security Logging and Alerting Failures

An attack that isn't logged never happened, as far as the system is concerned. An attack that's logged but never triggers an alert is barely better.

Every other failure mode in this article describes a way an attacker gets in, or gets access they shouldn't have. This one describes what happens after: nothing. Logins, failed logins, permission changes, and high-value transactions need to be recorded with enough context (who, what, when, from where) to reconstruct an incident later. Many applications log successful actions and skip the failures, which is backwards: a string of failed login attempts against one account is exactly the pattern worth catching before it succeeds, not after.

Logging alone isn't the whole picture. A log nobody reads is a record for an investigation that happens after the damage is done, not a way to catch it happening. Alerting is what turns logs into something acted on: thresholds that page a security team, dashboards that surface unusual patterns, automated responses to a spike in failed authorizations. A widely cited case involves a US health plan provider whose systems held sensitive records for millions of children. Because there was no monitoring in place, a breach could have been running undetected for years before an outside party reported it. The absence of an alert, not a single missed vulnerability, was what let it continue that long.

Logs are also an attack surface

Logging sensitive data (passwords, tokens, full credit card numbers) creates a second, often less-protected copy of exactly the information an attacker wants. And a log line built by concatenating unsanitized user input can itself become an injection point: part of what made Log4Shell so severe was that a logged string could contain a lookup expression the logging library would evaluate rather than just print. Treat log input with the same suspicion as any other untrusted data, and separate what's useful for debugging from what's actually safe to persist.

How Web Applications Fail: Mishandling of Exceptional Conditions

Software fails constantly, in small ways: a null value where one wasn't expected, a network call that times out, a downstream service that returns an error. What the system does in that moment is often where the real vulnerability lives.

An exceptional condition is any point where the code's assumptions turn out to be wrong: a required field is missing, a payment provider times out, memory runs out, a privilege check can't complete because the permissions service is unreachable. None of these are attacks by themselves. They become vulnerabilities when the application's response to them is worse than doing nothing at all: leaking a stack trace with a database schema in it, granting access because a check errored out instead of denying it, or leaving a multi-step transaction half-applied because a failure partway through was never rolled back.

That last case is the most damaging in practice. Consider a funds transfer implemented as three steps: debit the sender, credit the recipient, log the transaction. If a network interruption hits after the debit but before the credit, and the system doesn't roll the whole sequence back, an attacker who can reliably trigger that interruption has found a way to make money disappear from one account without it appearing anywhere else. The general principle is to fail closed: treat an incomplete operation as a failed one and undo it entirely, rather than trying to resume or patch it up from wherever it stopped.

The same category covers the more familiar problem of verbose error output, touched on under security misconfiguration above: an unhandled exception that reaches the user carries whatever the framework decided to put in a default error page, which can include file paths, library versions, or query fragments. The fix in both cases is the same discipline: catch errors close to where they happen, decide deliberately what to do about them, and centralize that decision so every part of the application handles failure the same way instead of each developer improvising one.

Security Principles

The failure modes above share common themes. The principles below are responses to those themes. They don't prevent every attack, but they limit damage and reduce the attack surface.

Principle
Defense in Depth

Don't rely on a single control. Validate input on the client and the server. Use parameterized queries and restrict database permissions. Hash passwords and rate-limit login attempts. Each layer compensates for failures in the others. They are complements, not alternatives.

Principle
Least Privilege

Every component (a user account, a service, a database connection, an API key, a CI/CD credential) gets exactly the permissions it needs and no more. A background job that reads orders doesn't need write access to the user table. Least privilege limits the blast radius of any individual failure.

Principle
Fail Securely

When something goes wrong, the default should be to deny access, not grant it. An error in an authentication check should result in access denied, not access granted. Generic error messages to users, detailed logs for operators. If a security check or a multi-step operation cannot complete, assume the worst and roll it back rather than leaving it half-done.

Principle
Never Trust Input

Validate and sanitize all input from external sources: users, third-party APIs, uploaded files, environment variables. Don't assume that because a form only presents valid options, the server will only receive valid values. The client sits outside the server's control, and anything it sends should be treated as untrusted.

Principle
Reduce Attack Surface

Every feature, endpoint, dependency, and open port is a potential entry point. Disable what isn't needed. Remove unused dependencies. Don't expose internal services to the public internet. The smallest possible attack surface is the easiest to defend.

Principle
Keep It Simple

Complexity is the enemy of security. The more complex a system, the harder it is to reason about its security properties and the more places there are for subtle errors. Prefer simple, well-understood patterns over clever custom solutions, especially for authentication and cryptography.

Thinking About Threats

The most valuable security habit is asking "how could this go wrong?" before shipping a feature, not after an incident.

Threat modeling is the practice of systematically identifying potential attacks before they happen. It doesn't require a formal process. The core habit is asking a few questions during design: what data does this feature handle? Who has access to it? What happens if an attacker can modify the input? What's the worst-case outcome if this goes wrong?

A useful mental framework for categorizing threats is STRIDE, which covers six classes: Spoofing (impersonating another user or system), Tampering (modifying data in transit or at rest), Repudiation (denying having performed an action), Information disclosure (exposing data to unauthorized parties), Denial of service (making a system unavailable), and Elevation of privilege (gaining permissions beyond what was granted). Running through these categories for a new feature takes minutes and often surfaces issues that would otherwise only appear in production.
