MCP

How MCP connects AI applications to external systems, and how authorization and trust boundaries govern that access.

Andreas Ögren
~13 min read
Last updated July 2026

An assistant may need to read a ticket, query an internal API, or retrieve a customer record. Each external system has its own interface and authentication rules. The Model Context Protocol (MCP) gives AI applications a common way to discover data and callable functions exposed by these systems.

Early AI integrations usually described each callable function directly in an application's model request. That approach works for a few stable functions, but every host must learn each service's schema, connection method, and lifecycle. MCP moves this integration boundary into a protocol so a host and a server can negotiate capabilities without sharing product-specific connector code.

An MCP deployment separates the user-facing application from its connections to external servers. The host decides which server capabilities a model can use and which calls require approval. Descriptions and data from every server are untrusted input because they may influence the model's next action.

Neutral protocol governance

MCP began at Anthropic and later moved under the Agentic AI Foundation. Neutral stewardship lets vendors develop the shared protocol together. Protocol stewardship does not authorize a server, so each organization must assess the servers connected to its applications.

Pair-Specific Connectors

Without a shared protocol, every pairing of AI application and external system needs a separate connector.

A coding assistant may need to read a ticket from an issue tracker. Its connector must authenticate with the tracker and translate the API into a schema the host understands. A second AI application would normally need another connector that repeats this translation and authentication work.

The translation work is more than an HTTP request. The connector has to turn service-specific operations into model-facing descriptions, preserve types in both directions, surface errors, and keep credentials outside the model's context. A change to the service API may require every connector author to update the mapping.

Separate connectors create an N×M integration problem because each of N hosts needs an adapter for each of M systems. With MCP, hosts implement one client protocol and each external system exposes one server interface. Two products are compatible only when their protocol versions, capabilities, and authentication work together. MCP connects agents to tools and context, while multi-agent systems covers delegation between agents.

The protocol reduces repeated integration work, but it does not make every server equally trustworthy or useful. A host still chooses which servers it supports, translates protocol capabilities into its user experience, and enforces its own approval policy. The shared interface creates an ecosystem boundary rather than a universal trust boundary.

Host, Client, and Server

MCP separates the user-facing application from the protocol connection and the server that exposes capabilities.

The host is the user-facing AI application a person opens and interacts with. A desktop assistant, integrated development environment (IDE) extension, or chat product can be a host. It decides what to show the user and when to call a model.

The model is not an MCP peer. It receives the tool definitions and content that the host places in a model request, then returns text or a proposed action. The host mediates every protocol operation, which gives it a place to apply policy even when the model proposes an unsafe call.

The client is the protocol component inside the host that speaks MCP. A host creates one client for each connected server, and each client communicates with exactly one server. The current protocol revision makes requests self-contained. Each request carries its protocol version, while request metadata can carry client identity and capabilities. Older revisions used an initialization handshake and a connection-scoped session, so deployed products may support different revisions during migration.

The one-client-to-one-server relationship keeps protocol traffic separate. A ticket-tracker server cannot directly send a message through the client's connection to a database server. A host may expose both servers to one model, which creates an indirect path between them. Authorization and approval controls must prevent content from one server from causing an unintended action through the other.

The server exposes a focused set of capabilities. A local server can run as a subprocess and communicate over standard input and output. A remote server can use Streamable HTTP, where each message is sent to one HTTP endpoint and a response may use a request-scoped server-sent event stream. Both transports carry MCP messages, while their deployment and authentication requirements differ.

A local server can use files and credentials available on the user's machine, so installation and process isolation carry much of the security burden. A remote server centralizes updates and can apply server-side access policy, but every call crosses a network and needs explicit authentication. Transport choice therefore changes the operational boundary even though the model sees similar capabilities.

Tools, Resources, and Prompts

MCP gives callable functions, contextual data, and reusable interaction templates different protocol primitives because hosts use and govern them differently.

A tool is a callable function exposed to the model. It may read data, perform a computation, or cause a side effect such as creating a ticket. Hosts should assess the effect of each tool and its arguments. Destructive or externally visible actions usually need stronger approval than read-only operations.

A tool definition contains a name, a description, and an input schema. The schema can require a ticket identifier and restrict a status argument to known values. Validation can reject a malformed proposal before it reaches the server. It cannot decide whether closing that particular ticket is appropriate, which is why business authorization and user approval sit outside schema validation.

A resource is data the host can read and place into context. Documents and database records are common examples. A resource read asks the server to return content without requesting a business operation that changes the source. The server may still record the read or perform other incidental work. Resource content may contain sensitive data or malicious instructions, so access control and prompt-injection defenses apply before it reaches the model.

Resources have identifiers, and servers can expose templates for sets whose members are too numerous to list. A source-code server might offer a template that accepts a repository path. The host can then request one file without presenting the full repository as a flat resource catalogue.

A prompt is a reusable interaction template offered by the server for a user to select. It can assemble instructions and arguments for a known workflow. Because the server supplies this text, the host should show its source and contents before use.

Prompts package a workflow for reuse, but they do not gain authority from being an MCP primitive. A prompt that asks for a release summary may suggest reading commits and issue records. The host still decides which sources are available and whether any proposed action is allowed.

Tools
Callable operations

Tools are functions the model can invoke to read information, perform a computation, or cause an external change. The host should base approval on the effect of each operation.

Resources
Data for context

A resource contains data such as a file, record, or snapshot for the host to read. The operation requests content instead of a business mutation. Its content may enter the model's context and affect later output or tool calls.

Prompts
User-selected templates

Prompts are reusable interaction templates supplied by a server for a user to choose. The host treats their instructions as untrusted server content.

The primitives reach the model through flows controlled by the host. For a tool call, the MCP client first requests the server's tool list. The host selects the definitions allowed for the current task and includes them in a model request. If the model proposes a call, the host validates the tool and its arguments and obtains any required approval. The client then sends the call to the server, and the host treats the returned result as untrusted input before using it in another model request.

Consider an assistant asked to summarize ticket 482. The host may expose a read-only ticket tool and a resource for the team's support policy. The model proposes the ticket lookup, the host validates the identifier, and the server returns the record. The model sees only the returned record and selected policy text. It never receives the tracker's access token or a direct network connection.

Resources and prompts begin with a host or user choice. The client can list resources and read selected content, while a prompt is fetched with its arguments after the user selects it. MCP carries these requests and responses between client and server. The host decides what reaches the model, what the user sees, and which operations require consent.

Enterprise Authorization

Organizations need a consistent way to grant and revoke employee access across many MCP servers.

When a remote HTTP server uses MCP's standardized authorization flow, it builds on OAuth. In the ordinary user-managed pattern, the client obtains an access token for one server on behalf of one user. Each employee may then need to authorize every server separately, and administrators cannot manage all access through existing identity policy.

Enterprise-Managed Authorization (EMA) is an optional extension that makes the organization's identity provider the policy point for server access. During single sign-on, the client can obtain an Identity Assertion JSON Web Token (JWT) Authorization Grant, known as an ID-JAG. It exchanges the grant with the server's authorization server for an audience-restricted access token. Administrators can then grant or revoke access through existing identity policy without asking every employee to complete a separate consent flow for every server.

EMA support requirements

The MCP project declared EMA stable in June 2026. The optional extension requires support from the client, identity provider, and server authorization stack. EMA controls access to the server, and the server or gateway authorizes each tool call according to the current business context.

Central provisioning does not remove the server's responsibility to authorize a request. An access token identifies an audience and granted scope, while the server still checks whether the employee may read ticket 482 or change its status. Identity policy answers who may reach the service. Domain authorization answers what that identity may do with a specific record.

MCP and Existing APIs

MCP usually sits in front of an existing service interface rather than replacing the service behind it.

An MCP server can call a REST or GraphQL API, run a database query, or use a vendor software development kit. The underlying interface continues to enforce business rules and store authoritative data. The MCP layer chooses which operations to expose and describes them in a form an AI host can discover.

Direct function calling solves a narrower problem. An application supplies tool definitions to one model API and executes proposed calls in its own code. MCP standardizes how a host discovers those definitions and exchanges requests with separately deployed servers. A small application with two internal functions may need no protocol layer. MCP becomes useful when several hosts, services, or independent teams need a shared integration boundary.

Proprietary plugin systems can offer deeper product integration because one vendor controls both ends. Their manifests, authentication flows, and distribution rules are tied to that product. MCP trades some product-specific behavior for reuse across compatible hosts. Agent-to-agent protocols address a different boundary because they let autonomous systems exchange tasks and results rather than expose a server's tools and resources.

The Gateway Pattern

Letting every AI application connect directly to every server becomes difficult to govern as the number of applications and servers grows.

An MCP gateway places a controlled data path between hosts and servers, much as an API gateway does for application traffic. It can apply common policy across hosts, including rate limits and a server allowlist. The gateway may inspect arguments and produce audit records. Each server authorizes access to its own data and actions.

The gateway is an architectural option rather than part of every MCP exchange. It reduces repeated policy code and gives operators one place to observe traffic. It can become a failure domain and a high-value target, so availability, credential isolation, and policy changes need the care given to other central infrastructure.

An audit record should identify who initiated a call and trace it through the host, server, and tool. The record should include the authorization decision and outcome. Arguments and results may contain secrets or personal data, so logs need redaction and retention controls. Each server should keep the application-level record required for its own actions.

Tool Poisoning and Rug Pulls

Tool metadata is untrusted text entering a system with authority to act.

A tool definition tells the model when a tool may help and which arguments it accepts. Tool poisoning places malicious instructions in this metadata so the model performs work the user did not intend. A rug pull changes a previously reviewed definition later. MCP can notify the client when a tool list changes. The client then needs to discard the earlier approval and require another review.

Returned resources and tool results create another route for indirect prompt injection. A support ticket may contain text that tells the model to upload a file through a second tool. The ticket content is evidence for the user's task, not an instruction with authority. The host has to preserve this distinction when it builds the model request and when it evaluates the proposed call.

The browser security article's treatment of cross-site scripting (XSS) covers a related problem. Untrusted input reaches a component with authority to act. In XSS, attacker-supplied markup reaches a browser that may execute it. With MCP, a tool's description reaches a model that may use the description when deciding what to do next.

Reviewing changing tool definitions

Clients should display complete tool definitions and compare them with the last approved version. A material change should require renewed consent. Allowlists and signed releases control which definitions are accepted, while schema validation limits their shape. Least-privilege tokens and per-call approval limit what malicious instructions can do if they reach the model.

Useful approval screens describe the concrete effect of a call. A confirmation for close_ticket should name the ticket, show the proposed resolution, and identify the account whose credentials will be used. A generic prompt that asks whether the assistant may continue gives the user too little information to judge the action.

Local and remote servers concentrate risk in different places. A local package can read machine files available to its process and can change after an update. A remote server exposes a network and identity boundary and can change its behavior without a local installation event. Package pinning and process isolation help with the first case, while endpoint allowlists, transport security, and server-side audit records help with the second.

Server metadata and returned content belong to the application's untrusted-input surface. Authorization and least-privilege credentials limit what an agent can access. Change detection and per-action checks protect the boundary as server definitions evolve, and gateway logs make decisions inspectable. Organizations should design these controls before agents receive access to sensitive systems.
