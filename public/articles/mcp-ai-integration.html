MCP

How MCP connects AI applications to external systems, and how authorization and trust boundaries govern that access.

Andreas Ögren
~7 min read
Last updated July 2026

An assistant becomes more useful when it can reach systems beyond the repository: an issue tracker, an internal API, or a customer record. Without a shared protocol, every AI application needs its own adapter for each system. The Model Context Protocol (MCP) defines a common way for an AI host to discover context and callable capabilities, reducing the amount of product-specific integration code.

The protocol itself is only one layer of the design. This article first separates the host, client, and server roles, then explains tools, resources, and prompts. The later sections cover authorization, gateways, audit trails, and the security consequences of giving untrusted server metadata to a model that can act.

Same governance as AGENTS.md

MCP began at Anthropic and later moved under the Agentic AI Foundation. Neutral stewardship helps a protocol intended to connect products from different vendors, but governance alone does not make individual servers trustworthy. Each deployment still needs its own authorization and security controls.

The Problem Before MCP

Before a shared protocol existed, every pairing of AI tool and data source needed its own bespoke connector.

Consider a coding assistant that needs to read a ticket from an issue tracker. The integration must authenticate, translate the tracker's API into a model-facing schema, and return the result in a form the host understands. Building that adapter for one assistant is manageable. Repeating it for every assistant creates parallel implementations of the same boundary, each with its own authentication and maintenance work.

This is the familiar N×M integration problem. Each of N hosts needs an adapter for each of M systems. MCP aims to move the boundary toward N+M by giving hosts one protocol to implement and systems one server interface to expose. Compatibility still depends on supported protocol versions, capabilities, and authentication, so the reduction is an architectural goal rather than a guarantee of plug-and-play behavior. MCP covers agent-to-tool communication; multi-agent systems covers delegation between agents.

Host, Client, and Server

Three roles, and almost everything about how MCP behaves follows from keeping them straight.

The host is the user-facing AI application the person opens and talks to, such as Claude Desktop, an IDE extension, or a chat product. The host is the thing making decisions about what to show the user and when to involve a model at all.

The client is the protocol component inside the host that speaks MCP. A host typically runs one client per connected server, and each client holds its own private, stateful session. A client talking to a ticket tracker doesn't know anything about a second client talking to a database, even though both live inside the same host. This separation prevents a server from directly addressing another client's protocol session. It is not complete containment. The host may expose capabilities from several sessions to the same model, so its authorization and approval controls must prevent one server's content from inducing actions through another.

The server exposes a focused set of capabilities. A local server can run as a subprocess and communicate over standard input and output. A remote server can use Streamable HTTP, which supports ordinary HTTP requests and optional server-sent events for streaming. The transport affects deployment and authentication, but both use the MCP data model above the transport layer.

Tools, Resources, and Prompts

MCP separates callable functions, contextual data, and reusable interaction templates into three primitives.

A tool is a callable function exposed to the model. It may read data, perform a computation, or cause a side effect such as creating a ticket. Risk therefore depends on the individual tool and its arguments, not on the primitive alone. Hosts should distinguish read-only operations from destructive or externally visible actions when they decide what requires approval.

A resource is data the host can read and place into context, such as a document, schema, or record. Reading it does not itself cause the side effects associated with a write tool, but the content may still be sensitive or malicious. Access control and prompt-injection defenses apply before that data reaches the model.

A prompt is a reusable interaction template offered by the server for a user to select. It can assemble instructions and arguments for a known workflow, but it remains text supplied across a trust boundary. The host should present its source and contents clearly rather than treating a server-authored template as trusted application code.

Tools
Actions with side effects

Functions the model invokes to do something, such as create, update, send, or query. The primitive that needs the closest review, since it can act on the model's own initiative.

Resources
Data for context

Something read rather than triggered, a file, a record, a snapshot. Lower risk on its own, though what it contains still becomes part of what the model reasons over.

Prompts
Vetted interaction patterns

Reusable templates a server author supplies, so a known-good way of combining its own tools doesn't have to be reinvented by every model that connects to it.

Enterprise Authorization

Connecting an agent to one more system is easy. Connecting it to forty of them, safely, for every employee at once, is the actual enterprise problem.

For remote HTTP servers, MCP defines an authorization flow built on OAuth. In the ordinary user-managed pattern, the client obtains an access token for one server on behalf of one user. That preserves individual consent, but it creates administrative friction when an organization needs to provision and revoke access consistently across many servers.

Enterprise-Managed Authorization (EMA) is an optional extension that makes the organization's identity provider the policy point for server access. During single sign-on, the client can obtain an Identity Assertion JWT Authorization Grant (ID-JAG) and exchange it with the server's authorization server for an audience-restricted access token. Administrators can then grant or revoke access through existing identity policy without asking every employee to complete a separate consent flow for every server.

Adoption is underway, not universal

The MCP project declared EMA stable in June 2026, but the extension is opt-in and requires support from the client, identity provider, and server authorization stack. It governs access to the server; it does not decide whether a particular tool call is appropriate in the current business context. Per-action authorization still belongs in the server or gateway.

The Gateway Pattern

Letting every AI application connect directly to every server becomes difficult to govern as the number of applications and servers grows.

An MCP gateway places a controlled data path between hosts and servers, much as an API gateway does for application traffic. It can centralize policy, rate limits, server allowlists, argument inspection, and audit logging. The gateway does not remove the need for server-side authorization, but it gives the organization one place to apply controls that should be consistent across hosts.

A useful audit record ties each call to the host, user, server, tool, decision, and outcome. Arguments and results may contain secrets or personal data, so logging them in full can create a second disclosure path. A gateway makes consistent redaction and retention possible, while each server should still keep the application-level record needed for its own actions.

Tool Poisoning and Rug Pulls

Tool metadata is untrusted text entering a system with authority to act.

The browser security article's treatment of XSS covers the same underlying problem, untrusted input reaching a place that has authority to act on it. There, the untrusted input was attacker-supplied markup reaching a browser that would execute it. Here, the untrusted input is a tool's own description field, and the place with authority is the model deciding what to do next.

A tool's name, description, and schema help the model decide when and how to call it. Tool poisoning places malicious instructions in that metadata so the model performs work the user did not intend. A rug pull changes a previously reviewed definition later. MCP supports notifications when a tool list changes, but the security outcome depends on whether the client detects the change, invalidates prior trust, and asks for a new review.

Why this is hard to catch by inspection alone

Defenses begin by treating server metadata as untrusted input. Clients can display complete definitions, compare them with the last approved version, and require renewed consent after a material change. Allowlists, signed releases, schema validation, least-privilege tokens, and per-call approval for sensitive actions reduce the damage if malicious instructions still reach the model.

These risks do not make MCP unusable. They make server metadata and returned content part of the application's untrusted-input surface. Authorization, least privilege, change detection, per-action checks, and an auditable gateway should be designed before agents receive access to sensitive systems.
