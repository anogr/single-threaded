AI Coding Assistants

How coding tools move from inline suggestions to repository-scale work, and how project guidance keeps agents on track.

Andreas Ögren
~15 min read
Last updated July 2026

AI coding assistants began as inline completion tools that offered a few characters or lines for a developer to accept or ignore. The label now covers agents that inspect a repository and carry a planned change through editing and verification. An agent working across the codebase needs more project guidance than a tool completing one line.

Repository-scale work begins with finding the relevant code and loading the project rules that source files do not express. It ends with a change the developer can verify without reconstructing the agent's entire session. Delegation saves time only when both parts work well.

A note on terms

An assistant here means any AI coding tool in an editor or terminal. An agent is an assistant that inspects and changes a project through tools, using each result to decide its next step. A product may provide both modes.

From Autocomplete to Agent

A completion suggests code at the cursor. An agent works toward a larger result such as fixing a bug or implementing a ticket.

Inline completion presents a small code suggestion at the cursor for the developer to accept or reject immediately. The product may build the suggestion from the current file, other open files, or indexed repository context. Accepting the text adds it to the codebase, so the developer has to verify its behavior.

In chat-based assistance, the developer directs each exchange. The product may run several searches or other tools within one turn, but control returns to the developer after the assistant explains a problem or proposes a change.

Agentic tools accept a task such as a bug report or feature description. The agent finds relevant files, forms a plan, and edits across the change boundary. It can run the build and tests and then revise the code when a check fails. The developer delegates line-by-line authorship and reviews the plan and finished diff.

One task can move through several modes. In a plan-first workflow, the agent first researches the change and proposes an approach. It waits for approval before using its editing and command tools. The developer can correct the scope or an incorrect assumption before either spreads across a multi-file diff.

Inline completion

Chat / ask

Chat turns a question or task into an explanation or proposed change, after which the developer decides what the next exchange should do.

Agent
One task at a time

Given a ticket or bug report, an agent explores the repository and plans a change. It edits the relevant files and runs the project's checks. If a check fails, the agent can revise the change before presenting the result for review.

The Agent Loop

An agent works through repeated model requests, tool calls, and checks until it reaches a result or a stopping condition.

An agentic product uses a harness to coordinate the model and its tools. For each model request, the harness assembles the task, selected conversation history, project instructions, and recent tool results. The model can propose another tool call or return a result. When a call is allowed, the harness executes it and supplies the observation in a later model request. This loop lets the agent search, edit, test, and revise without requiring the developer to direct every step.

Tool access sets the practical boundary of the agent's autonomy. Reading a source file has a different effect from changing it, running a command, or calling an external service. The harness can deny a tool, restrict its arguments, or require approval before an action executes. A prompt can describe the intended boundary, while the harness enforces the permissions that protect it.

Verification belongs inside the loop. A compiler error or failing test becomes new evidence the agent can use to revise its change. Passing checks support the result only within the behavior those checks cover. The developer still needs the final diff, the commands that ran, and any unresolved uncertainty to decide whether the task is complete.

A failed check changes the next iteration in a concrete way. If a type checker reports that a new return value can be undefined, the harness gives that diagnostic to the model together with the edited code. The model can inspect the caller, adjust the implementation, and run the check again. A retry limit, time budget, denied permission, or repeated failure should stop the loop and return control to the developer. Without a stopping condition, an agent can spend tokens changing symptoms without resolving the original problem.

Repository Context Selection

An agent cannot load every repository file into every request, so it must select the code relevant to the task.

Every model request has a context window that limits how many tokens the current input and generated answer can use. File-oriented assistants usually fill the input with the open file and some nearby or explicitly selected code. Such local context may be enough for a local edit. A change that crosses a service boundary may depend on callers and tests that the editor has not opened.

Repository-aware agents use search to decide what enters the context window. A semantic index can retrieve code related to the task by meaning. The agent may inspect file listings or use text and symbol search before reading selected files. Products often combine these methods, which lets an agent find a caller or test far from the file where the change began.

Each search method answers a different question. Text search finds an exact identifier or error message. Symbol search follows definitions and references that a language service can resolve. Semantic retrieval finds code whose wording differs from the task description, but similarity does not prove that the code is authoritative. A useful agent starts with the strongest available signal and checks the retrieved code against callers, tests, and repository structure.

Clear module boundaries and predictable names help search find related code. Tests placed near the code they cover provide another useful signal. In a tangled repository, the agent spends more of its context window reconstructing relationships that the codebase does not express directly.

A larger context window lets the agent inspect more code at once. An entire repository may exceed even a large window, while irrelevant files can bury useful evidence inside a long prompt. Models sometimes use information near the middle of a long context less reliably, as the lost-in-the-middle effect describes. The agent therefore needs good selection even when the model accepts a large input.

Context window vs. context file

The context window limits how many tokens the model can consider at once. A context file, covered next, is a scoped source of project instructions that a compatible tool may load into the window. It is one input the team can maintain within the available capacity.

Repository Context Files

Repository instructions supply project knowledge that search and source code may not reveal.

Many agentic tools can load repository instructions when their scope applies. Repository instruction files tell the agent how to build and test the project and explain local conventions that code search may not reveal. They can identify module ownership and actions that require human approval. Some tools support nested files so a subdirectory can add more specific guidance.

Coding products first established their own instruction formats. Claude Code uses CLAUDE.md, GitHub Copilot supports repository and path-specific custom-instruction files, and Cursor has product-specific project rules. Maintaining complete copies for several tools creates predictable drift when one file changes without the others.

AGENTS.md provides a shared Markdown format supported by several coding agents and development environments. A file at the repository root can hold project-wide guidance. Tools that implement hierarchical lookup can apply additional files within a subtree. Some product-specific settings need their own files. Shared guidance reduces how much those files must duplicate.

A shared format gives developers a predictable place to find project guidance, much like a README or package.json. An organization with many repositories can use this convention without teaching a different location for each coding tool.

A minimal AGENTS.md can contain a few headings of the kind a new engineer's onboarding document would already have.

- Install: pnpm install

- No default exports outside of route files.

- Never edit files under generated/.
- Database migrations require human review, don't run them automatically.

Contents of a Context File

A context file should contain project rules that apply often and cannot be enforced more reliably elsewhere.

Repository instructions consume context whenever the tool loads them. They should include exact build and test commands when the project needs unusual setup. They should explain local conventions or module boundaries that source code does not express clearly. Sensitive areas such as production configuration or database migrations should require approval before the agent changes them.

Formatters and linters should enforce stable formatting or naming rules for both human and generated code. Framework documentation can be retrieved when a task needs it. Repository instructions are best reserved for local facts and decisions that the agent cannot infer safely from the code.

Specific to this repo
Worth including

"API routes live under src/routes and must export a validation schema alongside the handler." Something a newcomer couldn't guess from the code alone.

Already enforced elsewhere
Not worth including

"Use two spaces for indentation." A formatter can enforce this rule consistently, so duplicating it as prose adds another source that can drift.

Repository guidance becomes obsolete as the project changes. A file written during a proof of concept may name a test command that was replaced months later, and the agent may follow it as confidently as a current command.

A stale file actively misleads

Teams should review repository guidance in pull requests and test the commands it contains. A code or process change that invalidates an instruction should update the corresponding guidance.

Keeping Documentation in Sync

Agents read project documentation and can draft updates when the code changes.

Docstrings, READMEs, and architecture decision records become obsolete when code changes without a corresponding prose update. An agent can inspect a diff and draft related documentation changes. Someone who understands the decision behind the code must review the draft.

Repository instructions can require an architecture decision record when a task changes a service boundary, data model, or dependency between modules. The agent can start the document, but the responsible team must make and explain the decision. Earlier records should continue to describe the circumstances in which their decisions were made.

An architecture decision record helps a future maintainer understand what was decided and why. A future agent can use the record to find the constraints that apply to another change. Plainly written constraints serve both readers without turning the record into tool-specific instructions.

An agent can reduce the work required to produce a documentation draft. Polished prose may describe an incorrect assumption, so the code and documentation should be reviewed together before either becomes the project's source of truth.

Working Across Multiple Tools

A canonical instruction file lets several assistants use the project rules without maintaining a full copy for each product.

A team may use different products for inline editing, terminal-based agent work, and automated review. Full copies of the project rules will drift as soon as one copy changes alone. The team should give the shared instructions one owner and one canonical source, then add thin adapters for products that expect another filename or format.

Teams can keep portable guidance in AGENTS.md and limit product-specific files to instructions that their tools cannot import. Some environments read the shared file directly. Others can import it or need a short adapter. Teams should check current product support before adding a bridge because this part of the ecosystem changes quickly.

CLAUDE.md Markdown 
@AGENTS.md

The adapter should point to the canonical file or restate only what the product cannot import. Generated copies can look authoritative after the source has changed and are best avoided. A product-specific file is appropriate for settings that apply only to one agent, such as its tool permissions or command conventions.

The team should assign an owner to AGENTS.md in the way it assigns ownership for lint or continuous-integration configuration. Every compatible agent may apply a changed instruction in later sessions, so ambiguous edits deserve careful review.

Skills, Prompt Files, and Subagents

Stable project rules belong in repository instructions. Specialized workflows and side tasks should be loaded only when needed.

A short context file can provide background knowledge for many tasks without consuming too much of every session. More specialized material should be loaded on demand. A skill can package a migration runbook, a prompt file can store a reusable request, and a subagent can handle exploratory work in a separate task thread.

Agent Skills package situational instructions with optional scripts, references, and templates. A skill lives in a folder built around SKILL.md. Compatible agents can inspect its short metadata first and load the full material when the task calls for it. A migration runbook or document workflow can therefore be available without occupying every coding session.

A prompt file stores a reusable request that a developer invokes deliberately. It behaves more like a task template than background configuration. For example, a prompt file can ask an editor agent to draft a changelog entry from the current diff. Repository instructions shape every relevant task, a skill supplies material for a specialized workflow, and a prompt file waits for someone to choose that workflow.

A subagent handles a bounded side task and usually receives a separate conversation history. It can search for every caller of a function or audit a directory without filling the main thread with each file and dead end it encounters. The subagent returns concise findings, leaving the coordinating agent with more room for the primary task. Products differ in how subagents are declared and which models, tools, filesystems, credentials, or other state they share.

Cost and Token Efficiency

Agentic work processes more input and output tokens than a short inline completion, so repeated tasks can create a significant service cost.

Inline completion uses a small amount of context and returns little output. An agentic session may read several files, ingest command output, and carry useful material across multiple iterations. Repository-aware work therefore costs more when the agent searches widely or retries often. The LLM article explains the underlying input and output costs.

At team scale, token usage becomes a budget line. Repository instructions can reduce repeated exploration by providing the exact build and test commands up front, while narrow tasks limit unnecessary file reads and retries. Model routing provides another way to control usage. Teams can evaluate smaller models for bounded tasks and reserve a more capable tier for work that needs broader reasoning.

Teams should measure the cost of the completed task. The total includes the context and generated output from every model call, plus any retries and validation. If a smaller model misunderstands the task, the resulting retries can cost more than one well-scoped request to a more capable model.

Effective Delegation

Delegation saves time when a developer can verify the result faster than producing it manually.

The strongest use cases produce a bounded result that the developer can verify. An explanation of a stack trace can be checked against the source, while a refactor can be checked with a focused diff and automated tests. In both cases, the repository provides evidence that makes the result inexpensive to review.

Large design decisions often depend on business context and risk tolerance that the repository does not contain. An assistant can gather options and explain their technical tradeoffs. The responsible team must choose among them because it has the missing context and owns the consequences.

Evidence makes delegation useful

Useful delegation pairs each generated result with accessible evidence. Source code can support an explanation, while types and tests can check a refactor. Generation saves less time when correctness is slow or subjective to establish.
