AI Coding Assistants

How coding tools move from inline suggestions to repository-scale work, and how project guidance keeps agents on track.

Andreas Ögren
~16 min read
Last updated July 2026

AI coding assistants began as inline completion tools, offering a few characters or lines for a developer to accept or ignore. The label now covers agents that can inspect a repository, plan a change, edit several files, run commands, and react to failures. Configuration therefore depends on the unit of work being delegated. Guidance that is enough for a line completion may be wholly inadequate for an agent changing a feature across the codebase.

The sections below follow that range from completion to agentic work. They explain how an assistant discovers relevant code, how repository instructions shape its choices, and when skills or subagents are a better fit than always-loaded guidance. The article closes with the less visible constraints: token cost, maintenance work, and the kinds of task where delegation saves time.

A note on terms

This article uses assistant for any AI coding tool in an editor or terminal. An agent is an assistant that works through a loop of inspecting, planning, editing, running tools, and responding to the results. A product may expose both behaviors, so the distinction describes the mode of work rather than the brand.

From Autocomplete to Agent

The tools share a name but not a unit of work. Some finish your sentence. Others finish your ticket.

Inline completion predicts the next few tokens from the current file and whatever nearby context the editor supplies. Its unit of work is deliberately small. The developer accepts or rejects each suggestion as it appears, so review happens at the same moment as authorship.

Chat-based assistance sits a step up. A developer asks a question or pastes an error, the model answers with an explanation or a proposed diff, and the developer decides whether to apply it. The unit of work is still small, usually a function or a file, and a human is in the loop on every exchange.

Agentic tools accept a task rather than a line or a snippet. Given a bug report or feature description, an agent can search for relevant files, form a plan, edit across the change boundary, run the build and tests, then respond to failures. Products differ in their tools and approval settings, but responsibility shifts toward review. The developer reviews a plan and a finished diff instead of authoring every line.

The modes can be combined within one task. A plan-first workflow begins like chat: the agent researches the change, proposes an approach, and waits. After approval it switches to execution and works through the plan with its tools. That checkpoint gives the developer a cheap place to correct scope or assumptions before they spread across a multi-file diff.

Inline completion
One token at a time

Predicts the next few characters or lines from open-file context. Lowest disruption, easiest to review since acceptance is instant and per line.

Chat / ask
One exchange at a time

A question, an error, or a snippet goes in. An explanation or a proposed change comes back. The developer decides, per exchange, whether to apply it.

Agent
One task at a time

Given a ticket or a bug report, it reads the repo, plans, edits multiple files, runs commands, and iterates on failures, then presents a finished result for review.

How an Agent Sees a Repository

A model's context window is finite. Almost everything about configuring an agent well comes down to what fills it.

Every model has a context window that limits how many tokens one request can contain. File-oriented assistants usually fill it with the open file and a small amount of nearby or explicitly selected code. This is enough for a local edit. A change that crosses a service boundary also needs distant callers, shared utilities, and tests that the editor may never have opened.

Repository-aware agents use search to decide what enters the context window. Some products maintain a semantic index and retrieve code related to the task by meaning. Others let the agent explore with file listings, text search, symbol search, and targeted reads. Many combine both approaches. The important change is that relevance is discovered during the task, which lets an agent find a caller or test far from the file where the change began.

Repository structure now affects the quality of that discovery. Clear module boundaries, predictable names, and tests near their owners give both search and the agent useful signals. A large repository can still work well, whereas a smaller but tangled one may force the agent to spend much of its context budget reconstructing relationships the codebase never made explicit.

Larger context windows allow an agent to inspect more code at once, but they do not remove the retrieval problem. An entire repository may still exceed the limit, and irrelevant files compete with the evidence the task needs. Information buried inside a long prompt can also be used less reliably than material near its edges, the lost-in-the-middle effect. Capacity helps after the right material has been found; it does not make selection unnecessary.

Context window vs. context file

The context window is a hard limit on how many tokens a single request can hold. A context file, covered next, is a document written once that gets loaded into that window every session. One is a constraint nobody controls, while the other is a lever a team controls directly.

Context Files: CLAUDE.md and AGENTS.md

If one file determines whether an agent behaves like a senior engineer on the project or a confused newcomer, this is it.

Most agentic tools can load repository instructions before starting work. These files capture the project knowledge that code search alone may not reveal: exact build and test commands, local conventions, ownership boundaries, and actions that require human approval. Some tools support nested instruction files so guidance can become more specific inside a subdirectory.

Products first established their own instruction formats. Claude Code uses CLAUDE.md, while GitHub Copilot supports repository and path-specific custom-instruction files. Cursor has product-specific project rules. Maintaining complete copies for several tools creates predictable drift, especially when one file changes without the others.

AGENTS.md emerged as a portable answer to that duplication. It is a plain-Markdown convention supported by several coding agents and development environments. A file at the repository root can hold shared guidance, while nested files can refine it for a subtree in tools that implement hierarchical lookup. Product-specific instruction files still exist, but a shared file reduces the amount of guidance that must be copied between them.

A shared format helps beyond one repository. Developers know where to look for project guidance, much as they already look for a README or package.json. The saving is small on one project but accumulates across an engineering organization with many repositories.

A minimal AGENTS.md is just a few headings of the kind a new engineer's onboarding doc would already have:

AGENTS.md Markdown 
# Project conventions

## Build & test
- Install: pnpm install
- Run tests: pnpm test -- --run
- Lint: pnpm lint

## Conventions
- Components use function declarations, not arrow functions.
- No default exports outside of route files.

## Boundaries
- Never edit files under generated/.
- Database migrations require human review, don't run them automatically.

What Belongs in a Context File

The instinct is to write down everything you know about the project. Resist it.

Repository instructions consume context whenever the tool loads them, so useful files stay selective. Include exact build and test commands, especially when the project needs unusual flags or setup. Record conventions the source cannot express clearly, ownership boundaries between modules, and actions that need approval. Generated files, production configuration, database migrations, and deployment definitions are common examples, but the boundary should reflect the project rather than a generic checklist.

What doesn't belong is a restatement of the whole style guide. Modern models already write idiomatic code in whatever language they're given, so telling one to use camelCase in JavaScript spends tokens confirming something it already does. Restating framework documentation or explaining a well-known library wastes space for a similar reason. Save the file for the part that's specific to this codebase, usually a small fraction of everything a team could write down about it.

Specific to this repo
Worth including

"API routes live under src/routes and must export a validation schema alongside the handler." Something a newcomer couldn't guess from the code alone.

Already known
Not worth including

"Use consistent indentation and meaningful variable names." The model already does this by default. Saying so just spends tokens confirming it.

A context file needs upkeep. Guidance written during a proof of concept may still name a test command that was replaced months later. The agent has no inherent way to distinguish that stale instruction from an accurate one.

A stale file actively misleads

An agent may follow an obsolete instruction as confidently as an accurate one. Review repository guidance in pull requests, test the commands it contains, and update it with the code or process change that made the old instruction false.

Keeping Documentation in Sync

A context file is one kind of document an agent reads. Agents increasingly write this kind of document too.

Docstrings, READMEs, and architecture decision records can become stale just like repository instructions. Code changes while prose stays unchanged. An agent that can inspect a diff can often draft the documentation changes implied by it. That draft is useful because it makes the missing update visible, but it still needs review by someone who understands the decision behind the code.

Architecture decision records benefit from an explicit trigger. Repository instructions can tell an agent to draft one when a task changes a service boundary, data model, or dependency between modules. The draft does not decide the architecture, and it should not rewrite an earlier decision to make the present change look inevitable. Its value is procedural: a decision that deserves a record is less likely to disappear merely because nobody remembered to start the document.

An architecture decision record now serves two readers. A future maintainer needs to know what was decided and why. A future agent needs the constraints that still apply when it proposes another change. Writing those constraints plainly improves the record for both audiences without turning it into tool-specific prompt material.

Cheaper documentation is useful only if the review step stays in place. An agent can produce a polished explanation of an incorrect assumption as readily as a correct one. Treat its contribution as a first draft tied to the code change, then review both together before either becomes the project's source of truth.

Working Across Multiple Tools

Most teams don't standardize on a single assistant. The instruction file shouldn't need rewriting for each one anyway.

A team may use one product for inline editing, another for terminal-based agent work, and a third for automated review. If every product receives a full copy of the project rules, those copies will drift. Shared instructions should therefore have one owner and one canonical source, even when adapters are needed for tools that expect a different filename or format.

A practical pattern is to keep portable guidance in AGENTS.md and make product-specific files as thin as their tools allow. Some environments read the shared file directly. Others can import it or need a short adapter that adds only the instructions unique to that product. Current support should be checked before adding a bridge, because this part of the ecosystem changes quickly.

CLAUDE.md Markdown 
@AGENTS.md

The adapter should point to the canonical file or restate only what the product cannot import. Avoid generated copies that look authoritative after the source has changed. A product-specific file is still useful for settings that genuinely apply only to that agent, such as a tool permission or command convention that another environment does not understand.

Team adoption needs clear ownership more than elaborate tooling. The owner of AGENTS.md influences how every compatible agent approaches the project, much as the owners of lint and CI configuration shape every contribution. Changes deserve review because one ambiguous instruction can alter many later sessions.

Skills, Prompt Files, and Subagents

Always-loaded instructions suit stable project rules. Situational knowledge and bounded side work need a different shape.

A context file holds background knowledge that applies broadly, which is why it stays small. Specialized material has a narrower audience. A migration runbook, a framework-specific house style, or a script for an occasional task should be available when needed without occupying every session. Skills, prompt files, and subagents separate those cases in different ways.

Agent Skills package situational instructions with optional scripts, references, and templates. A skill lives in a folder built around SKILL.md. Compatible agents can inspect its short metadata first and load the full material only when the task calls for it. That makes a skill a better home for a migration runbook or document workflow than an instruction file loaded for every coding task.

A prompt file stores a reusable request that a developer invokes deliberately. It behaves more like a task template than background configuration. For example, a prompt file can ask an editor agent to draft a changelog entry from the current diff. Repository instructions shape every relevant task, a skill supplies material for a specialized workflow, and a prompt file waits for someone to choose that workflow.

A subagent handles a bounded side task in a separate context. It can search for every caller of a function or audit a directory without filling the main session with each file and dead end it encounters. The subagent returns findings rather than its complete working transcript, leaving the coordinating agent with more room for the primary task. Products differ in how subagents are declared and which tools or models they may use, but isolation is the common mechanism.

Not the same "prompt" as MCP's

The next article in this series covers MCP, which also defines something called a prompt: a reusable interaction template a server offers to whatever host connects to it. A prompt file here is a local, editor-level convention with no relation to that primitive beyond sharing a name. Keep the two apart when the terms show up in the same conversation.

All three mechanisms place reusable structure around the agent instead of relying on one carefully worded request. Harness engineering extends that idea to permissions, feedback loops, isolation, and approval gates that apply across sessions.

Cost and Token Efficiency

An agent that reads a repository, runs commands, and iterates on failures spends a lot more tokens than a single autocomplete suggestion. At a certain scale, that difference shows up on an invoice.

Inline completion uses a small amount of context and returns little output. An agentic session may read several files, ingest command output, and carry useful material across multiple iterations. That additional context is part of repository-aware work, but it makes task cost sensitive to how widely the agent searches and how often it retries. The LLM article explains the underlying input and output costs.

At team scale, token usage becomes a budget line. Repository instructions can reduce repeated exploration by providing the exact build and test commands up front. Narrow tasks limit unnecessary file reads and retries. Model routing offers another lever. use a capable tier where the task needs it, and evaluate smaller models for bounded work rather than assuming one tier fits every request.

The relevant unit is therefore the completed task rather than the individual model call. Track the context read, generated output, retries, and validation work together. A cheap call that sends the agent down a wrong path can cost more overall than a well-scoped request to a more capable model.

Where This Pays Off

Delegation pays off when the result is useful and cheaper to verify than to produce manually.

The strongest use cases have a bounded result that the developer can verify. An assistant can explain an unfamiliar stack trace, locate callers during a refactor, draft tests around existing behavior, or help a developer find the entry points in a new codebase. Each task provides evidence in the repository or test output that makes a proposed answer cheap to check.

Large, ambiguous design decisions are a weaker fit for delegation. An assistant can identify options and surface tradeoffs, but the repository rarely contains the full business context or risk appetite needed to choose among them. Use the tool to improve the analysis, then leave the accountable decision with the team that owns the consequences.

Where it earns trust

The common thread is inexpensive verification. A proposed explanation can be checked against the stack trace and source. A refactor can be checked with types, tests, and a focused diff. When correctness is slow or subjective to establish, generation speed provides much less advantage.

One thing this article leaves open is what happens at the merge gate. Which code an assistant may touch freely, what review agent-authored changes need, and how a team writes those answers down are the subject of Governing AI-Written Code.
