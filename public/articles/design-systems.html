Design Systems

How shared design decisions become reusable guidance and assets across products, platforms, designers, and developers.

Andreas Ögren
~16 min read
Last updated July 2026

One team chooses the spacing inside a card. Another team builds a similar card months later and chooses a different value. The same divergence appears in button states, form validation, navigation, and interface language. Each local choice may be reasonable but together they make one product family feel like several unrelated products.

The cost goes beyond appearance. Teams repeatedly work through the same interaction and accessibility challenges. They create several implementations that must be tested, fixed, and maintained separately. A shared answer reduces that repeated work and gives users familiar behavior as they move between products.

A design system is a governed set of reusable interface decisions. Guidance explains those decisions, while design assets, tokens, and production components make them available in the tools that product teams use. Reuse can reduce repeated work and preserve tested behavior, but the result still depends on which decisions the system covers and how teams apply them.

The focus here is how a design system is structured and how it connects design work to production software. Detailed UX methods and design-tool workflows are outside that scope.

The System and Its Artifacts

People use a design system through several artifacts, each serving a different part of product work.

A design system contains reusable design assets, production code, guidance, and tools that connect them. Some artifacts guide product work, while others provide assets that designers or applications can use directly. Organizations group and name the artifacts differently, so their responsibilities matter more than their local labels.

A brand guide defines the identity that an organization wants people to recognize. It records choices such as logo usage, brand colors, typography, imagery, and tone of voice, along with rules that preserve those choices across different media. Its audience includes marketing, communications, and product teams, as they all represent the same organization. For example, the guide may reserve clear space around a logo and show which backgrounds may sit behind it but rules for button states, form spacing, and inline validation are not part of brand identity. That is the responsibility of a style guide

A style guide turns broad identity and product decisions into rules for a particular kind of work. An interface style guide may define the type scale, grid, spacing, icon treatment, colors, and contrast requirements for digital products. A content style guide may define terminology, capitalization, grammar, and the structure of error messages. These rules help designers, writers, and developers make recurring choices consistently.

A UI kit is a collection of reusable interface assets for design work. It includes components such as buttons, form fields, navigation bars, and cards, along with their variants, states, shared styles, and variables. It may also include usage guidance to help designers apply those assets consistently. Broader visual, content, and accessibility rules can live in a style guide or the design system's documentation. The UI kit itself lives in a design tool such as Figma.

A component library provides implementations of interface components, often corresponding to components in a UI kit. Application developers then install or reference the library and import components such as buttons, dialogs, navigation, and form fields into an application. Each component implements a programming interface together with styling and runtime behavior. For example, a dialog component may manage focus, respond to the Escape key, provide accessible semantics, and support application-controlled state. Its corresponding UI-kit component shows the dialog’s visual structure, variants, and states in the design file. Designers and developers may maintain these artifacts separately, but their variants, states, and intended behavior must remain aligned.

A token package distributes named values such as colors and spacing across design tools and software platforms. A documentation site explains intended use, shows examples, records status, and points consumers to the available assets and code. These two artifacts connect the guidance, design assets, and production code without replacing them.

ArtifactWhat it providesWhat it does not provide alone
Brand guide Identity rules for areas such as logos, typography, imagery, and brand color Product interaction behavior or production components
Style guide Guidance for visual treatment, interface language, or both Reusable assets that enforce the guidance

The design system coordinates the relevant artifacts under shared decisions about the intended experience and supported scope. The required set depends on that scope. A native mobile system may have no web component package, while a system built around an external library may add local design assets, content guidance, and product-specific components. Those shared decisions and the relationships between the artifacts form the system.

Decisions at Different Scopes

The artifacts introduced above carry shared decisions that range from one named value to the structure of a recurring product flow.

Validation in a registration form shows how these scopes differ. The UI kit and component library can provide fields, error messages, an error summary, and a submit button. The token package can provide the colors and spacing used by those parts. A product team must still decide when to show each error, how to connect it to its field, where to move focus after a failed submission, and how to help the user recover. A design system can preserve decisions at each of these scopes.

Foundations define basic rules shared across the product family, including color roles, typography, spacing, layout, motion, iconography, and voice. A design token gives a selected foundation value a stable name that tools and platforms can use. In the form example, a semantic token can identify the color role for error text while themes provide different values for that role. The token package introduced above distributes those names and values. Foundations make separate controls use the same visual language. They do not define the validation sequence.

A component captures one reusable part of the interface. A form-field component can define the relationship between its label, input, hint, and error message together with its visual states. The UI kit contains the design representation of that component, and the component library contains its production implementation. The component handles the behavior and choices that belong to the field itself.

A pattern records a reusable solution to a user task that spans several components. A validation pattern can specify when errors appear, how the error summary links to fields, what happens to focus after submission, and how messages help the user correct the problem. The pattern may use form fields and an error-summary component, but its main responsibility is the complete recovery experience rather than either control in isolation.

A template preserves a recurring page or flow structure. If several products use the same multi-step application flow, a template can arrange its heading, progress indicator, form pattern, navigation, and review step. Product teams supply the domain-specific fields, content, and rules. A design system needs a template only when that larger structure repeats.

These categories describe the scope of a decision. Teams do not need to create them in order. Work on a pattern may reveal that several products need a new component, while a component may remain useful without belonging to a shared template.

Evidence and principles inform decisions at every scope. Research, usability testing, accessibility testing, and product feedback show where people encounter problems and whether a proposed solution helps. Principles state the qualities that the organization wants teams to preserve when evidence does not yet settle a choice. They provide reasons and evaluation criteria rather than another layer of reusable interface structure.

The documentation site connects the scopes. It can explain the role of a token, the contract of a component, the reasoning behind a pattern, and the products for which a template is suitable. This guidance lets teams reuse the decisions as well as the visible assets.

Token Architecture

Tokens separate a design decision's stable meaning from the value that expresses it and the formats that software platforms consume.

A token set can separate decisions into three tiers:

  1. A primitive token such as color.palette.blue.500 holds a raw value without assigning it an interface role.
  2. A semantic token such as color.action.primary names a purpose and references the primitive that currently expresses it.
  3. A component token such as button.background.primary narrows that decision to one component and can reference the semantic token.

A rebrand can move color.action.primary from color.palette.blue.500 to a primitive in the new palette. Components that use the semantic role then receive the new color without changing their own definitions. Unrelated roles can continue to use the original blue. The references preserve why each value is used instead of spreading the same raw value across several unrelated decisions.

Not every component property needs a component token. Use the semantic token directly when the component should always follow the shared role. Add a component token only when the component needs a stable override point or must vary independently.

A shared interchange format lets tools exchange token definitions without replacing every reference with a copied value. The Design Tokens Community Group publishes the Design Tokens Format Module, a JSON format for exchanging token data. In that format, an object with a $value property is a token. The optional $type property tells tools how to interpret the value; a token can also inherit its type from a referenced token or a parent group.

tokens.ts TS 
const tokens = {
  "color": {
    "palette": {
      "blue": {
        "500": {
          "$type": "color",
          "$value": {
            "colorSpace": "srgb",
            "components": [0, 0.4, 0.8],
            "hex": "#0066cc"
          }
        }
      }
    },
    "action": {
      "primary": {
        "$type": "color",
        "$value": "{color.palette.blue.500}"
      }
    }
  },
  "button": {
    "background": {
      "primary": {
        "$type": "color",
        "$value": "{color.action.primary}"
      }
    }
  }
} as const;

The primitive token stores the color value. The other two tokens use curly-braced references, which tools resolve to the complete value of the referenced token. A translation tool can then turn the canonical token set into the representation that each platform reads while preserving one set of names and relationships.

The CSS output does more than translate a name. A custom property declared once, close to the root, reaches every element that reads it with var() because custom properties inherit by default, the mechanism Cascade, Specificity, and Inheritance covers in full. That's what lets a rebrand touch one declaration instead of every component that consumes it.

Representations That Must Agree

Designers and developers use different artifacts, but users should encounter the same decisions when the product runs.

A Figma library gives designers reusable components, styles, and variables. Token files carry named values into formats such as CSS custom properties or native platform resources. Code packages provide production behavior. Documentation connects those assets to their intended use. These artifacts share contracts, but they are not interchangeable.

Machine-readable values can often be generated from a common token source. Components are different. A Figma button and a React button express corresponding variants and states, yet one cannot be generated reliably from the other. The code implementation must account for semantics, runtime state, responsive behavior, and application integration that a design component does not execute.

No single artifact can own every kind of decision. A token repository may own shared color values. Production code owns runtime behavior. Figma may show visual composition most clearly. Documentation explains when each option applies. Teams need to name the owner for each decision and check that the other representations still agree with it.

System Boundaries

A useful design system states which products, platforms, and decisions it serves. Anything broader becomes difficult to keep coherent.

Scope begins with the products that should feel related. A single brand may operate several product families with different interaction needs. The shared system can provide brand foundations and common controls while allowing each family to maintain domain patterns of its own. Forcing every specialized workflow into a universal core usually produces components with too many options and unclear ownership.

Platforms create another boundary. Web, iOS, and Android can share semantic token names, accessibility intent, and interaction principles. They should still respect their native conventions and platform capabilities. A system may therefore publish one conceptual component with several platform implementations rather than pretending that identical code is the goal.

Brands and themes require a similar separation between stable meaning and variable expression. Semantic roles such as primary action or critical text can remain consistent while their colors, typography, or motion values vary. A theme should change presentation without changing what a component means. A separate product pattern is a better fit when behavior or task structure also changes.

LayerSuitable contentsTypical reach
Core Shared principles, semantic tokens, basic controls, and baseline accessibility behavior Across the organization or product family
Platform Web or native implementations that preserve the core intent through platform conventions Across products on one platform
Product or domain Specialized components and patterns for a recurring business context Across related products or teams
Local Feature-specific composition that has not proved reusable elsewhere One product or feature

Layers also clarify contribution. A local component does not represent failure. It should move into a wider layer only after its problem and solution recur. Promotion expands the compatibility, documentation, testing, and maintenance obligations that the system accepts.

Accessibility and Content

Shared components can raise the quality baseline, but no design system can make every composition correct automatically.

Accessibility belongs throughout the system. Foundations can define approved foreground and background pairings. Components can preserve native semantics, keyboard operation, focus behavior, and motion preferences. Patterns can explain focus movement and error recovery across several components. Documentation can publish test results and known limitations.

A color token has no contrast ratio by itself. Contrast exists between a foreground and its background in a particular state. The system can provide tested semantic pairings and restrict unsafe combinations, but product teams still need to test the pages they assemble. The same limit applies elsewhere. An accessible dialog component cannot repair a workflow that hides essential information behind unnecessary dialogs.

Content is also part of the interface contract. Terminology, voice, labels, validation messages, and empty states affect whether people understand what happened and what to do next. A content guide can establish recurring conventions without forcing every situation into one reusable sentence. Product context, translation, and pluralization still shape the final wording.

Accessibility Governance explains why shared semantics prevent repeated repair without guaranteeing an accessible product. UX Principles explains the usability and perception decisions that the system turns into reusable conventions.

Adoption and Evolution

A technically sound library has little value when teams cannot find the right asset, understand it, or migrate to it safely.

The consumers of a design system are designers, developers, content specialists, and product teams. Treating them as users changes what the system team builds. Searchable documentation, clear status labels, migration guidance, support, and a predictable release process become part of the product rather than administrative work around it.

Adoption also depends on fit. Repeated local wrappers and overrides may reveal a missing variant, an unsuitable API, or a domain need that belongs in an extension layer. Usage data and direct feedback help separate those gaps from one-off preferences. Product experience should feed changes back into the shared system.

Changes have a wider blast radius than ordinary application code. A token name, default component behavior, Figma variant, or documented pattern can become a dependency across many teams. Ownership, contribution rules, versioning, deprecation, and migration therefore belong to the operating model. Design System Governance discusses those concerns in full.

Choosing the Scope

The right starting point depends on how many independent decisions need to remain aligned, not on whether an organization can build a large library.

One product team can often succeed with a component library, a small token set, and concise usage guidance. Direct communication supplies much of the missing coordination. Formal layers add little when the same people make the design and implementation decisions together.

Several independent teams working on related products create a stronger case for a design system. Shared patterns become valuable because teams cannot rely on informal knowledge. A layered system becomes useful when the organization also spans platforms, brands, or distinct product domains.

Adopting an established external system can avoid rebuilding common controls and accessibility behavior. The tradeoff is that its visual language, component APIs, and release schedule become architectural constraints. A local layer can add brand tokens and domain patterns, but extensive overrides may cost more than owning a narrower system directly.

The decisions that already repeat across products provide a practical starting point. A shared asset becomes useful when it removes recurring work or preserves a tested behavior. Governance becomes necessary when independent teams begin changing those assets on separate schedules. Design System Governance explains how that operating model can scale. Demonstrated reuse should determine what the system adds.
