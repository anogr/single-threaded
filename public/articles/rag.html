Retrieval-Augmented Generation

How retrieval supplies current or private evidence, and how corpus design and access control determine answer quality.

Andreas Ögren
~8 min read
Last updated July 2026

Many product features need answers grounded in material that was not reliably learned during model training. A support assistant should use the current documentation, while an internal helper may need private runbooks or policies. As How Large Language Models Work explains, that material must be supplied at request time when the application needs a current or verifiable answer.

Retrieval-augmented generation (RAG) searches a prepared corpus before generation and places selected passages into the model's context. The model can then answer from those passages instead of relying only on learned associations. This article treats RAG as a product architecture, covering the request path, the indexing pipeline, access control, ownership, and the diagnostic work behind answer quality.

When a Feature Needs Retrieval

Three alternatives, and each one runs out in a different place.

A small and trusted corpus can be placed directly into the prompt. That is often the simplest design because it avoids a search index and makes the supplied evidence easy to inspect. The approach becomes less attractive as the material grows. Every request pays to process the full corpus, and important passages may be used less reliably when buried in a long context. Retrieval becomes useful when selection is cheaper and more dependable than repeated inclusion.

Fine-tuning can teach behavior, terminology, and recurring output patterns, and it may also affect factual associations. It does not provide a source that the application can update, inspect, or cite at request time. A changing policy or document collection therefore belongs in context or retrieval rather than in a training cycle.

Live systems are the third case, and they already have their own pattern. An account balance or a ticket status is fetched at request time through a tool call, the connection MCP standardizes. Tools fit live records and actions. Retrieval fits document knowledge, the material too large for the window and too settled to fetch record by record.

The simplest viable path follows from these alternatives. Put a small, stable, permission-safe corpus directly in context. Use tools for live records and actions. Introduce retrieval when the document set is too large, too dynamic, or too selectively accessible to send as a whole.

The Retrieve-Augment-Generate Flow

The request path selects evidence first, then asks the generating model to answer from it.

The request begins by converting the query into an embedding when semantic search is used. The retriever searches the index for candidate chunks, applies any permission filters, and selects evidence that fits the context budget. The generating model receives those passages with the user's question and instructions about how to use or cite them. Grounding improves only when the selected passages support the answer; placement in the prompt is not proof by itself.

Hybrid search combines semantic retrieval with lexical matching. The lexical side preserves exact identifiers, names, and error codes that embedding similarity may rank poorly. Reranking then scores a smaller candidate set with a more expensive relevance model before the final passages are chosen. These components may use learned models of their own, but they belong to retrieval rather than answer generation.

The distinction between retrieval and generation is the key to operating the feature. Search determines which evidence is available; generation determines how that evidence becomes an answer. A stronger generating model cannot recover a passage that retrieval omitted, while perfect retrieval cannot force the model to represent the passage faithfully. Each layer needs its own evaluation.

The Corpus and the Indexing Pipeline

The retriever can only be as good as the library it searches.

Before indexing begins, someone must define the corpus. Drafts and superseded documents may need exclusion, while conflicting sources need an explicit order of authority. Ownership and version metadata should be preserved because retrieval cannot decide which policy wins merely by comparing semantic similarity. These are information-architecture decisions made before search quality can be measured.

A retriever that surfaces an obsolete document may be working exactly as configured. The index contained a close match and lacked a rule that made the newer source authoritative. Corpus curation is therefore ongoing editorial and data-governance work, with a named owner and a process for deletion, supersession, and conflict resolution.

The indexing pipeline responds when documents are added or changed. It parses source formats, normalizes useful metadata, and divides content into chunks that can be retrieved independently. Small chunks may match a precise phrase while losing the surrounding qualification. Large chunks preserve more context but can dilute relevance and consume the prompt budget. The pipeline embeds or otherwise indexes each chunk, then updates only the affected material when possible.

Freshness depends on the delay between a source change and a searchable index update. That delay should be measured like any other data-pipeline lag. Failures in parsing, metadata extraction, deletion, or synchronization can all leave the model answering from stale material even when generation works correctly.

Who Owns the Pipeline

Managed or self-hosted is less about where the vectors live than about whose opinions run the pipeline.

A managed retrieval service may provide parsing, chunking, embedding, indexing, and source synchronization rather than only vector storage. Its value lies in removing operational work and supplying sensible defaults. The tradeoff is control: a corpus that needs custom parsing, domain-specific chunk boundaries, or unusual permission logic may not fit the service's extension points.

Self-hosting means owning the complete pipeline, including parsing, chunking, synchronization, evaluation, and index operations. PostgreSQL extensions such as pgvector can add vector search to an existing database, while dedicated search systems offer different scaling and filtering characteristics. The index choice matters, but it is only one component of the operational commitment.

The decision axes follow from that framing. Operational load favors managed. Data locality can force self-hosting when the corpus cannot leave a compliance boundary. And control matters when the corpus demands opinions the vendor doesn't offer, such as domain-specific chunking for contracts or code. The general managed-versus-self-hosted tradeoff is one the cloud computing article already teaches. This is that tradeoff, applied to a search pipeline.

Access Control on Retrieved Content

The model will summarize whatever the retriever hands it.

A RAG feature is also a search interface over its corpus. If users have different permissions, the retrieval query must enforce those permissions before any passage enters model context. Metadata filters, tenant partitions, or separate indexes can implement that boundary. Filtering the final prose is too late because the unauthorized content has already crossed into the generation step and may influence the answer.

Retrieved content also carries the same trust problem this site keeps meeting in AI systems. A retrieved document is untrusted input placed in front of a model with authority to act on what it reads, the framing the MCP article teaches for tool descriptions. A poisoned document in the corpus, one containing instructions rather than information, is an injection vector that arrives through the front door of the feature. Corpus curation from the previous section is part of the security boundary, not only a quality concern.

Finding the Failure

A bad answer has three possible causes, and each one has a different fix.

A retrieval failure occurs when the right material exists but is absent from the selected passages. The cause may lie in query rewriting, indexing, filters, lexical and semantic weighting, chunk boundaries, or reranking. Prompt changes at the generation layer cannot restore evidence the model never received.

A corpus failure occurs when retrieval returns a relevant passage whose content is stale, incorrect, or contradicted by another indexed source. Search tuning cannot repair the source of truth. The fix belongs in curation, versioning, and the indexing pipeline.

A generation failure occurs when the supplied passages support an answer but the model ignores, distorts, or overextends them. Citations can make this failure look authoritative even when the cited text does not support the claim. Evaluation should therefore check both answer correctness and citation entailment.

Debugging a RAG feature is the discipline of asking which layer failed before touching anything. What came back from retrieval is loggable and inspectable, which makes the first two causes cheap to check and the habit worth building into the feature from the start.

The Decision Path

The choices in order, each one owed to a mechanism above.

Begin with the source and update pattern. A small, trusted corpus can go directly into context. Live records and actions belong behind tools. A larger document collection may justify RAG once the team can name its owner, authority rules, freshness target, and permission model. Managed services reduce pipeline work; self-hosting earns its cost when locality, control, or retrieval behavior requires it.

When answer quality falls, inspect the retrieved evidence before changing the generating model. Better source material, permission-aware search, chunking, and reranking often address failures that generation cannot. A RAG feature combines information retrieval with language generation, and its evaluation should preserve that boundary instead of reducing the whole system to one answer score.
