Retrieval-Augmented Generation

How retrieval supplies current or private evidence, and how corpus design and access control determine answer quality.

Andreas Ögren
~12 min read
Last updated July 2026

Many product features need answers based on current or private source material. A support assistant may need the latest documentation, and an internal helper may need company runbooks or policies. Model training cannot guarantee access to either. As How Large Language Models Work explains, the application must supply the relevant material with the request.

Retrieval-augmented generation (RAG) searches a prepared corpus before generation and places selected passages into the model's context. The passages give the model evidence for its answer. A production RAG feature needs a request-time search path and an indexing pipeline that follows document changes. It must preserve access rules and expose enough information to diagnose poor answers.

The term came from research that combined a language model's learned parameters with a separately indexed collection of passages. The retriever supplied factual evidence that could be replaced without training the generator again. Modern systems use many search engines and model architectures, but they keep this division between information retrieval and answer generation.

Choosing Retrieval

Current information can enter a request directly, through a tool call, or through retrieval from a larger corpus.

An application can place a small, trusted corpus directly into the prompt. Direct context needs no search index, and developers can inspect all the evidence sent to the model. As the corpus grows, every request must process more irrelevant text and useful passages become harder for the model to find. Retrieval solves this problem by selecting a smaller set of passages for each request.

Fine-tuning can teach behavior, terminology, and recurring output patterns. It may change some factual associations as well, but it does not create a source that the application can update or cite at request time. Changing policies and document collections should therefore be supplied through context or retrieval.

Live records and actions should use the system that owns them. An account balance should come from the account system, and a ticket update should go through the issue tracker's API. Model tools expose these operations, and MCP standardizes one way for a host to discover and invoke them. Retrieval can search structured or unstructured material before generation. This article concentrates on document collections because their indexing, authority, and access rules expose the full pipeline clearly.

The source determines the simplest request path. A small set of stable documents with uniform access rules can go directly into context. Live records and actions should use tools. A large or frequently changing document collection may need retrieval, especially when users have access to different parts of the corpus.

The Retrieve-Augment-Generate Flow

The request path selects evidence first, then asks the generating model to answer from it.

For semantic search, the request begins by converting the query into an embedding. The retriever applies the user's access constraints while searching the index for candidate chunks. It then selects evidence that fits the context budget. The generating model receives the passages with the user's question and instructions for using or citing them. The answer is grounded only when those passages support its claims.

Hybrid search combines semantic retrieval with lexical matching. Lexical matching can find exact identifiers or error codes that embedding similarity ranks poorly. Reranking often applies a more expensive relevance model to the smaller candidate set before choosing the final passages. Hybrid search and reranking may use learned models, but their job is to select evidence for the generating model.

Search supplies the evidence, and generation turns the evidence into an answer. If search omits a relevant passage, the generating model never sees it. Even with the right passage, the model may misstate its contents. Evaluation should therefore measure whether retrieval selected the right evidence and whether the answer represented that evidence faithfully.

A request may need query transformation before search. A follow-up such as Does that apply in Sweden? depends on earlier conversation, so the system may form a standalone search query that includes the subject. Expansion can add synonyms used in the corpus. Each transformation can improve recall, but it can shift the user's intent, so operators need to retain the original query and inspect the transformed form.

Context assembly decides how the selected chunks reach the generator. The application can preserve titles, section headings, document versions, and stable source identifiers around each passage. These boundaries help the model distinguish one source from another and let the interface attach citations to the evidence. An application-linked citation can show which source was presented. It does not show whether the source supports the associated claim.

The Corpus and the Indexing Pipeline

Retrieval quality depends on the documents and metadata available in the corpus.

Before indexing begins, the corpus owner must decide which documents belong in the collection. Drafts and superseded documents may need to be excluded. When sources conflict, metadata should identify their versions and order of authority because semantic similarity cannot decide which policy applies. Search quality can be measured only after these information-architecture decisions are defined.

A relevant search result may be obsolete. The index may contain a close match without metadata that identifies a newer source as authoritative. A named corpus owner must remove obsolete material, mark superseded sources, and resolve conflicts as the collection changes.

The indexing pipeline responds when documents are added or changed. It parses source formats, normalizes useful metadata, and divides content into chunks that can be retrieved independently. Small chunks may match a precise phrase while losing the surrounding qualification. Large chunks preserve more context but can dilute relevance and consume the prompt budget. The pipeline embeds or otherwise indexes each chunk, then updates only the affected material when possible.

Chunk boundaries can follow a fixed token count or the document's structure. Fixed windows are easy to reproduce and can overlap so a sentence near one boundary appears with nearby text. Structure-aware chunking keeps a heading with its paragraphs or a function with its documentation, but it needs a parser for each source format. Parent-child retrieval offers another compromise. Search ranks small child chunks, then context assembly returns a larger parent section around each match.

Every chunk needs a stable connection to its source document and version. Without that identity, an update may add new chunks while leaving the old ones searchable. Deletion needs equal care because removing a source from the content system does not automatically remove derived vectors or lexical entries. Incremental indexing should treat replacement and deletion as first-class events rather than append every parsed result.

Freshness depends on the delay between a source change and a searchable index update, so the delay should be measured like any other data-pipeline lag. A parsing or synchronization failure can leave the model answering from stale material. Incorrect metadata extraction or incomplete deletion creates this problem as well.

Pipeline Ownership

The deployment choice assigns responsibility for the whole indexing pipeline.

A managed retrieval service may prepare source documents and keep the resulting index synchronized. The provider operates this pipeline and supplies default behavior for parsing and chunking. A service may be unsuitable when the corpus or its permission rules require behavior the product cannot express.

An organization that self-hosts must parse and divide source documents and synchronize later changes. It must evaluate retrieval quality and operate the index. PostgreSQL extensions such as pgvector can add vector search to an existing database. Dedicated search systems provide different scaling and filtering behavior. The database choice covers only one component of the pipeline.

Teams can prefer a managed service when its processing boundary and retrieval behavior meet their requirements. Data-locality rules may exclude services that process content in an unapproved region. Domain-specific formats, such as contracts or source code, may require parsing or chunking that a managed product does not provide. The cloud computing article explains the broader managed and self-hosted tradeoff.

Access Control on Retrieved Content

The model can use any passage that the retriever places in its context.

A RAG feature is a search interface over its corpus. If users have different permissions, the retrieval query must enforce them before placing a passage in the model's context. Every derived chunk needs permission metadata, and retrieval must reflect later changes to the source document's access rules. A system can enforce this boundary with metadata filters, tenant partitions, or separate indexes. Once unauthorized content reaches the model, it may influence the answer even if the application later filters the generated prose.

Filtering after vector search can create both security and quality problems. If the retriever takes the ten nearest chunks and then removes nine unauthorized results, the generator receives only one candidate even when other authorized passages exist. A search engine that supports permission-aware prefiltering can find the nearest candidates within the allowed set. Separate indexes provide stronger isolation but cost more to build and synchronize when users share much of the corpus.

Retrieved content crosses a trust boundary because a poisoned document can contain instructions that the model mistakes for part of the application's request. A read-only assistant may then produce a manipulated answer. If the model can call tools or its output drives another system, the injected instruction can lead to actions. The MCP article explains this risk for tool descriptions. Corpus provenance and write access therefore affect security as well as answer quality.

Corpus, Retrieval, and Generation Failures

The core evidence path separates bad answers into three failure layers, and each layer needs a different fix.

A retrieval failure occurs when the right material exists but is absent from the selected passages. The source may have been indexed or divided into chunks poorly, or an overly restrictive access filter may have removed content the user was allowed to read. A poor query rewrite, unsuitable search weighting, or an ineffective reranker can prevent a suitable indexed passage from being selected. Prompt changes at the generation layer cannot restore evidence the model never received.

A corpus failure occurs when retrieval returns a relevant passage whose content is stale, incorrect, or contradicted by another indexed source. Corpus owners must correct or remove the source material and ensure the indexing pipeline publishes the change. Search tuning alone cannot fix inaccurate content.

A generation failure occurs when the supplied passages support an answer but the model ignores, distorts, or overextends them. Citations can make this failure look authoritative even when the cited text does not support the claim. Evaluation should therefore check the answer and whether each cited passage supports the claim attached to it.

These layers diagnose the core path from source material to answer. A correct evidence path can still be undermined by authorization mistakes, stale caches, orchestration errors, prompt injection, or a user interface that attaches the wrong citation. Those failures belong to the surrounding application and should be checked when the corpus, retrieved passages, and generated answer are each correct in isolation.

Debugging a RAG feature begins by identifying the layer that failed. Authorized operators need to see which query and index version were used, which filters were applied, and which passages were retrieved with their scores. The final prompt shows whether generation received the expected evidence. Sensitive passages and user queries require redaction and retention controls so this observability does not create another disclosure path.

Evaluating Retrieval and Answers

A useful evaluation checks the evidence path separately from the prose produced from it.

A retrieval test set pairs representative queries with passages judged relevant by people who understand the corpus. Recall at k measures the fraction of relevant passages found within the first k results. When each query has one required passage, it becomes the fraction of queries where that passage was found. Mean reciprocal rank gives more credit when the first relevant passage appears near the top. Normalized discounted cumulative gain can compare ranked lists when several passages have different degrees of relevance. The metric should match the product because a citation assistant may need several supporting passages while a lookup feature may need one exact answer.

Answer evaluation starts with correctness and faithfulness. Correctness compares the answer with the expected result. Faithfulness asks whether the retrieved evidence supports the claims even when outside knowledge would make them true. Citation checks can then verify that each source identifier resolves to the displayed passage and that the passage supports the nearby claim. These checks expose a generator that produces a correct-looking answer from unsupported associations.

The evaluation set should include ordinary queries, access boundaries, conflicting sources, stale versions, and questions the corpus cannot answer. Abstention is a required behavior for the last case. A system that always produces a fluent response may score well on answer style while failing the product's grounding promise.

Offline tests make retrieval changes comparable before release. Production signals such as reformulated queries, citation opens, user corrections, and support escalations show where the test set is incomplete. Clicks alone are ambiguous because users may open a citation out of interest or doubt. Sampled human review can connect these signals back to retrieval quality and answer support.

Choosing the Request Path

The source and its update pattern determine whether an application needs direct context, tools, or retrieval.

A small, trusted corpus can go directly into context. Live records and actions should use tools connected to their source systems. A larger document collection can use RAG after the team assigns a corpus owner and defines authority, freshness, and access rules. The team can then choose a managed service or self-hosted pipeline according to its locality and retrieval requirements.

When answer quality falls, operators should inspect the retrieved evidence before changing the generating model. They can then correct the corpus or tune retrieval at the layer where the failure occurred. The answer path needs an explicit response for insufficient or conflicting evidence. A feature that promises grounded answers should not silently substitute unsupported claims from the model's learned associations.

RAG combines information retrieval with language generation. Evaluating the two parts separately shows whether a poor answer began with missing evidence or with the model's use of the evidence.
