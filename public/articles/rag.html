Retrieval-Augmented Generation

How a product feature gives a model knowledge it wasn't trained on, and why the quality is decided in the retrieval layer.

Andreas Ögren
~9 min read
Last updated July 2026

Sooner or later a product grows a feature that has to answer from material the model was never trained on. A support assistant should answer from the current documentation, a policy search from this year's policies, an internal helper from the company's own runbooks. A model's built-in knowledge is frozen at its training cutoff, as covered in how large language models work, so the material has to reach the model at request time, through the context window.

Retrieval-augmented generation (RAG) is the standard shape of the answer. Before each response, the system searches a prepared index of the corpus, places the best-matching pieces into the context window, and has the model generate from them. This article treats RAG as a component a product consumes rather than a system to build from scratch. It covers when a feature needs retrieval at all, how the two pipelines behind it work, and where the quality and security of the result are decided.

When a Feature Needs Retrieval

Three alternatives, and each one runs out in a different place.

The blunt alternative is to put the whole corpus into the prompt. For a small, stable corpus this works, and it should be the default until it stops working. It stops for two reasons the LLM article covers. Every request pays for every token, so a large corpus in every prompt shows up directly on the bill and the latency. And material buried in the middle of a very long prompt is weighed less dependably than material near its edges, the lost-in-the-middle effect, so a bigger prompt is not a proportionally better-informed one.

Fine-tuning looks like the second alternative and rarely is, for knowledge. Further training changes how a model behaves, its tone, format discipline, and domain fluency. Facts baked in this way inherit the same staleness as pretraining, because a corpus that changes daily would need retraining daily. Fine-tuning earns its keep for behavior. It is the wrong tool for keeping answers current.

Live systems are the third case, and they already have their own pattern. An account balance or a ticket status is fetched at request time through a tool call, the connection MCP standardizes. Tools fit live records and actions. Retrieval fits document knowledge, the material too large for the window and too settled to fetch record by record.

The honest default falls out of the first alternative. A corpus that fits comfortably in the context window doesn't need RAG yet, and the pipeline below is complexity that can wait until the corpus outgrows the prompt.

The Retrieve-Augment-Generate Flow

One request, five steps, and only the last one involves the language model.

The request path is short. The user's query is turned into an embedding, a vector that positions its meaning so that similar meanings sit nearby. The index is searched for the chunks of the corpus closest to that position. The best candidates are selected, placed into the context window alongside the user's question, and the model generates an answer grounded in what it was handed, citing the pieces it used.

Production systems rarely trust semantic similarity alone. Hybrid search runs a conventional keyword match alongside the vector search and merges the results, since exact identifiers, product names, and error codes are precisely what similarity-by-meaning is worst at. Reranking adds a second, more careful pass that re-scores the merged candidates and keeps the handful that will fit the context budget. Both are quality levers inside the retrieval step, and neither involves the generating model.

That is the pattern in miniature. The model appears once, at the end, doing the one thing it is good at, and everything that determines whether it was handed the right material happens earlier, in ordinary search infrastructure. RAG is a search problem wearing an AI costume, and the rest of this article is mostly about the search problem.

The Corpus and the Indexing Pipeline

The retriever can only be as good as the library it searches.

Before any pipeline runs, someone has to decide what the corpus is, and this is the half that gets skipped. Which documents belong in it, and which get excluded, such as drafts, superseded versions, or another team's half-finished notes? Which source counts as authoritative when two documents disagree, and which version wins when both are still indexed? These are information-architecture questions, and no part of the pipeline downstream can answer them.

They matter because a retriever that surfaces an obsolete document is working as designed. The search found the closest match, and the closest match was wrong, because the corpus contained it. Production teams repeatedly discover that retrieval quality is fine while the corpus disagrees with itself. Curation is therefore a standing editorial job with a named owner, not a one-time task on a launch checklist.

The mechanical half is a pipeline that runs whenever documents change. Content is ingested and parsed out of whatever formats it lives in. It is then split into chunks, the passages that will be individually embedded and retrieved. Chunking quietly dominates retrieval quality, because the chunk is both the unit of search and the unit the model eventually reads. Cut too small, a chunk matches well but arrives without its surrounding meaning. Cut too large, the match gets diluted and the chunk crowds the context budget. Each chunk is embedded and written to the index, and a document change re-runs the whole sequence for the content it touched.

Freshness, then, is a property of this pipeline rather than of any model. The gap between a document changing and its chunks re-indexing is the feature's staleness, and it is measured and tuned like any other data pipeline lag. Nothing in this section touched a model, which is the central point. The half of RAG that decides quality is data engineering.

Who Owns the Pipeline

Managed or self-hosted is less about where the vectors live than about whose opinions run the pipeline.

A managed retrieval service, the kind every major cloud provider now offers, does not merely store vectors. It owns most of the previous section. Parsing, chunking, embedding, indexing, and synchronization arrive as the vendor's opinions, tuned to work acceptably across most corpora. That is most of the value, since the undifferentiated pipeline work disappears. It is also most of the lock-in, since those opinions are exactly what a team cannot change when its material needs different treatment.

Self-hosting means owning every stage. The index itself is the easy part. pgvector adds vector search to a database most stacks already run, and dedicated vector databases serve heavier retrieval loads. The real commitment is operating the pipeline around the index, the parsing, chunking, and re-indexing machinery that the managed service would otherwise absorb.

The decision axes follow from that framing. Operational load favors managed. Data locality can force self-hosting when the corpus cannot leave a compliance boundary. And control matters when the corpus demands opinions the vendor doesn't offer, such as domain-specific chunking for contracts or code. The general managed-versus-self-hosted tradeoff is one the cloud computing article already teaches. This is that tradeoff, applied to a search pipeline.

Access Control on Retrieved Content

The model will summarize whatever the retriever hands it.

A RAG feature quietly becomes a search engine over everything in its corpus, and search engines leak whatever they can see. If the corpus contains documents some users must not read, the permission check has to happen inside the retrieval query, as per-user metadata filtering and tenant isolation at the index. Filtering after retrieval risks the content having already entered the context window. Instructing the model to withhold what a user shouldn't see is not access control at all, since the model has no reliable notion of should. The rule is short. Enforce permissions where the search runs, never where the answer is written.

Retrieved content also carries the same trust problem this site keeps meeting in AI systems. A retrieved document is untrusted input placed in front of a model with authority to act on what it reads, the framing the MCP article teaches for tool descriptions. A poisoned document in the corpus, one containing instructions rather than information, is an injection vector that arrives through the front door of the feature. Corpus curation from the previous section is part of the security boundary, not only a quality concern.

Finding the Failure

A bad answer has three possible causes, and each one has a different fix.

The first candidate is a retrieval failure. The right material exists in the corpus and never came back from the search, so the model answered without it. No prompt wording fixes this, because the model cannot cite what it never saw. The fix lives in the retrieval step, in the query handling, the hybrid-search balance, or the chunking that made the right passage unmatchable.

The second is a corpus failure. The right chunk came back, and its content is wrong, stale, or contradicted by another document in the index. The retriever and the model both did their jobs. The fix is the curation work from the corpus section, and mistaking this failure for a retrieval problem sends teams tuning search parameters that were never broken.

The third is a generation failure. Good chunks arrived and the answer ignores or misstates them. Its characteristic form is hallucination with citations, a fluent answer pointing at retrieved documents that don't support it, wearing the borrowed credibility of its sources. The fluency-is-not-certainty lesson applies with extra force here, because the citations make the fluency look verified.

Debugging a RAG feature is the discipline of asking which layer failed before touching anything. What came back from retrieval is loggable and inspectable, which makes the first two causes cheap to check and the habit worth building into the feature from the start.

The Decision Path

The choices in order, each one owed to a mechanism above.

A corpus that fits comfortably in the context window goes into the context window, and RAG waits. A feature that needs live records or actions gets tools through MCP rather than an index. Document knowledge at scale gets RAG, managed by default, self-hosted when data locality or the pipeline's opinions demand it. Permissions go into the retrieval query on day one, because retrofitting access control into an index that never recorded ownership is a rebuild. And the corpus gets a named owner, because curation is the maintenance work that outlives the launch.

The through-line for all of it is where the improvements come from. Teams reaching for a better model to fix a RAG feature are usually tuning the one component that was already fine. Better search, cleaner chunks, and a corpus that agrees with itself move these features far more often, because RAG is not an AI architecture. It is an information-retrieval architecture with a language model attached.
