RESTful API Design

How REST constrains an API, how to model resources, and when another interaction style fits better.

Andreas Ögren
~22 min read
Last updated July 2026

REST has shaped the conventions of many HTTP APIs, even when those APIs do not implement the full architectural style. Understanding its constraints makes it easier to separate REST itself from familiar URL and method conventions. It also makes the limits of the resource model clearer.

This article assumes familiarity with HTTP fundamentals. For a grounding in methods, status codes, headers, caching, cookies, and CORS, the HTTP article covers those first.

Background

REST was defined in a doctoral dissertation. Understanding where it came from explains why it looks the way it does.

Roy Fielding defined REST (Representational State Transfer) in his 2000 doctoral dissertation at the University of California, Irvine. An architectural style coordinates constraints on components and their interactions. REST applies such constraints to the connectors and data of a distributed hypermedia system. It is neither a protocol nor an API specification.

REST does not require HTTP, but the web is its defining implementation and most REST APIs use HTTP. HTTP supplies a uniform method vocabulary, representation metadata, status codes, and caching semantics. Following those semantics is necessary for a REST API, although it does not satisfy every REST constraint by itself.

The Richardson Maturity Model

The Richardson Maturity Model describes a progression in how an HTTP API uses resources, methods, and hypermedia. It is a useful teaching model rather than part of Fielding's REST definition.

Level 0
HTTP as a Tunnel

One endpoint receives all operations, commonly through POST. HTTP acts as a transport envelope while the request body carries the application operation.

Level 1
Resources

Multiple resources identified by different URLs, but a single HTTP method (usually POST) for all operations. The domain is decomposed into nouns but the verb layer is ignored.

Level 2
HTTP Verbs

Resource URLs are combined with HTTP method and status semantics. This is the style commonly described as a REST API, even though it stops short of REST's hypermedia constraint.

Level 3
Hypermedia Controls

Representations include links and controls for the available transitions. Clients follow those controls instead of constructing every interaction from out-of-band URL knowledge.

Scope of this article

This article concentrates on the resource and HTTP conventions at Level 2 because they dominate everyday API design. The architectural constraints section still explains hypermedia, since an API without it does not implement REST in Fielding's full sense.

REST Compared to Other API Designs

The resource model works well for many APIs, but operations, queries, and tightly coupled applications can favor other styles.

Understanding the alternatives makes it easier to choose the right tool and to recognize where REST's model imposes unnecessary friction.

REST vs. RPC (Remote Procedure Call)

Remote procedure call (RPC) APIs expose operations rather than a uniform resource interface. An endpoint might accept POST /cancelOrder with {"orderId": 42} in the body. gRPC is one RPC framework. It defines services with Protocol Buffers and normally carries calls over HTTP/2.

RPC fits domains where commands are more natural than resource manipulation, including workflow operations and internal service calls. Generated contracts can make calls predictable for consumers, especially with gRPC. The cost is that operation names and behavior come from the service contract rather than from a shared HTTP vocabulary.

REST vs. GraphQL

GraphQL is a query language and runtime developed by Meta and open-sourced in 2015. Rather than multiple resource-specific endpoints, a GraphQL API exposes a single endpoint through which clients issue typed queries and mutations.

GraphQL Strengths
Client-specified shape

The client selects the fields and related objects needed for a view. This can reduce unnecessary data and avoid several resource requests. A typed schema supports validation and client tooling.

GraphQL Tradeoffs
Single endpoint

Operations commonly share one URL, so ordinary URL-based HTTP caching is less direct. Servers must also control query cost and field-level authorization. Schema introspection is useful tooling, but access to it may need its own policy.

GraphQL fits well when the frontend has highly variable data requirements, particularly with multiple clients (web, mobile, third-party) that need different shapes of the same data.

REST vs. tRPC

tRPC is a TypeScript-first framework that infers a client contract directly from server procedures. It avoids a separate schema language when both sides can share TypeScript types during development.

The approach suits applications whose client and server evolve together in one TypeScript codebase. A language-neutral contract such as OpenAPI or Protocol Buffers is easier to consume across organizational and language boundaries.

A resource-oriented HTTP API is a strong option when many independent consumers need familiar semantics and ordinary HTTP caching. GraphQL favors client-selected data graphs. gRPC favors generated contracts and efficient internal calls, while tRPC favors close coupling inside a TypeScript application. The consumer boundary and interaction shape should decide among them.

Architectural Constraints

REST combines six constraints whose benefits and tradeoffs emerge when they are applied as a system.

Uniform Interface

The uniform interface distinguishes REST from styles built around service-specific operations. Although REST prescribes neither HTTP nor a particular URL shape, every REST interface follows four further constraints.

  • Identification of resources: A resource is identified in a representation, commonly through a URI on the web. The underlying resource remains distinct from any JSON, HTML, or image representation transferred to a client.
  • Manipulation of resources through representations: Clients interact with resources by exchanging representations. A client that holds a representation of a resource has enough information to modify or delete it.
  • Self-descriptive messages: A recipient can understand how to process a message from its method, metadata, media type, and representation semantics.
  • Hypermedia as the engine of application state (HATEOAS): Representations carry links and controls that tell the client which transitions are available next.

In an HTTP API, the uniform interface leads naturally to URLs that identify resources while methods carry shared request semantics. The familiar “nouns in URLs” rule is a design heuristic derived from that separation.

Statelessness

Each request contains the context needed to understand it without relying on an earlier interaction. Any compatible server component with access to the resource can process that request, so routing does not have to preserve an application session on one instance. A monitor can also understand an interaction from the request itself.

The constraint is often misstated as “the server stores no state.” Servers can store resource state. What they cannot do is rely on hidden session context from earlier interactions to understand the current request. Application state belongs in the client's representation of the interaction and must accompany each request when the server needs it.

Client–Server

The client and server are separate concerns with a well-defined interface between them. The server manages resources and business logic, while the client manages the user interface and user state, and neither knows the internal implementation of the other. This separation means the client and server can evolve independently as long as the interface contract is maintained.

Layered System

A client sees only the component it is connected to and cannot know whether another layer sits beyond it. That boundary allows caches, gateways, and reverse proxies to be inserted without changing the client-facing interface.

Cacheability

REST requires response data to be labeled, implicitly or explicitly, as cacheable or non-cacheable. HTTP expresses that policy through fields such as Cache-Control, ETag, and Last-Modified. A valid cached response can remove a network round trip and reduce work at the origin.

User-specific responses need a policy that prevents one person's data from being reused for another. Marking a response private limits storage to private caches, while no-store prevents storage when the content is too sensitive to retain. Public responses can use shared caches when their cache keys account for every request property that changes the representation.

Code on Demand Optional

Servers can extend client functionality by transferring executable code. JavaScript in a browser is the canonical example. This constraint is optional and rarely relevant in API design contexts.

Resource Modeling

Resource boundaries shape URLs, representations, and the operations that an API can express cleanly.

Resources Are Nouns, Not Verbs

A resource-oriented URL identifies a thing, while the HTTP method expresses what the client wants to do with it.

# Correct
GET /orders/42
POST /orders
DELETE /orders/42
# Incorrect — verbs in URLs
GET /getOrder?id=42
POST /createOrder
POST /deleteOrder

A verb in a URL is a signal to reconsider the resource model. Often there is an implicit noun: a cancellation is a resource, a report is a resource, a session is a resource.

URL Structure and Hierarchy

URL hierarchy should reflect containment or ownership relationships between resources. A resource nested under another is a sub-resource.

/users/9/orders # Orders belonging to user 9
/orders/42/items # Line items within order 42
/orders/42/items/7 # A specific line item

Deep nesting produces long URLs and couples resource identity to one access path. Nest only while the parent relationship adds meaning, then give independently addressable resources their own canonical URL. Two levels is a useful warning threshold rather than a protocol rule.

Identifiers

Resource identifiers should remain stable for as long as clients may refer to them. Opaque identifiers keep storage choices out of the contract. UUIDs work well when several systems create records independently, while sequential identifiers can be simpler and smaller. Neither choice replaces authorization. Guessing another identifier must not grant a client access.

/orders/a3f9b2c1-4d5e-6f7a-8b9c-0d1e2f3a4b5c # Preferred
/orders/42 # Acceptable, but exposes sequence

Granularity

Overly coarse resources return unnecessary data on every request. Overly fine resources require many requests to assemble a useful view. The right granularity depends on the access patterns of the clients. If every view that shows an order also shows the customer name, returning the customer name inline in the order response is reasonable. For public APIs, sparse fieldsets (?fields=id,name,status) are a useful middle ground.

HTTP Semantics

An HTTP-based REST API depends on the semantics of HTTP methods, status codes, fields, and caching.

For a full treatment of HTTP methods, status codes, headers, caching, and CORS, the HTTP article covers all of these in depth. This section focuses on how HTTP semantics apply specifically in the context of REST API design.

Methods and CRUD

Create, read, update, and delete (CRUD) provide a convenient first mapping to HTTP methods, but HTTP semantics are richer than database operations. GET is both safe and idempotent. PUT and DELETE remain idempotent even though they can change state, while POST makes neither guarantee. Those properties guide retry and caching behavior beyond the application handler.

A repeated DELETE may return 204 because the desired state already exists, or 404 because the resource is no longer present. Either contract can work when the API documents and applies it consistently.

PATCH formats

PATCH semantics require that the request body describe changes to apply, not the full resource. Two standard formats cover most cases.

JSON Merge Patch (RFC 7396) applies an object-shaped overlay. Present fields replace existing values, absent fields remain unchanged, and null removes a field. Requests use Content-Type: application/merge-patch+json.

PATCH /orders/42 JSON Merge Patch 
// Only "status" changes. All other fields are untouched.
{ "status": "cancelled", "cancellation_reason": "Customer request" }

Merge Patch is easy to read, but it cannot distinguish assigning null from removing a field. JSON Patch (RFC 6902) represents changes as an ordered array of operations. Its test operation can make a later change conditional on an expected value. JSON Patch requests use application/json-patch+json and suit cases that Merge Patch cannot express.

Status codes in REST

Use the status code that best describes the HTTP result, then put domain-specific detail in the response body. The following codes recur in resource APIs.

Error response format

Inconsistent error formats force clients to maintain several parsing paths. RFC 9457 defines Problem Details for HTTP APIs, a shared object format served as application/problem+json.

JSON 
{
  "type": "https://example.com/problems/insufficient-stock",
  "title": "Insufficient stock",
  "status": 422,
  "detail": "Requested quantity 5 exceeds available stock of 2 for item SKU-9981.",
  "instance": "/orders/42/items/7"
}

The type URI identifies the error kind and should resolve to documentation. The title is a stable human-readable summary. The detail is specific to this occurrence. An errors array is a common extension for field-level validation failures.

Rate limiting headers

Rate-limit information can help a client slow down before it receives a 429 response. Existing APIs use several incompatible X-RateLimit-* conventions. An active IETF draft instead defines structured RateLimit and RateLimit-Policy fields, but it remains a work in progress. A 429 response may include Retry-After to make the wait explicit.

Optimistic Concurrency

ETags let multiple clients modify the same resource safely, without locking.

Concurrent updates can overwrite one another when the server accepts the last write unconditionally. With optimistic concurrency, the server returns a strong ETag for the resource representation. A client repeats that value in If-Match when modifying the resource. If the representation has changed, the strong comparison fails and the server returns 412 Precondition Failed.

HTTP 
# 1. Fetch — server returns a version token
GET /orders/42
→ 200 OK
ETag: "v3"

# 2. Update — send the token in If-Match
PATCH /orders/42
If-Match: "v3"
→ 200 OK  (token matched, update applied)
ETag: "v4"

# If another client updated first, the token no longer matches
PATCH /orders/42
If-Match: "v3"
→ 412 Precondition Failed

After a 412 response, the client can fetch the latest representation and ask the user to reconcile the conflict. If-Match: * means that the operation should proceed only if a current representation exists. The ETag remains opaque because its construction belongs to the server.

Idempotency Keys

POST is not idempotent by definition. Idempotency keys provide that property anyway.

When a connection drops before a POST response arrives, the client cannot tell whether the operation completed. An immediate retry might create a duplicate. An idempotency key makes the logical operation recognizable across attempts. The client generates the key before its first request, and a server that sees the same key again returns the recorded outcome without repeating completed work.

HTTP 
POST /payments
Idempotency-Key: "a3f9b2c1-4d5e-6f7a-8b9c-0d1e2f3a4b5c"
Content-Type: application/json

{ "amount": 9900, "currency": "SEK", "card_token": "tok_xyz" }

The server retains enough information to recognize the key for a documented period. A completed retry with the same key and operation receives the original outcome without executing the operation again. Idempotency-Key is a widely implemented convention and the subject of an IETF draft, but it is not yet an HTTP standard. It is useful wherever duplicate execution would be harmful, including payment and order creation.

Keys must be client-generated

Generate a fresh UUID per logical attempt before sending the request, not from a prior response. If the key comes from the server, the round-trip to fetch it reintroduces the same network-failure problem idempotency keys are meant to solve.

Versioning

No versioning strategy is universally correct. The three common approaches each make different tradeoffs.

URL Path Versioning

https://api.example.com/v2/orders

A path version is visible in URLs, logs, and routing rules. It is also easy to exercise from a browser or command-line client. The tradeoff is that two representations of the same conceptual resource receive different identifiers. Despite that impurity, path versioning is easy for consumers to understand.

Request Header Versioning

API-Version: 2

Header versioning keeps one canonical resource URL. Logs and routing rules must capture the header explicitly, and a browser address bar cannot exercise the version on its own.

Content Negotiation

Accept: application/vnd.example.api+json; version=2

This approach treats a version as a choice of representation and negotiates it through Accept. The URL remains stable, but logs, browser testing, cache configuration, and routing all need to account for the header.

Versioning Considerations

  • Define whether a version covers the whole API or a smaller capability, then apply that scope consistently.
  • Give consumers a documented migration period before retiring a version.
  • Communicate deprecation timelines via response headers (Deprecation, Sunset) and documentation.
  • Treat additive fields as compatible only when the client contract requires consumers to tolerate unknown fields and enum values.

Breaking vs non-breaking changes

A breaking change causes a correctly-implemented existing client to fail or produce wrong results. Non-breaking changes can ship without a version bump, provided clients are written defensively.

ChangeBreaking?Notes
Add optional response fieldNoClients must ignore unknown fields.
Add optional request parameterNoExisting clients omit it; behaviour unchanged.
Relax validation (accept more values)NoPreviously valid requests still succeed.
Remove a response fieldYesClients reading that field break.
Remove or rename an endpointYesPublish a replacement and keep a documented migration window.
Add a required request fieldYesExisting clients that omit it get 400.
Change a field's typeYesEven if the value is semantically equivalent (e.g. number → string).
Narrow validation (reject previously valid values)YesPreviously valid requests now fail.
Change a status codeYesClients checking for exact codes break.
Add a new enum valueMaybeBreaking if clients switch exhaustively on the enum; safe if they handle unknown values gracefully.

OpenAPI

OpenAPI gives HTTP API contracts a machine-readable form that documentation, validation, and code-generation tools can share.

OpenAPI, which grew from the Swagger specification, describes HTTP APIs in JSON or YAML. A document can define paths, parameters, request and response schemas, security schemes, and expected status codes. OpenAPI 3.2, published in September 2025, is the latest specification line. OpenAPI 3.1 remains common in tooling and uses the JSON Schema 2020-12 vocabulary as its default base.

openapi.yaml OpenAPI 3.1 
openapi: "3.1.0"
info:
  title: Orders API
  version: "2"
paths:
  /orders/{id}:
    get:
      summary: Retrieve an order
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string, format: uuid }
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Order" }
        "404": { description: Not found }

Design-first vs code-first

In a design-first workflow, the OpenAPI document is reviewed before implementation. Teams can agree on the contract, generate mocks, and detect breaking changes in an ordinary diff. This works well when consumers need to coordinate before the server is ready.

In a code-first workflow, tooling derives the document from implementation metadata or types. That reduces duplicate authoring, but only if the generated contract is checked for omissions and unintended changes. The better workflow is the one that keeps the reviewed contract authoritative in the team's delivery process.

TypeScript client generation

Tools such as Hey API generate TypeScript clients from an OpenAPI document. Generated parameter and response types reduce hand-written contract duplication, but the result is only as accurate as the source document.

Pagination, Filtering, and Sorting

Collections with unbounded or growing membership need pagination so response cost remains controlled.

Pagination

Offset pagination uses a numeric offset and limit:

GET /orders?offset=40&limit=20

Offset pagination is easy to understand and supports jumping to a numbered page. Concurrent inserts or deletions can shift later offsets, causing a sequential client to skip or repeat records. Large offsets may also become expensive, depending on the data store and query plan.

Cursor pagination uses an opaque pointer to the last seen item:

GET /orders?cursor=eyJpZCI6NDJ9&limit=20

Cursor pagination continues from a position in a stable ordering. With a unique tie-breaker and a suitable index, it avoids the shifting-page problem and can keep query cost consistent. Clients usually move sequentially rather than jumping to an arbitrary page. The cursor should remain opaque so its encoding can change without breaking consumers.

Pagination metadata

Return the next cursor or offset and indicate whether another page is available. A total count is useful only when the product needs it and the server can compute it economically. Pagination controls may live in a response envelope or in standardized Link fields.

Filtering

Filtering is expressed via query parameters. Consistency within an API matters more than any particular syntax:

GET /orders?status=pending
GET /orders?created_after=2024-01-01&created_before=2024-06-30
GET /orders?status=pending,processing # multiple values
GET /orders?total_gte=100&total_lte=500 # range

The contract should say how unknown filters are handled. Returning 400 Bad Request exposes misspellings and unsupported fields instead of silently returning a broader result than the caller expected.

Sorting

Two conventions are common:

GET /orders?sort=created_at&order=desc # explicit direction parameter
GET /orders?sort=-created_at # prefix: - for desc, no prefix for asc
GET /orders?sort=-created_at,id # multi-field with prefix notation

Allowlist sortable fields and support them with indexes where the data store requires them. An unrestricted sort parameter can otherwise expose unexpectedly expensive query plans.

Handling Non-Resource Operations

REST's resource model maps cleanly to CRUD operations but produces friction for action-oriented, bulk, and asynchronous operations.

State Transitions

Operations that transition a resource from one state to another can be modeled as either a direct update or a sub-resource.

Direct update: the client sends the target state:

HTTP 
PATCH /orders/42
Content-Type: application/json

{ "status": "cancelled" }

Sub-resource: the transition itself is treated as a resource:

HTTP 
POST /orders/42/cancellations

The sub-resource approach is more expressive when transitions have their own attributes (a cancellation reason, a timestamp) or when a history of transitions needs to be recorded.

Bulk Operations

No single HTTP convention governs bulk operations. APIs commonly use either a batch resource containing several operations or a collection-level request whose filter selects the affected resources.

HTTP 
POST /orders/batch
Content-Type: application/json

{
  "operations": [
    { "method": "DELETE", "id": "42" },
    { "method": "DELETE", "id": "43" }
  ]
}

Clarify whether operations are atomic (all succeed or all fail) or non-atomic (partial success is possible), and what the response format looks like for partial failures.

Asynchronous Operations

An operation that continues after the response can return 202 Accepted and identify a status resource that the client can poll.

HTTP 
# Client creates the report
POST /reports
→ 202 Accepted
   Location: /reports/jobs/f3a9b2c1

# Client polls the job resource
GET /reports/jobs/f3a9b2c1
→ 200 OK
   { "status": "processing", "progress": 0.42 }

GET /reports/jobs/f3a9b2c1
→ 200 OK
   { "status": "complete", "result": { "href": "/reports/2024-q4" } }

When the job is complete, the response points to the result resource. This pattern is REST-native and works without webhooks or real-time infrastructure.

Search and Computation

For simple search, a GET with query parameters is idiomatic and allows caching:

GET /products?q=running+shoes&category=footwear

For complex queries (full-text search with ranking, facets, and multiple compound filters) request bodies are more practical. A POST to a dedicated endpoint is acceptable:

HTTP 
POST /products/search
Content-Type: application/json

{
  "query": "running shoes",
  "filters": { "category": "footwear", "price_lte": 150 },
  "facets": ["brand", "size"],
  "sort": "-relevance"
}

POST responses are cacheable only under explicit HTTP conditions, and most general-purpose caches do not implement that path. GET remains the interoperable choice for queries that fit comfortably in a URL. The HTTP QUERY method, standardized in June 2026, gives body-bearing queries safe and cacheable semantics. An API must still verify support throughout its request path before adopting it.

Real-Time Updates

REST describes request-driven interactions rather than an unsolicited event channel. Applications that need updates initiated by another party usually add one of the following mechanisms.

  • Server-Sent Events (SSE) stream events from server to browser over HTTP. The browser's EventSource API reconnects automatically, which suits feeds, notifications, and progress updates.
  • WebSockets provide a bidirectional message channel for interactions such as collaborative editing, chat, and other frequent two-way communication.
  • Webhooks deliver events to a URL controlled by another system. They suit asynchronous integration and require the verification described below.

Polling (repeated GET requests) is a valid fallback when real-time infrastructure is not available, particularly with conditional requests (If-None-Match) to minimize response bodies on unchanged resources.

Webhook security

A webhook receiver accepts requests initiated by another system, often at a public endpoint. Network location alone does not prove who sent a request. Production integrations therefore need sender verification and duplicate handling.

Payload signature verification establishes that a request came from a party holding the expected credential. Many providers sign the raw body with a shared secret and place the result in a provider-specific header. The receiver must follow the documented algorithm, timestamp rules, and encoding exactly. A constant-time comparison avoids leaking information about partial matches.

verify-webhook.ts TypeScript 
import { createHmac, timingSafeEqual } from 'node:crypto';

function verifyWebhook(
  rawBody: Buffer,
  signature: string,   // from the provider's signature header
  secret: string
): boolean {
  const expected = createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');
  const actualBytes = Buffer.from(signature, 'hex');
  const expectedBytes = Buffer.from(expected, 'hex');
  return actualBytes.length === expectedBytes.length
    && timingSafeEqual(actualBytes, expectedBytes);
}

Event idempotency protects the receiver when delivery is repeated. The sender should provide a stable event ID, which the receiver records before applying the event's effects. A later delivery with the same ID can then be acknowledged without repeating the work.

Always verify before acting

Acknowledge the webhook with a successful status only after verification and durable acceptance, such as committing the event to a queue. Perform slower domain work asynchronously when the provider's delivery timeout is shorter than that work. Otherwise a premature success can lose an event that was never safely recorded.
