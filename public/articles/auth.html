Authentication

How a login turns into a credential that's verified on every subsequent request, using sessions, tokens, passkeys, and API keys.

Andreas Ögren
~15 min read
Last updated July 2026

A successful login has to produce something the client can present on later requests. The server may keep the authentication state and give the client a reference to it. It may instead issue a credential that a service can validate from the credential's claims.

Those choices lead to sessions and tokens. The sections below explain their tradeoffs before turning to JWT validation, browser storage, passkeys, and credentials for machine clients.

Authentication vs Authorization

Two concepts that are frequently conflated and almost as frequently implemented incorrectly.

Identification states an identity, usually through a username or email address. It answers the question, "Who do you claim to be?"

Authentication verifies that claim with one or more credentials. These credentials are grouped into authentication factors: something the user knows, something they possess, or something inherent to them. Passwords and PINs belong to the first group. Phones and security keys belong to the second, while fingerprints and facial characteristics belong to the third. Multi-factor authentication requires evidence from more than one group.

Authorization determines what an authenticated identity may do. A valid login establishes who is making the request, but it does not grant access to every resource. The application must still decide whether that identity may perform the requested operation.

Conflating the two is a common source of access control vulnerabilities. An application that checks "is this user logged in?" for every request but not "does this user own this resource?" has authenticated correctly but failed at authorization. The security principles article covers broken access control in more depth.

Basic Authentication

The simplest authentication scheme is built into HTTP itself.

HTTP Basic Authentication sends a username and password with every request, base64-encoded inside an Authorization header. The scheme defines no separate session credential or issued token. The server receives the same reusable credentials on each request.

HTTP 
GET /reports
Authorization: Basic am9objpodW50ZXIy
# decodes to "john:hunter2"
Base64 is not encryption

Anyone who intercepts a Basic Auth header can decode it in one step and read the password directly. Basic Auth is therefore only acceptable over HTTPS, where the header is encrypted.

Repeatedly transmitting the password is Basic Authentication's central weakness. An intercepted request exposes the reusable credential itself rather than a limited stand-in. The user must then change the password everywhere it was reused. Tokens can instead be given a narrow scope and a limited lifetime, which is one reason user-facing applications generally prefer them.

Browser support introduces usability problems as well. A Basic challenge opens a native credential dialog outside the page, so the application cannot style or control it like a normal login form. Browsers also cache the credentials, and HTTP does not define a reliable logout mechanism that clears them.

Basic Authentication can still suit a small, non-browser integration whose credential can be issued, rotated, and revoked safely. HTTPS remains mandatory even on an internal network. As the number of clients or required permissions grows, scoped tokens or workload identities usually provide better control.

The userinfo URL syntax

The URI syntax https://alice:s3cr3t@example.com/private/ places credentials in the URL's userinfo component. Client behavior is inconsistent, and modern web APIs reject or restrict several uses of credentialed URLs. Avoid the syntax. URLs are copied into history, logs, diagnostics, and sharing tools that were never designed to hold passwords.

Sessions and Tokens

Two different approaches to keeping a user authenticated across requests.

After a user logs in, every subsequent request needs to prove that they did. HTTP is stateless, so this proof must be carried in the request itself. There are two broad strategies.

Server-side sessions

The server creates a session record on login and returns an opaque session ID (a random string with no inherent meaning). The browser stores this ID (typically in a cookie) and sends it with every request. The server looks up the session ID in a store (a database or in-memory cache like Redis) to retrieve the associated user and their permissions.

Advantage
Easy to revoke

Deleting the session record invalidates the session as soon as that change is visible to every server that accepts it. A design with one authoritative store can make logout and forced re-authentication predictable.

Tradeoff
Shared state required

Every server instance must be able to look up any session. In a multi-server environment this requires a shared session store, which becomes a dependency to manage and a potential bottleneck.

Token-based authentication

With token-based authentication, the client receives a signed token after login and returns it on later requests. The token may contain claims such as a subject, an audience, and an expiry time. A JSON Web Token (JWT) lets the server validate those claims locally, so authentication does not require a session lookup on every request.

Advantage
Local validation

A service can validate a signed, self-contained token without a session lookup. That property can reduce coordination between horizontally scaled services, although authorization data may still require shared state.

Tradeoff
Difficult to revoke

A self-contained token normally remains usable until it expires. Early revocation requires an online check or shared denylist, while short lifetimes limit the exposure window rather than revoking the token itself.

Opaque tokens and introspection

An opaque token occupies the space between these approaches. It travels in an Authorization header like a JWT, but the value is only a random identifier. The resource server therefore asks the issuer whether the token is active, commonly through the OAuth token introspection endpoint covered in the OAuth & OIDC article. Introspection adds a lookup, but it also lets the issuer withdraw access without waiting for the token to expire.

Real systems often combine the approaches. A browser may hold an opaque session cookie while a Backend for Frontend (BFF) keeps OAuth tokens on the server. Internal APIs can then receive short-lived access tokens without exposing those tokens to browser storage. The OAuth article owns that architecture in detail.

JSON Web Tokens

A compact claims format that can be signed, encrypted, or both.

A JSON Web Token (JWT) carries a set of JSON claims in a URL-safe format. JWT is a format rather than an authentication scheme. In a common authentication design, an issuer signs a JWT and the client presents it as Authorization: Bearer <token>. A service with the verification key can then validate the token without a session lookup.

The word Bearer names a separate property. A bearer token can be used by whoever possesses the string because the recipient validates the token, not the presenter. JWTs can also appear in sender-constrained designs, and bearer tokens do not have to be JWTs.

Structure

The signed JWT form used here is a compact JSON Web Signature. It has three base64url-encoded segments separated by dots: a header, a payload, and a signature. The header and payload encode JSON objects. An encrypted JWT uses a different five-part representation.

Header Payload Signature

The header identifies the token type and signing algorithm. The payload contains claims, statements about the user and the token itself. Decoded, a typical payload looks like:

Decoded JSON payload 
{
  "sub": "user_123",          // subject: the user's ID
  "iss": "auth.example.com",  // issuer: who created this token
  "aud": "api.example.com",   // audience: who should accept it
  "exp": 1719489600,          // expiry: Unix timestamp
  "iat": 1719486000,          // issued at: when it was created
  "roles": ["editor"]         // custom claim: application-specific
}

The signature covers the encoded header and payload. It is created with a private key for an asymmetric algorithm or a shared secret for a keyed hash. A verifier with the corresponding key can detect changes and confirm that the token came from a trusted issuer.

The payload is not encrypted

Base64url encoding is not encryption. Because it's reversible by anyone, the payload of a JWT is readable by anyone who intercepts the token. Never put passwords, secrets, or sensitive personal data in JWT claims. The signature prevents tampering, not reading.

Validation

JWT validation combines cryptographic checks with rules for the particular kind of token being accepted. A token that fails a required check must be rejected:

  • Algorithm and signature. Configure an allowlist of acceptable algorithms, select the trusted key, and verify the signature.
  • Time. Require and validate the time claims the token profile uses, commonly exp and sometimes nbf.
  • Issuer. Confirm the iss claim names the expected issuer.
  • Audience. Confirm the aud claim names this service, not another recipient.
  • Token kind. Apply distinct validation rules for access tokens, ID tokens, and any other JWT profile so one kind cannot be substituted for another.

A library can perform these checks only after the application supplies the expected algorithms, issuer, audience, and required claims. Decoding a token is not validation.

Pitfalls

JWTs are frequently misused beyond the validation checks above. Most of the common mistakes come down to trusting the token before validating it.

Not validating the signature. This sounds too obvious to be a real mistake, but several high-profile incidents have involved JWT libraries that, depending on configuration, accepted tokens without verifying the signature. Always use a well-maintained library and check that signature verification is not disabled or configurable per-request.

The alg: none attack. Some implementations accepted an unsigned token where an application expected a signed authentication token. Configure the allowed algorithm for each token type and reject none in every profile that requires integrity protection. The OAuth & OIDC attack list shows how that failure becomes an authentication bypass.

Overly long expiry. A self-contained token may remain usable after an account is compromised or disabled unless the system adds a revocation check. Keep access tokens short-lived according to the application's threat model, then use a protected refresh token when the client needs a longer session. The OAuth & OIDC article covers that pattern and its rotation requirements.

Storing sensitive data in claims. The payload of a signed JWT is readable. Include only the claims the recipient needs, and assume logs or diagnostics may capture the token. Use encryption when confidentiality is a protocol requirement rather than treating the signature as privacy protection.

Token Storage

Where a token is stored determines what kind of attack can steal it. There is no option without tradeoffs.

A browser application either exposes a token to JavaScript so code can attach it to requests, or relies on a cookie that the browser sends automatically. The choice changes which attacks can reach the credential.

localStorage
Vulnerable to XSS

Any JavaScript running on the page can read localStorage. Even a small XSS vulnerability can exfiltrate the token to an attacker's server. The attacker then has the token and can use it from anywhere, independently of the browser session.

HttpOnly cookie
Needs CSRF controls

JavaScript cannot read an HttpOnly cookie, which blocks direct theft through document.cookie. Automatic cookie attachment can create CSRF exposure, so the cookie policy and request defenses must be designed together. See the browser security article.

Most web applications should keep the session credential in an HttpOnly, Secure cookie and set SameSite deliberately. HttpOnly prevents scripts from reading the cookie, although an XSS payload can still make authenticated requests from the page. SameSite reduces CSRF exposure by limiting when cross-site requests include the cookie.

SameSite=Strict withholds the cookie on all cross-site requests, including the first request after a user follows an external link. That behavior can disrupt ordinary navigation into a signed-in application. SameSite=Lax is often a better fit because it permits cookies on top-level cross-site navigations that use safe methods, while withholding them from most cross-site subrequests and unsafe-method requests. Applications still need a CSRF defense for any flow their cookie policy permits.

Memory storage for SPAs

A token can live in a JavaScript variable rather than persistent browser storage. A single-page application keeps that variable across client-side route changes, but a reload or new tab starts a new JavaScript context. Memory storage reduces persistence after the page closes. It does not protect the token from XSS while the page is running. When a server component is available, a BFF architecture keeps OAuth tokens on the server and gives the browser an HttpOnly session cookie instead.

Every storage option above is guarding a bearer token against theft. Whoever holds the string can use it. DPoP, an OAuth-defined mechanism, changes that property by binding a token to a key controlled by the client. The client sends a proof instead of sending the private key, so the token string alone is insufficient. The OAuth & OIDC article covers the mechanism and its limits.

Passkeys and WebAuthn

A public-key credential that replaces the password itself, not just what happens after it.

A passkey is a discoverable public-key credential created for a particular relying party. The relying party stores the public key, while an authenticator protects the private-key material and uses it to produce signed assertions. Some passkeys remain bound to one authenticator. Others can be backed up and synchronized by a credential provider. Registration and sign-in use WebAuthn, the browser API through which a site asks an authenticator to create or use the credential.

This changes the password model in a way that matters for security. A password is a shared secret that a user can type into a convincing fake. A passkey never reveals its private key to the relying party, and the user does not type the credential. WebAuthn binds each assertion to the relying party and requesting origin. A lookalike domain therefore cannot obtain an assertion valid for example.com. A stolen table of public keys is not enough to authenticate because public keys cannot create signatures.

Platform authenticator
Face ID, Touch ID, Windows Hello

Managed by a platform such as iCloud Keychain or Google Password Manager and often synchronized across the user's devices. Hardware backing varies by platform and authenticator.

Roaming authenticator
Security keys (YubiKey and similar)

A separate authenticator reached through USB, NFC, or another supported transport. Organizations often choose these devices when they need credentials to remain on managed hardware.

The flow has two parts. During registration, the relying party sends a fresh random challenge and the browser asks an authenticator to create a credential. The returned registration data binds the challenge, origin, relying-party identifier, credential ID, and public key. During authentication, the relying party sends another challenge. After any required user verification, the authenticator returns a signed assertion that the server checks with the stored public key.

A passkey replaces the password as the credential, but the server still needs to establish a session or issue a token afterward, the same way covered above. A passkey is phishing-resistant since the signature is bound to the origin, so it can't be replayed against a lookalike site. Passkeys change how identity is proven at login, not what happens for the rest of the request lifecycle.

API Keys

A shared secret for machine-to-machine access, simple to issue and easy to mishandle.

An API key is a long random string issued by the server and shared with a specific client. The client presents it on every request. The server looks it up and determines what the client is allowed to do. Unlike user authentication, API keys typically identify an application or a team rather than an individual person.

Transmission

Send API keys in the API's documented request header. Some APIs define an Authorization scheme, while others use a custom header such as X-API-Key. Avoid query parameters because URLs are copied into access logs, browser history, analytics systems, and intermediary diagnostics.

HTTP 
# Key in the API's documented header
GET /data
X-API-Key: sk_live_a3f9b2c1d4e5f6a7b8c9

# Wrong. URLs are copied into logs and browser history.
GET /data?api_key=sk_live_a3f9b2c1d4e5f6a7b8c9

Storage and rotation

Store only a one-way representation of each API key so a database leak does not reveal credentials that can be replayed directly. A common design shows the raw key once, keeps a non-secret prefix for lookup, and stores a cryptographic hash of the secret portion. Use established library functions when comparing secret values rather than writing comparison code by hand.

Beyond hashing, a production key management setup needs three more properties:

  • Rotatable without downtime: issue a replacement key, accept both values for a brief overlap period, then revoke the old key.
  • Scoped to the minimum required permissions: a read-only key cannot be used to delete records even if it's stolen.
  • Revocable in an emergency: like any credential, a key needs a fast path to invalidation if it's suspected compromised.
mTLS as an alternative

For service-to-service calls inside a private network, mutual TLS can identify the calling service using its certificate instead of, or alongside, an API key. It's common in service meshes and zero-trust network setups, though issuing and rotating the certificates is handled by infrastructure or platform tooling rather than application code.

API keys in source code

A key committed to a repository should be treated as exposed, even if the commit is later removed. Revoke and replace it, then remove the value from history where appropriate. Keep runtime secrets in a secrets manager or another deployment-controlled store, and scan commits before they reach the shared repository.
