Authentication

How a login turns into a credential that's verified on every subsequent request, using sessions, tokens, passkeys, and API keys.

Andreas Ögren
~17 min read
Last updated July 2026

Every login form, JWT, passkey prompt, and API key eventually resolves to the same handful of mechanisms. Either the server records that a login happened and hands the client a reference to that record, or it issues a signed credential that carries the proof in itself. This article works through each of those mechanisms. It explains how sessions and tokens differ, what a JWT contains, and why it can be verified without a database lookup. The article then covers where each credential should be stored, how passkeys replace passwords with public-key cryptography, and where API keys still fit for machine-to-machine access.

Authentication vs Authorization

Two concepts that are frequently conflated and almost as frequently implemented incorrectly.

Identification presents identity, answering the question "who do you claim to be?", typically in the form of a user name or e-mail address.

Authentication proves identity. It answers the question "are you who you claim to be?" using credentials such as a password, a token, a certificate, or a biometric. The credentials that prove identity fall into three categories, called authentication factors. Something known is a secret the user can recall, such as a password or PIN. Something held is an object the user possesses, such as a phone, an authenticator app, or a hardware security key. Something inherent is a physical trait, such as a fingerprint or face. Requiring proof from more than one category at once is what multi-factor authentication means.

Authorization establishes permission. It determines what an authenticated identity is allowed to do, answering the question "does this identity have the right to perform this operation?" Authorization is always relative to an identity, since there is nothing to authorize without one. But authentication alone is not sufficient for authorization, because a valid login doesn't mean every resource is accessible.

Conflating the two is a common source of access control vulnerabilities. An application that checks "is this user logged in?" for every request but not "does this user own this resource?" has authenticated correctly but failed at authorization. The security principles article covers broken access control in more depth.

Basic Authentication

The simplest authentication scheme is built into HTTP itself.

HTTP Basic Authentication sends a username and password with every single request, base64-encoded inside an Authorization header. There's no session, no token, and nothing stored between requests. The server checks the credentials again on each request.

HTTP 
GET /reports
Authorization: Basic am9objpodW50ZXIy
# decodes to "john:hunter2"
Base64 is not encryption

Anyone who intercepts a Basic Auth header can decode it in one step and read the password directly. Basic Auth is therefore only acceptable over HTTPS, where the header is encrypted.

This retransmission is the core weakness. The credential on the wire is the real password, not a short-lived stand-in, so one intercepted request leaks something permanent and broadly scoped. A time-limited token would eventually expire on its own and could be revoked before then. The password can't be revoked at all, short of changing it everywhere it's used, which is most of why Basic Auth is rare in user-facing applications today.

The browser adds a second problem. The credential prompt is a native dialog the browser raises on its own whenever a response carries a Basic Auth challenge, separate from the page. It can't be styled to match the application, and there is no clean way to log out short of closing the browser, which caches the credential for the rest of the session.

Basic Auth still earns its place away from the browser, in settings such as internal tools behind a VPN, service-to-service calls on a private network, and simple webhook or CI callbacks. None of these go through a browser prompt, so the operational simplicity outweighs the downsides.

The userinfo URL syntax

The userinfo URL syntax, https://alice:s3cr3t@example.com/private/, is a URI feature that the browser converts into the same Basic Auth header, skipping the login prompt. Browsers hide the credentials from the address bar, but typing the URL still sends them, except on cross-origin subresources, where the browser drops them instead. Avoid this syntax, since a password in the URL leaks into browser history, access logs, and the Referer header.

Sessions and Tokens

Two different approaches to keeping a user authenticated across requests.

After a user logs in, every subsequent request needs to prove that they did. HTTP is stateless, so this proof must be carried in the request itself. There are two broad strategies.

Server-side sessions

The server creates a session record on login and returns an opaque session ID (a random string with no inherent meaning). The browser stores this ID (typically in a cookie) and sends it with every request. The server looks up the session ID in a store (a database or in-memory cache like Redis) to retrieve the associated user and their permissions.

Advantage
Easy to revoke

Deleting the session record immediately invalidates the session, everywhere. Logging out, detecting account compromise, or forcing re-authentication is instant and reliable.

Tradeoff
Shared state required

Every server instance must be able to look up any session. In a multi-server environment this requires a shared session store, which becomes a dependency to manage and a potential bottleneck.

Token-based authentication

The login response instead carries a signed token that encodes the user ID, roles, and expiry directly. The most common token format is the JSON Web Token (JWT), discussed in detail further down. On subsequent requests the client sends the token back. The server validates the signature and reads the claims without consulting any external store, which leaves it stateless with respect to authentication.

Advantage
Stateless and scalable

Any server instance can validate a token independently. No shared session store is required. This makes token-based authentication a natural fit for microservices and horizontally scaled deployments.

Tradeoff
Difficult to revoke

A token is valid until it expires. Revoking a token before expiry requires either a revocation list (which every server must check, reintroducing shared state) or very short token lifetimes paired with refresh tokens.

Opaque tokens and introspection

A third option sits between the two. An opaque token travels like a JWT in the Authorization header, but carries no information of its own. It is a random identifier, like a session ID. The resource server can't validate it locally, so it asks the issuer whether the token is still good, typically through a token introspection endpoint defined by OAuth and covered in the OAuth & OIDC article. This gives up the main appeal of a JWT, which is validation without a network round trip, in exchange for the same easy revocation sessions have.

Real systems often use both rather than picking one. An API gateway or Backend for Frontend (BFF) at the edge can hand the browser an opaque, instantly revocable token, introspect it once per request, then mint a short-lived JWT for that request to carry through internal services. Revocation stays centralized at the edge, while everything behind it validates locally without a repeated network call.

JSON Web Tokens

The most common way to implement the token-based approach above, a self-contained, signed credential any server can verify without a database lookup.

A JWT (JSON Web Token) is a self-contained credential. A server issues one after login, and the client attaches it to later requests, typically as Authorization: Bearer <token>. Any server holding the right key can verify the token on its own, without looking anything up in a database. That property is what makes it the token-based side of the sessions-versus-tokens tradeoff described above. The word Bearer in that header names its trust model. A bearer token is one that anyone holding the string can use, because the server checks that the token is valid but not who presents it.

Structure

Structurally, a JWT consists of three base64url-encoded segments separated by dots: a header, a payload, and a signature. The header and payload are JSON objects. The signature is the raw output of the signing algorithm.

The header identifies the token type and signing algorithm. The payload contains claims, statements about the user and the token itself. Decoded, a typical payload looks like:

Decoded JSON payload 
{
  "sub": "user_123",          // subject: the user's ID
  "iss": "auth.example.com",  // issuer: who created this token
  "aud": "api.example.com",   // audience: who should accept it
  "exp": 1719489600,          // expiry: Unix timestamp
  "iat": 1719486000,          // issued at: when it was created
  "roles": ["editor"]         // custom claim: application-specific
}

The signature is computed over the header and payload using the server's private key (for RSA or ECDSA algorithms) or a shared secret (for HMAC). It allows any holder of the corresponding public key or shared secret to verify that the token hasn't been tampered with.

The payload is not encrypted

Base64url encoding is not encryption. Because it's reversible by anyone, the payload of a JWT is readable by anyone who intercepts the token. Never put passwords, secrets, or sensitive personal data in JWT claims. The signature prevents tampering, not reading.

Validation

Accepting a JWT without validating it is equivalent to accepting no authentication at all. Validation is a fixed set of checks, and a token that fails any one of them is rejected:

  • Signature. Recompute the expected signature and reject any mismatch. A mismatch means the token was tampered with, or was never issued by a trusted party to begin with.
  • Expiry. Reject a token whose exp timestamp has already passed.
  • Issuer. Confirm the iss claim names an issuer the server trusts.
  • Audience. Confirm the aud claim names this service, not some other API the token was issued for.

Most JWT libraries run all four automatically once configured with the right key, issuer, and audience.

Pitfalls

JWTs are frequently misused beyond the validation checks above. Most of the common mistakes come down to trusting the token before validating it.

Not validating the signature. This sounds too obvious to be a real mistake, but several high-profile incidents have involved JWT libraries that, depending on configuration, accepted tokens without verifying the signature. Always use a well-maintained library and check that signature verification is not disabled or configurable per-request.

The alg: none attack. Some early JWT implementations accepted a token that declared its algorithm as none, meaning no signature was needed. An attacker could set any claims they liked and the server would accept the token as valid. Modern libraries reject alg: none by default, but the underlying lesson still applies. Never accept the algorithm claimed by the token itself, and specify the expected algorithm server-side instead. The same failure mode is cataloged as JWT Algorithm Confusion in the OAuth & OIDC article's attack list.

Overly long expiry. A JWT that is valid for 30 days cannot be revoked if the user's account is compromised or deleted. The standard approach is a short-lived access token (15 minutes to 1 hour) paired with a longer-lived refresh token that renews it. OAuth 2.0 formalized the pattern, and the OAuth & OIDC article covers it in more depth. The access token still can't be revoked early, but its short lifetime limits the damage.

Storing sensitive data in claims. Claims are readable by anyone who can intercept the token, the same as the rest of the payload. Limit claims to identifiers and roles, and don't include personal data, permissions that shouldn't be visible, or anything otherwise considered private.

Token Storage

Where a token is stored determines what kind of attack can steal it. There is no option without tradeoffs.

Browser-based applications must store authentication tokens somewhere the application can retrieve them to attach to API requests. The two main options are localStorage (or sessionStorage) and HttpOnly cookies, and they have opposite vulnerability profiles.

localStorage
Vulnerable to XSS

Any JavaScript running on the page can read localStorage. Even a small XSS vulnerability can exfiltrate the token to an attacker's server. The attacker then has the token and can use it from anywhere, independently of the browser session.

HttpOnly cookie
Vulnerable to CSRF

JavaScript cannot read an HttpOnly cookie, eliminating XSS-based token theft. However, cookies are sent automatically on cross-site requests, so an XSS-free application may still be vulnerable to CSRF unless SameSite is set correctly. See the browser security article.

The practical recommendation for most web applications is an HttpOnly, Secure cookie with SameSite set. HttpOnly removes XSS-based token theft, since scripts can't read the cookie, and SameSite blunts CSRF by controlling when the cookie is sent cross-site. SameSite=Strict is the tightest option, but it has a real cost. A user who arrives from an external link, such as an email or another site, sends no cookie on that first request. They land logged out and appear signed in only after a reload. For that reason many applications use SameSite=Lax for the session cookie. Lax withholds the cookie on the cross-site subrequests and unsafe-method requests where CSRF lives, while still sending it on a top-level navigation the user initiated themselves. Either way the server sets the cookie on login, and the browser attaches it automatically afterward.

Memory storage for SPAs

A third option is to hold the token in a JavaScript variable that lives only in memory, distinct from localStorage, sessionStorage, or an HttpOnly cookie. This only works in a single-page application (SPA). Its JavaScript context survives across the whole session, while a traditional multi-page app reloads that context on every navigation, losing the variable each time. The tradeoff is that a manual reload, a closed tab, or a link opened in a new tab loses the token too, requiring the application to silently re-authenticate. Memory storage is still reachable by XSS, since injected script shares the same privileges as the application (see the browser security article). For SPAs that can't rely on a same-site HttpOnly cookie, the recommended pattern instead is a BFF architecture, where the browser only ever holds a session cookie and a server-side component attaches the real access token to outgoing API calls.

Every storage option above is still only guarding a bearer token against theft. Whoever holds the string can use it, which is why so much of this section has been about limiting exposure rather than eliminating it. DPoP, an OAuth-defined mechanism, removes the bearer property instead by binding a token to a private key that never leaves the client, so a stolen token alone isn't enough to use it. It's covered in the OAuth & OIDC article.

Passkeys and WebAuthn

A public-key credential that replaces the password itself, not just what happens after it.

A passkey is a public/private key pair generated on the user's device specifically for one site. The private key never leaves the device or the user's synced keychain. Only the public key is ever sent to the server. Registration and sign-in both happen through WebAuthn, a browser API that is part of the FIDO2 standard. The API asks the operating system to create or use the key pair and returns a signed response the server can verify.

This inverts the password model in a way that matters for security. A password is a shared secret. The same string exists on the user's device and in the server's database, and it can be typed into any site that asks for it, including a convincing fake. A passkey's private key is never transmitted and never typed. The signature produced during sign-in is also bound to the origin that requested it, so a passkey created for example.com cannot be used to authenticate to a phishing page at a different domain, even one that looks identical. Database breaches are less damaging too. Stealing a table of public keys gives an attacker nothing usable, since a public key cannot sign anything on its own.

Platform authenticator
Face ID, Touch ID, Windows Hello

Backed by the device's secure hardware and synced across a user's devices through the operating system's keychain (iCloud Keychain, Google Password Manager). The common choice for consumer apps.

Roaming authenticator
Security keys (YubiKey and similar)

A physical device connected over USB or NFC, not tied to a single computer's keychain. Common where a hardware-backed credential is a compliance requirement.

The flow has two parts. During registration, the server sends a random challenge. The browser asks the authenticator to generate a new key pair and sign the challenge, then returns the public key and a credential ID for the server to store against the account. During authentication, the server sends a new challenge. The browser unlocks the existing private key, via Face ID, a PIN, or similar, to sign it, and the server verifies that signature against the stored public key.

A passkey replaces the password as the credential, but the server still needs to establish a session or issue a token afterward, the same way covered above. A passkey is phishing-resistant since the signature is bound to the origin, so it can't be replayed against a lookalike site. Passkeys change how identity is proven at login, not what happens for the rest of the request lifecycle.

API Keys

A shared secret for machine-to-machine access, simple to issue and easy to mishandle.

An API key is a long random string issued by the server and shared with a specific client. The client presents it on every request. The server looks it up and determines what the client is allowed to do. Unlike user authentication, API keys typically identify an application or a team rather than an individual person.

Transmission

API keys must be sent in headers, either the Authorization header or a custom header like X-API-Key. They must never be sent as URL query parameters. Query parameters end up in server access logs, browser history, CDN logs, and Referer headers when the page links elsewhere, any of which can expose the key to unintended parties.

HTTP 
# Correct — key in header
GET /data
Authorization: Bearer sk_live_a3f9b2c1d4e5f6a7b8c9

# Wrong — key in URL (ends up in logs, browser history, Referer headers)
GET /data?api_key=sk_live_a3f9b2c1d4e5f6a7b8c9

Storage and rotation

API keys should be stored hashed on the server, just like passwords. If the database is breached, the raw keys are not exposed. The client sees the key once, at creation, and after that the server only stores a hash. When comparing an incoming key to the stored hash, a constant-time comparison is used to avoid timing attacks.

Beyond hashing, a production key management setup needs three more properties:

  • Rotatable without downtime: the client generates a new key, the server accepts both old and new for a brief overlap period, then the old key is revoked.
  • Scoped to the minimum required permissions: a read-only key cannot be used to delete records even if it's stolen.
  • Revocable in an emergency: like any credential, a key needs a fast path to invalidation if it's suspected compromised.
mTLS as an alternative

For service-to-service calls inside a private network, mutual TLS can identify the calling service using its certificate instead of, or alongside, an API key. It's common in service meshes and zero-trust network setups, though issuing and rotating the certificates is handled by infrastructure or platform tooling rather than application code.

API keys in source code

Committing an API key to a public repository is one of the most common credential exposure incidents. Automated scanners watch public repositories for credential patterns and can begin abusing a key within minutes of it appearing. Use environment variables or a secrets manager, never hard-code credentials in source files, and add secret-scanning tools to the CI pipeline.
