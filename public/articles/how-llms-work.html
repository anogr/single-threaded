How Large Language Models Work

What tokens, context windows, and sampling are, and why cost, latency, and hallucination follow from the same mechanisms.

Andreas Ögren
~12 min read
Last updated July 2026

Deciding how much context to hand an agent, whether to trust a fluent answer, or which model tier a pipeline should call are all judgments about machinery. The other articles in this series treat the model as a black box that reads context and produces text or code. That framing works until a decision depends on what the box does inside, and most of the recurring decisions do.

This article opens the box to the depth those decisions need, and no further. It walks through how a model splits text into tokens, predicts one token at a time, and chooses among candidate continuations. From there it follows the mechanisms outward, to why models state falsehoods fluently, why long context costs both money and time, and why retrieval exists. Nothing here is about building or training a model. The goal is using one with fewer surprises.

Next-Token Prediction

Every capability the model shows emerges from one operation, repeated.

At the core of every large language model (LLM) is a simple repeated process. Given a sequence of text, the model estimates the probability of every possible fragment that could come next. These fragments are called tokens. One token is then selected, appended to the existing text, and the model repeats the same process using the longer sequence. Text generation is simply this cycle continuing until the model emits a stop token or reaches a predefined length limit. This approach is known as autoregressive generation, because each newly generated token becomes part of the input for the next prediction.

one-prediction-step.txt Text 
Input so far:   "The capital of France is"

Candidates:      Paris     0.91
                 located   0.03
                 the       0.02
                 known     0.01
                 …         …

Pick one, append it, run the step again.

Within each step, those probabilities are produced by a mechanism called attention. As the model makes its prediction, every token in the input can take other tokens into account, assigning different levels of importance to different parts of the context. This allows the model to connect a pronoun with a name mentioned several sentences earlier, or relate a variable on line 400 of a program to its declaration on line 12.

The model does not execute instructions in the way a traditional program does. Instead, it predicts a likely continuation of the text that contains the instruction. If you ask it to translate a paragraph, there is no hidden translate() function being called. The model generates the kind of text that, based on its training, is most likely to follow a request like that. This explains why small changes in wording can produce different results, why including a few concrete examples often guides the output more effectively than abstract instructions, and why an ambiguous prompt usually leads to an ambiguous response. A prompt is best understood as the beginning of a document, and the model's job is to continue writing it.

Tokens and Tokenization

The model reads and writes in units that sit between characters and words.

Before any prediction happens, input text is split into tokens, short fragments the model treats as atomic. The splitting is done by a tokenizer built with byte-pair encoding, an algorithm that finds the most frequent character sequences in a large corpus and promotes them to single units. Common words end up as one token each. Rare words split into several pieces. As a rule of thumb, a token averages around four characters of English, or about three quarters of a word.

Frequency decides the boundaries, and frequency has no sense of meaning. A common year can be a single token while an arbitrary ID number shatters into many. A well-known function name might cost one token while a project-specific identifier costs five. The same text can also tokenize differently across model families, since each vendor trains its own tokenizer on its own corpus.

tokenization.txt Text 
"The quick brown fox"   →  [The] [ quick] [ brown] [ fox]      4 tokens
"getUserById"           →  [get] [User] [By] [Id]              4 tokens
"x7f3a9"                →  [x] [7] [f] [3] [a] [9]             6 tokens

(Illustrative; boundaries differ between tokenizers.)

Everything downstream of this section is measured in tokens. The context limit is a token count, model pricing is quoted per token, and latency grows with the number of tokens processed. When a later section says a cost scales with length, token count is the length being measured.

The Context Window

One request, one budget, and everything the model should know competes for it.

A model can only condition its predictions on a bounded stretch of text. That bound is the context window, the maximum number of tokens a single request can hold. Everything the model is supposed to consider has to fit inside it together. The system prompt, the task instructions, any files or documents, the conversation so far, and the output of every tool call all draw from the same budget. Whatever falls outside the window does not exist for the model, however important it was two requests ago.

Windows have grown from a few thousand tokens a few years ago to hundreds of thousands on current models, with some reaching over a million. Growth has not removed the budget. It has moved the point where the budget binds, and raised the cost of filling it, for reasons the cost section explains.

Position inside the window matters too. Research on long-context behavior repeatedly finds a U-shaped pattern, in which information near the beginning or the end of a long prompt is used more reliably than information buried in the middle. The effect is known as lost in the middle. A fact placed at the midpoint of a very long prompt has not left the window, but it competes at a disadvantage. Placement is a decision alongside inclusion.

Thus, the model predicts one token at a time, and it only ever sees a finite window of context. Most of the practical behavior of AI tooling follows from that pair, from hallucinated function signatures to invoice-sized token bills.

Why context files stay small

The context files covered earlier in the series are spent from this budget on every request, needed or not, which is why the advice there is to keep them narrow. Managing the same budget across a whole session is the job context engineering names.

Sampling and Temperature

The distribution is computed. Something still has to choose.

Prediction ends with probabilities, and generation needs a token. The step between them is sampling. Always taking the single most likely candidate produces repetitive, oddly flat text, so by default the choice is made at random, weighted by the distribution. A candidate with a probability of 0.9 wins most of the time and loses occasionally.

Temperature controls how far that randomness spreads. Low values concentrate the choice on the top candidates, and a temperature of zero collapses to always picking the most likely one. High values flatten the distribution so that unlikely tokens get a real chance, which reads as creative on a good day and unhinged on a bad one. A companion setting, top-p, trims the candidate pool to the smallest set of tokens whose probabilities sum past a threshold before sampling among them.

Sampling explains why the same prompt produces different answers on different runs, and why "it said so yesterday" is weak evidence about today. What temperature does not control is correctness. Lowering it makes output more repeatable, and repeatably wrong is still wrong. If the model's distribution puts its weight on a false continuation, every sample at every temperature draws from that same weight. Temperature is a consistency dial, not a quality dial.

Where the Knowledge Comes From

The model consults nothing when it answers. It remembers, in a loose and lossy sense of the word.

The probabilities come from training. Pretraining exposes the model to a vast corpus of text and adjusts it, over an enormous number of prediction exercises, until it predicts that corpus well. General knowledge, languages, and code patterns all come from this stage. Fine-tuning then adapts the pretrained model to a narrower job using a smaller, targeted dataset. A further stage, reinforcement learning from human feedback (RLHF), shapes the model toward responses people rate as helpful. This stage is why a modern assistant answers a question instead of continuing it with three more questions, as raw pretrained models tend to.

Training ends on a date, and the model's built-in knowledge ends with it. That date is the knowledge cutoff. A library released after it, a renamed API, or last quarter's incident report are all invisible to the model unless the information arrives through the context window.

Hallucination is a natural consequence of the prediction process that generates every response. The model is designed to continue text by predicting what is most likely to come next, not by verifying facts or checking whether it actually knows the answer. When its training strongly supports the correct information, the most likely continuation is often also the correct one. When that support is weak or missing, the model can still produce a fluent and convincing continuation that matches the surrounding pattern. That might mean inventing a function that seems like it should exist in a software library, creating a citation that looks authentic but is not real, or confidently presenting information that is simply incorrect.

The delivery is the trap. Fluency signals that a continuation is statistically likely, and people read it as confidence. The model has no channel for certainty. It cannot know whether it is right, and its prose sounds identical in either case. Treating fluent output as verified output is the root of most misplaced trust in these systems, and no amount of prompt wording removes the need to check claims that matter.

When an application needs current or verifiable information, it has to provide that information to the model at the time of the request. There are two common ways to do this. Tools allow the model to retrieve live data or interact with external systems, with connections often standardized through MCP. Retrieval, often called retrieval-augmented generation (RAG), searches for relevant documents and adds them to the model's context before it starts generating a response. This retrieval process relies on one more important concept: embeddings.

Embeddings

A different job from generating text, and the machinery behind searching by meaning.

An embedding does a different job from everything above. Instead of producing text, an embedding model turns a piece of text into a vector, a long list of numbers positioned so that texts with similar meaning land near each other. Similarity becomes distance. "How do I reset my password" and "account recovery steps" sit close together in that space despite sharing no words, and both sit far from a paragraph about database migrations.

That property is what makes retrieval by meaning work. Embed every chunk of a corpus once to build an index, embed the query when it arrives, and fetch the nearest neighbors. The semantic repository indexing described in the assistants article works this way, embedding a codebase so an agent can find the files relevant to a task by meaning rather than by filename. The same pipeline underlies retrieval-augmented generation, where the fetched chunks are placed into the context window to ground an answer in source material. Vector databases exist to make the nearest-neighbor lookup fast at scale.

Why Inference Costs Time and Money

Latency and price are the same mechanism observed twice.

Every token in the window participates in computing every prediction. More context therefore means more computation per step, and the bill for that computation arrives in two currencies, once as waiting and once as money. This is why a long prompt is slow even when the answer is short, and why per-token pricing is the industry's universal unit.

Output carries a cost that input does not. The tokens of a request are processed together when it arrives, while output tokens are produced one at a time by the generation loop. A long answer costs wall-clock time in a way a long question does not, and output tokens are typically priced higher than input tokens for the same reason.

Prices differ by orders of magnitude between model tiers, and have fallen steeply year over year, which makes cost a design variable rather than a constant. The levers follow directly from the mechanism. Send less context. Route easy work to smaller models. Cache what repeats across requests. The cost section of the assistants article applies these levers to agent workloads, where the token volumes are largest.

The Decisions That Follow

Four practical constraints, each leading to a different design decision.

Context is finite, so it is best treated as a limited resource rather than a container to fill. Retrieving the most relevant information is usually more effective than including everything that might be useful, improving both reliability and cost. The position of the information within the context window matters. Important details buried in the middle of a long prompt are more likely to be overlooked than information placed near the beginning or end.

Prediction is statistical, so verification has to come from the system around the model rather than from the model itself. Lowering the temperature can make outputs more consistent, but it does not make them more accurate, and a confident, well-written answer is not evidence that it is correct. The review checkpoints discussed throughout this series, from plan review to risk-tiered code review, are practical ways to apply this principle.

A model's built-in knowledge is limited to what it learned during training, so any application that depends on current, changing, or private information needs a way to provide that information at request time. Tools connect the model to live systems, while retrieval supplies relevant documents. This matters because language models are optimized to continue text, not to decide whether they have enough information to answer. If a model is asked to answer from memory alone, it will still generate a plausible response, even when the required information is unavailable. Systems should therefore provide the information the model needs, rather than rely on it to recognize when it does not know.

To summarize, the model generates one token at a time and each prediction depends only on the current context window. Computation scales with the number of tokens processed, making cost and latency architectural concerns rather than operational surprises. Context size, output length, and model selection all influence efficiency long before usage costs appear.
