How Large Language Models Work

How token prediction and bounded context shape model behavior, reliability, latency, and cost.

Andreas Ögren
~10 min read
Last updated July 2026

Questions about context, trust, latency, and model choice all lead back to the same machinery. The other articles in this series mostly treat a model as a box that reads context and produces text or code. That abstraction is useful, but it stops being enough when an architectural decision depends on why the model behaves as it does.

This article opens that box only as far as those decisions require. It begins with tokens, next-token prediction, and sampling, then follows those mechanisms into hallucination, long-context behavior, retrieval, cost, and latency. The aim is not to teach model construction. It is to make the behavior of a model less surprising when one becomes part of a system.

Next-Token Prediction

Generation proceeds through one repeated operation: predict the next token from the tokens already present.

A generative large language model (LLM) receives a sequence of tokens, the text units it processes, and assigns a score to every token that could follow it. Those scores become a probability distribution, from which the system chooses one candidate. The chosen token is appended to the sequence, and the model runs again with the longer input. Generation continues until it produces a stopping token or reaches an output limit. This process is called autoregressive generation because every generated token becomes input to the next step.

one-prediction-step.txt Text 
Input so far:   "The capital of France is"

Candidates:      Paris     0.91
                 located   0.03
                 the       0.02
                 known     0.01
                 …         …

Pick one, append it, run the step again.

The model calculates those scores through many layers of learned transformations. One important mechanism is attention, which lets the representation of a token draw information from earlier tokens in the sequence. That connection can relate a pronoun to a name several sentences earlier or a variable use to its declaration. The implementation below that level matters when building models, but attention is enough to explain the practical behavior discussed here.

This loop changes how an instruction should be understood. The model does not call an internal translation function when asked to translate a paragraph. It generates the continuation that its training and post-training make likely after such a request. Wording matters because it changes the sequence being continued, while examples give the model a concrete pattern to follow. An ambiguous prompt leaves several plausible continuations open, so the answer may vary without the model having disobeyed anything.

Tokens and Tokenization

The model reads and writes in units that sit between characters and words.

Before prediction begins, a tokenizer splits the input into tokens. A token may represent a whole word, part of a word, punctuation, whitespace, or bytes. Many model families use a variant of byte-pair encoding or a related subword method that gives frequent sequences their own tokens while dividing rarer text into smaller pieces. English prose often averages fewer tokens than code, identifiers, or text written in some other languages, but the exact ratio depends on the tokenizer and the material.

Token boundaries reflect patterns in the tokenizer's training data rather than semantic meaning. A frequent identifier may stay intact while an unfamiliar one splits into several tokens; arbitrary numbers often fragment as well. The same text can therefore produce different token counts across model families, even before either model begins reasoning about it.

tokenization.txt Text 
"The quick brown fox"   →  [The] [ quick] [ brown] [ fox]      4 tokens
"getUserById"           →  [get] [User] [By] [Id]              4 tokens
"x7f3a9"                →  [x] [7] [f] [3] [a] [9]             6 tokens

(Illustrative; boundaries differ between tokenizers.)

Everything downstream of this section is measured in tokens. The context limit is a token count, model pricing is quoted per token, and latency grows with the number of tokens processed. When a later section says a cost scales with length, token count is the length being measured.

The Context Window

One request, one budget, and everything the model should know competes for it.

A model can only condition its predictions on a bounded stretch of text. That bound is the context window, the maximum number of tokens a single request can hold. Everything the model is supposed to consider has to fit inside it together. The system prompt, the task instructions, any files or documents, the conversation so far, and the output of every tool call all draw from the same budget. Whatever falls outside the window does not exist for the model, however important it was two requests ago.

Modern context windows can hold far more text than earlier generations, and some models accept hundreds of thousands of tokens or more. A larger limit only moves the boundary. Filling the window still consumes processing time and money, and the model may not use every position equally well.

Position inside the window matters too. Research on long-context behavior repeatedly finds a U-shaped pattern, in which information near the beginning or the end of a long prompt is used more reliably than information buried in the middle. The effect is known as lost in the middle. A fact placed at the midpoint of a very long prompt has not left the window, but it competes at a disadvantage. Placement is a decision alongside inclusion.

Two constraints now carry the rest of the article. The model generates one token at a time, and each request gives it only a finite amount of context. Together they explain much of the behavior that matters in application design, including fabricated function signatures, uneven long-context recall, latency, and token cost.

Why context files stay small

The context files covered earlier in the series consume part of this budget whenever a tool loads them. Keeping them narrow leaves more room for the task itself. Context engineering applies the same budgeting decision across an entire session.

Sampling and Temperature

The distribution is computed. Something still has to choose.

Prediction produces a probability distribution, but generation still needs one token. Sampling is the selection step between the two. A system may always choose the highest-probability candidate, or it may choose randomly with probabilities weighted toward the stronger candidates. Random sampling allows several plausible continuations instead of forcing the same locally most likely path every time.

Temperature reshapes the distribution before sampling. Lower values concentrate probability on the leading candidates, while higher values spread more probability across unlikely ones. APIs commonly treat zero as a request for the least random mode, although exact determinism still depends on the provider and serving system. A related setting, top-p, limits sampling to the smallest group of candidates whose combined probability reaches a chosen threshold.

Sampling is one reason the same prompt can produce different answers across runs. Temperature changes the amount of variation, not the truth of the underlying candidates. A lower setting may make a false answer more repeatable if the model already assigns it the highest probability. Temperature is therefore useful for controlling variation, but it cannot substitute for verification.

Where the Knowledge Comes From

Without tools or retrieved context, an answer can draw only on the current request and patterns learned during training.

The probabilities are learned during training. In pretraining, the model repeatedly predicts text drawn from a large corpus while its parameters are adjusted to reduce prediction error. That process teaches linguistic patterns, code structures, and associations that later appear as general knowledge. Post-training then shapes the pretrained model for instruction following and interaction. Providers use several methods for this stage, including supervised fine-tuning and preference optimization; reinforcement learning from human feedback (RLHF) is one well-known example.

The training corpus covers a bounded period, which providers usually describe with a knowledge cutoff. The boundary is not a guarantee that every earlier fact was learned, nor that no later fact appears. It does mean that a model cannot be relied on for a newly released library, a renamed API, or a recent incident unless that information is supplied through the request or a tool.

A hallucination occurs when plausible generation produces an unsupported or false claim. Without a retrieval or tool call, the model is not looking up a fact in a source of record. It is continuing from patterns in its parameters and the current context. Strong support may lead to the correct answer. Thin or conflicting support may instead produce a convincing function name or citation that fits the surrounding pattern but does not exist.

Fluency makes the failure easy to miss because correct and incorrect continuations can arrive in the same assured prose. Some systems can estimate uncertainty or cite supplied sources, but neither feature turns fluent text into verified fact. Claims that matter still need a check outside the generation step.

A system that depends on current, private, or verifiable facts must provide them at request time. Tools can fetch live records or act on external systems, and MCP standardizes one way to expose those capabilities. Retrieval selects relevant documents and places them in the context before generation. Semantic retrieval depends on one more concept: embeddings.

Embeddings

A different job from generating text, and the machinery behind searching by meaning.

An embedding model turns a piece of text into a vector rather than generating a continuation. Training places related texts near one another in the resulting vector space, according to the relationships the model has learned. A password-reset question may therefore sit near account-recovery instructions even when the two share few words, while remaining distant from a passage about database migrations.

Semantic retrieval uses that geometry as an index. The system embeds chunks of the corpus ahead of time, embeds each incoming query, then searches for nearby vectors. Repository indexes can use this approach to find code related by meaning rather than filename. Retrieval-augmented generation uses the same basic step before placing the selected chunks into the model's context. Vector-capable databases provide efficient nearest-neighbor search when the index grows large.

Why Inference Costs Time and Money

Latency and price are the same mechanism observed twice.

Processing more input requires more computation and memory, even though serving systems reuse intermediate work to avoid recalculating the whole prompt for every output token. Longer context therefore tends to increase latency and cost. Providers commonly expose that cost through token-based pricing because token counts closely track the amount of input and output the service processes.

Input and output affect latency differently. A provider can process the prompt in parallel across its token positions, while autoregressive output must be decoded sequentially. Long answers therefore add visible wall-clock time token by token. Many providers also price output tokens above input tokens, although the ratio is a commercial choice rather than a law of the architecture.

Model tiers can differ substantially in price, so routing is an architectural decision rather than a billing afterthought. The available levers follow from the mechanism: send only useful context, keep output focused, route bounded work to a suitable smaller model, and cache repeated prompt prefixes where the provider supports it. The assistants article applies these choices to agent workloads, where repeated repository context can dominate usage.

The Decisions That Follow

Four constraints, each one paying for a habit.

Because context is finite, it should be budgeted rather than filled by default. Retrieval can improve both cost and reliability when it selects the material a task needs instead of sending everything available. Placement matters as well, especially when important evidence would otherwise be buried inside a long prompt.

Statistical generation also means that verification belongs in the surrounding system. A low temperature can reduce variation, but it cannot establish correctness, and fluent wording does not prove a claim. The plan review and risk-tiered code review described elsewhere in the series turn that constraint into concrete gates.

Systems that depend on current or private facts need a grounding path. Tools suit live records and actions, while retrieval suits a document corpus. The application must also define what happens when neither path supplies enough evidence, rather than assuming the model will decline on its own.

Finally, token volume makes cost and latency architectural concerns. Context size, output length, caching, and model routing shape both before the first invoice arrives. The necessary design habits follow from a small set of mechanisms: sequential generation, bounded context, statistical prediction, and external grounding when the system needs facts.
