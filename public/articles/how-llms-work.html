How Large Language Models Work

How token prediction and bounded context explain model reliability, latency, and cost.

Andreas Ögren
~16 min read
Last updated July 2026

Models can produce plausible falsehoods or fail to use information supplied in a request. Response time and computational cost vary with the amount of text processed and generated. Context handling and token prediction explain these behaviors, so understanding the mechanism helps teams design prompts and verification.

Language models predate modern generative AI. Earlier statistical models estimated the next word from a short sequence of preceding words, while recurrent neural networks carried a learned state through a sequence one step at a time. Both approaches made long relationships difficult to learn or expensive to process. The Transformer architecture introduced in 2017 used attention to connect positions in a sequence more directly and allowed much of training to run in parallel. Larger Transformer models trained on broader corpora became the large language models used in current applications.

The explanation begins with next-token prediction, then connects bounded context and sampling to model behavior. The final sections cover learned knowledge and the separate embedding models used by retrieval systems. The focus is inference behavior that affects applications. Model architecture and training infrastructure stay outside the article's scope.

Next-Token Prediction

Generation repeatedly predicts the next token from the tokens already present.

A generative large language model (LLM) receives a sequence of tokens, the text units it processes. It scores the tokens that could come next and converts the scores into probabilities. The serving system chooses one candidate and adds it to the sequence before running the model again. Generation stops when the model produces a stopping token or reaches the output limit. The prediction-and-append loop is called autoregressive generation.

The model scores every token in its vocabulary on each step. These raw scores are commonly called logits. A softmax calculation converts them into a probability distribution whose values add up to one. The distribution does not report whether a statement is true. It reports which continuations fit the input and the patterns learned during training. A confident probability can therefore belong to a false continuation.

one-prediction-step.txt Text 
Input so far:   "The capital of France is"

Candidates:      Paris     0.91
                 located   0.03
                 the       0.02
                 known     0.01
                 …         …

Pick one, append it, run the step again.

The model calculates those scores through many Transformer layers. Each input token starts as a learned vector combined with information about its position. Attention lets the representation at one position draw information from other permitted positions in the sequence. Feed-forward layers then transform each position, while residual connections carry earlier representations through the network. Repeating these operations produces the final logits for the next token.

Attention can relate a pronoun to a name several sentences earlier or a variable use to its declaration. During autoregressive generation, a causal mask prevents a position from using tokens that have not been generated yet. The model can use the prompt and earlier output, then produces one new position. Serving systems cache intermediate attention data from earlier positions so each step does not recompute the entire sequence.

The model uses this generation loop for every instruction. When asked to translate a paragraph, it produces the continuation that training has associated with translation requests. Prompt wording changes the input sequence, and examples provide a pattern for the continuation. An ambiguous prompt can support several plausible continuations, so repeated requests may produce different answers.

This shared mechanism explains why one model can perform many tasks without a separate program for each one. A translation example, a code fragment, or a required response shape changes the conditional distribution for the continuation. The model has learned patterns associated with those tasks during training, and the request selects among them. The surrounding application still has to check whether the selected behavior satisfies the user's actual requirement.

Tokens and Tokenization

A tokenizer divides text into the units that the model reads and generates.

Before prediction begins, a tokenizer splits the input into tokens. One token may hold a whole word or only part of one. Punctuation and whitespace consume tokens too, and some tokenizers can represent raw bytes. Many model families use a variant of byte-pair encoding or a related subword method that gives frequent sequences their own tokens while dividing rarer text into smaller pieces. English prose often uses fewer tokens than source code or text in some other languages, although the exact ratio depends on the tokenizer and the material.

The tokenizer chooses boundaries from patterns in its training data. A frequent identifier may become one token, while an unfamiliar identifier splits into several. Numbers that lack a familiar pattern may split into several tokens too. Because model families can use different tokenizers, they can assign different token counts to identical text.

Tokenization balances vocabulary size against sequence length. A vocabulary with many whole words shortens common text but needs a larger output layer and handles unfamiliar words poorly. A smaller subword vocabulary can represent new names and mixed-language text, although it produces longer sequences. Byte-level fallbacks guarantee that arbitrary input can be represented, including unusual Unicode or source-code characters.

tokenization.txt Text 
"The quick brown fox"   →  [The] [ quick] [ brown] [ fox]      4 tokens
"getUserById"           →  [get] [User] [By] [Id]              4 tokens
"x7f3a9"                →  [x] [7] [f] [3] [a] [9]             6 tokens

(Illustrative; boundaries differ between tokenizers.)

Tokens are the unit used for the context limit and for most model pricing. Processing more tokens generally requires more computation, which affects latency. The later sections therefore use token count when discussing input or output length.

Character count is therefore a poor estimate of model work. A short string of identifiers, encoded data, or uncommon characters can use more tokens than a longer paragraph of familiar prose. Applications that enforce budgets should count with the tokenizer for the selected model rather than assume a fixed characters-per-token ratio.

The Context Window

Every input and generated output token uses part of a request's finite context window.

A model conditions its predictions on a bounded token sequence called the context window, which contains the input and generated output considered during one request. Instructions and user messages consume its capacity, as do supplied files and tool results. An API may reserve part of the window for the answer, leaving less room for input than the headline limit suggests. If a conversation no longer fits, the host can reject the request. Otherwise it must shorten the input by removing or summarizing older material, or retrieve that material only when needed.

A context window belongs to one model request. A chat application creates the appearance of a continuing conversation by sending selected earlier messages again on later requests. An agent harness may add summaries, repository instructions, or tool observations to those requests. Information stored in a conversation database does not influence a model call until the application includes or retrieves it.

This distinction separates model capacity from application memory. A larger window lets one request contain more source material, while an external memory system can retain far more information across requests. Retrieval decides which stored information should return to the window. Summarization compresses earlier material but may remove a condition that becomes important later.

Modern context windows can hold far more text than earlier generations, and some models accept hundreds of thousands of tokens or more. The larger limit lets an application supply more material. Processing more material increases work and cost, and models may not use every position in a long context equally well.

Long-context evaluations have found cases where models use relevant information near the beginning or end more reliably than information in the middle. Researchers call this position-dependent pattern lost in the middle. Its shape and severity depend on the model, task, and prompt length. The curve below illustrates one possible pattern. Fitting a fact inside the window does not guarantee that the model will use it reliably.

Long context creates a selection problem even before the limit is reached. Several passages may refer to similar names, and later tool output may contradict an earlier observation. Clear source labels, current-state summaries, and removal of obsolete material can make the relevant evidence easier to distinguish. Repeating every available document usually spends tokens without resolving which source should govern the answer.

Sequential generation and finite context explain several application-level behaviors. The model may produce a plausible function signature from learned patterns even when no source in the context confirms it. Relevant information can be difficult to use when it is buried in a long request. More input and output tokens increase the computation required for the request.

Why context files should be small

The context files covered earlier in the series consume part of this budget whenever a tool loads them. Short, relevant guidance leaves more room for the task itself. Context engineering applies this budgeting decision across an entire session.

Sampling and Temperature

Prediction produces several possible next tokens, so generation needs a method for selecting one of them.

Prediction produces a probability distribution over possible next tokens. Sampling selects one token from this distribution. A system may always choose the highest-probability candidate, or it may choose randomly with probabilities weighted toward the stronger candidates. Random selection allows several plausible continuations across repeated runs.

Temperature reshapes the distribution before sampling by changing how strongly the leading candidates are favored. Lower values narrow the choice, while higher values give unlikely candidates more probability. APIs commonly treat zero as a request for the least random mode, although exact determinism depends on the provider and serving system. A related setting called top-p limits sampling to the smallest group of candidates whose combined probability reaches a chosen threshold.

Temperature and top-p change selection after the model has produced its logits. They do not change the evidence available to the request or repair an incorrect learned association. Using both aggressively can make behavior difficult to reason about, so applications commonly tune one while leaving the other near its provider default.

Schema-constrained generation narrows the valid continuations further. A serving system can prevent output tokens that would violate a JSON schema or tool-call grammar. This improves structural validity, but a valid field can still contain the wrong identifier or an unsupported claim. Syntax constraints and factual verification solve different problems.

Sampling allows one prompt to produce different answers across runs. Temperature controls the amount of variation among the candidates. If the model gives a false answer the highest probability, a lower temperature may produce the false answer more consistently. Applications must verify factual claims regardless of the temperature setting.

Training and Model Knowledge

The model builds an answer from the current request and associations learned during training.

During pretraining, the model repeatedly predicts text from a large corpus and adjusts its parameters to reduce prediction error. It learns linguistic patterns, code structures, and factual associations through this process. Post-training then teaches the pretrained model to follow instructions and interact with users. Providers may use supervised fine-tuning or preference optimization at this stage. Reinforcement learning from human feedback (RLHF) is one well-known approach.

Pretraining turns examples in the corpus into distributed parameter changes. The resulting weights are not a document store with a stable key for each source. A model can reproduce some memorized sequences, especially when they appeared repeatedly, yet it cannot enumerate its training records or attach a reliable source to every association. This is why learned knowledge behaves differently from a database or search index.

Post-training changes which learned behaviors the model tends to produce. Instruction examples teach request and response patterns, while preference data favors outputs judged more useful or safer. Tool-use training can teach the model to emit a structured call when external information is needed. None of these stages gives the model direct access to a live system at inference time. The host must provide the tool and execute the call.

A provider may publish a knowledge cutoff as a product-level guide to the period covered by training. The date does not prove that the model learned every earlier fact. Applications should supply information about a newly released library, renamed API, or recent incident through the request or a tool.

A hallucination occurs when plausible generation produces an unsupported or false claim. At generation time, the model continues patterns from its parameters and current context. An application must provide a source of record through context, retrieval, or a tool when an answer needs factual support. Sparse or conflicting evidence can produce a convincing function name or citation that does not exist.

Several paths lead to a similar visible failure. The requested fact may be absent from training and context. A relevant passage may be present but difficult to use among competing text. Sampling may choose a plausible continuation unsupported by the evidence. Diagnosis therefore begins by inspecting the supplied sources and the generated claim rather than treating every false answer as a training-data problem.

Fluency makes hallucinations easy to miss because correct and incorrect claims can use equally assured prose. An uncertainty estimate may warn the application, and citations can show which sources were supplied. Consequential claims need comparison with an authoritative source.

A system that depends on current, private, or verifiable facts must provide them at request time. Tools can fetch live records or act on external systems, and MCP standardizes one way to expose those capabilities. Retrieval selects relevant documents and places them in the context before generation. Semantic retrieval performs this selection with embeddings, the concept introduced next.

Embeddings for Retrieval

Retrieval systems often use a separate embedding model to represent passages as vectors that search can compare.

The embedding model used for retrieval is separate from the generative LLM described above. It accepts text and returns a vector that represents the text for a retrieval task. Training arranges these vectors so related texts tend to be near one another. A password-reset question may therefore be near account-recovery instructions even when they share few words. A passage about database migrations would usually be farther away. These retrieval vectors should not be confused with the token representations used inside a generative model.

A retrieval system compares vectors with a similarity measure such as cosine similarity or a dot product. The index can return the nearest stored vectors without asking the generative model to read every document. Distance is only a ranking signal. Two passages can be semantically related while disagreeing, and the nearest passage may still be irrelevant to the user's specific constraint.

Lexical search answers a different question by matching terms in the query and document. It often handles exact identifiers, product codes, or error messages better than semantic similarity. Many retrieval systems combine lexical and vector scores, then use a reranker to examine the strongest candidates in more detail. The RAG article develops that pipeline and its evaluation.

Semantic retrieval uses the vector space as an index. The system embeds chunks of the corpus ahead of time and embeds each incoming query, then searches for nearby vectors. Repository indexes can use this method to find semantically related code even when filenames differ. Retrieval-augmented generation performs this search before placing selected chunks into the model's context. Vector-capable databases provide efficient nearest-neighbor search for large indexes.

Inference Cost and Latency

Latency and price both follow from how much computation inference requires.

Processing more input requires more computation and memory, even though serving systems reuse intermediate work to avoid recalculating the whole prompt for every output token. Longer context therefore tends to increase latency and cost. Providers commonly expose that cost through token-based pricing because token counts closely track the amount of input and output the service processes.

Inference has two visibly different phases. During prefill, the service processes the supplied input and builds the attention cache used for generation. During decode, it produces output tokens sequentially using that cache. A long document raises prefill work, while a long answer extends the decode phase and delays completion one token at a time.

Input and output contribute to latency in different ways. A provider can process the prompt in parallel across its token positions. Autoregressive output is decoded sequentially, so long answers add visible wall-clock time token by token. Providers often charge more for output tokens, with the exact ratio set commercially.

Serving systems batch requests to use accelerators efficiently, which can improve throughput while adding queueing delay for an individual request. Prompt caching can reuse work for an identical prefix, but only the unchanged portion benefits. Changing an early system instruction may invalidate the reusable prefix and force another prefill.

Large price differences between model tiers make routing part of application design. Applications can reduce work by sending useful context and requesting focused output. A smaller model may handle a bounded task adequately. Providers that support prompt caching can avoid processing an unchanged prefix repeatedly. The assistants article applies these choices to agent workloads, where repository context can dominate usage.

Application Design

The generation process determines how applications should manage context and verify results.

Applications should reserve context for information that supports the current task. Retrieval can reduce cost and improve reliability by selecting relevant material from a larger collection. Important evidence should be placed where the model can use it reliably within the final prompt.

A documentation assistant provides a useful example. The application retrieves passages from the current manual, labels their source and version, and asks the model to answer only from those passages. If retrieval finds no adequate source, the safe response reports that gap. Increasing temperature or adding more unrelated documentation would not provide the missing evidence.

The surrounding system must verify generated results. Temperature can reduce variation, but correctness requires evidence outside the model's wording. The plan review and risk-tiered code review described elsewhere in the series provide concrete verification gates.

Systems that depend on current or private facts need a grounding path. Tools can read live records and perform actions. Retrieval can select evidence from a document corpus. The application must define a safe response when these sources provide insufficient or conflicting evidence.

Token volume affects both cost and latency. Applications can reduce it by selecting relevant context and requesting focused output. Prompt caching and model routing can reduce repeated or unnecessarily expensive work. Each choice responds to the generation costs explained above. Models generate sequentially from bounded context and statistical predictions, so applications must supply and verify any facts their users depend on.
