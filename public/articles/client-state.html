Client State

How ownership, placement, organization, and propagation determine where application data belongs.

Andreas Ögren
~11 min read
Last updated July 2026

For much of the 2010s, frontend state management revolved around a single global store. Form input, interface toggles, and API responses could all pass through the same dispatch mechanism and appear in the same development timeline. Redux became a common answer to several problems that did not share the same lifecycle.

Careful teams still kept local interface state separate from fetched data. The harder problem was that few tools were designed specifically around the lifecycle of server-owned data. Product records therefore passed through the same actions and reducers as client-owned values such as an unfinished cart. The store accumulated loading flags, error handling, and refetch logic because it was being asked to coordinate a cache as well as application state.

A more useful model separates state management into four questions. First establish who owns the data, then decide where it belongs, how shared state should be organized, and how changes reach the screen. The sections below follow that order.

State Ownership

Client state and server state are distinguished by authority rather than by the side of the network holding a copy.

Ownership identifies the authoritative source for a piece of data. Product prices, account balances, and shipping statuses are owned by the server even when the browser displays or caches them. An optimistic update may change the browser's copy immediately, but the server can still accept, reject, or replace that value. Data with this lifecycle is commonly called server state.

The open state of a dropdown, text that has not yet been submitted, and the active tab usually belong to the browser. Their lifecycle begins and ends with the interface unless the product deliberately persists them elsewhere. Data governed by that lifecycle is client state.

Ownership is independent of rendering strategy. A server-rendered page gains client-owned state as soon as a menu opens, while a single-page app holds server-owned state after fetching a record. Confusing ownership with rendering location leads to misplaced data and unnecessary synchronization code.

Forms of Client State

Once server-owned data is set aside, client state separates into four forms with different lifecycles.

Ephemeral state exists only to drive the current interface. Examples include an open dropdown, a hovered row, and text entered before submission. It usually belongs to one component and can disappear when that component unmounts, so the framework's local-state primitive is often sufficient.

Other values need to survive a refresh, participate in browser history, or travel in a shared link. Product filters, settings tabs, and pagination often belong in the URL as navigation state. Keeping them only in memory makes a refreshed or shared page lose its context. UX Principles covers the design of stable, deep-linkable routes.

Application state is client-owned data shared across distant parts of the component tree. It is neither tied to one component's lifetime nor represented fully by the current URL. A theme, an unfinished client-side workflow, or a cart with local changes may fit this category. These values are the main candidates for a shared-state library.

Derived state is computed entirely from other values. A cart total comes from its line items, while a filtered list comes from a source list and a search term. Storing the result independently creates another value that must be synchronized. Computing it when needed, with memoization when the work is expensive, preserves a single source of truth.

A stored total is a total that can lie

A stored cart total can disagree with its line items after a missed update or competing writes. Computing the total from those items removes that synchronization path. Memoization can avoid repeated work when the calculation is expensive.

Redux and the Global Store

Redux gave large applications predictable coordination, but fetched data brought a different lifecycle into the same mechanism.

Before Redux, teams often coordinated distant parts of a component tree through long callback chains or ad hoc global objects. Redux replaced those arrangements with one store, explicit updates through actions and reducers, and development tools that expose the update sequence. Those properties remain useful when client-owned state is broad enough to need central coordination.

Fetched data complicated that model because a store does not automatically provide cache semantics. Teams implemented loading states, retries, invalidation, and refetching in reducers, thunks, or sagas. Much of the resulting boilerplate belonged to a hand-built cache rather than to the coordination of client-owned state.

Redux Toolkit didn't disappear

Redux Toolkit remains a reasonable option for complex client-owned state that crosses many features. Dedicated data-fetching tools narrow that use case by giving server-owned data a cache with its own lifecycle.

Server State as a Cache

When the server owns the data, the browser manages a copy whose freshness must be explicit.

A cache holds a reusable copy that may become stale and can be replaced after revalidation. A client store, by contrast, usually changes in response to an explicit local update. Server-owned data follows the cache contract because the browser cannot know whether another actor has changed the authoritative value.

Server-state libraries key requests by their parameters and track whether the cached result is fresh, stale, loading, or failed. They can keep stale data visible while fetching a replacement and can deduplicate concurrent requests for the same key. The application describes a freshness policy instead of recreating the request lifecycle in each component.

TanStack Query is a prominent example, with adapters for React, Solid, Vue, Svelte, and Angular built around the same query core. The shared model reflects a framework-independent concern: cached server data needs keys, freshness rules, invalidation, and request coordination. Once ownership is established, those cache semantics matter more than the component model used to display the result.

Stores and Atoms

Stores and atoms describe the shape of shared state. Propagation is a separate concern.

Client-owned application state can be organized as one store or as smaller independent units. A store-based approach keeps related fields behind one shared boundary. Components subscribe to selected slices and update the store through actions or setter functions. Redux Toolkit and Zustand both follow this broad shape, although their APIs and conventions differ.

An atom-based approach represents state as small, independently addressable units. Jotai is built around this model. A component subscribes to the atoms it reads, while derived atoms compose values without requiring one large object. Store libraries can reach similar subscription granularity through selectors, but the application must define those boundaries deliberately. A broad Context value has the opposite behavior, as explained in Context as a global store.

A cohesive state model often fits a store, especially when updates span several related fields. Atoms suit state that changes independently or composes naturally from smaller pieces. Redux Toolkit adds strong conventions and development tooling, while Zustand exposes a smaller store API and Jotai makes atomic composition the organizing principle. The useful distinction is the shape of the state, not a popularity ranking among libraries.

Stores and atoms answer how state is organized and subscribed to. The framework's reactivity model answers how a changed value reaches the rendered interface.

Signal-Based Reactivity

The store-versus-atom question was about how state is organized. This one is about how a change reaches the screen.

React's model is component-centric. A state update schedules rendering for the component that owns it. React may also render descendants unless memoization or another optimization lets it skip them. Reconciliation then determines which host elements need to change. The state value itself does not retain a list of the DOM bindings that consumed it.

Signals make dependency tracking part of the reactive value. A computation or template that reads a signal becomes one of its dependents. A later write can notify that narrower set instead of treating an entire component subtree as the initial unit of work. The exact scheduling and DOM update mechanism still varies by framework.

Solid builds its rendering model around fine-grained reactive primitives. Angular uses signals for reactive values and has made zoneless change detection the default in version 21 and later. Svelte 5 exposes compiler-supported reactivity through runes such as $state and $derived. Preact offers signals as a separate package. These systems share dependency tracking as an idea, but they do not all implement rendering in the same way.

React keeps this responsibility at the component and subscription level. Libraries such as TanStack Query, Zustand, and Jotai add cache or state subscriptions with narrower update boundaries, but they remain separate tools because they solve different ownership and organization problems. Signals change propagation mechanics. They do not decide whether data belongs in a cache, a URL, or application state.

When a Library Helps

Once ephemeral state has a hook, navigation state has the URL, and server state has a cache, what's left over for a dedicated library is often smaller than it looks.

Many applications can place most state without a global store. Ephemeral values remain local to a component, navigation state lives in the URL, and server state belongs in a cache. The remainder may be small enough for a nearby parent or a focused Context provider. A library becomes useful when that remainder spans unrelated parts of the tree or needs more selective subscriptions.

State shared between two adjacent components doesn't need to be promoted to global scope either. Lifting it to their nearest common parent and passing it down usually solves the problem with less machinery than a store would add.

When a store earns its place

A store or atom library earns its place when unrelated parts of the tree read and write the same client-owned state, or when selective subscriptions materially reduce unnecessary work. Complex editors, collaborative canvases, and dashboards with interacting controls often reach that point. The deciding evidence should come from ownership and update patterns rather than component count alone.

Choosing Where State Belongs

The four questions from the start of this article form one placement sequence.

Start with ownership. Server-owned data needs cache semantics. For client-owned data, ask whether the value should survive a refresh, appear in browser history, or travel in a link. If so, represent it in the URL. Everything else should remain near the components that use it until distant consumers or selective subscriptions justify a shared boundary.

The remaining candidate is client-owned state that does not belong in the URL and is shared across distant consumers. A store fits a cohesive model, while atoms fit independently changing pieces. Native signals may provide the required propagation mechanism, but they do not remove the need to place and organize the state deliberately.

The global-store era treated ownership, placement, organization, and propagation as one decision. Separating them produces smaller and more durable state boundaries. The library choice comes last, after the data's authority and lifecycle are understood.
