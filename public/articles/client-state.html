Client State

Why treating client and server state as one problem broke down, and the four questions that replaced it.

Deep dive
~15 min read
State management
July 2026

For a long stretch of the 2010s, state management meant one thing: put everything into a single global store and read it back out with selectors. It didn't matter whether the data came from a user typing into a form, a toggle in the interface, or a response from an API call. All of it went through the same dispatch mechanism and showed up in the same devtools timeline. Redux was the default answer almost regardless of the question being asked.

That collapse didn't mean every Redux app mixed a dropdown's open state and an API response in the same reducer without a second thought. Plenty of teams kept that boundary clean. The real gap was that Redux was the only tool built for coordinating state at all, so a product record fetched from an API got coordinated through the same actions and reducers as genuinely client-owned data, because nothing else was designed to hold it. A shopping cart shared across three components and a product fetched from an API don't share a lifecycle, and coordinating both by hand through the same mechanism is what made the store's async logic swell.

What follows treats client state as four separate questions instead of one collapsed problem. The table below maps each question to the section that answers it. The article then works through them in order, ending with a framework for placing any given piece of state correctly.

Ownership, Not Location

Client state and server state aren't defined by which side of the network they run on. They're defined by who's allowed to change the answer.

The distinction that matters is ownership: which side of a system is the authoritative source for a piece of data, and therefore has the final say over when it changes. A product's price, a user's account balance, and an order's shipping status are all owned by the server, even though a browser might display them, cache them, or optimistically update them the moment a user acts. Whatever the browser is holding is, at best, a recent copy. Data whose lifecycle is owned this way is usually called server state.

Whether a dropdown is open, what text is currently typed but not yet submitted, and which tab is active are owned by the client instead. No server request created them and none can override them, because the server was never asked and has no opinion on the matter. Data owned this way is client state.

Ownership doesn't track rendering strategy. A page rendered entirely on the server for its first paint still has client-owned state the moment a menu opens in the browser, and a single-page app still has server-owned state the instant it fetches a record over the network. The question of who owns a piece of data is separate from the question of where its markup gets produced, which is why the two get confused so often. Conflating them is what led teams to store server-owned data in tools built for client ownership, and to build ad-hoc syncing logic to keep client-owned drafts in a database table that never needed to know about them.

The Shapes of Client State

Once server-owned data is set aside, what's left splits into four kinds, and only one of them should usually be avoided.

The smallest and most common kind is ephemeral state: values that exist only to drive the interface in the moment, like whether a dropdown is open, which row is hovered, or what a user has typed into a field before submitting it. It usually lives in a single component, disappears the instant that component unmounts, and never needs to be shared, so a built-in hook is normally the entire solution.

Some state looks ephemeral but isn't, because a user expects to bookmark it, share it, or hit the back button and land where they left off. Filters on a product listing, the active tab on a settings page, and the current page number in a paginated table all belong in the URL as navigation state rather than in memory. Storing them in a component instead is why refreshing a filtered search so often resets it to defaults.

Application state is what's left once the first two categories are excluded: data shared across parts of the tree that don't share a nearby parent, and that isn't tied to one URL or one component's lifetime. An authenticated user's profile, a shopping cart, and a color theme are typical examples. This is the smallest category in practice, and it's the one people reach for a dedicated library to manage.

The fourth kind is derived state: a value computed entirely from other state, such as a cart's total price computed from its line items, or a filtered list computed from a source list and a search term. Derived state is the one kind that usually shouldn't be stored at all. Storing it means it can drift out of sync with the values it was computed from, a bug class that computing it fresh on every render eliminates by construction.

A stored total is a total that can lie

A cart total kept in its own field will eventually disagree with its line items, whether from a missed update path or a race between two handlers. Computing it on read, or memoizing the computation, costs a little more CPU time and guarantees it's never wrong.

What Redux Got Right, and Where It Was Misapplied

Redux solved the coordination problem it was built for. The problem was never really "too much state" so much as the wrong state ending up in it.

Before Redux, coordinating state across a large tree meant passing callbacks down through however many component layers separated a change from the components that needed to react to it, or reaching for whatever ad-hoc global object a team invented that week. Redux replaced both with one store, one way to change it through actions and reducers, and a devtools timeline that could replay any sequence of updates. For genuinely global, frequently cross-cutting application state in a large codebase, that combination was, and still is, a real improvement over the alternatives it replaced.

What actually drove the "Redux everywhere" era wasn't the store's design. It was the absence of anywhere else to put fetched data. Before dedicated server-state tools existed, a product record pulled from an API had nowhere purpose-built to live, so it went into the same store used for coordinating client-owned state instead, regardless of how carefully a given team kept its reducers organized. Every team then built its own loading flags, error handling, and refetch logic by hand inside reducers, thunks, or sagas, and every team's version had slightly different bugs. The complaint that followed was "Redux has too much boilerplate," but the boilerplate was mostly the cost of manually reimplementing a cache, not a cost of coordinating client-owned state.

Redux Toolkit didn't disappear

Large, established codebases with genuinely complex, deeply cross-cutting client state still use Redux Toolkit in 2026, and it remains a reasonable choice for that specific problem. What changed is the size of the problem it gets reached for, now that server data has somewhere else to go.

Managing Server State as a Cache

If the server owns the data, the client's job was never to store it correctly. It was to keep an appropriately fresh copy.

A cache, in this sense, is a local copy of data that's allowed to be temporarily wrong, expires on a known schedule, and can be silently replaced with a fresher copy without anyone needing to be told. That's a different contract than a store, which promises the data inside it is correct until something explicitly changes it. Server-owned data can only ever meet the cache contract, because the client was never the authority on it in the first place.

Tools built around this idea fetch data, keep it under a key derived from its parameters, mark it stale after a configurable window, and quietly refetch it in the background while the stale copy keeps rendering, a pattern generally known as stale-while-revalidate. Loading and error states fall out of the fetch's own lifecycle instead of being tracked by hand. Two components requesting the same data at once get deduplicated into a single request rather than firing twice.

TanStack Query, which began life as React Query, is the clearest example and by 2026 the default choice for this job in most new React codebases. It's also deliberately framework-agnostic. The same caching core ships as Solid Query, Vue Query, and Svelte Query, a reasonable sign that the underlying pattern is a general answer to server-owned data rather than a trick specific to one framework's rendering model. The deeper mechanics of cache invalidation, staleness windows, and how this interacts with browser and CDN caching are worth a dedicated look elsewhere. What matters here is narrower: once a value is recognized as server-owned, reaching for a cache instead of a store is the direct consequence of the ownership question from earlier, not a separate decision.

One Store vs. Many Atoms

This is a question about shape, not about how updates travel. That question comes next.

Once a piece of state is confirmed as client-owned application state, meaning it survived both the taxonomy above and the "do you actually need to store this" question that closes this article, there's still a choice about how to organize it. A store-based approach keeps one shared object holding many fields, updated through actions or setter functions, with components subscribing to whichever slice they read. Zustand and Redux Toolkit both work this way, differing mainly in how much ceremony sits between a component and an update.

An atom-based approach splits the same state into many small, independently addressable units instead of one object, an approach Jotai is built around. A component that reads one atom only re-renders when that specific atom changes, regardless of how many other atoms exist elsewhere in the app. That avoids a failure mode store-based approaches have to solve deliberately with selectors: a broad store update causing every subscriber to reconsider itself even when most of them don't care about the field that changed.

By 2026 the practical split is fairly settled. Zustand has become the default lightweight store for most apps that need one, largely because it requires no provider wrapping and has a small enough API to learn in an afternoon. Jotai holds a real niche wherever atomic granularity matters enough to be worth the extra conceptual step of thinking in individually composable units. Redux Toolkit persists mainly in large, already-established codebases that were built around it and have no pressing reason to migrate.

Whichever shape client state takes, updating it in either model still means telling the framework to re-render whatever depends on it. That's a separate question from how the state is organized, and it's where the next section picks up.

Signals: A Different Reactivity Model

The store-versus-atom question was about how state is organized. This one is about how a change actually reaches the screen.

React's model is component-centric. When state changes, React re-renders the component that owns it and, by default, the subtree beneath it, computes what the result looks like, and diffs that result against the previous render before patching only the parts of the real document that actually differ. The state change itself doesn't know what depends on it. The framework finds out by re-running components and comparing outputs.

Signals take a different approach: a signal tracks, at the moment it's read, exactly which computations or DOM bindings depend on it, so when its value changes, only those specific dependents update. Nothing re-runs a component function, and nothing diffs a tree, because the framework already knows precisely what needs to change and updates it directly.

By 2026, signals have become the norm almost everywhere except React. Solid pioneered the fine-grained version of this model and remains the performance reference point for it. Angular made signals the default reactive primitive and, starting with Angular 21, ships zoneless by default. That means it no longer needs Zone.js patching every asynchronous browser API just to detect that something might have changed. Zone.js became fully optional in Angular 22, cutting bundle size and removing a layer of change-detection overhead that used to run on every event regardless of whether it mattered. Svelte 5's runes look like ordinary variables, using $state, $derived, and $effect instead of a signal's usual get and set syntax, but they converge on the same signal-style tracking underneath. Preact ships signals as an add-on that can even be used inside a React tree for the specific components that need fine-grained updates without leaving the ecosystem.

React staying component-centric isn't an oversight. It's arguably the reason the React ecosystem grew so many separate, specialized tools instead of folding server caching and fine-grained client updates into one built-in primitive. TanStack Query, Zustand, and Jotai each solve part of a problem that frameworks with native signals solve with one reactive model. Placement, in a React codebase, is partly a workaround for a reactivity model that was never built to do fine-grained updates on its own.

Do You Need a Library at All?

Once ephemeral state has a hook, navigation state has the URL, and server state has a cache, what's left over for a dedicated library is often smaller than it looks.

A typical 2026 app handles most of its state without reaching for a global store. Ephemeral state lives in useState or useReducer and dies with its component. Navigation state lives in the URL through a router's search params. Server state lives in a cache. What remains is genuine application state, and in a lot of products that's a short list, small enough for React's context API or its framework's equivalent to handle without a dependency: an authenticated user, a theme, maybe a cart.

State shared between two adjacent components doesn't need to be promoted to global scope either. Lifting it to their nearest common parent and passing it down usually solves the problem with less machinery than a store would add.

When a store earns its place

Reach for Zustand, Jotai, or an equivalent once state is read and written from many unrelated parts of the tree, changes at high frequency, or needs derived selectors to avoid re-rendering components that don't care about the specific field that changed. A multi-step wizard, a collaborative canvas, or a dashboard with dozens of interacting filters are typical cases where context alone starts causing broad re-renders or turns into prop drilling, and a proper store pays for itself.

Choosing Where State Belongs

The four questions from the start of this article resolve, in practice, into one sequence.

Start with ownership: is the server the authoritative source for this data? If so, the answer is a cache, not a store, and trying to keep a hand-synced copy correct is solving a problem a caching library already solves better. If the data is genuinely client-owned, ask whether it needs to survive a page refresh or be shareable through a link. If it does, it belongs in the URL as navigation state, not in memory. If neither applies, ask whether the state is local to one component or a couple of adjacent ones. If it is, local state is not just sufficient but preferable, since promoting it to a global store adds indirection with nothing to show for it.

What's left after all three questions is the actual candidate for a store or an atom set: state that's genuinely client-owned, doesn't need to live in the URL, and is read or written across distant, unrelated parts of the tree. Which of those two fits depends on whether the state naturally forms one cohesive object or a set of independently changing pieces. If the framework already has native signals, a good part of the propagation question may already be handled without adding anything at all.

The failure of the "Redux everywhere" era wasn't that a global store is a bad idea. It's that one tool was asked to answer all four of these questions the same way, for every piece of state, regardless of what actually owned it or how it needed to update. Placing state correctly was always less about which library gets installed and more about answering ownership, placement, organization, and propagation honestly for each piece of data as it's created.
