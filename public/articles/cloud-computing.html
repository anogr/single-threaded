Cloud Computing

What cloud computing actually trades against an internal data center, the service categories every provider shares, and where AWS, Azure, and GCP differ.

Deep dive
~17 min read
Cloud infrastructure & providers
July 2026

Two teams can both say they run "in the cloud" while doing almost nothing alike. One provisions virtual machines and patches them the same way it always has, just on someone else's hardware. The other has never configured a server directly, calling managed services through an API and letting a provider handle everything underneath. Both are accurate uses of the term, which is exactly why the term alone explains so little.

This article starts with that spectrum and works outward. It starts with what actually changes between running infrastructure yourself and renting it, including where cloud costs more rather than less. From there it covers the building blocks that exist across every major provider: compute, storage, networking, managed data, messaging, and identity. It closes with the differences between AWS, Azure, and GCP that actually change an architecture decision, and the portability tradeoffs a provider choice carries with it.

What "Cloud" Actually Means

The term spans a range of how much infrastructure responsibility a team keeps. It isn't one technology.

Cloud computing is on-demand, self-service access to computing resources, provisioned in seconds or minutes and able to scale automatically, delivered over the internet. Those resources are provisioned and controlled through APIs rather than by hand, the property that makes automation, infrastructure as code, and continuous delivery pipelines possible in the first place. Billing is typically usage-based, renting the underlying hardware instead of owning it, though many services also support reserved or committed capacity at a lower price once usage is predictable. This article contrasts cloud against that alternative throughout: on-premises infrastructure, a company buying, racking, and operating its own servers in its own data center.

Cloud doesn't only mean a public provider like the ones this article focuses on for most of its length. Private cloud runs the same self-service, on-demand model on infrastructure dedicated to a single organization. Hybrid cloud deliberately combines the two rather than treating the choice as all-or-nothing, a pattern the next section returns to.

One more idea is worth introducing before anything else: the shared responsibility model. A provider operates and secures the underlying infrastructure below a boundary line, and the customer is responsible for everything above it: their own identity and access policies, network configuration, encryption choices, secrets, and application code. Exactly where that line sits shifts by service model, the subject of the section right after the on-premises comparison below.

Virtualization made this technically possible, letting one physical machine run many isolated environments at once, and Amazon Web Services' 2006 launch popularized paying for compute by the hour instead of buying a server outright. The specific unit has changed since: per second, per request, per gigabyte. The same idea, paying for what's used instead of what's owned, is still underneath almost every cloud billing model today.

Cloud vs. On-Premises

Elasticity is the headline benefit. It isn't the only line in the ledger.

The clearest advantage cloud infrastructure has over on-premises hardware is elasticity: capacity that expands and contracts with actual demand instead of sitting fixed at whatever was purchased. An on-premises deployment has to be sized for a projected peak: end-of-quarter processing, a product launch, a seasonal traffic spike. It then carries that full capacity as a fixed cost every day demand sits well below it. A cloud deployment can provision for the peak only while the peak is happening, and scale back down once it passes.

The rest of the comparison is more mixed, and worth laying out directly rather than assuming cloud wins on every dimension.

That last row is the one most easily overlooked in a conversation that otherwise favors cloud by default. At steady, predictable, high utilization, the ongoing cost of rented capacity can exceed the cost of owned hardware over a multi-year horizon. That's why cloud repatriation is worth naming: a company moving a specific, steady workload back on-premises or to colocation after initially defaulting to the cloud. It has become common enough that many organizations evaluate individual workloads for it, rather than treating the direction as fixed. It's evidence the decision runs in both directions, not a case against cloud generally. The workloads that get repatriated are usually the steady, predictable ones that never needed elasticity in the first place. Anything with variable demand tends to stay.

Many organizations land on a resolution rather than picking a side: hybrid cloud. It means keeping a specific workload on-premises for a reason like compliance or an existing capital investment, while running everything else on a public provider. Treated this way, the choice isn't binary at all. It's a workload-by-workload decision informed by the table above, applied separately to each system rather than to an organization as a whole.

The Service Model Spectrum

IaaS, PaaS, and SaaS are usually taught as three separate boxes. They read more clearly as one spectrum with a boundary that moves.

Infrastructure as a service (IaaS) rents the lowest-level building blocks, virtual machines, storage, and networking, leaving the operating system, runtime, and application entirely to the customer. Platform as a service (PaaS) moves the boundary up a layer: the provider also manages the operating system and runtime. The customer deploys application code onto a managed platform without configuring a server underneath it. Software as a service (SaaS) moves the boundary up again: the customer uses finished software, an email service or a CRM product, and manages none of the infrastructure or code behind it.

Serverless describes an operational model rather than a single product category: the provider manages the underlying servers entirely, and the customer never provisions capacity directly. Function as a service (FaaS) is the best-known example: code that runs only in response to an event and is billed per invocation. The same model shows up wherever a provider removes capacity planning from the customer's side. Serverless databases, serverless containers, and serverless messaging all apply the same idea to a different primitive.

The shared responsibility model introduced earlier becomes concrete once it's laid out layer by layer.

Networking doesn't appear as a fifth row on purpose. It isn't one point in the stack the way application or storage are. It's configured at every level from IaaS upward, rather than living at a single layer, which is why the next major section covers it on its own.

Two qualifications keep the table honest otherwise. A provider-managed layer narrows the operational work, patching, uptime, scaling, but rarely removes the customer's responsibility for configuring access to it correctly. A misconfigured permission on a fully managed database is still the customer's problem, even though the database itself is entirely the provider's. Exactly where a specific product draws its own line can also vary. The table shows the general pattern, not a guarantee for any one service.

Compute: VMs, Containers, and Functions

Four common ways to run a workload, each suited to a different shape of problem.

A virtual machine is the IaaS-level compute primitive: an emulated computer with its own operating system that the customer configures, patches, and scales. It suits a workload that runs continuously, needs direct control over the operating system, or depends on legacy software built to assume dedicated hardware. It's the traditional default, and still a reasonable one for plenty of workloads.

Managed container platforms sit in the middle, ranging from a simple service that runs a single container up to a fully managed Kubernetes offering. The provider operates the underlying cluster infrastructure. The customer supplies containerized applications and describes how they should run. What a container actually is, and how an orchestrator like Kubernetes schedules and scales one, is covered in full in Containers and Orchestration. This article only needs where managed container platforms sit relative to the other compute options.

Serverless functions sit at the far end of the spectrum defined in the previous section: no server management at all. In exchange, they carry constraints like execution time limits and cold starts, the delay when a function spins up from zero after sitting idle. They suit short, event-triggered work, resizing an uploaded image or reacting to a queue message, rather than a service that needs to respond instantly at all times.

A fourth category has become common enough to name on its own: managed machine learning platforms, infrastructure for training and serving models without provisioning GPU or TPU hardware directly. It's the compute-level primitive underneath the AI-specific strengths covered later in the provider comparison, not a separate concern from the compute choices above it.

Cloud-native, defined

Put together, these options define what cloud-native architecture actually means: designing around managed services, automation, and elastic, loosely coupled components. It's a different starting point than treating the cloud as a stand-in for a physical server room running the same architecture as before.

Storage: Object, Block, and File

Three storage types, distinguished by access pattern rather than by vendor product name.

Object storage holds unstructured data retrieved by key through an API, rather than opened and modified in place like a file on a local disk. That access pattern suits things like images, backups, and static assets well. It suits a database's working files poorly, since a database needs to modify small pieces of data in place far faster than an API round-trip allows.

Block storage behaves like a raw disk, typically attached to a single virtual machine, though some platforms support attaching one volume to several instances for specialized clustered workloads. It's exactly what a database's working files need: fast, in-place modification of small regions of data.

File storage provides a shared filesystem that multiple machines can mount and read or write at once. It suits a workload built around shared files, rather than an API or a single attached disk.

Within object storage specifically, providers typically price a standard tier for data read often against a cheaper archival tier for data kept for backups or compliance and rarely retrieved. That tradeoff, slower retrieval in exchange for lower storage cost, is a real, common decision rather than a footnote, and one of the more direct ways a storage choice affects a cloud bill.

Networking and Managed Data

The boundary a customer's resources sit inside, and the two shapes managed data comes in.

A virtual network is an isolated private network layer a customer defines within the provider's infrastructure, the boundary within which the customer's own resources talk to each other. What happens once traffic actually arrives at that boundary, a CDN, a load balancer, an API gateway, is covered in full in Web Application Networking. This article stops at the boundary itself.

A managed database hands patching, backups, and failover for a relational or NoSQL database to the provider. The alternative is self-hosting the same database engine on a virtual machine and owning that operational work directly.

A managed data warehouse serves a different use case entirely: analytical queries scanning large volumes of historical data for reporting. It's optimized for scanning many rows at once, rather than looking up or updating a single record the way an operational database does. Reaching for one over the other is a question of access pattern, not of which is the more advanced option.

Messaging and Identity

Who talks to whom, and who's allowed to do what.

Managed messaging splits into two patterns worth distinguishing by use case. A queue delivers each message to exactly one consumer, suited to distributing work across a pool of workers. A publish/subscribe service delivers a copy of each message to every subscriber, suited to broadcasting a single event to several independent systems at once.

Identity and access management (IAM) attaches permissions to identities, users, applications, or roles, rather than to network location. The principle of least privilege, granting only the access a given identity actually needs, applies here the same way it applies everywhere else. The fewer permissions a compromised credential carries, the less damage it can do. Modern cloud architectures increasingly authenticate a workload using an identity assigned to it directly, rather than a long-lived API key embedded in its configuration, so a leaked secret has less it can be used for.

Regions, Availability Zones, and Designing for Failure

Infrastructure fails. The physical layout of a cloud provider's data centers is built around that fact, not around the hope it doesn't happen.

A region is a geographic location with its own cluster of data centers. An availability zone is an isolated failure domain within a region, with its own power and networking, so a failure in one zone doesn't take down another. Resilience isn't the only reason a region gets picked. Proximity to users keeps latency down, and some workloads have to stay within a specific region for data residency or regulatory reasons, the compliance row from the on-premises comparison earlier in this article.

Because a zone, or even a region, can fail independently, systems are designed around that reality rather than an assumption of permanent uptime. A few habits follow directly from what a zone actually is. Instances run redundantly across zones. Services stay stateless, so any instance can handle any request. No single component's failure should be able to take down the whole system. None of this is unique to any one provider. It's a consequence of the physical layout every major provider uses.

Comparing AWS, Azure, and GCP

The only section where a vendor's product name actually matters.

AWS has the broadest service catalog and the largest global footprint of any provider, plus the largest ecosystem of third-party tooling and the largest hiring pool to draw from. That breadth makes it the common default for a greenfield team with no existing platform commitments. The reason is less that any single AWS service is unmatched, and more that whatever a team eventually needs, AWS almost certainly already offers some version of it.

Azure is strongest where an organization already runs Microsoft infrastructure, Active Directory (now Entra ID), .NET, Windows Server, or Microsoft 365, since identity and licensing integrate directly rather than needing a separate bridge. It has also become a leading option for enterprise AI adoption through Microsoft Foundry, Microsoft's unified AI platform. A company can reach models from OpenAI and other providers through it, inside Azure's own compliance and security boundary, instead of sending data to a separate vendor.

GCP's strengths concentrate in large-scale data analytics, BigQuery, one of the most influential serverless cloud data warehouse platforms, and machine learning infrastructure that includes its own custom processors built for that workload. It's a common entry point for data-focused teams even at companies whose core workloads run elsewhere. Its Kubernetes heritage, Google originated the project, is worth a passing mention but isn't the headline differentiator it once was, and its general enterprise penetration still lags AWS and Azure.

Portability and Lock-In

Compute travels between providers reasonably well. Almost nothing else does.

A virtual machine or a container image runs similarly on any provider, which makes compute the most portable layer of a cloud architecture. The deeper lock-in usually comes from a combination of places whose APIs and behavior don't carry over to another provider. Common examples include IAM policy structure, network configuration, observability tooling, event and messaging systems, managed databases, and increasingly provider-specific AI services. Managed databases remain the single deepest source on their own, but rarely the only one anymore. The data itself is a further, separate source once it's large enough. Moving a large dataset out of a provider costs real time and money, an effect sometimes called data gravity, independent of which specific services touch that data.

Two abstraction layers offer a partial answer. Infrastructure as code, covered in CI/CD and DevOps, and container orchestration, covered in Containers and Orchestration, both describe infrastructure in ways that move between providers more easily than hand-configured resources do. Neither makes a migration free. Both narrow how much of it is manual. Favoring components built on open, non-proprietary interfaces helps too: a managed database that still speaks standard PostgreSQL, or a service that exports telemetry through OpenTelemetry. The interface stays portable even when the infrastructure behind it doesn't.

Multi-cloud means deliberately running workloads across more than one provider, to use each for a specific strength from the comparison above. That trades the lock-in risk from the previous paragraph for real operational complexity: separate expertise, separate tooling, and separate failure modes to reason about in each environment. It's worth that cost for reasons like regulatory requirements or negotiating leverage. It isn't a default goal for a smaller team without one of those reasons already in hand.

Choosing a Provider

The right answer depends on specifics this article can't see: what a team already runs, and where its skills already sit.

The right provider depends on what a team already operates, where the relevant skills already sit, and which managed services actually matter for the workload, more than on any single feature comparison. The provider strengths covered above are a starting point to validate against those specifics, not a conclusion to import wholesale.

It's also worth revisiting the comparison from earlier in this article before assuming the answer is a public cloud provider at all. A steady, predictable, high-utilization workload is exactly the case where that assumption is worth questioning. The right answer for one system inside an architecture doesn't have to be the right answer for every system next to it.

None of this starts with a provider name, in the end. It starts with the same question the opening section raised: how much infrastructure responsibility a given system should hand off, and to whom. The service models, the building blocks, and the provider comparison in between are all ways of answering that one question more precisely.
