Cloud Computing

How renting infrastructure shifts responsibility and cost, the services public clouds provide, and the tradeoffs among AWS, Azure, and Google Cloud.

Andreas Ögren
~14 min read
Last updated July 2026

Two teams can both say they run “in the cloud” while operating very different systems. One may patch rented virtual machines much as it once patched physical servers. Another may deploy only to managed services and never configure an operating system. The label is accurate in both cases, so it says little about how much responsibility each team has retained.

The useful distinction is the boundary between what the provider operates and what the customer still owns. This article begins with that boundary and the tradeoffs between rented and privately operated infrastructure. It then introduces the common building blocks of public clouds before comparing AWS, Azure, and Google Cloud.

What "Cloud" Means

The term describes a range of responsibility boundaries rather than one technology.

Cloud computing provides on-demand network access to a shared pool of configurable resources. Customers can provision capacity without waiting for a provider employee, measure its use, and release it again as demand changes. Provider APIs make that lifecycle automatable through infrastructure as code and delivery pipelines. Pricing often follows consumption, although reservations and spending commitments can reduce rates for predictable use. On-premises infrastructure places the hardware and its operation under the organization's control, whether the equipment sits in its own facility or a colocation site.

Public cloud is only one deployment model. A private cloud offers similar self-service provisioning on infrastructure dedicated to one organization. Hybrid cloud connects private or on-premises systems with public-cloud services, allowing each workload to use the environment that fits its constraints.

The shared responsibility model describes how provider and customer duties divide. The provider secures and operates the cloud infrastructure, while the customer remains responsible for its data, identities, configurations, and application code. The exact division changes with the service model, but consuming a managed service never transfers every security or reliability decision to the provider.

Virtualization allowed providers to divide physical machines into isolated computing environments. The 2006 launches of Amazon S3 and EC2 helped turn storage and compute into resources that developers could provision through an API. Cloud pricing has since expanded beyond rented machine time to include requests, data volume, provisioned throughput, and other service-specific units.

Cloud vs. On-Premises

Elasticity is the headline benefit, but the rest of the cost and control ledger is more mixed.

Elasticity is the clearest advantage over fixed hardware capacity. Privately operated infrastructure must leave enough headroom for expected peaks or accept that demand can exceed supply. Cloud resources can be added for a peak and released afterward, provided the workload and service have been designed to scale that way. Elasticity is an available capability rather than an automatic property of every deployment.

The rest of the comparison is more mixed. Laying it out directly is more useful than assuming cloud wins on every dimension.

Steady utilization changes the cost comparison. A predictable workload may keep rented capacity busy enough that the provider's margin and service premium exceed the cost of operating owned hardware over the same period. Cloud repatriation means moving such a workload from a public cloud to privately operated infrastructure or colocation. The calculation must include people, facilities, support, financing, migration, and lost access to managed services, rather than comparing a cloud invoice with server prices alone.

A hybrid design avoids making one answer serve every workload. An organization might retain a system because of latency, regulation, or an existing investment while placing variable workloads in a public cloud. The relevant unit of comparison is therefore the workload and its dependencies, not the organization as a whole.

The Service Model Spectrum

IaaS, PaaS, and SaaS are usually taught as three separate boxes. They read more clearly as one spectrum with a boundary that moves.

Infrastructure as a service (IaaS) exposes low-level resources such as virtual machines, storage, and networks. The customer manages the guest operating system, runtime, and application. Platform as a service (PaaS) also delegates the operating system and runtime, leaving the customer to deploy and configure its application. With software as a service (SaaS), the provider operates the application as well, while the customer manages its users, data, and service configuration.

Serverless describes services that hide server provisioning and expose a higher-level unit of work or capacity. Function as a service (FaaS) runs code in response to events and commonly meters execution or requests. Serverless databases and container platforms use different billing units, and some still expose capacity settings, so the word does not imply identical scaling or pricing behavior.

The shared responsibility model introduced earlier becomes concrete once it's laid out layer by layer.

Networking doesn't appear as a fifth row on purpose. It isn't one point in the stack the way application or storage are, but something configured at every level from IaaS upward. That's why the next major section covers it on its own.

A managed layer reduces operational work but leaves important customer decisions in place. The provider may patch a database engine while the customer still controls identities, network exposure, backup policy, and data use. Product boundaries also vary, so the table is a starting model rather than a substitute for a service's own responsibility matrix.

Compute: VMs, Containers, and Functions

Four common ways to run a workload, each suited to a different shape of problem.

A virtual machine is the basic IaaS compute unit. It presents an operating system that the customer configures and patches. Virtual machines suit software that needs operating-system control, long-running processes, or compatibility with an existing server-based deployment model.

Managed container platforms sit in the middle, ranging from a simple service that runs a single container up to a fully managed Kubernetes offering. The provider operates the underlying cluster infrastructure. The customer supplies containerized applications and describes how they should run. What a container is, and how an orchestrator like Kubernetes schedules and scales one, is covered in full in Containers and Orchestration. This article only needs where managed container platforms sit relative to the other compute options.

Serverless functions remove guest operating-system and instance management from the customer. They also impose product-specific limits and may introduce a cold start while an execution environment initializes. Event-driven tasks fit the model well, although provisioned concurrency and other platform features can also support latency-sensitive endpoints.

Managed machine-learning platforms combine compute with model training, deployment, and lifecycle tools. Some offerings allocate accelerators on the customer's behalf, while others still ask the customer to choose instance types and capacity. They build on the same compute primitives but present them through a workload-specific control plane.

Cloud-native, defined

Cloud-native architecture uses cloud delivery characteristics as design inputs. It commonly favors automated provisioning, managed services, elastic capacity, and components that can change independently. Moving an unchanged server layout onto virtual machines uses cloud infrastructure, but it captures fewer of those characteristics.

Storage: Object, Block, and File

Three storage types, distinguished by access pattern rather than by vendor product name.

Object storage holds unstructured data retrieved by key through an API, rather than opened and modified in place like a file on a local disk. That access pattern suits things like images, backups, and static assets well. It suits a database's working files poorly, since a database needs to modify small pieces of data in place far faster than an API round-trip allows.

Block storage behaves like a raw disk, typically attached to a single virtual machine, though some platforms support attaching one volume to several instances for specialized clustered workloads. It's exactly what a database's working files need, since a database has to modify small regions of data quickly and in place.

File storage provides a shared filesystem that multiple machines can mount and read or write at once. It suits a workload built around shared files, rather than an API or a single attached disk.

Object-storage services usually divide data among access tiers. Tiers for infrequently read or archival data reduce storage charges but can add retrieval fees, minimum retention periods, or longer restore times. A lifecycle policy can move objects as their access pattern changes, provided the policy accounts for all of those costs.

Networking and Managed Data

The boundary a customer's resources sit inside, and the two shapes managed data comes in.

A virtual network is an isolated private network layer a customer defines within the provider's infrastructure, the boundary within which the customer's own resources talk to each other. What happens once traffic arrives at that boundary, such as a CDN, a load balancer, or an API gateway, is covered in full in Web Application Networking. This article stops at the boundary itself.

A managed database hands patching, backups, and failover for a relational or NoSQL database to the provider. The alternative is self-hosting the same database engine on a virtual machine and owning that operational work directly.

A managed data warehouse serves a different use case entirely, running analytical queries that scan large volumes of historical data for reporting. It's optimized for scanning many rows at once, rather than looking up or updating a single record the way an operational database does. Reaching for one over the other is a question of access pattern, not of which is the more advanced option.

Messaging and Identity

Who talks to whom, and who's allowed to do what.

Managed messaging commonly supports two delivery patterns. A queue lets competing consumers claim work so that one of them handles each delivery. The service may redeliver a message after a failure, so consumers often need idempotent processing. A publish/subscribe service gives each subscription its own delivery stream, allowing several systems to react independently to the same event.

Identity and access management (IAM) grants permissions to users, workloads, groups, and roles. Least privilege limits each identity to the actions and resources it needs. Cloud platforms can assign an identity directly to a workload and issue short-lived credentials when it runs. That approach removes long-lived API keys from application configuration and narrows the value of any credential that is exposed.

Regions, Availability Zones, and Designing for Failure

Cloud regions and zones divide infrastructure into failure domains so workloads can plan for outages.

A region is a geographic area in which a provider operates one or more data centers. An availability zone is a separate failure domain within a region, designed with independent power, cooling, and networking. Deploying across zones reduces exposure to a local failure, but the workload must use zonal or zone-redundant services correctly. Region choice also affects latency, service availability, price, and data-residency obligations.

Resilient systems choose a failure scope and duplicate the components that must survive it. Stateless application instances are easier to spread across zones because any healthy instance can accept the next request. Stateful components need replication and a tested failover path. Multi-region designs address a larger failure scope, but they also add data-consistency, latency, cost, and operational tradeoffs.

Comparing AWS, Azure, and GCP

The only section where a vendor's product name matters.

AWS offers a broad catalog that spans basic infrastructure and many specialized managed services. Its long market presence has also produced a large ecosystem of tools, partners, and practitioners. Those characteristics make it a reasonable candidate when a team has no existing platform commitment, but they do not make it an automatic default.

Azure has a natural fit in organizations already using Microsoft Entra ID, Microsoft 365, .NET, or Windows Server. Existing identity, administration, and licensing arrangements can reduce integration work. Microsoft Foundry adds a managed platform for building and governing AI applications with models from Microsoft, OpenAI, and other providers, subject to the terms and boundaries of the selected Azure service.

Google Cloud has a strong data and machine-learning portfolio. BigQuery provides a managed analytical warehouse, while Google offers tensor processing units and managed model-development services for machine-learning workloads. Google also originated Kubernetes, although managed Kubernetes is now available from every major provider. These strengths may justify using Google Cloud for particular workloads even when the rest of an organization runs elsewhere.

Portability and Lock-In

Compute moves between providers more readily than the services and data surrounding it.

Virtual machines and container images are relatively portable, but their surrounding configuration rarely moves unchanged. IAM policies, networks, observability, messaging, and managed databases expose provider-specific behavior. Data creates another constraint because moving a large volume takes time and may incur transfer charges. Data gravity describes how a growing dataset makes nearby services easier to adopt and the whole system harder to relocate.

Abstraction can reduce migration work without removing it. Infrastructure as code makes the existing configuration explicit, while container orchestration gives compute a similar operating model across providers. Open interfaces help at service boundaries. PostgreSQL compatibility and OpenTelemetry export, for example, preserve useful options even when the managed implementation remains provider-specific.

Multi-cloud means operating workloads across more than one public-cloud provider. It can satisfy a regulatory constraint, support an acquisition, or give a workload access to a particular service. It also multiplies identity models, tooling, skills, and failure modes. A team should adopt that complexity for a stated requirement rather than treating provider count as a resilience feature by itself.

Choosing a Provider

The right answer depends on specifics this article can't see, such as what a team already runs and where its skills already sit.

The right provider depends on what a team already operates, where the relevant skills already sit, and which managed services actually matter for the workload, more than on any single feature comparison. The provider strengths covered above are a starting point to validate against those specifics, not a conclusion to import wholesale.

Revisit the comparison from earlier in this article, too, before assuming the answer is a public cloud provider at all. A steady, predictable, high-utilization workload is exactly the case where that assumption breaks down. The right answer for one system inside an architecture doesn't have to be the right answer for every system next to it.

Provider choice comes after a more basic decision: how much responsibility should this workload hand off, and which responsibilities must the organization retain? Service models and managed products provide different answers. The right combination follows from the workload's constraints and the team's ability to operate what remains.
