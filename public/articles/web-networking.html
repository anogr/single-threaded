Web Application Networking

The infrastructure between a browser and the backend, and what each layer means for security and scalability.

Conceptual overview
Andreas Ögren
~14 min read
Architecture
Last updated July 2026

Web applications face three problems at once. The internet is hostile, user demand is unpredictable, and a single server has finite capacity. The infrastructure between a browser and application code exists to address all three.

Traffic from the public internet can come from anyone, so requests need to be filtered for threats before reaching application code, data needs to be encrypted in transit, and services inside the private network need to verify each other's identity rather than assume internal traffic is safe. Demand is a separate problem: load needs to be spread across multiple instances to absorb spikes, and content should be served from locations close to users to keep latency low. Routing is the third concern, directing each request to the right backend and centralizing access control rather than rebuilding it in every service.

This article works through the infrastructure that handles these concerns, where each component sits in the network, and how the layers relate to each other. It also covers how services communicate securely inside a private network, how different models for persistent browser connections affect infrastructure design, and how to think about which layers a given application actually needs.

The Request Path

The diagram below shows one common production arrangement. How many layers appear in practice depends on scale, security requirements, and use case.

A small application may use only two or three of these layers. A large platform might add more. The figure combines several so each component has a place in the picture before the deep-dives begin.

Take a user opening the application in their browser. Before the request is even sent, the browser performs a DNS lookup to resolve the hostname to an IP address, which often belongs to a CDN edge node rather than the origin server. The CDN handles TLS and serves cached responses immediately, keeping latency low for the majority of requests. Those that miss the cache reach the WAF, which inspects the HTTP content for attack signatures and drops hostile requests before they travel any further. Only clean traffic continues toward the origin.

At the origin, a perimeter firewall decides which connections enter the network at all, operating on IP addresses and ports rather than HTTP content. A reverse proxy in the public subnet is the first component that understands HTTP: it terminates TLS if this has not already happened at the edge, and routes each request by path to the right destination. API calls continue to an API gateway, which handles authentication and rate limiting before passing requests to a load balancer that distributes them across a pool of service instances.

The user sees a page load. The request that produced it crossed the public internet, was checked for threats, passed through a network boundary, and was routed to the right service, each step handled by infrastructure built for a different concern.

At the Edge: CDN and WAF

For most users, geography is the biggest source of latency. A CDN puts the application's front door close to where users actually are.

A CDN (Content Delivery Network) is a global network of servers positioned close to users in major population centers. Originally, the purpose was to serve static files (images, stylesheets, scripts) from a server near the user instead of routing every request to a central origin. A user in Stockholm connecting to a CDN point-of-presence in Stockholm gets a cached response in single-digit milliseconds rather than the 150+ milliseconds a round trip to a US data center would take.

How CDN routing works

When a CDN is configured for a domain, the domain's DNS record is pointed at the CDN's infrastructure. The CDN runs its own authoritative nameservers, which respond to each DNS query with the IP address of the nearest edge node, selected by geographic location or network proximity. The browser ends up connecting to a server a few milliseconds away with no awareness that the origin is elsewhere.

Modern CDNs do considerably more than cache files. For dynamic content that cannot be cached, the CDN terminates TLS at the nearest edge node and routes the remaining connection to the origin over the CDN's own high-capacity backbone, reducing latency even when nothing is served from cache. Many providers now offer edge compute (small functions that run at the edge node itself, before the request reaches the origin) as well as on-the-fly image and video optimization such as format conversion and resizing.

The CDN is also the first security layer many applications have. A WAF (Web Application Firewall) positioned at the edge inspects each HTTP request and blocks those that match known attack patterns: SQL injection, XSS payloads, path traversal attempts, and known bot signatures. Blocked requests are answered with a 403 and logged before any traffic reaches the origin. DDoS protection works on the same principle at a larger scale: a volumetric attack large enough to saturate a single data center's network connection is absorbed across the CDN's aggregate capacity in hundreds of edge locations, and the application servers never see the traffic.

Not all WAFs are CDN-integrated. In on-premises and regulated environments, a WAF is commonly deployed as a dedicated appliance (products like F5 and Imperva) sitting inline in the traffic path between the perimeter firewall and the internal network, independent of any CDN.

Protecting the origin

A CDN that provides WAF and DDoS protection is only effective if attackers cannot bypass it by connecting directly to the origin. If the origin's IP address is publicly discoverable, traffic sent directly to it skips the CDN entirely, along with all the security controls at the edge. The fix is to configure the origin's firewall to accept inbound traffic only from the CDN provider's published IP ranges, and to avoid exposing the origin IP in DNS records, error messages, or email headers. Without this, the CDN is security theater.

Load Balancers and Application Design

Horizontal scaling sounds simple: add more servers and distribute traffic. The complication is state stored in process memory.

A load balancer distributes incoming requests across a pool of application instances. When one instance fails its health check, traffic moves to the remaining healthy ones. When demand grows, new instances join the pool. This is horizontal scaling, the standard approach to availability and capacity in modern web applications.

A problem surfaces as soon as user sessions are involved. A user logs in, and server A creates a session record in memory. Their next request goes to server B. Server B has no knowledge of that session. The user appears to be logged out.

The solution is stateless application design. Session data lives in a shared external store (Redis is the most common choice) rather than in process memory. Any server can then handle any request because session state is not tied to a specific instance. The load balancer routes freely, and servers can be added, removed, or restarted without disrupting active sessions.

How requests are distributed across instances is controlled by the balancing algorithm.

Balancing algorithms
  • Round robin cycles through the instance pool in sequence. It works well when requests are similar in cost. Most cloud load balancers use this as the default.
  • Least connections routes each new request to whichever instance currently has the fewest active connections. This adapts better to variable workloads where some requests take much longer than others.
  • IP hashing uses a hash of the client's IP address to select the destination instance, so the same client consistently reaches the same server. It is not a substitute for stateless design: corporate users behind a NAT gateway all share a single IP, routing the entire office to one instance.
  • Weighted balancing assigns each instance a capacity weight, giving more traffic to instances with more resources. Useful when the pool contains machines of different sizes.

Health checks are the second major capability of a load balancer. The load balancer continuously probes each instance on a dedicated endpoint, and any instance that fails is removed from rotation automatically. A liveness check tests whether the process is still running, and a failure triggers a restart. A readiness check tests whether the instance is ready to accept traffic, and a failure pulls it from rotation without restarting it. An instance can be live but not ready: it may have started but not yet connected to its database, loaded required configuration, or completed a cache warmup.

Load balancers operate at either Layer 4 (TCP connections) or Layer 7 (HTTP requests). A Layer 4 load balancer distributes connections based on IP address and port without reading HTTP. A Layer 7 load balancer understands HTTP, which enables it to also perform reverse proxy functions such as routing by hostname or path, and TLS termination. Most web application load balancers today operate at Layer 7. AWS Application Load Balancer, GCP Load Balancing, and Azure Application Gateway all work this way.

TLS Termination

HTTPS is encrypted from the browser to wherever TLS terminates. That point is usually not the application server, and where it is matters.

TLS is almost always terminated at a reverse proxy or load balancer rather than at the application server itself. After that point, traffic travels as plain HTTP over the internal network. This is practical: certificates are managed in one place, application servers are simpler, and offloading TLS reduces CPU overhead on application instances. The trade-off is that internal traffic is unencrypted. In high-security or regulated environments, re-encrypting before forwarding to application servers removes that exposure, at the cost of higher operational complexity. Three models cover the common configurations:

Termination models
  • Terminate at CDN edge. TLS ends at the nearest edge node, minimizing handshake latency for users. The leg from CDN to origin may be plain HTTP or re-encrypted depending on configuration.
  • Terminate at load balancer. The most common setup. Certificates are managed in one place and application servers receive plain HTTP. Acceptable when the internal network is trusted.
  • Re-encrypt to application servers. Traffic is encrypted at every hop. Required in regulated environments or where the internal network cannot be assumed safe. Higher operational complexity.

Where TLS terminates creates a key constraint: any component that needs to inspect or modify HTTP content must be the TLS termination point, or must sit downstream of it. A WAF checking for injection patterns, an API gateway enforcing authorization, or an L7 load balancer routing by path all require access to decrypted HTTP. If the traffic arriving at that component is still an encrypted TLS stream, it cannot see inside it. A traditional network firewall is the exception: it operates on IP addresses and port numbers rather than HTTP content, so it can allow or block HTTPS connections without decrypting them.

Client IP address after termination

One consequence of reverse proxy termination is that the application server no longer sees the original client IP. It receives only the proxy's address. The proxy injects the client's real IP into an X-Forwarded-For header, which accumulates every address in the chain: X-Forwarded-For: client-ip, proxy-ip. Application code should trust only the rightmost IP added by a proxy the application explicitly trusts, or the proxy should strip all incoming X-Forwarded-For headers and set the value fresh from the real connection. Some setups use a dedicated X-Real-IP header that only the proxy can set, which avoids the chain ambiguity entirely.

Firewall

A firewall controls which network connections are permitted. Traditional firewalls operate at the network layer (IP addresses) and transport layer (ports and protocols), allowing or denying traffic based on source address, destination address, port number, and protocol. At this level, a firewall has no knowledge of HTTP or the application's behavior. Modern next-generation firewalls (NGFW) can additionally inspect traffic at the application layer, applying policies based on application type or threat signatures, but the core role is the same: the firewall is a boundary enforcer that decides whether a connection is allowed before any application code runs.

A firewall enforces rules like "the database accepts connections only from the application servers, not from the internet." Good firewall design follows a default-deny posture: everything is blocked unless explicitly permitted. If a connection does not match a permitted rule, it is dropped at the boundary.

In cloud environments, firewalls are typically implemented as security groups attached to individual instances or subnets rather than as a single perimeter appliance. Each resource carries its own inbound and outbound rules, making firewall policy granular and distributed. The effect is the same: connections that do not match a permitted rule are dropped.

Reverse Proxy

The name makes more sense once a forward proxy is defined. A forward proxy works on behalf of the client: a corporate proxy or VPN sits in front of the user, makes outbound requests on their behalf, and the destination server sees the proxy's address rather than the original client's. A reverse proxy is the mirror image. It works on behalf of the server. Clients connect to the proxy's address, and the actual backend servers are not directly reachable from outside.

A reverse proxy sits in front of one or more backends, accepting connections on their behalf and forwarding each request to the right backend. The value of this arrangement is that cross-cutting concerns can be handled at the proxy rather than repeated in every backend. TLS can be terminated there, and responses can be cached and compressed. Headers can be rewritten, and requests can be routed to entirely different applications based on the URL path. That last point becomes concrete with an example: a single domain can send /login to an authentication service and /my-account to a profile service, with the proxy directing each request to the right backend. The client sees one address. The proxy decides what runs behind it. These things can also be done within application code, but a reverse proxy centralizes them for all backends without changing the applications themselves.

Nginx and Caddy are the most common standalone reverse proxies, but in practice these components overlap considerably. An AWS Application Load Balancer is simultaneously a load balancer and a reverse proxy. An Nginx instance can act as reverse proxy, load balancer, and static file server at once. These distinctions are conceptual: they describe a primary job and what a component needs to see to do it. When evaluating a product, the useful question is which of these jobs it covers and how well.

API Gateway

An API gateway is a reverse proxy with application-level policies built in. It sits in front of backend services and enforces cross-cutting concerns centrally:

  • Authentication and authorization
  • Rate limiting
  • Routing by API version or path
  • Analytics
  • Developer-facing features like API key management

It can also transform requests and responses, translating between protocols, rewriting headers, or converting payload formats so that backend services and clients can evolve independently. Where a general-purpose reverse proxy is neutral about what flows through it, an API gateway is opinionated about API traffic specifically.

The practical benefit is that these concerns are handled once at the gateway rather than duplicated across every service. Individual services receive already-authenticated requests and can focus on domain logic. For external developers, the gateway is typically the visible face of the API: the endpoint they connect to, where access is granted and usage is tracked.

Network Zones

Not everything should be reachable from the internet. Placing components in the right zone is one of the most effective security controls available.

In cloud infrastructure, network segmentation is implemented through subnets within a VPC (Virtual Private Cloud), the customer-carved network boundary covered at a higher level in Cloud Computing Fundamentals. Components are placed in public or private subnets based on whether they need to accept inbound connections from the internet.

Public subnets hold components that accept inbound internet traffic: load balancers, CDN origin connections, and NAT gateways. These have public IP addresses. Private subnets hold application servers and internal services that should only be reachable from inside the network. They have no public IP and are not routable from the internet. The data tier goes further still: databases accept connections only from application servers in the private subnet.

In traditional on-premises architecture, this intermediate zone between the internet and the internal network was called a DMZ (demilitarized zone). A DMZ sits between two firewalls: one facing the internet, one facing the internal network. Public-facing servers such as web servers and reverse proxies live in the DMZ, isolated from internal systems even if compromised. The cloud VPC model achieves the same thing with public and private subnets and security group rules, but the underlying principle is identical: public-facing components are separated from internal ones by a firewall boundary, and no direct path from the internet to the internal network exists.

This layering is the network implementation of defense in depth. An attacker who compromises a component in the public subnet still faces firewall boundaries before reaching private instances. A misconfigured load balancer does not automatically expose the database. Compromising the database requires compromising an application server first.

Application servers in private subnets still need outbound internet access for third-party API calls, OS package updates, and similar. A NAT gateway in the public subnet provides this: private instances route outbound traffic through it, but inbound connections from the internet cannot traverse NAT. The asymmetry is intentional.

Service-to-Service Communication

Traffic between services inside the network has a different character from traffic entering it. It still needs its own security and reliability controls.

In a single-service application, the only traffic worth thinking about is inbound. In a multi-service architecture, most of the traffic volume is internal: service A calls service B, which calls service C, which writes to a database. This internal traffic is sometimes called east-west, to distinguish it from north-south traffic that crosses the perimeter.

East-west traffic is often assumed to be safe because it never leaves the private network. That assumption is reasonable in some cases but dangerous in others. An attacker who gains access to one compromised instance inside the perimeter has free movement if there are no controls on internal traffic. Mutual TLS (mTLS) is the standard response: every service presents a certificate, and services only accept connections from other services with valid, trusted certificates. Both ends authenticate each other, and traffic is encrypted at every hop.

A service mesh handles mTLS and reliability concerns centrally, without touching application code. The mesh takes care of certificates, retries, timeouts, and traffic metrics across all services. The traditional approach injects a sidecar proxy container alongside each service instance to intercept its traffic. A newer model uses eBPF to enforce the same policies at the Linux kernel level, with no sidecar process at all. Whether a service mesh is worth the operational overhead depends on scale. For smaller deployments, applying mTLS at the application level or enforcing it at the network boundary may be sufficient.

Circuit breaker

A circuit breaker is a reliability pattern for services. When a downstream service starts failing or responding slowly, a circuit breaker stops sending it new traffic immediately rather than letting requests queue up waiting for timeouts that will never succeed. After a short recovery window it sends a probe request, and if that succeeds normal traffic resumes. This prevents a single degraded service from causing cascading failures across the system.

Persistent Connections

HTTP's request-response model covers most use cases. When the server needs to push data to the browser unprompted, the model needs to change.

Standard HTTP is strictly client-initiated. The browser asks. The server answers. This is sufficient for the vast majority of web application interactions. But some patterns require the server to deliver data to the client without waiting for a request: a live dashboard updating in real time, a collaborative document where other users' edits appear instantly, a notification that arrives as it happens rather than when the user next refreshes.

WebSockets upgrade an HTTP connection to a persistent, full-duplex channel. Either side can send messages at any time. The connection stays open for the session's duration, making WebSockets the right choice when the browser also sends frequent messages to the server: live collaboration, real-time gaming, trading interfaces.

Server-Sent Events (SSE) are simpler: a persistent, one-way stream from server to browser over a normal HTTP connection. The browser cannot push over the same channel, but it can make separate HTTP requests. SSE handles many real-time use cases without the added complexity of WebSockets, and the browser's EventSource API includes built-in reconnection logic.

When Each Layer Applies

These layers do not all appear in every architecture. Each one exists to solve a specific problem, and the right set is determined by which of those problems are present.

A monolithic application with moderate traffic often needs nothing more than Nginx or Caddy acting as a reverse proxy in front of the application: it terminates TLS, compresses responses, and keeps the application server's IP off the public internet. That is enough for many deployments.

The moment multiple instances of the same application are needed, a load balancer becomes necessary. The trigger is less about raw traffic volume than about resilience: even at modest load, two instances behind a load balancer means the application survives a single server failure without going down.

An API gateway becomes valuable when authentication, rate limiting, and API versioning turn into cross-cutting concerns shared by multiple services. In a monolith, those concerns live in the application code. In a system with independent services, each team implementing the same authentication logic produces fragility and inconsistency. The gateway enforces these policies once at the entry point, and services downstream receive requests that have already been authenticated and validated.

Most production systems at scale end up combining layers rather than choosing one. A CDN sits at the edge absorbing cache hits and DDoS traffic. An API gateway handles authentication and routing. Load balancers distribute requests across service instances. In some deployments, a lightweight reverse proxy runs alongside each service for internal TLS and compression. None of these layers is redundant with the others because each one handles a category of problem the others cannot. The layers cooperate rather than compete, and the right architecture is the one that includes exactly the layers whose problems are present.
