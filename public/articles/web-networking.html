Web Application Networking

How requests pass through edge, routing, security, and service layers before they reach application code.

Andreas Ögren
~18 min read
Last updated July 2026

A public request must reach the right application without exposing more of the system than necessary or concentrating all traffic on one server.

Public traffic is untrusted, so connections need encryption and requests may need inspection before they reach application code. Internal location is not proof of identity either. Services still need authenticated and authorized connections. Capacity adds a separate constraint because traffic must be distributed across healthy instances, while cacheable content can move closer to users. Routing joins these concerns by sending each permitted request to the correct backend.

The request path provides the organizing thread for these components. It begins at the edge, continues through network and application routing, and ends with communication between services. Persistent browser connections add a different traffic shape, so they receive separate treatment before the final architecture guidance.

The Request Path

The diagram shows one production arrangement, while scale, security requirements, and use case determine how many layers a deployment needs.

A small application may use only two or three of these layers. A large platform might add more. The figure combines several so each component has a place in the picture before the deep-dives begin.

Consider a user opening the application. The browser first uses DNS to resolve the hostname. In a CDN-backed deployment, the resulting address routes the connection to a nearby CDN edge rather than directly to the origin. The edge terminates the client-facing TLS connection and can answer from cache.

Requests that continue toward the origin pass through the configured web application firewall (WAF), which applies HTTP-aware security rules. Traffic allowed by those rules proceeds. The WAF reduces exposure but does not prove that every surviving request is harmless.

At the origin boundary, a perimeter firewall admits only permitted network connections. A reverse proxy can then route HTTP requests by host or path and may terminate another TLS connection from the edge. API traffic may continue through an API gateway for policies such as authentication and rate limiting. A load balancer finally selects a healthy service instance.

The resulting page load hides that chain from the user. Each layer made a narrower decision than the one before it, moving from global routing and edge policy toward one application instance.

At the Edge: CDN and WAF

Because distance adds network latency, a CDN moves the public entry point and cacheable responses closer to users.

A content delivery network (CDN) operates distributed edge locations that can answer requests on behalf of an origin. Serving a cached image, stylesheet, or script from a nearby edge shortens the network path and removes work from the origin. The latency improvement depends on the user's network, the edge location, and where the origin runs.

How CDN routing works

A domain points clients toward the CDN, but providers route the final connection in different ways. Some return location-dependent addresses through DNS. Others advertise the same anycast address from many locations and let internet routing select a nearby reachable edge. In both designs, the browser connects to the CDN while the origin remains behind it.

CDNs can also proxy dynamic requests. The edge terminates the browser's TLS connection, then opens a separate protected connection toward the origin. Some providers route that leg over their own network and offer edge compute or media transformation along the way. Those features vary by provider and do not require the response itself to be cacheable.

An edge WAF evaluates HTTP requests against managed and application-specific rules. It can block or challenge traffic that resembles injection, path traversal, abusive automation, or other unwanted behavior. Distributed denial-of-service protection works at a larger scale by absorbing and filtering traffic across the provider's network before allowed requests reach the origin.

A WAF does not have to run inside a CDN. It may be a cloud service, a software proxy, or a dedicated appliance placed elsewhere in the request path. Its defining feature is access to HTTP content, not a particular deployment model.

Protecting the origin

Edge controls can be bypassed when an attacker can connect directly to the origin. Restrict origin ingress to authenticated CDN connections or to the provider's published network ranges, depending on the service. Avoid publishing the origin address through unrelated DNS records or application output. The exact control matters more than hiding the address, since addresses can leak over time.

Load Balancers and Application Design

Horizontal scaling sounds simple: add more servers and distribute traffic. The complication is state stored in process memory.

A load balancer distributes incoming traffic across a pool of application instances. It stops selecting targets that fail health checks and can admit new instances as the pool grows. Adding instances in this way is horizontal scaling. It can increase capacity and reduce dependence on any single application process.

A problem surfaces as soon as user sessions are involved. A user logs in, and server A creates a session record in memory. Their next request goes to server B, which has no knowledge of that session, so the user appears to be logged out.

One solution is stateless application design at the instance boundary. Session data lives in a shared store or travels in a protected client credential instead of remaining in one process. Any healthy instance can then handle the next request. Sticky sessions are another option, but they couple availability and scaling behavior to the load balancer's affinity rules.

How requests are distributed across instances is controlled by the balancing algorithm.

Balancing algorithms
  • Round robin cycles through healthy targets in sequence. It works well when targets have similar capacity and requests have similar cost. Several application load balancers use it as their default, but defaults vary by product and load-balancer type.
  • Least connections routes each new request to whichever instance currently has the fewest active connections. This adapts better to variable workloads where some requests take much longer than others.
  • IP hashing uses a hash of the client's IP address to select the destination instance, so the same client consistently reaches the same server. It is not a substitute for stateless design: corporate users behind a NAT gateway all share a single IP, routing the entire office to one instance.
  • Weighted balancing assigns each instance a capacity weight, giving more traffic to instances with more resources. Useful when the pool contains machines of different sizes.

Health checks let a load balancer avoid targets that cannot serve traffic. Container orchestrators add a useful distinction between readiness and liveness. A readiness probe controls whether an instance receives traffic, while a liveness probe tells the orchestrator when a container should be restarted.

An application can be live but temporarily unready while it starts, warms a cache, or recovers from an overload. The load balancer removes an unhealthy target from rotation. The surrounding platform decides whether that target should be restarted.

Load balancing can happen at Layer 4 or Layer 7. A Layer 4 device distributes transport connections without interpreting HTTP. A Layer 7 load balancer acts as an HTTP reverse proxy, which enables host and path routing as well as TLS termination. The choice depends on whether the infrastructure needs HTTP awareness, transport-level performance, source-address preservation, or support for non-HTTP protocols.

TLS Termination

HTTPS protects traffic until the client-facing TLS connection ends, and that termination point shapes every downstream security decision.

Many deployments terminate the client-facing TLS connection at a CDN, reverse proxy, or load balancer. That centralizes public certificate management and gives the proxy access to HTTP for routing and policy enforcement. The next hop may use plain HTTP inside a controlled network, a new TLS connection to the origin, or mutual TLS between internal services. The choice determines which network segments carry plaintext and which components must manage certificates.

Termination models
  • Termination at the CDN edge ends the browser-facing TLS connection close to the user. The CDN then uses either HTTP or a separate TLS connection for the origin leg.
  • Termination at the load balancer centralizes public certificate management at the origin boundary. The backend hop follows the network's threat model and may be encrypted separately.
  • Re-encryption to application servers protects every network hop at the cost of additional certificate and identity management.

Any component that inspects or modifies HTTP must terminate the incoming TLS connection or receive traffic after another component has decrypted it. WAF rules, gateway authorization, and Layer 7 path routing all depend on access to HTTP content. If a new TLS connection protects the next hop, the receiving component terminates that connection before applying its policy.

A network firewall does not need to decrypt HTTPS when its rules use only addresses, ports, and transport protocols. Application-aware inspection is different because it must gain controlled access to the plaintext.

Client IP address after termination

An HTTP reverse proxy opens its own backend connection, so the application normally sees the proxy as the network peer. Proxies preserve client-address information in a standardized Forwarded field or in conventions such as X-Forwarded-For. Never trust those values directly from the public internet. Configure the proxy to sanitize incoming forwarding fields, and configure the application with the exact trusted proxy hops so it selects the first untrusted address correctly.

Firewall

A firewall controls which network traffic may cross a boundary. Network and transport rules match properties such as source, destination, protocol, and port without interpreting the application's HTTP behavior. Products described as next-generation firewalls can add application identification and threat inspection. In either case, the firewall enforces network policy before traffic reaches the protected workload.

A firewall enforces rules like "the database accepts connections only from the application servers, not from the internet." Good firewall design follows a default-deny posture: everything is blocked unless explicitly permitted. If a connection does not match a permitted rule, it is dropped at the boundary.

Cloud platforms express these controls through constructs such as instance or interface security groups, subnet access-control lists, and managed network firewalls. The attachment point and state model differ between products, but the design goal is the same: expose only the flows that the workload requires.

Reverse Proxy

The name becomes clearer beside a forward proxy. A forward proxy makes outbound requests on behalf of clients, so destination servers communicate with the proxy. A reverse proxy accepts inbound requests on behalf of servers. Clients connect to its public address while it selects and contacts the backend.

This extra hop creates one place for concerns shared by several backends. The proxy can terminate TLS, compress responses, apply cache policy, and rewrite selected fields. It can also send /login to an authentication service while routing /my-account to a profile service. Clients see one public origin even though several applications handle the traffic behind it.

Products often combine these roles. Nginx or Caddy can proxy requests, balance traffic, and serve static files. A managed application load balancer is also an HTTP reverse proxy. The labels describe responsibilities rather than mutually exclusive boxes, so an architecture should show which component performs each job.

API Gateway

An API gateway is a reverse proxy with application-level policies built in. It sits in front of backend services and enforces cross-cutting concerns centrally:

  • Authentication and authorization
  • Rate limiting
  • Routing by API version or path
  • Analytics
  • Developer-facing features like API key management

It can also transform requests and responses, translating between protocols, rewriting headers, or converting payload formats so that backend services and clients can evolve independently. A general-purpose reverse proxy stays neutral about what flows through it. An API gateway, by contrast, is opinionated about API traffic specifically.

A gateway gives shared policies one enforcement point and one public API surface. Downstream services can consume verified identity context, but they still enforce authorization for their own resources and should authenticate calls across service boundaries. Centralization reduces duplicated edge logic without turning the internal network into a trust boundary.

Backend for Frontend (BFF)

An API gateway centralizes routing and policies that several API consumers share. A Backend for Frontend (BFF) takes the opposite approach. It is a server layer built for one specific frontend, shaped around that frontend's data needs rather than around a generic API contract.

A BFF sits between one frontend and the services it uses. It can aggregate several backend calls and return a response shaped for one screen or interaction. Separate web and mobile BFFs make sense when those clients have genuinely different workflows, release constraints, or data needs. They are unnecessary when both clients would merely repeat the same pass-through layer.

The tradeoff is more infrastructure to run. Each dedicated BFF is another deployable, with its own release cadence and its own team boundary to keep straight. A BFF earns its place when a client's data-shaping needs genuinely diverge from what a shared API already returns, not by default for every frontend a product ships.

The BFF is the frontend-specific API boundary. It may sit in front of a shared gateway, behind one, or call services directly through internal controls. The pattern does not require one fixed ordering. Keeping authentication tokens off the browser is one reason to introduce this layer. In that design, the BFF stores tokens server-side and gives the browser an opaque session cookie.

Network Zones

Not everything should be reachable from the internet. Placing components in the right zone is one of the most effective security controls available.

Cloud networks use subnets, routes, and firewall policy to control reachability inside a virtual private cloud (VPC). The broader cloud model is covered in Cloud Computing. A public subnet has a route to an internet gateway. A private subnet does not expose its workloads through that direct inbound path.

A public subnet has a route to an internet gateway and can contain internet-facing load balancers or outbound NAT gateways. A route alone does not make every workload reachable because public addressing and firewall policy still apply. Private subnets have no direct route for inbound internet traffic and commonly hold application services. A separate data tier can restrict database connections to the specific application identities or network sources that require them.

Traditional on-premises networks often place public services in a demilitarized zone (DMZ) between external and internal controls. A compromised public server then faces another policy boundary before it can reach internal systems. Cloud subnets, routes, and security controls can express the same separation without reproducing the physical topology exactly.

This separation contributes to defense in depth. Compromise of a public component does not automatically grant every internal network path. The remaining controls still need correct identity, authorization, and firewall policy because segmentation limits movement rather than making it impossible.

Private workloads may still need outbound internet access for external APIs or software updates. A NAT gateway can translate those outbound connections through a public address and allow the corresponding response traffic back. It does not create a route for unsolicited inbound connections. Private endpoints or controlled egress proxies are alternatives when traffic should avoid or tightly govern public internet access.

Service-to-Service Communication

Traffic between services inside the network has a different character from traffic entering it. It still needs its own security and reliability controls.

A multi-service application adds traffic that never crosses the public perimeter. One service calls another, which may call a third service or a data store. Architects often call this east-west traffic, in contrast to north-south traffic entering or leaving the system.

A private network reduces exposure but does not authenticate the caller. Without internal controls, one compromised workload may be able to reach many others. Mutual TLS (mTLS) addresses the connection identity problem by requiring both peers to present trusted certificates. It authenticates both ends and encrypts the hop, while application authorization still decides what the authenticated caller may do.

A service mesh provides a shared control layer for service-to-service traffic. Sidecar-based meshes place a proxy beside each workload, while other implementations use node-level proxies and kernel networking facilities. Depending on the product, the mesh can manage mTLS identities, telemetry, timeouts, and selected retry or routing policies. Those features move configuration out of application code but add another distributed system to operate. Direct application libraries or platform-level mTLS may be enough when the service graph is small.

Circuit breaker

A circuit breaker stops calls to a dependency after failures cross a configured threshold. During the open period, callers fail quickly instead of adding more work to a struggling service. A later probe determines whether normal traffic can resume. The pattern can limit a cascading failure, but its thresholds and fallback behavior must match the operation.

Persistent Connections

HTTP's request-response model covers most use cases. When the server needs to push data to the browser unprompted, the model needs to change.

An ordinary HTTP exchange begins with a client request and ends with a server response. Repeating that pattern works for most interactions, including polling. Live feeds and collaborative applications need updates to arrive while no new request is being made, so they keep a channel open for server-initiated messages.

A WebSocket session begins through HTTP and becomes a persistent, full-duplex message channel. Either side can send after the session is established. This fits interactions with frequent traffic in both directions, such as collaborative editing or multiplayer games.

Server-Sent Events (SSE) keep an HTTP response open as a one-way event stream from server to browser. Client actions use separate HTTP requests. The browser's EventSource API reconnects after an interrupted stream, which makes SSE a good fit for feeds, progress, and notifications.

When Each Layer Applies

These layers do not all appear in every architecture. Each one exists to solve a specific problem, and the right set is determined by which of those problems are present.

A modest monolithic application may need only a managed ingress or a reverse proxy in front of the application. That component can terminate TLS, compress responses, and keep the application process off the public network. Additional layers should correspond to an identified routing, scale, or security requirement.

Multiple interchangeable application instances need some mechanism that selects a healthy target, usually a load balancer or platform service. Capacity is only one reason to add it. Redundancy can also keep traffic flowing during an instance failure, provided that the surrounding data stores and network path do not remain single points of failure.

An API gateway becomes useful when several services share public concerns such as authentication, rate limiting, or version routing. Central policy reduces drift between entry points. Services still validate the identity context they receive and enforce resource-level authorization, since the gateway cannot make every domain decision on their behalf.

Larger systems often combine several responsibilities in fewer products. A CDN may provide caching, DDoS mitigation, WAF rules, and global routing. A managed gateway may also balance traffic, while a service platform handles internal discovery and TLS. Draw the responsibilities first, then map them to products. That reveals both accidental duplication and gaps more clearly than counting boxes by name.
