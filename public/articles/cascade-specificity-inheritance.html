Cascade, Specificity, and Inheritance

How a browser chooses among competing declarations and supplies values through inheritance.

Andreas Ögren
~11 min read
Last updated August 2026

Two valid rules can assign different values to the same property on the same element. A base stylesheet might set a card's text to a neutral gray, and a theme stylesheet loaded afterward might set the same card's text to the brand's navy color. The browser must therefore choose which declaration sets the card's color.

CSS handles competing declarations and missing values as two different cases. When declarations set the same property on the same element, the cascade applies a fixed precedence order and selects the winning declaration. Specificity is one comparison within that order, not a measure of a rule's overall power. When no declaration sets a property, the browser uses defaulting to determine the property's value. An inherited property receives its parent's computed value through inheritance, while a non-inherited property uses its own initial value.

The Cascade

The browser resolves conflicts among declarations through an ordered sequence of comparisons.

The cascade orders declarations that set the same property on the same element and selects the one with the highest precedence. For the two normal author rules in the card example, the relevant comparisons are origin and importance, cascade layer, specificity, and source order. The browser stops as soon as one declaration has higher precedence. Both stylesheets use .card, and neither rule belongs to a named layer. The declarations tie on origin, importance, layer, and specificity. Because the theme stylesheet is linked later, its navy declaration wins by source order.

Origin identifies who supplied a declaration. Browser defaults belong to the user-agent origin, styles in a user stylesheet belong to the user origin, and the site's styles belong to the author origin. Both card rules come from the site, so they tie at the author origin. If the neutral gray came from a browser default instead, the navy author declaration would win at the origin comparison. Among normal declarations, author styles outrank user styles, which outrank user-agent styles. The author origin resolves this hypothetical conflict before layers or specificity are considered.

!important changes the origin comparison. A user stylesheet could set the card's color with an important declaration. That declaration beats both normal author rules before layer or specificity can matter. If the theme rule is also important, the important user declaration still wins. Among the three important origins, user-agent declarations have the highest precedence, followed by user declarations and author declarations. This reversal lets important user declarations that increase font size or change the color scheme override a page's important author styles. Authors therefore shouldn't use !important merely to override another author rule.

!important as a last resort

In ordinary author styles, an important declaration can be overridden only by another important declaration with higher precedence. Adding !important to resolve one conflict makes later overrides harder because competing author declarations must also be important. When declarations reach the specificity comparison, a later declaration can win only if its selector matches or exceeds the earlier selector's specificity.

Within the author origin, cascade layers are compared before selector specificity. The base rule can belong to @layer base while the theme rule belongs to @layer theme. If theme is declared later, the navy declaration in theme wins at the layer comparison. The result stays the same if the base rule uses an ID and the theme rule uses one class, because the browser compares layers before specificity. Normal declarations outside a layer outrank every normal layered declaration. Important declarations reverse the layer order, so earlier layers outrank later ones and important layered declarations outrank important unlayered declarations. A project can define one layer order across all its stylesheets as part of its CSS architecture.

If both .card rules remain unlayered, the layer comparison also ends in a tie. The browser then compares their selectors. Two identical .card selectors tie on specificity, so the later theme stylesheet wins by source order. If one rule used a more specific selector, that rule would win before source order is considered.

Specificity

When declarations tie on origin, importance, and layer, the browser compares their selector specificity.

Specificity is a weight the browser calculates from a selector's structure. The browser compares specificity only after declarations tie on origin, importance, and layer. The selector with the higher calculated weight wins.

The browser records separate counts for ID, class, and type selectors. It compares those counts in that order. Because the ID count is compared first, one ID outweighs any number of class or type selectors. If the ID counts tie, one class outweighs any number of type selectors.

  1. ID selectors are compared first.
  2. Class selectors are compared second. Attribute selectors and pseudo-classes, such as [type="submit"] and :hover, count the same as a class.
  3. Type selectors are compared last. Pseudo-elements, such as ::before, count the same as a type.

The selectors below show why one ID outweighs three classes.

specificity.css CSS 
#save-btn { color: var(--accent); }
/* (1, 0, 0) — one ID */

.card .actions .save-button { color: var(--text-dim); }
/* (0, 3, 0) — three classes, still loses to the ID above */

The universal selector and :where() add no specificity. Combinators such as a descendant space or a child > also add nothing to the calculation. :where() always counts as zero regardless of what's written inside its parentheses. Unlike :where(), :is(), :has(), and :not() take the specificity of the most specific selector in their selector-list argument. Therefore :where(#save-btn) has (0, 0, 0), while :is(.save-button, #save-btn) has (1, 0, 0) because the ID is its most specific argument. Rules in a reset or default theme can wrap their selectors in :where(), keeping those selectors at zero specificity so a later class selector can override them.

:nth-child() and :nth-last-child() count the pseudo-class itself plus the most specific selector in an of clause. The selector :nth-child(2n of .featured) therefore has (0, 2, 0). One class count comes from :nth-child(), and the other comes from .featured.

Inline style attributes are compared separately from selector specificity. Within the author origin, a normal inline declaration beats every normal selector-based declaration, no matter how specific those selectors are. An important author declaration can override a normal inline style, while an important inline declaration outranks other important author declarations.

The @scope at-rule limits where selectors in its enclosed style rules can match. The element where the scope begins is its scoping root. When declarations inside @scope blocks remain tied after specificity, the browser compares scope proximity before source order. The rule whose scoping root is closest to the matched element wins. If scope proximity also ties, or neither rule is scoped, source order is the cascade's final comparison. The later declaration wins, whether it appears in the same stylesheet or in a stylesheet linked afterward. Outside @scope, distance through the document tree does not affect the cascade. A selector with a longer ancestor chain does not outrank a shorter selector for that reason.

Inheritance

The cascade chooses among declarations that apply to an element. If none sets the property, defaulting uses inheritance or the property's initial value.

Browsers need a value for every CSS property on every element, even though stylesheets declare only some of them. If no declaration sets an inherited property on an element, the element receives its parent's computed value. For a non-inherited property, defaulting uses the property's initial value instead.

A property's definition determines whether defaulting uses the parent's computed value or the property's initial value. Cascading and defaulting produce each property's specified value. The browser then resolves the specified value into a computed value. An inherited property receives its parent's computed value when the cascade produces no cascaded value for that property. A non-inherited property with no cascaded value instead takes its own initial value, its built-in default, regardless of the parent. A card styled with color: #1a1a1a and border: 1px solid gives a nested <em> the same color because color is inherited. The nested <em> does not receive the card's border because border is not inherited. Its own border takes the initial value none.

CSS defines whether each property inherits. Text-related properties such as color, font-family, and line-height usually inherit so descendants share the surrounding text style. Box properties such as border, margin, and width do not inherit because each box needs its own layout values. Otherwise, nested boxes would receive the parent's border, margin, or width even though each box has its own role in layout.

Unregistered custom properties inherit by default. A descendant can read an inherited custom property with var(). An @property registration can disable inheritance by setting inherits: false. Descendants can therefore inherit design-token values declared on an ancestor.

CSS provides five keywords for choosing an inherited value, the initial value, or a value from a lower-precedence part of the cascade.

  • inherit takes the parent's computed value even if the property normally wouldn't inherit it.
  • initial takes the property's own built-in default even if it normally inherits.
  • unset acts like inherit on an inherited property and like initial on a non-inherited property.
  • revert acts as if declarations from the current cascade origin did not apply to that property. In author styles, it uses the value that would win without author-origin declarations.
  • revert-layer acts as if declarations in the current cascade layer did not apply to that property. The cascade then continues through declarations with lower precedence.

Because color is inherited, color: unset gives the card its parent's computed color. If @layer base sets the card's color to gray and a later @layer theme declares color: revert-layer, the browser ignores the theme declaration, leaving the base layer's gray declaration as the winner. If a normal theme rule uses color: revert instead, the browser ignores author-origin declarations for that property and checks the user and user-agent origins before defaulting.

inheritance.css CSS 
.card { border: 1px solid var(--border); color: var(--text-dim); }

.card__highlight {
  color: inherit;  /* redundant here: color already inherits by default */
  border: inherit; /* forces the highlight to inherit the card's border */
}

Writing Predictable CSS

Layer order determines priority between groups of rules. For inherited properties, inheritance provides the value when no declaration wins on the element itself.

The root sets a color that the save button would inherit if neither button rule applied. Two rules in different layers set color on the button itself. The earlier base layer uses a long, highly specific selector. The later components layer uses a single class.

resolution.css CSS 
:root { color: #1a1a1a; }

@layer base, components;

@layer base {
  #page .sidebar .card .save-button { color: red; }
  /* (1, 3, 0) — very specific, but declared in the earlier layer */
}

@layer components {
  .save-button { color: var(--accent); }
  /* (0, 1, 0) — wins because layer order is compared before specificity */
}

Both competing declarations are normal author declarations, so they tie on origin and importance. components was declared after base, so its declaration wins at the layer step. Because the layer order resolves the conflict, the browser does not compare specificity. The winning declaration sets the button's color, so the inherited root color is not used.

Flat, low-specificity selectors let layers and source order control precedence without adding IDs or !important merely to override an existing rule. A project using BEM can combine flat class selectors with an explicit layer order, making precedence easier to trace across its CSS codebase.

Default inheritance lets an author declare a shared value once instead of repeating it on every descendant. Unregistered custom properties inherit by default, so a descendant can use a value declared on an ancestor unless it declares its own. A component can therefore declare a design-token custom property at its root and let descendants inherit it.
