React Patterns & Component Design

Six recurring patterns for structuring React components, and the three behaviors of the framework itself that make them necessary.

Field guide
~16 min read
React
July 2026

React doesn't ship a pattern library. What it ships is a small set of rules about how state and rendering relate to each other, and most of what people call a "React pattern" is really a way of working within those rules instead of around them. Compound components, the state reducer trick from Downshift, headless hooks: none of these are things React tells you to do. They are solutions that kept showing up once enough teams hit the same wall, and eventually the community gave them names.

This is a field guide to six of them. For each one: the problem it solves, a minimal version of the code, and when reaching for it is the wrong call. Before any of that, it's worth naming the three behaviors of React that make these patterns necessary in the first place, because every pattern below is really just a different arrangement of the same three constraints.

Three pillars

Every pattern in this article is a different arrangement of the same three rules.

The first is declarative rendering. A React component describes what the UI should look like for a given state, it doesn't script the sequence of DOM operations that gets it there. Compare this to something like jQuery, where updating a counter meant finding the node and setting its textContent by hand, and every place in the code that touched that node had to know about every other place that touched it. In React, the same counter is a function of one number.

counter.jsx JSX 
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}

Nothing in that component reaches into the DOM. It describes a button whose label is always whatever count currently is, and React figures out on its own which DOM operations, if any, are needed to make that true. That's also what makes the component testable and predictable: the output only ever depends on its inputs.

The second is one-way data flow. State lives in exactly one component, and it moves down the tree as props. A child never reaches up and changes its parent's state directly, it calls a function the parent handed it, and the parent decides what to do with that. There's no two-way binding where a child input and a parent variable stay magically in sync, the sync is something you write, explicitly, as a callback.

name-input.jsx JSX 
function Parent() {
  const [name, setName] = useState('');
  return <NameInput value={name} onChange={setName} />;
}

function NameInput({ value, onChange }) {
  return (
    <input
      value={value}
      onChange={(e) => onChange(e.target.value)}
    />
  );
}

NameInput never owns name. It receives the current value as a prop and asks the parent to change it by calling onChange, the change flows back up as an event rather than as a direct mutation. Every pattern later in this article, including the ones that look like they're breaking this rule with context or refs, is still built on top of it.

The third is that React is reactive to state change, specifically. A component re-renders because setState or a reducer's dispatch ran, not because you told it to refresh. There's no render() call scattered through the codebase the way there might be in an imperative UI framework. This sounds like a small distinction, but it's the reason concurrent rendering, batching, and the useSyncExternalStore-style hooks that bridge non-React state into a component all exist: React needs render to stay a pure function of state so it's free to schedule, interrupt, and retry that function on its own terms.

Pillar
Declarative rendering

Describe the UI for a given state. Don't script the DOM operations that produce it.

Pillar
One-way data flow

State moves down as props, changes move up as events. No implicit two-way binding.

Pillar
Reactive to state change

Render runs because state changed, never because something called it directly.

Compound components

A parent shares state with its children through context, so the composition reads like markup instead of a config object.

A tab component with a handful of options can take a single config prop and be done with it. Once it needs icons on some tabs, a disabled state on others, and a custom badge next to one of them, that config object turns into its own miniature schema, and the component's API stops looking like React at all. The compound component pattern solves this by letting the parent expose several sub-components instead of one prop-driven black box. A shared piece of state, usually which tab is active, lives in the parent and is passed to the children implicitly through context rather than explicitly through props.

tabs.jsx JSX 
const TabsContext = createContext(null);

function Tabs({ children, defaultValue }) {
  const [active, setActive] = useState(defaultValue);
  return (
    <TabsContext value={{ active, setActive }}>
      {children}
    </TabsContext>
  );
}

function Tab({ value, children }) {
  const { active, setActive } = useContext(TabsContext);
  return (
    <button
      aria-selected={active === value}
      onClick={() => setActive(value)}
    >
      {children}
    </button>
  );
}

Tabs.Tab = Tab;

The consumer never sees TabsContext. They see Tabs and Tabs.Tab, which read as ordinary nested elements:

usage.jsx JSX 
<Tabs defaultValue="profile">
  <Tabs.Tab value="profile">Profile</Tabs.Tab>
  <Tabs.Tab value="billing">Billing</Tabs.Tab>
</Tabs>

Adding an icon to one tab, or a badge to another, means adding a prop to that one Tabs.Tab instance, not touching a shared config shape used by every tab in the app. This is the pattern underneath most accessible component libraries, Radix and React Aria included, because it lets them ship a set of primitives that compose however the consumer needs without predicting every layout up front.

When not to use it

Context requires the children to stay descendants of the provider in the React tree, so a sub-component that needs to render through a portal, or be reordered by something outside the component's control, fights the pattern instead of benefiting from it. And for a component with no real sub-parts, a couple of props is still the simpler and more discoverable API.

State reducer

Compound components fix composition. This fixes control: letting the owner of a component override how its state changes without forking it.

Sooner or later a shared component's default behavior is almost right for a new use case, but not quite. A disclosure widget that should stay open after a selection instead of auto-closing, a combobox that shouldn't clear its input on blur. The obvious fix is a new boolean prop for each variation, and that works until the tenth variation, at which point the prop list has become a config object all over again. The state reducer pattern, popularized by Kent C. Dodds' Downshift library, offers a different way out: the component still owns its state and its useReducer, but the consumer can supply a function that intercepts the reducer's proposed next state and rewrites it before it's applied.

use-toggle.js JavaScript 
function internalReducer(state, action) {
  switch (action.type) {
    case 'toggle':
      return { on: !state.on };
    default:
      return state;
  }
}

function useToggle({ stateReducer = (state, action, changes) => changes } = {}) {
  const [state, dispatch] = useReducer((state, action) => {
    const changes = internalReducer(state, action);
    return stateReducer(state, action, changes);
  }, { on: false });

  return { on: state.on, toggle: () => dispatch({ type: 'toggle' }) };
}

By default stateReducer just returns whatever the internal reducer computed, so useToggle() behaves normally with no configuration at all. A consumer who needs different behavior, say a toggle that can only be switched on and never back off, passes their own function that inspects the proposed changes and returns something else instead:

usage.jsx JSX 
const { on, toggle } = useToggle({
  stateReducer: (state, action, changes) =>
    state.on ? state : changes,
});

Nothing about useToggle's internals changed. The override lives entirely in the consumer's code, which is the point: the component doesn't need to anticipate every variation in advance, it just needs one seam where a consumer can reach in.

When not to use it

This pattern makes a component's internal action vocabulary part of its public API, which is real surface area for someone else to learn and for you to keep stable. It earns its cost on a shared design-system primitive that other teams need to customize. For a one-off component with a single consumer, just change the component.

Headless components

Split behavior from presentation entirely: a hook owns the logic, the consumer owns every pixel of markup.

A styled component that ships its own markup and CSS is fast to use and slow to restyle. Every team that wants a different look ends up fighting the shipped styles with overrides, or forking the component outright. The headless pattern sidesteps this by not shipping markup at all. All the interactive logic, the keyboard handling, the ARIA attributes, lives in a hook. The hook returns state and a set of prop getters, and the consumer decides what elements to render and how they look. This is the same idea Downshift introduced for comboboxes, and it's why libraries like TanStack Table and React Aria ship as hooks rather than styled components: a table or a date picker has wildly different visual requirements from one product to the next, but the logic of sorting rows or navigating a calendar with a keyboard barely changes.

use-disclosure.js JavaScript 
function useDisclosure(initial = false) {
  const [isOpen, setIsOpen] = useState(initial);

  return {
    isOpen,
    getTriggerProps: () => ({
      'aria-expanded': isOpen,
      onClick: () => setIsOpen((open) => !open),
    }),
    getPanelProps: () => ({ hidden: !isOpen }),
  };
}

The hook never renders a <button> or a <div>. It hands back plain objects that a consumer spreads onto whatever elements they choose:

faq-item.jsx JSX 
function FAQItem({ question, answer }) {
  const { getTriggerProps, getPanelProps } = useDisclosure();
  return (
    <div className="faq-item">
      <button {...getTriggerProps()}>{question}</button>
      <p {...getPanelProps()}>{answer}</p>
    </div>
  );
}

Two products can use useDisclosure and end up with completely different markup, animation, and styling, while sharing the exact same open and close logic. Nothing about the hook cares what a "trigger" or a "panel" actually is.

When not to use it

Headless hooks push accessibility responsibility onto every consumer, they still have to spread the right props onto the right elements, and it's easy to forget one. For an internal tool that nobody is going to re-skin, a plain styled component with sensible defaults ships faster and is harder to misuse.

Polymorphic components

Let a component render as a different element entirely, so callers stop choosing between a dedicated Link prop and an as prop.

A design system's Button sometimes needs to be a link styled as a button, navigating instead of firing a click handler. Duplicating all of Button's styling logic into a separate LinkButton is one option, and it works until the two drift out of sync. An older fix is an as prop that swaps the rendered tag, but that only covers a small, hardcoded list of alternatives, and it still wraps whatever gets passed in a component the caller didn't ask for. The pattern that's become standard, popularized by Radix's Slot, is asChild: instead of rendering a wrapper element, the component merges its own props onto a single child the caller provides.

button.jsx JSX 
function Button({ asChild, className, ...props }) {
  const Comp = asChild ? Slot : 'button';
  return <Comp className={cx('btn', className)} {...props} />;
}
usage.jsx JSX 
<Button asChild>
  <a href="/pricing">See pricing</a>
</Button>

With asChild set, Slot clones the single <a> child and merges Button's className, event handlers, and ref onto it, rather than rendering a <button> wrapped around an <a>. The DOM stays one valid element, and the anchor keeps its native behavior: right-click to open in a new tab, middle-click, and crawlability all still work, because it's still a real link under the hood rather than a button that fakes navigation with an onClick.

When not to use it

asChild needs exactly one valid element as its child, it breaks or behaves unpredictably with fragments, text nodes, or multiple children. Merging props, especially className and event handlers, has to be done carefully or one side silently overwrites the other. If the only requirement is swapping between a small, known list of tags, a plain as prop is simpler and easier to type correctly.

Custom hooks

The pattern that replaced higher-order components and render props for most everyday reuse.

Before hooks, sharing stateful logic across components meant one of two things. A higher-order component, a function that took a component and returned a new one with extra props injected, or a render prop, a component whose child was a function it called with some data. Both worked, and both had real costs. Two HOCs wrapping the same component could inject props with the same name and silently collide, and a component tree wrapped in three or four HOCs was legitimately hard to read in React DevTools, since every one of them added a layer that had nothing to do with what was actually on screen. Render props avoided the naming collisions but nested visually in the JSX even though nothing about them was rendering nested DOM.

A custom hook sidesteps both problems. It's a plain function that calls other hooks and returns values directly, no wrapping component, no extra tree depth, and it reads exactly like the built-in hooks it's composed from. A hook that wraps localStorage is a good example of the third pillar in practice: the storage changes outside of any setState call, so the hook needs useSyncExternalStore, not useState, to stay correctly synced with it.

use-local-storage.js JavaScript 
function subscribe(callback) {
  window.addEventListener('storage', callback);
  window.addEventListener('local-storage', callback);
  return () => {
    window.removeEventListener('storage', callback);
    window.removeEventListener('local-storage', callback);
  };
}

function useLocalStorage(key, initialValue) {
  const cache = useRef();

  const getSnapshot = () => {
    const raw = localStorage.getItem(key);
    if (!cache.current || cache.current.raw !== raw) {
      cache.current = { raw, value: raw ? JSON.parse(raw) : initialValue };
    }
    return cache.current.value;
  };

  const value = useSyncExternalStore(subscribe, getSnapshot);

  const setValue = (next) => {
    localStorage.setItem(key, JSON.stringify(next));
    window.dispatchEvent(new Event('local-storage'));
  };

  return [value, setValue];
}

Calling const [theme, setTheme] = useLocalStorage('theme', 'dark') still reads exactly like useState, even though nothing inside it is useState. The cache ref exists only to keep getSnapshot returning a stable reference between calls, and the local-storage event covers same-tab updates that the native storage event doesn't fire for. Two components reading the same key, or the same key changing in another tab, stay in sync automatically, something useState and useEffect alone can't guarantee. There's no wrapper component to find in the tree and no injected prop names to remember, which is a large part of why hooks displaced HOCs and render props for most reuse: the API surface is just a function signature.

When not to use it

A hook can share logic, but it can't control composition or the shape of rendered output. If the reusable thing needs to arrange children, own markup, or expose sub-components, that's a job for compound components or the headless pattern, not a hook returning a single value.

Context selectors

A single large context re-renders every consumer on every change. Splitting it is the fix that costs almost nothing.

React re-renders every component subscribed to a context whenever that context's value changes, whether or not the component actually reads the part that changed. A common mistake is one large context holding both frequently changing state and the dispatch function used to update it. Every component that only wants to dispatch an action, and never reads the state itself, still re-renders on every update, because it's subscribed to the same context object as everything else.

The fix costs almost nothing: split the state and the dispatch function into two separate contexts. A reducer's dispatch is referentially stable across renders, so a component that only calls useContext on the dispatch context never has a reason to re-render at all.

count-provider.jsx JSX 
const CountStateContext = createContext(0);
const CountDispatchContext = createContext(() => {});

function CountProvider({ children }) {
  const [count, dispatch] = useReducer(
    (state, action) => (action.type === 'increment' ? state + 1 : state),
    0
  );

  return (
    <CountStateContext value={count}>
      <CountDispatchContext value={dispatch}>
        {children}
      </CountDispatchContext>
    </CountStateContext>
  );
}

A component that calls useContext(CountDispatchContext) to dispatch an increment never re-renders when count changes, because it isn't subscribed to CountStateContext at all. When two contexts still isn't granular enough, selector libraries take this a step further and let a component subscribe to a slice of a single context value, but the split above solves the common case without adding a dependency.

When not to use it

Splitting contexts adds real boilerplate, two providers and two hooks instead of one, for a problem that might not exist yet. Profile with React DevTools first. This is a fix for a measured re-render problem, not a default way to structure every context in an app.

Where these patterns stop

None of the six patterns above break the three pillars from the start of this article. Compound components and headless hooks still pass state down and events up, they just move context or a return value into the path instead of a prop. The state reducer pattern still renders declaratively, it only changes who gets to decide what the next state is. Context selectors don't change what triggers a re-render, they just narrow which components are subscribed to it. Every pattern here is a negotiation over where state lives and who's allowed to shape it, never a way around React's own rules.

What's deliberately out of scope is the boundary these patterns all assume: a single component tree running on the client. React Server Components move part of that tree onto the server, and Actions replace the manual loading, error, and data trio with something closer to a native form submission. That's a different set of tradeoffs from anything covered here, and it gets its own treatment separately.
