React Patterns & Component Design

Six ways to shape reusable component APIs, grounded in React's rendering and state model.

Andreas Ögren
~9 min read
Last updated July 2026

React defines how components render and how state moves through a tree, but it leaves component APIs to the application. The recurring patterns in this article grew out of that open space. Each one solves a problem that appears when a reusable component needs more flexibility than another boolean prop can provide.

The first section establishes the parts of React's model that the patterns rely on. The remaining sections show the problem behind each pattern, a small implementation, and the point at which the added abstraction stops paying for itself.

The React model underneath the patterns

The patterns differ in API shape, but they all preserve the same direction of data and control.

Declarative rendering means that a component describes the interface for its current props and state. React works out which DOM updates are needed after the component returns. Application code therefore expresses a counter as a button whose label comes from count, rather than as a sequence that finds a node and changes its text.

counter.tsx TSX 
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}

The component does not reach into the DOM. During render, its output depends only on its inputs. Event handlers may update state, and React renders again with the new value.

One-way data flow gives each piece of state an owner. The owner passes values to descendants through props or context. A child requests a change by calling a callback or dispatching an action; it does not mutate its parent's state directly.

name-input.tsx TSX 
function Parent() {
  const [name, setName] = useState('');
  return <NameInput value={name} onChange={setName} />;
}

function NameInput({ value, onChange }) {
  return (
    <input
      value={value}
      onChange={(e) => onChange(e.target.value)}
    />
  );
}

NameInput receives the current value and reports edits through onChange. The parent remains the source of truth. Context and custom hooks can hide some of this plumbing, but they do not reverse the flow.

Finally, React schedules rendering after state updates and when a parent renders. Components may also subscribe to context or an external store. Because React can start, pause, or repeat render work, the render phase must remain pure. Effects and event handlers are where synchronization and other side effects belong.

Pillar
Declarative rendering

Describe the UI for a given state. Don't script the DOM operations that produce it.

Pillar
One-way data flow

Owners pass values down. Children request changes through callbacks or actions.

Pillar
Reactive to state change

State, parent renders, context, and external subscriptions can schedule new render work.

Compound components

Related component parts share behavior while callers keep control of their arrangement.

A small tab component can accept an array of labels. That API becomes awkward when individual tabs need richer content or different behavior. Every new exception expands the configuration schema.

Compound components expose the parts directly. The parent owns shared state, such as the selected tab, while its children read that state through context. Callers compose ordinary JSX instead of describing the same tree indirectly through data.

tabs.tsx TSX 
const TabsContext = createContext(null);

function Tabs({ children, defaultValue }) {
  const [active, setActive] = useState(defaultValue);
  return (
    <TabsContext value={{ active, setActive }}>
      {children}
    </TabsContext>
  );
}

function Tab({ value, children }) {
  const { active, setActive } = useContext(TabsContext);
  return (
    <button
      aria-selected={active === value}
      onClick={() => setActive(value)}
    >
      {children}
    </button>
  );
}

Tabs.Tab = Tab;

The context stays private to the implementation. Callers work with Tabs and Tabs.Tab, so the structure remains visible at the call site.

usage.tsx TSX 
<Tabs defaultValue="profile">
  <Tabs.Tab value="profile">Profile</Tabs.Tab>
  <Tabs.Tab value="billing">Billing</Tabs.Tab>
</Tabs>

Rich content can now be placed in one tab without changing a shared data shape. Libraries such as Radix Primitives and React Aria Components use composition for the same reason: each part keeps a focused contract while the caller controls the final structure. The broader design principle is covered in Software Design Principles.

When not to use it

Use this pattern when the parts form one conceptual control and need shared state. A portal does not break context because it changes DOM placement, not the React parentage. The pattern becomes brittle when required parts must be discovered by inspecting arbitrary children or when a small prop API would express the same control more clearly.

State reducer

A reusable component proposes its next state, and the caller may refine that decision.

Shared controls often need one variation that the original API did not predict. A combobox might keep its menu open after a selection, for example. Adding a boolean for every variation eventually turns the component into a matrix of interacting options.

The state reducer pattern gives the caller one controlled extension point. The component calculates a proposed state change, then passes it through a caller-supplied reducer before committing it. Downshift exposes this pattern through its stateReducer API.

use-toggle.ts TS 
function internalReducer(state, action) {
  switch (action.type) {
    case 'toggle':
      return { on: !state.on };
    default:
      return state;
  }
}

function useToggle({ stateReducer = (state, action, changes) => changes } = {}) {
  const [state, dispatch] = useReducer((state, action) => {
    const changes = internalReducer(state, action);
    return stateReducer(state, action, changes);
  }, { on: false });

  return { on: state.on, toggle: () => dispatch({ type: 'toggle' }) };
}

The default reducer accepts the proposed change, so the hook needs no configuration for its normal behavior. This caller prevents the toggle from returning to off after it has been enabled.

usage.tsx TSX 
const { on, toggle } = useToggle({
  stateReducer: (state, action, changes) =>
    state.on ? state : changes,
});

The component still owns its state machine and public actions. The caller changes one transition without copying the implementation or asking the component to predict that variation.

When not to use it

The action names and proposed state now form part of the public contract, so they must remain stable. That cost can be worthwhile for a widely reused primitive. A component with one owner is usually clearer when its behavior is changed directly.

Headless components

Reusable behavior is supplied without prescribing the rendered markup or visual style.

A styled component is convenient while its markup and appearance match the product. Reuse becomes harder when another product needs a different DOM structure or styling system. A headless component moves state and interaction behavior into a hook or unstyled primitive, leaving the caller to render the interface.

Prop getters are one common API. They combine the event handlers and accessibility attributes that belong on a particular element. Downshift and the lower-level React Aria hooks use this approach for controls whose behavior is difficult to reproduce correctly.

use-disclosure.ts TS 
function useDisclosure(initial = false) {
  const [isOpen, setIsOpen] = useState(initial);

  return {
    isOpen,
    getTriggerProps: () => ({
      'aria-expanded': isOpen,
      onClick: () => setIsOpen((open) => !open),
    }),
    getPanelProps: () => ({ hidden: !isOpen }),
  };
}

The hook returns props instead of elements. The caller applies those props to the trigger and panel.

faq-item.tsx TSX 
function FAQItem({ question, answer }) {
  const { getTriggerProps, getPanelProps } = useDisclosure();
  return (
    <div className="faq-item">
      <button {...getTriggerProps()}>{question}</button>
      <p {...getPanelProps()}>{answer}</p>
    </div>
  );
}

Callers may choose different surrounding markup and styling while sharing the open-state behavior. The hook still assumes that its trigger props land on an interactive element, so freedom of presentation does not remove semantic requirements.

When not to use it

A low-level hook is easy to misuse because callers must place every returned prop on a suitable element. Prefer a higher-level unstyled component when it can preserve the required semantics without blocking customization. A styled component is often enough when the markup and appearance have a single owner.

Polymorphic components

Share presentation and behavior while allowing the caller to choose the underlying element.

A design system may want a button visual treatment on both actions and links. The semantics still matter: an action belongs on a <button>, while navigation belongs on an <a>. Copying the styles into separate components can make them drift.

A polymorphic component lets the caller select the element. One version uses an as prop. Radix Primitives uses asChild, which merges a primitive's props and behavior onto one child instead of adding a wrapper.

button.tsx TSX 
function Button({ asChild, className, ...props }) {
  const Comp = asChild ? Slot : 'button';
  return <Comp className={cx('btn', className)} {...props} />;
}
usage.tsx TSX 
<Button asChild>
  <a href="/pricing">See pricing</a>
</Button>

With asChild, the anchor remains the only DOM element. It therefore keeps native link behavior, including opening in a new tab and exposing link semantics to assistive technology. The slotted child must spread the received props and accept the ref for the composition to work.

When not to use it

Polymorphism transfers semantic responsibility to the caller. A component must not make a heading or link behave like a button by appearance alone. Slot-based APIs also require one compatible child and well-defined rules for merging handlers, classes, and refs. Separate components are clearer when only two known semantic variants exist.

Custom hooks

Extract stateful behavior into a function without adding another component to the tree.

Higher-order components and render props can share stateful behavior, but both add structure around the component that uses them. Injected props may collide, and several wrappers can obscure the useful parts of a tree in development tools. Render props make the data flow explicit, although they also add nesting to the JSX.

A custom hook packages calls to other hooks behind a domain-specific function. Each caller still receives its own state unless the hook subscribes to a shared external source. The hook changes how logic is reused; it does not create shared state by itself.

Browser connection status is an external source because it can change without a React state update. useSyncExternalStore gives the hook a consistent way to read that value and subscribe to browser events.

use-online-status.ts TS 
function subscribe(callback: () => void) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

function getSnapshot() {
  return navigator.onLine;
}

function getServerSnapshot() {
  return true;
}

export function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    getSnapshot,
    getServerSnapshot
  );
}

Components call useOnlineStatus() without knowing how the browser subscription works. The third argument supplies a stable value during server rendering and hydration. The hook hides integration details while leaving the returned value and its meaning explicit.

When not to use it

A hook shares behavior, not markup, and each call normally has independent state. Use a component when the abstraction must enforce structure or semantics. Use context or an external store when separate callers must observe the same state.

Split contexts by what changes

Separate stable commands from changing state when consumers need different subscriptions.

A component that calls useContext subscribes to the whole context value. React compares the previous and next values with Object.is; it does not track which object field the component read. A new value therefore updates every consumer of that context.

State and dispatch often change at different rates. useReducer keeps the identity of dispatch stable, so placing it in a separate context prevents state changes from notifying components that only dispatch actions.

count-provider.tsx TSX 
const CountStateContext = createContext(0);
const CountDispatchContext = createContext(() => {});

function CountProvider({ children }) {
  const [count, dispatch] = useReducer(
    (state, action) => (action.type === 'increment' ? state + 1 : state),
    0
  );

  return (
    <CountStateContext value={count}>
      <CountDispatchContext value={dispatch}>
        {children}
      </CountDispatchContext>
    </CountStateContext>
  );
}

A dispatch-only consumer is no longer updated by CountStateContext. It can still render for other reasons, such as its own state or a parent render. If consumers need finer subscriptions within one large state object, an external store with selectors may be a better fit. Client State covers that decision in depth.

When not to use it

Two contexts add providers, hooks, and names that callers must learn. Split them when the subscriptions express a real difference in responsibility or when profiling shows useful work being repeated. A small, rarely changing value does not need this machinery.

Where these patterns stop

Choose the smallest API that leaves the caller enough control. Props are the clearest starting point. Compound parts help when callers need to arrange a control. A state reducer serves shared primitives with legitimate behavioral variants, while a headless API serves products that need control over markup. Polymorphism is useful only when it preserves native semantics.

These patterns describe component APIs inside a React tree. They do not decide whether state belongs in a local component, context, or an external store; that belongs to Client State. They also do not define the server/client module boundary, which is covered in React Server Components.
