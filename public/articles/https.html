HTTPS and Certificates

How TLS protects a connection, authenticates a server, and establishes trust in its certificate.

Andreas Ögren
~11 min read
Last updated July 2026

TLS protects data while it moves between a browser and a server. Encryption provides confidentiality, while authenticated encryption also detects modification in transit. Certificates let the browser authenticate the server. HTTPS combines that protected TLS connection with HTTP.

The TLS handshake establishes encryption and authenticates the server before ordinary application traffic begins. Understanding that sequence makes certificate fields and trust chains easier to reason about. The final sections apply the same model to local development, internal services, and production deployments.

A protected channel and an authenticated server

TLS must protect the connection and prove which server is on the other end. A connection that provides only one of those guarantees is not enough.

Solved by symmetric + asymmetric crypto
Protected channel

Authenticated encryption prevents a network observer from reading traffic or changing it without detection. It protects requests and responses as they travel between the two TLS endpoints.

Solved by certificates + a chain of trust
Identity

The certificate and handshake prove that the server controls a private key for the requested hostname. The browser then connects that certificate to a trusted root.

TLS 1.3 establishes both guarantees before the browser sends ordinary HTTP application data. The handshake section below walks through that sequence.

Why HTTPS matters even with nothing to hide

Browsers use transport security for more than the connection indicator. Many platform features are exposed only in a secure context, even when the application handles no obvious secret. Loopback origins such as http://localhost are treated as potentially trustworthy for development. An ordinary internal hostname over HTTP receives no such exception.

APIs gated behind a secure context

Service Workers, Geolocation, WebAuthn, Web Crypto, and camera or microphone access are among the features restricted to secure contexts. Some broader APIs, including Clipboard, gate particular methods rather than the entire interface.

The TLS handshake

Steps 1 and 2 use asymmetric math (ECDHE) to derive a shared secret. From there, everything including the certificate travels encrypted, and step 4 is where ordinary application traffic begins.

StepWhat happensCrypto
1. Client Hello Browser opens the connection and says hello: supported TLS versions, supported cipher suites, a random number, and an ephemeral public key share for the key exchange. Nothing secret is transmitted yet. plaintext
2. Server Hello Server picks a cipher, sends back its own random number, and its own key share. At this point both sides can independently derive the same shared secret using Diffie-Hellman math, without ever transmitting the secret itself. asymmetric (key exchange)
3. Certificate + Finished The server's Certificate, CertificateVerify, and Finished messages travel under handshake encryption. The browser validates the certificate chain and hostname, verifies proof of the certificate private key, and checks the Finished message before replying. certificate verification
4. Secure session Both sides now hold symmetric session keys derived from the earlier exchange. Every request and response from here on is encrypted with fast symmetric crypto. symmetric (bulk encryption)

Anatomy of a certificate

A certificate is a small, signed document, and each field below serves a specific purpose.

FieldExamplePurpose
Subject Alternative Name (SAN) app.internal.company.com The identity this certificate vouches for. Modern browsers check the SAN list specifically, not the older Common Name field, even if it's also present.
Issuer Acme Internal CA The Certificate Authority that verified this identity and signed the certificate. Could be a public CA like Let's Encrypt, or an internal CA a company runs itself.
Validity notBefore / notAfter A not-before and not-after date. Expired certificates are treated as fully untrusted. There is no grace period.
Public key EC P-256 The TLS endpoint's public key. The matching private key stays with that endpoint or its managed key service. A CertificateVerify signature proves possession during the handshake.
Signature SHA-256 + RSA The issuer's signature over the rest of the certificate, made with the issuer's private key. This is the part a browser verifies.
How the server knows which certificate to send

A single IP address, load balancer, or CDN edge often serves many hostnames with different certificates. The browser identifies the requested hostname through Server Name Indication (SNI) in the Client Hello. Traditional SNI is visible to network observers even though later handshake messages are encrypted. Encrypted Client Hello (ECH) can conceal that information when the browser, DNS setup, server, and network path all support it.

The chain of trust

A certificate is only as good as whoever signed it. Browsers walk the chain upward until they hit a root that's already trusted.

Trust anchor
Root CA

Self-signed and kept offline or tightly protected. Its public key is preinstalled in the OS and browser's trust store.

Day-to-day issuer
Intermediate CA

Signed by the root, used for everyday certificate issuing so the root itself rarely has to be touched or exposed.

app.internal.company.com
Leaf cert

The certificate a server presents during the handshake. Signed by the intermediate.

Self-signed certificates break the chain

A self-signed certificate is signed by its own private key instead of a trusted CA's. The connection can still be encrypted, but the browser cannot authenticate the endpoint from that certificate alone. An active attacker could substitute a different self-signed certificate unless the expected certificate was trusted through another channel.

Certificate Transparency and revocation

The chain proves who signed a certificate. Two more mechanisms keep the signers honest and deal with certificates that have to be pulled early.

A valid chain does not reveal whether a certificate was issued by mistake or after a compromise. Certificate Transparency (CT) makes publicly trusted issuance observable through append-only logs and signed certificate timestamps. Current Chrome, Safari, and Firefox policies require qualifying publicly trusted certificates to satisfy their CT rules. Domain owners can monitor those logs for certificates they did not request.

Revocation handles certificates that become unsafe before they expire, perhaps because a private key leaked or control of the domain changed. A Certificate Revocation List (CRL) publishes revoked serial numbers in batches. The Online Certificate Status Protocol (OCSP) instead lets a client ask about one certificate, but direct queries reveal the destination to the CA and browsers have often failed open when a responder is unreachable.

Browser vendors reduce those privacy and availability problems with vendor-managed revocation data, stapled status information, and other mechanisms rather than a live CA query for every connection. The exact strategy is browser and CA policy, so revocation does not behave like a single global lookup.

Shorter certificate lifetimes reduce how long a compromised certificate remains useful and limit reliance on revocation checks. Publicly trusted TLS certificates issued from 15 March 2026 have a maximum validity of 200 days, with further reductions scheduled through 2029. These limits make automated issuance and renewal part of normal certificate operations.

Trust stores, and why internal certs get flagged

Operating systems and browsers ship with trust stores containing root certificates selected under their own policies. Public CAs such as Let's Encrypt issue chains that end at one of those roots, allowing a browser to validate the chain without local setup.

Companies often run an internal certificate authority for services that are not public. Its certificates remain untrusted to browsers and tools such as Node.js until the relevant trust store contains that CA's root. Without that trust anchor, certificate validation fails even when the service sent the intended chain.

Distribution is therefore part of the design. Device management or group policy can install the internal root certificate on managed clients that need those services. Other clients should continue to reject the chain.

Node.js trust configuration

Node.js normally uses the CA source selected by its build, commonly the bundled Mozilla snapshot. Installing an internal root in the operating-system store may therefore fix a browser without fixing a Node client. Supported Node releases that provide --use-system-ca can add the system store. NODE_EXTRA_CA_CERTS extends the known roots from a PEM file, unless application code explicitly replaces the ca option.

shell Bash 
NODE_EXTRA_CA_CERTS=/path/to/ca.pem node server.js
The tempting shortcut

NODE_TLS_REJECT_UNAUTHORIZED=0 disables certificate verification instead of establishing trust. Avoid it even as a temporary fix because it can escape into scripts, shell profiles, or deployment configuration.

The practical playbook

Three different situations, three different answers. Most "why is this cert broken" questions trace back to applying the wrong one.

Local dev (Vite): make the local machine trusted

mkcert creates a local development CA, installs its root into supported local trust stores, and issues locally trusted certificates for names such as localhost. Other devices do not trust that CA unless its root is installed there too.

shell Bash 
mkcert -install
mkcert localhost app.local
vite.config.ts TS 
import fs from 'node:fs'

export default {
  server: {
    https: {
      key: fs.readFileSync('./localhost-key.pem'),
      cert: fs.readFileSync('./localhost.pem'),
    },
  },
}

Quicker but noisier: @vitejs/plugin-basic-ssl auto-generates a self-signed cert, but the browser will still warn.

Shared internal environments: one CA, company-wide

Staging, QA, and internal tools shared across teams typically rely on a company-run internal CA, usually managed by a platform or IT team. That CA issues certificates for *.internal.company.com-style domains, and its root certificate gets pushed to every employee device once.

If a warning appears on one machine but not another, compare their trust stores and the certificate chain before changing the service. A missing internal root is common, but hostname, time, and chain errors can produce similar warnings.

Production-style services: let the edge handle it

A reverse proxy or load balancer often terminates public TLS so certificate renewal and policy stay at the edge. The hop from that edge to the application is a separate trust boundary.

nginx.conf Nginx 
# nginx terminates TLS,
# proxies to Node in plain HTTP
listen 443 ssl;
ssl_certificate     app.crt;
ssl_certificate_key app.key;
location / {
  proxy_pass http://127.0.0.1:3000;
}

Plain HTTP on the internal hop is acceptable only when the deployment's network controls and threat model treat that path as trusted. Re-encrypt the hop, or use mutual TLS, when traffic crosses shared infrastructure or requires workload identity.

Common pitfalls

PitfallWhat to know
Expiry isn't optional Publicly trusted certificates issued from 15 March 2026 may last at most 200 days. The scheduled maximum falls to 100 days in 2027 and 47 days in 2029. Clients reject certificates outside their validity period, so issuance and renewal need monitoring as well as automation.
SAN, not CN Current browser hostname verification uses the Subject Alternative Name extension. Put every supported DNS name there rather than relying on the legacy Common Name field.
Mixed content An https page calling an http API gets the request silently blocked. Common when a Vite dev server is https but proxies to a plain-http backend.
"Untrusted" ≠ "unencrypted" A self-signed certificate can negotiate modern encryption, but the client lacks a configured trust path for its identity. A warning can also signal hostname, validity, or algorithm problems, so inspect the actual error.
localhost gets a free pass Loopback origins such as http://localhost are potentially trustworthy for secure-context checks. http://app.internal.company.com gets no general exemption.
Check the whole chain A server that sends only its leaf cert and forgets the intermediate will work in some browsers and fail in others, depending on what's cached.
HSTS remembers Once a browser records HSTS, it upgrades HTTP before the network request and does not allow bypassing certificate errors for that host. Preload removal is possible but slow, so treat submission as a long-lived operational commitment.
Certificate Transparency Certificates from public CAs like Let's Encrypt get published to public CT logs by design. An internal-only hostname issued one of these becomes publicly searchable, even though the service behind it isn't reachable.
Wildcards aren't infinite A certificate for *.internal.company.com covers exactly one subdomain level, not deeper nesting like api.app.internal.company.com, and not the bare domain itself.
