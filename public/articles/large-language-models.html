Large Language Models

How large language models generate responses and what that means for their reliability, latency, and cost.

Andreas Ögren
~35 min read
Last updated September 2026

A conventional computer program follows instructions that developers have written in advance. Its code defines how to process inputs, make decisions, and produce outputs. This works well when the relevant inputs and rules can be specified explicitly. Natural language is harder to handle this way because the same request can be expressed in many forms, and its meaning often depends on context.

A large language model (LLM) takes a different approach. Instead of relying on developers to write rules for every possible request, it learns statistical patterns from large amounts of data during training. When given some text, it uses the learned patterns to predict what is likely to come next. It generates a response one small piece at a time, repeatedly using the text produced so far as context for the next prediction.

This simple generation process can produce remarkably varied results. It can answer questions, write prose, generate code, and work through problems. But generating a plausible continuation is not the same as verifying that it is correct. A response can be fluent, detailed, and convincing while still containing mistakes.

This article explains how an LLM turns input into a response and how this process gives rise to both its capabilities and its limitations. The focus is on inference, the work an already trained model performs when handling a request. Training is covered only where it helps explain inference. Training infrastructure, model comparisons, and the details of building foundation models are outside the scope.

Model Input at Inference Time

An LLM does not directly interact with the user, files, or the web. A surrounding application decides what information to send to the model for each inference.

The user interacts with an application, which in turn interacts with the model. The application handles features such as the user interface, conversation history, file access, and web access. It gathers information, sends selected information to the model, and receives the model's response. The model itself only receives input from the application and generates a response from that input.

The text the user submits to the application is the prompt. Before sending anything to the model, the application can add other context, such as its own instructions, parts of the conversation history, contents of attached files, or information retrieved from the web. The prompt together with the context supplied by the application forms the model input for that inference. In this article, prompt means the text submitted by the user, while model input means everything supplied to the model for one inference. The term prompt is sometimes used more broadly for the complete model input, but we'll use the more narrow definition.

An attachment to a user message is thus not automatically part of the model input. Consider a coding application in which the user writes Explain @src/session.ts. The prompt contains the user's request and the file reference, but the model cannot open the file by itself. The application can interpret the reference, read its contents, and include relevant source code as context in the model input. If the application does not include the file contents, the model will not receive them. A URL works in much the same way. A prompt containing a URL does not by itself give the model access to the page. The application can fetch the page and include some or all of its contents as context. Applications that provide web search or browsing features perform this work outside the model.

The same rule applies to conversation history. A model does not have access to an earlier message merely because it appeared earlier in the interface. An application may include some earlier messages as context for a particular inference. Information from a previous message can influence the current response only when the application includes it in the current model input.

Images and documents are usually supported. The application can include attached images in the model input. For a document, the application might extract its text, send images of its pages, or use another supported approach. An attachment shown in the interface and the content actually sent to the model are therefore not necessarily the same thing.

The user therefore sees a larger system than the LLM itself. Features such as file access, conversation history, and web retrieval belong to the surrounding application. For each inference, the model receives the prompt together with additional context the application includes. The next section looks at how the text in this input is represented for the model.

Tokens and Tokenization

A tokenizer divides text into the units that a model reads and generates.

Before text reaches the model, a tokenizer divides it into tokens. Each token has a numeric identifier, and the complete set of tokens recognized by the model is its vocabulary. A token can represent a whole word, part of a word, whitespace, special characters, or combinations of these.

The tokenizer does not divide every word into pieces of the same size. Common words and character sequences can have tokens of their own, while less familiar text is built from smaller tokens. This approach is known as subword tokenization. It solves a practical vocabulary problem. A model cannot have a separate vocabulary entry for every possible name, product identifier, misspelling, or newly invented word, but it still needs a way to represent them. Combining reusable pieces allows a finite vocabulary to represent effectively unbounded text.

Compare these examples of familiar and unfamiliar text. A common word may fit into a single token, a recognizable identifier may split into several familiar parts, but an unusual string may need to be divided into much smaller pieces.

tokenization.txt Text 
"The quick brown fox"   →  [The] [ quick] [ brown] [ fox]      4 tokens
"getUserById"           →  [get] [User] [By] [Id]              4 tokens
"x7f3a9"                →  [x] [7] [f] [3] [a] [9]             6 tokens

(Illustrative. Boundaries differ between tokenizers.)

Different tokenizers use different vocabularies, so identical text can produce different token sequences and token counts. Character count and word count can provide a rough estimate because longer text generally requires more tokens, but there is no fixed conversion between them. Familiar prose may fit into relatively few tokens, while unusual names, identifiers, or other less familiar sequences can require more.

This means two passages with the same number of words do not need to consume the same amount of model capacity. A paragraph of ordinary English and a paragraph filled with UUIDs, source code, or uncommon names can have very different token counts. Tokenization therefore affects how much material fits into a request and how usage is measured.

Because the request and response are both token sequences, usage is measured in tokens. Input tokens are supplied to the model, while output tokens are generated by the model. These counts can affect both the amount of text a request can contain and its cost. After tokenization, the model processes the resulting sequence using numerical values learned during training.

How an LLM Generates Text

A trained Transformer turns the current token sequence into a probability distribution, selects one token, and repeats the process to generate a response.

The Transformer

The tokenizer supplies an identifier for each token, but an identifier only names an entry in the vocabulary. The model uses that identifier to look up a learned token vector, which is a list of numbers representing information the model has learned about that token and its relationships to other tokens. Every occurrence of a token begins with the same vector, so the starting vector does not represent what the token means in a particular context.

A neural network is a system of connected numerical calculations whose behavior is shaped during training.

A Transformer is a type of neural network that turns starting token vectors into context-sensitive representations. It processes a representation at every token position through a stack of Transformer layers. Each layer contains self-attention, a mechanism that moves information between token positions, and additional learned calculations that update each representation. The outputs from one layer become the inputs to the next, so later layers can build on relationships formed in earlier ones.

Many text-generating LLMs use a decoder-only Transformer, which predicts each new token from the tokens that precede it. The rest of this article follows that architecture.

The model also incorporates position information so the same tokens in a different order can produce different results. The Transformer therefore has access to both which tokens occur and where they occur. The layers use that information to update each position without changing the token sequence itself.

The result of these layers is a contextual representation at every position. Each representation reflects both its current position and information drawn from the sequence. A token vector represents a vocabulary item before this particular context has been processed, while a contextual representation reflects what that token is doing here. The model ultimately uses the representation at the final position to predict what token should come next.

From Context to Candidate Scores

The contextual representation at the final position does not identify a single next token. The model uses it to produce one score for every token in the vocabulary. A higher score means that a candidate fits the current sequence better than a candidate with a lower score. The serving software can convert the complete set of scores into a probability distribution, where every value is non-negative and all values sum to one. This distribution gives the software a basis for selecting the next token.

As the response grows, the current sequence contains the prompt followed by the tokens generated so far. Consider a coding assistant answering a question about a TypeScript function. The application has placed the developer's question and the contents of the referenced file in the prompt. After the model has generated The function can return, the serving software might derive the following distribution from the model's scores.

one-prediction-step.txt Text 
Prompt
  Source:   "return sessions.get(id);"
  Question: "Why can getSession return undefined?"

Generated so far: "The function can return"

Candidates:    undefined    0.72
               a            0.12
               the          0.08
               null         0.03

Remaining probability across the vocabulary: 0.05

(Token boundaries and probabilities are illustrative.)

The value 0.72 assigns 72 percent of the next-token distribution to undefined for this exact sequence. It compares that candidate with the other candidates for the next position. It does not mean that the completed explanation has a 72 percent chance of being correct. The supplied code provides request-specific evidence through its tokens, while the model's learned numerical values provide relationships established during training.

Generating a Response

Once the distribution is available, the serving software selects one token, appends it to the current sequence, and uses the model to calculate another distribution for the expanded sequence. This repeated process is autoregressive generation. Each selected token becomes input to the next prediction, so one choice can change every token that follows.

Thus, later tokens depend on earlier generated tokens that did not exist when generation began. If the model generates undefined, the next prediction is conditioned on The function can return undefined. If it instead generates null, the next prediction is conditioned on The function can return null. The model is now continuing a different sequence.

The tokenizer converts the generated token identifiers back into text and a response is created one token at a time. Generation stops when the serving software selects a special token that marks the end of the response or reaches another stopping condition.

Choosing the Next Token

A decoding strategy selects one candidate from the model's probability distribution.

A decoding strategy determines how the serving software selects a token from the probability distribution. Greedy decoding always selects the highest-probability token, which makes the choice deterministic for a given distribution. Sampling instead makes a weighted random choice, so high-probability tokens are more likely without being guaranteed. In the coding example, greedy decoding selects undefined, while sampling could select null.

The benefit of greedy decoding is consistency. The drawback is that repeatedly taking the locally most probable next token does not guarantee the best complete response, and deterministic output can still be deterministically wrong. Sampling introduces variation, which can be useful when several continuations are reasonable, such as when drafting prose or generating alternatives.

Temperature changes how strongly sampling favors the leading candidates. A lower temperature concentrates probability around candidates the model already scores highly, while a higher temperature gives lower-scoring candidates more opportunity to be selected. If an incorrect continuation already receives a strong score, lowering the temperature can make that same mistake more repeatable rather than correcting it.

Inside the Transformer

Transformer layers use learned parameters and self-attention to decide how the tokens in a sequence influence each prediction.

Weights and Parameters

The name neural network comes from an analogy with networks of neurons in the brain. In an artificial neural network, however, the connected components are mathematical operations rather than biological neurons.

A neural network organizes its calculations into layers of nodes. The input enters the first layer, and each later layer transforms values produced by the layer before it. The final layer produces the network's output. A weight controls how strongly one incoming value contributes to a calculation. Because the calculations use different weights, one incoming value can have more influence than another. A weight is one kind of parameter, the general name for an adjustable number stored in the model. The complete set of parameters determines how the network transforms an input token sequence into a prediction of the next token.

Self-Attention

Within each Transformer layer, self-attention lets one token position draw information from other permitted positions in the same sequence. It compares the current representations and calculates how strongly information from each permitted position should contribute to an update. This is the part of the layer that carries information between positions. Other learned calculations transform each position after that information has been combined.

The word self means that the positions come from the same sequence. The sequence is not itself an actor that pays attention. Self-attention is one component inside a Transformer layer rather than another name for the complete Transformer.

A decoder-only Transformer prevents a position from using tokens that come after it. Each position can attend to itself and earlier positions, while later positions are hidden by a causal mask. Other Transformer architectures can allow attention in both directions, but doing so during training here would reveal the token that the model is supposed to predict.

Consider The server crashed because it ran out of memory. The starting vector for it identifies that token but does not state what the pronoun refers to. As its representation passes through Transformer layers, self-attention lets information from earlier positions such as server and crashed influence it. Later layers can therefore represent it in a way that reflects its likely relationship to the server.

The token memory comes later, so it cannot influence the representation at it. When the Transformer processes the final position, however, that position can draw from the entire preceding sentence. This direction matters because the model uses the representation at the final position to predict what token should come next.

Training and Post-Training

Training finds the parameters used during inference, while post-training shapes how the model responds to instructions.

Pretraining

Training is the process that finds useful values for these parameters. During pretraining, the model receives token sequences and predicts what comes next. Its predictions are compared with the tokens that actually followed, and the parameters are adjusted to reduce the gap. Repeating this process across large amounts of text gradually produces parameters that capture useful statistical relationships among tokens and the contexts in which they appear.

Post-Training

Additional post-training can further adjust these parameters so the model is more likely to follow instructions and produce useful responses. The methods vary among models and depend on the behavior the training process is intended to encourage. Once training is complete, the resulting parameters are used to process new requests.

The model produced by pretraining is often called a base model. It has learned to continue token sequences, but it has not necessarily learned the conversational behavior users expect from an assistant. Post-training can produce an instruction-tuned model that is more likely to interpret a request as an instruction and follow conversational roles. Both models still generate responses by predicting tokens.

This creates a clear boundary between learning and use. Training changes the model's parameters based on examples. During inference, those parameters are fixed while the model calculates a response to new input. A prompt can guide the current inference by changing its input, but it does not normally update those parameters.

The Context Window

Every prediction can use only the bounded token sequence available in its current request.

Request Capacity

The model does not process an unlimited amount of text at once. For each request, it works with a bounded sequence of tokens called the context window. The limit exists because relating more token positions requires more computation and memory inside the model. Supporting a larger context window therefore makes inference more expensive, so every model is designed and served with some maximum sequence length rather than an unlimited one.

Everything the model needs to use for that request has to fit inside this token budget. That can include system instructions, the user's current message, earlier conversation turns that the application sends again, source code selected by the application, and results obtained from external systems. The generated response also extends the sequence, so services generally have to leave capacity for output rather than filling the entire available window with input.

For example, suppose a coding application has a 100,000-token context budget. Its instructions might use 2,000 tokens, conversation history 15,000, referenced files 30,000, related code selected from the repository 35,000, and the current question 500. Those pieces have already consumed most of the available space before the model begins answering. Adding another large file may require the application to remove older conversation history, include fewer code excerpts, summarize material, or leave less room for the response.

The application boundary described earlier also determines what consumes this capacity. A file on disk or a page on the web consumes no context space while it remains outside the request. Once the application includes extracted text or another encoded representation, that input becomes part of the context budget.

Conversation History and Memory

The context window is best understood as the model's working space for one request, not as its permanent memory. Information stored elsewhere by the application does not consume context-window space until it is included in a request, but it also cannot influence the model while it remains outside that request. A coding assistant creates the appearance of continuous memory by storing earlier messages and choosing which of them to send again. If an old message is not resent, summarized, or otherwise brought back into the current context, the model cannot use it for that inference.

Long-term memory is therefore an application feature rather than another name for a large context window. The two solve related but different problems. A larger context window allows more information to be considered at once, while long-term memory lets an application keep information outside the current request and decide when to bring it back. The application might resend an old message verbatim, summarize several messages, or select a stored fact only when it becomes relevant.

Fitting and Using Information

A large context window does not mean that every included token will influence the answer equally well. Long-context evaluations have found tasks where a model uses relevant information near the beginning or end more reliably than information in the middle. This position-dependent behavior is called lost in the middle. This creates an important difference between fitting information and using information. A large source file can fit within the advertised context limit yet still be difficult for the model to use reliably for a particular task. Context-window size is therefore a capacity specification, not a guarantee of perfect recall.

Useful context also has to be selected even when all available material fits. Two branches can contain different versions of a function, generated files can repeat source code, and irrelevant modules consume tokens while competing for attention. Including paths and repository revision information helps the application preserve these distinctions. The goal is not to fill the context window. It is to supply the smallest set of code, evidence, and instructions that the task needs.

Inference Cost and Latency

Input processing and sequential output generation create different kinds of work.

Processing the Input

A user experiences a generated response as one operation, but inference contains two computationally different phases. Understanding that distinction explains why adding large source files often affects the delay before the answer starts, while requesting a long explanation or patch affects how long generation continues afterward.

Before the first output token can be selected, the model has to process the input tokens and build the internal information needed to begin generation. This initial phase is often called prefill. Calculations across the supplied input can make substantial use of parallel hardware, but longer input still requires more computation and memory. Instructions, conversation history, referenced files, and retrieved code all contribute to this work because all of them are input tokens.

Compare two requests that ask why getSession can return undefined. One includes the function, its return type, and the relevant caller. The other includes every file in the authentication directory. Even if both eventually produce the same short explanation, the second request gives the model far more input to process before it can begin generating. This is why indiscriminately filling a large context window can increase latency even when the extra code provides no useful evidence.

The delay before the first generated token is often discussed separately from total response time because it affects how responsive an application feels. A system that begins streaming an answer after half a second feels different from one that remains silent for several seconds, even if both finish at nearly the same time. Reducing unnecessary input can therefore improve the time before generation begins.

Generating the Output

After prefill, the model enters the autoregressive generation loop described earlier. The first output token is selected, then that token becomes part of the sequence used to calculate the second, and so on. This phase is often called decoding. Here, decoding names the complete output phase. During each step of that phase, the decoding strategy determines how the serving software selects the next token.

Decoding has a dependency that prefill does not. Token 80 cannot be selected until token 79 is known. The model may perform enormous amounts of parallel numerical work inside each individual prediction step, but the output positions themselves form a sequence. Asking for another 500 generated tokens therefore adds roughly another 500 sequential selection steps.

This creates two different optimization levers. If a coding assistant takes too long to start responding, the application should examine how much source text it sends and how efficiently that input is processed. If it starts quickly but takes too long to finish, response length and decoding speed become more important. Treating all latency as one problem can hide which part of the request is actually expensive.

Token Usage and Cost

Token usage can also affect monetary cost. When a provider meters input and output tokens separately, repeatedly including large source files increases input usage, while requesting a longer explanation or patch increases output usage. The prices need not be the same for the two categories, so reducing 1,000 input tokens and reducing 1,000 output tokens do not necessarily save the same amount.

This does not imply that shorter prompts are always better. Omitting the type or caller that explains the behavior may reduce cost while making the answer less reliable. The practical goal is to keep the instructions and code the task needs while omitting material that does not help. The requested output should be no longer than the user or downstream system needs.

Grounding and Hallucinations

Reliable factual output depends on relevant evidence supplied during inference and, where necessary, checks performed outside the model.

Evidence at Inference Time

A language model creates a particular reliability problem because it can generate a sentence in the same fluent style whether that sentence is well supported, poorly supported, or false. Fluency is produced by next-token prediction, so fluent wording is not itself evidence that the underlying claim has been checked.

Consider a coding assistant that receives the question “Why can getSession return undefined?” without the contents of session.ts. The model may know several common reasons from training and can produce a plausible explanation. Yet it does not know whether this implementation reads a map, parses a cookie, calls a database, or deliberately returns undefined for another reason. General knowledge about TypeScript cannot establish what this repository actually does.

Grounding addresses that problem by supplying identified evidence during inference. In a coding application, the evidence might be a source file, a type declaration, compiler output, or a test result. The contents of session.ts enter the context as tokens and give the model repository-specific information to use in its explanation. Grounding changes the model's input rather than its trained parameters.

This distinguishes grounding from training. If the implementation of getSession changes, retraining an LLM would be a slow and indirect way to communicate that repository change. Supplying the current source during inference gives the request access to the new implementation immediately. Training is useful for teaching broad patterns and behavior. Grounding is useful when a response must depend on particular evidence available at request time.

Unsupported and False Claims

A hallucination is generated content that presents false information as though it were true. The term is also sometimes used more broadly for claims that are not supported by the available evidence. Those ideas overlap but are not identical. A statement can be true but unsupported by the supplied source, while another statement can be both unsupported and false.

For example, suppose the application supplies only the following code.

session.ts TypeScript 
const sessions = new Map<string, Session>();

export function getSession(id: string): Session | undefined {
  return sessions.get(id);
}

If the model claims that sessions expire after 30 minutes, that claim is unsupported by the supplied code. It might accidentally be true because another file removes old entries, but this evidence does not establish it. If the application has no expiration behavior, the same statement is also a hallucination under the narrower definition used here. Applications that must explain a particular codebase often need to reject unsupported claims whether or not they happen to be true.

The generation mechanism explains why these failures are possible. Pretraining improves next-token prediction rather than turning the parameters into an authoritative database lookup. During inference, the model scores continuations according to its learned relationships and the current context. A plausible but unsupported continuation can therefore receive a high score. Nothing in the basic next-token mechanism performs a separate factual check before the token is emitted.

This is why reducing sampling randomness does not solve hallucinations. Suppose the unsupported phrase after 30 minutes receives the highest score. Greedy decoding can select it every time. Lower temperature may make the same error more consistent. Decoding controls which continuation is selected from the model's candidates. It does not introduce missing evidence.

Sources, Tools, and Retrieval

Source references have a similar distinction. If the application knows which files and line ranges it supplied, it can attach those references to the response. If the model itself generates a reference such as src/cache.ts:42, that path and line number are another sequence of generated tokens. They may be correct, but generation alone does not prove that the location exists or supports the explanation. A code reference is useful evidence only when the application can connect it to the repository state that the model received.

Different questions also require different kinds of grounding. Source code can establish what the checked-out implementation says. Compiler output is stronger evidence for whether that code type-checks, while a test result or runtime trace can show how it behaved during a particular execution. None of those sources alone proves which revision is deployed in production. The application should use evidence that answers the particular question rather than treating every piece of context as interchangeable.

Tools and retrieval provide two common grounding paths. An agent harness can let the model request a file read, repository search, compiler run, or test run. The application decides which operations are permitted, performs them through controlled code, and can place the results into the next model request.

Retrieval-augmented generation, or RAG, instead searches a collection for passages or code excerpts that appear relevant and places selected results in the context. Retrieval is useful when a repository is too large to send in every request. Both tools and retrieval obtain evidence outside the model and place useful results in the current context so generation can use them.

Grounding therefore improves the information available to generation, but it does not remove every failure mode. Retrieval can select a similarly named function from the wrong module or branch. A tool can return stale or misunderstood output. The model can misread correct code. An application that requires stronger assurance must test the whole evidence path rather than treating the presence of retrieval or tools as a guarantee of correctness.

Embeddings for Retrieval

A separate embedding model can represent text as vectors so an external retrieval system can select useful context for the LLM.

Searching by Meaning

Grounding creates a selection problem. A repository can contain thousands of files, while only a few functions and types explain the behavior in question. Sending the entire repository with every request would consume context capacity and input computation even though most of the code is irrelevant. The application therefore needs a way to find promising excerpts before it calls the LLM.

Exact search solves part of this problem and is especially useful when a developer names a symbol such as getSession. Other questions use different words from the implementation. A developer may ask, “Where does the server recover the signed-in user's session?” while the code reads sessions.get(id). Few words match even though the question and function are closely related.

Retrieval Vectors

An embedding model provides another kind of search signal. It converts a query or code excerpt into a fixed-length vector designed so that texts with related meanings tend to have similar vectors. A retrieval system can therefore compare the vector for the developer's question with vectors previously created for repository excerpts. The question about recovering a session can rank near getSession even without an exact keyword match.

This use of vectors resembles the token vectors introduced earlier, but the purpose is different. A token vector inside the LLM is part of the model's internal computation for one vocabulary token. A contextual representation changes as the Transformer processes that token in a particular sequence. A retrieval embedding, by contrast, usually represents a complete query or content excerpt so an external search system can compare it with other queries or excerpts.

The retrieval system normally computes embeddings for code excerpts ahead of time and stores them in an index. When a question arrives, it creates an embedding for the query and measures how similar that vector is to the stored vectors. Excerpts with stronger similarity scores rank higher. Only selected source text needs to be inserted into the LLM's context.

This creates a useful division of labor. The embedding model indicates which code excerpts seem semantically related to the query. The LLM then receives the actual source text and answers the developer's question. The embedding itself does not contain code that the LLM secretly reads. It is a numerical search representation used to decide which text should be retrieved.

The Limits of Similarity

Similarity is therefore a ranking signal, not proof. A function in legacy/session.ts may be extremely similar to the current implementation while no longer being used. A test double may repeat the same symbol names but behave differently from production code. Embedding search can narrow a repository efficiently, but even the highest-ranked excerpt remains a candidate rather than established evidence.

This also explains why embeddings do not solve the context-window problem by making the context window effectively infinite. A vector index can represent a large repository for search, but only selected source text enters the model's current request. Code that remains only in the index does not directly influence generation. Retrieval expands what the application can choose from, while the context window still limits what the LLM can consider during a particular inference.

The RAG article explains how retrieval systems divide documents into searchable passages, combine different search signals, rank candidates, and evaluate whether the resulting evidence actually improves answers.

Application Design

An application has to supply evidence, constrain operations, and validate results around the model.

Separate the Responsibilities

The mechanisms in the preceding sections create a useful engineering boundary. An LLM is good at transforming supplied context into likely continuations. It is not, by itself, the entire coding application. Other components have information and powers the model does not have. A repository index can find relevant symbols, application code can enforce file permissions, a compiler can check types, and a test runner can exercise behavior.

Changing the prompt or decoding settings cannot correct a failure at every boundary. A prompt can tell the model to inspect a file, but it cannot supply source code that the application never read. A lower temperature can make output more consistent, but it cannot prove that a proposed change type-checks.

The LLM computes scores for the next token from its parameters and current context. The model-serving software tokenizes the assembled text, runs the network, applies a decoding strategy to select generated tokens, and converts those tokens back into text. The surrounding application decides what information enters the request, what external operations are available, and what must be checked before a result is trusted or acted upon.

Structured Output

When another program must parse the output, the application may care less about varied wording than about whether the response is syntactically valid. Changing temperature cannot guarantee valid JSON because it changes candidate probabilities without ruling out syntactically invalid continuations. A model asked to return JSON could otherwise generate a missing quote, an unexpected field, or ordinary prose around the object.

Schema-constrained generation addresses that structural problem by ruling out token choices that would make the output violate a required structure. For example, a diagnostic could require a file path, a line number, and a severity whose value is "error", "warning", or "info". The serving system can constrain generation to that shape and set of allowed representations.

Structural validity is not the same as factual validity. A perfectly valid diagnostic can still name the wrong file or line. Schema constraints can rule out invalid syntax, but they do not prove that a diagnostic describes the code correctly.

A Code Request Path

Consider the complete path for the getSession question. A developer asks why the function can return undefined and refers to src/session.ts. The application resolves that path against the current workspace and reads the file. It can then use symbol search or a repository index to find the Session type and a relevant caller while preserving paths and revision information for everything it selects.

The LLM receives the question together with the selected source text. It can explain that Map.get yields undefined when no value exists for the key and relate that behavior to the function's return type. The explanation is generated from code that the application supplied. The model has not independently opened session.ts or inspected the rest of the repository.

Now suppose the developer asks for a fix. The problem has changed from explaining code to changing it. The application has to limit which files can be edited, apply the proposed patch, and decide which compiler checks or tests should run. Those operations and checks belong to the surrounding application and its coding workflow. They are not consequences of generating a convincing patch.

This path places each control where the relevant information is available. Context assembly selects the repository evidence before generation, workspace permissions govern file access, and compiler checks or tests evaluate a proposed change afterward. Generated structure and behavior need separate checks because syntactically valid code can still implement the wrong behavior.

Match Controls to Causes

The final table connects the major model mechanisms to their visible consequences. The important pattern is that the application response should match the cause of the problem rather than treating the model as a single black box with one universal reliability setting.

MechanismObservable consequenceApplication response
Next-token generationFluent wording does not by itself establish factual supportSupply authoritative evidence and verify consequential claims against it
Bounded contextInformation omitted from the current request cannot directly influence that inferenceSelect, summarize, or retrieve information that should participate in the request
SamplingRepeated requests can follow different continuation pathsChoose decoding settings appropriate to the desired variation, while validating requirements independently
Schema constraintsOutput can have a guaranteed structure while containing an incorrect valueEnforce structure during generation and validate field values against application rules afterward
Retrieval by similarityA closely related excerpt can come from an obsolete or irrelevant implementationTreat retrieved code as a candidate and preserve its path and repository revision
Autoregressive generationLonger responses require more sequential decoding stepsRequest focused output when additional generated text does not improve the task

Generated results therefore require verification in proportion to what happens if they are wrong. A code explanation may need to remain faithful to the referenced source. A generated file path or line number should be checked against the workspace. A proposed software change may require compiler checks, tests, and risk-tiered code review. An irreversible or security-sensitive operation may require explicit authorization before the application allows it to run.

The central design lesson follows directly from how the model works. An LLM generates continuations from learned parameters and a bounded current context. Applications become reliable by deciding what evidence enters that context, what actions exist outside it, and which checks must succeed before generated output is trusted. Model capability matters, but application design determines how that capability is connected to real information and real consequences.
