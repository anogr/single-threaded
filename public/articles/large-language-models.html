Large Language Models

How models turn a finite request into generated text, and why their mechanism shapes reliability, latency, and cost.

Andreas Ögren
~30 min read
Last updated September 2026

Most software depends on knowing what its input will look like. Developers define fields, formats, and valid values, then write code that handles them. Language does not fit neatly into that model. A person can make the same request in countless ways. They can rely on context, omit information that seems obvious, or combine instructions with prose and code. Trying to account for all of these possibilities with explicit rules quickly becomes impractical.

Large language models take a different approach. Instead of defining how every possible request should be interpreted, they learn patterns from large amounts of data. Before a generative large language model (LLM) receives an input, a tokenizer divides the input into a sequence of units called tokens. An LLM predicts what token is likely to come next. The software running the model selects a token based on that prediction, adds it to the sequence, and runs the extended sequence through the model for the next prediction. This cycle repeats until the software stops generation and returns the response. What looks like answering a question, translating a passage, or writing code is produced through this repeated prediction process.

This mechanism is the underlying reason behind both the model's capabilities and its limitations. The model can use patterns learned during training together with information supplied in the current request, but it does not independently look up facts, remember every earlier conversation, or verify that a plausible sentence is true. The repeated prediction process therefore determines what information can influence a response and which checks the surrounding application still needs to perform.

This article follows the process from the input to the output the model generates. The focus is on inference, the work performed by an already trained model when it handles a request. Training is covered only where it explains inference. Training infrastructure and comparisons among particular models are outside the scope.

Tokens and Tokenization

A tokenizer divides text into the units that a model reads and generates.

A model does not receive raw text directly. Before the text reaches the model, a tokenizer divides it into tokens. Each token has a numeric identifier, and the complete set of tokens recognized by the model is its vocabulary. A token can contain a whole word, part of a word, punctuation, or whitespace.

The tokenizer does not divide every word into pieces of the same size. Common words and character sequences can have tokens of their own, while less familiar text is built from smaller tokens. This approach is known as subword tokenization. It solves a practical vocabulary problem. A model cannot have a separate vocabulary entry for every possible name, product identifier, misspelling, or newly invented word, but it still needs a way to represent them. Combining reusable pieces allows a finite vocabulary to represent effectively unbounded text.

Compare these examples of familiar and unfamiliar text. A common word may fit into a single token, a recognizable identifier may split into several familiar parts, but an unusual string may need to be divided into much smaller pieces.

tokenization.txt Text 
"The quick brown fox"   →  [The] [ quick] [ brown] [ fox]      4 tokens
"getUserById"           →  [get] [User] [By] [Id]              4 tokens
"x7f3a9"                →  [x] [7] [f] [3] [a] [9]             6 tokens

(Illustrative. Boundaries differ between tokenizers.)

Different tokenizers use different vocabularies, so identical text can produce different token sequences and token counts. Character count and word count can provide a rough estimate because longer text generally requires more tokens, but there is no fixed conversion between them. Familiar prose may fit into relatively few tokens, while unusual names, identifiers, or other less familiar sequences can require more.

This means two passages with the same number of words need not consume the same amount of model capacity. A paragraph of ordinary English and a paragraph filled with UUIDs, source code, or uncommon names can have very different token counts. Tokenization therefore affects how much material fits into a request and how usage is measured.

Because the request and response are both token sequences, usage is measured in tokens. Input tokens are supplied to the model, while output tokens are generated by the model. These counts can affect both the amount of text a request can contain and its cost. After tokenization, the model processes the resulting sequence using numerical values learned during training.

The Neural Network

A language model transforms tokens through a neural network whose learned numerical values determine how information influences the result.

Weights and Parameters

A neural network is a system of connected numerical calculations. The name comes from an analogy with networks of neurons in the brain. In an artificial neural network, the connected components are mathematical operations rather than biological neurons.

A neural network organizes its calculations into layers of nodes. The input enters the first layer, and each later layer transforms values produced by the layer before it. The final layer produces the network's output. A weight controls how strongly one incoming value contributes to a calculation. Because the calculations use different weights, one incoming value can have more influence than another. A weight is one kind of parameter, the general name for an adjustable number stored in the model. The complete set of parameters determines how the network transforms an input token sequence into a prediction of the next token.

The diagram isolates how weights give incoming values different amounts of influence. Real language models use billions of parameters and more structured calculations to transform the information represented by the input tokens.

Learning the Parameters

Training is the process that finds useful values for these parameters. During pretraining, the model receives token sequences and predicts what comes next. Its predictions are compared with the tokens that actually followed, and the parameters are adjusted to reduce the gap. Repeating this process across large amounts of text gradually produces parameters that capture useful statistical relationships among tokens and the contexts in which they appear.

Additional post-training can further adjust these parameters so the model is more likely to follow instructions and produce useful responses. The methods vary among models and depend on the behavior the training process is intended to encourage. Once training is complete, the resulting parameters are used to process new requests.

This creates a clear boundary between learning and use. Training changes the model's parameters based on examples. During inference, those parameters are fixed while the model calculates a response to new input. The next section looks more closely at what happens during that calculation.

From Tokens to Predictions

A Transformer processes the tokens in a sequence and scores the possible next tokens.

Building a Contextual Representation

The tokenizer supplies an identifier for each token, but an identifier only names an entry in the vocabulary. The model uses that identifier to look up a learned token vector, which is a list of numbers representing information the model has learned about that token and its relationships to other tokens. Every occurrence of a token begins with the same vector, so the starting vector does not represent what the token means in a particular context.

The phrases dog bites man and man bites dog contain the same words in a different order, even though the words play different roles. In she deposited cash at the bank, bank has a different meaning than in she sat beside the river bank. A starting token vector based only on token identity cannot express either difference. Position information preserves the order of the sequence, while information from earlier tokens lets each later position reflect what preceded it.

A Transformer is a neural-network architecture that updates token vectors using position information and information from other token positions. In the generative model described here, each position can use only itself and earlier positions when predicting the next token. This processing turns a starting token vector into a representation of that token at that point in the sequence. The starting vector for bank can therefore be updated differently in the two sentences because the preceding tokens are different.

To build these representations, the Transformer uses self-attention to compare information at the current position with information from earlier positions and determine what should contribute strongly to the update. Attention does not mean that the model retrieves a complete earlier sentence unchanged. It provides a learned way for information at one position to influence the representation at another.

For example, consider code containing const retryLimit = 5 followed later by attempts >= retryLimit. When processing the later occurrence of retryLimit, the model can give the earlier declaration strong influence. That helps its representation of the later identifier reflect information introduced at the declaration. Other attention patterns may simultaneously connect the comparison operator, the variable attempts, and surrounding code.

The result is a contextual representation, a numerical representation that reflects both the current position and information drawn from the sequence. The token vector represents a vocabulary item before this particular context has been processed, while the contextual representation reflects what that token is doing here. The model ultimately uses the representation at the final position to predict what token should come next.

From Context to Candidate Scores

The contextual representation at the final position does not identify a single next token. The model uses it to produce one score for every token in the vocabulary. A higher score means that a candidate fits the current sequence better than a candidate with a lower score. The serving software can convert the complete set of scores into a probability distribution, where every value is non-negative and all values sum to one. This distribution gives the software a basis for selecting the next token.

The complete input supplied before generation begins is the prompt. As the response grows, the current sequence contains the prompt followed by the tokens generated so far. For example, consider a fictional documentation assistant called Northstar that answers questions from a product manual. Suppose its prompt contains the manual instruction and question shown below. After the model has generated Start by creating, the serving software might derive this distribution from the model's scores.

The value 0.72 assigns 72 percent of the next-token distribution to a for this exact sequence. It compares a with the other candidates for the next position. It does not mean that the completed response has a 72 percent chance of being factually correct. The manual supplies request-specific evidence through its tokens, while the model's parameters supply relationships learned during training.

Generating a Response

Once the distribution is available, the serving software selects one token, appends it to the current sequence, and sends the expanded sequence through the model again. This repeated process is autoregressive generation. Each selected token becomes input to the next prediction, so one choice can change every token that follows.

Thus, later tokens depend on earlier generated tokens that did not exist when generation began. If Northstar generates a, the next prediction is conditioned on Start by creating a. If it instead generates new, the next prediction is conditioned on Start by creating new. The model is now continuing a different sequence.

The tokenizer converts the generated token identifiers back into text and a response is created one token at a time. Generation stops when the serving software selects a special token that marks the end of the response or reaches another stopping condition.

Choosing the Next Token

A decoding strategy selects one candidate from the model's probability distribution.

A decoding strategy determines how the serving software selects a token from the probability distribution. Greedy decoding always selects the highest-probability token, which makes the choice deterministic for a given distribution. Sampling instead makes a weighted random choice, so high-probability tokens are more likely without being guaranteed. In the Northstar example, greedy decoding selects a, while sampling could select new.

The benefit of greedy decoding is consistency. The drawback is that repeatedly taking the locally most probable next token does not guarantee the best complete response, and deterministic output can still be deterministically wrong. Sampling introduces variation, which can be useful when several continuations are reasonable, such as when drafting prose or generating alternatives.

Temperature changes how strongly sampling favors the leading candidates. A lower temperature concentrates probability around candidates the model already scores highly, while a higher temperature gives lower-scoring candidates more opportunity to be selected. If an incorrect continuation already receives a strong score, lowering the temperature can make that same mistake more repeatable rather than correcting it.

There is another kind of uncertainty that temperature does not solve. When another program must parse the output, the application may care less about varied wording than about whether the response is syntactically valid. A model asked to return JSON could otherwise generate a missing quote, an unexpected field, or ordinary prose around the object.

Schema-constrained generation addresses that structural problem by ruling out token choices that would make the output violate a required structure. For example, if a field must be one of "active", "revoked", or "expired", the serving system can constrain generation to that shape and set of allowed representations.

Structural validity is not the same as factual validity. A perfectly valid JSON response such as {"status":"revoked"} can still be wrong if the key is actually active. Schema constraints can rule out invalid syntax, but they do not prove that the value describes reality.

The Context Window

Every prediction can use only the bounded token sequence available in its current request.

Request Capacity

The model does not process an unlimited amount of text at once. For each request, it works with a bounded sequence of tokens called the context window. The limit exists because relating more token positions requires more computation and memory inside the model. Supporting a larger context window therefore makes inference more expensive, so every model is designed and served with some maximum sequence length rather than an unlimited one.

Everything the model needs to use for that request has to fit inside this token budget. That can include system instructions, the user's current message, earlier conversation turns that the application sends again, documents supplied by the application, and results obtained from external systems. The generated response also extends the sequence, so services generally have to leave capacity for output rather than filling the entire available window with input.

For example, suppose an application has a 100,000-token context budget. A long system instruction might use 2,000 tokens, conversation history 15,000, supplied documents 60,000, and the current question 500. Those pieces have already consumed most of the available space before the model begins answering. Adding another large document may require the application to remove older conversation history, include fewer passages, summarize material, or leave less room for the response.

Conversation History and Memory

The context window is therefore best understood as the model's working space for one request, not as its permanent memory. Information stored elsewhere by the application does not consume context-window space until it is included in a request, but it also cannot influence the model while it remains outside that request. A chat application creates the appearance of continuous memory by storing earlier messages and choosing which of them to send again. If an old message is not resent, summarized, or otherwise brought back into the current context, the model cannot use it for that inference.

The Northstar application may store the first question and answer before receiving a follow-up. Storage alone does not give the model access to either message. The application has to select them and place them in the next request, as the figure shows.

Long-term memory is therefore an application feature rather than another name for a large context window. The two solve related but different problems. A larger context window allows more information to be considered at once, while long-term memory lets an application keep information outside the current request and decide when to bring it back. The application might resend an old message verbatim, summarize several messages, or select a stored fact only when it becomes relevant.

Fitting and Using Information

A large context window does not mean that every included token will influence the answer equally well. Long-context evaluations have found tasks where a model uses relevant information near the beginning or end more reliably than information in the middle. This position-dependent behavior is called lost in the middle. Its shape and severity vary by model, task, and prompt length, so the curve below represents an observed pattern rather than a universal performance law.

This creates an important difference between fitting information and using information. A document can fit within the advertised context limit yet still be difficult for the model to use reliably for a particular task. Context-window size is therefore a capacity specification, not a guarantee of perfect recall.

Useful context also has to be selected even when all available material fits. Similar passages can disagree, an old instruction can conflict with a newer one, and irrelevant passages compete for attention while consuming tokens. Including source and version information lets the application preserve distinctions such as “manual version 4.2” versus “manual version 3.8.” The goal is not to fill the context window. It is to supply the smallest set of information that gives the model the evidence and instructions it needs.

Grounding and Hallucinations

Reliable factual output depends on relevant evidence supplied during inference and, where necessary, checks performed outside the model.

Evidence at Inference Time

A language model creates a particular reliability problem because it can generate a sentence in the same fluent style whether that sentence is well supported, poorly supported, or false. Fluency is produced by next-token prediction, so fluent wording is not itself evidence that the underlying claim has been checked.

Consider Northstar without the manual passage. A user asks how to rotate an API key. The model may have encountered many descriptions of API-key rotation during training and may produce a perfectly reasonable procedure. But Northstar's product could use a different sequence. The general answer might say to revoke the current key first, while Northstar requires the replacement to be created first. The problem is not that the model cannot produce useful general knowledge. It is that general knowledge and product-specific authority are different things.

Grounding addresses that problem by supplying identified evidence during inference, such as a manual passage, database record, or result read from a live system. The Northstar manual passage enters the context as tokens, which gives the model request-specific information it can use while generating the answer. Grounding changes the model's input rather than its trained parameters.

This distinguishes grounding from training. If Northstar changes its key-rotation procedure tomorrow, retraining an LLM would be a slow and indirect way to communicate one changed fact. Supplying the new manual during inference gives the current request access to the new procedure immediately. Training is useful for teaching broad patterns and behavior. Grounding is useful when a response must depend on particular evidence available at request time.

Unsupported and False Claims

A hallucination is generated content that presents false information as though it were true. The term is also sometimes used more broadly for claims that are not supported by the available evidence. Those ideas overlap but are not identical. A statement can be true but unsupported by the supplied source, while another statement can be both unsupported and false.

For example, suppose the Northstar manual contains only the following instruction.

evidence-example.txt Text 
Manual:
"Create a replacement key before revoking the old key."

If the model adds, “The old key remains valid for 24 hours,” that claim is unsupported by the passage. It might accidentally be true according to some other Northstar document, but this evidence does not establish it. If Northstar actually invalidates the key immediately, the same statement is also a hallucination under the narrower definition used here. Applications that must answer from specified sources often need to reject unsupported claims whether or not they happen to be true.

The generation mechanism explains why these failures are possible. Pretraining improves next-token prediction rather than turning the parameters into an authoritative database lookup. During inference, the model scores continuations according to its learned relationships and the current context. A plausible but unsupported continuation can therefore receive a high score. Nothing in the basic next-token mechanism performs a separate factual check before the token is emitted.

This is why reducing sampling randomness does not solve hallucinations. Suppose the unsupported phrase for 24 hours receives the highest score. Greedy decoding can select it every time. Lower temperature may make the same error more consistent. Decoding controls which continuation is selected from the model's candidates. It does not introduce missing evidence.

Sources, Tools, and Retrieval

Citations have a similar distinction. If the application already knows which manual passages it supplied, it can attach those source references to the response. If the model itself generates a citation such as “Section 8.4,” that citation is another sequence of generated tokens. It may be correct, but generation alone does not prove that Section 8.4 exists or supports the claim. A citation is valuable evidence only when the application can connect it to an actual source and, where needed, verify that the source entails the statement being made.

Different facts also require different kinds of grounding. A product manual is appropriate evidence for documented procedure. It may be poor evidence for a live fact such as whether key abc123 is currently active. That value belongs to the system that stores current key state. For consequential operations, the application should use the source that is authoritative for the particular fact rather than assuming that all grounding sources are interchangeable.

Tools and retrieval provide two common grounding paths. A tool lets the application read from or act on another system, such as looking up the current status of a key. The model can propose or request the operation, but the application decides whether the operation is permitted and executes it through controlled code. The result can then enter the context as new input.

Retrieval-augmented generation, or RAG, instead searches a document collection for passages that appear relevant and places selected passages in the context. Retrieval is useful when the evidence already exists as documents but the collection is too large to send in every request. Both tools and retrieval obtain evidence outside the model and place useful results in the current context so generation can use them.

Grounding therefore improves the information available to generation, but it does not remove every failure mode. Retrieval can select the wrong document. A live tool can return stale or misunderstood data. The model can misread a correct passage. An application that requires stronger assurance must test the whole evidence path rather than treating the presence of “RAG” or “tools” as a guarantee of correctness.

Retrieval Embeddings

An embedding represents text as a vector so a retrieval system can compare semantic similarity without sending the whole collection to the LLM.

Searching by Meaning

Grounding creates a selection problem. Suppose the Northstar manual contains 20,000 passages but only three concern API-key rotation. Sending the entire manual with every question would consume context capacity and input computation even though most of the text is irrelevant. The application therefore needs a way to find promising passages before it calls the LLM.

Exact keyword search solves part of this problem. If the question contains rotate API key and the manual contains exactly those words, a text search may work well. But people and documents often describe the same idea differently. A user may ask, “How do I replace a credential without breaking access?” while the manual says, “Create a replacement key before revoking the old key.” Few words match even though the meanings are closely related.

Retrieval Vectors

An embedding model provides another kind of search signal. It converts a query or passage into a fixed-length vector designed so that texts with related meanings tend to have similar vectors. A retrieval system can therefore compare the vector for the user's question with vectors previously created for manual passages. The Northstar question about replacing credentials can rank near the key-rotation passage even without exact wording.

This use of vectors resembles the token vectors introduced earlier, but the purpose is different. A token vector inside the LLM is part of the model's internal computation for one vocabulary token. A contextual representation changes as the Transformer processes that token in a particular sequence. A retrieval embedding, by contrast, usually represents a complete query or passage so an external search system can compare it with other queries or passages.

The retrieval system normally computes passage embeddings ahead of time and stores them in an index. When a question arrives, it creates an embedding for the query and measures how similar that vector is to the stored vectors. Passages with stronger similarity scores rank higher. Only the selected passages need to be inserted into the LLM's context.

This creates a useful division of labor. The embedding model indicates which passages seem semantically related to the query. The LLM then receives the actual text of those passages and answers the user's question. The embedding itself does not contain a passage that the LLM secretly reads. It is primarily a numerical search representation used to decide which text should be retrieved.

The Limits of Similarity

Similarity is therefore a ranking signal, not proof. Two passages can discuss the same topic while giving different instructions. A document titled “Legacy API-key rotation” may be extremely similar to the query while being obsolete. A nearby passage may describe revoking user sessions rather than API keys. Embedding search can narrow a large collection efficiently, but even the highest-ranked passage remains a candidate rather than established evidence.

This also explains why embeddings do not solve the context-window problem by making the context window effectively infinite. A vector index can represent millions of passages for search, but only selected passage text enters the model's current request. Information that remains only in the index does not directly influence generation. Retrieval expands what the application can choose from, while the context window still limits what the LLM can consider during a particular inference.

The RAG article explains how retrieval systems divide documents into searchable passages, combine different search signals, rank candidates, and evaluate whether the resulting evidence actually improves answers.

Inference Cost and Latency

Input processing and sequential output generation create different kinds of work.

Processing the Input

A user experiences a generated response as one operation, but inference contains two computationally different phases. Understanding that distinction explains why adding a large document often affects the delay before the answer starts, while requesting a long answer affects how long generation continues afterward.

Before the first output token can be selected, the model has to process the input tokens and build the internal information needed to begin generation. This initial phase is often called prefill. Calculations across the supplied input can make substantial use of parallel hardware, but longer input still requires more computation and memory. Instructions, conversation history, and retrieved passages all contribute to this work because all of them are input tokens.

For Northstar, compare two requests that ask exactly the same question. One includes a 200-token passage containing the relevant rotation procedure. The other includes the entire 40,000-token manual. Even if both eventually produce the same short answer, the second request gives the model far more input to process before it can begin generating. This is why indiscriminately filling a large context window can increase latency even when the extra text provides no useful evidence.

The delay before the first generated token is often discussed separately from total response time because it affects how responsive an application feels. A system that begins streaming an answer after half a second feels different from one that remains silent for several seconds, even if both finish at nearly the same time. Reducing unnecessary input can therefore improve the time before generation begins.

Generating the Output

After prefill, the model enters the autoregressive generation loop described earlier. The first output token is selected, then that token becomes part of the sequence used to calculate the second, and so on. This phase is often called decoding. Here, decoding names the complete output phase. During each step of that phase, the decoding strategy determines how the serving software selects the next token.

Decoding has a dependency that prefill does not. Token 80 cannot be selected until token 79 is known. The model may perform enormous amounts of parallel numerical work inside each individual prediction step, but the output positions themselves form a sequence. Asking for another 500 generated tokens therefore adds roughly another 500 sequential selection steps.

This creates two different optimization levers. If Northstar takes too long to start responding, the application should examine how much input it sends and how efficiently that input is processed. If it starts quickly but takes too long to finish, response length and decoding speed become more important. Treating all latency as one problem can hide which part of the request is actually expensive.

Token Usage and Cost

Token usage can also affect monetary cost. When a provider meters input and output tokens separately, repeating a large manual passage increases input usage, while requesting a longer explanation increases output usage. The prices need not be the same for the two categories, so reducing 1,000 input tokens and reducing 1,000 output tokens do not necessarily save the same amount.

This does not imply that shorter prompts are always better. Removing the passage that establishes the correct Northstar procedure may reduce cost while making the answer less reliable. The practical goal is to keep the instructions and evidence the task needs while omitting material that does not help. The requested output should be no longer than the user or downstream system needs.

Application Design

An application has to supply evidence, constrain operations, and validate results around the model.

Separate the Responsibilities

The mechanisms in the preceding sections create a useful engineering boundary. An LLM is good at transforming supplied context into likely continuations. It is not, by itself, the entire application. Other components have information and powers the model does not have. A retrieval system can search a document collection, application code can enforce permissions, a database can provide authoritative state, and a validator can reject values that violate business rules.

Changing the prompt or decoding settings cannot correct a failure at every boundary. A prompt can tell the model to use a particular source, but it cannot retrieve a document that the application never supplied. A lower temperature can make output more consistent, but it cannot prove that an account number exists. A JSON schema can enforce a field's shape, but it cannot authorize the operation represented by that field.

The model computes scores used to predict the next token from its parameters and current context. The serving system runs inference and applies a decoding strategy to turn those scores into generated tokens. The surrounding application decides what information enters the request, what external operations are available, and what must be checked before a result is trusted or acted upon.

The Northstar Request Path

Consider the complete Northstar path. A user asks, “How do I rotate an API key?” The application first needs evidence. Its retrieval system searches the product documentation and selects the passage stating that a replacement key must be created before the old key is revoked. The application preserves information such as the document version so an obsolete procedure is not silently treated as current.

The LLM then receives the question and selected passage and explains the procedure in natural language. At this point, generation is useful because the source may be terse while the user wants an explanation. The model can turn “Create a replacement key before revoking the old key” into a clearer sequence and explain why that order avoids losing access.

Now suppose the user asks, “Can you revoke the old key for me?” The problem has changed. Explaining an operation requires information, while performing an operation requires authority. The application might expose a revocation tool, but it should determine which key may be revoked, whether the user has permission, and whether a replacement exists before executing anything. Those checks belong in controlled application logic rather than in generated prose.

The Northstar path places each control where the relevant information is available. Document selection can reject obsolete sources before they enter the prompt, while the revocation boundary can check authority and current key state before an operation executes. Generated structure and values need separate checks because a schema cannot evaluate the business rules behind a field.

Match Controls to Causes

The final table connects the major model mechanisms to their visible consequences. The important pattern is that the application response should match the cause of the problem rather than treating the model as a single black box with one universal reliability setting.

Generated results therefore require verification in proportion to what happens if they are wrong. A documentation answer may need only to remain faithful to source material supplied by the application. A generated identifier used in an API call should be checked against permitted values. A proposed software change may require tests and risk-tiered code review. An irreversible or security-sensitive operation may require explicit authorization before any tool is allowed to execute it.

The central design lesson follows directly from how the model works. An LLM generates continuations from learned parameters and a bounded current context. Applications become reliable by deciding what evidence enters that context, what actions exist outside it, and which checks must succeed before generated output is trusted. Model capability matters, but application design determines how that capability is connected to real information and real consequences.
