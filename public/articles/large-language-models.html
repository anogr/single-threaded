Large Language Models

How models turn a finite request into generated text, and why their mechanism shapes reliability, latency, and cost.

Andreas Ögren
~19 min read
Last updated August 2026

Most software depends on knowing what its input will look like. Developers define fields, formats, and valid values, then write code that handles them. Language does not fit neatly into that model. A person can make the same request in countless ways. They can rely on context, omit information that seems obvious, or combine instructions with prose and code. Trying to account for all of these possibilities with explicit rules quickly becomes impractical.

Large language models take a different approach. Instead of defining how every possible request should be interpreted, they learn patterns from large amounts of data. Before a generative large language model (LLM) receives an input, a tokenizer divides the input into a sequence of units called tokens. An LLM predicts what token is likely to come next. The software running the model selects a token based on that prediction, adds it to the input and sends the extended sequence through the model for the next prediction. This cycle repeats until the software stops generation and returns the response. What looks like answering a question, translating a passage, or writing code is produced through this repeated prediction process.

The repeated prediction process determines what information can influence a response and which checks the surrounding application still needs to perform. This article follows that process from the input to the output the model generates. The focus is on inference, the work performed by an already trained model when it handles a request. Training is covered only where it explains inference. Training infrastructure and comparisons among particular models are outside the scope.

Tokens and Tokenization

A tokenizer divides text into the units that a model reads and generates.

A model does not receive raw text directly. Before the text reaches the model, a tokenizer divides it into tokens. Each token has a numeric identifier, and the complete set of tokens recognized by the model is its vocabulary. A token can contain a whole word, part of a word, punctuation, or whitespace.

The tokenizer does not divide every word into pieces of the same size. Common words and character sequences can have tokens of their own, while less familiar text is built from smaller tokens. This approach is known as subword tokenization. It allows a fixed vocabulary to represent words, names, and identifiers that do not have tokens of their own.

Compare these examples of familiar and unfamiliar text. A common word may fit into a single token, a recognizable identifier may split into several familiar parts, but an unusual string may need to be divided into much smaller pieces.

tokenization.txt Text 
"The quick brown fox"   →  [The] [ quick] [ brown] [ fox]      4 tokens
"getUserById"           →  [get] [User] [By] [Id]              4 tokens
"x7f3a9"                →  [x] [7] [f] [3] [a] [9]             6 tokens

(Illustrative. Boundaries differ between tokenizers.)

Different tokenizers use different vocabularies, so identical text can produce different token sequences and token counts. Character count and word count can provide a rough estimate because longer text generally requires more tokens, but there is no fixed conversion between them. Familiar prose may fit into relatively few tokens, while unusual names, identifiers, or other less familiar sequences can require more.

Because the request and response are both token sequences, usage is measured in tokens. Input tokens are supplied to the model, while output tokens are generated by the model. These counts can affect both the amount of text a request can contain and its cost. After tokenization, the model processes the resulting sequence using numerical values learned during training.

The Neural Network

A language model transforms tokens through a neural network whose learned numerical values determine how information influences the result.

Weights and Parameters

A neural network is a system of connected numerical calculations. The name comes from an analogy with networks of neurons in the brain. In an artificial neural network, the connected components are mathematical operations rather than biological neurons.

A neural network organizes its calculations into layers of nodes. The input enters the first layer, and each later layer transforms values produced by the layer before it. The final layer produces the network's output. A weight controls how strongly one incoming value contributes to a calculation. Because the calculations use different weights, one incoming value can have more influence than another. A weight is one kind of parameter, the general name for an adjustable number stored in the model. The complete set of parameters determines how the network transforms an input token sequence into a prediction of the next token.

The diagram isolates how weights give incoming values different amounts of influence. Real language models use many more parameters and more structured calculations to transform the information represented by the input tokens.

Learning the Parameters

Training is the process that finds useful values for these parameters. During pretraining, the model receives token sequences and predicts what comes next. Its predictions are compared with the tokens that actually followed, and the parameters are adjusted to reduce the gap. Repeating this process across large amounts of text gradually produces parameters that capture useful statistical relationships among tokens and the contexts in which they appear.

Additional post-training can further adjust these parameters so the model is more likely to follow instructions and produce useful responses. The methods vary among models and depend on the behavior the training process is intended to encourage. Once training is complete, the resulting parameters are used to process new requests.

This creates a clear boundary between learning and use. Training changes the model's parameters based on examples. During inference, those parameters are fixed while the model calculates a response to new input. The next section looks more closely at what happens during that calculation.

From Tokens to Predictions

A Transformer processes the tokens in a sequence and scores the possible next tokens.

Building a Contextual Representation

The tokenizer supplies an identifier for each token, but an identifier only names an entry in the vocabulary. The model uses that identifier to look up a learned token vector, which is a list of numbers representing information the model has learned about that token and its relationships to other tokens. Every occurrence of a token begins with the same vector, so the starting vector does not represent what the token means in a particular context.

The phrases dog bites man and man bites dog contain the same words in a different order, even though the words play different roles. In she deposited cash at the bank, bank has a different meaning than in she sat beside the river bank. Position information distinguishes the order of tokens, while information from earlier tokens helps determine the role and meaning of each token in the sequence.

A Transformer is a neural-network architecture that updates token vectors using position information and information from other token positions. In the generative model described here, each position can use only itself and earlier positions. This processing turns a starting token vector into a representation of that token in the current sequence. The starting vector for bank can therefore be updated differently in the two sentences because the preceding tokens are different.

To build these representations, the Transformer uses self-attention to compare information at the current position with information from earlier positions and decide what to combine. For example, consider code containing const retryLimit = 5 followed later by attempts >= retryLimit. When processing the later occurrence of retryLimit, the comparison can identify the earlier declaration as relevant and allow information from that position to contribute to the updated representation. This connects the use of the identifier with information supplied at its declaration.

The result is a contextual representation, a numerical representation that reflects both the current position and information drawn from earlier in the sequence. The model uses the representation at the final position to predict what token should come next. The figure summarizes how a token identifier becomes this contextual representation.

From Context to Candidate Scores

The contextual representation at the final position does not identify a single next token. The model uses it to produce one score for every token in the vocabulary. A higher score means that a candidate fits the current sequence better than a candidate with a lower score. The serving software can convert the complete set of scores into a probability distribution, where every value is non-negative and all values sum to one. This distribution gives the software a basis for selecting the next token.

The complete input supplied before generation begins is the prompt. As the response grows, the current sequence contains the prompt followed by the tokens generated so far. For example, consider a fictional documentation assistant called Northstar that answers questions from a product manual. Suppose its prompt contains the manual instruction and question shown below. After the model has generated Start by creating, the serving software might derive this distribution from the model's scores.

The value 0.72 gives a a 72 percent share of the distribution for this exact sequence. It does not mean that the response has a 72 percent chance of being factually correct. The manual supplies request-specific evidence through its tokens, while the model's parameters supply relationships learned during training.

Generating a Response

Once the distribution is available, the serving software selects one token, appends it to the current sequence, and sends the expanded sequence through the model again. This repeated process is autoregressive generation. Each selected token becomes input to the next prediction, so one choice can change every token that follows.

Generation stops when the serving software selects a special token that marks the end of the response or reaches another stopping condition. The tokenizer converts the generated token identifiers back into text. Selecting a rather than new changes every later prediction in the Northstar response, so the next section examines how the serving software makes that choice.

Choosing the Next Token

A decoding strategy selects one candidate from the model's probability distribution.

A decoding strategy determines how the serving software selects a token from the probability distribution. Greedy decoding always selects the highest-probability token, which makes the choice deterministic for a given distribution. Sampling instead makes a weighted random choice, so high-probability tokens are more likely without being guaranteed. In the Northstar example, greedy decoding selects a, while sampling could select new. Sampling allows different candidates to be selected, but an early choice changes the sequence used for every later prediction and can produce a different response.

Temperature reshapes the distribution before sampling. A lower temperature concentrates probability on the leading candidates, while a higher temperature gives weaker candidates more chance of selection. The setting changes variation rather than evidence. If an incorrect token already has the highest probability, concentrating the distribution can make that error more repeatable.

When another program has to parse the output, variation in its structure creates a different problem. Schema-constrained generation lets the serving system rule out choices that would make the output violate a required JSON structure. This can enforce the structure, but a valid field can still contain the wrong identifier or an unsupported claim. Structural validity and factual support therefore require separate checks.

The Context Window

Every prediction can use only the bounded token sequence available in its current request.

The context window is the maximum number of tokens that can take part in one model request. Instructions, messages, supplied documents, and tool results use this capacity. The generated response uses it as well. The model and service determine how the limit is shared, so allowing room for a longer response can reduce the space available for input.

The context window belongs to a request rather than to an entire conversation. A chat application creates continuity by selecting earlier messages and sending them again with each new request. History stored by the application cannot affect a prediction until the application returns it to the model as input.

The Northstar application may store the first question and answer before receiving a follow-up. Storage alone does not give the model access to either message. The application has to select them and place them in the next request, as the figure shows.

Long-term memory is therefore an application feature rather than a larger context window. The application may summarize old messages or retrieve selected records when they become relevant. Either method decides what returns in a later request. Information omitted from that request is unavailable to the model for its prediction.

Capacity does not guarantee effective use. In Lost in the Middle, researchers tested several language models on tasks that required information placed at different positions in a long input. The models often performed better when the relevant information appeared near the beginning or end than when it appeared in the middle. This position-dependent behavior is called lost in the middle. Its shape and severity vary by model, task, and prompt length, so the curve below represents an observed pattern rather than a universal performance law.

Useful context still has to be selected even when all available material fits. Similar passages can disagree, and an old instruction can conflict with a newer one. Including source and version information lets the application preserve that distinction in the prompt. Unrelated documents consume capacity without contributing relevant evidence.

Grounding and Hallucinations

Reliable factual output depends on relevant evidence supplied during inference and, where necessary, checks performed outside the model.

A trained model's parameters can encode information learned during training, but they should not be treated as an authoritative source for current or private facts. Grounding supplies identified evidence during inference, such as a document or a result read from a live system. The Northstar manual passage enters the context as tokens, which makes its contents available to the next-token calculation. Grounding changes the model's input rather than its trained parameters.

A hallucination is generated content that presents false information as though it were true. The term is also sometimes used more broadly for claims that are not supported by the available evidence. A claim can be unsupported by the supplied evidence even when it happens to be correct. For an assistant that is expected to answer from the Northstar manual, both outcomes are failures, but under the narrower definition used here, only the false claim is a hallucination.

The generation mechanism explains how a hallucination can occur. Pretraining improves next-token prediction rather than turning the parameters into an authoritative source lookup. During inference, the model scores possible tokens according to learned relationships and the current context, and the serving system chooses the next token according to its decoding strategy. Without the Northstar passage, this process could produce a plausible menu path that the manual never states. If the response presents that path as a fact about Northstar, fluent wording provides no guarantee that the claim is true.

Sampling can change which false or unsupported continuation appears, but removing randomness cannot establish truth. The application can show which passages were supplied by attaching references to the documents it selected. A citation written by the model is itself generated output and therefore must be verified. The application still has to determine whether the cited passage actually supports the answer. A consequential answer may also require validation against the system that authoritatively stores the relevant fact.

Tools and retrieval provide two grounding paths. A tool can read a live record or perform an action. The model can request the operation, but the application decides whether it is allowed. If the application performs the operation, its result can enter the context as new input. Retrieval-augmented generation instead selects passages from a document collection and places them in the context. In both cases, the model generates in light of the supplied result. The surrounding system remains responsible for obtaining adequate evidence, verifying claims where necessary, and controlling any action.

Retrieval Embeddings

An embedding represents text as a vector so a retrieval system can compare semantic similarity without sending the whole collection to the LLM.

A document collection may be too large to place in every prompt. An embedding model converts a query or passage into a fixed-length vector designed for comparison. It is trained so texts with related meanings tend to be near one another in the resulting vector space. The Northstar rotation question can therefore be close to a passage about replacing credentials even when they share few exact words. A retrieval vector represents a whole query or passage. It serves a different purpose from the token vectors and contextual representations inside the LLM, which help produce next-token scores.

The retrieval system stores a vector for each searchable passage. When a query arrives, it converts the query into another vector and compares it with the stored vectors. Passages with more similar vectors rank higher, which gives the system a way to select text that may answer the query before the LLM processes it.

Similarity is a ranking signal rather than proof that a passage answers the query. Related passages can disagree, and the highest-scoring passage can still miss an exact identifier or other crucial detail. Retrieval returns selected passages as ordinary text, which the application can insert into the model's context. An embedding is therefore neither a larger context window nor a hidden store that the LLM can consult by itself. The RAG article explains how a retrieval pipeline finds and evaluates this evidence.

Inference Cost and Latency

Input processing and sequential output generation create different kinds of work.

Before the first output token can be selected, the serving system has to process the input tokens. This initial phase is often called prefill. Calculations for different input positions can be parallelized, but a longer input still requires more computation and memory. Retrieved passages add input tokens like any other part of the prompt. More input therefore tends to increase the time before the first output token appears.

Output generation follows the autoregressive loop explained earlier. Each selected token becomes part of the sequence used to predict the next token, so output positions cannot all be calculated at once. A longer response adds another sequential prediction step for every additional token. This dependency tends to increase the time required to produce a longer response.

When a provider charges by token usage, cost depends on the number of input and output tokens it meters and the rate applied to each. Repeating the Northstar manual passage increases input usage, while requesting a longer response increases output usage. The application can influence these quantities through context selection and output limits.

Application Design

An application has to supply evidence, constrain operations, and validate results around the model.

The model computes scores used to predict the next token from its parameters and current context. The serving system runs inference and applies a decoding strategy to select tokens from those scores. The surrounding application supplies evidence, controls permitted operations, and decides whether generated results may be used. The table separates these responsibilities.

ComponentResponsibilityBoundary
ModelProduces next-token scores from parameters and contextDoes not independently retrieve sources, execute external operations, or establish that its output is correct
Serving systemRuns inference, selects tokens according to a decoding strategy, and may apply decoding constraintsToken selection does not establish which evidence is authoritative or whether generated claims are true
ApplicationSelects context, controls tools and permissions, validates results, and decides whether they may be usedCannot recover evidence that was never retrieved or otherwise supplied merely by changing token selection

For the Northstar assistant, the retrieval system selects the API-key passage and preserves its source and version. The application places the passage beside the question and defines what should happen when no adequate evidence supports an answer. The LLM can explain the supplied material, but its generation does not establish that the material is authoritative.

Each failure in this example has to be addressed at the boundary that can detect or control it. The application tests whether retrieval returns adequate evidence for the question and verifies generated claims where the required level of assurance warrants it. Schema constraints can enforce response structure, while application code checks whether structured values are permitted and valid for the intended operation. Increasing context size or lowering temperature does not repair evidence that was never supplied.

Token budgets follow from this request path. Selecting only relevant evidence reduces input work and preserves context capacity for other required information and generated output. A focused output requirement can reduce the number of sequential generation steps. These choices can reduce latency and cost without changing which evidence supports the answer.

Generated results require verification in proportion to their consequence. A documentation answer can be checked against source material supplied by the application, while a proposed software change may require risk-tiered code review. The application should decide whether a result may be used only after the checks required for that use have passed.
