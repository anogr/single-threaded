Software Design Principles

Why the same handful of rules for structuring code and dependencies keep reappearing across languages.

Deep dive
~31 min read
Software design
July 2026

A design principle is a rule of thumb for shaping code and the dependencies between its parts. It emerges from repeated observations of the same kind of mistake across many projects. A principle isn't enforced by the compiler, nor is it universally correct. Instead, it's a trade-off that pays off in a particular context, and understanding when to apply it is just as important as understanding the principle itself. This article explores the most enduring design principles, not as a checklist to apply everywhere, but as tools for solving recurring problems in real codebases.

A codebase that ignores these principles doesn't fail loudly. A one-line fix in a payment method breaks checkout, because two features were quietly sharing state neither owner knew about. A new hire spends a full day tracing what a single function does before daring to touch it, because it does five unrelated things under one name. A test can't run without spinning up a database, a mail server, and half the application, because nothing in the code was built to run in isolation. Each of these traces back to the same handful of recurring issues:

  • Understanding gets harder, because behavior that looks self-contained turns out to depend on something two files away that nobody documented.
  • Changing gets riskier, because a fix in one place can break a feature that was silently relying on it.
  • Testing gets harder, because nothing can be verified without dragging in the rest of the system.
  • Extending gets more fragile, because new behavior has to be wedged into a structure that wasn't built to expect it.

Every principle in this article addresses one or more of these costs, though pushed past the problem it was meant to solve, most start adding costs of their own back into the system. Many other concerns, such as correctness and security, also benefit indirectly when a system is easier to understand, change, test, and extend.

This article groups the structural principles into four branches, based on the kind of decision each one governs.

  • Build less principles decide whether a piece of code should exist at all, before anything gets organized.
  • Organize code well principles decide where a responsibility lives once it does exist, and what it's allowed to know about its neighbors.
  • Depend safely principles decide how one piece of code is allowed to rely on another without the two becoming impossible to change independently.
  • Communicate cleanly principles decide what an object should expose about itself, and who gets to make decisions based on it.

Fail fast sits outside all four, since it's a runtime discipline about how quickly a problem surfaces, not a structural rule about how code is arranged.

History

These ideas didn't arrive from one place. Some genuinely emerged in isolation. A Navy contractor described one in the 1960s. A researcher building an experimental object-oriented language described another in 1972. A pair of graduate students at Northeastern rediscovered a version of a third in the 1980s while working on something else entirely. Other ideas share more of a common thread. Liskov, Meyer, and Lieberherr were all working inside the same academic object-oriented research community in the late 1980s, and their principles arrived within a year of each other. What both groups have in common is the absence of any coordinated effort. Nobody sat down to build a unified theory of software design. Each was staring at a different kind of mess and reaching for whatever fixed it.

That's why these principles keep resurfacing under different names in different decades.

Build less

The cheapest code to maintain is the code that was never written, so this branch comes first. It decides what shouldn't exist before the next branch worries about how to organize what does.

YAGNI

A configuration flag gets added for a use case that seems inevitable. A parameter accepts three strategies even though the product only has one today. Six months later the flag has one value in every environment that has ever run the service, and nobody remembers why the branch exists. That's the failure YAGNI (You Aren't Gonna Need It) names. Capability built for a need that may never arrive gets paid for immediately, in code that has to be read, tested, and kept working, against a benefit that may never materialize. The principle comes out of Extreme Programming in the late 1990s, and its instruction is blunt. Don't build it until something in front of you actually requires it.

The most common misreading of YAGNI is "never plan ahead." That's not what it says. YAGNI is about refusing to build speculative capability, not about refusing an obvious, cheap structural choice that's already in front of you. Naming a variable clearly, or putting a data-access call behind a small function instead of scattering it across a component, costs nothing extra today and isn't what YAGNI is warning against. The principle targets the flag nobody asked for, the abstraction layer built for a second implementation that never gets written, and the plugin system for one plugin.

KISS

KISS (Keep It Simple, Stupid) traces to a mid-century engineering culture, U.S. Navy and aerospace teams reacting to systems whose complexity had outgrown the people maintaining them. In software it means the same thing it meant to them. Complexity is a cost, not a sign of sophistication, and it should only exist where the problem actually requires it. KISS in practice looks like a conditional inverted to remove nesting, an early return that collapses three branches into one, or a function that does one thing instead of five under one name. The test is whether a reader can hold the logic in their head, not whether the code looks impressive.

Overused, KISS becomes an excuse to hide complexity instead of removing it. Collapsing three genuinely distinct cases into one branch that "mostly" handles all of them isn't simplification. It's a bug waiting for the input that exposes the case that got merged away. Real simplicity reduces the number of things a reader has to track without reducing the number of things the code correctly handles.

Rule of Three

Extracting an abstraction from one example is a guess. The Rule of Three, associated with Don Roberts and Ralph Johnson's research and popularized through Martin Fowler's Refactoring (1999), gives that guess a deadline. Wait for a third occurrence of a pattern before generalizing it. The first occurrence is just code. The second might be coincidence, two things that happen to look similar today for unrelated reasons. Only the third gives enough evidence that the shape is real rather than a resemblance that will diverge the moment either call site changes for its own reason.

The rule cuts both ways. Extracting after the second occurrence risks generalizing from a coincidence, building an abstraction shaped by two examples that happen to look alike today for unrelated reasons. Waiting past the third occurrence has its own cost. Every call site that should have shared logic keeps drifting further from the others until unifying them means reconciling three or four subtly different implementations instead of two. There's no fixed count that's correct for every case. Three is a reasonable default because it's the point where a real pattern is more likely than a coincidence, not a guarantee.

DRY

DRY (Don't Repeat Yourself) is about a single source of truth for a piece of knowledge, not a rule against two code blocks looking similar. Andrew Hunt and David Thomas stated it precisely in The Pragmatic Programmer (1999). Every piece of knowledge must have a single, unambiguous, authoritative representation. The failure it targets is a business rule that changes in one place a developer remembers to update, while an identical rule sitting somewhere else quietly goes stale.

validate-email.ts TS 
// The same shape existed inline in createUser, updateUser, and
// importUsers before the third call site made it worth naming.
function assertValidEmail(email: string): void {
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
    throw new Error(`Invalid email: ${email}`);
  }
}

Two things had to be true for the extraction above to be sound. The check had to appear a third time, per the Rule of Three, and it had to represent the same piece of knowledge each time, not three rules that merely resembled each other today. That second condition is where DRY is most often misapplied. Merging two things that only look alike into one shared abstraction feels productive in the moment. It stops feeling productive once they diverge for unrelated reasons and the shared function grows an if (isSpecialCase) branch to keep serving both, until the abstraction is harder to read than the duplication it replaced. A wrong abstraction costs more than the duplication it was meant to remove.

Organize code well

Once a piece of behavior earns its place in the codebase, the next question is where it lives and what it's allowed to know about its neighbors. Get that right, and the same code becomes easier to find, easier to reason about, and easier to test on its own.

Encapsulation and information hiding

David Parnas's 1972 paper "On the Criteria to Be Used in Decomposing Systems into Modules" made an argument that still holds. A module should hide an implementation decision behind a stable interface, so that changing the decision later doesn't require changing everything that depends on the module. Parnas called this information hiding. Encapsulation is the practice that follows from it in most languages today. Expose a method that performs an operation, not the internal data structure that operation happens to use today. A queue class exposing enqueue() and dequeue() can switch its internal storage from an array to a linked list without a single caller noticing. A queue class that exposes its backing array directly can't.

This is the oldest of the organizational principles here, predating separation of concerns by two years. The two principles that follow in this section overlap heavily with encapsulation applied at a specific scale, though neither reduces to it completely. Single responsibility is partly encapsulation at the level of a module, and partly a claim about cohesion, keeping together the code that changes for one reason. Interface segregation is partly encapsulation at the level of an interface, and partly about limiting how much of an interface's volatility a caller is exposed to. Overdone, encapsulation turns defensive. Every field gets a getter and a setter that exposes it right back out, hiding nothing, or a legitimate configuration need routes through three layers of indirection because nothing was left adjustable. Hiding a decision is only valuable when the decision might actually change. That's also why a plain, immutable value object, a coordinate pair or a date range, is usually better off exposing its fields directly. There's no implementation decision underneath a value object like that to protect, so a method wrapped around the field would just be encapsulation with nothing to hide.

Separation of concerns

Edsger Dijkstra used the phrase "separation of concerns" in a 1974 essay on the discipline of programming, describing it as a way of thinking rather than a way of organizing folders. A concern is a distinct area of responsibility, such as what the user sees, what the business rule says should happen, or how the data gets stored. When one piece of code handles more than one concern, a change to one risks breaking the other, because they were never truly separate, only sitting in the same function.

Separation of concerns is often read as a statement about file structure, such as a UI folder and a services folder. That's a side effect, not the point. Two functions can live in the same file and still be properly separated if one only computes a value and the other only renders it. Two functions can live in different folders and still violate the principle if the rendering function reaches back to recompute business logic on its own.

Overapplied, separation of concerns produces layers that don't correspond to anything real. A single, genuinely cohesive piece of logic gets split into a controller, a service, and a repository, each doing almost nothing on its own. A change to that one concern now means editing three files that were only ever separated on paper. Splitting pays off when the pieces can plausibly change for different reasons and at different rates. It doesn't pay off just because a template exists for a three-layer folder structure.

Single Responsibility Principle

Robert C. Martin's phrasing for the Single Responsibility Principle (SRP) is "a module should have one, and only one, reason to change." The word doing the real work in that sentence is "reason," not "method." A module that validates a form, persists it to a database, and sends a confirmation email is doing three jobs. Each job changes for a different business reason, such as a new validation rule, a new storage backend, or a new email provider. Any one of those changes forces an edit to code that has nothing to do with the actual reason for the change, and risks breaking the two unrelated responsibilities sitting next to it.

SRP is the principle most often taken too literally. Reading "one reason to change" as "one method per class" produces the opposite of the intended result. The class count balloons into dozens of one-line classes, each trivially simple on its own. The actual logic ends up scattered so thin across them that understanding one piece of business behavior means opening ten files instead of one. A responsibility is a reason a stakeholder would ask for a change, not a count of lines.

Interface Segregation Principle

The Interface Segregation Principle (ISP) applies the same idea to interfaces instead of modules. A caller shouldn't be forced to depend on methods it never uses. A single Machine interface requiring print(), scan(), and fax() forces a print-only device to implement two methods it can't support. It also couples every caller of print() to changes made to the scanning method it never touches. Splitting that one interface into Printer, Scanner, and Fax lets a caller depend on exactly the capability it needs and nothing else. That's what makes the principle a form of encapsulation applied at the interface boundary rather than the module boundary.

Taken too far, ISP produces an interface for every single method, such as a Printable, a Scannable, or a Faxable, each with exactly one member. A class that genuinely needs all three now implements three interfaces to do the job one interface could have described. A reader has to open three files to see the full shape of what the class does. The split is worth making when callers actually differ in which capability they need. It isn't worth making just to keep interfaces small for their own sake.

High cohesion, low coupling

Cohesion and coupling are the clearest lens for what the four principles above have in common, though not a complete account of what each one does on its own. Cohesion describes how closely the responsibilities within a module belong together. High cohesion means the module's responsibilities naturally fit together. Encapsulation and the Single Responsibility Principle (SRP), when applied well, tend to promote high cohesion, and both also make a module easier to test in isolation. Coupling describes the dependencies between modules. Low coupling means modules depend as little as possible on one another. Separation of concerns and the Interface Segregation Principle (ISP) applied well help reduce coupling between modules. ISP's narrower interfaces carry the added benefit of making it easier to discover which capability a caller actually needs.

Depend safely

Organizing code well decides where a responsibility lives, and lowers coupling by shaping what's inside each module. This branch reduces the same coupling from a different angle. It decides how one piece of code is allowed to depend on another, without the two becoming impossible to change independently.

Open/Closed Principle

Bertrand Meyer stated the Open/Closed Principle (OCP) in Object-Oriented Software Construction (1988). A module should be open for extension but closed for modification. In practice this shows up as a growing chain of conditionals. A charge() function with a branch per payment method works fine until the fifth payment method needs to be added. At that point every new case is a new edit to a function that every existing case already depends on. A mistake in the new branch can break a payment method that had nothing to do with the change.

charge.ts TS 
// Before: a new payment method means editing this function again,
// next to every method that already works.
function charge(method: string, amount: number) {
  if (method === 'card') return chargeCard(amount);
  if (method === 'wallet') return chargeWallet(amount);
  if (method === 'invoice') return chargeInvoice(amount);
  throw new Error(`Unsupported method: ${method}`);
}

// After: adding a new provider is a new entry, not a new branch,
// and existing entries are untouched.
const chargeHandlers: Record<string, (amount: number) => Charge> = {
  card: chargeCard,
  wallet: chargeWallet,
  invoice: chargeInvoice,
};

function charge(method: string, amount: number) {
  const handler = chargeHandlers[method];
  if (!handler) throw new Error(`Unsupported method: ${method}`);
  return handler(amount);
}

The map itself still gets a new line for every payment method. That's not the textbook form of OCP, where a new class is added in a new file and nothing existing is touched at all. What it does close off is the risk that used to matter most. A new case can no longer break an existing one, because adding chargeWallet's entry can't alter what chargeCard's entry does. A plugin registry or a common interface implemented by a new class gets closer to the classic form, but reaching for that heavier structure before it's earned is its own mistake.

Building a registration table, a plugin loader, or a strategy interface for a case that has exactly one implementation and no realistic second one adds a layer of indirection. That costs a reader time to trace, in exchange for flexibility nothing will ever use. The branch chain earlier in this section was worth replacing because payment methods actually multiply. A function with one permanently fixed behavior doesn't need the same treatment.

Liskov Substitution Principle

Barbara Liskov introduced what became known as the Liskov Substitution Principle (LSP) in a 1987 OOPSLA keynote, later formalized with Jeannette Wing. The idea: if S is a subtype of T, a program built to work with objects of type T should keep working correctly when handed an object of type S instead. The textbook illustration is a Square that extends Rectangle and overrides setWidth() to also change the height. It compiles cleanly, but it breaks any code that set a rectangle's width and height independently and expected the two to stay that way.

A more realistic version of the same failure shows up whenever a subclass narrows what its base type promised rather than fully supporting it. A caching repository that extends a general-purpose Repository class but backs onto a read-only cache is a natural thing to write and technically compiles.

caching-repository.ts TS 
class Repository<T> {
  write(item: T): void { /* persist to the primary store */ }
  read(id: string): T { /* ... */ }
}

// Compiles cleanly. Breaks every caller that trusted the base
// Repository's contract that write() succeeds.
class CachingRepository<T> extends Repository<T> {
  write(item: T): void {
    throw new Error('CachingRepository is read-only');
  }
}

Any caller written against Repository, unaware that this particular subtype throws on write(), breaks the moment it receives a CachingRepository instead. The usual instinct when this surfaces is to add an instanceof check at every call site that might receive the subtype. That papers over one violation while creating a second problem. Every caller now has to know about every subtype's quirks, which is exactly the coupling encapsulation was supposed to prevent. The actual fix is to stop modeling the relationship as inheritance in the first place.

Composition over inheritance

The LSP violation above is a symptom of modeling "is-a" where the real relationship is "has-a." A caching repository isn't a kind of repository that happens to reject writes. It's a thing that holds a cache and a repository and coordinates between them. Composition over inheritance means building behavior this way by default. Assemble an object out of smaller collaborators with their own clear contracts, rather than extending a base class and hoping every method it exposes makes sense for the new case.

caching-repository.ts TS 
class CachingRepository<T> {
  constructor(private cache: Cache<T>, private source: Repository<T>) {}

  read(id: string): T {
    return this.cache.get(id) ?? this.source.read(id);
  }
  // No write() method to promise and then break.
}

Rebuilt this way, CachingRepository never claims to be a full Repository, so there's no promise to break. Composition solves the substitution problem directly instead of working around it. The failure mode at this end of the spectrum is the opposite of inheritance's. Compose too many small, single-purpose collaborators, and following one request through the system means opening ten files to find where anything actually happens.

Dependency Inversion Principle

A high-level policy, "send a welcome email on signup," hard-wired to a low-level detail, a specific SMTP client, means changing the detail requires editing the policy. The Dependency Inversion Principle (DIP), from Robert C. Martin, is the fix stated abstractly. Depend on abstractions, not concretions. High-level modules and low-level modules should both depend on an interface between them, rather than the high-level module depending directly on the low-level module's implementation.

DIP is a principle, not a technique, and it's worth being precise about the difference, because it gets conflated constantly with the pattern that follows it. Dependency inversion says what should be true of the relationship between two modules. Dependency injection, next, is one way of making it true in code, not a synonym for it.

Dependency Injection

Dependency Injection (DI) satisfies DIP concretely. A class receives its dependency from outside instead of constructing it internally. Martin Fowler's 2004 article on inversion of control containers gave the pattern its modern name. It also gave it a now-standard justification. A class built this way can be tested against a fake dependency and swapped onto a different implementation without its own code changing.

signup-service.ts TS 
// Hard-wired: SignupService can't be tested or swapped onto a
// different mailer without editing this class.
class SignupService {
  private mailer = new SmtpMailer();
  complete(email: string) { this.mailer.send(email, 'Welcome'); }
}

// Injected: the dependency arrives from outside, satisfying DIP.
class SignupService {
  constructor(private mailer: Mailer) {}
  complete(email: string) { this.mailer.send(email, 'Welcome'); }
}

Overused, DI produces an interface and an injected dependency for something with exactly one implementation and no realistic second one, ever. That's DIP's ceremony without DIP's benefit. The layer of indirection exists because the pattern is familiar, not because two independently changeable modules actually needed to be decoupled.

Inversion of Control

Code that drives its own control flow can only be reused inside that same flow. A function that calls its own dependencies directly, in the order it chooses, can't easily be run inside a test harness, a UI framework's render cycle, or a plugin host. All of those need to be the one calling the shots. Inversion of Control (IoC), sometimes called the Hollywood principle after "don't call us, we'll call you," inverts that. The framework or container calls your code, instead of your code calling the framework.

An event listener is IoC in its simplest form. The browser decides when onClick runs, not the code that defines it. A test framework invoking every function named like a test is the same shape at a larger scale. Dependency injection is frequently the mechanism IoC uses to hand control over. A container builds an object graph and calls into it, rather than the object graph reaching out to build itself.

The same inversion that makes code reusable also makes it harder to trace. Once a container decides when and with what to call a piece of code, tracing that call means reading the container's wiring, not just reading the code in order. A new developer can't always answer "who calls this?" just by reading the codebase, because the call happens through configuration or a naming convention, not a direct reference. IoC is worth the cost when a framework, a test runner, or a plugin host genuinely needs to own the call. A small script or a linear pipeline with one obvious caller doesn't need a container standing in the middle.

DIP, DI, and IoC are not the same thing

These three get used interchangeably in conversation, but each names something different.

  • Dependency Inversion Principle is the rule itself, that two modules should depend on a shared abstraction rather than one depending on the other's concrete implementation.
  • Dependency Injection is one concrete technique for satisfying it, where a class receives its dependencies from outside instead of constructing them itself.
  • Inversion of Control is the broader pattern behind dependency injection, where a framework or container calls your code instead of your code calling it.

DIP states the goal, DI is one way to reach it in code, and IoC is the shift in control that makes DI possible.

Where SOLID fits

Single Responsibility and Interface Segregation from the previous section, plus Open/Closed, Liskov Substitution, and Dependency Inversion from this one, are the five principles bundled historically as SOLID (see the history). They're grouped in this article by what they actually govern, responsibility placement versus dependency safety, rather than by acronym position, but the acronym isn't lost. It's just not the organizing structure.

Communicate cleanly

The last branch asks a narrower question than the first three. Once an object exists and owns its own state, what should it expose, and who gets to decide based on it? Get it wrong, and a change three objects away ripples into code that never asked to know about it.

Law of Demeter

The Law of Demeter (LoD) came out of Karl Lieberherr and Ian Holland's Demeter project at Northeastern University in 1987, and its informal statement is "only talk to your immediate friends." A method should call methods on objects it directly holds, not reach through one object to get a second object and then call a method on that.

billing-city.ts TS 
// Breaks if Customer ever restructures how it stores an address.
const city = order.getCustomer().getAddress().getCity();

// Order only talks to its immediate collaborator.
const city = order.getBillingCity();

The first version chains through three classes' internal structure at once, touching Order, Customer, and Address in a single expression. If Customer ever stores a shipping address and a billing address separately instead of one address field, every chain like this one breaks, scattered across however many call sites reach into the object graph. The delegating method on the second line is the same coupling problem section two named for modules, applied to a single call chain.

Overused, the Law of Demeter turns into a rule about syntax instead of dependencies. Every class in the chain grows a one-line wrapper method whose only job is forwarding a call to the next collaborator. The codebase fills with wrapper-method bloat like getBillingCity() that exist purely to satisfy the rule. That's worth doing when Customer's internal structure is genuinely likely to change. It's wasted ceremony when it isn't, an extra method to read, test, and maintain for a structure that was never going anywhere. The rule is about not depending on another object's internal structure, not about refusing to chain method calls. A chain over immutable value objects, such as a fluent builder, is harmless, because there's no changeable internal structure to leak in the first place.

Tell, Don't Ask

Pulling an object's internal state out to make a decision about it externally duplicates logic that belongs with the data, and it breaks the same encapsulation boundary the Law of Demeter protects. Tell, Don't Ask is the corrective habit. Instead of reading a flag and branching on it outside the object, tell the object what outcome is wanted. Let it decide how, using only the state it needs to see. A shopping cart shouldn't expose its item count so calling code can decide whether it's empty. It should expose a method that answers that question itself.

checkout.ts TS 
// Checkout reads the cart's raw count and re-implements the
// "is it empty" decision outside the object that owns the state.
function canCheckout(cart: Cart, user: User): boolean {
  return cart.items.length > 0 && hasValidPayment(user);
}

// The cart answers a question about its own state. Checkout still
// owns the broader decision, composed from checks that are its job.
class Cart {
  hasItems(): boolean { return this.items.length > 0; }
}

function canCheckout(cart: Cart, user: User): boolean {
  return cart.hasItems() && hasValidPayment(user);
}

The hasItems method draws a deliberate line. It answers for the cart's own state and nothing else. Pushed too far, Tell Don't Ask pulls decisions into an object that has no business making them. A shopping cart can reasonably decide whether it's empty. It can't reasonably decide whether checkout is allowed today, because that depends on inventory, the user's account standing, and a promotion schedule the cart has never heard of. Forcing that decision inside the cart means either injecting every collaborator it might ever need an answer from, or duplicating their logic locally to avoid asking. Some decisions genuinely belong to a caller with a wider view, and asking a few objects for their state is more honest than pretending one of them can decide alone.

Command Query Separation

Bertrand Meyer's Command Query Separation (CQS), also from Object-Oriented Software Construction, draws a line between two kinds of methods. A command does something and returns nothing. A query answers something and changes nothing. A method that does both is unsafe to call from a place that only meant to observe, a log statement or a debugger watch expression, because observing it also changes state.

cart-queue.ts TS 
// Reading this call also empties the cart, so a log statement
// that calls it silently changes what happens next.
function popNextItem(cart: Cart): Item {
  return cart.items.shift();
}

// Command and query, safe to call independently or not at all.
function removeNextItem(cart: Cart): void { cart.items.shift(); }
function peekNextItem(cart: Cart): Item { return cart.items[0]; }

CQS is a guideline, not a hard constraint, and plenty of well-established methods break it on purpose. Array.prototype.pop() removes the last element and returns it in one call, and nobody considers that a design flaw. An auto-incrementing counter that returns the new value on every call does the same thing, and so does a SQL INSERT that returns the generated id from the same statement that created the row. Splitting either into a separate command and query would mean an extra round trip, or a second read that could see a different answer than the write just produced. The line worth holding is narrower than "never combine." A method that returns state while changing it is fine when the return value is inseparable from the change, the very thing the write just produced. It's a problem when the return value is incidental and calling the method for its side effect alone becomes a trap for the next person to read it.

Law of Demeter, Tell Don't Ask, and Command Query Separation all circle back to the same underlying question, what an object should expose and who decides based on it. Each approaches it from a different angle, one about traversal, one about control flow, one about method shape. That's why they're grouped together here rather than scattered across other sections.

Fail fast

Every principle so far is about how code is arranged. This one is about how quickly a program admits something is wrong, which is why it sits outside the tree above rather than inside one of its branches.

Invalid state discovered far from where it was introduced is expensive to debug. The error message points at the symptom, not the cause, and tracing backward through however many function calls separate them takes real time. Fail fast is the discipline of surfacing a problem at its source instead of letting it propagate. In practice that's a guard clause at a function's boundary that throws immediately on an invalid argument, rather than passing it through and letting it corrupt something three calls later.

A quieter version of the same mistake is a function that can't do what it was asked to do, and returns as if it had anyway. A save that silently drops a write on a duplicate key hides the failure. So does an update that returns without changing anything because the record it was supposed to update doesn't exist. Both look like they succeeded from the caller's side. The caller has no way to tell "done" from "silently skipped," and the bug surfaces later as whatever code assumes work that never actually ran.

update-email.ts TS 
// Returns normally whether the update happened or not. A caller
// can't tell "saved" from "silently did nothing."
function updateEmail(id: string, email: string): void {
  const user = users.get(id);
  if (!user) return;
  user.email = email;
}

// Fails at the point where the assumption breaks, not three
// calls later when something expects the email to have changed.
function updateEmail(id: string, email: string): void {
  const user = users.get(id);
  if (!user) throw new Error(`No user with id ${id}`);
  user.email = email;
}

The exception is a function whose job is to reach a state rather than perform an action. Deleting a record that's already gone is the clearest case. The caller wanted the record gone, and it already is. Returning as if the delete succeeded is accurate, not a swallowed failure. The same reasoning covers a create-if-missing call, or cancelling a subscription that's already cancelled. What makes the silent return acceptable here is that the desired end state already holds. Nothing was skipped that the caller was depending on.

delete-user.ts TS 
// No error if the id was already gone. The caller's goal, "this
// record shouldn't exist," is already true, so this isn't a failure.
function deleteUser(id: string): void {
  users.delete(id);
}

In a modern TypeScript codebase, fail fast increasingly happens before the program even runs. Strict mode turns a value that might be undefined into a compile error at the point it's used, not a runtime crash the first time a user hits the missing case. An exhaustive switch over a union type, checked with a never assertion in the default branch, fails to compile the moment a new case is added to the union without a matching branch. That catches the gap before the code ships rather than after. Static typing enforced this way is fail fast moved one step earlier, from the first bad input to the first bad line.

The failure mode is treating every unexpected input as a hard crash. Code that calls a service which occasionally times out, and which the caller can reasonably retry or fall back from, shouldn't throw an unrecoverable error at the first sign of trouble. Fail fast is for state that's actually invalid and shouldn't be allowed to continue, not for every condition a caller might reasonably want to handle itself.

Where these principles pull against each other

Return to the opening claim. Every principle reduces one of four costs, namely understanding, changing, testing, or extending. Every misuse story above is one of those same four costs being paid back after a different one was reduced.

PrincipleReducesOverused becomesCost that comes back
DRYDuplicate knowledgeA wrong shared abstraction forced to cover cases that were never really the sameUnderstanding, changing
SRPMixed responsibilitiesHundreds of tiny classes, logic scattered thin across all of themUnderstanding
OCPModification riskA plugin or strategy architecture for a case that will never have a second variantUnderstanding, extending
DIP / DIHard-wired concretionsAn interface with exactly one implementation, foreverUnderstanding
KISSAccidental complexityOversimplification that hides real edge cases instead of removing themExtending, testing
YAGNISpeculative buildingRead as "never plan," creating debt the moment the "unlikely" need arrives anywayChanging

The pattern in that table is the whole argument of this article compressed into one shape. Nothing on this list is free, and nothing on this list is free of a stopping point. DRY removes duplicated knowledge until the abstraction it creates has to serve two things that were never actually the same thing. OCP removes the risk of editing working code until the extension point it adds is speculation dressed up as architecture. The practical heuristic that falls out of all seventeen principles is the same one. Apply a principle when it removes a cost you can already point to in the code in front of you. That cost might be a specific change that's hard to make, a specific concept that's hard to follow, or a specific case that's hard to test. Not because the principle is well known, and not preemptively, before that cost has actually shown up.
