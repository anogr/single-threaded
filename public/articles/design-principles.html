Software Design Principles

How recurring problems in code structure led to familiar rules, and how to tell when those rules stop helping.

Andreas Ögren
~22 min read
Last updated July 2026

A design principle is a rule of thumb for shaping code and the dependencies between its parts. Each principle captures a problem that has appeared in many systems, but none is a compiler rule or a universal prescription. Applying one exchanges one kind of cost for another, so its value depends on the problem at hand and whether that exchange still pays off.

Structural problems rarely announce themselves with the name of a principle. They appear as ordinary friction. A checkout fix breaks another payment method because both depend on hidden state. A function is difficult to trace because several unrelated jobs sit behind one name. A small test pulls in a database and half the application because the code cannot run in isolation. These recurring costs are more useful to recognize than the labels:

  • Understanding gets harder, because behavior that looks self-contained turns out to depend on something two files away that nobody documented.
  • Changing gets riskier, because a fix in one place can break a feature that was silently relying on it.
  • Testing gets harder, because nothing can be verified without dragging in the rest of the system.
  • Extending gets more fragile, because new behavior has to be wedged into a structure that wasn't built to expect it.

Every principle in this article addresses one or more of these costs. Once applied beyond the problem it solves, the principle can add back the complexity it removed elsewhere. Code that is easier to understand and test often supports correctness and security, although neither follows from good structure alone.

The structural principles fall into four groups according to the decision each one helps make.

  • Build less asks whether a capability should exist before deciding how to organize it.
  • Organize code well asks where a responsibility belongs and what it needs to know about neighboring code.
  • Depend safely asks how two parts can collaborate without becoming needlessly difficult to change independently.
  • Communicate cleanly asks what an object should expose and where decisions about its state should live.

Fail fast sits outside these groups because it governs how quickly a runtime problem surfaces rather than how code is arranged.

History

These ideas did not arrive as one method. Information hiding grew from research into modular decomposition. The Law of Demeter emerged from the Demeter project, and Liskov's work on data abstraction clarified the obligations of a subtype. Other rules came from engineering practice or received names after authors recognized the same lesson across many projects.

The shared vocabulary arrived after the underlying problems were already familiar. That history helps explain why some principles overlap and why their wording varies between authors.

Build less

Before organizing code, decide whether the capability is needed and whether its complexity has earned a place in the system.

YAGNI

A configuration flag is added for a use case that seems inevitable. A parameter accepts several strategies even though the product has one. Months later, every environment uses the same value and nobody remembers why the branch exists. YAGNI (You Aren't Gonna Need It) names the cost of that speculation. An unused capability must still be understood, tested, and maintained before it provides any benefit. The rule, associated with Extreme Programming, is to build a capability when a real requirement calls for it rather than when a future use merely seems plausible.

YAGNI does not rule out planning. It separates choices that keep today's design easy to change from speculative capabilities that must be carried until a possible future arrives. Clear names and a small boundary around data access solve present problems. A flag with no current use or a plugin system with one plugin usually does not.

KISS

KISS (Keep It Simple, Stupid) came into software from a broader engineering maxim. It treats complexity as a cost that the problem must justify. In code, simplicity may come from a direct data flow or from separating unrelated work that was hidden inside one function. The relevant test is whether the simplest correct design remains clear when someone needs to change it.

KISS becomes harmful when it hides complexity instead of removing it. Collapsing several distinct cases into one branch that handles most of them leaves the missing distinctions to surface as bugs. A simpler design reduces what a reader must track while still representing every case the software needs to handle.

Rule of Three

Extracting an abstraction from one example requires guessing which details will remain stable. The Rule of Three, popularized in Martin Fowler's Refactoring, suggests tolerating two similar implementations and considering an extraction when a third appears. The extra examples make the common shape easier to see, although they do not prove that all three cases represent one concept.

Waiting carries its own cost because similar implementations can drift into subtly different versions. Three is therefore a timing heuristic, not a threshold that makes an abstraction correct. Extract earlier when the duplicated knowledge is already clear and costly. Wait longer when the resemblance may disappear as the cases evolve.

DRY

DRY (Don't Repeat Yourself) concerns duplicated knowledge rather than code that merely looks similar. Andrew Hunt and David Thomas framed the principle around giving each piece of knowledge one authoritative representation. It matters when the same business rule must be updated in several places because any missed copy can quietly become stale.

validate-email.ts TS 
// The same shape existed inline in createUser, updateUser, and
// importUsers before the third call site made it worth naming.
function assertValidEmail(email: string): void {
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
    throw new Error(`Invalid email: ${email}`);
  }
}

The extraction above is sound only if every call site represents the same rule, and occurrence counts cannot establish that. Similar code may belong to different concepts that later diverge. A shared function then accumulates special cases, obscuring both rules until the abstraction costs more than the original duplication.

Organize code well

Once behavior earns its place in the codebase, its location and boundaries determine how easily people can find, understand, and test it.

Encapsulation and information hiding

David Parnas's 1972 paper "On the Criteria to Be Used in Decomposing Systems into Modules" argued that modules should hide design decisions likely to change. Information hiding keeps the effects of those changes behind a stable interface. Encapsulation provides the code boundary that enforces that separation. A queue exposing enqueue() and dequeue(), for example, can change its storage without forcing callers to change with it.

The next principles apply related boundaries at different scales. Single responsibility groups behavior that changes for the same reason, while interface segregation limits the surface a caller depends on. Neither principle requires accessors around every field. A getter and setter that expose an unchanged value hide no design decision. Plain immutable values, such as coordinates or date ranges, may gain nothing from a method around each field.

Separation of concerns

Edsger Dijkstra described separation of concerns as a way of reasoning about a program rather than a prescription for organizing folders. A concern is a distinct area of responsibility. Presentation, business policy, and persistence are common examples. When one piece of code handles unrelated concerns, a change to one can disturb another because the implementation ties them together.

Folder structure can reflect separate concerns, but it cannot create the separation by itself. Two functions in one file may remain independent when one computes a value and the other renders it. Functions in different folders remain coupled when the rendering code reimplements business logic.

Overapplication produces layers that do not correspond to distinct responsibilities. One cohesive operation gets split across a controller, service, and repository that each do almost nothing alone. A change then crosses three files whose separation exists only on paper. Splitting pays off when the pieces can plausibly change for different reasons or at different rates, not because a project template provides three folders.

Single Responsibility Principle

The classic phrasing of the Single Responsibility Principle (SRP) says that a module should have one reason to change. Robert C. Martin later related that reason to the people or roles requesting the change. Form validation, persistence, and email delivery answer to different concerns even when they occur in one workflow. A change to validation policy should not put storage or delivery logic at risk.

Reading "one reason to change" as "one method per class" produces the opposite of the intended result. Dozens of tiny classes may look simple in isolation while scattering one business operation across many files. A responsibility describes a coherent source of change, not a line or method count.

Interface Segregation Principle

The Interface Segregation Principle (ISP) applies a similar idea to the contracts seen by callers. A caller should not depend on methods it never uses. A Machine interface that requires print(), scan(), and fax() forces a print-only device to pretend it supports two irrelevant operations. Separate capability interfaces let each caller depend only on the operation it needs.

Taken too far, ISP produces one interface per method even when every caller needs the same complete capability. The extra names and files then obscure a contract that one interface could have expressed clearly. A split earns its place when callers genuinely need different subsets of behavior, not merely because smaller interfaces look cleaner.

High cohesion, low coupling

Cohesion describes how closely the responsibilities inside a module belong together. Coupling describes how much one module depends on others and how readily a change can propagate between them. A cohesive module has a recognizable purpose, while a loosely coupled one makes few narrow assumptions about its collaborators. Encapsulation, separation of concerns, SRP, and ISP pursue those qualities from different directions without guaranteeing them.

Depend safely

Module boundaries organize responsibilities, while dependency rules determine how those modules can collaborate without tying their evolution together.

Open/Closed Principle

Bertrand Meyer stated the Open/Closed Principle (OCP) in Object-Oriented Software Construction (1988). A module should allow new behavior to be added without repeatedly changing stable code. Consider a charge() function with one branch per payment method. Every new method edits control flow shared by the existing ones, so a local addition can disturb unrelated behavior.

charge.ts TS 
// Before: a new payment method means editing this function again,
// next to every method that already works.
function charge(method: string, amount: number) {
  if (method === 'card') return chargeCard(amount);
  if (method === 'wallet') return chargeWallet(amount);
  if (method === 'invoice') return chargeInvoice(amount);
  throw new Error(`Unsupported method: ${method}`);
}

// After: adding a new provider is a new entry, not a new branch,
// and existing entries are untouched.
const chargeHandlers: Record<string, (amount: number) => Charge> = {
  card: chargeCard,
  wallet: chargeWallet,
  invoice: chargeInvoice,
};

function charge(method: string, amount: number) {
  const handler = chargeHandlers[method];
  if (!handler) throw new Error(`Unsupported method: ${method}`);
  return handler(amount);
}

The map still gains an entry for each payment method, so the module is not literally closed to edits. The useful change is narrower: adding a handler no longer alters the control flow used by existing handlers. A plugin registry could move registration outside the module, but that machinery is justified only when independent registration is a real requirement.

Registration tables, plugin loaders, and strategy interfaces all add indirection. That cost can pay off when implementations multiply or register independently. A function with one stable behavior has no such pressure. Extension points should follow observed variation rather than the familiarity of a pattern.

Liskov Substitution Principle

Barbara Liskov introduced the substitution idea behind the Liskov Substitution Principle (LSP) in a 1987 OOPSLA keynote. Later work with Jeannette Wing formalized behavioral subtyping. A subtype must preserve the promises on which clients of its base type rely. The familiar Square and Rectangle example fails when clients may set a rectangle's width and height independently but a square cannot honor that contract.

The same failure appears whenever a subtype accepts fewer valid operations or provides weaker guarantees than its contract promises. A read-only cache may compile as a subclass of a writable Repository, yet it cannot honor the inherited write operation.

caching-repository.ts TS 
class Repository<T> {
  write(item: T): void { /* persist to the primary store */ }
  read(id: string): T { /* ... */ }
}

// Compiles cleanly. Breaks every caller that trusted the base
// Repository's contract that write() succeeds.
class CachingRepository<T> extends Repository<T> {
  write(item: T): void {
    throw new Error('CachingRepository is read-only');
  }
}

A caller written against Repository is entitled to use write(). A subtype that throws because writing is unsupported breaks that expectation. Adding instanceof checks only spreads knowledge of the broken contract into every caller. The model should separate readable and writable capabilities, or treat the cache as a collaborator instead of a substitute.

Composition over inheritance

The violation above treats a coordination role as a subtype. A cache-backed reader can instead hold a cache and a source, choosing which one answers each read. Composition over inheritance favors assembling behavior from collaborators with explicit contracts. Inheritance remains useful when a subtype can preserve its parent's complete behavioral contract.

caching-repository.ts TS 
class CachingRepository<T> {
  constructor(private cache: Cache<T>, private source: Repository<T>) {}

  read(id: string): T {
    return this.cache.get(id) ?? this.source.read(id);
  }
  // No write() method to promise and then break.
}

Rebuilt this way, CachingRepository no longer promises write support. Composition removes the invalid contract instead of working around it. The approach can still be overused. Turning every step into a separate collaborator may leave one request scattered across a long chain of tiny files.

Dependency Inversion Principle

A signup policy that constructs a specific SMTP client mixes its purpose with one delivery mechanism. The Dependency Inversion Principle (DIP), formulated by Robert C. Martin, introduces a stable boundary between them. The policy depends on the capability to send a message, and the SMTP adapter implements that capability. The policy no longer imports the adapter's concrete type.

DIP describes the desired relationship between modules. Dependency injection, covered next, is one technique that can help create that relationship. The terms are related but not interchangeable.

Dependency Injection

Dependency Injection (DI) supplies an object's collaborators from outside instead of constructing them inside the object. Martin Fowler's 2004 article distinguished constructor, setter, and interface injection under that name. DI supports DIP when the injected dependency is expressed through an appropriate abstraction. Injecting a concrete type still separates construction from use, but it does not invert a source-code dependency by itself.

signup-service.ts TS 
// Hard-wired: SignupService can't be tested or swapped onto a
// different mailer without editing this class.
class SignupService {
  private mailer = new SmtpMailer();
  complete(email: string) { this.mailer.send(email, 'Welcome'); }
}

// Injected: the dependency arrives from outside, satisfying DIP.
class SignupService {
  constructor(private mailer: Mailer) {}
  complete(email: string) { this.mailer.send(email, 'Welcome'); }
}

DI becomes ceremony when a stable implementation is hidden behind an interface that no caller needs to replace or isolate. The extra boundary makes the code harder to trace without protecting a meaningful source of change. Injection earns its place when separating construction, substitution, or testing provides a concrete benefit.

Inversion of Control

A framework often owns the main control flow and invokes application code at defined extension points. Inversion of Control (IoC) names that arrangement. Event handlers, test functions, and plugin callbacks all run because a host calls them. Application code supplies the behavior, while the host controls when it runs.

An event listener is a small example because the browser decides when its handler runs. A test runner does the same for registered tests. Dependency injection applies the broader idea to object construction. A container may perform the injection, although ordinary construction code can also pass dependencies explicitly.

Inversion can make call paths harder to trace because a container or framework may connect code through configuration, registration, or convention. Answering “who calls this?” then requires reading the host's wiring as well as the function. The cost is justified when the host needs to own the lifecycle. A small linear script with one obvious caller gains little from a container.

DIP, DI, and IoC are not the same thing

The three terms are often mixed together, although each describes a different part of the design.

  • Dependency Inversion Principle concerns the direction of source-code dependencies across a boundary.
  • Dependency Injection supplies an object with collaborators that were created elsewhere.
  • Inversion of Control is the broader arrangement in which a host controls part of the program's flow.

DI can support DIP, and dependency injection containers are one example of IoC. Neither relationship makes the terms synonyms.

Where SOLID fits

SOLID groups Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion. This article places them beside related ideas according to the decisions they govern. The history explains how principles with different origins came to share the label.

Communicate cleanly

An object's public surface determines how much of its state and internal structure the rest of the system must understand.

Law of Demeter

The Law of Demeter (LoD) came from the Demeter project led by Karl Lieberherr and Ian Holland at Northeastern University. Its informal wording is "only talk to your immediate friends." A method should collaborate with objects it receives or directly holds instead of reaching through them to traverse a wider object graph.

billing-city.ts TS 
// Breaks if Customer ever restructures how it stores an address.
const city = order.getCustomer().getAddress().getCity();

// Order only talks to its immediate collaborator.
const city = order.getBillingCity();

The first version exposes the path from Order through Customer to Address. If the customer model later separates shipping and billing addresses, every call site that knows the old path may need to change. The delegating method gives callers the information they need without exposing that route through the object graph.

Used as a syntax ban, the Law of Demeter produces forwarding methods with no useful boundary behind them. A method such as getBillingCity() earns its place when it hides how an order finds its billing address. It adds noise when it only renames a stable public operation. The principle concerns knowledge of another object's structure, not the number of dots in an expression. A fluent API can therefore use a call chain without violating the underlying idea.

Tell, Don't Ask

Reading an object's internal state and interpreting it elsewhere can duplicate logic that belongs with the data. Tell, Don't Ask keeps that local decision behind the object's boundary. Instead of exposing an item count so every caller can decide whether a cart is empty, the cart can answer hasItems() itself.

checkout.ts TS 
// Checkout reads the cart's raw count and re-implements the
// "is it empty" decision outside the object that owns the state.
function canCheckout(cart: Cart, user: User): boolean {
  return cart.items.length > 0 && hasValidPayment(user);
}

// The cart answers a question about its own state. Checkout still
// owns the broader decision, composed from checks that are its job.
class Cart {
  hasItems(): boolean { return this.items.length > 0; }
}

function canCheckout(cart: Cart, user: User): boolean {
  return cart.hasItems() && hasValidPayment(user);
}

The hasItems() method draws a boundary around the cart's own state. Checkout eligibility crosses several boundaries because it may also depend on inventory, account status, or commercial policy. Forcing that broader decision into the cart would give it unrelated dependencies. Local decisions belong with their data, while coordination across several owners belongs in code with the necessary view.

Command Query Separation

Bertrand Meyer's Command Query Separation (CQS), also from Object-Oriented Software Construction, distinguishes commands from queries. A command changes state, while a query returns information without changing observable state. Combining both roles can surprise code that meant only to observe, including logging and debugger expressions.

cart-queue.ts TS 
// Reading this call also empties the cart, so a log statement
// that calls it silently changes what happens next.
function popNextItem(cart: Cart): Item {
  return cart.items.shift();
}

// Command and query, safe to call independently or not at all.
function removeNextItem(cart: Cart): void { cart.items.shift(); }
function peekNextItem(cart: Cart): Item { return cart.items[0]; }

CQS is a guideline rather than a hard constraint. Array.prototype.pop() removes and returns the same element in one operation. A database insert may likewise return its generated identifier because a separate read would add another operation and could observe a different state. Combining the roles is clearest when the return value is the direct result of the command. The risky case is hidden mutation during an operation that appears to be an observation.

These three principles govern the same boundary from different angles. The Law of Demeter limits traversal into collaborators. Tell, Don't Ask keeps local decisions with the object that owns the relevant state. Command Query Separation makes observation and mutation easier to distinguish at the method boundary.

Fail fast

Structural principles shape the code, whereas fail-fast behavior shortens the distance between an invalid condition and the point where it becomes visible.

Invalid state becomes harder to diagnose after it has travelled through the system. The eventual error points to a symptom, while the cause sits several calls earlier. Fail fast means rejecting invalid state near the boundary where it enters. Guard clauses are one form, but parsers, type checks, and explicit validation results can enforce the same discipline without relying on exceptions.

A normal return can also hide failure. An update that ignores a missing record appears successful, so later code proceeds as though the change occurred. The operation should return an explicit result or raise an error according to its contract, allowing the caller to distinguish success from rejection.

update-email.ts TS 
// Returns normally whether the update happened or not. A caller
// can't tell "saved" from "silently did nothing."
function updateEmail(id: string, email: string): void {
  const user = users.get(id);
  if (!user) return;
  user.email = email;
}

// Fails at the point where the assumption breaks, not three
// calls later when something expects the email to have changed.
function updateEmail(id: string, email: string): void {
  const user = users.get(id);
  if (!user) throw new Error(`No user with id ${id}`);
  user.email = email;
}

Some operations promise an end state rather than a particular action. Deleting a record that is already absent can succeed because the requested state already holds. The same reasoning may apply to create-if-missing or cancelling an already cancelled subscription. A quiet return is appropriate only when the contract promises the state and the caller does not depend on whether a transition occurred.

delete-user.ts TS 
// No error if the id was already gone. The caller's goal, "this
// record shouldn't exist," is already true, so this isn't a failure.
function deleteUser(id: string): void {
  users.delete(id);
}

TypeScript can move some failures into development. With strict null checking, a value that may be undefined must be narrowed before code uses it as a definite value. A never check can make an unhandled union member fail type checking in an exhaustive switch. These techniques do not replace runtime validation at external boundaries, but they expose some inconsistencies earlier.

Failing fast does not require every unexpected condition to crash the process. A service timeout may be handled through retry, fallback, or an explicit error returned to the caller. The principle applies when continuing would hide the cause or allow invalid state to corrupt later work. Recoverable failures still need a contract that lets the caller respond.

Balancing the principles

A principle is useful while the cost it removes remains greater than the complexity introduced by applying it.

PrincipleReducesOverused becomesCost that comes back
DRYDuplicate knowledgeA wrong shared abstraction forced to cover cases that represent different conceptsUnderstanding, changing
SRPMixed responsibilitiesHundreds of tiny classes, logic scattered thin across all of themUnderstanding
OCPModification riskA plugin or strategy architecture for a case that will never have a second variantUnderstanding, extending
DIP / DIHard-wired concretionsAn interface with exactly one implementation, foreverUnderstanding
KISSAccidental complexityOversimplification that hides real edge cases instead of removing themExtending, testing
YAGNISpeculative buildingRead as "never plan," creating debt the moment the "unlikely" need arrives anywayChanging

Apply a principle when it addresses a cost visible in the code. The evidence might be a change that spreads too far, a concept that is difficult to follow, or a dependency that blocks a useful test. Then account for the complexity introduced by the solution. DRY stops helping when unrelated concepts are forced behind one abstraction. OCP stops helping when an extension point serves only imagined variants. A familiar name alone is not evidence that the trade is worthwhile.
