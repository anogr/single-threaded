UI Architecture Patterns

How MVC, MVP, MVVM, and Layered Architecture shaped React, Vue, and Angular.

Deep dive
~23 min read
Architectural patterns
July 2026

A user interface always has to answer the same three questions, no matter which decade or platform built it. What is the data? What does the screen show? And what sits between those two, deciding how a change on one side reaches the other? Every pattern in this article answers that third question differently, by deciding where the mediating piece lives, how much it's allowed to do, and how tightly it lets the other two talk to each other directly.

This is an old problem. Graphical interfaces have needed an answer since the 1970s, decades before there was a web browser to build "frontend architecture" for, and the patterns a team reaches for today are largely new implementations of ideas older than most of the people using them.

This article traces that lineage forward. It opens with three related patterns that all share the same three-letter shape, namely Model-View-Controller, Model-View-Presenter, and Model-View-ViewModel, each one built to fix a limitation the pattern before it left open. It then turns to layered architecture, a separate idea about how a whole application splits into tiers rather than how one screen organizes itself. It closes by looking at where React, Vue, and Angular land against all of it in 2026, and where each has moved past comparisons to these older patterns entirely.

Where These Patterns Came From

Each pattern below exists because the one before it hit a wall its platform couldn't get past on its own.

The story starts in 1979, at Xerox PARC, where a Norwegian computer scientist named Trygve Reenskaug was visiting the Learning Research Group, the team working toward Alan Kay's Dynabook concept, an early vision of a personal computer built for learning rather than just computing. Reenskaug was trying to solve a specific problem: how to let a user work with several views onto one complex dataset and keep all of them in sync as the underlying data changed. His first note on the idea, written that May, called it Thing-Model-View-Editor. After talking it through with Adele Goldberg, he settled on a different name that December: Model-View-Controller.

MVC never landed on one settled definition, and the reason traces back to its own first implementation. By the time Jim Althoff and others built MVC into the Smalltalk-80 class library, Reenskaug had already left PARC and wasn't involved in the work. Althoff's version used the word Controller for something Reenskaug's original note had called the Editor, the part handling device input for a specific view. Two names for overlapping ideas, baked into the pattern's reference implementation before it had even left the building it was invented in.

What MVC left unresolved was how strictly View and Model had to stay apart. In the original conception, a View could read the Model directly, which is convenient right up until an application has enough views and enough shared data that nobody can say for certain what happens when one of them changes. That gap is what the next pattern closed.

Model-View-Presenter came out of Taligent, a joint venture between Apple, IBM, and Hewlett-Packard, in the early 1990s, documented in a paper by Taligent's CTO, Mike Potel. Taligent folded in 1998, but the pattern didn't die with it. Andy Bower and Blair McGlashan carried it into Dolphin Smalltalk's UI framework, and Microsoft picked it up in the 2000s for Windows Forms, Silverlight, and ASP.NET. It also became a defining pattern in early Android development, where a Presenter mediating between an Activity and its data was, for years, close to the standard way to structure a screen. MVP's actual contribution was closing MVC's gap directly. The Presenter now mediates everything, and the View never touches the Model on its own. That enabled a screen's logic to be unit-tested without instantiating a real View, since the Presenter held every decision a test needed to exercise.

MVP still left one job to the developer: writing the code that kept a Presenter's state and a View's display in sync, by hand, every time either side changed. That's the piece Microsoft closed next, and this time the fix came from a change in what the platform itself could do.

Model-View-ViewModel was built inside Microsoft by architects Ken Cooper and Ted Peters, and announced publicly in 2005 by Windows Presentation Foundation (WPF) and Silverlight architect John Gossman on his blog. It's explicitly a variation of an earlier idea, Martin Fowler's Presentation Model pattern, adapted for a platform that could finally do something MVP's platforms couldn't: bind a View's display to a ViewModel's state declaratively, in both directions, without a developer writing the propagation code themselves. A ViewModel exposes state and commands. The binding engine keeps the View synchronized with it. What used to be a Presenter's job by hand became the platform's job automatically.

Read end to end, each pattern answers a limitation in the one before it. MVC arbitrated multiple views onto one shared dataset. MVP closed the direct View-to-Model read MVC left open, and made screen logic testable as a side effect. MVVM automated the synchronization work MVP still did by hand, once a platform could offer declarative binding to automate it with.

Layered architecture, often called N-tier, has a different and mostly unrelated history. Three-tier architecture, presentation, business logic, and data, grew out of mainframe and early client-server computing, where the three tiers were frequently three physically separate machines talking over a network. MVC and its descendants arbitrate a GUI widget's live state between a Model and the Views watching it. Layered architecture decides where code physically or logically runs, and which tier is allowed to call which.

MVC: The Original Triad

Model, View, and Controller, close to exactly as Reenskaug described them, minus the definitional argument about where the boundary sits.

The three roles are close to what Reenskaug described. The Model holds the application's data and the rules for changing it correctly, and it knows nothing about how that data gets displayed. The View renders that data for a user to see, and it reads the Model directly to do it, querying whatever fields it needs each time it draws. The Controller handles input, whether that's a keystroke, a click, or a device event, and translates it into operations on the Model.

What keeps multiple Views of the same Model in sync is the Observer pattern. The Model keeps a list of every View watching it, and instead of a View polling to check for changes, the Model notifies its dependents that something has changed. The notification typically carries little or no application data, so each View rereads the Model and redraws itself as needed. That's what let Reenskaug's original design support several Views on one dataset without any of them polling or duplicating state on their own.

That same direct View→Model relationship became one of the pressure points that later patterns such as MVP sought to address. Nothing in the original design stops a View from reading Model state that has nothing to do with the notification it just received, and nothing stops two Views from interpreting the same notification differently. That was a reasonable tradeoff in a Smalltalk environment in 1979, where a handful of tightly coupled Views watched one Model. That approach becomes increasingly difficult to manage as applications grow and many Views observe large shared Models.

One clarification matters here, since it causes real confusion: the "MVC" most developers meet first, in Rails, Django, Laravel, or a dozen other server-side web frameworks, is the multi-page, server-rendered world introduced above wearing Reenskaug's three names, not the same pattern in a new coat of paint. The Observer relationship described above needs a Model instance that stays alive in memory long enough for a View to watch it, and HTTP doesn't offer that. Each request is stateless. A Controller action runs, a View renders once from whatever data the Controller handed it, and by the time a user is looking at the result, the objects that produced it are already gone. There's nothing left to notify, so the Controller ends up doing a different job. It translates an incoming HTTP request into a response, closer to a request router than to the input-arbitration role Reenskaug had in mind for a live GUI widget.

Not impossible, just not HTTP

The missing Observer relationship above is a property of HTTP specifically, not a limit of the web as a whole. A persistent connection, WebSockets, Server-Sent Events, SignalR, keeps the same kind of live channel open that a desktop GUI's event loop does. A server-side Model can push a change out over it the moment something changes, the way real-time dashboards and collaborative editors already do. What a Controller-per-request model can't do, a different transport underneath the same server can.

MVP and MVVM never went through the same borrowing. Neither name attached itself to a server-side web framework, because both were solving a problem specific to a live, in-memory GUI, one the server-rendered web didn't have until client-side JavaScript made a browser tab capable of behaving like one.

MVP: Everything Through the Presenter

The Presenter mediates everything. The View never reads the Model, and nothing propagates automatically.

Model-View-Presenter keeps the original MVC's three roles but redraws the boundary between them. The Model still holds data and the rules for changing it correctly. The View still renders, but it's deliberately kept passive. It exposes methods and events for the Presenter to call, and does nothing on its own beyond displaying whatever it's told to display. The Presenter sits in the middle, reading the Model, deciding what the View should show, and pushing that decision to the View by calling it directly. Nothing skips the Presenter in either direction.

That's the gap MVC left open, closed by construction rather than by discipline. A View built the MVP way can't reach into the Model even if a developer is tempted to let it, because the View was never handed a reference to the Model in the first place. The tradeoff is that every bit of synchronization a binding engine might otherwise handle has to be written by hand, inside the Presenter, every time the Model changes in a way the View needs to reflect.

That constraint has a benefit. Since a Presenter depends on a View interface rather than a concrete View, its logic can be unit-tested by handing it a fake View and asserting what it called. Testing a screen's logic without a real View, or something standing in for one, wasn't really an option under MVC. It's also why MVP outlived Taligent by decades. Android development leaned on it for years, and Windows Forms and Silverlight teams kept reaching for it long after Taligent itself had folded.

MVVM: Declarative Binding Arrives

A ViewModel exposes state and commands. The View binds to them. The binding engine, not a developer, keeps both sides in sync.

Model-View-ViewModel keeps the same three-part shape as the patterns before it, with the middle role renamed and its job changed. The Model still holds data and the rules for changing it. The View still renders. The ViewModel sits between them, but instead of handling input directly the way a Controller or Presenter would, it exposes state and commands that the View binds to, and lets a binding engine handle the actual propagation in both directions.

That word declarative is doing real work in the sentence above, and it's worth being precise about what changes. A View built the MVP way states, in code a developer wrote, exactly how to push a Presenter's state onto a label or a button's enabled flag, and exactly when to do it. A View built the MVVM way states what it wants bound, a label's text to a property, a button's click to a command, and leaves the decision of when and how to propagate that change to the binding engine underneath it. The developer describes the relationship. The platform executes it.

This is also where the general idea of reactivity, tracking a value and automatically updating whatever depends on it, first shows up as a first-class platform feature rather than something a developer implements by hand inside a Presenter. The mechanics of how modern reactivity systems actually track dependencies, and where signals fit into that story, are covered in more depth in Client State. What matters here is narrower: MVVM is the pattern that made declarative, automatic synchronization the norm, and it did that specifically because its originating platform, WPF, shipped a binding engine capable of it.

Layered Architecture: Tiers, Not Views

Three layers, one rule: a layer may only call the layer directly beneath it.

Layered architecture, also called N-tier, splits an application into horizontal layers, most commonly presentation, business logic, and data access, and enforces one rule across all of them: a layer is only allowed to call the layer directly beneath it. The presentation layer can call business logic. Business logic can call data access. Presentation is never supposed to reach past business logic straight into data access, no matter how tempting that shortcut looks on a Friday afternoon.

The payoff is durability under change. A team can swap the database, rewrite the entire user interface, or replace how business rules are implemented, and provided the layer boundaries held, the layers on either side of the one being replaced don't need to know or care. That's a meaningfully different kind of protection than anything MVC, MVP, or MVVM offer, because none of those three say anything about where code runs or which tier owns which responsibility. They're answering a different question, the one this section exists to keep separate from the last one.

The layering that only exists in a diagram

A presentation component that imports a database client directly, just this once, is the layering violation in practice. It compiles. It works today. It's also the reason a data migration six months later means auditing the UI layer instead of one query, because the boundary that was supposed to prevent exactly that stopped being real the day it was first skipped.

This is also why a typical modern product still separates "the frontend," "an API layer," and "a database," even when a single framework nominally owns all three ends of that chain. The tiers are a decision about where responsibilities live, not about which repository or team happens to own the code that implements them.

The three tiers above describe what a layer's responsibility is, not how the code implementing it gets grouped into folders. A codebase organized by layer puts every component in one folder, every service in another, and every repository class in a third, so a single feature such as checkout has its code scattered across all three. The alternative, usually called feature-based or vertical-slice organization, groups code by domain instead. A checkout/ folder holds its own thin slice through presentation, business logic, and data access, sitting next to a similarly self-contained cart/ folder. Both are still layered architecture in the sense that matters here, the call-direction rule from presentation to business logic to data access still holds inside each slice. Feature-based organization answers a different, folder-level question: whether related code lives near other code that changes for the same reason, or near other code that merely looks the same technically. Most frontend codebases lean feature-based today for exactly that reason, since a change to checkout should touch one folder, not three scattered across the whole tree.

Where React, Vue, and Angular Land

Three frameworks, three different relationships to these patterns, and one claim worth arguing with directly rather than repeating.

Vue: MVVM by Design

Vue is a component-based framework built around declarative rendering, reactive state, and a lightweight programming model. Vue has consistently described itself in terms of MVVM, and the pattern maps naturally onto how modern Vue applications are structured.

The fundamental architectural unit is the component, which encapsulates a template together with the state and behavior that drive it. The template declaratively binds to that state and responds to user events. Components can maintain their own local state or consume shared state from composables or application-wide stores. Business logic, data access, and other cross-cutting concerns are typically factored into composables or dedicated state management libraries rather than embedded directly in components.

Vue closely follows the MVVM pattern. The template acts as the View, while the component exposes the reactive state and methods consumed by that template, serving as the ViewModel. Composables and state stores are not equivalent to the Model in the classical MVC sense. They provide reusable application logic, shared state, or both.

Vue's reactivity system is central to this model. Reactive objects, refs, and computed values automatically track dependencies as they are read. Components and templates that read reactive values automatically become dependent on them, allowing Vue to update only the parts of the UI affected by a state change instead of broadly re-rendering across the component tree.

counter.ts TypeScript 
import { ref, computed } from 'vue';

export function useCounter() {
  const count = ref(0);
  const doubled = computed(() => count.value * 2);

  function increment(): void {
    count.value++;
  }

  return {
    count,
    doubled,
    increment
  };
}

In this example, the composable encapsulates reusable reactive state and behavior. A component calls useCounter() and binds directly to the returned count and doubled values in its template. Because these are reactive values, Vue automatically tracks those dependencies and updates only the UI that consumes them when their values change.

Angular: An Explicit Hybrid

Angular is a component-based framework built around dependency injection, declarative templates, and reactive state. Angular has historically been discussed in terms of MVC and MVVM. While neither pattern maps cleanly onto modern Angular applications, MVVM provides the closer architectural analogy.

The fundamental architectural unit is the component, which encapsulates a template together with the presentation logic that drives it. Components obtain their dependencies through Angular's dependency injection system rather than constructing or locating them directly. Business logic, data access, shared application state, and other cross-cutting concerns are commonly encapsulated in injectable services, while templates declaratively bind to component properties and react to user events.

From a UI architecture perspective, Angular most closely resembles MVVM. The template acts as the View, while the component exposes the state and behavior consumed by that template, effectively acting as the ViewModel. Injectable services are not the Model in the classical MVC sense. Instead, they provide whatever application services the component depends on, such as domain models, repositories, API clients, or state stores. How responsibilities are divided between components and services is largely an application design decision rather than something prescribed by Angular.

Modern Angular further reinforces this reactive model through signals. A signal represents a reactive value, while computed signals derive values automatically from other signals. Components and templates that read a signal automatically become its dependents, allowing Angular to target change detection only at the affected components instead of broadly traversing the component tree.

counter.component.ts TypeScript 
@Injectable({ providedIn: 'root' })
export class CounterStore {
  readonly count = signal(0);
  readonly doubled = computed(() => this.count() * 2);

  increment(): void {
    this.count.update(n => n + 1);
  }
}

In this example, the service encapsulates reactive state and behavior that exposes signals. The component injects the store, and its template binds directly to the store's count and doubled signals. Because these are signals, Angular automatically tracks the dependency and refreshes only the UI that consumes them when their values change.

React: A Library, Not a Pattern

React is a component-based library built around declarative rendering, unidirectional data flow, and composable components. Unlike Angular and Vue, React does not describe itself in terms of MVC or MVVM. Instead, it focuses on rendering a UI from state while leaving the overall application architecture largely to the developer.

The fundamental architectural unit is the component, implemented as a function that returns a description of the UI. Components manage local state through hooks such as useState, derive values during rendering, and respond to user events by updating state. Shared state, business logic, data access, and other cross-cutting concerns are typically factored into custom hooks, context providers, or third-party libraries. React intentionally provides few architectural conventions beyond the component model itself.

React is often described as the View in MVC, although that characterization is incomplete. A React component combines rendering, state, and behavior, giving it responsibilities traditionally associated with both the View and the ViewModel. Unlike Angular or Vue, however, React does not prescribe where application logic or state should live. Whether an application adopts an MVC, MVVM, or another architectural style depends almost entirely on the surrounding ecosystem rather than on React itself.

React's rendering model is driven by state changes. When a component's state or props change, React re-executes that component to produce a new description of the UI. React then reconciles that result with the previous render and applies only the necessary changes to the DOM instead of replacing it wholesale.

useCounter.ts TypeScript 
import { useState } from 'react';

export function useCounter() {
  const [count, setCount] = useState(0);
  const doubled = count * 2;

  function increment(): void {
    setCount(n => n + 1);
  }

  return {
    count,
    doubled,
    increment
  };
}

In this example, the custom hook encapsulates reusable state and behavior. A component calls useCounter() and renders the returned count and doubled values, wiring its increment function to a click handler. Because count is state, calling setCount inside increment triggers React to re-render the component and patch only the parts of the DOM that actually changed.

Unlike Angular and Vue, React intentionally stops at the component model and rendering engine, leaving higher-level architectural patterns to the surrounding ecosystem.

Comparing the Patterns

The interesting question was never which pattern is best. It's which problem each one solves, and whether a given application still has that problem.

MVC's directness is also its weakness. A View that's allowed to read the Model straight away is fast to build and just as fast to lose control of, once an application has grown past a handful of screens and enough of them are watching the same shared data. That's exactly the gap MVP closed by forcing everything through a Presenter, at the cost of writing that Presenter by hand. MVC, in its GUI-arbitration form, earns its keep on small, self-contained screens, a form or two built around one dataset, not an application where several views need to update each other independently.

MVVM's binding layer removes glue code, but it doesn't remove complexity. It moves that complexity into the framework's own reactive system, where it's harder to see. Debugging a binding failure means reasoning about a system whose propagation logic a developer never wrote, whereas a hand-written Presenter's data flow, however tedious to produce, is at least fully readable in a developer's own code. Refusing two-way binding in the first place trades the convenience MVVM offers for a data flow that stays fully traceable through a single, predictable cycle, no matter how large the application gets.

Layered architecture buys long-term maintainability and clean team boundaries. A frontend team, an API team, and a data team can each change their own layer without reading the others' code first. The cost is upfront ceremony that's simply wasted effort on an application one or two people maintain end to end. Its best fit is exactly the enterprise, multi-team scenario the pattern grew up solving in the first place, not a weekend project.

None of this is mutually exclusive in a real codebase. A layered backend routinely sits behind an MVVM-flavored frontend without any contradiction, because the two patterns answer different questions entirely. MVC, MVP, and MVVM describe how UI responsibilities are organized, while layered architecture describes how the overall system is divided. Most production systems mix more of these patterns than a single-pattern framing ever really suggests, whether that framing calls itself an MVC app or an MVVM app.

Choosing an Architecture

For a new team, the honest answer usually isn't "pick a pattern." It's "pick your framework's own idiom, and stop importing a foreign one wholesale."

Vue's idiom is ViewModel-shaped, and fighting that by forcing a Presenter-style manual sync layer on top of it mostly adds work Vue's reactivity system was built to do automatically. Angular's idiom is an explicit, evolving hybrid, and a modern Angular app leans on signals and dependency-injected services rather than picking a side of the MVC-versus-MVVM debate its own documentation has never fully settled. React resists being forced into MVVM's binding mental model, because its own render cycle is already one-way before any state-management library gets added.

Layered architecture is the one exception

Where should presentation, business logic, and data access responsibilities live, and who's allowed to call whom, is largely independent of which frontend framework a team picked. That's worth deciding deliberately regardless of whether the UI layer sitting on top leans MVC, MVVM, or something else entirely.

None of the three frameworks discussed here got MVC, MVP, or MVVM handed to them unchanged from an old academic whiteboard. Each inherited a problem those older patterns first named, such as arbitrating shared state across multiple views, keeping a screen testable, or synchronizing a display without writing glue code by hand. Each then built its own answer, shaped by what its underlying platform could do.

Modern frontend architecture has moved beyond MVC/MVVM comparisons into reactive state management, server/client boundaries, and unidirectional data flow. React Server Components render on the server and never become client-side state at all. Vue's server-rendering setup and Angular's SSR-with-hydration story do the same job through different mechanisms. A modern web application can mix both execution models rather than sitting entirely in one. Knowing whether a given piece of UI runs as server-rendered markup or as hydrated client state matters more in ordinary development work than picking a single architecture label for the whole app.
