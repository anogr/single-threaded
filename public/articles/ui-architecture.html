UI Architecture Patterns

How MVC, MVP, MVVM, and Layered Architecture shaped React, Vue, and Angular.

Andreas Ögren
~14 min read
Last updated July 2026

Every user interface connects application data to something a person can see and change. The difficult part is deciding what mediates between those sides. Model-View-Controller (MVC), Model-View-Presenter (MVP), and Model-View-ViewModel (MVVM) assign that responsibility differently.

The problem predates the web. Graphical interfaces have separated data, presentation, and input handling since the 1970s. Modern frameworks inherited those concerns, although their component and reactivity models no longer map neatly onto one historical pattern.

The article follows that lineage from MVC through MVP and MVVM, then separates those UI patterns from layered architecture. It closes by comparing their ideas with React, Vue, and Angular. The goal is to understand the responsibility boundaries, not to force each framework under one old label.

Origins of the Patterns

Each pattern reflects the capabilities and constraints of the UI platform around it.

Trygve Reenskaug developed MVC while visiting Xerox PARC in 1979. He was exploring how people could work with several views of one underlying model and keep those views coordinated as the model changed. An early note called the idea Thing-Model-View-Editor. Later that year, the name became Model-View-Controller.

MVC never acquired one universal definition. The Smalltalk-80 implementation evolved after Reenskaug left PARC, and its Controller emphasized input handling for a View. Later desktop and server frameworks reused the same names for related but different responsibility boundaries.

In the original GUI model, a View could read the Model directly and observe it for changes. That relationship was convenient, but it coupled display code to the Model's interface. MVP introduced a stricter mediator between them.

Model-View-Presenter emerged from Taligent in the 1990s and later appeared in Smalltalk and Microsoft UI guidance. The Presenter reads the Model and drives a passive View through an interface. That separation makes presentation logic testable without constructing the real UI.

MVP still requires explicit synchronization between Presenter and View. MVVM moved that work into a binding engine supplied by the platform.

Model-View-ViewModel developed inside Microsoft for data-binding platforms such as Windows Presentation Foundation. It adapts the earlier Presentation Model idea around declarative bindings. A ViewModel exposes state and commands, while the binding engine synchronizes those values with the View.

The progression is a change in mediation. MVC lets Views observe and read a shared Model. MVP routes View interaction through a Presenter. MVVM retains an intermediate presentation model but delegates much of the synchronization to declarative binding.

Layered architecture addresses a different scale. It separates responsibilities such as presentation, business logic, and data access across logical layers or deployment tiers. MVC and its descendants organize interaction within the UI. Layering controls dependencies across the wider application.

MVC: The Original Triad

The original GUI pattern separates domain state, presentation, and input handling.

The Model holds domain state and the rules that govern it without depending on presentation. The View reads the Model and renders a representation for the user. The Controller interprets input and translates it into operations on the Model.

The Observer pattern coordinates several Views of the same Model. The Model notifies dependents after a change, and each View reads the data it needs before redrawing. Views can therefore stay synchronized without polling or owning duplicate domain state.

Direct View-to-Model access became a pressure point for later patterns. A View can read more state than a notification concerns, and separate Views can interpret the same change differently. The relationship becomes harder to manage as Models grow and more Views observe them.

Server-side web frameworks use MVC terminology for a different lifecycle. A controller handles an HTTP request, obtains data, and selects a view that renders a response. The original Observer relationship does not persist after the response because the View is not a live object watching an in-memory Model. The names remain useful, but the runtime relationships differ from Smalltalk MVC.

Live updates use another channel

The web can still support live updates. WebSockets, Server-Sent Events, or a framework transport can push changes after the initial response. That channel is an additional mechanism rather than a property of the request-and-response MVC lifecycle.

MVP and MVVM did not undergo the same borrowing. Both patterns assume a live interface whose state remains available for ongoing synchronization. Server-rendered pages gained that lifecycle only after client-side JavaScript made the document behave more like an application.

MVP: Everything Through the Presenter

The Presenter mediates everything. The View never reads the Model, and nothing propagates automatically.

Model-View-Presenter redraws the boundary around a passive View. The View exposes events and display methods without reading the Model directly. The Presenter handles those events, reads or updates the Model, and tells the View what to display. Every interaction between Model and View passes through that mediator.

The boundary prevents the View from becoming coupled to the Model's interface. It also makes the Presenter responsible for every synchronization path. Displaying a new value, enabling a control, or reacting to a Model change requires explicit Presenter code.

A Presenter can depend on a View interface instead of a concrete UI. Tests can provide a fake View, trigger an input, and assert which display methods were called. That testability made MVP useful on platforms whose Views were otherwise expensive or awkward to instantiate.

MVVM: Declarative Binding Arrives

A ViewModel exposes state and commands. The View binds to them. The binding engine, not a developer, keeps both sides in sync.

Model-View-ViewModel keeps a three-part structure but changes the mediator's interface. The ViewModel exposes observable state and commands that the View can bind to. A binding engine propagates changes, reducing the explicit display calls that a Presenter would make.

The relationship is declarative. A label binds its text to a property, and a button binds its action to a command. The platform decides when to propagate updates. MVP expresses the corresponding work through imperative calls written in the Presenter.

MVVM depends on platform support for observing values and updating bindings. Modern frameworks implement reactivity through different mechanisms, including proxies, compiler transforms, change detection, and signals. Client State compares those propagation models. MVVM's architectural contribution is the declarative contract between View and ViewModel.

Layered Architecture: Tiers, Not Views

Three layers, one rule: a layer may only call the layer directly beneath it.

Layered architecture divides an application into horizontal responsibilities, commonly presentation, business logic, and data access. In a strict closed-layer design, each layer depends only on the one beneath it. Some systems use open layers that permit selected shortcuts, but those exceptions weaken the isolation the pattern is meant to provide.

Stable interfaces between layers contain change. Replacing a data-access implementation should not require presentation code to understand the new database. This protection differs from MVC, MVP, and MVVM, which organize interaction within the UI rather than dependencies across the whole system.

The layering that only exists in a diagram

A presentation component that imports a database client bypasses the business and data-access boundaries. The code may compile and work, but a later data migration must now inspect the UI layer as well. The shortcut expands the surface of future change.

This is also why a typical modern product still separates "the frontend," "an API layer," and "a database," even when a single framework nominally owns all three ends of that chain. The tiers are a decision about where responsibilities live, not about which repository or team happens to own the code that implements them.

Logical layers do not require top-level folders named after technical roles. A feature-based structure can keep checkout/ presentation and domain code near each other while preserving the dependency direction inside that feature. Folder organization answers which files change together. Layering answers which responsibilities may depend on which others.

React, Vue, and Angular

Modern component frameworks inherit parts of these patterns without implementing any one of them unchanged.

Vue: MVVM by Design

Vue combines declarative templates with reactive component state. Its design has often been explained through MVVM because a component exposes values and behavior that a template consumes.

The fundamental architectural unit is the component, which encapsulates a template together with the state and behavior that drive it. The template declaratively binds to that state and responds to user events. Components can maintain their own local state or consume shared state from composables or application-wide stores. Business logic, data access, and other cross-cutting concerns are typically factored into composables or dedicated state management libraries rather than embedded directly in components.

The template resembles a View, while the component's setup state and methods resemble a ViewModel. Composables and stores provide reusable logic or shared state, but neither automatically becomes the classical Model. The application still decides where domain rules and data access belong.

Vue's reactivity system is central to this model. Reactive objects, refs, and computed values automatically track dependencies as they are read. Components and templates that read reactive values automatically become dependent on them, allowing Vue to update only the parts of the UI affected by a state change instead of broadly re-rendering across the component tree.

counter.ts TypeScript 
import { ref, computed } from 'vue';

export function useCounter() {
  const count = ref(0);
  const doubled = computed(() => count.value * 2);

  function increment(): void {
    count.value++;
  }

  return {
    count,
    doubled,
    increment
  };
}

In this example, the composable encapsulates reusable reactive state and behavior. A component calls useCounter() and binds directly to the returned count and doubled values in its template. Because these are reactive values, Vue automatically tracks those dependencies and updates only the UI that consumes them when their values change.

Angular: An Explicit Hybrid

Angular combines declarative templates, components, dependency injection, and reactive primitives. MVVM is a useful analogy for the template-to-component relationship, but it does not describe the framework's full application architecture.

The fundamental architectural unit is the component, which encapsulates a template together with the presentation logic that drives it. Components obtain their dependencies through Angular's dependency injection system rather than constructing or locating them directly. Business logic, data access, shared application state, and other cross-cutting concerns are commonly encapsulated in injectable services, while templates declaratively bind to component properties and react to user events.

The template can be treated as the View and the component as its ViewModel-like mediator. Injectable services supply domain operations, repositories, API clients, or shared state. They are not one uniform Model layer, and Angular leaves their responsibility boundaries to the application.

Modern Angular further reinforces this reactive model through signals. A signal represents a reactive value, while computed signals derive values automatically from other signals. Components and templates that read a signal automatically become its dependents, allowing Angular to target change detection only at the affected components instead of broadly traversing the component tree.

counter.component.ts TypeScript 
@Injectable({ providedIn: 'root' })
export class CounterStore {
  readonly count = signal(0);
  readonly doubled = computed(() => this.count() * 2);

  increment(): void {
    this.count.update(n => n + 1);
  }
}

In this example, the service encapsulates reactive state and behavior that exposes signals. The component injects the store, and its template binds directly to the store's count and doubled signals. Because these are signals, Angular automatically tracks the dependency and refreshes only the UI that consumes them when their values change.

React: A Library, Not a Pattern

React renders component output from props and state through one-way data flow. It does not prescribe MVC or MVVM, and it leaves data access, domain logic, shared state, and routing to the application and surrounding libraries.

The fundamental architectural unit is the component, implemented as a function that returns a description of the UI. Components manage local state through hooks such as useState, derive values during rendering, and respond to user events by updating state. Shared state, business logic, data access, and other cross-cutting concerns are typically factored into custom hooks, context providers, or third-party libraries. React intentionally provides few architectural conventions beyond the component model itself.

Calling React “the View” understates what a component can contain. Components may combine rendering, local state, and event behavior, which overlaps with both View and ViewModel responsibilities. The surrounding architecture determines where domain and coordination logic sit.

React's rendering model is driven by state changes. When a component's state or props change, React re-executes that component to produce a new description of the UI. React then reconciles that result with the previous render and applies only the necessary changes to the DOM instead of replacing it wholesale.

useCounter.ts TypeScript 
import { useState } from 'react';

export function useCounter() {
  const [count, setCount] = useState(0);
  const doubled = count * 2;

  function increment(): void {
    setCount(n => n + 1);
  }

  return {
    count,
    doubled,
    increment
  };
}

In this example, the custom hook encapsulates reusable state and behavior. A component renders the returned count and doubled values and connects increment to a click handler. Calling setCount schedules a render, after which React commits the DOM changes required by the new output.

Unlike Angular and Vue, React intentionally stops at the component model and rendering engine, leaving higher-level architectural patterns to the surrounding ecosystem.

Comparing the Patterns

The interesting question was never which pattern is best. It's which problem each one solves, and whether a given application still has that problem.

MVC keeps the path from View to Model direct, which reduces mediation but increases coupling. MVP inserts an explicit Presenter and gains testable presentation logic at the cost of synchronization code. MVVM keeps the mediator while asking a binding engine to handle much of that synchronization.

Declarative binding removes repetitive display calls but moves propagation into the framework. Debugging then requires understanding dependency tracking and binding lifecycles. Explicit one-way updates expose more of that path in application code, although they may require additional plumbing.

Layering pays off when responsibilities change independently and stable interfaces can protect the rest of the system. It can become ceremony in a small application where one team changes every part together. The value comes from containing real change, not from reproducing a diagram.

These patterns can coexist because they operate at different scales. An MVVM-shaped UI may call a layered backend, and a React application may use Presenter-like objects for selected workflows. Production systems usually combine responsibility boundaries instead of adopting one label for the whole codebase.

Choosing an Architecture

Begin with the framework's data flow, then add boundaries for problems the application can name.

Vue and Angular already provide declarative bindings and reactive dependency tracking, so a manual Presenter layer should solve a specific testing or separation need. React begins with one-way rendering and adds coordination through components, hooks, and external stores. Importing another platform's pattern wholesale usually duplicates mechanisms the framework already supplies.

Layered architecture is the one exception

The dependency direction between presentation, business logic, and data access remains an application-level decision. It should be explicit regardless of which UI framework or historical pattern shapes the presentation layer.

React, Vue, and Angular inherited concerns that the older patterns made visible: shared state, testable presentation logic, and synchronization between data and display. Their answers are shaped by browser components, module systems, compilers, and reactive runtimes rather than by the original desktop implementations.

Architecture decisions now also include reactive state, server and client execution, hydration, and cache boundaries. Those mechanisms affect where code runs and how updates propagate. MVC, MVP, and MVVM remain useful vocabulary for responsibilities, but they are no longer complete descriptions of a web application.
