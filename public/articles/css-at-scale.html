CSS at Scale

How teams keep CSS maintainable as codebases, component counts, and contributor lists grow.

Andreas Ögren
~19 min read
Last updated July 2026

A small stylesheet rarely needs much architecture. Its authors can remember the selectors, understand their order, and see where a change will land. That shared context fades as components and contributors multiply. Eventually, changing one class can affect a screen its author has never opened. CSS architecture exists to make those effects predictable again.

These problems arise because selectors share a global namespace, rules compete in the cascade, and inheritance crosses component boundaries. The browser applies those rules to the document without knowing which component, file, or team owns them.

CSS architecture gives teams a way to make ownership and interactions explicit. This article explains how the main approaches create that predictability and compares their effects on developers, build tools, and browsers.

The Scaling Problem

Namespace sharing, the cascade, and inheritance are useful CSS mechanisms, but as the number of authors and rules grows, the same mechanisms make interactions harder to predict.

A selector in an ordinary document can match elements anywhere in that document. Several selectors may therefore match the same element and assign different values to the same property. The cascade resolves that conflict according to a defined order. If a descendant has no declaration for an inherited property, inheritance gives it the computed value from its parent even though the parent's selector does not match the descendant. As the number of rules and authors grows, tracing both direct matches and inherited values becomes harder.

The browser does not associate a class name with the component that introduced it. A class selector can match elements throughout the document, regardless of which file, team, or component it was written for. A .card class in a checkout component and a .card class in a marketing component are the same selector as far as the browser is concerned. A rule written for either .card can therefore style both components. Neither team necessarily knows the other one exists.

Collisions often lead to specificity escalation. Specificity is a weight calculated from a selector. An author whose rule loses may add another class or an ID to increase that weight. Marking a declaration !important changes its cascade importance rather than its specificity. The immediate problem disappears, but the next override must clear a higher bar. Over time, local fixes create a stylesheet whose effective priority is difficult to understand from any one file.

Removing a rule safely requires evidence that no page, viewport, or component state still depends on it. A declaration that loses in one context may still apply elsewhere. If tests do not exercise every dependent case, deletion remains risky, so unused CSS tends to remain.

The Pain Points

The available architectures can be compared in six dimensions.

The first three dimensions follow from how ordinary CSS rules share selector space and compete in the cascade. Names can collide, cascade priority can escalate, and interactions between matching rules can make removal harder to prove.

The remaining three dimensions describe concerns that do not follow directly from CSS's namespace or cascade. Style performance depends on selector matching and the elements affected when styles must be recalculated. Theme consistency depends on whether teams share and enforce a vocabulary of values. Build and tooling coupling depends on whether styling requires a build step or JavaScript runtime. The rest of the article compares each approach across all six dimensions.

DimensionWhat it looks likeWhat drives it
Global namespace collisions Two unrelated components pick the same class name, one silently overrides the other's styles after a merge. Ordinary class names are not locally scoped.
Specificity wars Overrides pile up as extra selector segments, then ID selectors, then !important, because class rules keep losing to higher-priority declarations. The cascade uses its defined priority order. It cannot infer which declaration an author meant to win.
Dead, unremovable CSS Stylesheets only grow. Nobody deletes a rule because nobody can prove another rule doesn't depend on it still being there. Whether a rule affects an element can depend on other rules that match the same element.
Selector and style performance Deeply nested selectors and oversized stylesheets can increase style-recalculation work, especially on large, frequently updated DOM trees. Selector matching cost depends on selector complexity and the affected elements.
Theming inconsistency Two teams both implement "the primary brand colour" with a slightly different value, because nothing enforces a single source of truth. Custom properties and design tokens remain conventions unless tooling enforces them.
Build/tooling coupling A style change requires a rebuild, or style generation adds client work as components render. Some architectures tie styling to the bundler or the JavaScript runtime.

All six dimensions affect how confidently a team can change CSS. A namespace collision may surface on a page that was never exercised during the original change. New contributors may have to discover the accumulated selector priority through trial and error. Uncertain ownership keeps dead rules in the bundle, while inconsistent tokens turn a visual change into a repository-wide search. Routine styling work slows as each change requires more investigation.

Architectures and Tools

CSS approaches act at different stages of the styling workflow, so they solve different parts of the scaling problem.

Some approaches tell developers how to name and order ordinary selectors. Others accept styling syntax that the browser does not understand and compile it to CSS, generate CSS from application code, or rewrite class names during the build. Browser features can also limit where selectors match without requiring generated names. The article groups these approaches into six families.

  • Methodologies provide conventions for naming selectors, organizing rules, and controlling source order.
  • Preprocessors add reusable syntax and compile it into ordinary CSS.
  • CSS-in-JS places style definitions in JavaScript or TypeScript and generates CSS during the build or while the application renders.
  • Utility-first CSS generates small classes that developers combine in markup.
  • Scoped and hashed CSS rewrites local selectors during the build to prevent class-name collisions.
  • Native component scoping uses CSS and DOM features implemented by the browser to limit selector reach.

Methodologies

Block, Element, Modifier (BEM) is a naming convention. A component gets a block name, its internal parts get block__element names, and variations get block--modifier names, all as flat, single-class selectors with no nesting. .card__title--highlighted is unambiguous about what it styles and carries a specificity of exactly one class, the same as every other BEM selector in the codebase.

card.html HTML 
<div class="card card--highlighted">
  <h3 class="card__title">Title</h3>
  <p class="card__body">…</p>
</div>

BEM relies on flat selectors. Rules written as single classes have equal specificity, so source order resolves conflicts without adding selector weight. The convention does not guarantee unique block names, remove unused rules, or enforce theme tokens. BEM makes class names easier to coordinate, but every class still lives in the document-wide namespace.

Scalable and Modular Architecture for CSS (SMACSS) and Object-Oriented CSS (OOCSS) add organizational rules. OOCSS separates reusable structure from visual skin. SMACSS groups rules into categories such as base, layout, module, state, and theme. Those categories change where developers place rules, but the browser still receives ordinary selectors in one shared cascade.

Inverted Triangle CSS (ITCSS) focuses on order. Generic, low-specificity rules appear first, followed by increasingly specific components, utilities, and overrides. Later rules therefore also tend to have higher specificity. Cascade layers can now encode that priority directly. ITCSS still helps a team decide which categories belong earlier or later.

BEM Specificity wars, plus lower collision risk through block-based names Enforced namespace isolation, dead CSS, theming Teams without a build step, or as naming discipline layered on top of any other approach
SMACSS / OOCSS Some organizational discipline through file structure Namespace collisions, specificity wars, performance Legacy codebases already organized this way

Preprocessors

CSS preprocessors transform an authoring language into CSS before the browser receives it. Sass and its SCSS syntax support compile-time variables, nesting, mixins, functions, and modules. The output still participates in the ordinary cascade, so Sass alone does not prevent namespace collisions or specificity escalation. Developers can reuse calculations, pass arguments to mixins, and split source code into modules before compiling it to CSS.

Native CSS now provides nesting and custom properties, so those features no longer require a preprocessor. Sass still provides compile-time functions, loops, mixins, and a mature module system. Existing Sass codebases can continue using those compile-time features. They still need separate naming or scoping rules because the browser receives ordinary CSS.

Less is another CSS preprocessor with different syntax. Less also compiles to ordinary CSS, so it has the same namespace and cascade limits as Sass.

Sass / SCSS Authoring ergonomics: variables, mixins, nesting, partial organization Namespace collisions, specificity wars, dead CSS, tooling coupling Existing Sass codebases, or projects needing compile-time functions, loops, or mixins
Less The same authoring category as Sass The same namespace, cascade, dead-CSS, and build-coupling gaps as Sass Legacy projects already using Less

CSS-in-JS

CSS-in-JS covers two different implementation strategies. Runtime libraries such as styled-components and Emotion evaluate style definitions and coordinate generated class names while the application renders. Build-time libraries, often called zero-runtime CSS-in-JS, extract CSS ahead of execution. Vanilla Extract, Panda CSS, StyleX, and Linaria use this strategy. The browser receives a static stylesheet while application code refers to generated class names.

The code for React Server Components is not sent to the browser. A runtime CSS-in-JS library therefore needs framework support to collect styles during server rendering and to manage styles when interactive components run in the browser. Extracted CSS avoids that coordination because the stylesheet exists before either server or client components render.

Build-time tools differ in what developers write and in the CSS they generate. Vanilla Extract emphasizes typed theme contracts and CSS authored from TypeScript. Panda CSS generates utilities and recipes from a token system. StyleX produces atomic CSS and is designed for large codebases. Linaria extracts styles written with CSS-in-JS syntax. All four produce static CSS before the application runs.

Some build-time tools give design-token names TypeScript types. Vanilla Extract and Panda CSS can make token names part of the TypeScript program, so an unknown token fails during development before it becomes a missing CSS value. Sass variables are checked while Sass compiles, but CSS custom-property references remain strings unless another tool validates them.

theme.css.ts TypeScript 
import { createTheme } from '@vanilla-extract/css';

export const [themeClass, vars] = createTheme({
  color: {
    brand: '#3a6ea5',
    text: '#1a1a1a',
  },
  space: {
    sm: '8px',
    md: '16px',
  },
});

// vars.color.brnad would fail to compile: no such token exists

A design system defines the values inside a theme contract, including type scales, spacing scales, and colors assigned to interface meanings.

Utility-First CSS

Utility-first CSS styles an element by combining classes that each control a small part of its appearance. Authors add these names to the HTML class attribute or the JSX className prop. A card might use class="flex items-center gap-4 rounded-lg border" without a separate .card rule.

Tailwind generates the stylesheet during the build. It reads HTML, JSX, and other source files as plain text and collects tokens that could be class names. If it recognizes p-4, it emits a .p-4 rule that sets padding. A utility such as p-8 is absent from the generated stylesheet when Tailwind does not find that name in the configured sources. Class names generally need to appear as complete tokens because the scanner does not evaluate JavaScript expressions.

Utility names refer to values in Tailwind's theme. For example, p-4 selects a step from the spacing scale, while a configured name such as bg-brand can refer to a project color. Prefixes add conditions to a utility. hover:bg-brand applies the background on hover, and a responsive prefix can place a utility inside a media query.

The shared vocabulary reduces the need for teams to invent local class names that might collide. Base utilities use single-class selectors, which keeps their specificity low, and source detection limits unused utility output. These benefits come from the generated stylesheet rather than from selector isolation. Global rules can still match the same elements.

The cost appears in the markup. A component can accumulate a long class list as it adds responsive changes, interaction states, and conditional styles. A reusable component or helper can keep repeated combinations in one place, but that component or helper then owns the class list and its variants.

Tachyons established many of the same functional-CSS ideas earlier. Projects that already use Tachyons can keep its functional classes. Tailwind offers the larger contemporary ecosystem and a more extensive variant system.

Tachyons Generated utility classes avoid local class collisions and keep selector specificity low Smaller vocabulary and ecosystem than Tailwind Existing functional-CSS codebases

Scoped & Hashed CSS

CSS Modules prevent local class-name collisions during the build. A stylesheet is written as ordinary CSS, one file per component. The build step rewrites every local class name into a generated name, so .card might become .Card_card__a3f9k before the browser sees it. The component references the original name through an imported object, styles.card, so authoring still looks like normal CSS while the page uses the generated selector.

Generated names prevent local class-name collisions. Two components can still make incompatible layout assumptions about shared markup, and global selectors can still match elements in either module. A global selector such as .page p can therefore override a paragraph inside a CSS Module according to the usual layer, specificity, and source-order rules.

CSS Modules solve local class-name collisions and encourage component-sized stylesheets. Flat selectors can also keep specificity manageable, although the format does not enforce that discipline. Theming still needs tokens, and unused CSS depends on what the build tool can eliminate. Authors write ordinary CSS while the build supplies generated local names.

Component compiler scoping keeps ordinary class names in component styles but rewrites the selectors and matching elements during compilation. Vue scoped styles add a component-specific attribute to both sides of the match. Svelte adds a class derived from the component styles. Application code continues to use the class names written in the component, so it needs no imported class-name mapping.

CSS Modules Class-name collisions between modules, via generated local names Theming, tooling coupling, specificity wars if authors nest deeply Component-per-file frameworks without a full CSS-in-JS or utility system
Component compiler scoping (Vue / Svelte) Most selector leakage across component boundaries, via generated attributes or classes Parent/child root exceptions, theming, build coupling, and specificity conflicts within a component Projects using a component compiler with scoped-style support

Native Component Scoping

Shadow DOM creates a selector boundary around a separate tree. @scope only limits where a group of selectors can match.

Shadow DOM attaches an isolated subtree with its own style scope to an element. Selectors inside the shadow root do not match elements outside it, and document selectors do not normally cross into the shadow tree. Inherited properties, including CSS custom properties, can still cross the host boundary. Design systems can use inherited custom properties as a deliberate channel for tokens while keeping ordinary selectors isolated.

@scope limits a group of selectors to a DOM subtree and can define a lower boundary where that scope stops. The feature reached Baseline newly available status in December 2025, so projects supporting older browser releases may still need a fallback. The elements remain in the document tree, and document styles can still match them.

card.css CSS 
@scope (.card) to (.card-actions) {
  .title { font-weight: 600; }
  .body  { color: var(--text-dim); }
}
/* .card-actions and anything inside it fall outside the scope */

Modern Trends

A project can extract component styles at build time, process the resulting CSS separately, and rely on browser features for layer order and selector scope.

Static extraction lets teams use CSS-in-JS authoring without generating styles at runtime. Some components in a server-first application never execute in the browser, so they cannot generate styles there at runtime. The extracted stylesheet exists before those components render. Applications may keep runtime libraries when existing components call styled-components or Emotion APIs, or when styles are calculated during rendering. The browser must then execute that styling code.

Site-wide stylesheets can define resets, tokens, typography, and shared utilities. Individual components can use CSS Modules, @scope, or static extraction for their own rules. The browser combines both sets of declarations in the same cascade.

The CSS generated by Sass, Tailwind, a CSS Modules build, or a CSS-in-JS extractor can pass through a final processor before deployment. Lightning CSS can rewrite newer syntax for selected browsers, add vendor prefixes, and minify the resulting stylesheet. PostCSS parses a CSS file and runs the plugins configured for that project. Autoprefixer, for example, adds vendor prefixes. Adding or replacing the final processor does not require developers to rewrite their SCSS, utility classes, or CSS Module files.

Cascade layers let authors declare priority groups that resolve before specificity within those groups. If the order is reset, base, utilities, components, and overrides, a normal rule in the later overrides layer can outrank a more specific rule in reset.

app.css CSS 
@layer reset, base, utilities, components, overrides;

@layer reset {
  #app button { all: unset; }
}

@layer overrides {
  button { color: var(--accent); }
  /* wins over the ID selector above because @layer overrides
     was declared later */
}

Layer order decides which named layer wins before the browser compares selector specificity. Specificity still matters between competing rules inside the same layer. The example and figure use normal declarations. Important declarations reverse the order of named layers, while normal declarations outside any layer outrank layered normal declarations.

Container queries let a component respond to its container size, while @scope limits selectors to a subtree. Neither feature requires JavaScript or generated class names. Build tools can still reject unknown token names, generate utility classes, extract CSS from TypeScript, or rewrite newer syntax for older browsers. A project can add a tool when it needs one of those checks or transformations.

Tradeoffs

Improving one dimension can leave another unchanged or add a cost elsewhere.

A naming convention becomes harder to enforce as more contributors add selectors. An application that renders HTML on the server and hydrates it in the browser needs runtime CSS-in-JS to produce compatible class names and style order in both places. A design system with typed token names can reject an unknown spacing or color token during development. Existing code determines how many stylesheets and components a migration must change.

A project can assign each problem to a separate technique. Cascade layers can order third-party and application CSS, CSS Modules can generate local class names, and custom properties can carry shared token values. If cascade layers already control priority, adding another ordering convention increases the rules contributors must learn without changing which declaration wins.

CombinationDimensions addressedDimensions left open
Tailwind + CSS Modules Namespace collisions and specificity wars, plus reduced unused Tailwind output and scoped component styles for anything too conditional for utility classes Theming still depends on convention rather than a typed contract, tooling coupling remains
Vanilla Extract or Panda CSS + @scope Generated names, typed tokens, static output, and bounded selectors Build coupling remains; older browsers may need a scoping fallback
Sass + cascade layers Authoring ergonomics (Sass), specificity wars (layer ordering resolving before specificity) Namespace collisions and dead CSS remain unaddressed by either half

Cascade layers define priority, @scope limits selector reach, and container queries provide component-level responsiveness. None of those browser features checks token names or generates a CSS file. TypeScript-based styling tools can reject unknown tokens, extractors can move component styles into static stylesheets, and CSS processors can rewrite syntax for older browsers.

Contributors should be able to identify which file owns a rule and which declaration will win. A team that values utility composition may prefer Tailwind. A typed design system may justify Vanilla Extract or Panda CSS. An established Sass codebase can adopt cascade layers without rewriting its SCSS. In every case, contributors need to know where a new rule belongs and how to override it without increasing selector weight.
