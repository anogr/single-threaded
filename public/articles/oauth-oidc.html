OAuth & OIDC

How OAuth's delegation model and OpenID Connect's identity layer fit together, and the architecture patterns that keep tokens out of the browser.

A field guide
~39 min read
Authentication & authorization flows
Updated June 2026

Before OAuth existed, an application that needed access to a user's data on another service had only one real option: ask for that user's password directly. A photo-printing service that wanted to read a user's photo library in Google Photos would collect the Google password itself, store it, and log in as the user whenever it needed access. That arrangement handed the requesting application everything the user's account could do, not just photo access, and left a password sitting in a third party's database. OAuth exists to remove that arrangement entirely. Instead of a password, the user grants a scoped, revocable token. That token proves the photo-printing app may perform a specific set of actions, and the app never sees the user's actual credentials. The user authenticates directly with Google, decides exactly what to share, and can revoke that access later without changing a password anywhere.

OAuth's design deliberately stops there. It hands out a token proving permission, but nothing in the specification says who that token belongs to. That gap turns into a real problem the moment a "sign in with Google" button needs to know the user's actual identity, not just a permission slip. OIDC fills that gap. It reuses OAuth's architecture, and adds one new artifact: a signed token asserting who just authenticated. OAuth answers what a client may do. OIDC answers who is doing it.

This article explains why each protocol exists, and how they work together to provide secure authentication and authorization. It also discusses common implementation mistakes, security best practices, and recent developments such as OAuth 2.1 and authorization for AI agents. It builds on the credential mechanics covered in the authentication fundamentals article.

Authorization vs Authentication

OAuth 2.0 is an authorization framework. It exists to answer the question "what is this app allowed to do on the user's behalf?" The original RFC never actually defines who the user is. Identity simply isn't OAuth's job.

OIDC was built specifically to close that gap. It layers authentication on top of OAuth's authorization mechanics and answers "who is this user?" by introducing a new artifact, the ID token.

History and Related Protocols

A little context on where these specifications came from, and what else occupies the same space.

OAuth has two major versions that are not compatible with each other. OAuth 1.0, published in 2007, is essentially obsolete today. OAuth 2.0, published in 2012, replaced it and is the version almost every modern integration means when it says "OAuth." OAuth 2.1 is a different kind of update. It is not a third incompatible protocol. Its own draft specification describes it as a consolidation of OAuth 2.0 plus the security extensions and best practices published in the years since. Nothing in OAuth 2.1 breaks compatibility with OAuth 2.0. It just makes certain optional practices mandatory and drops a couple of grants that turned out to be unsafe.

OAuth and OIDC aren't the only federation protocols in use. SAML (Security Assertion Markup Language) is an older, XML-based protocol that predates OAuth and solves browser login only, using a signed XML assertion instead of a JWT, with no real notion of API authorization. Corporate identity providers and enterprise B2B integrations still commonly speak SAML rather than OIDC, simply because it was already deployed first. It's common for a single application to support both: OIDC as the default for direct users, SAML as an integration path for enterprise customers whose identity team requires it.

Roles & Actors

Every OAuth conversation, no matter how complex, is really just four parties talking to each other in a fixed pattern.

Before any of the redirects and tokens make sense, it helps to fix the cast of characters firmly in mind, because the entire specification is written in terms of these four roles, and almost every security property in OAuth exists to keep one of them from impersonating or deceiving another.

Resource Owner
The User

The user who actually owns the protected data. The resource owner is the one who decides whether to grant or deny access. They authenticate directly with the authorization server, never with the client app.

Client
The Application

The application requesting access on the user's behalf. The client receives tokens once the user has granted access, but it is never supposed to see the user's credentials at any point.

Authorization Server
The Auth Server (IdP)

The system that authenticates the user, captures their consent, and issues tokens. In the identity world this is usually called an Identity Provider, or IdP. This is the component most teams choose to outsource rather than build, because getting it wrong is expensive.

Resource Server
The API

The server that actually hosts the protected data. Its only real job in this story is to accept an access token on incoming requests, validate it, and decide whether the scopes attached to that token permit the requested operation.

The same distinction, with names attached

Mapped onto these four roles, the distinction from the introduction becomes concrete. The user is the resource owner since they own the photos in Google Photos. The photo-printing app is the client that needs access to the photos. Google Identity is the authorization server and Google Photos is the resource server.

The resource owner grants the client a scoped token through the authorization server, and the client never sees a password. The resource server simply checks that token against the requested operation. Identity, when it matters, arrives separately through OIDC's ID token.

Client Types

Not all OAuth clients can be trusted equally. The spec splits them into two categories precisely so it can treat them differently.

The single question that determines which category a client falls into is simple: can this application keep a secret from the end user? A server-side app's code runs somewhere the user can never inspect, so it can hold a real secret. Anything running on the user's own device or in their own browser can always be decompiled, inspected, or read directly, so it cannot. This distinction matters as soon as a client tries to prove its identity when redeeming a token, covered below, so it's worth settling before looking at any of the flows themselves.

Confidential Client
Can keep a secret

Server-side apps where code runs in a trusted environment. Can safely store a client_secret or use private_key_jwt for stronger client authentication. Examples: Express, Django, Rails, Spring Boot apps.

Public Client
Cannot keep a secret

Code runs on the user's device, so anyone can inspect it. Cannot use a client secret, and instead relies on PKCE, a mechanism covered in its own section further down, to prove its identity without one. Examples: SPAs, React/Vue apps, mobile apps, CLIs. Today, AI agent runtimes on user devices also fall into this category.

Client secrets in frontend code

Embedding a client_secret in a JavaScript bundle doesn't keep it secret. Anyone can find it in DevTools. Public clients must use PKCE, and no client secret. For server-side clients, private_key_jwt is preferable to shared secrets wherever the auth server supports it. It's phishing-resistant and doesn't require secret rotation.

Tokens

Three tokens, three jobs. Confusing them is the single most common source of OAuth bugs.

If there's one mental model worth memorizing from this entire guide, it's this: the access token is for machines, the ID token is for the application, and the refresh token is for staying logged in quietly. Mixing these up (sending an ID token to an API, or treating an access token as proof of identity) is responsible for a surprising share of real-world OAuth bugs.

Access Token
API Credential

The credential attached to every API request, typically as Authorization: Bearer <token>. Intentionally short-lived, usually minutes to a couple of hours. It may be a JWT the resource server verifies locally, or an opaque string requiring an introspection call. Either way, its only job is proving the bearer has permission for a given set of scopes.

ID Token
Identity Proof (OIDC)

A JWT meant for the application itself to consume directly rather than forward anywhere. It carries claims about who just authenticated, and its presence is what turns a plain OAuth exchange into an OIDC login. Never send this to an API. That's the access token's job.

Refresh Token
Silent Re-auth

A long-lived credential (days, weeks, sometimes months) that the client exchanges for a fresh access token once the old one expires, without bothering the user to re-authenticate. Because it lives so much longer, it's also the most sensitive one to leak. It should never be sent to a resource server, and should never end up where JavaScript can read it.

Token Lifetimes (relative)

Lifetimes vary by provider, but the relative ordering below is close to universal. The shorter-lived a token is, the more freely it can be passed around. The longer-lived it is, the more carefully it needs to be guarded.

JWT vs Opaque Access Tokens

The OAuth spec never mandates an access token format. An access token can be a self-contained JWT that any resource server can verify using a public key, or it can be a short opaque string that only the authorization server knows how to interpret. Opaque tokens require a call to the introspection endpoint on every request. This is slower, but tokens can be instantly revoked. JWTs are faster to validate locally but can't be revoked before expiry unless a separate denylist is built. Many production systems use JWTs for access tokens precisely because local-validation speed matters at API scale, while accepting that revocation isn't instant.

Avoid decoding access tokens in client code

Even when an access token happens to be a JWT, treat it as opaque from the client's perspective. Its format and contents are a contract between the authorization server and the resource server, not something frontend code should depend on. Use the ID token for identity information instead.

Scopes

Scopes are how OAuth implements the principle of least privilege. They let a client ask for exactly what it needs, nothing more.

A scope is simply a string that names a unit of access. When the client sends the user to the authorization server, it lists the scopes it wants, and the consent screen is essentially a human-readable translation of that list. Once granted, the requested scopes get baked into the access token, and the resource server checks, on every request, that the token carries the scope required for that operation.

OIDC Standard Scopes

OIDC defines a small set of standard scopes so that identity providers don't all invent their own conventions for "give me the user's email." These are worth memorizing since they appear in nearly every integration:

openid
Turns a plain OAuth request into an OIDC request. Required to receive an ID token at all. Without it, only an access token is returned.
profile
Name, picture, website, locale, birthdate, and similar non-sensitive profile fields.
email
The user's email address along with whether it has been verified.
address
The user's physical mailing address, when the provider stores one.
phone
Phone number and its verification status.
offline_access
Requests a refresh token back, so the user doesn't need to log in again every time their access token expires.

Beyond these standard ones, real applications almost always define their own custom scopes shaped around their API, things like read:orders or admin:users. Designing good scopes is really an exercise in API design: think in terms of the operations a client should be allowed to perform on a resource.

Scopes are not a substitute for fine-grained authorization

Scopes describe what categories of action a token is allowed to attempt. They're a coarse-grained gate. They generally don't express "can this user edit this specific document." That kind of fine-grained, resource-level authorization is usually handled separately, inside the application's own logic, after the scope check has already passed.

Grant Types

A grant type is just a recipe: the specific sequence of requests a client follows to walk away with tokens.

OAuth defines several of these recipes because "getting a token" looks completely different depending on the kind of client being built. A web app with a logged-in human in front of it has very different constraints than a cron job with no user at all, or a smart TV with no keyboard. Picking the wrong grant type for the situation is one of the most common OAuth mistakes.

Recommended for most apps

Authorization Code + PKCE

This is the workhorse flow, and almost certainly the right one to reach for absent a specific reason not to. The user is redirected away to the authorization server, where they authenticate and consent, and is then redirected back carrying a short-lived authorization code rather than a token. That code is then traded for actual tokens through a separate, back-channel request that never touches the browser. PKCE sits alongside this exchange specifically to stop that authorization code from being usable by anyone other than the client that requested it, even if it gets intercepted along the way.

Use when: building a web app with a backend, a single-page app, or a mobile app: essentially any flow where a real human is sitting in front of a browser or device. In OAuth 2.1, PKCE is required for all authorization code flows regardless of client type.

Machine-to-machine

Client Credentials

There's no user anywhere in this flow. It's the client authenticating as itself, using its own client_id and client_secret (or a private key JWT), to get an access token that represents the application's own identity rather than any person's. It's the simplest grant in the spec: a single back-channel request, no redirect, no consent screen, no browser.

Use when: there are background jobs, microservices, or daemons that need to call an API with no user context attached. A nightly batch job pulling data from a partner API is the textbook case. Also heavily used by AI agents calling APIs on a pre-authorized basis.

// POST /token (back-channel)
grant_type=client_credentials
&client_id=my-service
&client_secret=••••••••
&scope=read:reports
Input-constrained devices

Device Authorization Grant

Designed for devices that have no convenient way to handle a browser redirect (smart TVs, CLI tools, or IoT devices with no keyboard). Instead of opening a browser on the device itself, it displays a short code and a URL. The user picks up their phone or laptop, visits that URL, types in the code, and authenticates there instead, while the original device quietly polls the token endpoint in the background until approval comes through.

Use when: building a CLI tool (this is exactly how gh auth login works), a smart TV app, or any other device without a practical way to render a full browser-based login screen. Increasingly also used for headless AI agent authorization.

Deprecated

Implicit Flow

This was OAuth's original answer for single-page apps, back before PKCE existed: rather than returning a code that gets exchanged for tokens, the authorization server returned the access token directly in the URL fragment, as in #access_token=.... It seemed reasonable at the time, but tokens sitting in a URL turn out to leak in all sorts of mundane ways: browser history, referrer headers sent to third-party scripts, and server access logs all end up holding a live credential.

Do not use: removed in OAuth 2.1

Use Authorization Code + PKCE for SPAs instead. It solves the same problem without exposing tokens in the URL. The implicit flow has been formally removed from the OAuth 2.1 specification.

Avoid

Resource Owner Password Credentials

In this grant, the client itself collects the user's username and password through its own form and sends them straight to the token endpoint. It quietly defeats the entire premise of OAuth, which is that the client app should never see the user's actual credentials. It also makes multi-factor authentication and social login effectively impossible to support.

Removed in OAuth 2.1

ROPC has been formally dropped from OAuth 2.1. The only legitimate use case left is a temporary bridge while migrating an existing system that already stores user passwords directly. For any new system, Authorization Code + PKCE is the right choice.

Endpoints

Every authorization server exposes the same small handful of URLs. These five cover enough to read any OAuth integration.

GET /authorize Authorization endpoint (browser redirect) ►

The endpoint where the browser flow begins. The client redirects the user here, the authorization server authenticates them and shows a consent screen, then redirects back to the client with an authorization code attached. This is the only endpoint that speaks directly to the user. Every other endpoint in OAuth is a back-channel machine-to-machine call.

  • response_typeAlways code for the authorization code flow.Required
  • client_idIdentifies the client application to the authorization server.Required
  • redirect_uriWhere to send the user back with the code. Must exactly match a pre-registered URI in OAuth 2.1.Required
  • scopeSpace-separated list of permissions the app is requesting. Include openid for OIDC.Required
  • stateA random value generated by the client, stored client-side, and verified on return. Defeats CSRF attacks against the login flow.Required
  • code_challengeThe SHA-256 hash of the PKCE code_verifier. Required in OAuth 2.1.Required
  • code_challenge_methodShould always be S256. Never use plain.Required
  • nonceOIDC-specific. A random value embedded in the returned ID token to prevent replay attacks.OIDC
  • request_uriPAR-specific. Replaces all other params with a reference to a pushed request object. See PAR section below.PAR
POST /token Token endpoint (back-channel fetch) ►

The endpoint where authorization codes get redeemed for actual tokens, and where refresh tokens get exchanged for new access tokens. Everything here happens as a direct server-to-server (or SPA-to-server) request, not a browser redirect, which is why this endpoint never exposes tokens in a URL. When DPoP is used, the JWT proof header is bound to this endpoint.

  • grant_typeOne of: authorization_code, refresh_token, client_credentials, or the device code URN.Required
  • codeThe authorization code from the /authorize callback. One use only. It expires in seconds.auth_code only
  • code_verifierThe PKCE secret generated before the redirect. The server hashes it and checks it against the stored challenge.PKCE required
  • redirect_uriMust exactly match the URI used in /authorize. Just a validation parameter, not a new redirect.Required
  • client_idThe application's identifier. Confidential clients authenticate here with a secret or private key JWT.Required
GET /.well-known/openid-configuration Discovery endpoint (auto-configuration) ►

OIDC's discovery endpoint. Returns a JSON document listing every endpoint, supported algorithm, scope, and capability of this authorization server. This is how a client library can talk to Google, Okta, and Keycloak with no provider-specific code. It just reads this document and configures itself. Every modern OIDC provider exposes this URL. Use it rather than hardcoding endpoint URLs in application config.

GET /.well-known/jwks.json JWKS endpoint (public keys for JWT verification) ►

The JSON Web Key Set endpoint. Returns the authorization server's current public keys in a standardized format. When a JWT is received, the client library fetches this document to find the right key, identified by the kid claim in the JWT header, and uses it to verify the signature. Most libraries cache this document and only re-fetch when they encounter an unknown key ID.

POST /revoke Revocation endpoint (back-channel fetch) ►

The counterpart to issuing tokens is being able to take them back. Call it with a refresh token (or, on some providers, an access token) when a user logs out, and the authorization server invalidates it immediately rather than waiting for it to expire naturally. This matters most for refresh tokens. A proper "log out everywhere" feature is really just a call to this endpoint.

GET /logout (end_session_endpoint) RP-initiated logout (browser redirect) ►

Revoking a token, above, only affects that token. It does nothing about the session the authorization server itself is still holding open, so a user who clicks "log out" in the app can often click "sign in" right after and land back inside without ever seeing a login screen. OIDC's RP-initiated logout endpoint closes that gap: redirecting the browser here ends the user's session at the authorization server, the same way /authorize started one. Its location is published as end_session_endpoint in the discovery document above, rather than assumed to always be /logout.

  • id_token_hintThe ID token issued at login. Tells the server which session to end without asking the user to re-authenticate first.Required
  • post_logout_redirect_uriWhere to send the browser once the session is cleared. Must exactly match a pre-registered URI, the same rule as redirect_uri.Recommended
  • client_idSometimes required alongside post_logout_redirect_uri so the server can confirm that redirect target belongs to this client.Provider-dependent
  • stateRound-tripped back on the post-logout redirect. Same purpose as state in /authorize.Optional

PKCE (Proof Key for Code Exchange)

A clever cryptographic handshake that turns a stealable authorization code into something useless to anyone but the client that requested it.

PKCE (pronounced "pixie") exists to solve a very specific problem: how to prove that whoever is redeeming an authorization code is the exact same client that originally requested it, when that client has no secret it can use to prove its identity? The trick is to generate a secret on the fly, for that one login attempt only, and only ever reveal it at the very last step.

1
Generate code_verifier

A cryptographically random 43–128 character string. Stays in the client. Never sent to the auth server directly.

↓
2
Hash it → code_challenge

code_challenge = BASE64URL(SHA256(code_verifier))
This hash is sent to the auth server in the /authorize request.

↓
3
Auth server stores the challenge

It ties the code_challenge to the authorization code it issues. The challenge is a commitment: the verifier can't be back-computed from it.

↓
4
Token exchange: send the verifier

POST to /token with code_verifier. The server hashes it and checks it matches the stored challenge. If not, the request is rejected.

Why this stops code theft

An attacker who intercepts the code in the redirect URL doesn't have the code_verifier. It was never in a URL. They'd need to break SHA-256 to derive it from the challenge. That's computationally infeasible.

While PKCE was originally specified as a mitigation for public clients, OAuth 2.1 requires it everywhere, even for confidential server-side clients that do have a client secret. It's cheap to implement and closes off an entire class of attack, so there's little reason not to use it universally.

Pushed Authorization Requests (PAR) 2026

PAR flips the authorization flow. Instead of stuffing everything in a URL, the parameters are pushed to the server first, and a reference comes back.

Pushed Authorization Requests address a subtle weakness in the standard authorization code flow: all authorization parameters travel in the browser's URL, where they can be logged, intercepted, or tampered with. PAR moves those parameters to a back-channel POST first.

1
Client POSTs parameters to /par

All authorization parameters (scope, redirect_uri, PKCE challenge, etc.) are sent as a back-channel POST, authenticated with client credentials. No browser involved yet.

↓
2
Server returns a request_uri

The server stores the parameters and returns a short-lived, one-time-use request_uri reference: an opaque token that stands in for the full parameter set.

↓
3
Browser redirect uses only the request_uri

The redirect to /authorize carries just client_id and request_uri. All the sensitive parameters are already safely stored on the server side.

Why PAR matters today

PAR is now mandatory in FAPI 2.0 (Financial-grade API) and strongly recommended as a general security best practice. It's also a prerequisite for Rich Authorization Requests (RAR), which allow structured authorization data (like specifying exactly which bank accounts a fintech app may access) rather than flat scope strings. For high-security or regulated applications, PAR is no longer optional.

State Parameter & CSRF

A single random string is all that stands between a login flow and a class of attack that links the wrong account to the wrong session.

The state parameter looks almost too simple to matter. It's just an opaque random value generated by the client, sent along with the authorization request, and checked against what comes back when the user returns. But that simple round trip is exactly what defeats a CSRF attack against the OAuth flow itself: it proves that the browser completing the login is the same browser that initiated it.

Attack without state

Without state, an attacker could trick a victim into completing an OAuth flow that logs them into the attacker's account, then steal their session actions (payment, data entry). Always verify state on every callback.

What OIDC Adds to OAuth

OIDC doesn't replace anything in OAuth. It's a small, deliberate set of additions layered on top.

Understanding OAuth's authorization code flow means essentially already understanding OIDC's login flow too. The redirects, the back-channel token exchange, PKCE, the state parameter, all of it carries over unchanged. What OIDC contributes is a handful of new, standardized pieces bolted onto that same foundation, all aimed at one goal: letting the client walk away knowing exactly who just logged in, in a way that's portable across providers. Including the openid scope in the authorization request is all it takes to opt into it.

ID Token
A JWT about the user

Returned alongside the access token. Contains who the user is: their subject identifier, email, name. The application reads this directly. It is not sent to APIs.

UserInfo Endpoint
Fetch more claims

An authenticated GET endpoint that returns user profile data. Useful when claims aren't in the ID token, or when fresher data than login time is needed.

Nonce
Replay protection

A random value sent in /authorize, embedded in the ID token. The application verifies it matches, which prevents an old token from being replayed.

Discovery
Auto-configuration

OIDC standardizes the /.well-known/openid-configuration endpoint so clients can auto-discover all endpoints and capabilities without hardcoding URLs.

It's this last point, standardization, that's arguably OIDC's biggest practical contribution. Plain OAuth leaves a lot of room for interpretation: providers were free to invent their own ways of representing user profile data. OIDC pins all of that down, which is exactly why a single OIDC client library can talk to Google, Microsoft, Okta, and a dozen other providers with barely any provider-specific code.

The three-part structure behind any JWT, header, payload, and signature, along with how the signature gets verified, is covered in the authentication fundamentals article. An ID token doesn't change any of that. It just guarantees a fixed set of identity claims will be present in the payload:

nonce
Replay protection value, checked against the nonce sent in /authorize.
at_hash
Hash of the access token, binding the ID token to a specific access token.
email_verified
Boolean flag from the email scope. The email claim shouldn't be trusted for authentication unless this is true.

UserInfo Endpoint

The ID token is a snapshot taken at login. Sometimes what's true right now matters more.

An OIDC endpoint that returns fresh profile data for the authenticated user. Call it with a Bearer access token that includes the openid scope. The ID token is a snapshot taken at login. If the user has since changed their display name or avatar, the UserInfo endpoint reflects the current state.

// Frontend or backend fetch (requires a valid access token)
const res = await fetch('https://auth.example.com/userinfo', {
  headers: { 'Authorization': `Bearer ${accessToken}` }
});
const user = await res.json();
// { sub, email, name, picture, ... }
ID token vs UserInfo

The ID token is a snapshot at login time. The UserInfo endpoint returns the current state. If the user's avatar is displayed and might change, call UserInfo. For simply establishing identity at login, the ID token is enough.

DPoP (Demonstrating Proof of Possession) 2026

DPoP makes a stolen bearer token useless.

DPoP solves a fundamental weakness of Bearer tokens: anyone who obtains a Bearer token can use it. DPoP cryptographically binds an access token to a specific private key held by the client, so even a captured token can't be replayed by an attacker who doesn't hold that key.

🔑
Client generates a key pair

An ephemeral public/private key pair is created by the client. The public key will be embedded in tokens. The private key never leaves the client.

📸
Client sends a DPoP proof JWT to /token

A short-lived JWT signed by the private key that proves the client holds the private key right now.

✅
Auth server binds the access token to the public key

The issued access token contains a thumbprint of the client's public key. The token is now "sender-constrained."

🔒
API verifies DPoP proof on every request

The client attaches both the access token and a fresh DPoP proof JWT to each API call. The resource server verifies the proof's signature matches the key thumbprint in the token. A stolen token without the private key is useless.

DPoP adoption today

DPoP is mandatory in FAPI 2.0 and supported by major identity providers. For most web apps, the BFF pattern achieves similar protection by keeping tokens off the browser entirely. For SPAs that must hold tokens client-side, DPoP is the strongest mitigation available.

A Common BFF Architecture

A secure pattern that ties together the session cookie, a server-side token store, and the API layer behind it.

Use a Backend for Frontend (BFF) where a server component handles the OAuth flow and stores tokens server-side. The browser only gets a session cookie. Tokens never touch the browser's storage, so the entire XSS token theft surface disappears. This is the strongly recommended architecture for any app that can support a server component.

A common BFF architecture starts with the browser that holds a single opaque session identifier in an HttpOnly, Secure cookie. It carries no claims of its own and is only a lookup key. The BFF, a server-side process the frontend talks to instead of the authorization server or the resource APIs directly, keeps a fast key-value store, typically Redis, mapping that session identifier to the access token, refresh token, and ID token issued for that session. Redis fits well here because it is shared across every BFF instance behind a load balancer, and its per-key expiry lines up naturally with token lifetimes.

The BFF also exposes its own endpoint, something like /bff/userinfo, for the frontend to read identity claims. Internally it either reads the cached ID token or calls the authorization server's UserInfo endpoint, and returns plain JSON to the browser. The browser never handles a JWT directly.

When the browser needs data from an API, it sends the session cookie to the BFF rather than to the API itself. The BFF looks up the session in Redis, discards the cookie, and attaches the corresponding access token to the request it forwards through the API gateway. Because that access token is a JWT, each microservice behind the gateway verifies the signature, expiry, audience, and scope locally using the public keys obtained from the authorization server's JWKS endpoint, without a network call back to the authorization server on every request. Only the BFF, at the edge, ever talks to the authorization server directly.

Access tokens are deliberately short-lived, so this exchange eventually fails. The BFF is the only component that notices.

1

Before forwarding a request, or after receiving a 401 from the resource server, the BFF notices the cached access token has expired.

Common Attacks & Mitigations

Most OAuth vulnerabilities aren't flaws in the specification. They're implementations that quietly skip a step the spec assumes will be done.

PKCE, state validation, careful token storage, and signature verification can all feel like ceremony when the goal is just a working login button. Each one exists because someone, somewhere, shipped a version without it and got burned.

ATTACK Authorization Code Interception ►

An attacker intercepts the code in the redirect URI (via referrer headers, browser history, or a malicious app registering the same custom URI scheme).

Mitigation: PKCE (+ PAR)

Full mechanism above: PKCE binds the code to a verifier the attacker never sees, and PAR removes the parameters from the browser URL entirely.

ATTACK CSRF / Open Redirect ►

Attacker initiates an OAuth flow and tricks the victim into completing it. This links the victim's identity to the attacker's account.

Mitigation: state parameter

Full mechanism and example code above: State Parameter & CSRF.

ATTACK Token Theft via XSS ►

A Cross-Site Scripting vulnerability lets an attacker run JavaScript that reads tokens from localStorage or sessionStorage and exfiltrates them.

Mitigation: HttpOnly cookies + BFF (+ DPoP)

If a token must live in the browser, DPoP sender-binds it so a stolen copy can't be replayed.

ATTACK JWT Algorithm Confusion (alg:none) ►

An attacker crafts a token with "alg":"none" and no signature. Naive verifiers that trust the alg header accept it as valid.

Mitigation: allowlist algorithms

Covered in full, alongside JWT's other common pitfalls, in the JWT Pitfalls section of the authentication fundamentals article: never let the token's own alg header decide how it gets verified, and reject none always.

ATTACK Open Redirect via redirect_uri ►

If an authorization server validates redirect_uri loosely (only checking that it starts with the right domain), an attacker can register a lookalike path and redirect a freshly issued authorization code to an attacker-controlled endpoint.

Mitigation: exact-match redirect URI allowlists

Authorization servers must require the redirect_uri sent at login to exactly match one pre-registered for that client. No wildcards, no prefix matching. This is now mandatory in OAuth 2.1.

ATTACK ID Token Replay Without a Nonce ►

Without a nonce, a previously issued, still-unexpired ID token could be captured and replayed by an attacker to impersonate a login session.

Mitigation: nonce verification

Generate a fresh, random nonce for every authorization request, store it client-side, and verify the value embedded in the returned ID token matches it exactly before trusting the token. See nonce under What OIDC Adds.

ATTACK Mix-Up Attack (multi-IdP) ►

In a multi-IdP setup, an attacker tricks the client into sending an authorization code issued by a legitimate IdP to a malicious IdP's token endpoint, or vice versa.

Mitigation: iss parameter + PAR

An iss parameter in the authorization response lets clients verify which server issued the response. PAR also significantly reduces this risk by tying the request to a specific server before the redirect happens.

Refresh Tokens & Rotation

The mechanism that lets users stay logged in for weeks without re-typing a password, and the part that needs the most careful handling.

Refresh tokens solve a real tension in the design of short-lived access tokens: access tokens need to expire quickly so a leaked one does limited damage, but users shouldn't have to re-authenticate every hour either. A refresh token is the answer: a long-lived credential that, kept safely on the server, can be silently traded for a brand-new access token whenever the old one runs out, with the user never noticing.

Refresh Token Rotation
Single-use refresh tokens

Each time a refresh token is used, a new one is issued and the old one invalidated. If a stolen token is used, the legitimate user's next refresh fails. That failure is what signals the theft. Required in OAuth 2.1 for public clients.

Refresh Token Families
Reuse detection

Servers track "families" of rotated tokens. If an already-used token is presented (indicating theft), the entire family is revoked, which logs out all devices for that user. This turns detection into containment.

Refresh token storage

Refresh tokens are as sensitive as passwords. Store them server-side only (database or encrypted store). Never in localStorage, never in the browser. Treat exposure of a refresh token as equivalent to account compromise.

OAuth 2.1: What's New 2026

OAuth 2.1 is not a new protocol. It's a curated consolidation of a decade of security best practices into a single, tighter document.

OAuth 2.1 folds the most important security best practices and several extensions into one coherent specification. This removes the footguns that experience has shown developers tend to stumble into. As of today the specification is still an IETF draft rather than a published RFC, but its requirements are already stable and widely implemented by major authorization servers, so treating it as the current baseline is safe in practice. An implementation that already follows current best practices is probably already compliant with 2.1. The key changes are:

PKCE: Mandatory
Required for all auth code flows

Previously PKCE was specifically recommended for public clients. In OAuth 2.1 it's required for every client using the authorization code grant, confidential clients included. PKCE is now table stakes.

Implicit & ROPC: Removed
Two grants eliminated

The implicit flow and Resource Owner Password Credentials grant are no longer part of the specification. Code that still uses them is a clear signal the implementation needs updating.

Redirect URI
Exact-match only

OAuth 2.1 mandates exact-match redirect URI comparison: no wildcards, no prefix matching. This closes off a class of authorization code redirect attacks that loose matching enabled.

Refresh Token Rotation
Default, not optional

Refresh token rotation is now the expected default for public clients. Sender-constrained refresh tokens (tied to a specific client via DPoP or mTLS) are the recommended approach for confidential clients.

Agentic & AI Authorization 2026

When an AI agent acts on a user's behalf (booking flights, sending emails, querying databases) the authorization model gets more complex.

AI agents and LLM-based assistants are a real authorization use case that existing OAuth flows weren't quite designed for. The core challenge: a user delegates authority to an agent, and that agent may need to call many APIs, run for a long time, spawn sub-agents, or operate without the user being present at all. Standard OAuth handles the initial delegation well, but the devil is in the details.

Delegation Problem
Who is acting: user or agent?

When an agent calls an API, the API needs to know both who authorized the action (the user) and which agent is acting. Token Exchange is a grant type, sent to the same /token endpoint as any other, that lets a client trade one token for another rather than starting a fresh login. Alongside the token being exchanged, it can name a separate actor_token identifying the agent, so the token that comes back chains both identities and creates an auditable delegation trail.

Scope Minimization
Least privilege for agents

Agents should receive narrow, task-scoped tokens rather than broad user-level access. Rich Authorization Requests allow structured, resource-specific authorization data, e.g. "access only this Google Doc" rather than "access all Drive files."

Long-lived Sessions
Agents that outlive a login session

An agent running an hours-long task needs refresh tokens with rotation that is actually enforced. Consider time-boxing agent authority: issue tokens with a max lifetime matching the expected task duration rather than allowing indefinite access.

Human in the Loop
Step-up auth for sensitive actions

Even a pre-authorized agent should trigger step-up authentication for high-impact actions (sending money, deleting data). OIDC's max_age and acr parameters let resource servers demand fresh user authentication when the stakes are high.

Watch out: token laundering via agents

When an agent framework accepts tokens as inputs and passes them to other services, the chain needs careful validation. An attacker-controlled agent could present a legitimate user token to escalate privileges. Always verify iss, aud, and scope at every hop, and consider mTLS or DPoP binding throughout the chain.

FAPI & High-Security Profiles 2026

FAPI 2.0 is what OAuth looks like when the stakes are high enough that every optional best practice becomes mandatory.

The Financial-grade API Security Profile (FAPI 2.0), published by the OpenID Foundation, takes the OAuth security best practices and turns them into a strict, auditable profile. It was designed for open banking but is increasingly adopted for any regulated API, including healthcare, government, and payments. Building to this profile means using all of the following:

PAR
Pushed Authorization Requests: mandatory. All authorization parameters travel back-channel.
DPoP or mTLS
Sender-constrained tokens: mandatory. Plain Bearer tokens are not permitted.
RAR
Rich Authorization Requests for structured, resource-specific access data.
private_key_jwt
Client authentication via signed JWTs rather than shared secrets.
PKCE S256
Mandatory for all authorization code flows. plain is not acceptable.
Exact redirect URIs
Pre-registered, exact-match. No wildcards, no prefix matching, no exceptions.
Should I care about FAPI if I'm not in fintech?

FAPI 2.0 is a useful benchmark even outside regulated APIs. Its requirements represent a curated list of the most impactful security controls. Think of it as a security checklist rather than a compliance obligation. The components most worth adopting broadly are PAR (removes parameters from browser URLs), DPoP (stops token replay), and private_key_jwt (eliminates shared secret management).

That's the shape of OAuth and OIDC: four roles, three tokens, one well-trodden flow, and a growing stack of security enhancements (PKCE, state, nonce, rotation, DPoP, PAR), each closing a specific, real attack. Most libraries handle these mechanics automatically, but knowing what they're doing is what makes it possible to debug a broken integration, audit an existing implementation, authorize an AI agent safely, or make an informed call the day a library doesn't quite fit the situation. For implementation specifics, the auth provider's SDK documentation and the OAuth 2.1 draft spec are the two references worth keeping close.
