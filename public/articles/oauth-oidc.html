OAuth & OIDC

How OAuth's delegation model and OpenID Connect's identity layer fit together, and the architecture patterns that keep tokens out of the browser.

Andreas Ögren
~31 min read
Last updated July 2026

Delegated access once meant giving a third-party application the user's password. A photo-printing service that needed a Google Photos library might have stored the Google credentials and signed in as the user. The service then gained the full authority of that account, while another database acquired a reusable password.

OAuth replaces that arrangement with scoped tokens. The user authenticates with the service that owns the data and authorizes a defined set of actions. The client receives a credential for that delegated access, never the user's password, and the grant can be withdrawn independently.

OAuth defines delegated authorization, not a login protocol. An access token tells an API which authority was granted, but a client should not treat that token as proof of the user's identity. OpenID Connect (OIDC) adds authentication to the same flow through a signed ID token and standardized identity claims.

The protocol becomes easier to follow once its roles and token boundaries are clear. The sections below establish those foundations before explaining the authorization code flow, browser architectures, common attacks, and higher-security profiles. The credential mechanics come from the authentication article.

Authorization vs Authentication

OAuth 2.0 is an authorization framework. It answers the question "what is this app allowed to do?" The protocol does not give the client an authenticated user identity.

OIDC adds authentication to OAuth's authorization flow. Its ID token tells the client which user authenticated and supplies the claims needed to validate that assertion.

History and Related Protocols

A little context on where these specifications came from, and what else occupies the same space.

OAuth 1.0 and OAuth 2.0 are incompatible protocols, and new integrations generally use OAuth 2.0. OAuth 2.1 takes a different approach to versioning. The active Internet-Draft consolidates OAuth 2.0 with later security guidance, requires protections such as PKCE, and omits the implicit and resource owner password credentials grants. An OAuth 2.0 deployment that already follows the current security best practice may need little or no protocol-level change.

OAuth and OIDC are not the only federation protocols in use. Security Assertion Markup Language (SAML) is an XML-based framework commonly used for enterprise single sign-on. Its browser profiles exchange signed assertions rather than OIDC ID tokens. Applications often support OIDC for newer integrations and SAML for organizations whose identity infrastructure already depends on it.

Roles & Actors

OAuth assigns four roles so that delegated authority can cross system boundaries without giving the client the user's credentials.

OAuth defines four roles. One deployment may assign several roles to the same system, but the boundaries still matter because each role receives different credentials and makes different decisions.

Resource Owner
The User

The entity that can grant access to a protected resource. In an interactive flow this is usually the end user, who authenticates through the authorization server rather than giving a password to the client.

Client
The Application

The application requesting access. In the authorization code flow it receives tokens after authorization without collecting the user's password.

Authorization Server
The Authorization Server

The system that issues tokens after obtaining authorization and, in user-facing flows, authenticating the user. When it also implements OIDC, it acts as an OpenID Provider for identity.

Resource Server
The API

The server hosting the protected resource. It validates the access token and enforces the token's audience, granted authority, and the application's own resource-level authorization rules.

The same distinction, with names attached

Mapped onto these four roles, the distinction from the introduction becomes concrete. The user is the resource owner since they own the photos in Google Photos. The photo-printing app is the client that needs access to the photos. Google Identity is the authorization server and Google Photos is the resource server.

The resource owner grants the client a scoped token through the authorization server, and the client never sees a password. The resource server checks that token against the requested operation. Identity, when it matters, arrives separately through OIDC's ID token.

Client Types

Not all OAuth clients can be trusted equally. The spec splits them into two categories precisely so it can treat them differently.

Client type depends on whether the deployment can protect credentials issued to that client. A server-side application can keep a secret or private key in an environment controlled by its operator. Code distributed to a browser or user device cannot preserve a shared secret because the user or an attacker can inspect the package. This distinction determines which client-authentication and token-protection options are meaningful.

Confidential Client
Can keep a secret

Server-side applications whose credentials run in an operator-controlled environment. They can authenticate with a protected shared secret, a private key, or another supported method.

Public Client
Cannot keep a secret

Code is distributed to an environment the client operator does not fully control, so an embedded shared secret cannot authenticate an installation. Browser applications, native applications, command-line tools, and locally installed agent runtimes commonly fall into this category. PKCE protects the authorization code exchange without pretending the application can keep a fixed secret.

Client secrets in frontend code

A client_secret embedded in a JavaScript bundle is public information, regardless of its name. Browser clients should use the authorization code flow with PKCE and must not rely on that value for authentication. Confidential clients can use a shared secret or an asymmetric method such as private_key_jwt; the latter avoids distributing the same secret to both parties, but its signing keys still require protection and rotation.

Tokens

Access, ID, and refresh tokens travel through the same flow, but each has a different recipient and purpose.

The resource server consumes the access token. The client consumes the ID token to complete an OIDC login, while the authorization server accepts the refresh token when the client needs new credentials. An ID token is not an API credential, and an access token is not a general-purpose identity assertion for the client.

Access Token
API Credential

The client presents this credential to a resource server, commonly as Authorization: Bearer <token>. It may be a JWT validated locally or an opaque value checked through introspection. Its lifetime, audience, and authority should be limited to the API's needs.

ID Token
Identity Proof (OIDC)

A signed JWT whose audience is the client. It carries claims about the authentication event and subject. The client validates it and does not forward it as an API credential.

Refresh Token
Silent Re-auth

The client exchanges this credential at the token endpoint to obtain new tokens without repeating the interactive authorization flow. It often outlives an access token and therefore needs stronger storage, rotation, or sender constraint. A refresh token is never an API credential.

Token Lifetimes (relative)

Providers choose lifetimes according to their threat model and session policy. The bars show a common relative pattern rather than prescribed values. A short lifetime limits replay after theft; it does not make a token safe to expose or pass to an unintended recipient.

JWT vs Opaque Access Tokens

OAuth does not mandate an access-token format. A resource server may validate a self-contained JWT locally. It may instead resolve an opaque value through token introspection or a local cache. Introspection makes current token state available to the resource server, while local JWT validation avoids an online check. Neither choice guarantees instant revocation because caching and distributed state affect how quickly a change reaches every recipient.

Avoid decoding access tokens in client code

Even when an access token happens to be a JWT, treat it as opaque from the client's perspective. Its format and contents are a contract between the authorization server and the resource server, not something frontend code should depend on. Use the ID token for identity information instead.

Scopes

Scopes are how OAuth implements the principle of least privilege. They let a client ask for exactly what it needs, nothing more.

A scope is a string that names a unit of access. The client can request scopes, and the authorization server decides which subset to grant. The resulting authority is associated with the access token. A JWT may carry that information in a claim, while an opaque token keeps it in server-side state. The resource server then checks the granted scope alongside its own authorization rules.

OIDC Standard Scopes

OIDC defines a small set of standard scopes for requesting groups of identity claims. Providers may support or release only a subset of the optional claims.

openid
Turns a plain OAuth request into an OIDC request. Required to receive an ID token at all. Without it, only an access token is returned.
profile
Name, picture, website, locale, birthdate, and similar non-sensitive profile fields.
email
The user's email address along with whether it has been verified.
address
The user's physical mailing address, when the provider stores one.
phone
Phone number and its verification status.
offline_access
Requests access that can continue while the user is absent, normally through a refresh token. OIDC requires consent handling, and the provider can still decline the request.

APIs commonly define custom scopes such as read:orders. Scope design should follow the operations a client needs rather than mirror every user role or database permission.

Scopes are not a substitute for fine-grained authorization

Scopes describe what categories of action a token is allowed to attempt. They're a coarse-grained gate. They generally don't express "can this user edit this specific document." That kind of fine-grained, resource-level authorization is usually handled separately, inside the application's own logic, after the scope check has already passed.

Grant Types

A grant type is a recipe: the specific sequence of requests a client follows to walk away with tokens.

A grant is the credential or method a client uses to obtain an access token. Interactive applications, unattended services, and input-constrained devices have different security constraints, so they use different grants.

Recommended for most apps

Authorization Code + PKCE

The user agent visits the authorization server, where the user authenticates and authorizes access. The redirect back carries a short-lived authorization code. The client exchanges that code at the token endpoint, and PKCE binds the code to the client instance that started the flow.

Use when: a web, browser-based, or native application needs authorization from a person. The active OAuth 2.1 draft requires PKCE for authorization code flows, while the published security best practice requires it for public clients and recommends it for confidential clients.

Machine-to-machine

Client Credentials

There's no user anywhere in this flow. It's the client authenticating as itself, using its own client_id and client_secret (or a private key JWT), to get an access token that represents the application's own identity rather than any person's. It's the simplest grant in the spec: a single back-channel request, no redirect, no consent screen, no browser.

Use when: there are background jobs, microservices, or daemons that need to call an API with no user context attached. A nightly batch job pulling data from a partner API is the textbook case. Also heavily used by AI agents calling APIs on a pre-authorized basis.

// POST /token (back-channel)
grant_type=client_credentials
&client_id=my-service
&client_secret=••••••••
&scope=read:reports
Input-constrained devices

Device Authorization Grant

Designed for devices that have no convenient way to handle a browser redirect (smart TVs, CLI tools, or IoT devices with no keyboard). Instead of opening a browser on the device itself, it displays a short code and a URL. The user picks up their phone or laptop, visits that URL, types in the code, and authenticates there instead, while the original device quietly polls the token endpoint in the background until approval comes through.

Use when: a command-line tool, television, or similar device cannot receive a normal browser redirect. The device displays a verification URI and code while polling at the interval instructed by the authorization server.

Deprecated

Implicit Flow

The implicit grant returns an access token in the redirect URI fragment instead of returning a code for a token-endpoint exchange. Fragments are not sent in HTTP requests, but browser history, page scripts, extensions, and redirect handling can still expose the token. The flow also lacks the code exchange where PKCE and sender-constrained token issuance can add protection.

Do not use: removed in OAuth 2.1

Use Authorization Code with PKCE for browser applications. RFC 9700 deprecates the implicit grant, and the active OAuth 2.1 draft omits it.

Avoid

Resource Owner Password Credentials

In this grant, the client collects the user's password and sends it to the token endpoint. That expands the places where the password can be exposed and does not fit authentication that requires redirects, multiple steps, or modern phishing-resistant credentials.

Removed in OAuth 2.1

RFC 9700 says this grant must not be used, and the active OAuth 2.1 draft omits it. Migrate existing deployments to a flow where the authorization server, rather than the client, handles user authentication.

The endpoint roles are stable, while their URLs and optional capabilities come from provider metadata.

GET /.well-known/openid-configuration Discovery endpoint (auto-configuration) ►

OIDC discovery returns provider metadata such as endpoint locations, issuer identity, supported response types, and key-set location. A conforming client uses this document to configure protocol behavior instead of guessing endpoint paths. Deployment-specific policy can still require provider configuration outside the discovery document.

GET /.well-known/jwks.json JWKS endpoint (public keys for JWT verification) ►

The JSON Web Key Set endpoint publishes verification keys in a standardized format. A JWT header can carry a kid parameter that helps a verifier select a key. Clients should use library-managed caching and key rotation while still applying issuer, audience, algorithm, and claim validation.

POST /revoke Revocation endpoint (back-channel fetch) ►

The revocation endpoint lets a client ask the authorization server to invalidate an access or refresh token. Revoking a refresh token can stop that client from minting more access tokens, but already issued access tokens may remain usable until their recipients observe revocation or the tokens expire. A complete account-wide logout also requires the provider's session and grant-management behavior.

GET /logout (end_session_endpoint) RP-initiated logout (browser redirect) ►

Revoking a token affects that token or its associated grant. It does not necessarily end the session at the authorization server. The user may therefore sign in again without seeing a login screen.

OIDC's relying-party-initiated logout endpoint lets the client ask the provider to end that session. Providers publish its location as end_session_endpoint in discovery metadata, so clients must not assume the path is always /logout.

PKCE (Proof Key for Code Exchange)

A cryptographic handshake that turns a stealable authorization code into something useless to anyone but the client that requested it.

Proof Key for Code Exchange (PKCE, pronounced "pixie") binds an authorization code to the client instance that started the request. The client creates a high-entropy verifier for one authorization transaction and sends only a derived challenge in the front channel.

1
Generate code_verifier

A high-entropy 43–128 character string. It stays with the client during the browser redirect and is sent later to the token endpoint.

↓
2
Hash it → code_challenge

code_challenge = BASE64URL(SHA256(code_verifier))
This hash is sent to the auth server in the /authorize request.

↓
3
Auth server stores the challenge

It ties the code_challenge to the authorization code it issues. The challenge is a commitment: the verifier can't be back-computed from it.

↓
4
Token exchange: send the verifier

POST to /token with code_verifier. The server hashes it and checks it matches the stored challenge. If not, the request is rejected.

Why this stops code theft

An attacker who intercepts the code in the redirect URL doesn't have the code_verifier. It was never in a URL. They'd need to break SHA-256 to derive it from the challenge. That's computationally infeasible.

PKCE was introduced for public clients. RFC 9700 now requires it for public clients and recommends it for confidential clients. The active OAuth 2.1 draft goes further by requiring it for authorization code flows except for narrowly defined alternatives.

State Parameter & CSRF

The client must bind each authorization response to the browser transaction that started it.

The state parameter carries opaque client state through the redirect. When it is an unpredictable, one-time value securely bound to the user agent, it can also protect the redirect endpoint from CSRF. The client must compare the returned value with the transaction it started and reject a mismatch.

Attack without state

A client needs a CSRF defense on every authorization response. A securely bound state value is the general mechanism. Under the conditions defined by current security guidance, PKCE or a validated OIDC nonce can provide that binding instead. If state is sent, it must be verified.

What OIDC Adds to OAuth

OIDC adds an identity layer to an OAuth authorization flow.

An OIDC authorization request includes the openid scope. The token response then includes an ID token that the client validates as evidence of the authentication event. Discovery metadata and standardized claims let one protocol library work across conforming providers, although provider policy and optional features still vary.

ID Token
A JWT for the client

Contains the stable subject identifier and claims about the authentication event. Profile claims such as name or email appear only when requested and released by the provider.

UserInfo Endpoint
Fetch more claims

A protected endpoint that returns claims about the authenticated subject. Providers decide which requested claims to release and how quickly profile changes appear.

Nonce
Replay protection

A per-transaction value sent in the authentication request. If used, the client requires the same value in the ID token and checks it during validation.

Discovery
Auto-configuration

OIDC standardizes provider metadata at /.well-known/openid-configuration, including the issuer, endpoint locations, keys, and advertised capabilities.

The issuer and subject claims together identify the user within the provider's namespace. Applications should key accounts on that pair rather than on an email address, which can change or be reassigned.

The authentication article owns JWT structure and general validation. OIDC then adds profile-specific rules:

iss · sub · aud
The client requires the expected issuer, a locally unique subject for that issuer, and its own client identifier in the audience.
exp · iat
The expiry is enforced. Issued-at time supports freshness checks according to the client's policy.
conditional claims
nonce is required when requested. at_hash depends on the flow, while email and other profile claims depend on scopes and provider release policy.

UserInfo Endpoint

A protected endpoint for standardized claims about the authenticated subject.

Call UserInfo with an access token issued for that endpoint. The response must include the same sub value as the ID token. It can provide claims omitted from the ID token, but the specification does not promise that profile changes appear immediately.

userinfo.ts TS 
// Requires an access token issued for UserInfo
const res = await fetch('https://auth.example.com/userinfo', {
  headers: { 'Authorization': `Bearer ${accessToken}` },
})
const user = await res.json()
ID token vs UserInfo

Use the validated ID token to establish the login subject. Use UserInfo when the application needs claims the provider exposes through that endpoint. Treat provider-specific freshness and caching as deployment behavior rather than a protocol guarantee.

A Common BFF Architecture

A server-side OAuth client keeps tokens away from browser storage and proxies API calls.

A Backend for Frontend (BFF) can act as the confidential OAuth client for a browser application. It handles the authorization response, stores tokens on the server, and gives the browser a session cookie. An XSS payload can still perform actions through the user's session, but it cannot read an access or refresh token that never enters the browser.

The browser holds an opaque session identifier in an HttpOnly, Secure cookie with an appropriate SameSite policy. The BFF maps that identifier to protected server-side state containing the OAuth grant and tokens. A distributed deployment needs a shared or consistently routed session store, but the storage technology is an implementation choice.

The BFF can expose a session-information endpoint for the frontend. It returns only the identity and session fields the UI needs, derived from validated server-side state or the provider's UserInfo endpoint. The browser does not need to parse protocol tokens.

For an API call, the browser sends its session cookie to the BFF. The BFF applies CSRF protection, resolves the session, and forwards the request with the access token intended for the resource server. The API validates that token according to its format and profile. An optional API gateway may sit on that path, but it does not replace authorization inside the resource service.

When an access token expires, the BFF can use a refresh token if the authorization server issued one and the grant is still active.

Common Attacks & Mitigations

Most OAuth vulnerabilities aren't flaws in the specification. They're implementations that quietly skip a step the spec assumes will be done.

PKCE, request correlation, careful token storage, and token validation address different boundaries in the flow. Removing one does not make the others compensate for it.

ATTACK Authorization Code Interception ►

An attacker intercepts the code in the redirect URI (via referrer headers, browser history, or a malicious app registering the same custom URI scheme).

Mitigation: PKCE

PKCE makes an intercepted code unusable without the verifier held by the client instance that began the transaction.

ATTACK CSRF / Open Redirect ►

Attacker initiates an OAuth flow and tricks the victim into completing it. This links the victim's identity to the attacker's account.

Mitigation: state parameter

Full mechanism and example code above: State Parameter & CSRF.

ATTACK Token Theft via XSS ►

A Cross-Site Scripting vulnerability lets an attacker run JavaScript that reads tokens from localStorage or sessionStorage and exfiltrates them.

Mitigation: keep tokens server-side

A BFF prevents direct extraction of OAuth tokens from browser storage. DPoP can limit replay of a copied token, but malicious code running inside the legitimate client may still be able to request proofs and act through the current session.

ATTACK JWT Algorithm Confusion (alg:none) ►

An attacker crafts a token with "alg":"none" and no signature. Naive verifiers that trust the alg header accept it as valid.

Mitigation: allowlist algorithms

The JWT pitfalls section owns this mechanism. OAuth and OIDC token profiles require signed tokens where a signature is expected, so configure an algorithm allowlist and reject none for those profiles.

ATTACK Open Redirect via redirect_uri ►

If an authorization server validates redirect_uri loosely (only checking that it starts with the right domain), an attacker can register a lookalike path and redirect a freshly issued authorization code to an attacker-controlled endpoint.

Mitigation: exact-match redirect URI allowlists

Authorization servers use exact string matching against a registered redirect URI. The published security best practice already requires this, with a variable-port exception for native-app loopback redirects. The OAuth 2.1 draft carries that rule forward.

ATTACK ID Token Replay Without a Nonce ►

Without a nonce, a previously issued, still-unexpired ID token could be captured and replayed by an attacker to impersonate a login session.

Mitigation: nonce verification

Generate a fresh, random nonce for every authorization request, store it client-side, and verify the value embedded in the returned ID token matches it exactly before trusting the token. See nonce under What OIDC Adds.

ATTACK Mix-Up Attack (multi-IdP) ►

In a multi-IdP setup, an attacker tricks the client into sending an authorization code issued by a legitimate IdP to a malicious IdP's token endpoint, or vice versa.

Mitigation: issuer binding

A client that works with multiple authorization servers must bind each response to the issuer that began the transaction. The authorization-response iss parameter is the standard mechanism. Distinct redirect URIs can serve as a fallback where that mechanism is unavailable.

Refresh Tokens & Rotation

The mechanism that lets users stay logged in for weeks without re-typing a password, and the part that needs the most careful handling.

A refresh token lets a client obtain another access token without repeating the interactive authorization flow. It often carries longer-lived authority than an access token, so the authorization server decides whether to issue one and binds it to the client, granted scope, and resource servers.

Refresh Token Rotation
Single-use refresh tokens

Each use returns a new refresh token and invalidates the previous value. Reuse of an invalidated token reveals that two parties may hold the same grant. Public clients must use rotation or sender-constrained refresh tokens under RFC 9700.

Refresh Token Families
Reuse detection

The server retains the relationship between successive tokens. If an invalidated value reappears, it can revoke the active grant and require authorization again. Other sessions need not be affected unless provider policy chooses broader containment.

Refresh token storage

Prefer a server-side client that stores refresh tokens in a protected token store. If a public client receives one, current best practice requires rotation or sender constraint and storage appropriate to that platform. Do not place a long-lived refresh token in browser localStorage.

Advanced OAuth

Everything up to here covers the flows a typical application needs. What follows goes deeper than most teams will use day to day: sender-constrained tokens, pushed requests, the newer consolidated specification, and the profiles built for regulated and agent-driven systems. Reach for these when a threat model, a compliance regime, or an autonomous client calls for them.

Pushed Authorization Requests (PAR)

PAR flips the authorization flow. Instead of stuffing everything in a URL, the parameters are pushed to the server first, and a reference comes back.

Pushed Authorization Requests (PAR) move the authorization parameters to a direct POST before the browser redirect. The authorization server validates the pushed request and returns a reference for the front channel. This improves integrity and can keep request details out of browser-visible URLs.

1
Client POSTs parameters to /par

The client sends the authorization parameters to the PAR endpoint. Confidential clients authenticate; public clients follow the server's registered-client rules.

↓
2
Server returns a request_uri

The server stores the validated request and returns a short-lived request_uri reference. The client uses each reference for one authorization transaction.

↓
3
Browser redirect uses only the request_uri

The browser redirect carries client_id and request_uri in profiles such as FAPI 2.0. The authorization server resolves the remaining parameters from the pushed request.

Where PAR is required

The final FAPI 2.0 Security Profile requires PAR for authorization code flows. Other deployments can adopt it when they need authenticated request parameters, less front-channel exposure, or compatibility with a security profile that mandates it. Rich Authorization Requests can be used with PAR but do not depend on it.

DPoP (Demonstrating Proof of Possession)

DPoP binds an access token to a client-held key so the token string alone cannot be replayed from another client.

Anyone who obtains an ordinary Bearer token can present it. DPoP changes that property by requiring a signed proof from the key to which the access token was bound. An attacker who captures only the token cannot create that proof.

🔑
Client generates a key pair

The client chooses an asymmetric key pair and protects the private key. The public key appears in DPoP proof headers; access tokens carry or reference its thumbprint.

📸
Client sends a DPoP proof JWT to /token

For each protected request, the client signs a short-lived proof JWT covering fields such as the target URI, HTTP method, creation time, and a unique identifier.

✅
Auth server binds the access token to the public key

The authorization server binds the access token to the proof key, commonly through a cnf.jkt thumbprint. The token is now sender-constrained.

🔒
API verifies DPoP proof on every request

The client attaches the access token and a fresh DPoP proof. The resource server checks the proof signature, token hash, method, target URI, time window, and key binding. A copied token alone cannot satisfy those checks.

What DPoP does not solve

FAPI 2.0 accepts DPoP or mutual TLS for sender-constrained access tokens. DPoP limits replay outside the client that holds the key. It does not remove XSS, stop malicious code from acting inside that client, or replace audience and authorization checks at the API.

OAuth 2.1

The OAuth 2.1 draft consolidates OAuth 2.0 with the security guidance that implementers otherwise have to assemble from later documents.

OAuth 2.1 remains an active IETF Internet-Draft, so it should not be described as a finished standard. Its direction is still useful: new implementations can follow the published OAuth 2.0 Security Best Current Practice now and use the draft to understand how that guidance is being brought into one framework. The principal changes are:

PKCE: Mandatory
PKCE becomes the default

The draft requires PKCE for authorization code flows apart from narrowly defined alternatives. RFC 9700 already requires PKCE for public clients and recommends it for confidential clients.

Implicit & ROPC: Removed
Two grants omitted

The draft does not define the implicit or Resource Owner Password Credentials grants. RFC 9700 already deprecates the former and prohibits the latter.

Redirect URI
Exact redirect matching

The draft carries forward RFC 9700's exact string comparison. Native applications using a loopback redirect retain the specified variable-port exception.

Refresh Token Rotation
Refresh-token replay detection

Public clients that receive refresh tokens must use rotation or sender constraint. Confidential clients authenticate at the token endpoint, which binds their refresh tokens to the client identity.

Agentic & AI Authorization

When an AI agent acts on a user's behalf (booking flights, sending emails, querying databases) the authorization model gets more complex.

Long-running agents put pressure on parts of authorization that interactive clients can often keep simple. An agent may call several APIs, continue after the user leaves, or delegate a subtask to another component. OAuth can establish the initial grant, but the system still has to preserve the user, client, audience, and scope boundaries throughout the task.

Delegation Problem
Who is acting: user or agent?

An API may need both the subject that authorized an action and the component acting for that subject. OAuth Token Exchange lets a client request a token for a new audience from existing subject and optional actor tokens. A deployment can represent delegation with an act claim, but that output and its policy are profile-specific rather than automatic.

Scope Minimization
Least privilege for agents

Agents should receive narrow, task-scoped tokens rather than broad user-level access. Rich Authorization Requests allow structured, resource-specific authorization data, e.g. "access only this Google Doc" rather than "access all Drive files."

Long-lived Sessions
Agents that outlive a login session

An agent that outlives its access token may need a refresh token protected by rotation or sender constraint. Give the overall grant an explicit end as well, so authority does not continue indefinitely after the task should have finished.

Human in the Loop
Step-up auth for sensitive actions

High-impact actions may require fresh or stronger user authentication. A client can request freshness with OIDC max_age and request authentication-context values with acr_values. The ID token's auth_time and acr claims let the client verify what occurred. An API normally signals this requirement through an application or authorization profile rather than sending OIDC parameters itself.

Watch out: token laundering via agents

When an agent framework accepts tokens as inputs and passes them to other services, the chain needs careful validation. An attacker-controlled agent could present a legitimate user token to escalate privileges. Always verify iss, aud, and scope at every hop, and consider mTLS or DPoP binding throughout the chain.

FAPI & High-Security Profiles

FAPI 2.0 defines a stricter OAuth profile for APIs whose threat model requires stronger client authentication, request integrity, and token replay protection.

The final Financial-grade API Security Profile (FAPI 2.0), published by the OpenID Foundation, defines an interoperable OAuth profile for high-value APIs. It combines a constrained authorization code flow with sender-constrained tokens and stronger client authentication. Its core requirements include:

PAR
Pushed Authorization Requests: mandatory. All authorization parameters travel back-channel.
DPoP or mTLS
Sender-constrained tokens: mandatory. Plain Bearer tokens are not permitted.
Issuer binding
Clients check the authorization-response iss value to prevent mix-up attacks.
Asymmetric client auth
Clients support mutual TLS, private_key_jwt, or both. A shared client secret alone is not sufficient.
PKCE S256
Mandatory for all authorization code flows. plain is not acceptable.
Exact redirect URIs
Pre-registered redirect URIs use exact matching under the profile's OAuth security requirements.
Use the profile as a profile

FAPI's security properties come from interoperating requirements across the client, authorization server, and resource server. Individual controls such as PAR or DPoP can help elsewhere, but adopting a few of them does not make an implementation FAPI-conformant. Use the complete profile when a threat model, ecosystem, or certification requires it.

Libraries should handle the protocol details, but the architecture still decides which party may receive each credential and how long that authority lasts. Use the provider's SDK documentation for implementation behavior, the published OAuth security best practice for the current baseline, and the active OAuth 2.1 draft to follow the consolidation work.
