Web Components

How custom elements, Shadow DOM, and HTML templates work together as browser-native components.

Andreas Ögren
~27 min read
Last updated July 2026

Component libraries provide reusable interface elements such as buttons, menus, and cards. Instead of implementing the elements throughout an application, developers can define them once and reuse them wherever they are needed. Each component brings together its markup, styling, and behavior behind a defined interface, making it easier to build consistent user interfaces.

Many component libraries are built for a particular application framework, such as React or Vue. While this works well within that framework, sharing components across applications built with different technologies can be more difficult. A React component, for example, cannot be used directly in a Vue application without additional work.

Web Components provide a way to create reusable HTML elements using standard browser APIs, without tying them to a particular application framework. They allow developers to define new elements, encapsulate their internal structure and styling, and expose interfaces that can be used through HTML, JavaScript, and CSS. Once registered, a custom element can be used in a page much like a built-in HTML element:

index.htmlHTML
<base-button>Save changes</base-button>

Throughout this article, we'll build this small <base-button> Web Component. We'll start by defining a custom HTML element, then give it an internal button, reusable markup, and encapsulated styling. Along the way, we'll explore the underlying browser APIs, how they work together, and when each one is useful.

Main building blocks

Web Components are built using several browser technologies, each with a different responsibility. To understand how they fit together, consider what we need to build our <base-button> element.

First, the browser needs to recognize <base-button> as a custom HTML element and know what to do when one appears on the page. Custom Elements let us register a tag name and associate it with a JavaScript class that defines the element's behavior.

Next, our component needs somewhere to keep its internal native button. With Shadow DOM, a shadow root can be attached to the custom element, creating a separate DOM tree called a shadow tree. This gives the component its own internal structure and creates boundaries for DOM access and CSS selectors.

Rather than constructing that internal structure one element at a time, we can define it in an HTML template and clone its contents for each component instance. The template can also contain slots, which specify where content supplied by the page, such as the button's label or icons, will appear.

CSS has specific behavior and features for shadow trees. Selectors inside and outside a shadow tree have separate scopes, while inheritance and a small set of special selectors cross the boundary in controlled ways. Rules inside the shadow tree can come from <style> elements or constructed stylesheets, and both can be used together.

The technologies can be combined as needed. A custom element can work without a shadow root, and a shadow root can be populated without using a template. Slots are useful when a shadow tree needs to display content supplied by the page.

Our <base-button> will combine all of them. Its tag name and class are registered through Custom Elements. Each instance has a shadow root containing a native button, with its internal markup cloned from a template. Slots display the label and optional icons supplied by the page, and the internal rules are stored in one constructed stylesheet object shared by all of the shadow roots.

The following sections build the component step by step, introducing each browser API as we need it.

Custom elements

A custom element is a browser-managed DOM element with a tag name and behavior defined by a JavaScript class. It can be written in page markup and accessed through standard DOM APIs, just like a built-in element.

BaseButton is an autonomous custom element, which means its class extends HTMLElement and it uses its own tag name. Custom-element names include a hyphen so they cannot collide with built-in HTML tags. This article focuses on autonomous custom elements.

Before the class can be used, its tag name and constructor must be added to the custom-element registry. The default registry is available through customElements, and a definition is added with define().

base-button.tsTypeScript
export class BaseButton extends HTMLElement {
  // ...
}

customElements.define('base-button', BaseButton);

This registers <base-button> as a new HTML element. After registration, a <base-button> instance can be created through HTML like this:

page.htmlHTML 
<base-button variant="primary" size="lg">
  Save changes
</base-button>

It can also be created by calling document.createElement('base-button') in JavaScript:

page.tsTypeScript 

const button = document.createElement('base-button');
button.textContent = 'Save changes';
button.setAttribute('variant', 'primary');
document.body.append(button);

Whether the element is created from markup or through the DOM API, everything exposed outside it is part of its public contract. The contract is developed throughout the article as each underlying browser feature is explained.

Construction and lifecycle

Construction and lifecycle callbacks cover different parts of an element's lifetime. Each instance is initialized once in its constructor. Lifecycle callbacks run later when the element becomes connected to a document, stops being connected, or has an observed attribute changed.

  • constructor() runs once for each custom-element instance. It initializes the element.
  • connectedCallback() runs whenever the element or an ancestor containing it is inserted into a document. Work that requires a document connection, such as setting up document-level listeners, can start here.
  • disconnectedCallback() runs whenever the element itself or an ancestor is removed from the document. Work started while the element was connected can be stopped here.

An element can be removed from the document and inserted again without creating a new instance. Its constructor runs only once, but its connection callbacks may run multiple times.

Attributes have a separate lifecycle callback. A class declares the attribute names it wants to observe in observedAttributes, and attributeChangedCallback() runs when one of those attributes is added, changed, or removed.

The class outline places these methods in BaseButton before their implementations are developed in later sections. The button will expose a disabled attribute, so its name already appears in observedAttributes.

base-button.tsTypeScript
export class BaseButton extends HTMLElement {
  static observedAttributes = ['disabled'];

  constructor() {
    super();
    // One-time internal setup
  }

  connectedCallback() {
    // Work that requires a document connection
  }

  disconnectedCallback() {
    // Connection-scoped work is stopped here
  }

  attributeChangedCallback(name: string, oldValue: string | null, newValue: string | null) {
    // Handle attributes being added, changed, or removed
  }
}

customElements.define('base-button', BaseButton);

connectedCallback() can perform setup after an element enters a document, but the setup must be safe when the element is removed and inserted again. Work started for the duration of a connection, such as a document listener or timer, should be stopped in disconnectedCallback().

Upgrade

A custom element may be parsed before or after its JavaScript class is registered. Both orders are valid, but they affect what is available when the constructor runs.

  • HTML first: If the browser parses <base-button disabled>Save changes</base-button> before its definition is registered, the element initially exists in the DOM without its custom behavior. When customElements.define() is called, the existing element is upgraded to the registered class and its constructor runs. At this point, the disabled attribute and text content are already present.
  • JavaScript first: If the class is registered before the browser parses the tag, the constructor runs as the element is created. Its attributes and child nodes have not yet been added, so neither disabled nor the text content is available. When document.createElement('base-button') is called after registration, construction completes before later statements add attributes or children.

This difference is why the constructor should not depend on attributes or child content. Reading disabled during construction would produce different results depending on whether the element was upgraded or created after registration.

Instead, the constructor should only perform setup that is independent of page markup, such as initializing private state. Initial and later values of observed attributes are handled in attributeChangedCallback(), while work that requires a document connection belongs in connectedCallback(). This allows the component to initialize consistently regardless of which order the HTML and JavaScript arrive in.

Repeated registration

A tag name can only be registered once in the custom-element registry, and a constructor cannot be registered under several names. Attempting either throws an exception. Code that may evaluate more than once can check the registry before defining the element.

base-button.tsTypeScript
if (!customElements.get('base-button')) {
  customElements.define('base-button', BaseButton);
}

Shadow DOM

Shadow DOM adds a second DOM tree to an element, which is called the host. The second tree begins at its shadow root, which is attached to the host through a special relationship instead of being added as an ordinary child. Nodes placed beneath the shadow root belong to the shadow tree.

Nodes written between the opening and closing tags of <base-button> belong to the light DOM. They stay in the document tree as children of the host when a shadow root is attached. A custom element can have light-DOM nodes supplied by page markup and shadow-tree nodes supplied by its component implementation, with each set retaining its own parent relationships.

We can now give <base-button> its own shadow tree containing a native button. The constructor creates this internal structure once for each instance. The registration call remains at module scope, outside the class.

base-button.tsTypeScript
export class BaseButton extends HTMLElement {
  private readonly control: HTMLButtonElement;

  constructor() {
    super();

    // Create the permanent internal tree for this instance.
    const root = this.attachShadow({ mode: 'open' });

    this.control = document.createElement('button');
    this.control.type = 'button';
    this.control.textContent = 'Save changes'; // Note: this creates a duplicate
    root.append(this.control);
  }

  // ...
}

When a <base-button> element is created or upgraded, its constructor is called. The call to super() initializes the HTMLElement part of the instance and must happen before this can be accessed. After that call, this is the BaseButton instance represented by the host in the page. Calling attachShadow() on it creates and attaches the new shadow root to that particular host and returns the root.

The constructor then creates the native button, appends it to the shadow root, and stores its reference in the control field for later callbacks. These steps are performed once in the constructor because the root and internal button belong to the permanent structure of the instance. If attachShadow() were called from connectedCallback(), removing and reinserting the element would cause another call on a host that already has a programmatically created shadow root, and the second call would throw an exception.

After construction, the shadow tree supplies the contents rendered inside the host. Text written between the <base-button> tags still exists in the light DOM, but it is not rendered because the shadow tree does not provide a place for it. The internal button displays its own hard-coded text instead. The Slots section shows how to replace the hard-coded label with the light-DOM text.

DOM queries

Every DOM query has a starting point and is limited to its tree. A document-level query can find the base-button host because the host belongs to the document tree. The search stops at the shadow boundary, so the internal native button is not included. To reach the button, a second query must be started from the shadow root.

shadow-queries.tsTypeScript
const host = document.querySelector('base-button');

const fromDocument = document.querySelector('base-button button'); // null

const fromShadowRoot = host?.shadowRoot?.querySelector('button'); // internal native button

This separation prevents a broad document query for buttons from accidentally including the custom element's internal native button. Page code can depend on the <base-button> element without depending on whether its shadow tree contains a button, an icon, or an extra wrapper. The internal structure can then change while the public properties, methods, and events of the host stay consistent.

CSS selectors

CSS selectors are scoped similarly to DOM queries. A page rule that gives every button square corners does not select the button in the shadow tree. A rule inside the shadow tree can style that internal button without changing buttons elsewhere on the page. This separation prevents unrelated page styles from changing the internal layout and prevents shadow-tree styles from leaking into the surrounding page.

Although CSS selectors cannot cross the shadow boundary, inherited properties such as color and font-family still pass from the host to its internal elements. This allows a component to inherit the page's text color and font without exposing its internal elements to the page's CSS selectors. The styling section explains how to customize other aspects of a component's appearance.

Open and closed roots

The mode passed to attachShadow() controls whether the attached root is available through the host's shadowRoot property. With mode: 'open', the property returns the root, allowing outside JavaScript to access its internal elements explicitly. Ordinary document queries and CSS selectors still cannot cross the shadow boundary.

With mode: 'closed', the shadowRoot property returns null. However, the root reference returned by attachShadow() can still be retained or exposed, so closed mode does not provide security isolation. Both modes provide the same tree and CSS encapsulation.

Templates

Every BaseButton instance needs the same internal styles and native button. Creating each node separately in the constructor works for a small structure, but it becomes difficult to read as more elements are added. An HTML template lets that structure be written as markup once and copied into each instance.

A <template> element holds markup for later use. The browser parses the markup into DOM nodes, but does not render them where the template is declared. The nodes are available through the template's content property, which returns a DocumentFragment. This fragment is a container for the prepared nodes and does not add another element around them.

In the next version of BaseButton, the template is created once at module scope. Each constructor clones the prepared nodes into the new instance's shadow root.

base-button.tsTypeScript
// This template is created once at module scope and shared by every instance.
const template = document.createElement('template');
template.innerHTML = `
  <style>...</style>
  <button type="button">Save changes</button>
`;

export class BaseButton extends HTMLElement {
  private readonly control: HTMLButtonElement;

  constructor() {
    super();

    const root = this.attachShadow({ mode: 'open' });

    // Each instance receives its own clone of the template content.
    root.append(template.content.cloneNode(true));

    // Store the cloned native button for later callbacks and public methods.
    const control = root.querySelector('button');
    if (!(control instanceof HTMLButtonElement)) {
      throw new Error('BaseButton requires an internal button');
    }
    this.control = control;
  }

  // ...
}

cloneNode(true) creates a new fragment containing copies of every node in template.content. Appending the cloned fragment moves its children into the shadow root and leaves the original template content available for the next instance. If template.content were appended directly, its nodes would be moved out of the template and only the first button would receive them. An equivalent structure can be created with ordinary DOM methods when a template is unnecessary.

Slots

The current BaseButton has two separate sources of content. Its native button and hard-coded label are in the shadow tree, while text written between the <base-button> tags stays in the light DOM. Once the shadow root has been attached, this light-DOM text is no longer visible because the shadow tree has no position where it can be rendered.

A slot provides such a position. A <slot> element is placed in the shadow tree, and light-DOM nodes assigned to it are rendered at its position. The nodes stay in the light DOM, so their DOM parents do not change. This allows the native button to stay inside the shadow tree while its label and optional icons come from page markup.

An unnamed <slot> is called the default slot. Text and elements without a slot attribute are assigned to it. Named slots provide separate positions for other content. For example, an element with slot="prefix" is assigned to <slot name="prefix">.

The template can now replace the hard-coded label with a default slot. Named slots on either side provide optional positions for a prefix and a suffix.

base-button.tsTypeScript
template.innerHTML = `
  <style>...</style>
  <button type="button">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;
page.htmlHTML
<base-button>
  <svg slot="prefix">...</svg>
  Save changes
</base-button>

The SVG is assigned to the prefix slot because its slot attribute contains the name prefix. The text node has no slot name, so it is assigned to the default slot and becomes the visible button label. Nothing is assigned to the suffix slot, so nothing is rendered at that position. The light-DOM icon and text keep their original parents after they have been assigned.

Content written inside a <slot> element is fallback content. It is rendered when no light-DOM node has been assigned to the slot. For example, <slot>Save changes</slot> would provide a label when the page leaves the element empty. The default slot in this example has no fallback because a useful button needs a label supplied by the page.

Attributes and properties

The button needs to be disabled from either HTML or JavaScript. In HTML, the state can be written as <base-button disabled>. In JavaScript, it is more natural to assign button.disabled = true. These two forms configure the custom-element host, while the native button inside the shadow tree has its own disabled property. The implementation must keep the public state and the internal control synchronized.

Attributes are the values written in HTML or changed with methods such as setAttribute(). An attribute is either absent or contains text. Even a value written as count="20" is returned by getAttribute() as the string "20". Properties are values on the JavaScript object and may use types such as booleans, numbers, objects, or functions. A custom element can provide both interfaces when a value should be convenient to use from markup and JavaScript.

disabled follows the boolean-attribute convention used by built-in HTML elements. Its presence means true, regardless of the text assigned to it. Both disabled="" and disabled="false" mean disabled. The false state is represented by removing the attribute.

The JavaScript property can be implemented by reading and writing this attribute. This relationship is called reflection. In the code below, the attribute's presence is read by the getter and changed by the setter. Because disabled is included in observedAttributes, every change is reported through attributeChangedCallback() and can be copied to the internal native button.

base-button.tsTypeScript
export class BaseButton extends HTMLElement {
  // The constructor and control field come from the previous sections.

  static observedAttributes = ['disabled'];

  get disabled(): boolean {
    return this.hasAttribute('disabled');
  }

  set disabled(value: boolean) {
    // Store the public property value in the host attribute.
    this.toggleAttribute('disabled', value);
  }

  attributeChangedCallback(name: string) {
    if (name === 'disabled') this.syncDisabled();
  }

  private syncDisabled() {
    // Copy host state to the internal native button.
    this.control.disabled = this.disabled;
  }

  // Other class members are unchanged.
}

A property assignment reaches the internal button through four steps.

  1. Page code assigns button.disabled = true.
  2. The setter adds the disabled attribute to the host.
  3. The browser calls attributeChangedCallback() because disabled appears in observedAttributes.
  4. syncDisabled() copies the resulting boolean value to the native button.

When disabled is present in the original HTML or changed with setAttribute(), the process starts at step three. Removing the attribute makes the getter return false, and the callback enables the internal button. The attribute is therefore the stored public state, while the property offers a boolean JavaScript interface to it.

Primitive public values can often use this reflected relationship. With a string property, the attribute text can be returned directly. With a numeric property, the text must be parsed when it is read and an assigned number must be converted to text when it is written. For example, a count property could expose count="20" as the number 20 and convert an assignment of 30 back to count="30". The documented behavior should cover missing, empty, and invalid attributes. A numeric property might return a default value in those cases, while its setter might reject numbers outside the supported range.

Reflection is useful when a value should be available in markup, JavaScript, CSS selectors, or serialized HTML. It is unnecessary when the value is only used from JavaScript, and it can be wasteful for state that changes frequently. The variant and size values in this example are attributes because shadow-tree CSS reads them. Matching properties could be added if assignments such as button.variant = 'secondary' were part of the public interface.

Objects, arrays, functions, and DOM nodes generally belong in properties because converting them to attribute text loses their original type and object identity. Actions are usually exposed as methods. Only values that affect native behavior should be copied to the internal native element. For example, disabled is copied to the native button, while variant can be handled entirely by CSS.

Properties set before upgrade

Page code can assign button.disabled = true before BaseButton is registered. At this point, the browser stores disabled directly on the unupgraded element as an own property. After upgrade, this property takes precedence over the getter and setter inherited from BaseButton, so assigning or reading disabled would bypass the reflected property defined by the class.

The solution to this issue is to reapply through the class setter when the element is first connected. upgradeProperty() saves the own property's value, deletes the property, and assigns the saved value again. The second assignment reaches the setter, which reflects the value to the attribute and updates the internal button.

base-button.tsTypeScript
export class BaseButton extends HTMLElement {
  // Existing fields, constructor, properties, and callbacks are omitted.

  connectedCallback() {
    // Reapply a value assigned before the element was upgraded.
    this.upgradeProperty('disabled');
  }

  private upgradeProperty(name: 'disabled') {
    if (!Object.prototype.hasOwnProperty.call(this, name)) return;

    const value = this[name];
    Reflect.deleteProperty(this, name);
    this[name] = value;
  }
}

Styling the boundary

The page stylesheet and the stylesheet inside a shadow tree use separate selector scopes. Page selectors can match the <base-button> host and its light-DOM children, but they cannot match the native button in the shadow tree. Selectors inside the shadow tree can match the native button, but they cannot match elements elsewhere on the page. CSS provides several mechanisms for styling across this boundary without removing the separation between the trees.

The first examples keep the shadow-tree styles in the <style> element inside the HTML template. When the template is cloned, the style element becomes part of the shadow root and its rules receive shadow-tree scope. The examples labeled base-button.ts · template style belong in this element. Examples labeled page.css belong to the stylesheet of the surrounding page. After the styling boundary has been explained, these internal rules will be moved into one constructed stylesheet object shared by every BaseButton shadow root.

Selector boundaries

A normal page selector can style the host because the host belongs to the document tree. A selector for native buttons stops at the shadow boundary.

page.cssCSS
base-button {
  margin-inline: 1rem;
}

button {
  border-radius: 0;
}

The first rule applies to the custom-element host. The second rule applies to native buttons in the page, but it doesn't select the native button inside <base-button>.

Ordinary selectors in the template's <style> element work in the other direction. They style elements in the shadow tree without changing matching elements in the page.

base-button.ts · template styleCSS
button {
  border-radius: 0.375rem;
}

This rule applies to the internal native button without changing native buttons elsewhere on the page.

The host

The host belongs to the document tree rather than the shadow tree, so an ordinary selector in the shadow stylesheet cannot match it. The :host pseudo-class allows the shadow stylesheet to select the host. It can define component defaults and respond to public state represented by host attributes.

base-button.ts · template styleCSS
:host {
  display: inline-flex;
}

:host([disabled]) {
  opacity: 0.55;
}

:host([variant="secondary"]) button {
  background: transparent;
}

:host([size="lg"]) button {
  font-size: 1.0625rem;
}

:host selects the <base-button> element itself. The functional form matches it only when the condition in parentheses is true. In the last two rules, the public attributes are checked on the host and the resulting declarations are applied to its internal button.

The host can also be selected from the page. When a normal page rule and a normal :host rule both set a property on the host, the page rule takes precedence. Rules on :host should therefore provide defaults. Properties required by the internal control should be declared on that control.

Inheritance

Properties such as text color and the individual font properties inherit by default. The shadow boundary does not stop this inheritance. When the surrounding page supplies a font and color to <base-button>, elements in its shadow tree can inherit the computed values through the host.

The internal element in this example is a native button, and browsers normally give native buttons their own font and color through the user-agent stylesheet. A property is inherited only when no declaration on the element supplies its value. Without an internal rule, the native button may therefore use the browser's control styles instead of the font and color on <base-button>.

base-button.ts · template styleCSS
button {
  color: inherit;
  font: inherit;
}

color: inherit explicitly uses the inherited text color, while font: inherit does so for all the font properties covered by the shorthand. These declarations override the browser's default control styles. Properties that should be independent of page styling can instead be assigned values inside the shadow stylesheet.

Custom properties

CSS custom properties inherit by default, so a value assigned to the host can be used inside the shadow tree. A component can expose specific styling options by referencing custom properties in its internal declarations.

base-button.ts · template styleCSS
button {
  border-radius: var(--base-button-radius, 0.375rem);
}
page.cssCSS
base-button {
  --base-button-radius: 4px;
}

The component uses 0.375rem as its default radius when no custom value is supplied. The page can override that value without selecting the internal button. Other internal declarations are unaffected because they do not reference this custom property. Names exposed in this way and the declarations they control become part of the public styling interface.

Shadow parts

Custom properties let the page supply values for specific declarations chosen by the component. A shadow part provides broader control by allowing page CSS to style a named internal element directly. The element is given a public name through its part attribute.

base-button templateHTML
<button type="button" part="control">
  <slot name="prefix"></slot>
  <slot></slot>
  <slot name="suffix"></slot>
</button>

Page CSS can select this named element through ::part().

page.cssCSS
base-button::part(control) {
  font-weight: 700;
}

The page can now apply CSS declarations to the named button without accessing its shadow root. Because a part exposes an element rather than a specific styling value, it provides a broader styling interface than a custom property.

Slotted content

The prefix icon and label are rendered inside the native button, but they still belong to the light DOM. They can be styled by ordinary page selectors.

page.cssCSS
base-button [slot="prefix"] {
  color: var(--action-icon-color, currentColor);
}

The shadow stylesheet can provide limited defaults with ::slotted(). This pseudo-element matches elements assigned directly to a slot.

base-button.ts · template styleCSS
::slotted([slot="prefix"]),
::slotted([slot="suffix"]) {
  inline-size: 1em;
  block-size: 1em;
  flex: none;
}

::slotted() does not select descendants of an assigned element, and text nodes cannot be selected with it. The page can style light-DOM content directly, while the shadow stylesheet can provide defaults for elements assigned to the component's slots.

Constructed stylesheets

A constructed stylesheet is a CSSStyleSheet object created in JavaScript, with its CSS rules set through replaceSync(). One object can be shared by several shadow roots. The stylesheet is adopted by a shadow root when its object is included in the root's adoptedStyleSheets array. The object and its parsed rules are not copied for each root, so separate stylesheets do not have to be created and parsed for every component instance. Changes made to the shared object affect every shadow tree that has adopted it.

Sharing the stylesheet object does not create a shared selector scope. Its selectors are evaluated separately within each shadow tree. A button rule therefore applies to the internal button in each BaseButton shadow tree. Buttons elsewhere on the page are outside that selector scope.

The CSS rules developed above can now be moved from the template's <style> element into baseButtonStyles. The object is created once outside the class and shared by every BaseButton shadow root. The template continues to contain the button and slots. During construction, the shared stylesheet is adopted by the new shadow root and a new copy of the template content is appended.

base-button.tsTypeScript
// One stylesheet object is shared by every BaseButton shadow root.
const baseButtonStyles = new CSSStyleSheet();
baseButtonStyles.replaceSync(`
  :host {
    display: inline-flex;
  }

  :host([disabled]) {
    opacity: 0.55;
  }

  :host([variant="secondary"]) button {
    background: transparent;
  }

  :host([size="lg"]) button {
    font-size: 1.0625rem;
  }

  button {
    border-radius: var(--base-button-radius, 0.375rem);
    color: inherit;
    font: inherit;
  }

  ::slotted([slot="prefix"]),
  ::slotted([slot="suffix"]) {
    inline-size: 1em;
    block-size: 1em;
    flex: none;
  }
`);

// The template now contains only the internal DOM structure.
template.innerHTML = `
  <button type="button" part="control">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

export class BaseButton extends HTMLElement {
  private readonly control: HTMLButtonElement;

  constructor() {
    super();

    const root = this.attachShadow({ mode: 'open' });

    // This shadow root adopts the shared stylesheet object.
    root.adoptedStyleSheets = [baseButtonStyles];

    // Clone the button and slots from the markup-only template.
    root.append(template.content.cloneNode(true));

    // Store the cloned button for callbacks and public methods.
    const control = root.querySelector('button');
    if (!(control instanceof HTMLButtonElement)) {
      throw new Error('BaseButton requires an internal button');
    }
    this.control = control;
  }

  // ...
}

One stylesheet object is shared by all of the shadow roots, while the button and slot nodes are copied into each shadow tree. The stylesheet contains the CSS rules, and the template provides the DOM structure.

Events

Page code should be able to handle activation of <base-button> without reaching into its shadow tree. The internal native button already provides native click activation for pointer and keyboard input. Browser-dispatched click events bubble and cross shadow boundaries, so a listener attached to the custom-element host receives the event.

page.tsTypeScript
const button = document.querySelector('base-button');

button?.addEventListener('click', (event) => {
  // currentTarget is the element on which this listener was registered.
  console.log(event.currentTarget); // <base-button>
});

Whether an event path can cross a shadow boundary is represented by its composed value. Whether it continues through ancestor nodes is represented by bubbles. Native click events have both behaviors, so the event passes from the internal button through the shadow root and host into the surrounding page.

When a click starts on the native button inside the shadow tree, event retargeting hides the internal element from outside listeners. Inside the shadow tree, event.target is the native button. Outside the shadow tree, it is the <base-button> host. The figure shows how the visible target changes for this event.

A click can instead start on the slotted prefix icon. Slotted nodes stay in the light DOM, so an outside listener may receive the SVG or one of its child elements as event.target. Code that needs the component on which the listener was registered should use event.currentTarget. In the example above, currentTarget is always <base-button>, regardless of where the click started.

event.composedPath() returns the propagation path and can be useful when the original path is needed for diagnostics. A closed shadow root hides its internal nodes from paths observed outside the root.

No replacement event is needed for BaseButton because the native click already has the required behavior. A custom element may dispatch a CustomEvent when it exposes an action with no corresponding native event. An event dispatched by an internal element needs composed: true to cross the shadow boundary. It needs bubbles: true when listeners on page ancestors should receive it. An event dispatched on the host already starts outside the shadow tree. Its name and payload form part of the public interface.

Accessibility

Web accessibility means making websites usable by people with different abilities, including those who rely on keyboards, screen readers, and other assistive technology. Browsers use HTML semantics to create an accessibility tree that exposes information about elements, such as their roles, names, and states. For <button>Save changes</button>, the browser exposes a button named “Save changes” and provides focus and keyboard activation. If the button is disabled, its disabled state and behavior are handled by the browser as well.

Native semantics in a shadow tree

Internal elements in the shadow DOM are exposed to the accessibility tree just like elements in the light DOM. The native button inside <base-button> is exposed as a button, and its built-in focus and keyboard behavior continue to work. Using a native control inside the shadow tree avoids recreating these semantics and interactions on the custom-element host.

The host does not acquire button semantics from the base-button tag name or the BaseButton class. Page markup places public attributes and content on the host, while the browser gets the button's accessible behavior from the internal control. Attributes and content placed on the host must therefore be transferred to the internal button when they are meant to change the internal button.

The accessible name

A native button normally gets its accessible name from its contents. In the page markup, the words “Save changes” are a light-DOM child of <base-button>, outside the internal native button. The default slot places this text inside the button's rendered content, allowing it to become the button's accessible name.

base-button.ts · templateHTML
<button type="button" part="control">
  <slot name="prefix"></slot>
  <slot></slot>
  <slot name="suffix"></slot>
</button>
page.htmlHTML
<base-button>
  <svg slot="prefix" aria-hidden="true">...</svg>
  Save changes
</base-button>

The text is assigned to the default slot, so the internal button is exposed with the name “Save changes.” The SVG is rendered through the prefix slot. Because the icon is purely decorative, aria-hidden="true" excludes it from the accessible name.

This version of BaseButton requires a visible label in the default slot. An aria-label written on the host is not transferred to the internal button, so <base-button aria-label="Save changes"></base-button> is not supported by this implementation. Supporting that interface would require forwarding the attribute's value to the internal button.

Disabled state

A disabled attribute has built-in behavior on a native button. On <base-button>, it is only a public value and does not automatically disable the internal control. The property setter reflects changes to the host attribute. When this attribute changes, attributeChangedCallback() calls syncDisabled().

base-button.tsTypeScript
private syncDisabled() {
  this.control.disabled = this.disabled;
}

Setting the native property gives the internal button its normal disabled behavior. It cannot be activated with the keyboard or pointer, and assistive technology receives its disabled state from the browser. The assignment connects the public state on the host to the accessible behavior of the internal control.

Focus

With a native button, the element returned to page code is already focusable. A reference to <base-button> points to its host instead. The host has no tabindex and is not focusable in this example, so calling its inherited focus() method would not focus the internal button.

When enabled, the internal native button participates in keyboard navigation, so pressing Tab can move focus to it without making the host an additional tab stop. A public focus() method allows page code to move focus through its reference to the host.

base-button.tsTypeScript
export class BaseButton extends HTMLElement {
  // ...

  focus(options?: FocusOptions): void {
    this.control.focus(options);
  }
}

Page code calls focus() on <base-button>, and the method moves focus to the native button. The focus indicator therefore belongs to the internal control and can be styled in the template with button:focus-visible.

Testing across the boundary

A test that checks only the host attributes does not show whether they affect the internal control. Keyboard testing should confirm that Tab reaches the button, Enter and Space activate it, and the disabled state prevents activation. Inspection of the accessibility tree should confirm the button role, the name “Save changes,” and the disabled state. Programmatic testing should confirm that calling focus() on the host moves focus to the internal button. Broader guidance is covered in the linked Web Accessibility article.
