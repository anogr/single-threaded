Web Components

How browser-managed elements combine behavior, DOM composition, style boundaries, and a stable public interface.

Andreas Ögren
~20 min read
Last updated July 2026

Component libraries are often built around a single application framework. Reusing a control in another framework, an older application, or a server-rendered page can be difficult when its interface and update model depend on the original environment.

Web Components can be used to define new HTML elements in the browser. Behavior and markup can be contained within each element, while familiar HTML, DOM, and CSS interfaces are available outside it.

A small <base-button> is used throughout the article. Because little application logic is involved, the explanation can concentrate on the boundary around a component. Routing, application state, and server-data orchestration are outside its scope.

The element boundary

A custom element is used much like any other HTML element. It can be configured with attributes, content can be placed between its tags, supported styles can be applied through its CSS interface, and interaction can be observed through DOM events.

page.htmlHTML 
<base-button variant="primary" size="lg">
  <svg slot="prefix" aria-hidden="true">...</svg>
  Save changes
</base-button>

A custom element is a browser-managed DOM element with a tag name and behavior defined in application code. Its public contract consists of every interface available outside the element. The contract includes the tag name and HTML attributes, JavaScript properties and methods, content passed through slots, DOM events, and any supported CSS custom properties or shadow parts.

Configuration
Attributes and properties

Serializable configuration can be written as HTML attributes, while richer JavaScript values belong in properties.

Composition

Nodes supplied in light DOM are rendered at positions defined by slots without a change in ownership.

Communication

Methods provide commands, while events make results and interactions observable outside the element.

Appearance
Custom properties and parts

Supported style changes are exposed through named CSS interfaces.

Custom elements, Shadow DOM, and templates are often used together, but each has a different purpose. Registration and lifecycle callbacks are part of the Custom Elements API. A separate DOM root with selector and query boundaries can be created through Shadow DOM, while parsed markup can be stored in a template and cloned for each instance. Any combination of these features can be used.

Definition and upgrade

An unfamiliar tag can be parsed before its class is registered. Before registration, <base-button> exists in the DOM as an undefined element without any behavior from the class. The markup and defining module can be loaded in either order.

base-button.tsTypeScript
class BaseButton extends HTMLElement {
  constructor() {
    super();
  }
}

customElements.define('base-button', BaseButton);

An element is registered by passing a valid name and constructor to customElements.define(). An autonomous custom element extends HTMLElement, and its name must include a hyphen to avoid collisions with built-in tags. Customized built-in elements are another option, but their HTML syntax and browser support can make cross-browser use more difficult.

When define() is called, existing elements matching the new definition are upgraded. During upgrade, the registered prototype is applied, the constructor runs, and reactions are queued for observed attributes already present. connectedCallback() then runs if the element is connected to the document. Elements created after registration use the registered class immediately.

The constructor is suitable for basic setup after super(), including private state, a shadow root, and internal nodes. Host attributes and child nodes may be unavailable during construction, so any setup involving them belongs in a later callback.

A definition in the document’s default registry is available for the lifetime of the page, and a second registration of its name or constructor causes an exception. For a module that may be evaluated more than once, the registry should be checked before define() is called.

base-button.tsTypeScript
if (!customElements.get('base-button')) {
  customElements.define('base-button', BaseButton);
}

await customElements.whenDefined('base-button');

whenDefined() can be awaited before methods or properties from the custom class are used. Rendering requires no wait because matching elements are upgraded automatically after registration.

Connection and cleanup

A custom element may be connected, disconnected, and connected again during its lifetime. Its connection state can change through DOM reordering, conditional rendering, or movement between documents, with a lifecycle callback invoked after each transition.

connectedCallback() is called whenever the element is connected to a document. Document-dependent work can begin there, including size observation, a subscription to a shared service, or an event listener on window.

Work begun during connection should be stopped in disconnectedCallback() after the element is disconnected. This cleanup avoids duplicate observers, listeners, and subscriptions after reconnection. Listeners attached to nodes inside the shadow tree usually require no cleanup because the nodes are disconnected with the host.

No document-level listeners, observers, or subscriptions are created in the <base-button> example. Only property assignments made before definition are recovered during the first connection, so no work is required in disconnectedCallback().

attributeChangedCallback() is called when an observed attribute is added, replaced, or removed. Attribute names must appear in observedAttributes, and values already present are processed during upgrade, possibly before the first connection.

Attributes and properties

Element configuration is represented differently in HTML and JavaScript. Attributes are serialized as text in markup, while properties are read and written on the element object. These interfaces are often synchronized for built-in elements, and the convention should be followed when one custom-element value is available through both markup and JavaScript.

The disabled attribute is a boolean attribute, so its presence represents true regardless of its text. Both disabled="" and disabled="false" disable the element, while removing the attribute changes the state to false.

base-button.tsTypeScript
static observedAttributes = ['disabled'];

get disabled(): boolean {
  return this.hasAttribute('disabled');
}

set disabled(value: boolean) {
  this.toggleAttribute('disabled', value);
}

attributeChangedCallback(name: string) {
  if (name === 'disabled') this.syncDisabled();
}

The property reflects to the attribute. Setting button.disabled = true adds the attribute, while removal of the attribute causes the property getter to return false. The serialized value is stored in HTML and represented as a boolean in JavaScript.

Four steps are involved in copying a property assignment to the internal button.

  1. button.disabled = true is assigned.
  2. The property setter adds disabled to the host.
  3. The browser calls attributeChangedCallback().
  4. syncDisabled() sets the native button's disabled property to true.

A change made directly in markup is handled from step three onward. If disabled is removed from the host, the property getter returns false and the internal button is enabled during synchronization. In both directions, the public value is stored in the attribute and used to update the internal control.

Reflection is suitable for values with a clear HTML representation. Objects, functions, and large data structures usually exist only as properties. Commands such as show() or reset() are best represented by methods, while readable or assignable state belongs in properties.

A property assignment made before definition creates an own property on the unresolved element. After upgrade, the accessor on the class prototype is hidden by the own property. The early value can be recovered by reading it, deleting the own property, and assigning the value again after connection so it passes through the setter.

base-button.tsTypeScript
private upgradeProperty(name: 'disabled' | 'variant' | 'size') {
  if (!Object.prototype.hasOwnProperty.call(this, name)) return;

  const value = Reflect.get(this, name);
  Reflect.deleteProperty(this, name);
  Reflect.set(this, name, value);
}

In the complete example, recovery is limited to the first connection by a guard. Once the early assignments have passed through their setters, the internal button can be synchronized from the resulting host state.

Shadow DOM

A shadow root is a separate DOM root attached to a host element. The host is part of the document tree, while nodes written between its tags belong to the light DOM and internal nodes belong to the shadow tree. During rendering, nodes from both trees can appear together through slot assignment without a change in DOM ownership.

Nodes inside the shadow tree are unavailable to ordinary document-level selectors and queries. ID lookup within the component is limited to the shadow root, so internal nodes are outside the scope of page selectors and internal selectors are limited to their own tree.

The boundary can be crossed in specific ways. CSS properties may be inherited from the host, along with language and text direction. Other controlled connections are available through slots, event propagation, focus navigation, and explicit styling hooks.

base-button.tsTypeScript
const root = this.attachShadow({ mode: 'open' });
root.append(template.content.cloneNode(true));

An open root is accessible through element.shadowRoot. For a closed root, the property returns null, although the reference returned by attachShadow() can be retained inside the component. A closed root should be treated as private API, though it is not a security boundary. Open roots are usually easier to inspect, test, and integrate.

Templates

Markup inside a template is parsed without being rendered in the surrounding document. The parsed nodes are available from its content property as a DocumentFragment, which can be cloned when the internal nodes for each instance are created.

base-button.tsTypeScript
const template = document.createElement('template');
template.innerHTML = `
  <style>...</style>
  <button type="button" part="control">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

this.shadowRoot?.append(template.content.cloneNode(true));

When a fragment is appended, its nodes are moved into the destination. Appending the template's original fragment directly would leave it empty after the first use, so a clone is normally created for each instance. An equivalent structure can be created with ordinary DOM methods when a template is unnecessary.

Slots

A slot is a position in the shadow tree where light-DOM content can be rendered. A child with slot="prefix" is assigned to <slot name="prefix">, while children without a slot attribute are assigned to the default slot.

Markup inside a slot element is used as fallback content whenever no light-DOM node has been assigned. A useful default can be provided there and replaced through page markup.

slot-observation.tsTypeScript
const prefix = this.shadowRoot?.querySelector<HTMLSlotElement>(
  'slot[name="prefix"]'
);

prefix?.addEventListener('slotchange', () => {
  const visibleNodes = prefix.assignedElements({ flatten: true });
  this.toggleAttribute('has-prefix', visibleNodes.length > 0);
});

A slotchange event is dispatched whenever the set of assigned nodes changes. Changes deeper inside an assigned subtree do not affect slot assignment, so no event is dispatched for them. The current assignment can be inspected through assignedNodes() or assignedElements().

Styling the boundary

Nodes in a shadow tree cannot be reached by ordinary selectors outside the component. Supported style changes must therefore be exposed through explicit CSS interfaces.

component-and-page.cssCSS
/* Inside the shadow root */
:host { display: inline-flex; }
button { border-radius: var(--base-button-radius, 0.375rem); }
::slotted([slot="prefix"]) { inline-size: 1em; }

/* In the page stylesheet */
base-button { --base-button-radius: 999px; }
base-button::part(control) { font-weight: 700; }

With a custom property, a value is assigned through the component API and used by a CSS rule inside the shadow tree. More direct styling is possible when an internal element is exposed as a part. The closer dependency on internal structure means part names and their purpose should be included in the public API.

Nodes assigned directly to a slot can be selected with ::slotted(), but descendants inside an assigned element cannot. The descendants belong to the surrounding light-DOM subtree and can be styled from the page.

A style element inside the template is a clear starting point. If many shadow roots use identical styles, a constructed stylesheet can be assigned to each root through adoptedStyleSheets. An unchanged external CSS interface can be provided with either approach.

Events

Inside a shadow tree, the usual capture and bubble phases still apply. Propagation beyond the tree depends on two flags. With bubbles: true, the event is propagated through ancestor nodes. With composed: true, its path may cross a shadow boundary.

Browser-dispatched interface events such as click are composed, so a click from the internal button can be received outside the component. At the shadow boundary, the event is retargeted, and event.target contains the <base-button> host for an outside listener. The full propagation path can be inspected with event.composedPath(), subject to the visibility rules for closed roots.

Activation of the internal button already produces a native click, which can propagate through the host without a replacement event. A CustomEvent is appropriate when the interaction has no corresponding native event. A task card, for example, could dispatch an archive-request event after its archive action is selected.

task-card.tsTypeScript
this.dispatchEvent(new CustomEvent('task-archive-request', {
  detail: { taskId: this.taskId },
  bubbles: true,
  composed: true,
  cancelable: true,
}));

The event name and payload are part of the public contract. Events intended for listeners outside the shadow tree must be dispatched with composed: true. Before an action associated with a cancelable event is completed, defaultPrevented or the return value from dispatchEvent() must be checked.

For the button example, native click propagation can be followed through four stages.

  1. A composed click is dispatched from the internal native button.
  2. The propagation path passes through the shadow root and the <base-button> host.
  3. Outside listeners receive the event with event.target retargeted to the host.
  4. The click is handled by a page or framework listener on the public element boundary.

Accessibility and forms

Shadow DOM changes DOM and CSS boundaries, but accessibility must still be built into the component. Correct semantics, an accessible name, keyboard behavior, visible focus, and state perceivable by assistive technology all require deliberate support. When a native control is used, its browser behavior is retained instead of being recreated on a generic element.

In this example, the default slot is placed inside a native <button>, so visible text such as “Save changes” becomes the button label. Keyboard activation and disabled behavior are inherited from the native control. Content in the prefix and suffix slots should be decorative or add information missing from the label. An aria-label on the custom-element host is not automatically applied to the internal button, so component code must forward its value when the attribute is supported.

A clear public interface is needed for programmatic focus because a reference to <base-button> points to the host while the focusable button is inside the shadow tree. Calls to the public focus(options) method are forwarded to the internal button, and its focus indicator is styled with :focus-visible.

Extra support is required for form participation because a native control inside a shadow tree does not automatically make the custom-element host part of the surrounding form. The internal control in this example has type="button", which gives the host the behavior of an ordinary action button.

For an input-like autonomous custom element, form association can be enabled with static formAssociated = true and attachInternals(). Submission values, validity, labels, form ownership, and form lifecycle callbacks can then be configured through ElementInternals.

Accessibility testing crosses the boundary

Testing should cover keyboard input, browser accessibility inspection, supported screen readers, zoom, forced colors, and high-contrast settings. Screenshots can show focus and visible labels, but accessible names, roles, states, and announcements require browser inspection or assistive-technology testing.

The broader model behind these requirements is covered in Web Accessibility. In a component library, semantic and interaction guarantees should be versioned alongside properties and events.

Before definition

An element may appear on screen before its defining module loads. During this interval, light-DOM content is available as text or fallback structure. Unresolved custom elements can be selected with :not(:defined), although a blank region is often shown when every unresolved element is hidden.

With Declarative Shadow DOM, a shadow root can be included in HTML through a template with shadowrootmode="open" or shadowrootmode="closed". The shadow tree is created and rendered during parsing, so internal markup can appear in the original HTML response before the custom-element code runs.

server-rendered.htmlHTML
<base-button variant="primary">
  <template shadowrootmode="open">
    <style>...</style>
    <button type="button" part="control"><slot></slot></button>
  </template>
  Save changes
</base-button>

An existing root must be taken into account during client initialization because a call to attachShadow() with a matching mode returns and clears a declaratively created root, replacing the server-rendered internals. In the complete implementation, this.shadowRoot is read first. A root is created and the template is cloned only when no root content exists, after which the native button is found in the resulting tree.

With Declarative Shadow DOM, structure and styles are available before JavaScript runs. The properties, methods, and lifecycle behavior from the custom class become available after registration, so server rendering and upgrade form separate parts of component initialization.

When to use Web Components

Web Components are a good fit for controls and widgets that need a stable browser interface across frameworks or applications. Typical examples include design-system primitives, embedded tools, media controls, and independently delivered microfrontend surfaces.

Portability requires additional API work. Attribute and property semantics must be kept consistent, slots and parts must be versioned, accessibility must cross the shadow boundary, and server rendering and loading need deliberate design. For a component used in one framework application, the framework's component model and tooling may be a better choice.

Within framework code, a custom element is represented as a DOM node, while its shadow tree and lifecycle are handled by the custom-element class. A wrapper can be added for adapted names, TypeScript declarations, refs, defaults, and application policy without changing the DOM implementation. This pattern is covered in Wrapping Web Components in React.

Web Components are particularly useful as a lower-level interface beneath application frameworks when an element needs to work across several runtimes or without a framework. Wider reuse can justify the extra work involved in API and lifecycle design.

Complete example

In the complete implementation, the public contract consists of reflected disabled, variant, and size properties, a focus method, three content slots, one shadow part, and the native click event. If an open declarative shadow root already exists during upgrade, it is reused, and the internal control is always created with type="button".

base-button.tsTypeScript
type Variant = 'primary' | 'secondary' | 'ghost';
type Size = 'sm' | 'md' | 'lg';

const variants = new Set<Variant>(['primary', 'secondary', 'ghost']);
const sizes = new Set<Size>(['sm', 'md', 'lg']);

const template = document.createElement('template');
template.innerHTML = `
  <style>
    :host {
      display: inline-flex;
    }

    :host([variant="secondary"]) button {
      background: transparent;
      color: var(--base-button-secondary-color, CanvasText);
      border-color: var(--base-button-secondary-border, currentColor);
    }

    :host([variant="ghost"]) button {
      background: transparent;
      color: var(--base-button-ghost-color, CanvasText);
      border-color: transparent;
    }

    :host([disabled]) { opacity: 0.55; }

    button {
      border: 1px solid transparent;
      border-radius: var(--base-button-radius, 0.375rem);
      background: var(--base-button-primary-background, Highlight);
      color: var(--base-button-primary-color, HighlightText);
      cursor: pointer;
      display: inline-flex;
      align-items: center;
      justify-content: center;
      gap: 0.5em;
      font: inherit;
      padding: 0.5em 1em;
    }

    :host([size="sm"]) button { font-size: 0.8125rem; }
    :host([size="lg"]) button { font-size: 1.0625rem; padding: 0.65em 1.2em; }
    button:disabled { cursor: default; }
    button:focus-visible { outline: 2px solid currentColor; outline-offset: 3px; }
    ::slotted([slot="prefix"]),
    ::slotted([slot="suffix"]) { inline-size: 1em; block-size: 1em; }
  </style>
  <button type="button" part="control">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

export class BaseButton extends HTMLElement {
  static readonly tagName = 'base-button';
  static observedAttributes = ['disabled'];

  private readonly control: HTMLButtonElement;
  private propertiesUpgraded = false;

  constructor() {
    super();

    const root = this.shadowRoot ?? this.attachShadow({ mode: 'open' });
    if (!root.hasChildNodes()) {
      root.append(template.content.cloneNode(true));
    }

    const control = root.querySelector('button');
    if (!(control instanceof HTMLButtonElement)) {
      throw new Error('BaseButton requires an internal button');
    }
    this.control = control;
  }

  connectedCallback() {
    if (!this.propertiesUpgraded) {
      this.upgradeProperty('disabled');
      this.upgradeProperty('variant');
      this.upgradeProperty('size');
      this.propertiesUpgraded = true;
    }

    this.syncDisabled();
  }

  attributeChangedCallback(name: string) {
    if (name === 'disabled') this.syncDisabled();
  }

  get disabled(): boolean {
    return this.hasAttribute('disabled');
  }

  set disabled(value: boolean) {
    this.toggleAttribute('disabled', value);
  }

  get variant(): Variant {
    const value = this.getAttribute('variant') as Variant | null;
    return value && variants.has(value) ? value : 'primary';
  }

  set variant(value: Variant) {
    this.setAttribute('variant', value);
  }

  get size(): Size {
    const value = this.getAttribute('size') as Size | null;
    return value && sizes.has(value) ? value : 'md';
  }

  set size(value: Size) {
    this.setAttribute('size', value);
  }

  focus(options?: FocusOptions): void {
    this.control.focus(options);
  }

  private syncDisabled() {
    this.control.disabled = this.disabled;
  }

  private upgradeProperty(name: 'disabled' | 'variant' | 'size') {
    if (!Object.prototype.hasOwnProperty.call(this, name)) return;

    const value = Reflect.get(this, name);
    Reflect.deleteProperty(this, name);
    Reflect.set(this, name, value);
  }
}

if (!customElements.get(BaseButton.tagName)) {
  customElements.define(BaseButton.tagName, BaseButton);
}

In the declaration below, the tag name is mapped to its TypeScript class so the specific element type can be returned by DOM queries without a framework dependency.

base-button.d.tsTypeScript
import { BaseButton } from './base-button';

declare global {
  interface HTMLElementTagNameMap {
    'base-button': BaseButton;
  }
}
