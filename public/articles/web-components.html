Web Components

How custom elements, Shadow DOM, and HTML templates combine into a reusable button that works across framework boundaries.

Andreas Ögren
~17 min read
Last updated July 2026

A component library often begins inside one application framework. Trouble arrives when the same design system must also serve a Vue application, an older jQuery page, or a server-rendered site. A React component cannot move into those environments unchanged because its implementation depends on React.

Web Components address that boundary through browser APIs rather than another application framework. They let developers define reusable HTML elements that can be consumed from plain JavaScript and from frameworks that support custom elements. The component still needs JavaScript and browser APIs at runtime, but it does not depend on one framework's component model.

This article explains the core Web Component APIs and combines them in a BaseButton custom element. The companion article then shows how a React wrapper can adapt that element to an application-specific component API.

How the platform model developed

Early Web Components work grouped four related proposals under one name:

  • Custom Elements defined new HTML elements with application behavior.
  • Shadow DOM provided a separate DOM and style scope inside an element.
  • HTML Templates held parsed markup that could be cloned when needed.
  • HTML Imports proposed loading one HTML document from another, but did not remain part of the platform.

The first versions changed substantially as browser vendors worked through interoperability problems. HTML Imports were dropped, while custom elements, Shadow DOM, templates, and slots became part of the browser platform. Their core features are now broadly available, although individual additions have their own compatibility timelines.

The motivation remained consistent: package behavior, markup, and styles behind an HTML element without requiring a particular application framework to interpret that element.

The three core technologies

Web Components bring together three platform technologies. Each can be used on its own, although they are commonly combined.

Custom elements let code define an HTML element such as <base-button> with behavior supplied by a JavaScript class. After the definition is registered, the browser upgrades matching elements and runs the relevant lifecycle callbacks.

Shadow DOM attaches a separate tree to a host element. Selectors outside that tree do not select its internals, and selectors inside it do not reach into the surrounding page. Inherited CSS properties and explicit styling hooks still cross the boundary, so the encapsulation is controlled rather than absolute.

HTML templates provide a <template> element whose contents are parsed but not rendered with the surrounding page. Code can clone that content whenever it needs another instance of the component's internal structure.

Web Components are most useful when one UI element must cross framework boundaries or be embedded in applications owned by different teams. Design-system controls, media players, and self-contained widgets often fit that requirement. The shared element can outlive a framework migration while each consuming application keeps its own rendering and state model.

They do not provide an application architecture. Routing, shared application state, and server-data orchestration still belong to the surrounding framework or application code.

How they differ from framework components

Framework components and Web Components both package UI behavior behind a reusable interface, but they operate at different layers.

A framework component is interpreted by that framework's runtime, compiler, or both. Its props, update model, and lifecycle belong to the framework. The framework eventually creates and updates DOM nodes, but the component itself is meaningful only within that framework's component tree.

A custom element is a DOM element managed by the browser. Strings can enter through HTML attributes, richer values can be assigned as JavaScript properties, and communication outward uses DOM events. Frameworks may add their own conventions around those surfaces, but the underlying contract remains the DOM.

Key distinction

A framework can render and configure a custom element as a DOM node, but it does not render the element's shadow tree or control its custom-element callbacks. That internal behavior remains with the browser and the element class.

Current frameworks can handle many custom-element properties and events directly. A wrapper is still useful when an application wants framework-specific names, types, refs, or server-rendering behavior. The companion article develops that kind of React adapter.

Custom Elements

The example in this article is an autonomous custom element, so its class extends HTMLElement. The platform also defines customized built-in elements that extend classes such as HTMLButtonElement, but Safari does not support that form. Autonomous custom-element names contain a hyphen, which keeps them distinct from present and future built-in HTML names.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  // The browser calls this once for each element instance.
  constructor() {
    super(); // always first
  }
}

A derived constructor must call super() before it can use this. For a custom element, that call also runs the HTMLElement constructor required by the platform. Omitting it makes construction fail before the element can initialize.

Defining elements

The class becomes usable after registration with customElements.define(). The browser uses that definition for new <base-button> elements and upgrades matching elements that were created earlier in the document.

base-button.ts TypeScript 
// Pass the tag name, then the class. The name must contain a hyphen.
customElements.define('base-button', BaseButton);

The default registry at window.customElements applies to the document and does not provide an operation for removing a definition. Registering the same name or constructor twice throws an exception, so libraries commonly guard repeated module evaluation:

base-button.ts TypeScript 
if (!customElements.get('base-button')) {
  customElements.define('base-button', BaseButton);
}

Scoped custom-element registries can associate a separate set of definitions with a shadow tree. They avoid global name collisions in applications that need independently versioned components, but the default document registry remains the common choice for elements intended for broad consumption.

Shadow DOM

Shadow DOM creates a separate tree attached to a host element. A document-level querySelector() does not search that tree, and ordinary selectors do not cross its boundary. IDs are resolved within the shadow tree. Inherited properties, CSS custom properties, slots, events, and explicit styling hooks still connect the component to the surrounding page.

The constructor can attach a shadow root before creating the component's internal DOM:

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;

  constructor() {
    super();
    // 'open' lets JS outside the element reach shadow internals
    // via element.shadowRoot. Use 'closed' to prevent that.
    this.shadow = this.attachShadow({ mode: 'open' });
  }
}

With mode: 'open', outside code can reach the root through element.shadowRoot. A closed root returns null from that property, which can be useful when the public contract deliberately excludes direct DOM access. Neither mode is a security boundary. Open roots are usually easier to inspect, test, and integrate, while accessibility depends on the semantics exposed by the component rather than on this mode alone.

Setting CSS

Selectors in a shadow root are scoped to that tree. The :host pseudo-class selects the host element from within the shadow stylesheet. Constructed stylesheets let several roots adopt the same CSSStyleSheet object, while a <style> element inside the template remains a valid declarative alternative.

base-button.ts TypeScript 
// Create once at module scope so all instances share one stylesheet
const sheet = new CSSStyleSheet();
sheet.replaceSync(`
  :host { display: inline-flex; cursor: pointer; }

  /* Attribute selectors read state straight off the host element */
  :host([variant="primary"]) button { background: #f0a500; }
  :host([disabled]) { opacity: 0.45; pointer-events: none; }
`);

// Adopt it in the constructor, so every instance shares one parsed sheet
this.shadow.adoptedStyleSheets = [sheet];

Ordinary custom properties declared with a -- name inherit by default, including through the host into its shadow tree. A component can use that behavior as an explicit theming surface. For example, its internal CSS may read --base-button-radius, while consumers set the value on the element or an ancestor.

HTML Templates

A <template> element stores its parsed contents in a DocumentFragment without rendering them in the surrounding document. Cloning that fragment reuses the parsed structure. A <slot> inside a shadow tree provides a destination for the host's light-DOM children, allowing consumers to place ordinary markup inside the custom element.

base-button.ts TypeScript 
const template = document.createElement('template');
template.innerHTML = `
  <button part="button">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

// Inside the constructor, clone and append:
this.shadow.appendChild(template.content.cloneNode(true));

The part attribute gives the inner button a public styling name. Consumers can target that name with ::part(button) without receiving unrestricted selector access to the rest of the shadow tree.

Building BaseButton

The component can now combine those primitives with lifecycle callbacks, observed attributes, properties, and events. Each part adds one piece of the element's public or internal contract.

Lifecycle callbacks

Custom elements expose callbacks for connection, disconnection, adoption into another document, and observed attribute changes. The platform also provides connectedMoveCallback for state-preserving moves made with Element.moveBefore(). The component below relies on the callbacks needed for ordinary insertion, removal, and attribute updates.

connectedCallback runs when the element becomes connected to a document. Work that depends on connection, such as starting an observer or subscribing to an external source, belongs here. The callback can run more than once during an element's lifetime.

disconnectedCallback runs when the element stops being connected. It should undo subscriptions or resource ownership established during connection so that a later reconnection starts from a clean state.

attributeChangedCallback runs when an attribute named by observedAttributes is added, changed, or removed. The next section uses it to keep the internal button synchronized.

adoptedCallback runs when the element is adopted into another document. Most application components do not need special behavior for that transition.

A gotcha with connectedCallback

Moving an element with ordinary DOM insertion methods can trigger disconnection followed by reconnection. Setup must therefore tolerate repeated calls, and cleanup must release any external listeners or subscriptions created during connection. Element.moveBefore() and connectedMoveCallback provide a separate state-preserving path when that newer API is used.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;
  private innerButton: HTMLButtonElement | null = null;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    this.shadow.adoptedStyleSheets = [sheet];
    this.shadow.appendChild(template.content.cloneNode(true));
  }

  connectedCallback() {
    this.innerButton = this.shadow.querySelector('button');
    this.innerButton?.addEventListener('click', this.handleClick);
    this.syncDisabled();
    this.syncType();
  }

  disconnectedCallback() {
    this.innerButton?.removeEventListener('click', this.handleClick);
    this.innerButton = null;
  }
}

Observed attributes and attributeChangedCallback

Attribute values are strings or null when an attribute is absent. In HTML, <base-button disabled> creates a boolean attribute whose presence represents true; the empty string is its serialized value. The browser calls attributeChangedCallback only for names returned by observedAttributes. Other attributes still change normally, but they do not trigger that callback.

base-button.ts TypeScript 
// Tell the browser which attributes to watch
static get observedAttributes(): string[] {
  return ['disabled', 'variant', 'size', 'type'];
}

attributeChangedCallback(name: string) {
  if (name === 'disabled') this.syncDisabled();
  // 'type' gets the same treatment. 'variant' and 'size' are read
  // straight off the attribute in CSS, via :host([variant="…"])
}

During an upgrade, attributeChangedCallback can run before connectedCallback. The synchronization methods therefore tolerate a null internal button. Once connected, syncAll() applies the current attribute state to the rendered control.

Properties and upgrading them

Attributes provide a string-based, serializable surface. JavaScript properties can carry booleans, numbers, objects, and other values that do not fit naturally in markup. A property may reflect to an attribute when that relationship is useful and unsurprising. The disabled property below follows native HTML conventions by reflecting a boolean to attribute presence.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  // Expose a boolean `disabled` property that mirrors the attribute
  get disabled(): boolean {
    return this.hasAttribute('disabled');
  }
  set disabled(value: boolean) {
    value
      ? this.setAttribute('disabled', '')
      : this.removeAttribute('disabled');
  }

  // variant, size, and type follow the same get/set-through-attribute shape
}

A timing problem appears when code assigns myButton.disabled = true before the custom-element definition is registered. The assignment creates an own property on the unresolved element. After upgrade, that property shadows the accessor on BaseButton.prototype, so later reads and writes bypass the class's setter.

The upgrade helper reads the own property, deletes it, and assigns the value again so the prototype setter runs. This example calls the helper during the first connection. Under strict null checking, TypeScript rejects delete this[prop] for required properties with error TS2790. Reflect.deleteProperty() performs the runtime operation without applying that compile-time restriction.

base-button.ts TypeScript 
private upgradeProperty(prop: keyof this) {
  if (Object.prototype.hasOwnProperty.call(this, prop)) {
    const value = this[prop];
    // Required properties aren't optional in TS's eyes, so a plain
    // `delete this[prop]` fails to compile (TS2790). Reflect.deleteProperty
    // does the same job without fighting the type checker.
    Reflect.deleteProperty(this, prop); // remove the expando
    this[prop] = value;  // re-set through the class setter
  }
}

connectedCallback() {
  this.upgradeProperty('disabled');
  this.upgradeProperty('variant');
  this.upgradeProperty('size');
  this.upgradeProperty('type');
  // ... rest of setup
}

Custom events

Custom elements communicate outward through DOM events. Native events should remain native when their semantics already fit, as they do with a button's click event. A CustomEvent is useful when the component reports a higher-level action or needs a typed detail payload. Event names belong to the component's public API, so a descriptive prefix can reduce collisions.

Synthetic events default to composed: false. An event dispatched inside a shadow tree therefore needs composed: true to cross the shadow boundary, and it also needs bubbles: true to continue bubbling through ancestors. The example dispatches from the host, where crossing a shadow boundary is unnecessary, but keeps both options so the event contract remains explicit if its origin later moves inward.

base-button.ts TypeScript 
// Type the detail payload for consumers
interface BaseButtonClickDetail {
  originalEvent: MouseEvent;
  variant: Variant;
  disabled: boolean;
}

private handleClick = (e: MouseEvent) => {
  // Prevent the native click from propagating out of the shadow
  e.stopPropagation();

  const detail: BaseButtonClickDetail = {
    originalEvent: e,
    variant: this.variant,
    disabled: this.disabled,
  };

  this.dispatchEvent(
    new CustomEvent<BaseButtonClickDetail>('base-button:click', {
      detail,
      bubbles:  true,
      composed: true, // keep the event public if its origin moves inward
    })
  );
};

// Arrow function stored as a class field so `this` is always bound,
// and so the exact same reference can be removed in disconnectedCallback.

Storing the handler as a class-field arrow function preserves both its this value and its identity. A regular method can work too, but it must be bound once and the same bound function must be passed to both addEventListener() and removeEventListener().

The full component

The complete class brings together the shared stylesheet, template, lifecycle callbacks, observed attributes, property accessors, upgrade helper, and event handler. A registration guard at the bottom avoids an exception if development tooling evaluates the module again. The full source section keeps the implementation in one place.

The result is a framework-independent custom element with scoped internal styles, a template-based shadow tree, typed properties, and a custom event. Browsers run the emitted JavaScript directly. TypeScript compilation remains a development choice rather than a Web Components requirement.

A framework wrapper can add its own prop names, type declarations, refs, or event conventions without changing the DOM-level element. The companion article, Wrapping Web Components in React, develops that adapter for React.

const template = document.createElement('template');

  <button part="button">

// ── Element class ──────────────────────────────────────
export class BaseButton extends HTMLElement {
  static readonly tagName = 'base-button';

  static get observedAttributes() {
    return ['disabled', 'variant', 'size', 'type'] as const;
  }

  private shadow: ShadowRoot;
  private innerButton: HTMLButtonElement | null = null;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    this.shadow.adoptedStyleSheets = [sheet];
    this.shadow.appendChild(template.content.cloneNode(true));
  }

  // ── Lifecycle ──────────────────────────────────────────
  connectedCallback() {
    this.upgradeProperty('disabled');
    this.upgradeProperty('variant');
    this.upgradeProperty('size');
    this.upgradeProperty('type');

    this.innerButton = this.shadow.querySelector('button');
    this.innerButton?.addEventListener('click', this.handleClick);
    this.syncAll();
  }

  disconnectedCallback() {
    this.innerButton?.removeEventListener('click', this.handleClick);
    this.innerButton = null;
  }

  attributeChangedCallback(
    name: string,
    _old: string | null,
    _next: string | null
  ) {
    if (name === 'disabled') this.syncDisabled();
    if (name === 'type') this.syncType();
  }

  // ── Properties ────────────────────────────────────────
  get disabled() { return this.hasAttribute('disabled'); }
  set disabled(v: boolean) {
    v ? this.setAttribute('disabled', '') : this.removeAttribute('disabled');
  }

  get variant(): Variant {
    return (this.getAttribute('variant') ?? 'primary') as Variant;
  }
  set variant(v: Variant) { this.setAttribute('variant', v); }

  get size(): Size {
    return (this.getAttribute('size') ?? 'md') as Size;
  }
  set size(v: Size) { this.setAttribute('size', v); }

  get type(): BtnType {
    return (this.getAttribute('type') ?? 'button') as BtnType;
  }
  set type(v: BtnType) { this.setAttribute('type', v); }

  // ── Private helpers ────────────────────────────────────
  private upgradeProperty(prop: keyof this) {
    if (Object.prototype.hasOwnProperty.call(this, prop)) {
      const value = this[prop];
      Reflect.deleteProperty(this, prop);
      this[prop] = value;
    }
  }

  private syncDisabled() {
    if (this.innerButton) this.innerButton.disabled = this.disabled;
  }

  private syncType() {
    if (this.innerButton)
      this.innerButton.type = this.type as HTMLButtonElement['type'];
  }

  private syncAll() {
    this.syncDisabled();
    this.syncType();
  }

  // ── Event handler ──────────────────────────────────────
  private handleClick = (e: MouseEvent) => {
    e.stopPropagation();
    this.dispatchEvent(
      new CustomEvent<BaseButtonClickDetail>('base-button:click', {
        detail: {
          originalEvent: e,
          variant: this.variant,
          disabled: this.disabled,
        },
        bubbles: true,
        composed: true,
      })
    );
  };
}

// ── Registration ───────────────────────────────────────
if (!customElements.get(BaseButton.tagName)) {
  customElements.define(BaseButton.tagName, BaseButton);
}
