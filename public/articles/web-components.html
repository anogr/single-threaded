Web Components

How custom elements, Shadow DOM, and HTML templates work at the platform level, built step by step into a real BaseButton component.

Andreas Ögren
~15 min read
Last updated July 2026

There is a moment every team eventually hits: a component library built in React is humming along as the design system's foundation, and then someone asks whether it could work in the Vue project, or the legacy jQuery app, or the server-rendered Astro site that marketing just launched. The honest answer, usually, is no. Not without rewriting it.

Web Components are the platform's answer to that problem. They are not a framework. They are a collection of browser APIs that let developers define custom, reusable HTML elements that work anywhere HTML works: in React, in Vue, in a plain HTML file, in an email renderer that supports custom elements. Understanding them is useful even for teams that live in React all day, since knowing where the framework ends and the platform begins clarifies what any given abstraction is doing.

This article covers every major Web Component API and builds a real BaseButton custom element step by step. The companion article picks it up from there and wraps it for first-class use in React.

A brief history

The idea of extending HTML with custom tags is nearly as old as the web itself. In 2011, Alex Russell and the Chrome team at Google published the first draft of what they called "Web Components," a set of four related specifications:

  • Custom Elements: define new HTML tags with their own behavior.
  • Shadow DOM: encapsulated markup and styles that don't leak in or out.
  • HTML Templates: inert, reusable markup fragments that get cloned into the page.
  • HTML Imports: a way to load one HTML document from another, later dropped from the spec.

The ambition was enormous: a native component model for the web that required no build tools and no framework. Browser vendors disagreed on the details for years. Firefox and Apple resisted parts of the v0 API. HTML Imports were eventually dropped entirely. The community moved on to v1 of the spec in 2016, and by 2020 all major browsers had shipped compatible implementations. Google's Polymer library, which had been the de facto way to use Web Components during the turbulent v0 era, gave way to lighter libraries like Lit, FAST, and Stencil. Today the APIs are stable, well-supported, and genuinely pleasant to use.

What did not change over that decade is the core motivation: a way to package behaviour, markup, and styles together in a self-contained unit, without depending on any particular framework to parse or execute it.

What they are and what they are good at

Web Components are built on three browser APIs that can be used independently or together:

Custom Elements let code define a new HTML tag (say, <base-button>) backed by a JavaScript class. The browser upgrades any matching element in the DOM by instantiating that class and calling lifecycle hooks.

Shadow DOM attaches a private subtree to an element. Styles defined inside the shadow root do not leak out, and external styles do not bleed in, which makes the component genuinely encapsulated.

HTML Templates provide a <template> element whose content is parsed but not rendered. Cloning it stamps out DOM cheaply and safely.

Web Components are strongest when a component needs to cross framework boundaries. A design system button, a date picker, a media player, a syntax highlighted code block: these are all good candidates. They are also a natural fit for teams that ship embeddable widgets, micro-frontends, or components that will outlive any particular framework choice.

They are less suited to application-level concerns: routing, global state, server data fetching. For those, use the framework that has already solved them well.

How they differ from framework components

Component frameworks, React, Vue, Svelte, Angular, and the rest, look similar to Web Components on the surface: both encapsulate markup, behaviour, and optionally styles. But they operate at completely different layers.

A framework component, a React function, a Vue single-file component, a Svelte file, is understood and rendered by that framework's own runtime or compiler. It only exists inside that framework's tree. The framework, not the browser, manages its lifecycle: mounting, updating, and unmounting. Passing data in means passing values through whatever prop mechanism the framework defines, and responding to changes means re-rendering, or for a compiled framework like Svelte, running the specific DOM updates the compiler generated ahead of time.

A custom element, by contrast, is a browser citizen. The DOM itself manages its lifecycle. Data flows in through HTML attributes (strings) and JavaScript properties (any value), and its events are regular DOM events. React, Vue, Svelte, Angular, or plain JavaScript can all interact with it through the same DOM APIs used for a <div>.

Key distinction

Most frameworks manage some kind of intermediate representation that eventually maps to real DOM: a virtual DOM in React, a reactive dependency graph in Vue, compiled update instructions in Svelte. Custom elements are real DOM already. The browser manages them directly. When a custom element is used inside any of these frameworks, the framework still only sees an opaque DOM node. It has no awareness of the element's internal lifecycle or shadow DOM.

This is why wrapping a Web Component for use in a framework like React, Vue, or Angular requires a little care: the gap between the framework's prop/event model and the DOM's attribute/property/event model has to be bridged manually. The companion article covers that bridge for React in detail.

Custom Elements

The entry point to Web Components is HTMLElement. Every custom element extends it, either directly or through one of the specialised subclasses like HTMLButtonElement. Custom element tag names must contain a hyphen. This is a parsing rule that reserves single-word names for future HTML elements.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  // The browser calls this once, when the class is first defined.
  constructor() {
    super(); // always first
  }
}

The super() call is non-negotiable: it sets up the element's prototype chain and associates the instance with the underlying DOM node. Leave it out and the browser throws a ReferenceError before anything else can run.

Defining elements

Once the class exists, it gets registered with the Custom Elements registry using customElements.define. From that moment forward, every <base-button> in the document (including ones already in the DOM) will be upgraded.

base-button.ts TypeScript 
// Pass the tag name, then the class. The name must contain a hyphen.
customElements.define('base-button', BaseButton);

Registrations are permanent and global. An element cannot be undefined, and the same name cannot be redefined. In practice this means guarding against double-registration in module-heavy environments:

base-button.ts TypeScript 
if (!customElements.get('base-button')) {
  customElements.define('base-button', BaseButton);
}

Shadow DOM

Shadow DOM creates a separate DOM tree attached to an element. Code outside the component cannot query into it with document.querySelector, styles do not cross the boundary by default, and IDs inside the shadow root are scoped to it. This is real encapsulation: not naming conventions, not CSS Modules, not build-time transforms.

A shadow root gets attached inside the constructor:

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;

  constructor() {
    super();
    // 'open' lets JS outside the element reach shadow internals
    // via element.shadowRoot. Use 'closed' to prevent that.
    this.shadow = this.attachShadow({ mode: 'open' });
  }
}

mode: 'open' is almost always the right choice. Closed shadow roots are a footgun. They break accessibility tools and testing libraries without providing meaningful security, since motivated code can always get around them.

Setting CSS

Styles inside a shadow root are written as regular CSS but are completely scoped. The :host pseudo-class styles the custom element itself (the outer DOM node) from within the shadow. The modern approach uses Constructable Stylesheets, which lets multiple elements share a single parsed stylesheet object rather than injecting a <style> tag per instance.

base-button.ts TypeScript 
// Create once at module scope so all instances share one stylesheet
const sheet = new CSSStyleSheet();
sheet.replaceSync(`
  :host { display: inline-flex; cursor: pointer; }

  /* Attribute selectors read state straight off the host element */
  :host([variant="primary"]) button { background: #f0a500; }
  :host([disabled]) { opacity: 0.45; pointer-events: none; }
`);

// Adopt it in the constructor, so every instance shares one parsed sheet
this.shadow.adoptedStyleSheets = [sheet];

CSS Custom Properties (variables) defined on :host or outside the component do cross the shadow boundary. This is intentional. It is the recommended way to expose a theming API from a Web Component: define --base-button-radius on :host, let consumers override it on the element or any ancestor.

HTML Templates

A <template> element's content is a DocumentFragment that is parsed by the HTML parser but never rendered. Cloning it is cheap: no re-parsing, no layout, no paint. The <slot> element inside a template is a placeholder for light DOM children, which lets consumers of the component write natural HTML inside the tag.

base-button.ts TypeScript 
const template = document.createElement('template');
template.innerHTML = `
  <button part="button">
    <slot name="prefix"></slot>
    <slot></slot>
    <slot name="suffix"></slot>
  </button>
`;

// Inside the constructor, clone and append:
this.shadow.appendChild(template.content.cloneNode(true));

The part attribute on the inner button exposes a named part to the ::part() CSS pseudo-element, letting consumers style internals from outside the shadow root in a controlled way.

Building BaseButton: step by step

Now that the primitives are in place, it's time to build the component properly. What follows covers lifecycle callbacks, observed attributes, properties, and events in sequence, ending with the full component.

Lifecycle callbacks

Custom elements have four lifecycle callbacks. Three of them matter in practice:

connectedCallback fires when the element is inserted into a document. This is the right place to attach event listeners, start observers, or render imperative content that depends on being in the DOM. Roughly comparable to a framework's mount phase: React's useLayoutEffect combined with component mount, Vue's onMounted, or Svelte's onMount.

disconnectedCallback fires when the element is removed from a document. Clean up event listeners and any external subscriptions here. Roughly comparable to a framework's unmount phase: the cleanup function returned from React's useEffect, Vue's onUnmounted, or Svelte's onDestroy.

attributeChangedCallback fires when one of the element's observed attributes changes. More on this shortly.

The fourth, adoptedCallback, fires when the element is moved into a different document (via document.adoptNode). This is rare in practice and rarely needed.

A gotcha with connectedCallback

An element can be connected and disconnected multiple times, for example if it is moved in the DOM. Do not assume connectedCallback runs exactly once. Relatedly, listeners should always be removed in disconnectedCallback, even when the element seems permanent.

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  private shadow: ShadowRoot;
  private innerButton: HTMLButtonElement | null = null;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    this.shadow.adoptedStyleSheets = [sheet];
    this.shadow.appendChild(template.content.cloneNode(true));
  }

  connectedCallback() {
    this.innerButton = this.shadow.querySelector('button');
    this.innerButton?.addEventListener('click', this.handleClick);
    this.syncDisabled();
    this.syncType();
  }

  disconnectedCallback() {
    this.innerButton?.removeEventListener('click', this.handleClick);
    this.innerButton = null;
  }
}

Observed attributes and attributeChangedCallback

Attributes on a custom element are always strings. Writing <base-button disabled> gives an attribute value of an empty string, not a boolean. The browser will only call attributeChangedCallback for attributes listed in the static observedAttributes array. Any attribute left off that list has its changes silently ignored.

base-button.ts TypeScript 
// Tell the browser which attributes to watch
static get observedAttributes(): string[] {
  return ['disabled', 'variant', 'size', 'type'];
}

attributeChangedCallback(name: string) {
  if (name === 'disabled') this.syncDisabled();
  // 'type' gets the same treatment. 'variant' and 'size' are read
  // straight off the attribute in CSS, via :host([variant="…"])
}

Notice that attributeChangedCallback may fire before connectedCallback. This can happen when the element is parsed from HTML. Attributes are processed first. The sync methods guard against a null innerButton for exactly this reason.

Properties and upgrading them

Attributes are a limited surface: they only accept strings, and they are part of the HTML serialisation. For richer data (booleans, numbers, objects), JavaScript properties get exposed on the element class instead. Properties and attributes should mirror each other for the common cases, using a pattern sometimes called "attribute/property reflection":

base-button.ts TypeScript 
class BaseButton extends HTMLElement {
  // Expose a boolean `disabled` property that mirrors the attribute
  get disabled(): boolean {
    return this.hasAttribute('disabled');
  }
  set disabled(value: boolean) {
    value
      ? this.setAttribute('disabled', '')
      : this.removeAttribute('disabled');
  }

  // variant, size, and type follow the same get/set-through-attribute shape
}

There is a subtle problem here called the property upgrade timing issue. If someone sets myButton.disabled = true using JavaScript before the custom element class has been defined and the element upgraded, the property assignment goes to the raw DOM node as a plain expando, not through the class's setter. When the upgrade eventually happens, that setter never fires.

The fix is to check for and apply any pre-upgrade expando properties in connectedCallback. One TypeScript wrinkle: disabled, variant, size, and type are all required properties on the class, so a plain delete this[prop] fails to compile with TS2790, since the compiler only allows deleting properties it considers optional. Reflect.deleteProperty does the same thing at runtime without that restriction:

base-button.ts TypeScript 
private upgradeProperty(prop: keyof this) {
  if (Object.prototype.hasOwnProperty.call(this, prop)) {
    const value = this[prop];
    // Required properties aren't optional in TS's eyes, so a plain
    // `delete this[prop]` fails to compile (TS2790). Reflect.deleteProperty
    // does the same job without fighting the type checker.
    Reflect.deleteProperty(this, prop); // remove the expando
    this[prop] = value;  // re-set through the class setter
  }
}

connectedCallback() {
  this.upgradeProperty('disabled');
  this.upgradeProperty('variant');
  this.upgradeProperty('size');
  this.upgradeProperty('type');
  // ... rest of setup
}

Custom events

Web Components communicate outward through DOM events. The convention is to dispatch a CustomEvent with a namespaced name. Prefixing with the component name prevents collisions. Setting composed: true is required when an event originates within a shadow tree and must cross the shadow boundary. It is not strictly necessary when dispatching from the host element itself.

base-button.ts TypeScript 
// Type the detail payload for consumers
interface BaseButtonClickDetail {
  originalEvent: MouseEvent;
  variant: Variant;
  disabled: boolean;
}

private handleClick = (e: MouseEvent) => {
  // Prevent the native click from propagating out of the shadow
  e.stopPropagation();

  const detail: BaseButtonClickDetail = {
    originalEvent: e,
    variant: this.variant,
    disabled: this.disabled,
  };

  this.dispatchEvent(
    new CustomEvent<BaseButtonClickDetail>('base-button:click', {
      detail,
      bubbles:  true,
      composed: true, // cross the shadow boundary
    })
  );
};

// Arrow function stored as a class field so `this` is always bound,
// and so the exact same reference can be removed in disconnectedCallback.

The arrow function stored as a class field is important. A regular method reference (this.handleClick) would require each call to addEventListener and removeEventListener to use the same bound reference, a common source of listener leaks.

The full component

Every piece covered so far (the shared stylesheet, the template, the lifecycle callbacks, the observed attributes, the property accessors, the upgrade guard, and the click handler) lives on the same class. The registration guard at the bottom avoids the "already defined" error that shows up in hot-reloading dev environments. The complete, unabridged file is in the full source section below.

That's the complete platform-level picture: a custom element with encapsulated styles, a template-based shadow DOM, typed properties, and a custom event. It runs in any framework, or none at all, with no build step required beyond compiling the TypeScript itself.

The same kind of bridging is needed for any component framework: typed props, forwarded refs or bindings, and glue code that reconciles the framework's render model with the DOM's imperative one. The companion article, Wrapping Web Components in React, works through that bridge for React specifically.

  <button part="button">

// ── Element class ──────────────────────────────────────
export class BaseButton extends HTMLElement {
  static readonly tagName = 'base-button';

  static get observedAttributes() {
    return ['disabled', 'variant', 'size', 'type'] as const;
  }

  private shadow: ShadowRoot;
  private innerButton: HTMLButtonElement | null = null;

  constructor() {
    super();
    this.shadow = this.attachShadow({ mode: 'open' });
    this.shadow.adoptedStyleSheets = [sheet];
    this.shadow.appendChild(template.content.cloneNode(true));
  }

  // ── Lifecycle ──────────────────────────────────────────
  connectedCallback() {
    this.upgradeProperty('disabled');
    this.upgradeProperty('variant');
    this.upgradeProperty('size');
    this.upgradeProperty('type');

    this.innerButton = this.shadow.querySelector('button');
    this.innerButton?.addEventListener('click', this.handleClick);
    this.syncAll();
  }

  disconnectedCallback() {
    this.innerButton?.removeEventListener('click', this.handleClick);
    this.innerButton = null;
  }

  attributeChangedCallback(
    name: string,
    _old: string | null,
    _next: string | null
  ) {
    if (name === 'disabled') this.syncDisabled();
    if (name === 'type') this.syncType();
  }

  // ── Properties ────────────────────────────────────────
  get disabled() { return this.hasAttribute('disabled'); }
  set disabled(v: boolean) {
    v ? this.setAttribute('disabled', '') : this.removeAttribute('disabled');
  }

  get variant(): Variant {
    return (this.getAttribute('variant') ?? 'primary') as Variant;
  }
  set variant(v: Variant) { this.setAttribute('variant', v); }

  get size(): Size {
    return (this.getAttribute('size') ?? 'md') as Size;
  }
  set size(v: Size) { this.setAttribute('size', v); }

  get type(): BtnType {
    return (this.getAttribute('type') ?? 'button') as BtnType;
  }
  set type(v: BtnType) { this.setAttribute('type', v); }

  // ── Private helpers ────────────────────────────────────
  private upgradeProperty(prop: keyof this) {
    if (Object.prototype.hasOwnProperty.call(this, prop)) {
      const value = this[prop];
      Reflect.deleteProperty(this, prop);
      this[prop] = value;
    }
  }

  private syncDisabled() {
    if (this.innerButton) this.innerButton.disabled = this.disabled;
  }

  private syncType() {
    if (this.innerButton)
      this.innerButton.type = this.type as HTMLButtonElement['type'];
  }

  private syncAll() {
    this.syncDisabled();
    this.syncType();
  }

  // ── Event handler ──────────────────────────────────────
  private handleClick = (e: MouseEvent) => {
    e.stopPropagation();
    this.dispatchEvent(
      new CustomEvent<BaseButtonClickDetail>('base-button:click', {
        detail: {
          originalEvent: e,
          variant: this.variant,
          disabled: this.disabled,
        },
        bubbles: true,
        composed: true,
      })
    );
  };
}

// ── Registration ───────────────────────────────────────
if (!customElements.get(BaseButton.tagName)) {
  customElements.define(BaseButton.tagName, BaseButton);
}
