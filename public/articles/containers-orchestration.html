Containers and Orchestration

How container images become running workloads, how Kubernetes coordinates them, and when a simpler platform fits better.

Andreas Ögren
~26 min read
Last updated August 2026

Applications depend on more than their source code. They need runtimes, system libraries, configuration, and other dependencies. When these pieces are installed separately on each machine, differences between development, testing, and production can cause an application to behave differently after deployment.

A container image packages an application with the files and dependencies it needs to run. A team can build and test an image once, then use the same artifact across environments. When the image is started, it runs as a container, using the host's kernel while remaining isolated from other processes. This article uses Docker to build images and run containers.

Running a few containers on one machine is relatively straightforward. Across multiple machines, workloads need to be placed where resources are available, restarted after failures, connected so they can find one another, and updated without unnecessarily interrupting users. An orchestrator automates these tasks across a pool of machines called a cluster.

Kubernetes is an orchestrator for running and managing containerized workloads. Teams describe the workloads and resources they want through the Kubernetes API, and Kubernetes continually works to keep the cluster in that desired state. This article follows that path from Docker and containers through Kubernetes and Helm, then explains which responsibilities are outside Kubernetes' scope.

Why Containers

Containers reduce environment drift and make replacement a repeatable operation.

Traditional server deployments install an application directly onto a long-lived machine. Patches, emergency edits, and dependency upgrades accumulate over time, so machines that began from the same setup can diverge. Environment drift is the resulting difference between environments that were intended to behave alike.

Virtual machines

A virtual machine (VM) packages a complete guest operating system on a hypervisor, software that divides one physical machine's CPU, memory, and storage among several guests. The guest operating system travels inside the VM, so moving the VM to a new host reproduces the same environment. This reduces environment drift compared with installing an application directly on a physical machine.

Containers

A container packages the application and its dependencies and runs them as isolated processes on the host's existing kernel. A VM runs its own guest operating system, while a container shares the host kernel. Without a guest OS to start or store, a container usually starts faster and uses less storage and memory. Kernel sharing provides less isolation than hardware virtualization, but that mostly matters when mutually untrusted tenants share the same host.

The figure compares a VM with the common Linux process-isolation model. Each container has its own namespace and cgroup membership, implemented by the shared host kernel. Windows and hypervisor-isolated containers use different boundaries, which the next section describes.

Immutable infrastructure

An image is a read-only package that includes everything needed to run a container, including files, binaries, libraries, and process configuration. Starting an image creates a container, a running instance with its own writable layer and one or more processes. The image underneath stays unchanged, so the same image can start any number of containers without affecting one another.

Container deployments usually apply application and dependency changes by replacing an instance. Starting a container is fast and inexpensive enough for this model. A team builds and tests a new image, starts containers from the new image, and removes the old containers. The artifact that passed testing is therefore the one that runs in production. Runtime changes are recorded in a versioned build definition and applied through a replacement image. This replacement model is known as immutable infrastructure.

What a Container Is

An image supplies the filesystem and process configuration. A container runtime starts an isolated process based on the image.

Docker is a widely used containerization platform. It pairs a command-line client with a background daemon that builds images and starts containers from them. Docker Hub is its public registry, a service that stores images so teams can publish and retrieve them. Docker did not invent the kernel isolation mechanisms containers rely on, but it packaged them behind one accessible workflow along with a layered filesystem for images, turning tools that once required deep Linux systems knowledge into commands any developer could run.

As containers caught on, tool developers needed a way to build and run images without tying every tool to Docker specifically. Docker, CoreOS, and other container projects founded the Open Container Initiative (OCI) in 2015 to standardize container images and runtimes. OCI specifications define the image format, the configuration and lifecycle expected by a low-level runtime, and the protocol used to distribute images. Independent tools can exchange these standardized artifacts without depending on Docker.

A container runtime is the software that starts a container from an image and enforces its isolation using the host kernel. Several Linux kernel features work together to achieve this isolation. Namespaces give a process a scoped view of resources such as process identifiers, mounts, users, and network interfaces, so it sees what looks like its own machine even though it is running alongside others. Control groups (cgroups) account for and constrain resources such as CPU and memory, so one container cannot starve the others. Capabilities divide privileged operations into smaller permissions, seccomp profiles filter system calls, and mandatory access controls apply security rules to processes and files. The resulting isolation depends on these settings and the security of the shared kernel.

Windows supports process isolation and Hyper-V isolation. Hyper-V isolation gives each container a lightweight VM and its own kernel, trading away some of the speed and density benefits of a shared kernel for stronger isolation between containers. Kubernetes support for Windows containers is limited to process isolation on Windows nodes. The shared-kernel examples below use Linux terms such as namespaces and cgroups.

Supply Chain

An image digest gives the build, registry, and deployment stages one identity for the packaged software.

A Dockerfile is a text file that lists, in order, the instructions used to assemble an image. FROM selects a base image, and instructions such as COPY and RUN create filesystem layers on top of it. Instructions such as WORKDIR and CMD set image configuration. The builder processes the instructions from top to bottom, so each step operates on the result of the steps before it.

Dockerfile Dockerfile 
# Stage 1: build, with the full toolchain
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev

# Stage 2: runtime dependencies and build output
FROM node:24-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
CMD ["node", "dist/server.js"]

The example uses a multi-stage build. The first stage contains the toolchain and source needed to produce the application. The final stage copies selected output and runtime dependencies into a fresh base. The exported image omits the build tools, which reduces its size and the software exposed at runtime.

The builder reuses a cached result when an instruction and its inputs match an earlier build. Once an instruction misses the cache, every instruction after it reruns as well, even when its own inputs haven't changed. The example takes advantage of this by installing dependencies with npm ci before copying in the application source, so an edit to the source code does not invalidate the cached dependency layer. Placing stable steps like dependency installation before frequently changing ones like copying source files preserves more of the cache and shortens rebuilds. The exported image stores each of these steps as a read-only filesystem layer, and registries and hosts can share identical layers across separate images.

A CI/CD pipeline builds the image in a controlled, repeatable environment, runs automated tests and security scans, attaches a provenance record describing how the build was produced or a cryptographic signature, and publishes the image to a registry. An image manifest lists the image's configuration and filesystem layers. A cryptographic digest identifies the manifest and selects the exact image content for later environments.

The image supports several architectural controls:

  • Repeatability. A digest selects the same image content wherever it is deployed, although runtime configuration and host operating system behavior can still affect execution.
  • Immutability. Image content is read-only. Tags are mutable references, so a digest provides the stable identity for promotion and verification.
  • Versioning. Tags provide readable labels, while digests provide an exact answer to which image content a deployment selected.
  • Promotion through environments. Staging and production can select the same digest. Using one digest avoids a rebuild that might silently choose a different dependency version.
  • Vulnerability scanning. A scanner compares the packages it detects with vulnerability data. Its report covers those detected packages and known vulnerabilities.
  • Supply-chain integrity. Signatures and provenance can bind an image digest to a build identity. A software bill of materials (SBOM) records components for later analysis.

These controls apply to container deployments with or without Kubernetes. Kubernetes schedules workloads whose container specifications refer to images, so tags, digests, registry policy, and build evidence carry into the cluster. The image identifies the packaged software. The workload specification and runtime configuration add the environment-specific part of the deployment record.

Why Orchestration Exists

Across several hosts, a deployment needs placement, replacement, and stable routes to healthy instances.

A process manager, Docker Compose, or a similar tool can run containers on a single host, handle restarts, and let containers reach each other. Once an application spans multiple machines, new coordination problems appear. Workloads need placement on hosts with enough capacity, failed instances need automatic replacement, and clients need a stable way to reach a service even as its containers stop, restart, or move.

An orchestrator addresses these problems by managing a cluster as one pool of resources. Teams declare the desired state of an application, including how many instances to run, how much CPU and memory each one needs, and where they may be placed. The orchestrator continuously compares that declaration with the cluster's actual state. When a host fails, it reschedules the affected workloads onto another one. When an instance becomes unhealthy, it replaces that instance. An autoscaler can increase the declared number of instances as demand grows.

Docker Swarm, HashiCorp Nomad, and Kubernetes all coordinate container workloads across multiple hosts. They share the goal of maintaining desired applications and automating operational tasks, but they differ significantly in their APIs, scheduling capabilities, ecosystem maturity, and operational complexity.

Core Objects

Each Kubernetes object describes one part of a running workload or the behavior around it.

An orchestrator maintains a declared state, and Kubernetes represents it as a set of API objects. A team creates these objects to describe what it wants, such as how many instances of an application should be run and how they should be reachable, and Kubernetes continuously works to make the cluster's actual state match the declared state. Each object type is responsible for one part of that description, from running a set of containers to routing traffic to them.

Pod

A Pod is the smallest deployable unit in Kubernetes. It groups one or more containers that are scheduled together, share a network namespace, and can share selected storage volumes. Most Pods run a single container. A Pod holds more than one when those containers need to run on the same machine and share that network or storage, such as the sidecar pattern, where a supporting container extends the main application by proxying its network traffic or synchronizing files with it. Even inside a shared Pod, each container keeps its own filesystem and resource settings.

Pods are disposable. Kubernetes replaces a failed or evicted Pod with a new one that has a new IP address and identity, rather than restarting the old Pod in place. An eviction deliberately removes a Pod from a node, often because the node is short of resources or needs maintenance. Applications run through objects that create and replace Pods as needed.

Deployment

A Deployment manages a set of identical Pods for a stateless application, whose durable data lives outside its instances. It creates the requested number of Pod replicas from one template and replaces any that fail, keeping the declared number of instances running without manual intervention. A Deployment does this through a ReplicaSet, an object that keeps a fixed number of Pods matching one template running. The Deployment creates a new ReplicaSet for each Pod template and shifts replicas from the old one to the new one during a rollout.

Service

A Service gives a changing set of Pods one stable network identity. A Deployment creates replacement Pods with new IP addresses, so clients need an address independent of any individual Pod. A Service selects Pods by label, a key-value tag attached to a Kubernetes object, and exposes them behind one stable address.

Gateway API and Ingress

The Gateway API describes how traffic enters a cluster and reaches Services. A Gateway represents the traffic-handling infrastructure, while an HTTPRoute maps hostnames and paths to Services. A compatible controller reads these resources and configures a load balancer or reverse proxy. Gateway API is installed as an add-on and supports features such as traffic weighting. Its resource model separates the concerns of infrastructure providers, cluster operators, and application developers. The older Ingress API provides simpler HTTP routing and is still common in existing clusters, though its API is frozen.

Several supporting objects scope and configure these four. A Namespace groups related objects under one set of names and policies, letting a cluster host multiple teams, applications, or environments without name collisions. A ResourceQuota can cap the aggregate resources and object counts allowed within a Namespace. A ConfigMap stores non-sensitive configuration separately from the container image, so the same image can run with different settings in each environment. A Secret holds sensitive configuration separately since its security depends on access controls and encryption settings.

Other objects manage workloads with a different lifecycle than a Deployment's stateless replicas. A Job runs Pods until a task completes, and a CronJob creates Jobs on a schedule. A DaemonSet places one Pod on every eligible node, or on a selected subset, for node-local functions such as networking and log collection.

Control Plane and Worker Nodes

Kubernetes separates cluster coordination from the machines that run application containers.

A Kubernetes cluster separates coordination from workload execution, so problems in a running application are less likely to affect the components that keep the whole cluster running. The control plane exposes the API, stores cluster data, schedules Pods, and runs controllers. Worker nodes provide the compute on which application Pods run. Small and development clusters can place both roles on one machine but the responsibilities are separated even when the components share a host.

The API server accepts and validates requests that read or change cluster state, and stores that state in etcd, a distributed key-value database. The scheduler watches for Pods that have been created but have no assigned node, and picks one for each. Controllers continuously compare what has been created with what was requested and correct any difference, such as recreating a Pod that disappeared. This repeating comparison is reconciliation.

A worker node runs the components that turn an assigned Pod specification into containers and network routes:

  • The kubelet watches the Pod specifications assigned to its node and asks the runtime to create their containers.
  • The container runtime pulls images and manages container lifecycles through the Container Runtime Interface (CRI).
  • kube-proxy implements Service networking on many clusters. Clusters that use another service dataplane can omit it.

Updating a Deployment changes the desired Pod template through the API server. The Deployment controller creates a new ReplicaSet, the scheduler assigns its pending Pods to nodes, and each node's kubelet asks the local runtime to start them. Thus, several independent control loops cooperate to perform the deployment.

Control-plane responsibility in managed Kubernetes

Managed services such as Amazon EKS, Google Kubernetes Engine, and Azure Kubernetes Service operate the control plane for the customer. Each service draws a different line around nodes, upgrades, networking, policy, and add-ons.

Helm Charts and Releases

Helm renders a configurable set of Kubernetes resources and tracks each installed instance.

A Kubernetes manifest is a YAML or JSON document that declares one or more API objects. Raw manifests work well when an application has only a few resources and one configuration. Across several environments, most of the YAML stays the same and a small set of settings changes. Copying the YAML gives those shared parts room to diverge. Helm adds a templating and packaging layer for the resources. Helm renders the templates into standard manifests and submits the resulting resources to the Kubernetes API. Kubernetes then validates, accepts, and reconciles the rendered objects in the usual way.

Helm chart

A Helm chart is a versioned package of files that describe a related set of Kubernetes resources. Its required Chart.yaml file identifies the chart and its version. The templates/ directory contains manifest templates, and a values.yaml file supplies their default inputs. The key idea to make charts reusable by separating templates from values. The chart can keep the YAML files for the Deployment and Service together as one package, while exposing the image tag, replica count, and Service port as settings for each environment.

Values file

The values file supplies configuration for one use of the chart. Helm merges user-supplied values over the chart's defaults, then evaluates the templates to produce concrete manifests. Separate values files can select development and production settings without copying the whole resource set. Teams review and validate the rendered output with the same policy checks they use for handwritten YAML.

Releases

Installing a chart creates a release, which is one named instance of that chart in a cluster namespace. One chart can produce several independent releases with different names and values, such as installing the same application separately for a staging namespace and a production namespace. Helm records the chart, configuration, and rendered resources for each release revision. A chart version identifies the package while a release revision identifies a point in the history of one installation.

An upgrade renders the selected chart and values for an existing release, updates the affected Kubernetes resources, and records a new revision. A rollback selects an earlier release revision and applies its resource definitions as another revision. The rollback can restore an earlier Deployment image or configuration. Helm has no record of database migrations, messages sent to other systems, or other side effects outside the Kubernetes resources. Application changes need compatibility and recovery plans for those effects.

Scheduling and Resource Management

The scheduler uses resource requests and placement rules to select a node. The node enforces resource limits at runtime.

A node's CPU and memory are finite, and several Pods usually share the same one, so Kubernetes needs to know how much each container needs before deciding where to place it, and needs a way to stop one container from using more than its share once it is running. Each container can declare a request and a limit for resources such as CPU and memory. A request reserves capacity for scheduling. The scheduler adds the requests for a Pod and chooses a node with enough allocatable capacity. A limit constrains runtime use. On Linux, the container runtime normally maps limits to cgroups. The kernel enforces a CPU limit by throttling the process. When a process tries to allocate memory above its limit, the kernel may terminate it through an out-of-memory kill.

Kubernetes schedules a Pod only on nodes that have enough available resources and that satisfy the Pod's placement rules. A taint repels Pods from a node unless they carry a matching toleration. Combining that pair with node affinity can reserve nodes for particular workloads, such as keeping ordinary applications off GPU nodes. Node affinity requires or prefers nodes with selected labels. Pod affinity and anti-affinity place workloads near each other or keep them apart. Topology spread constraints distribute replicas across failure domains, parts of the cluster such as nodes or zones that can fail independently.

Networking

Kubernetes networking covers Pod addresses, stable Service discovery, and traffic entering the cluster.

A cluster's networking has to let external traffic into the cluster and route traffic between Pods as they are replaced. Kubernetes gives every Pod its own IP on a shared cluster network. A Container Network Interface (CNI) plugin assigns Pod addresses and connects them across nodes. Pods can then communicate without address translation between them, so a Pod's address looks the same to itself and to every other Pod in the cluster.

By default, every Pod accepts network traffic from any other Pod in the cluster. A NetworkPolicy turns this default-open behavior into an explicit allow list by declaring the permitted incoming traffic (ingress) or outgoing traffic (egress) for selected Pods. Namespaces provide no automatic network isolation. Workloads that cross trust boundaries need explicit policies and a CNI plugin that enforces them.

Replacement Pods receive new addresses, so a client that remembered one would eventually try to reach a Pod that no longer exists. Service networking solves this by giving clients a stable destination for replaceable Pods. A Service represents a changing set of endpoints and usually provides a virtual IP plus DNS discovery. kube-proxy implements the forwarding rules on many clusters. Alternative dataplanes can provide the same Service behavior. A stable Service in front of changing Pods matches the load-balancing pattern from Web Application Networking.

Edge routing sends external traffic into the cluster. A Service of type LoadBalancer can expose one network service directly. Providing every HTTP-facing Service with its own load balancer becomes expensive and difficult to manage as the number of applications grows. Ingress and Gateway API resources let many Services share one entry point and describe HTTP routes from hostnames and paths to Services. These entry points commonly terminate TLS, where the controller decrypts the incoming connection using a certificate stored in a Secret, then forwards the request to a Service. A separate controller implements the declared rules. The Kubernetes project has frozen the Ingress API and recommends Gateway for new capabilities. Both provide the reverse proxy role at the cluster boundary.

State and Storage

Kubernetes can preserve storage and workload identity.

Deployment Pods are designed to be replaceable. This works well for stateless applications because their durable data is stored elsewhere, so a failed Pod can be replaced on another node. Stateful applications, such as databases, have additional requirements because their data must survive Pod replacement. Individual replicas may need stable identities, and operations such as replication, backup, and recovery must preserve the data correctly. Kubernetes provides the building blocks for persistent storage and stable identity. The application or a database operator, a controller that automates database-specific operations, handles the remaining behavior.

A PersistentVolume represents storage available to the cluster, while a PersistentVolumeClaim is a request for storage that a workload can use. Kubernetes binds the claim to suitable storage, which may be provisioned dynamically through a Container Storage Interface driver that connects Kubernetes to the underlying storage system. A StatefulSet gives its Pods stable identities and supports ordered deployment, scaling, and termination. When a StatefulSet defines volume claim templates, Kubernetes creates a separate PersistentVolumeClaim for each Pod, allowing its storage to persist when that Pod is replaced.

A StorageClass defines a type of storage and how it should be provisioned. When a PersistentVolumeClaim requests that class, Kubernetes can dynamically provision a suitable volume on demand. Details such as where the storage can be attached, how it can be accessed, whether it is retained after release, and how backup and restore work depend on the StorageClass configuration, storage provider, and workload design.

In-Cluster
Run stateful workloads on Kubernetes

Running the workload in the cluster keeps its configuration under the Kubernetes control plane. The team or a database operator handles replication, backup, failover, upgrades, and recovery testing. This fits organizations that have the required expertise or need cluster-local operation.

Externalized
Use a managed database service

A managed relational, NoSQL, or messaging service moves part of the operational work to a provider. The exact service determines which backups, upgrades, failover modes, and recovery guarantees are included. Cluster workloads connect to it over the network.

Stateless workloads fit naturally with Kubernetes because their Pods can be replaced without preserving local state. Stateful workloads can run effectively on Kubernetes when reliable storage is available and the application or an operator can manage replication, backup, recovery, and upgrades. A managed external service shifts much of this operational responsibility to the service provider. The choice is therefore not just about where the data is stored, but also about who is responsible for operating and protecting it.

Deployment and Rollout Strategies

A rollout strategy balances downtime, temporary resource use, and exposure to a faulty version.

Kubernetes uses probe results to decide when a new container can receive traffic and when the kubelet should restart it. A startup probe delays the other checks until initialization completes, giving a slow-starting application room to boot without being mistaken for unhealthy. A readiness probe controls whether Services send traffic to the Pod. A container can be running normally but not yet ready for requests, such as while it is still warming a cache, so failing this probe pulls it out of rotation without restarting it. A liveness probe tells the kubelet when to restart a container, for cases where the process is technically still running but stuck in a way only a restart can fix.

When an application is updated, Kubernetes needs to replace the old Pods without unnecessarily interrupting service. By default, a Deployment uses a RollingUpdate, which gradually scales up a new ReplicaSet and scales down the old one within the maxSurge and maxUnavailable bounds. Alternatively, the Recreate strategy removes the old Pods before creating the new ones, which can cause a period of unavailability.

Applications can use broader rollout patterns to control how new versions are introduced and receive traffic. Rolling, blue-green, and canary rollouts make different trade-offs between availability, resource usage, rollback speed, and the risk of exposing users to a faulty release.

RequirementStrategyHow it works
Gradual replacement with controlled availabilityRolling updateA Deployment scales old and new ReplicaSets within the configured surge and unavailability bounds.
Quickly reverse the traffic cutoverBlue-greenTwo versions run side by side. Traffic can switch back quickly when their state changes are compatible.
Limit exposure to a risky changeCanaryThe new version receives a small slice of real traffic first. Its share increases after health and behavior checks pass.

Kubernetes provides different levels of native support for these patterns. A Deployment implements rolling replacement directly through RollingUpdate. Blue-green and canary need additional mechanisms to control which version receives traffic. Blue-green can switch traffic between parallel versions using resources such as Services. Precise canary traffic weighting requires a capable gateway, ingress controller, service mesh that manages service-to-service traffic, or rollout controller.

Infrastructure maintenance creates a different kind of interruption. A PodDisruptionBudget (PDB) limits how many Pods may be unavailable during voluntary disruptions, such as draining a node by safely evicting its workloads for maintenance. If another eviction would violate the budget, the drain may have to wait. A PDB does not prevent involuntary failures, such as a node failure, and cannot maintain availability when the cluster lacks capacity for replacement Pods.

Scaling

Workload replicas, Pod resources, and cluster nodes scale through separate control loops.

Horizontal scaling changes the number of workload instances. Vertical scaling changes the resources available to each instance. Their effectiveness depends on how the application uses those resources. Horizontal scaling increases capacity by adding replicas, so the application's work must be distributable among them. A stateless web server handling many independent requests is a natural fit. A single job that cannot divide its work gains little from additional replicas.

It is impractical to manually adjust replica counts as demand changes, so Kubernetes can automate the process. A HorizontalPodAutoscaler periodically adjusts a scalable workload's desired replica count from observed metrics. These can describe resources such as CPU and memory or application demand such as request rate and queue length. CPU and memory scaling relies on a cluster metrics API and appropriate resource requests.

Additional Pods require somewhere to run. A node autoscaler can add nodes when Pods cannot be scheduled because the cluster lacks suitable capacity. It can remove eligible underused nodes according to its implementation and provider integration. Pod and node autoscaling operate through separate control loops, so scaling may take longer when Kubernetes must first provision a node and then start the new Pods.

VerticalPodAutoscaler (VPA) is a separately installed controller that chooses CPU and memory requests for Pods. It uses observed resource usage to recommend or apply new requests as workload needs change. Its update mode determines how recommendations reach running Pods. Recreate evicts a Pod so its workload controller can replace it. When supported by the installed VPA and cluster, InPlaceOrRecreate attempts an in-place resize and falls back to replacement when necessary. Horizontal and vertical autoscaling need careful configuration when they respond to the same resource metrics because their control loops can interact and produce unstable scaling behavior.

The Platform Around Kubernetes

A production platform combines Kubernetes with application telemetry, security policy, delivery, and recovery systems.

Observability

Kubernetes can tell you whether workloads and nodes are running, and it exposes status, events, and system metrics. That information helps diagnose the cluster, but it does not explain everything happening inside an application. Teams need logs, application metrics, traces, dashboards, and alerts to understand application behavior. Kubernetes can integrate with these tools as part of a complete observability system.

Secrets

Applications need a safe way to receive passwords, API keys, and other sensitive values. Kubernetes provides Secrets to keep these values separate from ordinary configuration. The data field in a Secret manifest uses base64 encoding, which provides no encryption. Teams must decide who can access secrets, how they are encrypted at rest and rotated, and whether they should come from an external secret store.

Admission policy

Kubernetes can restrict what Pods are allowed to do through Pod Security Admission, which applies built-in security profiles when a Pod is created. Organizations often need additional rules specific to their environment, such as requiring particular labels or allowing images only from approved registries. Admission policies or a separate policy engine can enforce rules defined by the organization.

Build and delivery

A CI/CD pipeline builds container images. The pipeline, image registry, vulnerability scanning tools, and the team's release process determine whether an image is safe to deploy. Kubernetes receives the resulting image and manages the workload that runs it.

Backup and recovery

Kubernetes can attach persistent storage to workloads. Teams need a backup and disaster recovery strategy that defines what data to back up, where copies are stored, how long they are retained, and how applications and data are restored after a failure. Storage and backup tools implement those decisions.

A production Kubernetes platform includes more than the cluster itself. Kubernetes provides the API and controllers that coordinate workloads. Surrounding systems handle delivery, identity, policy, observability, secrets, and recovery.
