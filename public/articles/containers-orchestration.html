Containers and Orchestration

How container images become running workloads, how Kubernetes coordinates them, and when a simpler platform fits better.

Andreas Ögren
~23 min read
Last updated August 2026

Applications depend on more than their own source code. A deployment also needs a runtime, system libraries, and configuration that agree with the environment used for testing. Installing those pieces separately on each machine leaves room for drift, even when the setup begins from the same instructions.

Containers solve that problem by packaging an application with everything it depends on into one portable image, so the same image behaves the same way wherever it runs. Docker is the platform most teams use to build and run those images, and it's the one this article refers to throughout.

Once containers are spread across several hosts, someone or something still has to decide where each one runs and step in when one fails. Other services need a reliable way to find it, and rolling out a new version means replacing containers without taking the application down.

An orchestrator is software that takes on these responsibilities, coordinating placement, recovery, discovery, and rollouts across a pool of machines. Kubernetes is the orchestrator this article focuses on. It gives teams one consistent API for describing what a workload needs, but operating it also means running a cluster and the platform services around it. A smaller deployment may not need any of that. Running containers on a single host or through a managed container service can be simpler than operating a cluster.

Why Containers

Containers reduce environment drift and make replacement a repeatable operation.

Traditional server deployments install an application directly onto a long-lived machine. Patches, emergency edits, and dependency upgrades accumulate over time, so machines that began from the same setup can diverge. Environment drift is the resulting difference between environments that were intended to behave alike.

Virtual machines

A virtual machine (VM) packages a complete guest operating system on a hypervisor, software that divides one physical machine's CPU, memory, and storage among several guests. Because the guest operating system travels inside the VM, moving it to a new host reproduces the same environment instead of depending on whatever that host has installed. This reduces environment drift compared to installing directly on a physical machine, since the VM carries its own operating system wherever it goes.

Containers

A container packages just the application and its own dependencies, not an entire operating system, and it runs as an isolated process on the host's existing kernel rather than inside a guest OS of its own. Compared to a VM, a container is faster to start and lighter on storage and memory, since there's no guest operating system to start or store. The downside is that isolation comes from the kernel itself rather than from a hypervisor. Sharing a kernel provides weaker isolation than hardware virtualization, which matters most when mutually untrusted tenants share the same host.

Immutable infrastructure

An image is a read-only package that includes everything needed to run a container, like files, binaries, libraries, and configuration. Starting an image creates a container with a writable layer and one or more running processes.

Because starting a new container is fast and cheap, container deployments usually replace an instance instead of changing it in place. A team builds and tests a new image, then starts new containers from that exact image and removes the old ones, so the artifact that passed testing is the same one that ends up running. Nothing is reinstalled, patched, or reconfigured by hand once a container is running, so drift has no chance to accumulate. Runtime changes live in a versioned build definition instead of in edits applied to a live machine, which is what makes this pattern immutable infrastructure.

What a Container Is

An image supplies the filesystem and process configuration. A container runtime turns that description into an isolated process.

Docker is the most popular containerization platform. It pairs a command-line client with a background daemon that builds images and starts containers from them. Docker Hub, its public registry, lets teams publish and pull those images. Docker did not invent the kernel isolation mechanisms containers rely on, but it packaged them behind one accessible workflow along with a layered filesystem for images. Docker, CoreOS, and other container projects founded the Open Container Initiative (OCI) in 2015 to provide a standard for containers.

OCI publishes separate specifications for images, runtime bundles, and distribution. The image specification describes the manifest, configuration, and filesystem layers. The runtime specification describes the bundle and lifecycle expected by a low-level runtime. These standards let different projects build, distribute, and run the same image format.

A container runtime is the software that starts a container from an image and enforces its isolation using the host kernel. On Linux, namespaces give a process a scoped view of resources such as process identifiers, mounts, users, and network interfaces. Control groups (cgroups) account for and constrain resources such as CPU and memory. Capabilities, seccomp profiles, mandatory access controls, and runtime configuration add further restrictions. The resulting isolation depends on the runtime configuration and the security of the shared kernel.

Windows supports process isolation and Hyper-V isolation. Hyper-V isolation gives each container a lightweight VM and its own kernel. Kubernetes support for Windows containers is limited to process isolation on Windows nodes. The shared-kernel examples below use Linux terms such as namespaces and cgroups.

Images as a Supply Chain Artifact

An image digest gives the build, registry, and deployment stages one identity for the packaged software.

A Dockerfile is a text file that lists, in order, the instructions used to assemble an image. Instructions such as FROM, COPY, and RUN each add a new filesystem layer on top of the one before it, whether that means selecting a base image, copying in files, or running a command. The builder executes the file from top to bottom, so the sequence of instructions in the file is also the sequence of layers in the resulting image.

Dockerfile Dockerfile 
# Stage 1: build, with the full toolchain
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev

# Stage 2: runtime, nothing but the build output
FROM node:24-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
CMD ["node", "dist/server.js"]

The example uses a multi-stage build. The first stage contains the toolchain and source needed to produce the application. The final stage copies selected output and runtime dependencies into a fresh base. The exported image omits the build tools, which reduces its size and the software exposed at runtime.

The builder reuses a cached result when an instruction and its inputs match an earlier build. Once an instruction misses the cache, every instruction after it reruns as well, even when its own inputs haven't changed. The example takes advantage of this by installing dependencies with npm ci before copying in the application source, so an edit to the source code does not invalidate the cached dependency layer. Placing stable steps like dependency installation before frequently changing ones like copying source files preserves more of the cache and shortens rebuilds. The exported image stores each of these steps as a read-only filesystem layer, and registries and hosts can share identical layers across separate images.

A CI/CD pipeline can build the image in a controlled environment, run tests, scan it, attach provenance or a signature, and publish it to a registry. A cryptographic digest identifies the published manifest and selects the exact image content for later environments. Trust depends on the verified build process and the evidence attached to that digest.

The image supports several architectural controls:

  • Repeatability. A digest selects the same image content wherever the target platform can run it. Runtime configuration and host-kernel behavior can change how that content behaves.
  • Immutability. Image content is read-only. Tags are mutable references, so a digest provides the stable identity for promotion and verification.
  • Versioning. Tags provide readable labels, while digests provide an exact answer to which image content a deployment selected.
  • Promotion through environments. Staging and production can select the same digest. Using one digest avoids a rebuild that might silently choose a different dependency version.
  • Vulnerability scanning. A scanner compares the packages it detects with vulnerability data. Its report covers those detected packages and known vulnerabilities. Application behavior and runtime configuration need separate assessment.
  • Supply-chain integrity. Signatures and provenance can bind an image digest to a build identity. A software bill of materials (SBOM) records components for later analysis.

These controls apply to container deployments with or without Kubernetes. Kubernetes schedules workloads whose container specifications refer to images, so tags, digests, registry policy, and build evidence carry into the cluster. The image identifies the packaged software. The workload specification and runtime configuration add the environment-specific part of the deployment record.

Why Orchestration Exists

Across several hosts, a deployment needs placement, replacement, and stable routes to healthy instances.

One host can run several containers under a process manager or Docker Compose. A multi-host deployment adds placement and coordination problems. Each workload needs capacity, failed instances need replacement, and clients need a stable route even as individual instances move.

An orchestrator maintains a declared workload across a pool of machines. It schedules work according to available resources and placement rules, then watches the result and reacts when something goes wrong, replacing a failed instance and updating its routing so traffic still reaches a healthy one. Successful recovery requires spare capacity, correct health checks, and applications that tolerate replacement.

Docker Swarm, HashiCorp Nomad, and Kubernetes all coordinate container workloads across machines. Their APIs, scheduling features, and operating models differ.

Core Objects

Each Kubernetes object describes one part of a running workload or the behavior around it.

Running an application on Kubernetes means creating API objects that describe the workload and its supporting behavior. The objects below cover the main path from a container image to a reachable application.

A Pod can contain several tightly coupled containers. In the sidecar pattern, a supporting container extends the main application, perhaps by proxying its network traffic or synchronizing files. Containers in the Pod share its network namespace and can mount shared volumes. Each container keeps its own filesystem and resource settings.

Controllers normally create application Pods from templates. A Deployment is appropriate for the stateless service below because it maintains replicas and manages rollouts. The Service then selects those Pods by label and gives clients a stable destination.

deployment.yaml YAML 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.4.2
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080

Kubernetes reads the requests in the resources block when it places each Pod. The Service finds the Pods through the app: web label shared by its selector and the Pod template.

Other workload controllers manage different lifecycles. A Job runs Pods until a task completes, and a CronJob creates Jobs on a schedule. A DaemonSet places a Pod on every eligible node, or on a selected subset, for node-local functions such as networking and log collection.

A Namespace scopes object names and policy targets. A ResourceQuota can cap aggregate resources and object counts within that scope.

Control Plane and Worker Nodes

Kubernetes separates cluster coordination from the machines that run application containers.

A Kubernetes cluster separates coordination from workload execution. The control plane exposes the API, stores cluster data, schedules Pods, and runs controllers. Worker nodes provide the compute on which application Pods run. Small and development clusters can place both roles on one machine. The responsibilities stay separate even when the components share a host.

The API server accepts and validates requests that read or change cluster state. It stores that state in etcd. The scheduler selects a node for each unscheduled Pod. Controllers compare the requested state with the observed state and act on any difference. This control loop is reconciliation, and it runs again whenever cluster conditions change.

A worker node runs the components that turn an assigned Pod specification into containers and network routes:

  • The kubelet watches the Pod specifications assigned to its node and asks the runtime to create their containers.
  • The container runtime pulls images and manages container lifecycles through the Container Runtime Interface (CRI).
  • kube-proxy implements Service networking on many clusters. Clusters that use another service dataplane can omit it.

Updating a Deployment changes the desired Pod template through the API server. The Deployment controller creates a new ReplicaSet, the scheduler assigns its pending Pods to nodes, and each node's kubelet asks the local runtime to start them. Several independent control loops cooperate to perform the deployment.

Control-plane responsibility in managed Kubernetes

Managed services such as Amazon EKS, Google Kubernetes Engine, and Azure Kubernetes Service operate the control plane for the customer. Each service draws a different line around nodes, upgrades, networking, policy, and add-ons.

Helm Charts and Releases

Helm renders a configurable set of Kubernetes resources and tracks each installed instance.

Raw manifests work well when an application has few resources and one configuration. Across several environments, most of the YAML stays the same and a small set of settings changes. Copying the files makes those shared parts harder to maintain. Helm adds a templating and packaging layer for the resources. Kubernetes then validates, admits, and reconciles the rendered objects in the usual way.

A chart is a versioned package of files that describe a related set of Kubernetes resources. Its required Chart.yaml file identifies the chart and its version. The templates/ directory contains manifest templates. A values.yaml file supplies their default inputs. The chart can keep the web Deployment and Service together and expose settings such as the image tag, replica count, and Service port.

A values file supplies configuration for one use of the chart. Helm merges user-supplied values over the chart's defaults, then evaluates the templates to produce concrete manifests. Separate values files can select development and production settings without copying the whole resource set. Teams review and validate the rendered output with the same policy checks they use for handwritten YAML.

Installing a chart creates a release, which is one named instance of that chart in a cluster namespace. The same chart can produce several independent releases with different names and values. Helm records the chart, configuration, and rendered resources for each release revision. A chart version identifies the package. A release revision identifies a point in the history of one installation.

An upgrade renders the selected chart and values for an existing release, updates the affected Kubernetes resources, and records a new revision. A rollback selects an earlier release revision and applies its resource definitions as another revision. The rollback can restore an earlier Deployment image or configuration. Helm has no record of database migrations, messages sent to other systems, or other side effects outside the Kubernetes resources. Application changes need compatibility and recovery plans for those effects.

Scheduling and Resource Management

The scheduler uses resource requests and placement rules to select a node. The node enforces resource limits at runtime.

Each container can declare a request and a limit for resources such as CPU and memory. The scheduler adds the requests for a Pod and chooses a node with enough allocatable capacity. A request reserves scheduling capacity without capping actual use. On Linux, the runtime normally maps limits to cgroups. The kernel throttles CPU use at the limit. Memory enforcement is reactive and may end with the kernel killing a process.

Placement is a bin-packing problem because every Pod has a shape and every node has finite capacity. Taints and tolerations reserve nodes or keep unsuitable workloads away. Node affinity selects machine characteristics, while Pod affinity and anti-affinity influence whether workloads run together or apart. Topology spread constraints provide a more direct way to distribute replicas across nodes, zones, or other failure domains.

Networking

Kubernetes networking covers Pod addresses, stable Service discovery, and traffic entering the cluster.

Pod networking gives workloads addresses for direct communication. Kubernetes expects each Pod to receive an IP on the cluster network, and a network plugin connects those addresses across nodes. Pods can communicate without address translation between them. The underlying dataplane may use routing, overlays, or tunnels to provide that behavior.

Pods accept network traffic when no matching policy restricts them. A NetworkPolicy declares the allowed ingress or egress for selected Pods. Enforcement requires a network plugin that supports the API. Namespaces provide no automatic network isolation, so workloads that cross trust boundaries need an explicit policy design.

Service networking gives clients a stable destination for replaceable Pods. A Service represents a changing set of endpoints and usually provides a virtual IP plus DNS discovery. kube-proxy implements the forwarding rules on many clusters. Alternative dataplanes can provide the same Service behavior. A stable Service in front of changing Pods matches the load-balancing pattern from Web Application Networking.

Edge routing brings external traffic into the cluster. A Service of type LoadBalancer can expose a network service directly. Ingress and Gateway API resources describe protocol-aware HTTP routes from hostnames and paths to Services. A separate controller implements those rules. The Kubernetes project has frozen the Ingress API and recommends Gateway for new capabilities. Both provide the reverse proxy role at the cluster boundary.

State and Storage

Kubernetes can preserve storage and workload identity. Database correctness also depends on the software that manages the data.

Deployment Pods are designed to be replaceable. A stateless replica can move because durable data lives elsewhere. Stateful software adds requirements around persistent storage, stable identity, ordering, replication, backup, and recovery. Kubernetes provides primitives for storage and identity. The application or a database operator implements the database-specific behavior.

A PersistentVolume represents storage available to the cluster, and a PersistentVolumeClaim requests storage for a workload. A Container Storage Interface (CSI) driver connects Kubernetes to a storage system. A StatefulSet gives Pods stable ordinal identities and ordered lifecycle behavior. When its template includes volume claim templates, each Pod receives a claim that persists across Pod replacement.

A StorageClass describes a class of storage and its provisioner. Dynamic provisioning can create a volume when a claim requests that class, avoiding manual pre-provisioning. The storage provider and workload design determine retention, topology, access mode, backup, and restore behavior.

In-Cluster
Run stateful workloads on Kubernetes

Running the workload in the cluster keeps its configuration under the Kubernetes control plane. The team or a database operator handles replication, backup, failover, upgrades, and recovery testing. This fits organizations that have the required expertise or need cluster-local operation.

Externalized
Use a managed database service

A managed relational, NoSQL, or messaging service moves part of the operational work to a provider. The exact service determines which backups, upgrades, failover modes, and recovery guarantees are included. Cluster workloads connect to it over the network.

Stateless workloads align naturally with replaceable Pods. Stateful workloads can also run well on Kubernetes when a team has an appropriate storage system and an operator that understands the application's lifecycle. A managed external service moves part of that operational work to the provider. The choice concerns who operates the data system as much as where its storage is attached.

Deployment and Rollout Strategies

A rollout strategy balances downtime, temporary resource use, and exposure to a faulty version.

Kubernetes uses probe results to decide when a new container can receive traffic and when the kubelet should restart it. A startup probe delays the other checks until initialization completes. A readiness probe controls whether Services send traffic to the Pod. A liveness probe tells the kubelet when to restart a container.

A Deployment uses RollingUpdate unless configured with the Recreate strategy. The controller scales up a new ReplicaSet and scales down the old one within the maxSurge and maxUnavailable bounds. Availability during the rollout depends on those bounds, readiness probes, available capacity, and application compatibility.

Rolling, blue-green, and canary rollouts describe how workloads and traffic move from one version to the next. Kubernetes provides the objects and controllers used to implement each pattern.

RequirementStrategyHow it works
Gradual replacement with controlled availabilityRolling updateA Deployment scales old and new ReplicaSets within the configured surge and unavailability bounds.
Quickly reverse the traffic cutoverBlue-greenTwo versions run side by side. Traffic can switch back quickly when their state changes are compatible.
Reduce the blast radius of a risky changeCanaryThe new version receives a small slice of real traffic first. Its share increases after health and behavior checks pass.

A Deployment implements rolling replacement natively. Blue-green needs parallel versions and a mechanism for redirecting traffic. A traffic-weighted canary needs a capable gateway, ingress controller, service mesh, or rollout controller. Scaling ReplicaSets only changes endpoint counts. Exact request shares require a traffic layer that supports weights.

Infrastructure maintenance creates a different kind of interruption. A PodDisruptionBudget limits how many replicas may be unavailable through voluntary evictions, such as a node drain. The budget can make a drain wait. Involuntary failures or a shortage of replacement capacity can make the workload unavailable.

Scaling

Workload replicas, Pod resources, and cluster nodes scale through separate control loops.

Horizontal scaling changes the number of instances. Vertical scaling changes the resources available to an instance. Kubernetes supports both, although adding replicas only increases capacity when the application can divide work among them.

A HorizontalPodAutoscaler periodically changes a scalable workload's desired replica count from observed resource, custom, or external metrics. CPU and memory utilization depend on a metrics API and meaningful resource requests. Replica count follows the configured metrics. Traffic affects scaling only when one of those metrics reflects the demand.

More Pods require enough node capacity. A node autoscaler can add capacity when Pods are unschedulable and remove suitable underused nodes according to its implementation and provider integration. Workload and node scaling use independent control loops. Scale-up time includes Pod startup and any delay while new nodes become ready.

A VerticalPodAutoscaler (VPA) recommends or applies new resource requests. Its update mode determines how recommendations reach running Pods. Recreate mode evicts Pods so their workload controller creates replacements. In-place modes can resize running Pods when the cluster and VPA features support the change. Horizontal and vertical autoscaling need coordinated metrics because both controllers can otherwise react to the same resource signal.

What Kubernetes Doesn't Solve

Kubernetes supplies workload orchestration primitives. A production platform adds application telemetry, security policy, delivery, and recovery.

Kubernetes exposes workload and node status, events, and component metrics. Understanding application behavior requires logs, application metrics, traces, dashboards, and alerting. The team chooses and operates that observability stack alongside the cluster.

A Secret object separates sensitive data from ordinary configuration. Its values are base64 encoded, and etcd stores them unencrypted by default. Teams configure encryption at rest and design access control, rotation, external secret stores, and application handling separately. Pod Security Admission enforces standardized Pod restrictions. Organization-specific rules, such as approved registries or required labels, need admission policies or a policy engine.

Image building, vulnerability risk decisions, backup, and disaster recovery belong to systems outside the workload controllers. A CI/CD pipeline, registry controls, storage tooling, and operational processes provide those functions.

A production platform connects the cluster API with delivery, identity, policy, observability, and recovery systems. Kubernetes coordinates the running containers inside that larger operating environment.

Choosing the Right Platform

The decision depends on whether Kubernetes solves enough recurring coordination problems to justify the platform work around it.

Kubernetes brings a large API surface and several distributed control loops. Managed control planes operate some of those components. Teams continue to own workload design and some combination of upgrades, policy, networking, observability, and incident diagnosis. Scheduling, independent scaling, standard workload APIs, or a shared platform can justify that work when they solve recurring problems.

Local Kubernetes is useful when development needs to exercise manifests, controllers, or other cluster behavior. Docker Compose or a direct container runtime usually gives a faster loop for applications that only need their containers and dependencies.

When managed Kubernetes helps

Amazon EKS, Google Kubernetes Engine, and Azure Kubernetes Service operate the control plane. Managed Kubernetes fits teams that need the Kubernetes API and want the provider to own those components. Node management, networking integration, upgrade automation, and security defaults differ across services.

A team can begin with one host or a managed container service and adopt Kubernetes when coordination problems appear. Some products never reach that point. Current reliability, scaling, and governance requirements determine the smallest workable model. When later migration is plausible, portable images and clear data and network boundaries keep that option open.
