Containers and Orchestration

How container images become running workloads, how Kubernetes coordinates them, and when a simpler platform fits better.

Andreas Ögren
~20 min read
Last updated July 2026

Applications depend on more than their own source code. A deployment also needs a runtime, system libraries, and configuration that agree with the environment used for testing. Installing those pieces separately on each machine leaves room for drift, even when the setup begins from the same instructions.

Containers package the application and its runtime dependencies into one portable image while leaving the kernel to the host. They occupy a different point from virtual machines, serverless functions, and managed platforms in the compute landscape described in Cloud Computing. Once a deployment spans several machines, packaging is no longer the whole problem. Workloads also need placement, recovery, service discovery, and controlled updates.

A container orchestrator handles that coordination. Kubernetes is the focus here because its model exposes the architectural choices clearly, not because every container workload needs a cluster. The article builds from image and process isolation to orchestration, then closes by comparing Kubernetes with simpler operating models.

Why Containers

The technology makes more sense once the operational problems it solves are clear.

Traditional server deployments install an application directly onto a long-lived machine. Patches, emergency edits, and dependency upgrades accumulate over time, so machines that began from the same setup can diverge. Environment drift is the resulting difference between environments that were intended to behave alike.

Virtual machines reduce that drift by packaging a complete guest operating system behind a hypervisor. Each virtual machine (VM) has its own kernel and can run a different operating system from its neighbors. The boundary is strong, but every instance includes an operating system and reserves resources for it.

Process-isolated containers take a lighter approach. A container packages the application with its user-space dependencies and shares the host kernel. A container is an isolated process, not a separate machine. It generally starts faster and consumes less storage and memory than a comparable VM. The tradeoff is a shared-kernel boundary, which is weaker than hardware virtualization for hostile multi-tenant workloads.

Containers also encourage replacement instead of repair. A team builds and tests a new image, then starts containers from it in place of the old version. This use of immutable infrastructure keeps runtime changes in a versioned build definition rather than in a server's history. A rollback can then select a previous image, although persistent data and external side effects may need their own recovery steps.

The figure compares the common Linux process-isolation model with a VM. Windows and hypervisor-isolated containers add other variants, but the shared-kernel model explains the operational difference most deployments rely on.

What a Container Is

An image supplies the filesystem and process configuration. The runtime turns that description into an isolated process.

An image is a content-addressed package containing filesystem layers plus metadata such as the command, environment defaults, and supported platform. Starting an image creates a container with a writable layer and one or more running processes. The image can remain unchanged in a registry while containers created from it start, stop, and disappear.

The Open Container Initiative (OCI) publishes separate specifications for images, runtime bundles, and distribution. The image specification describes the manifest, configuration, and filesystem layers. The runtime specification describes the bundle and lifecycle expected by a low-level runtime. Open standards let tools built by different projects exchange images and run them without making Docker Engine part of the Kubernetes API.

Docker popularized containers. It didn't monopolize them.

Kubernetes removed its in-tree dockershim integration in version 1.24. Nodes now need a runtime that implements the Container Runtime Interface (CRI), such as containerd or CRI-O, or an external adapter such as cri-dockerd. Docker-built OCI images continue to run because the image format is separate from the node runtime.

On Linux, namespaces give a process a scoped view of resources such as process identifiers, mounts, users, and network interfaces. Control groups (cgroups) account for and constrain resources such as CPU and memory. Capabilities, seccomp profiles, mandatory access controls, and runtime configuration add further restrictions. These controls isolate an ordinary host process, but their effectiveness depends on configuration and kernel security.

Windows also supports process-isolated containers, and Kubernetes can schedule Windows workloads onto Windows nodes. Windows offers Hyper-V isolation as well, where each container receives a lightweight virtual machine and its own kernel. The rest of this article uses Linux terminology because namespaces and cgroups make the shared-kernel model easiest to see.

Images as a Supply Chain Artifact

The image connects build reproducibility, deployment identity, and supply-chain controls.

A Dockerfile describes a sequence of build steps. The builder can reuse cached results when an instruction and its inputs still match, while a cache miss normally causes later dependent steps to run again. Ordering stable dependency installation before frequently changing source files therefore shortens rebuilds. The exported image stores filesystem changes as read-only layers, which registries and hosts can share across images.

Dockerfile Dockerfile 
# Stage 1: build, with the full toolchain
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev

# Stage 2: runtime, nothing but the build output
FROM node:24-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
CMD ["node", "dist/server.js"]

The example uses a multi-stage build. The first stage contains the toolchain and source needed to produce the application. The final stage copies selected output and runtime dependencies into a fresh base. Build tools stay behind unless the final stage explicitly copies them, reducing image size and the software exposed at runtime.

A CI/CD pipeline can build the image in a controlled environment, run tests, scan it, attach provenance or a signature, and publish it to a registry. The resulting digest identifies the bytes that move through later environments. Not every organization uses every control, so trust comes from the verified build process rather than from the image format itself.

The image supports several architectural controls:

  • Repeatability. A digest selects the same image content wherever the target platform can run it. Runtime configuration and host-kernel behavior can still differ.
  • Immutability. Image content is read-only, but tags are mutable references. A digest is the stable identity for promotion and verification.
  • Versioning. Tags provide readable labels, while digests provide an exact answer to which image content a deployment selected.
  • Promotion through environments. The same image that passed testing in staging is the one deployed to production, rather than being rebuilt at each stage. That removes an entire class of failure caused by a rebuild silently picking up a different dependency version.
  • Vulnerability scanning. A scanner can compare the packages it detects with vulnerability data. The result is useful evidence, not proof that the image is safe.
  • Supply-chain integrity. Signatures and provenance can bind an image digest to a build identity. A software bill of materials (SBOM) records components for later analysis.

These controls apply to container deployments with or without Kubernetes. Kubernetes schedules Pods whose container specifications refer to images, so tags, digests, registry policy, and build evidence carry into the cluster. The image identifies packaged software. The workload specification and runtime configuration complete the deployment record.

Why Orchestration Exists

Packaging answers what should run. Orchestration answers where it runs and how the system responds when conditions change.

One host can run several containers under a process manager or Docker Compose. A multi-host deployment adds placement and coordination problems. Each workload needs capacity, failed instances need replacement, and clients need a stable route even as individual instances move.

An orchestrator maintains a declared workload across a pool of machines. It schedules work according to available resources and placement rules, then observes the result. Controllers replace failed workloads, while networking components update service endpoints as instances appear and disappear. Recovery still depends on spare capacity, correct health checks, and applications that tolerate replacement.

Docker Swarm, HashiCorp Nomad, and Kubernetes all provide forms of orchestration. Kubernetes receives the detailed treatment below because its control-plane and object model have shaped much of the surrounding ecosystem.

Control Plane and Worker Nodes

Every decision Kubernetes makes about where a container runs starts in one part of the cluster and ends in another.

A Kubernetes cluster separates coordination from workload execution. The control plane exposes the API, stores cluster data, schedules Pods, and runs controllers. Worker nodes provide the compute on which application Pods run. Small or development clusters may place both roles on one machine, but the responsibilities remain distinct.

The API server validates requests and acts as the front door to cluster state. etcd is the backing store used by the API server. The scheduler selects a node for each unscheduled Pod, while controllers compare requested state with observed state and act on differences. This recurring control loop is reconciliation. Users describe an outcome, and controllers keep working toward it as conditions change.

A worker node needs two core components and often a third:

  • The kubelet watches the Pod specifications assigned to its node and asks the runtime to create their containers.
  • The container runtime pulls images and manages container lifecycles through the CRI.
  • kube-proxy implements Service networking on many clusters. It is optional because another network dataplane can provide the same function.

Updating a Deployment changes the desired Pod template through the API server. The Deployment controller creates a new ReplicaSet, the scheduler assigns its pending Pods to nodes, and each node's kubelet asks the local runtime to start them. Several independent control loops cooperate to perform the deployment.

Most clusters don't run this by hand

Managed services such as Amazon EKS, Google Kubernetes Engine, and Azure Kubernetes Service operate the control plane on the customer's behalf. Responsibility for nodes, upgrades, networking, policy, and add-ons varies by service and configuration. The closing decision guide returns to that boundary.

Core Objects

Kubernetes objects are usually taught as a vocabulary list. They make more sense taught as answers to specific problems.

Running an application on Kubernetes means creating API objects that describe the workload and its supporting behavior. The objects below cover the main path from a container image to a reachable application.

ProblemObjectWhat it does
Run one or more related containersPodThe smallest deployable unit. Its containers are scheduled together and share network and selected storage resources.
Maintain replicas and roll out a stateless workloadDeploymentManages ReplicaSets, replaces missing Pods, and controls the transition between Pod templates.
Give it a stable network identityServiceRepresents a changing group of Pods behind stable discovery, so clients do not track individual Pod addresses.
Describe external HTTP routingIngress or Gateway APIDeclares how hostnames and paths reach Services. A controller must implement the routing.
Scope names and policyNamespaceGroups namespaced objects so access rules, quotas, and other policies can target them.
Provide configuration to workloadsConfigMapStores non-sensitive configuration separately from the container image, allowing the same image to be deployed with different settings. Sensitive values belong in a Secret instead.

A Pod can contain several tightly coupled containers. In the sidecar pattern, a supporting container extends the main application, perhaps by proxying its network traffic or synchronizing files. Containers in the Pod share its network namespace and can mount shared volumes, but each retains its own filesystem and resource settings.

Controllers normally create application Pods from templates. A Deployment is appropriate for the stateless service below because it maintains replicas and manages rollouts. The Service then selects those Pods by label and gives clients a stable destination.

deployment.yaml YAML 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.4.2
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080

The scheduler uses the requests in the resources block when placing each Pod, as the next section explains. The Service finds its endpoints through the app: api label shared by its selector and the Pod template.

Other controllers express different lifecycles. A Job runs Pods until a task completes, and a CronJob creates Jobs on a schedule. A DaemonSet places a Pod on every eligible node, or on a selected subset, for node-local functions such as networking and log collection.

A Namespace creates scope but does not isolate workloads by itself. A ResourceQuota can cap aggregate resources and object counts within that scope. Role-based access control, NetworkPolicies, and admission policies provide other boundaries. The built-in Pod Security Admission controller can enforce the Baseline or Restricted Pod Security Standards by namespace.

Scheduling and Resource Management

Scheduling combines declared resource needs with placement rules, then leaves runtime enforcement to the node.

Each container can declare a request and a limit for resources such as CPU and memory. The scheduler adds the requests for a Pod and chooses a node with enough allocatable capacity. A request reserves scheduling capacity without capping actual use. On Linux, the runtime normally maps limits to cgroups. CPU use above a limit is throttled, while memory enforcement is reactive and may end with a process being killed by the kernel.

Placement is a bin-packing problem because every Pod has a shape and every node has finite capacity. Taints and tolerations reserve nodes or keep unsuitable workloads away. Node affinity selects machine characteristics, while Pod affinity and anti-affinity influence whether workloads run together or apart. Topology spread constraints provide a more direct way to distribute replicas across nodes, zones, or other failure domains.

Health probes affect lifecycle and traffic rather than scheduling. A liveness probe tells the kubelet when a container should be restarted. A readiness probe controls whether the Pod is considered ready for Service traffic. A startup probe delays liveness and readiness checks until a slow-starting application has initialized, preventing premature restarts.

Networking

Kubernetes networking is easier to hold in your head as three separate questions than as one topic.

Pod networking answers the first question: how do workloads address one another? Kubernetes expects each Pod to receive an IP on the cluster network. A network plugin implements that model and connects Pods across nodes. The standard model lets Pods communicate without translating addresses between nodes, although the underlying dataplane may use routing, overlays, or tunnels to make that behavior possible.

Communication is allowed unless policy selects a Pod and restricts it. A NetworkPolicy declares allowed ingress or egress for selected Pods, but enforcement depends on a network plugin that supports the API. Namespaces do not create network isolation automatically, so workloads that cross trust boundaries need an explicit policy design.

Service networking answers the second question: how does a client find replaceable Pods? A Service represents a changing set of endpoints and usually provides a stable virtual IP plus DNS discovery. kube-proxy implements the forwarding rules on many clusters, while alternative dataplanes can provide the same Service behavior without it. The result matches the load-balancing pattern in Web Application Networking: a stable destination in front of changing backends.

Edge routing answers the third question: how does traffic enter the cluster? A Service of type LoadBalancer can expose a network service directly. For protocol-aware HTTP routing, Ingress and Gateway API resources describe how hostnames and paths map to Services, while a separate controller implements those rules. The Kubernetes project has frozen the Ingress API and recommends Gateway for new capabilities. Both play the reverse proxy role at the cluster boundary.

State and Storage

Kubernetes can preserve storage and workload identity, but it does not operate a database correctly merely by keeping its disk.

Deployment Pods are designed to be replaceable. A stateless replica can move because durable data lives elsewhere. Stateful software adds requirements around persistent storage, stable identity, ordering, replication, backup, and recovery. Kubernetes provides primitives for those requirements, while the application or an operator still owns the database-specific behavior.

A PersistentVolume represents storage available to the cluster, and a PersistentVolumeClaim requests storage for a workload. A Container Storage Interface (CSI) driver connects Kubernetes to a storage system. A StatefulSet gives Pods stable ordinal identities and ordered lifecycle behavior. When its template includes volume claim templates, each Pod receives a claim that can remain bound to persistent storage across replacement.

A StorageClass describes a class of storage and its provisioner. Dynamic provisioning can create a volume when a claim requests that class, avoiding manual pre-provisioning. Retention, topology, access mode, backup, and restore behavior still depend on the storage provider and workload design.

In-Cluster
Run stateful workloads on Kubernetes

Keeps workload configuration under the cluster's control plane. The team or a database operator must still handle replication, backup, failover, upgrades, and recovery testing. This can fit when the organization already owns that expertise or needs cluster-local operation.

Externalized
Use a managed database service

A managed relational, NoSQL, or messaging service moves part of the operational work to a provider. The exact service determines which backups, upgrades, failover modes, and recovery guarantees are included. Cluster workloads connect to it over the network.

Stateless workloads align naturally with replaceable Pods. Stateful workloads can also run well on Kubernetes when a team has an appropriate storage system and an operator that understands the application's lifecycle. A managed external service is often attractive because it changes who carries that operational responsibility, not because Kubernetes is unable to attach persistent storage.

Deployment and Rollout Strategies

Which rollout strategy fits is a question about acceptable risk and acceptable downtime, not a technical preference.

A Deployment uses RollingUpdate unless configured with the Recreate strategy. The controller scales a new ReplicaSet up while scaling the old one down, bounded by maxSurge and maxUnavailable. Availability depends on those settings, readiness probes, capacity, and application compatibility. A rolling update does not guarantee zero downtime by itself.

These are deployment patterns rather than Kubernetes objects. Kubernetes provides the building blocks, while the rollout strategy determines how traffic moves from one version to the next.

RequirementStrategyHow it works
Gradual replacement with controlled availabilityRolling updateA Deployment scales old and new ReplicaSets within the configured surge and unavailability bounds.
Quickly reverse the traffic cutoverBlue-greenTwo versions run side by side. Traffic can switch back quickly if state changes remain compatible.
Reduce the blast radius of a risky changeCanaryThe new version receives a small slice of real traffic first, and is only rolled out further once it's confirmed healthy.

A Deployment implements rolling replacement natively. Blue-green needs parallel versions and a mechanism for redirecting traffic. A traffic-weighted canary also needs a capable gateway, ingress controller, service mesh, or rollout controller. Scaling ReplicaSets changes endpoint counts, but it does not guarantee an exact share of requests.

Infrastructure maintenance creates a different kind of interruption. A PodDisruptionBudget limits how many replicas may be unavailable through voluntary evictions, such as a node drain. It can make a drain wait, but it cannot prevent involuntary failures or guarantee availability when the cluster lacks replacement capacity.

Scaling

Workload replicas, Pod resources, and cluster nodes scale through separate control loops.

Horizontal scaling changes the number of instances. Vertical scaling changes the resources available to an instance. Kubernetes supports both, although adding replicas only increases capacity when the application can divide work among them.

A HorizontalPodAutoscaler periodically changes a scalable workload's desired replica count from observed resource, custom, or external metrics. CPU and memory utilization depend on a metrics API and meaningful resource requests. Traffic does not automatically produce more replicas unless the chosen metric reflects that demand.

Extra Pods still need nodes. A node autoscaler can add capacity when Pods remain unschedulable and remove suitable underused nodes according to its implementation and provider integration. The workload and node control loops are independent, so scale-up includes both Pod startup time and any delay while new nodes become ready.

A Vertical Pod Autoscaler (VPA) recommends or applies new resource requests. Depending on its mode and cluster capabilities, applying a recommendation may replace Pods or resize them in place. Horizontal and vertical autoscaling can conflict when both react to the same resource metric, so they need coordinated policies.

What Kubernetes Doesn't Solve

Kubernetes supplies workload orchestration primitives. A usable platform adds the policies and services that make those primitives safe to operate.

Kubernetes exposes workload and node status, events, and component metrics, but it does not explain application behavior. Logs, application metrics, traces, dashboards, and alerting need an observability stack chosen and operated alongside the cluster.

A Secret object separates sensitive data from ordinary configuration, yet its values are only base64 encoded and are stored unencrypted in etcd unless encryption at rest is configured. Access control, rotation, external secret stores, and application handling remain separate concerns. Pod Security Admission enforces standardized Pod restrictions. Organization-specific rules, such as approved registries or required labels, need admission policies or a policy engine.

Kubernetes also does not build application images, decide whether a vulnerability is acceptable, or design backup and disaster-recovery procedures. A CI/CD pipeline, registry controls, storage tooling, and operational processes fill those gaps.

The platform boundary therefore extends beyond the cluster API. Delivery, identity, policy, observability, and recovery must work together even when Kubernetes coordinates the running containers.

Choosing the Right Platform

The useful question is not whether Kubernetes can run the workload, but whether its control model earns the platform cost.

Kubernetes brings a large API surface and several distributed control loops. Managed control planes remove some maintenance, but teams still own workload design, upgrades, policy, networking, observability, and incident diagnosis at some boundary. The cost is justified when scheduling, independent scaling, standard workload APIs, or a shared platform solves recurring problems.

Local Kubernetes can help test manifests and controllers, but it is not required for ordinary container development. Docker Compose or a direct container runtime often gives a faster loop when the application does not depend on Kubernetes behavior.

SituationFits wellWhy
One application on one hostDocker Compose or a system serviceCoordinates several local containers without introducing a cluster control plane.

Mostly managed cloud servicesNo orchestratorIf few custom workloads remain, an orchestrator may add more operating cost than value.
Managed Kubernetes

Amazon EKS, Google Kubernetes Engine, and Azure Kubernetes Service operate the control plane. Each service offers different levels of node management, networking integration, upgrade automation, and security defaults. Managed Kubernetes narrows the operating boundary without removing it.

Platform choices can change as the system changes. A team can begin with one host or a managed container service, then adopt Kubernetes after coordination problems become concrete. Other products never need that move. The sound decision is the smallest operating model that meets the workload's present reliability, scaling, and governance needs without blocking a credible next step.
