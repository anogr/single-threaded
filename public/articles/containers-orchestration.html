Containers and Orchestration

Docker and Kubernetes at the level a deployment decision requires, from what a container actually is to when Kubernetes is the wrong choice.

Deep dive
~29 min read
Containers & Kubernetes
July 2026

Before containers, deploying an application meant reproducing an entire server environment by hand: the right operating system version, the right system libraries, the right runtime, and the right versions of everything the application depended on. A developer's laptop and a production server rarely agreed on all of these at once, which is why "it works on my machine" became a running joke rather than a debugging step.

Containers solve a narrower problem than virtual machines do, and that narrowness is exactly what makes them fast and portable. Where containers and VMs each sit inside the wider landscape of cloud compute options, alongside serverless functions and managed platforms, is covered in Cloud Computing Fundamentals. Once containers become numerous enough, though, another problem appears: hundreds of containers spread across dozens of machines still need something deciding what runs where, restarting what fails, and rerouting traffic when conditions change. That's the role of a container orchestrator. Kubernetes is by far the most widely adopted example, and the one this article focuses on.

This article works through both layers at the level a deployment decision requires. It builds up from what a container actually is, through why orchestration becomes necessary, to how Kubernetes structures that job, and closes with a framework for deciding whether Kubernetes is the right choice at all.

Why Containers

The technology makes more sense once the operational problems it solves are clear.

Long before containers, most applications ran on dedicated physical servers. A server was provisioned, an operating system installed, and the application configured directly on top of it. Moving that application to a new server, or scaling it by adding a second one, meant repeating the entire setup by hand. Two servers that were supposedly identical routinely weren't, because some dependency had been upgraded on one and not the other, or a configuration file had drifted since the last change. This gap between environments, commonly called environment drift, was one of the most persistent sources of production incidents.

Virtual machines improved on this by letting one physical server run several isolated operating systems at once, each with its own kernel, memory, and disk. A hypervisor sits between the hardware and each guest operating system, giving every virtual machine (VM) the illusion of dedicated hardware. That isolation is strong, but it's also expensive: every VM carries the weight of a full guest operating system, which means minutes to boot and gigabytes of disk spent on an OS the application doesn't actually need.

Containers keep the isolation but drop the duplicated operating system. A container packages an application with its dependencies and shares the host machine's kernel instead of running its own. A container is an isolated process, not a separate machine. That difference is why a container starts in milliseconds instead of minutes, why a container image measures in megabytes rather than gigabytes, and why a single host can run far more containers than it could virtual machines.

Containers also change how deployments are managed. Instead of a server that evolves over time through patches and configuration changes, the application itself becomes the unit of deployment. A new container image is built, tested, and started to replace the old one wholesale, rather than patched in place with a change that might not match whatever was tested. This pattern, known as immutable infrastructure, treats a running instance as disposable: if something is wrong, it isn't fixed in place, it's replaced with a new image built from a known-good definition. Combined with a registry that stores every built image, this also turns a rollback into starting the previous image again, rather than reconstructing what a server looked like before a bad change.

What a Container Actually Is

Many people who work with Kubernetes daily have never actually asked what happens the moment a container starts.

A container image and a running container are two different things. An image is a static, versioned bundle of application code, a language runtime, system libraries, and configuration, packed into a set of read-only layers. A container is what happens when that image is unpacked and started as an isolated, running process on a host. The distinction matters because an image can sit in a registry indefinitely without doing anything, while a container is a live process with a lifecycle: starting, running, and eventually stopping.

Both the image format and how a container actually runs are defined by open standards from the Open Container Initiative (OCI), rather than by Docker itself. The OCI image specification defines how layers, metadata, and configuration are packaged. The OCI runtime specification defines what a compliant runtime must do to start a container from that bundle: create the right namespaces, apply resource limits, and execute the process. Because these are open standards, several independent implementations exist, and Docker Engine is only one of them.

Docker popularized containers. It didn't monopolize them.

Docker is still the tool most developers reach for locally, but Kubernetes dropped built-in support for running Docker Engine directly as of version 1.24, when it removed the dockershim compatibility layer. Production clusters run containerd or CRI-O as the container runtime instead. Those runtimes manage images and container lifecycles while delegating the low-level process creation to an OCI-compliant runtime such as runc. Kubernetes talks to them through the Container Runtime Interface (CRI), rather than depending on Docker specifically.

Underneath any of these runtimes, the actual isolation comes from two Linux kernel features that predate containers by years. Namespaces give a process its own view of resources it would otherwise share with everything else on the host: its own process IDs, its own network interfaces, its own mounted filesystem. A process inside a container cannot see or affect processes outside it, even though nothing has actually been virtualized. Control groups (cgroups) limit and account for the resources a process is allowed to use, such as CPU time and memory. That's what stops one container from starving every other process on the same host. A container is, in the end, an ordinary Linux process that the kernel has been told to see a smaller world and use a smaller share of resources. The kernel is shared; the isolation is a set of restrictions layered on top of a normal process.

Namespaces and cgroups are Linux kernel features, which makes containers fundamentally a Linux technology. Windows containers exist, and Kubernetes can schedule them onto Windows nodes, but the tooling, ecosystem, and community support around them are all considerably thinner than on Linux, which is why nearly everything else in this article assumes a Linux workload.

Images as a Supply Chain Artifact

An image is not just a deployment artifact. It's also the point where security, versioning, and reproducibility either get handled once or get handled nowhere.

Every instruction in a Dockerfile, the file that defines how an image is built, produces a new read-only layer stacked on top of the previous one. Layers are cached and shared: if two images both start from the same base layer, that layer is stored and downloaded only once. Ordering instructions from least to most frequently changing keeps that cache useful, since a build tool invalidates a layer, and every layer after it, the moment anything in that layer changes.

Dockerfile Dockerfile 
# Stage 1: build, with the full toolchain
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: runtime, nothing but the build output
FROM node:20-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
CMD ["node", "dist/server.js"]

This is a multi-stage build: the first stage has everything needed to compile the application, and the second copies only the finished output into a clean base image. The compilers, source files, and build-time dependencies from stage one never reach the image that actually gets deployed, which keeps the final image smaller and reduces the amount of software an attacker could exploit if a vulnerability turned up in a build tool.

In practice, images are usually built automatically by a continuous integration and deployment (CI/CD) pipeline, rather than on a developer's machine. That pipeline becomes the point where an image is compiled, tested, scanned, signed, and published to a registry, turning the image into the trusted artifact that moves through every deployment environment unchanged.

Beyond build mechanics, an image is where several architectural concerns for a deployment actually get enforced:

  • Reproducibility. The same image runs consistently on a laptop and in production, assuming compatible CPU architectures and OS versions, because it's the same bytes rather than a re-run of an install script that might resolve different dependency versions each time.
  • Immutability. Once built and tagged, an image doesn't change. Fixing a bug means building a new image, not patching the running one.
  • Versioning. Image tags, or better, content-addressable digests, give every deployment a precise, auditable answer to what code is actually running right now.
  • Promotion through environments. The same image that passed testing in staging is the one deployed to production, rather than being rebuilt at each stage, which removes an entire class of failure caused by a rebuild silently picking up a different dependency version.
  • Vulnerability scanning. Because an image is a fixed, inspectable artifact, it can be scanned for known-vulnerable packages before it's ever deployed, and a pipeline can block a release outright if a scan fails.
  • Supply-chain integrity. Image signing and a software bill of materials (SBOM) let a deployment pipeline verify that an image was built by a trusted process and hasn't been tampered with since, rather than trusting the registry blindly.

None of this requires Kubernetes specifically. It's true of any container-based deployment. But Kubernetes pulls images from a registry as its basic unit of deployment, so every one of these properties carries straight through into how a cluster behaves. What it schedules, what it can roll back to, and what a security team can audit afterward all trace back to the image itself.

Why Orchestration Exists

Running one container on one host is easy. The moment there's more than a handful of either, something has to decide what runs where.

A single host running a handful of containers can be managed by hand: start this one, stop that one, restart whichever crashed. That stops being realistic once an application is split across dozens of services, each running several replicas for redundancy, spread across enough hosts that no single machine could hold all of them. Someone, or something, has to decide which host runs which container, notice when a container or an entire host disappears, and route traffic to whatever is currently healthy.

An orchestrator is software that makes those decisions continuously instead of a person making them once at deploy time. An operator describes the desired state of the system (for example, that three replicas of an application should always be running), and the orchestrator continuously works to make reality match that description. It schedules containers onto hosts based on available capacity, and it restarts or replaces containers that fail their health checks. If an entire host disappears, it reschedules that host's workloads elsewhere. It also keeps its internal record of where everything is running up to date, so other components, like a load balancer, always know where to send traffic.

Docker Swarm, HashiCorp Nomad, and Kubernetes all do this job. Kubernetes has become the default choice for most new infrastructure, which is why the rest of this article focuses on it specifically.

Control Plane and Worker Nodes

Every decision Kubernetes makes about where a container runs starts in one part of the cluster and ends in another.

A Kubernetes cluster is divided into two kinds of machines with entirely different jobs. The control plane makes decisions: it holds the cluster's entire desired state, decides what should be running where, and reacts when reality drifts from that state. Worker nodes do the actual work, each one running the containers themselves on whatever physical or virtual machine that node happens to be.

Inside the control plane, several components split up the decision-making. The API server is the single entry point: every other component, including a human running a command-line tool, talks to the cluster only through it. Behind that, etcd stores the cluster's entire state, the scheduler decides which node a new container should run on based on available resources, and a set of controllers continuously compare what's actually running against what was requested, correcting any difference they find. This comparison of desired state against actual state, run continuously rather than once, is called declarative reconciliation, and it's the design principle underneath everything else in this article: describe the outcome that should exist, not the steps to get there. None of these components run the application itself. That's the worker node's job.

Each worker node runs three things. A kubelet is the agent that receives instructions from the API server and makes sure the containers assigned to that node are actually running. A kube-proxy handles network routing to and from containers on that node. And the container runtime itself, whichever OCI-compliant one the cluster is configured to use, is what actually starts and stops the containers.

A request to deploy a new version of an application goes through the API server, gets recorded in etcd, is assigned to a node by the scheduler, and is finally carried out by that node's kubelet talking to its local container runtime. Every layer covered in the rest of this article, objects, scheduling, networking, sits on top of this split between deciding and doing.

Most clusters don't run this by hand

Managed services like Amazon EKS, Google GKE, and Azure AKS operate and patch the control plane above on the cluster owner's behalf, which is the default deployment model for most organizations adopting Kubernetes today rather than something added on later. The full comparison against other platforms is covered in the decision framework that closes this article.

Core Objects

Kubernetes objects are usually taught as a vocabulary list. They make more sense taught as answers to specific problems.

Running an application on Kubernetes means describing what should exist and letting the control plane continuously work to match reality to that description. Six objects cover most of what a deployment decision actually needs to reason about.

ProblemObjectWhat it does
Run a containerPodThe smallest deployable unit: one or more containers that always run together on the same node, sharing a network address and storage.
Keep it running, roll out changes safelyDeploymentManages a set of identical Pod replicas, replacing failed ones automatically and controlling how new versions are rolled out.
Give it a stable network identityServiceA stable virtual IP and DNS name in front of a group of Pods, so Pods can be replaced without anything else needing to track their individual, short-lived addresses.
Let traffic in from outside the clusterIngressRoutes external HTTP(S) traffic to the right Service based on hostname or path, similar to a reverse proxy at the cluster's edge.
Separate workloads sharing a clusterNamespaceA logical partition used for access control and resource limits, so different teams or environments can share infrastructure without colliding.
Provide configuration to workloadsConfigMapStores non-sensitive configuration separately from the container image, allowing the same image to be deployed with different settings. Sensitive values belong in a Secret instead.

The Pod row also hints at something easy to miss: a Pod can hold more than one container on purpose. The most common reason is the sidecar pattern, where a second container extends the main one without modifying it. A logging agent that ships a container's logs to a collector, or a proxy that terminates TLS on its behalf, is a typical example. The two containers still share the Pod's single network address and storage, so from outside the Pod they behave as one unit.

A Pod is almost never created directly in practice. It's the Deployment that creates and manages Pods on the operator's behalf, which is why the manifest below defines a Deployment and a Service together rather than a bare Pod.

deployment.yaml YAML 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.4.2
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080

The resources block under the container is worth noting here, since it's the same value the scheduler reads to decide which node has room for this Pod, covered next. The selector in the Service is how it finds its Pods: by label, not by any fixed list of addresses.

Deployment is the workhorse for long-running services, but it isn't the only workload type worth knowing. A Job runs a container to completion for a one-off or batch task, rather than keeping it running indefinitely. A CronJob schedules a Job on a recurring basis. A DaemonSet ensures exactly one Pod runs on every node, the pattern used for node-level agents such as log collectors.

Namespace on its own only draws a boundary. It doesn't enforce anything by default. A ResourceQuota caps the total CPU, memory, and object count a namespace's workloads can consume combined, which is what actually stops one team from exhausting a shared cluster's resources. Pod Security Standards, enforced by the Pod Security Admission controller at the namespace level, replaced the deprecated PodSecurityPolicy mechanism. They restrict what a Pod is allowed to do, such as running as root or mounting the host's filesystem.

Scheduling and Resource Management

The scheduler's job sounds simple: pick a node. What makes it non-trivial is fitting many differently sized workloads onto a fixed pool of machines without wasting capacity.

Every container in a Pod can declare two numbers: a request, the amount of CPU and memory it needs to run acceptably, and a limit, the maximum it's allowed to consume before Kubernetes intervenes. The scheduler only looks at requests when deciding where a Pod fits. It will only place a Pod on a node that has enough unreserved capacity to cover the request, treating that capacity as spoken for even if the container ends up using less. Limits are enforced afterward by the same cgroups mechanism covered earlier: a container that exceeds its memory limit is killed and restarted, and one that exceeds its CPU limit is throttled rather than killed.

Fitting many Pods with different requests onto a fixed set of nodes is a bin-packing problem, solved fresh by the scheduler for every new Pod rather than once at cluster setup. Two clusters with identical total capacity can end up needing very different numbers of nodes, depending on how well individual Pod sizes happen to pack together. Beyond plain capacity, an operator can constrain scheduling further. Taints keep certain Pods off certain nodes unless explicitly tolerated. Affinity rules pull related Pods toward or away from each other, useful for spreading replicas across failure domains or keeping latency-sensitive Pods on the same node. These are worth knowing exist rather than needing right away. Most deployment decisions are made correctly with just requests, limits, and probes configured sensibly.

Resource limits aren't the only thing that can get a container restarted or pulled out of rotation. A liveness probe checks whether a container is still working, and a failure gets it killed and restarted, the same outcome as exceeding a memory limit but triggered by application health instead of resource usage. A readiness probe checks whether a container is ready to accept traffic, and a failure removes it from behind its Service without restarting it, useful for a container that's alive but still warming up a cache or waiting on a dependency. A startup probe covers slow-starting containers, giving them longer than the liveness probe would otherwise allow before health checks start counting against them.

Networking

Kubernetes networking is easier to hold in your head as three separate questions than as one topic.

How do Pods talk to each other? Kubernetes assumes every Pod has its own IP address on a flat, cluster-wide network. It doesn't implement that network itself. Instead, a plugin conforming to the Container Network Interface (CNI), with Calico and Cilium being common choices, is responsible for assigning Pod IPs and wiring up the routes between nodes. With that network in place, any Pod can reach any other Pod's IP directly, regardless of which node either one happens to be running on. This is a deliberate simplification: application code never needs to know about NAT or port mapping between containers on the same node versus different ones, because from the network's perspective there's no difference.

That openness is the default, not a guarantee. A NetworkPolicy restricts which Pods can talk to which others, selected by label rather than IP, acting as a firewall rule scoped to the cluster's internal traffic. Most single-team clusters never need one. Multi-tenant clusters, where workloads from different teams or trust boundaries share the same network, usually add them as one of the first security controls.

How do clients find a Pod that could be replaced at any moment? Pod IPs are not something anything else should depend on directly, since a Pod is disposable and gets a new IP every time it's recreated. A Service solves this by giving a group of Pods, selected by a label rather than a fixed list, one stable virtual IP and DNS name that stays constant no matter how many times the Pods behind it come and go. Each node's kube-proxy maintains the routing rules that translate a request to the Service's stable address into a request to one of the currently healthy Pods behind it, the same load-balancing job a load balancer performs outside the cluster. Some clusters skip kube-proxy entirely: certain CNI plugins, Cilium's eBPF-based dataplane being the most common example, implement that same routing directly in the kernel instead. The pattern is directly analogous to the reverse proxies and load balancers covered in Web Application Networking: a stable address in front of a changing pool of backends, just implemented inside the cluster instead of in front of it.

How does traffic get into the cluster at all? A Service's virtual IP is only reachable from inside the cluster by default. An Ingress sits at the cluster's edge and routes external HTTP and HTTPS traffic to the right internal Service based on hostname or URL path, the same job a reverse proxy does in a traditional deployment. Most clusters run an Ingress controller, commonly NGINX or a cloud provider's own implementation, that reads Ingress objects and configures itself accordingly, rather than Kubernetes implementing routing logic itself. A newer API, the Gateway API, is gradually complementing Ingress with a more expressive and portable way to configure the same routing, though Ingress remains the more common starting point for most clusters today.

State and Storage

Kubernetes was designed around Pods that can be destroyed and recreated without anyone caring which specific instance survives. A database doesn't work that way, and that mismatch is the most consequential state decision in any Kubernetes deployment.

A stateless web server replica can be killed and replaced at any moment with no consequence, because it holds nothing that isn't reconstructible from a request or an external store. Kubernetes assumes this by default: a Deployment's Pods are interchangeable, and losing one is a non-event. A database, a message queue, or anything else that holds data on local disk breaks that assumption immediately, because replacing the Pod without preserving what was on its disk means losing data.

Kubernetes separates the problem of storage from the problem of identity. A PersistentVolume represents actual storage, provisioned from a cloud disk, a network filesystem, or similar, through a plugin conforming to the Container Storage Interface (CSI) that each cloud provider or storage vendor implements. A PersistentVolumeClaim is how a Pod requests storage without needing to know exactly what kind of volume, or which CSI driver, backs it. A StatefulSet then provides the other half of the solution: unlike a Deployment, it gives each Pod a stable, unique identity and its own PersistentVolumeClaim, so the same Pod is reattached to the same storage across restarts. That's what clustered databases and other stateful systems actually need.

In practice, a PersistentVolume is rarely created by hand ahead of time. A StorageClass tells Kubernetes how to provision one automatically, using whichever CSI driver and disk type the class specifies, the moment a PersistentVolumeClaim asks for storage that doesn't exist yet.

In-Cluster
Run stateful workloads on Kubernetes

Keeps everything on one platform and one deployment model. Requires the team to operate storage, backups, failover, and upgrades themselves, work a managed database service does automatically. Makes sense when the team already has that operational expertise, or when data locality inside the cluster genuinely matters.

Externalized
Use a managed database service

A managed relational or NoSQL service, for example Amazon RDS, Cloud SQL, or a managed Kafka offering, already solves clustering, failover, and backups. The cluster's stateless workloads simply connect to it over the network. This is the more common choice, since most teams would rather not re-solve a problem a cloud provider already solved well.

Kubernetes is very good at running stateless workloads, and that's not a limitation so much as where its design assumptions actually hold. Storage orchestration inside a cluster is genuinely difficult to get right, which is why most production Kubernetes deployments run application Pods in-cluster and lean on an external, managed service for anything that has to remember something between restarts.

Deployment and Rollout Strategies

Which rollout strategy fits is a question about acceptable risk and acceptable downtime, not a technical preference.

A Deployment's default behavior is a rolling update: new Pods running the updated version are started gradually while old ones are terminated, so a fixed number of Pods stay available throughout and users never see downtime. That default doesn't fit every requirement, though, particularly when a rollback needs to be instant rather than another gradual rollout in reverse, or when a change is risky enough that it should reach a small fraction of traffic before reaching everyone.

These are deployment patterns rather than Kubernetes objects. Kubernetes provides the building blocks, while the rollout strategy determines how traffic moves from one version to the next.

RequirementStrategyHow it works
No downtime during a routine releaseRolling updateKubernetes' default. New replicas start and pass health checks before old ones are terminated, a few at a time.
Rollback needs to be instantBlue-greenTwo full environments run side by side. Traffic is switched from the old one to the new one all at once, and switched back just as fast if something's wrong.
Reduce the blast radius of a risky changeCanaryThe new version receives a small slice of real traffic first, and is only rolled out further once it's confirmed healthy.

Kubernetes' built-in rolling update covers the first case natively. Blue-green and canary both need something extra. Blue-green needs two environments running simultaneously and a way to redirect traffic between them. A fine-grained canary, ten percent of traffic rather than ten percent of replicas, usually needs a service mesh or an Ingress controller capable of weighted routing, since a plain Deployment can only approximate canary behavior by scaling replica counts.

Every strategy above assumes the application itself is what's changing. A cluster's infrastructure changes too. Nodes get drained for maintenance or upgraded on a rotation, and each drain can evict every Pod running on that node at once. A PodDisruptionBudget tells Kubernetes the minimum number of replicas that must stay available during this kind of voluntary disruption. A node drain then waits and proceeds gradually, rather than taking out an entire replica set in one move.

Scaling

More instances or bigger ones: the two ways to scale, and Kubernetes clearly prefers one of them.

There are two fundamentally different ways to scale an application. Vertical scaling gives an existing instance more CPU or memory. Horizontal scaling adds more instances and spreads work across them. Kubernetes is designed primarily around horizontal scaling, since replacing and replicating Pods is one of its core assumptions.

A HorizontalPodAutoscaler watches a metric, most often CPU or memory usage, though it can also scale on custom application metrics. It adjusts the number of Pod replicas in a Deployment up or down to keep that metric near a target. It solves demand at the application layer: more traffic means more replicas.

That only helps if the cluster's nodes have room for the extra replicas. A cluster autoscaler solves the layer underneath: it adds new nodes when Pods are waiting to be scheduled because nothing has capacity, and removes nodes when they sit underused. The two work independently, and both are normally left running unattended rather than adjusted by hand.

Kubernetes can also scale vertically. A Vertical Pod Autoscaler (VPA) recommends or adjusts the CPU and memory requests assigned to Pods instead of changing the number of replicas. It's useful for right-sizing workloads, but horizontal scaling remains the more common approach for highly available services because it increases both capacity and redundancy.

What Kubernetes Doesn't Solve

Kubernetes is one layer of a platform. Teams that treat it as the whole platform usually find out the hard way what it was never designed to provide.

None of what Kubernetes does out of the box tells an operator what's actually happening inside a running application, or why a specific request failed. That's the job of an observability stack, collecting and correlating logs, metrics, and traces across every Pod. Kubernetes doesn't provide this natively, even though nearly every production cluster ends up needing one layered on top.

Some areas do have Kubernetes primitives, but those primitives are only part of the solution. A Secret object can store sensitive values, but base64 encoding isn't encryption. Vanilla Kubernetes stores that base64 value in etcd as-is unless an operator explicitly configures encryption at rest, though most managed cloud offerings now enable some form of it by default. Even encrypted at rest, a Secret still isn't the same as a dedicated secrets-management system, with rotation, fine-grained access policies, and an audit trail. Pod Security Standards cover baseline restrictions like blocking root privileges, but enforcing anything more specific to an organization, such as requiring every image to come from an approved registry, is also nothing Kubernetes does on its own. It needs an admission controller or a policy engine, such as OPA Gatekeeper or Kyverno, sitting in front of the API server.

Other capabilities sit entirely outside Kubernetes. Getting code into the cluster still needs a separate CI/CD pipeline. Scanning images for vulnerabilities, backing up data, and planning for disaster recovery are all still the team's responsibility.

Kubernetes schedules and runs containers extremely well, but everything around that job is a set of decisions the platform leaves to whoever operates it: security, delivery, governance, and visibility.

Choosing the Right Platform

Most of the real decisions in this space are made before a single YAML file gets written: whether to use an orchestrator at all, and if so, which one.

Kubernetes solves real problems, but it also carries real operational weight. Someone has to run the control plane, keep it patched and upgraded, and understand enough of its internals to debug it when something goes wrong. That cost is worth paying at a certain scale and not worth paying below it. The comparison that matters isn't a feature checklist. It's how much operational complexity a team is signing up for, weighed against how much of Kubernetes' capability actually gets used.

None of this is only a production decision, though. Docker Desktop can also run a single-node Kubernetes cluster locally, purely for development, which is often how a developer first encounters the objects covered earlier in this article.

SituationFits wellWhy
One application, one host, low trafficDocker ComposeRuns multiple containers from one config file and no cluster to operate. No scheduling, no self-healing, nothing to patch beyond the host itself.
A small, fixed set of services across a few hostsNomad or Docker SwarmA lighter orchestrator than Kubernetes, with a smaller feature set and a much smaller operational footprint. Mirantis continues to maintain Swarm and has committed to supporting it into the next decade. Its own investment and the wider ecosystem's innovation are concentrated on Kubernetes, though, so Swarm mainly suits existing Docker-based shops rather than new projects.
Many services, multiple teams, need to scale independentlyKubernetesWhere scheduling, self-healing, and the surrounding ecosystem of tooling actually pay for the operational cost of running it.
Workloads that spike unpredictably or run only occasionallyServerless containers (Fargate, Cloud Run)Runs a container without managing any cluster or nodes at all, billed by actual usage rather than reserved capacity. A middle ground between plain containers and a full orchestrator.
Mostly using managed cloud services alreadyNo orchestratorIf most of an architecture is already managed services, a managed database, a managed queue, a serverless function platform, there may be little left that benefits from an orchestrator at all.
Managed Kubernetes

Managed offerings like Amazon EKS, Google GKE, and Azure AKS run and patch the control plane on the team's behalf, which is why most organizations that do choose Kubernetes never operate a control plane themselves. The remaining decision is almost always about the worker nodes and everything layered on top, not whether to run etcd by hand.

None of these are permanent choices. A team can start with Docker Compose and move to Kubernetes once services and traffic actually justify it, and plenty of successful products never make that move at all. The mistake isn't picking the "wrong" one on day one. It's adopting Kubernetes' operational weight before anything in the architecture actually needs what it provides.
