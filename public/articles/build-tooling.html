Build Tooling

How module graphs become production assets, and how the main development servers and bundlers divide the work.

Andreas Ögren
~12 min read
Last updated July 2026

A frontend project is written as a graph of source modules and external packages. That graph is convenient for authors, but it is not necessarily the right delivery shape for a browser. Build tools transform unsupported syntax, resolve dependencies, remove code they can prove is unnecessary, and divide the result into deployable assets. The goal is a correct output whose loading behavior suits the application.

Two optimizations shape that output. Tree-shaking removes exports and modules that cannot affect the program, while code-splitting moves reachable code behind loading boundaries. Development adds a different requirement: transforms and updates must reach the browser quickly enough to preserve flow.

The sections below explain those mechanisms before comparing Vite, esbuild, Rollup, webpack, Turbopack, Rspack, and Bun. Composition across independently built applications belongs to the microfrontends article.

From Task Runners to Module Graphs

Bundling and running tasks used to be the same job. They split apart because they aren't the same problem.

Before browsers supported modules, script tags shared a global environment and applications created their own conventions for dependency order. Browserify let browser code use CommonJS-style require() calls and bundled the resulting graph into files the browser could load. Grunt and Gulp addressed an adjacent problem by running tasks such as compiling Sass, processing images, and concatenating scripts. Task runners automate steps, while bundlers understand module relationships.

webpack brought scripts, styles, images, and fonts into one extensible module graph. Loaders transformed inputs, while plugins changed broader parts of the compilation. Babel handled JavaScript syntax that target browsers could not yet parse. Rollup later focused on ES modules and library output, favoring a smaller runtime footprint and formats suitable for package publishing.

esbuild changed expectations by implementing parsing, transformation, and bundling in Go with extensive parallelism. Vite used that speed for dependency optimization while serving application source through native ES modules during development. Production builds still performed full bundling and optimization. Separating the development server from the production pipeline became Vite's defining architectural choice.

Rust-based tools then moved into several layers of the stack. SWC became Next.js's compiler, Turbopack built a framework-specific incremental bundler, and Rspack pursued webpack compatibility. Rolldown and Oxc now provide Vite with a unified bundling and transformation toolchain. These projects differ in scope, but all aim to reduce the cost of repeatedly analyzing the same module graph.

The Dev Server and the Production Build Are Different Jobs

Development optimizes feedback time, while production optimizes the assets delivered to users.

During development, a saved change should reach the browser with minimal invalidation and transformation. Production has different priorities. The build can spend more time removing code, choosing chunk boundaries, compressing syntax, and producing stable asset names because those decisions affect every user.

Vite treats these as separate workflows. During development it serves application source as transformed ES modules, allowing the browser to request imports as needed. Dependencies receive separate optimization because a package may expose many internal modules or use CommonJS. Vite 8 uses Rolldown to pre-bundle those dependencies and to bundle production output. The workflows share an engine, but application source remains unbundled in the default development mode.

vite.config.ts TypeScript 
import { defineConfig } from 'vite';

export default defineConfig({
  // dev: serves ES modules directly, esbuild/Rolldown only pre-bundles deps
  // build: bundles, tree-shakes, and code-splits the app for production
  build: {
    target: 'es2022',
    sourcemap: true,
  },
});

A direct “Vite versus webpack” comparison therefore mixes products with different boundaries. Vite combines a development server with an orchestrated production build. webpack uses one bundler architecture in both environments. Turbopack and Rspack also maintain module graphs during development, but their Rust implementations and incremental designs differ from webpack's engine.

Tree-Shaking Fundamentals

Tree-shaking combines module reachability with side-effect analysis.

A bundler begins at configured entry points and follows imports through the module graph. Static ES module syntax exposes named relationships without executing the program, which lets the bundler determine that some exports are never referenced. It can remove those exports when doing so cannot change observable behavior.

CommonJS is harder to analyze because require() and module.exports participate in ordinary runtime control flow. Bundlers can optimize some familiar patterns, but the guarantees are weaker than with statically analyzable ES modules. Tree-shaking therefore depends on both module format and the tool's ability to reason about side effects.

utils.ts TypeScript 
export function formatDate(d: Date) { return d.toISOString(); }
export function formatCurrency(n: number) { return `$${n.toFixed(2)}`; }
export function debugLog(...args: unknown[]) { console.log(...args); }

If entry.ts only ever writes import { formatDate, formatCurrency } from './utils', a bundler can prove that debugLog is never reachable from the entry point. It can drop debugLog, and everything that function alone depends on, from the final bundle without executing a single line of it.

Barrel files can obscure that analysis when they re-export modules with side effects. The bundler must preserve any imported module whose evaluation may change program behavior, even when none of its exports are read. The sideEffects field in package.json helps package authors describe that boundary. Setting it to false promises that unused modules can be dropped, while a file list preserves entries such as polyfills and imported CSS. An incorrect declaration can remove necessary behavior, so it is a semantic promise rather than a performance switch.

The whole-library import trap

Writing import _ from 'lodash' references the package's default export object. That shape is harder to reduce than a named import from an ES module build. For example, import { debounce } from 'lodash-es' gives the bundler a specific export to trace. A bundle analyzer can confirm whether the package and import form produce the expected output.

Code-Splitting Fundamentals

Tree-shaking removes unreachable code. Code-splitting defers reachable code until a loading boundary needs it.

Reachable code can still include routes and features that a visitor never opens. Code-splitting places some of that code in separate chunks and loads it when the corresponding path is needed. A dynamic import() creates an asynchronous module boundary, giving the bundler a natural place to emit another chunk. Frameworks can generate equivalent boundaries from their route structure.

router.tsx TypeScript / React 
import { lazy, Suspense } from 'react';

// SettingsPage and its dependencies become their own chunk,
// fetched only when a visitor navigates to /settings
const SettingsPage = lazy(() => import('./pages/SettingsPage'));

function Route() {
  return (
    <Suspense fallback={<Spinner />}>
      <SettingsPage />
    </Suspense>
  );
}

Route-based splitting places a natural boundary around each page or route segment, and many frameworks generate those chunks automatically. Navigating to /settings can then fetch settings code that the landing page did not need.

In an application built from Server and Client Components, the client boundary comes first. A component that never enters the client module graph does not ship as browser JavaScript. Code-splitting determines when reachable client code arrives. The server and client boundary determines whether it arrives at all.

Shared dependencies complicate splitting. If two route chunks import the same library, the bundler may place that library in a shared chunk instead of duplicating it. Very fine splitting can add request and scheduling overhead, while coarse chunks make visitors download unrelated code. Framework defaults are a useful starting point, but measured loading behavior should decide whether manual boundaries improve the result.

Content hashes connect chunks to HTTP caching. A filename such as settings.a1b2c3.js changes when its content changes, so immutable assets can use a long cache lifetime. A new deployment references new names while unchanged chunks remain reusable. This works only when the HTML or manifest that points to those assets has an appropriate freshness policy of its own.

The Tool-by-Tool Landscape

The tools overlap, but each is optimized around a different primary job.

Vite is a common choice for applications outside frameworks that prescribe their own build pipeline. It combines a native-ESM development server with a plugin API based on Rollup's hooks. Vite 8, released in March 2026, replaced its previous esbuild-and-Rollup pairing with Rolldown for dependency optimization and production builds.

esbuild remains a fast standalone transformer and bundler with a deliberately compact API. It works well for small packages, command-line tools, and build steps that do not need a large plugin ecosystem. Applications that require framework integration or more control over chunking often encounter it indirectly through higher-level tooling.

Rollup remains oriented toward libraries that need controlled output across module formats. Higher-level wrappers reduce its configuration surface for TypeScript packages. Precise publishing output and an application-oriented development server are different requirements and may lead to different tools.

webpack remains valuable where a mature application depends on its loaders, plugins, and established configuration. Replacing that pipeline has a real migration cost. Rspack offers a closer transition path by implementing much of webpack's configuration and loader surface on a Rust engine, although compatibility must still be tested against the specific project.

Turbopack, Vercel's Rust-based bundler, is tightly coupled to Next.js and is the framework's default for both development and, since Next.js 16, production builds as well. Its value proposition is specific to that coupling. Because Vercel controls both the framework and the bundler, Turbopack can make assumptions and optimizations a general-purpose bundler can't. That comes at the cost of being a poor fit for anything that isn't a Next.js app.

Rspack takes the opposite approach from Turbopack. It implements a webpack-compatible configuration and loader model in Rust, making migration from an existing webpack application its central use case. Compatibility is broad rather than absolute, so teams need to test custom loaders, plugins, and output assumptions before treating the engine as a drop-in replacement.

Bun includes a Zig-based bundler through bun build. It can suit packages and server applications already using Bun's runtime and package manager. For browser applications, the decision also depends on development-server behavior, framework integrations, and plugin requirements rather than on the bundler in isolation.

The Rust Convergence 2026

Rust implementations now cover the parsers, transformers, and bundlers that repeatedly process the module graph.

Oxc is a Rust toolchain for parsing, resolving, transforming, minifying, and linting JavaScript and TypeScript. Rolldown builds bundling on that infrastructure while maintaining compatibility with much of Rollup's plugin model. Vite 8 made Rolldown its default bundler in March 2026, replacing two engines with one toolchain.

VoidZero, the company behind Vite, Vitest, Rolldown, and Oxc, joined Cloudflare in June 2026. The announcement states that the projects will remain open source, vendor-agnostic, and community-driven. The ownership change matters because these tools now provide shared infrastructure for several framework ecosystems, even though their technical governance remains project-specific.

The convergence is incomplete. esbuild remains a Go project, and webpack continues to support production systems with deep ecosystem dependencies. Rust has become common in newer engines, but implementation language alone does not justify migrating a working pipeline. Existing compatibility costs and measured bottlenecks should drive that decision.

Choosing a Tool

The honest answer to "which bundler" is usually "whichever one your framework already picked for you."

Next.js 16 uses Turbopack by default for development and production builds. Projects that depend on unsupported webpack plugins can opt back into webpack while they close that compatibility gap. Outside a metaframework with its own pipeline, Vite provides a broadly integrated development server and production build.

For an established webpack application, migration cost matters more than a theoretical tool ranking. Vite changes the development architecture and plugin model. Rspack preserves more of webpack's configuration surface while replacing the engine. A compatibility trial can show whether that narrower migration removes the measured bottleneck without forcing a broader rewrite.

A published package has another set of priorities. Its consumers need predictable exports, module formats, type declarations, and minimal accidental runtime code. Rollup and Rolldown-based library tools provide more direct control over that output than an application-oriented development server.

Microfrontends add a composition layer above the individual build. Module Federation and related tooling coordinate several independently produced graphs at runtime, while each graph still needs tree-shaking and code-splitting. The microfrontends tooling section covers that separate decision.
