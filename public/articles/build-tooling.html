Build Tooling

How tree-shaking and code-splitting work under the hood, and which of today's bundlers fits which job.

Andreas Ögren
~21 min read
Last updated July 2026

A typical frontend project consists of hundreds or thousands of source modules that import one another, along with thousands more pulled in transitively from node_modules. Browsers can load ECMAScript modules directly, but shipping an application's source tree unchanged is rarely ideal. Production builds usually transpile TypeScript and JSX into standard JavaScript, remove development-only code, optimize and minify the output, and package modules into a set of files that balances startup cost, caching, and parallel loading. Rather than downloading an entire application up front, the build can also split it into chunks that are fetched only when a route or feature actually needs them.

That summary hides most of the interesting engineering. Tree-shaking statically analyzes the module graph to determine which imports and exports are actually used, allowing unused code to be eliminated when modules are written in a form the optimizer can reason about. Code-splitting then decides where the remaining graph can be divided into separately loaded chunks without changing the program's behavior. Making those optimizations both correct and fast enough for an edit-refresh development workflow has driven much of the evolution of frontend tooling over the past several years, from JavaScript-based bundlers toward high-performance implementations in Go and Rust. This article explains how tree-shaking and code-splitting work under the hood, then examines Vite, esbuild, Rollup, webpack, Turbopack, and newer tools, with an eye toward when each is the right choice. Bundler choices specific to microfrontends, including Module Federation and the Rspack and Zephyr tooling built around it, are covered in the microfrontends article instead of repeated here.

From Task Runners to Bundlers

Bundling and running tasks used to be the same job. They split apart because they aren't the same problem.

Before any of today's tools existed, the browser had no module system. Every script tag shared one global scope, and keeping a large jQuery-era codebase from stepping on its own variables was a matter of discipline, not tooling. Browserify, released in 2011, was the first tool to matter here. It let developers write Node-style require() calls and walk the resulting dependency graph into one file the browser could load, effectively smuggling CommonJS modules into a place they were never designed to run. Grunt and Gulp arrived around the same time to solve an adjacent but different problem. They ran a sequence of tasks, such as compiling Sass, minifying images, or concatenating scripts, rather than resolving a module graph. A task runner and a bundler answer different questions, though early tooling often treated them as competitors anyway.

webpack, first released in 2012 by Tobias Koppers, absorbed both jobs into one tool and became the default answer for most of the following decade. Its core idea was that everything, whether JavaScript, CSS, images, or fonts, counts as a module flowing through a graph of loaders and plugins. That flexibility let it absorb the entire ecosystem's fads as they arrived, including CSS Modules, hot module replacement, tree-shaking once ES modules made static analysis possible, and code-splitting via dynamic import(). Babel, released in 2014 as 6to5, filled the adjacent gap of letting developers write syntax browsers didn't support yet, and the two tools became the standard pairing for years. Rollup, released in 2015 by Rich Harris, took a narrower and more opinionated position. It targeted ES modules specifically, ahead of webpack's own tree-shaking, and produced flatter, more readable output that library authors preferred over webpack's more general-purpose runtime wrapper.

The landscape's first real shock came from outside the JavaScript ecosystem entirely. esbuild, released by Evan Wallace in 2020, is written in Go and compiled to native code. It bundled and transformed source ten to a hundred times faster than the JavaScript-based tools it was compared against, largely because it parallelizes across cores in a way a single-threaded Node process can't. It didn't replace webpack's plugin ecosystem or its code-splitting sophistication. But it made an entire category of work, such as transforming TypeScript and JSX or bundling dependencies for local development, fast enough to stop being a bottleneck. Vite, released the same year by Evan You, built its dev-time story directly on top of that speed. Instead of bundling an app before serving it, Vite serves source files as native ES modules straight to the browser during development, and uses esbuild only to pre-bundle the (rarely changing) contents of node_modules. That split, covered in detail in the next section, is the architectural idea that reshaped how most new projects approach building for the rest of the decade.

The second shock, underway since roughly 2023, is still reshaping the landscape: a wholesale move from Go to Rust across the toolchain. SWC, a Rust-based compiler, replaced Babel inside Next.js years before this trend had a name. Vercel's Turbopack, announced in 2022 and written in Rust by the same Tobias Koppers who built webpack, positioned itself explicitly as webpack's successor. Rspack, from ByteDance, took the opposite approach of cloning webpack's configuration surface in Rust rather than replacing its mental model. And most recently, Rolldown and Oxc, both stewarded by Evan You's company VoidZero, have set out to replace the Rollup-plus-esbuild combination sitting underneath Vite with a single Rust toolchain. The rest of this article treats these not as a list of competing options to memorize, but as answers to two much narrower questions: how does a tool decide what code is dead, and how does it decide what to defer.

The Dev Server and the Production Build Are Different Jobs

Optimizing for iteration speed and optimizing for shipped-file size pull in opposite directions, which is why the best tools stopped trying to do both with the same code path.

During development, the only thing that matters is how fast a change to one file reaches the browser. Bundle size is irrelevant, since nobody's connection speed matters on localhost. The fewer things that stand between a saved file and an updated screen, the better. During a production build, the opposite priorities apply. Build time matters far less than someone waiting on a real network connection, so it's worth spending extra seconds tree-shaking aggressively, splitting chunks carefully, and minifying every byte that ships.

Vite's architecture is built directly around treating these as separate problems rather than one continuum. Its dev server doesn't bundle application code at all. Each source file is served as a native ES module, and the browser's own module loader requests each import as needed. That native ESM-in-browser support is what reduces Vite's dev-time job to "transform this one file quickly," not "resolve the whole graph on every save." node_modules dependencies get a separate treatment, because a package like lodash-es might be spread across hundreds of internal files. Pre-bundling them once at startup, historically with esbuild and now with Rolldown as of Vite 8, converts that into a small number of flat modules so the browser isn't making hundreds of requests for one dependency's internals. Only the production build path bundles, tree-shakes, and splits the application's own code, which is exactly what the rest of this article is about.

vite.config.ts TypeScript 
import { defineConfig } from 'vite';

export default defineConfig({
  // dev: serves ES modules directly, esbuild/Rolldown only pre-bundles deps
  // build: bundles, tree-shakes, and code-splits the app for production
  build: {
    target: 'es2022',
    sourcemap: true,
  },
});

This split is also why comparing "Vite versus webpack" head to head is a little imprecise. Vite is a dev server plus a build orchestrator that historically delegated production bundling to Rollup underneath. webpack has always been one bundler used for both jobs, which is part of why its dev-time hot reload was traditionally slower than Vite's. It was running the same bundling machinery both times, just incrementally. Turbopack and Rspack both inherit webpack's single-pipeline model but rebuild the engine in Rust rather than splitting the two jobs the way Vite does, betting that Rust's raw speed can close the dev-time gap without needing an architectural split at all.

Tree-Shaking Fundamentals

Tree-shaking isn't smart. It's a reachability check, and it only works when the code is honest about what it can reach.

The mental model is simple: starting from an app's entry point, a bundler follows every import statement it can see and marks each export it reaches as live. Anything never reached by that walk (an unused named export, a function nobody imports) gets dropped from the final bundle entirely, not just minified into a shorter name. This only works reliably against ES modules, because import and export are static. They have to appear at the top level of a file and reference fixed names, so a bundler can build that reachability graph without running any code. CommonJS's require() and module.exports are just function calls and object assignments at runtime, which a bundler generally can't safely trace the same way. A library shipped only as CommonJS is close to a black box as far as tree-shaking is concerned. It's all or nothing.

utils.ts TypeScript 
export function formatDate(d: Date) { return d.toISOString(); }
export function formatCurrency(n: number) { return `$${n.toFixed(2)}`; }
export function debugLog(...args: unknown[]) { console.log(...args); }

If entry.ts only ever writes import { formatDate, formatCurrency } from './utils', a bundler can prove that debugLog is never reachable from the entry point. It can drop debugLog, and everything that function alone depends on, from the final bundle without executing a single line of it.

Two things break this in practice more often than the mechanism itself does. The first is barrel files, an index.ts that re-exports everything from a directory so consumers can write one tidy import line instead of five. A bundler still has to prove each individual re-exported name is unreachable before dropping it. Some barrel patterns, particularly ones mixing export * with modules that have side effects, make that proof hard enough that bundlers fall back to keeping the whole file. The second is the sideEffects field in package.json. A side effect here means a module does something observable merely by being imported, beyond exposing its named exports, such as installing a polyfill, mutating a global, or registering a custom element. Without that field, a bundler has to assume any module might have one, and keeping a module around "just in case" defeats tree-shaking for anything that module touches, even exports nobody uses. Setting "sideEffects": false tells the bundler that none of a package's modules do this. Listing specific files instead, such as "sideEffects": ["./src/polyfills.js", "*.css"], narrows that promise to exactly the files that need it.

The whole-library import trap

Writing import _ from 'lodash' pulls in a reference to the entire default export object, and a bundler generally can't prove which of its dozens of methods the rest of the file calls off of it. Named imports from an ESM-native build, for instance import { debounce } from 'lodash-es', give the bundler a specific, traceable export to reach instead of an opaque object. That's usually the actual fix when a bundle analyzer turns up a surprisingly large dependency that "should" have been small.

Code-Splitting Fundamentals

Tree-shaking removes code nobody uses. Code-splitting defers code somebody uses, just not yet.

Even after tree-shaking, a real application's reachable code can be large, including a settings page, a rarely used export flow, or an admin panel most visitors never open. Code-splitting is the decision to ship that code as a separate file the browser only fetches when it's needed, rather than folding everything reachable into one bundle a visitor downloads on their very first page load. The mechanism that triggers a split is almost always a dynamic import() call, which returns a promise rather than resolving synchronously the way a static import does. That syntactic difference is also the signal a bundler uses to decide where a chunk boundary belongs: a dynamic import() tells the bundler "this can safely be its own file, fetched later," in a way a static import at the top of a module cannot.

router.tsx TypeScript / React 
import { lazy, Suspense } from 'react';

// SettingsPage and its dependencies become their own chunk,
// fetched only when a visitor navigates to /settings
const SettingsPage = lazy(() => import('./pages/SettingsPage'));

function Route() {
  return (
    <Suspense fallback={<Spinner />}>
      <SettingsPage />
    </Suspense>
  );
}

Route-based splitting is the most common shape this takes in practice. Most metaframeworks, Next.js among them, apply it by default without any explicit lazy() call, so each page or route segment becomes its own chunk automatically. Navigating to /settings then fetches the settings chunk rather than code that was already sitting unused in the bundle for the homepage. For apps built around Server and Client Components, what lands in the client bundle at all is itself a decision upstream of code-splitting. A component that never crosses the client boundary doesn't need to be split, because it never ships to the browser in the first place. Code-splitting decides when reachable client code arrives. The server/client boundary decides whether it needs to arrive as JavaScript at all, and the two decisions compound rather than substitute for each other.

Splitting also creates a genuine coordination problem: shared dependencies. If Dashboard and Settings both import a large date-formatting library, a naive splitter would duplicate that library into both chunks. Modern bundlers instead compute a separate shared, or vendor, chunk for dependencies used across multiple entry points, so it's fetched once and cached rather than shipped twice. Getting this balance right is its own optimization problem. Split too aggressively and a page waits on a dozen small round trips instead of one larger file. Split too coarsely and visitors download code for routes they'll never open. That tradeoff is why frameworks increasingly make this decision automatically rather than asking developers to hand-tune chunk boundaries themselves.

One detail ties code-splitting to caching directly. Bundlers name each output chunk with a content hash, such as settings.a1b2c3.js rather than settings.js, so the filename itself changes whenever the content does. That lets every chunk safely carry a max-age far in the future, since a stale cached copy can never match a new deployment's filenames. The mechanism is the same long-lived HTTP caching covered in the HTTP article, just applied automatically through the filename itself. It's a small mechanical detail, but it explains why aggressive splitting doesn't come at the cost of re-downloading everything on every visit.

The Tool-by-Tool Landscape

Most of these tools aren't competing for the same job.

Vite has settled into the role of default choice for new frontend projects that aren't tied to a specific metaframework's own bundler. It's the build tool underneath Vue, Svelte, Solid, and Astro's own tooling, alongside plenty of plain React setups. Its dev-server split covered earlier is the headline feature, but its plugin API, modeled closely on Rollup's, is what let it absorb the ecosystem so quickly: a plugin written against Rollup's hook interface mostly works in Vite unmodified. As of Vite 8, released in March 2026, Rolldown is the bundler underneath both dev pre-bundling and production builds by default, with no opt-in required. It replaces the esbuild-plus-Rollup combination Vite ran on for its first several years.

esbuild remains, on its own, the fastest widely used transform-and-bundle tool for a small app or a single package, and it's still actively maintained by Evan Wallace. Its niche today is narrower than it looked in 2020. It's the engine quietly running inside other tools' dev-time transform steps more often than it's reached for directly as an app's production bundler. esbuild remains a common choice for building small libraries and CLIs, where its limited code-splitting sophistication isn't a real constraint.

Rollup's audience has stayed exactly where it was: library authors who care about clean, flat ESM and CJS output more than raw build speed, since a library's build runs occasionally rather than dozens of times a day the way an app's dev server does. tsup, the esbuild-powered zero-config wrapper that spent years as the default starting point for new TypeScript library templates, is no longer actively maintained. Its own docs now point newcomers to tsdown, a Rolldown-powered successor from the same lineage that keeps the zero-config approach while fixing tsup's rougher edges around ESM output.

webpack itself is best described today as stable rather than stagnant. Its core team still ships bug fixes, and the plugin ecosystem stays active enough that major frameworks test against it. But active feature development has clearly slowed, and Tobias Koppers, its original author, now works on Turbopack instead. Large, mature codebases with years of accumulated webpack configuration and loaders are the main place it's still the pragmatic choice. That's not because a rewrite is impossible, but because Rspack now offers a lower-risk path off webpack than a full migration to a differently shaped tool ever did.

Turbopack, Vercel's Rust-based bundler, is tightly coupled to Next.js and is the framework's default for both development and, since Next.js 16, production builds as well. Its value proposition is specific to that coupling. Because Vercel controls both the framework and the bundler, Turbopack can make assumptions and optimizations a general-purpose bundler can't. That comes at the cost of being a poor fit for anything that isn't a Next.js app.

Rspack takes the opposite bet from Turbopack: instead of a new mental model, it reimplements webpack's own configuration surface and loader API in Rust, aiming for close to drop-in compatibility. For a large existing webpack codebase, that compatibility is the entire pitch. Migrations commonly complete in days rather than the months a move to a differently configured bundler would take. That speed comes with a tradeoff, since not every webpack loader has an Rspack-compatible equivalent yet. But it exchanges a narrower slice of ecosystem coverage for a large, immediate build-time improvement with minimal config changes.

Bun, primarily known as an all-in-one JavaScript runtime, ships its own bundler via bun build, written in Zig rather than Rust or Go. It's a reasonable choice for simple app or server bundles, and for teams already committed to Bun as their runtime and package manager. Even so, most teams that adopt Bun for its runtime and install speed still reach for Vite specifically for frontend dev serving and production builds. That combination captures most of the practical benefit without giving up Vite's plugin ecosystem.

The Rust Convergence 2026

The same rewrite that hit esbuild's category in 2020 is now happening one layer down, in the parsing and transform code every one of these tools depends on.

Oxc, short for the Oxidation Compiler, is a Rust toolchain covering parsing, linting, resolving module paths, and transforming syntax (stripping TypeScript types or lowering JSX, among other jobs). Rather than one more bundler, it's shared low-level infrastructure other tools build on, the same role Babel's parser used to play for the JavaScript-based generation of tooling. Rolldown, a Rust bundler with a Rollup-compatible plugin API and esbuild-level feature coverage, is built on top of Oxc. It reached a stable 1.0 release in May 2026 with a locked API and backward-compatibility guarantees, clearing the way for Vite 8 to make it the default a few months later.

The clearest sign of how seriously the ecosystem is treating this shift arrived in June 2026, when Cloudflare acquired VoidZero, the company behind Vite, Vitest, Rolldown, and Oxc, and folded Evan You's team into its own engineering organization. Cloudflare committed to keeping all of it MIT-licensed and vendor-agnostic, and set up an independently governed fund to support contributors unaffiliated with either company. It's a deliberate hedge against the toolchain underneath most of the frontend ecosystem becoming a single vendor's proprietary lever. Whatever its business motivations, the acquisition is a fair marker of how central Vite's toolchain has become: it's no longer treated as one bundler brand competing with others so much as shared substrate underneath a large share of the ecosystem.

Not everything has converged yet. esbuild remains Go and actively maintained, not a relic being quietly retired. webpack's JavaScript codebase isn't going anywhere either, given how much production infrastructure still depends on it. The convergence is real at the level of new default choices, such as new projects, new Vite installs, and new library scaffolding, rather than a wholesale replacement of what's already deployed. That distinction matters for the decision framework below: migrating an existing, working build pipeline for a marginal speed gain is a different calculus than picking a starting point for something new.

Choosing a Tool Today

The honest answer to "which bundler" is usually "whichever one your framework already picked for you."

For a new project built on Next.js, the decision is effectively made already. Turbopack is the default and the path with the least friction, and there's little reason to fight that default outside of a narrow, specific compatibility gap. For a new project not tied to a particular metaframework, such as a Vue, Svelte, Solid, or plain React app built without Next.js's constraints, Vite is the reasonable default. Picking it also means inheriting Rolldown's speed without having to evaluate that choice directly.

For a team maintaining a large, working application already built on webpack, the calculation is about migration cost rather than which tool is theoretically best. Rewriting onto Vite means adjusting to a different plugin model and dev-time architecture. Migrating to Rspack instead means keeping the existing configuration and loader setup largely intact while swapping the engine underneath it. That's why it's become the pragmatic first move for exactly this situation, rather than a destination in its own right. Reassessing whether a bigger rewrite is worth it can happen later, once the build-time pain that prompted the migration in the first place is no longer forcing the decision.

For a package meant to be published and consumed by projects the author doesn't control, the priority shifts again: clean, predictable output across module formats matters more than build speed, since the build itself runs occasionally rather than on every save. Rollup, or tsdown as a lower-configuration, Rolldown-powered wrapper around that same output quality, remains the better fit than an app-oriented bundler tuned for iteration speed instead.

New app, no metaframework
Vite

Default choice. Fast dev server, Rolldown-powered build, broad plugin ecosystem inherited from Rollup's API.

New app, Next.js
Turbopack

Already the framework default for dev and production builds since Next.js 16. Fighting it buys little.

Existing large webpack app
Rspack

Keeps existing config and loaders largely intact. The pragmatic migration path, not a permanent destination.

One case sits outside this framework entirely: a team building microfrontends, where the bundler choice is entangled with a composition mechanism like Module Federation rather than a single app's build. That decision belongs to the tooling section of the microfrontends article rather than a repeat of it here. The same section explains why Rspack shows up again there for a different reason (Module Federation 2.0's unified runtime), and where Zephyr fits for cross-bundler dependency resolution. The through-line from this article into that one stays the same: tree-shaking and code-splitting are properties of how a bundler reasons about a single module graph. Composing several independently built graphs into one page, which is what microfrontends do, is a layer on top of everything covered here, not a replacement for it.
