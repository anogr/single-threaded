Agentic Coding Workflows

How stronger evidence turns generated code into work a team can safely maintain.

Andreas Ögren
~12 min read
Last updated July 2026

Andrej Karpathy coined “vibe coding” in 2025 for a specific way of working. A developer tells an AI tool what the program should do and keeps prompting until the result appears to work. They accept the code without reviewing the implementation in detail. The term describes this lightweight verification practice and can apply to assistants as well as agents.

Vibe coding can be reasonable for disposable experiments whose failure affects only the developer. Once other people will depend on the code, the team needs stronger evidence. It must agree on the intended behavior before implementation and verify the result before users depend on it. Specifications record this agreement, while tests and guardrails help the team check the result and limit unsafe actions.

Building on the previous article

The terms assistant and agent follow the definitions in AI Coding Assistants. Either kind of tool can be used for vibe coding. The workflow becomes risky when observed behavior is accepted without reviewing the code or checking it independently.

Vibe Coding

Vibe coding treats observed behavior as enough evidence to accept generated code.

During vibe coding, the developer may run the program and adjust the prompt several times without building an understanding of the generated implementation. The shortcut saves time when the code will be discarded and a failure affects only the developer. Code that other people depend on needs additional checks because one successful run covers only the inputs and conditions used in that run.

Verification determines whether a session counts as vibe coding. One developer may read the diff, compare it with the surrounding code, and reject anything that does not fit. Another may accept the generated change as soon as the program runs. The first developer inspects the implementation. The second relies only on observed behavior, which makes the workflow vibe coding.

Disposable Experiments

The shortcut is reasonable when the developer can spot a failure quickly and discard the result without affecting anyone else.

A developer exploring an unfamiliar API might ask an agent to produce a small test program, run it with sample data, and discard it afterward. A personal prototype can be treated similarly when an incorrect result has no effect beyond the developer's own work. In these cases, reviewing every generated line may take longer than replacing the whole artifact.

Shared code changes who bears the consequences of a defect. A broken experiment wastes its author's time, while a production defect can block users or damage their data. Those users did not choose to skip verification, so the developer must add the checks needed for the possible harm before sharing the code.

Failures in Shared Code

Generated code has ordinary software defects, but agents can produce and spread them faster.

An agent can produce code that compiles and passes a narrow happy-path test while violating an assumption outside the files it inspected. For example, a request handler may appear correct even though the agent missed an authorization rule in middleware. A database query may run successfully but omit the tenant filter required by the application. A short demonstration will not exercise either missing constraint.

An agent can build a large, internally consistent diff before anyone challenges the premise behind it. Reviewers must then understand more code at once, and a polished implementation can hide the false assumption that shaped every file. Speed increases the amount of code built on one premise and makes an early mistake more expensive to unwind.

A demo proves one path

A successful demo shows that one path worked with one set of inputs. Production code must preserve its rules across valid and invalid inputs, and security or operational checks may cover effects that the interface cannot show. Teams should spend more effort on these checks as the possible harm increases.

Spec-Driven Development

A specification lets the team review the intended behavior before implementation spreads a mistaken premise through the codebase.

Spec-driven development records what a change should achieve before implementation begins. Reviewers can read the specification to challenge its scope and constraints without first reconstructing the author's intent from a diff. Acceptance criteria describe the observable behavior that reviewers will approve. A technical plan can then map the approved requirements to the codebase and divide the work into implementation tasks.

The amount of specification should follow the size and risk of the change. One precise acceptance criterion may be enough for a bounded fix whose effects are easy to test. A feature that changes authorization, stored data, or several services needs enough detail to expose its rules and dependencies before implementation.

GitHub's open-source Spec Kit is one implementation of the pattern. Its workflow has four main steps, using commands whose exact spelling varies by agent integration. The following list shows one common form.

  1. /speckit.specify develops the feature specification.
  2. /speckit.plan records the technical approach.
  3. /speckit.tasks produces an ordered implementation list.
  4. /speckit.implement executes those tasks.

Spec Kit automates this sequence for several coding agents, but teams do not need the toolkit to use the workflow. Ordinary Markdown files can provide the specification, plan, and task list within an existing development process.

The following fragment shows a generated specification before any plan or code exists.

spec.md Markdown 
## Requirement: Password reset via email

**User story:** As a user who forgot their password, I want to
request a reset link by email so I can regain access without
contacting support.

**Acceptance criteria**
- Reset link expires after 15 minutes
- Link is single-use, invalidated after first successful reset
- Rate limited to 3 requests per email per hour
- No indication given whether the email exists in the system

The fragment describes behavior without choosing function names or file paths. A reviewer can therefore notice a missing rule, such as whether issuing a new reset link invalidates older unused links, before implementation begins. In a finished diff, the reviewer would have to infer the intended behavior and then notice that no code implements the missing rule.

A specification is a working agreement, so discoveries during planning may change it. If repository research shows that the service cannot invalidate one link without invalidating all sessions, the team should revise and approve the requirement before implementation continues. Keeping a link from each task and test back to the relevant criterion makes this change visible and helps reviewers find requirements that received no implementation evidence.

Tests from the Specification

Acceptance criteria state the behavior to preserve. Tests turn selected examples from the criteria into repeatable checks.

Acceptance criteria become easier to test when they name the event, the system state, and the required response. Easy Approach to Requirements Syntax (EARS) provides patterns for writing requirements in this form. A criterion such as When a reset link has already been used, the system shall reject it gives a test a concrete case to exercise. EARS makes a known rule more precise. The team must discover missing rules and decide whether each requirement is correct.

A spec-driven workflow can use test-driven development and behavior-driven development during implementation. Test-driven development (TDD) uses a short cycle. The developer writes a failing test, adds enough code to pass it, and then refactors the result. Behavior-driven development (BDD) uses discussion and concrete examples to develop shared understanding before turning agreed examples into executable specifications. The project specification supplies the broader intent and constraints for both practices.

Writing a specification leaves the test design to the team. Spec Kit, for example, adds test tasks only when the specification or user requests them. Some requirements need automated examples or lower-level tests, while others can be checked only by inspecting a running system. The specification records the intended behavior, and each test provides evidence for the cases it exercises.

An agent can satisfy a test task with assertions that never detect a defect, so generated tests need review. Mutation testing changes the implementation in small ways and checks whether the suite fails. Tests that continue to pass may not protect the affected behavior. Some mutations leave observable behavior unchanged, so a person must interpret the report. Reviewers should examine edits to an existing failing test especially closely because weakening an assertion can remove the requirement that caused the failure.

Generating new tests
Mutation analysis

Mutation testing changes the implementation and checks whether the tests notice. A high mutation score can give stronger evidence than line coverage alone. Reviewers must examine surviving mutants because some leave behavior unchanged or affect irrelevant code.

Editing existing tests
Human approval gate

When an agent changes a failing test, a person must confirm that the revised assertion protects the intended behavior. A weakened assertion can make the suite pass without appearing in a coverage report.

Context Engineering

Prompt engineering improves the wording and examples in one request. Context engineering chooses the information available throughout the task.

Context engineering decides what an agent can see and when it sees it. Every instruction, file, and tool result included in a model request uses part of its finite context window. During implementation, the agent needs access to the approved specification and the relevant parts of the plan. Unrelated tool output should not crowd out either document.

The context files covered in the previous article contain stable project knowledge used across many tasks. The specification and plan add information for the current change and can leave the context when the task ends. Subagents can keep exploratory side work in a separate task thread and return only the findings needed by the main task. Together, these techniques reserve the main thread for information that supports the agent's next decision.

Selection happens again on every model request. An early planning request may need the specification, repository map, and related interfaces. A later debugging request needs the failing test, recent edit, and relevant implementation. Repeating the entire session on every turn spends capacity on stale observations. Summaries and persistent task state can carry decisions forward while the harness reloads authoritative source files when their exact contents are needed.

Harness Engineering

A harness applies tools, permissions, and automated checks across every agent session.

Harness engineering designs the software and policy around the model. The harness decides which tools the agent may use and which actions need approval. It can run automated checks and isolate the agent's work. Harness controls apply across sessions and limit which actions the model can take even when its prompt or context is incomplete.

A written instruction cannot guarantee that the model will follow a rule such as a ban on production migrations. The harness can withhold the production credential or require approval before the command executes. Either control enforces the rule when the model overlooks the instruction.

A small harness might isolate the agent in a worktree and deny access to production credentials. After each edit, it can run deterministic tests and record the tool calls. Larger systems can retain task state and coordinate several agents. The multi-agent systems article covers the additional coordination work required when a task genuinely benefits from parallel workers.

Recorded tool calls make a run inspectable after the generated explanation is gone. The record can show which files the agent read, which command produced a failure, and whether approval preceded an external action. Replaying every model decision may be impossible when a provider or model version changes, but retaining inputs, outputs, tool effects, and versions gives an investigation concrete evidence.

Prompt Engineering

Prompt engineering improves one request by refining its wording, examples, and structure.

One session
Context Engineering

Context engineering selects the project rules and task-specific decisions that fill one session's window.

Every session
Harness Engineering

Harness engineering builds persistent controls around every session. Permissions and automated feedback prevent recurring mistakes.

The harness can run mutation tests and return their results to the agent. It can block file edits until a person approves the plan, then require the grounding check described next. Each control catches a specific failure before correction becomes expensive.

Context Blindness

Repository changes can invalidate a clear plan before implementation begins.

Context blindness occurs when an internally consistent plan no longer matches the repository. It may rely on an old function signature, a moved file, or a data model changed by a later migration. Reading the plan alone will not reveal the mismatch because its statements agree with one another. The conflict appears only when those assumptions are checked against the current code.

A grounding step checks the plan against the live repository before implementation. It can verify that referenced paths exist, inspect the current function signatures, and compare data-model assumptions with the latest migrations. The check may be performed by the implementing agent or by a separate read-only pass. At this stage, correcting the plan is cheaper than unwinding an implementation built from obsolete assumptions.

Ungrounded
Plan trusted at face value

The plan appears consistent and receives approval. Implementation may then fail partway through or produce incorrect code based on an obsolete assumption.

Grounded
Plan checked against the repo

Before implementation, the plan's claims about code and data are checked against the current repository so obsolete assumptions can be corrected.

Review Gates

Review effort should follow the possible harm while giving people a chance to correct intent and approach before implementation hides them.

Vibe coding lets implementation begin without an independent review. For a consequential change, a controlled spec-driven workflow can ask a person to approve the specification before technical planning begins. A second review can check the grounded plan before the agent changes any files. The first review may find a missing requirement, while the second can correct a mistaken dependency before it spreads through a large diff.

A bounded, reversible change may combine specification and plan review or proceed directly to diff review when its intent is clear and automated checks constrain the result. Changes that affect authorization, personal data, payments, or destructive operations need earlier and more specialized approval. The team should choose each gate from the effect of a failure and the cost of reversing it.

The final diff needs review against the behavior approved in the specification. Plan review checks the proposed approach against the repository. Diff review then determines whether the agent implemented the approved change safely.
