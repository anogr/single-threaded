Agentic Coding Workflows

How specifications, tests, context, and guardrails make agentic development safer once code is meant to last.

Andreas Ögren
~12 min read
Last updated July 2026

Andrej Karpathy coined “vibe coding” in 2025 for a specific way of working. The developer describes the desired behavior in natural language, accepts the generated code, and judges it by what the program appears to do rather than by reading every line. The phrase quickly broadened into a label for almost any AI-assisted development, but the original distinction is still useful. It describes the verification practice around the tool, not the tool itself.

This article draws the boundary around that practice and explains why the acceptable boundary changes with the cost of failure. It then develops a safer workflow for production work, moving from specifications and executable tests to context management, guardrails, and human approval.

Building on the previous article

This article assumes the assistant/agent distinction from AI Coding Assistants. Vibe coding can happen with either kind of tool. Its risk comes from accepting behavior without understanding or independently verifying the code that produced it.

What Vibe Coding Means

The useful boundary is not whether AI wrote the code, but whether anyone established that the result was safe to rely on.

Vibe coding means directing an AI tool in natural language and accepting its output because the result appears to work. The developer may run the program and adjust the prompt several times, but does not build an understanding of the generated implementation. That can be a rational shortcut when the code is disposable. It is not a verification method.

The working practice around the tool is more important than the tool itself. Two developers can run the same agent on the same task and be doing very different things. One reads every diff before it merges, catches the parts that don't fit, and rejects or rewrites what's wrong. The other accepts the result once it runs. Both count as "using AI to code," but only one of them is vibe coding in the sense used in this article.

The Legitimate Cases

Karpathy's own later framing draws the boundary better than most of the discourse that followed his original post.

The approach fits work with a deliberately small blast radius. A weekend prototype, a personal script, or a throwaway exploration of an API can all qualify. The codebase does not have to be tiny; the consequence of failure does. If an incorrect result costs little and the artifact can be discarded, understanding every generated line may cost more than it protects.

The calculation changes when the code has to serve anyone other than the person who wrote it. The tool doesn't get worse when the stakes go up. What changes is the price of the missing verification step. Skipping it cost nothing while only the author's own time was on the line. Now it carries the cost of whatever a stranger does with a bug nobody caught.

The Production Failure Pattern

Generated code usually fails through ordinary software defects. The workflow makes those defects easier to ship in volume.

An agent can produce code that compiles, passes a narrow happy-path test, and still violates an assumption outside the files it inspected. Authorization rules may live in middleware the agent never opened. A database client may require tenant filtering that is conventional rather than type-checked. A retry may be correct for reads but duplicate a payment when copied into a write path. None of these failures is unique to generated code, and each can survive a demonstration that “works.”

Agentic speed changes the exposure. A developer can now create a large, internally consistent diff before anyone has challenged the premise behind it. Reviewers must understand more code at once, while the polish of the implementation can make the original assumption harder to notice. The resulting risk comes from scale and misplaced confidence rather than from a new species of bug.

Behavior is evidence, not understanding

A successful demo establishes that one path worked with one set of inputs. Production confidence needs the relevant invariants, failure paths, security boundaries, and operational effects to be checked. The amount of checking should follow the cost of being wrong.

Spec-Driven Development

A specification creates an early review point for intent, before implementation detail makes a mistaken premise expensive to unwind.

Spec-driven development records what a change should achieve before implementation begins. The specification stays separate from the code, so a reviewer can challenge scope, constraints, and acceptance criteria without first reconstructing intent from a diff. A technical plan and task breakdown can then translate that agreed behavior into implementation steps.

GitHub's open-source Spec Kit is one implementation of the pattern. Its core workflow moves through four artifacts:

  1. /speckit.specify develops the feature specification.
  2. /speckit.plan records the technical approach.
  3. /speckit.tasks produces an ordered implementation list.
  4. /speckit.implement executes those tasks.

The toolkit supports integrations with several coding agents, but the sequence does not depend on Spec Kit. A team can use the same review points with ordinary Markdown artifacts and its existing development process.

A fragment of what a generated specification looks like in practice, before any plan or code exists:

spec.md Markdown 
## Requirement: Password reset via email

**User story:** As a user who forgot their password, I want to
request a reset link by email so I can regain access without
contacting support.

**Acceptance criteria**
- Reset link expires after 15 minutes
- Link is single-use, invalidated after first successful reset
- Rate limited to 3 requests per email per hour
- No indication given whether the email exists in the system

The fragment contains no function names, no file paths, and nothing else that presumes a particular implementation. This is deliberate. A reviewer can catch a missing requirement, like the rate limit or the no-enumeration rule, in the minute it takes to read four bullet points. Catching the same gap in a finished diff means noticing what isn't there, which is a much harder thing to review for.

Tests as the Executable Spec

A well-written acceptance criterion isn't just readable by a person. It's close enough to a test case that turning one into the other is barely a translation.

The password-reset example resembles Easy Approach to Requirements Syntax (EARS), a set of patterns developed at Rolls-Royce for writing constrained natural-language requirements. Forms such as “when X happens, the system shall Y” make the trigger and required response explicit. The result is easier for a person to review and easier to translate into test cases, although a consistent sentence shape cannot by itself make a requirement complete or unambiguous.

This makes it easier to see how spec-driven development differs from two older practices it keeps getting compared to. Test-driven development says write the failing test first. Behavior-driven development says write the behavior first, in language a non-engineer on the team can still read, then derive the test from it. Spec-driven development pushes the artifact up one more level. Write the whole spec, with behavior, constraints, and edge cases together, and let an agent generate the code, the tests, and often a first pass at documentation from that single source. Each of the three chooses a different artifact as the one everything else follows from.

Generated tests need their own verification because an agent can satisfy a test task with assertions that prove very little. Mutation testing provides one mechanical check: it introduces small changes into the implementation and measures whether the tests detect them. Surviving mutations can reveal behavior the suite did not protect. Some mutations are equivalent to the original behavior, so the report still needs interpretation. Editing an existing failing test is riskier, because removing or weakening an assertion can make the suite green while discarding the requirement. Such edits need a reviewer to confirm that the test still expresses the intended behavior.

Generating new tests
Mutation analysis

Mutation testing changes the implementation and checks whether the tests notice. A high mutation score is stronger evidence than line coverage alone, but surviving mutants still need review because some are equivalent or irrelevant.

Editing existing tests
Human approval gate

A test changed to make a red suite green again needs a person to confirm it's still checking the right thing. The failure mode here is silent and doesn't show up in a coverage report.

Context Engineering

Prompt wording shapes one request; context engineering shapes the information available throughout the task.

Context engineering is the work of deciding what an agent can see and when it sees it. The managed resource is the finite context window, not only the wording of the latest prompt. In a spec-driven workflow, the specification and relevant plan must remain available during implementation without being buried under unrelated tool output.

The context files covered in the previous article are one piece of this, the stable, rarely-changing part of what an agent should always know about a project. Spec-driven development adds a second, session-specific layer on top. The specification and plan generated for this particular task become part of what the agent references while implementing it, effectively acting as working memory for that one piece of work. Subagents approach the problem from the other direction. They keep a large exploratory side-task out of the main session by returning findings instead of every file and dead end. Getting this right is less about any single clever instruction and more about making sure the right documents are in front of the model at the moment they're needed.

Harness Engineering

Context engineering asks what the model can see this session. Harness engineering asks a broader question. It asks what stops a mistake from recurring in a later session.

Harness engineering moves one level beyond the context of a particular session. The harness is the standing software and policy around the model. It includes tool access, permission checks, feedback loops, isolation, observability, and approval gates. Prompt and context design stay part of the system, but the harness determines which mistakes are possible and which are caught automatically.

A repository instruction can tell an agent not to run a production migration, but the model may misunderstand or overlook the instruction. A harness can withhold the production credential or require an approval before the command executes. The latter control applies to every session and does not depend on the model choosing correctly. This is the central value of the harness: recurring risks become properties of the surrounding system instead of reminders embedded in prose.

A harness can be small. A permission policy, an isolated worktree, deterministic tests, and a log of tool calls already provide meaningful control around one agent. Larger systems add persistent task state and coordination across several agents. That expansion introduces a separate set of tradeoffs, covered in multi-agent systems, and should follow a real need for parallel work rather than the availability of more agents.

One request
Prompt Engineering

Getting a single request phrased well, one exchange at a time, through the wording, the examples, and the structure.

One session
Context Engineering

Curating what fills the window for a session, such as specs, rules, and prior decisions, so a good prompt has the right material behind it.

Every session
Harness Engineering

Building the standing infrastructure around the agent, such as tool permissions, guardrails, feedback loops, and observability, so a whole class of mistake can't recur.

The earlier controls fit naturally into this layer. Mutation testing gives the agent deterministic feedback about weak tests. A plan checkpoint prevents implementation before a person has approved the intended change. The grounding step in the next section checks whether that plan still matches the repository. Each control assumes that plausible output may be wrong, then catches a different failure before it reaches production.

Context Blindness

A spec can be perfectly well written and still describe a repository that no longer exists.

Context blindness occurs when an internally consistent plan no longer matches the repository. It may rely on an old function signature, a moved file, or a data model changed by a later migration. Reading the plan alone will not reveal the mismatch because every statement can still fit the plan's own assumptions. The conflict appears only when those assumptions are checked against the current code.

A grounding step checks the plan against the live repository before implementation. It can verify that referenced paths exist, inspect the current function signatures, and compare data-model assumptions with the latest migrations. The check may be performed by the implementing agent or by a separate read-only pass. Either way, the plan is corrected while it is still cheap to change.

Ungrounded
Plan trusted at face value

The plan reads correctly and gets approved. Execution fails partway through, or worse, succeeds against a stale assumption and produces something quietly wrong.

Grounded
Plan checked against the repo

Before implementation, specific claims in the plan (a signature, a file path, a schema) are verified against the current codebase, and the plan is corrected if reality has moved.

Where the Human Gate Belongs

Review the plan, not just the diff.

Pure vibe coding has no gate at all, which is what makes it fast for a throwaway script and dangerous for anything else. A well-run spec-driven workflow has an obvious place to put one, right after the plan and task list are generated and before any file has changed. A wrong plan takes a few minutes to read and correct. A wrong forty-file diff built from that same wrong plan takes much longer to review. A subtle gap, like the missing rate limit in the earlier example, is far easier to let slip past a diff review than past someone reading four acceptance criteria.

Plan review does not replace review of the final diff. It catches errors in intent before they become implementation, while diff review checks whether the approved plan was carried out safely.
