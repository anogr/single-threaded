Layout, Spacing, and Sizing

How browsers turn content and available space into adaptable layouts, and how clear ownership keeps those decisions maintainable.

Andreas Ögren
~33 min read
Last updated August 2026

A web page starts with two kinds of input. HTML describes the page's content and structure, such as a heading, a paragraph, or a list of products, without saying where on the page any of it should appear. CSS describes how that content should look and how much space it should take, but it does not fix an exact position either. Neither format works like a drawing or a file from design software, where every element already sits at a fixed x and y coordinate. Before anything can appear on screen, the browser has to turn that content and those style rules into an actual arrangement of pixels. During layout, the browser generates rectangular boxes from the document's elements and text, determines how large those boxes should be, and places them in relation to one another.

That arrangement is not fixed once it is computed. The viewport is the visible area of the web page within the browser window, and its dimensions differ across screens and change whenever someone resizes the window or rotates a device. The content on the page can change too, since the same page might show different data or a different language depending on who requests it. A reader can also enlarge the text to make it easier to read. The browser has to calculate sizes and positions again every time any of these things change. CSS layout makes it possible to preserve the page's relationships under those changing conditions, instead of describing one fixed arrangement that only works at a single size.

Sizing controls how much space a box may take and whether that space comes from its content, its surroundings, or a declared limit. Spacing controls the distance inside a box and between neighboring boxes. The surrounding layout provides the available space for a box, and the box's content contributes its required size. Changing either the available space or the content can change the box's final size. Within a fixed available width, for example, increasing the space inside a box leaves less room for its content and can cause text to wrap.

This article explains how CSS layout works and how to apply it to adaptable web pages. It covers how layout, sizing, and spacing work together.

Layout Combines Available Space and Content Size

CSS layout combines constraints supplied by a parent with sizes contributed by its children.

An element that directly contains another element is its parent, and directly contained elements are its children. An online store page's body contains a navigation column, a main product catalog, and a recommendation column as its children. The navigation column contains links to product categories. The catalog is the page's primary content, while the recommendations supplement it with a smaller selection of products. Each direct child that serves a distinct page-level purpose is a page region.

A media query makes page-level rules conditional on a viewport characteristic such as a minimum width. Those rules can place the three regions side by side in a wide viewport and stack them when the viewport is too narrow for that arrangement. At the width illustrated below, the page layout assigns most of the available width to the catalog and narrower shares to navigation and recommendations.

The page layout arranges the three regions, and each region then lays out its own children. The layout established by a parent determines how its child boxes share the available space. The catalog region is the parent of its product cards, and each card is in turn the parent of its own image, name, price, and link. The page layout constrains the available space, and each nested layout receives a share of it. This is the top-down direction of layout.

Parent constraints do not provide enough information to determine every size. The parent layout also uses size information from its children. Words and wrapping opportunities determine the possible widths of a piece of text, while an image may provide dimensions in its source. A longer product name can make its card taller. When a catalog row's height depends on the cards inside it, a taller card then increases the height of the whole row. This is the bottom-up direction of layout.

Top-down and bottom-up describe where the sizing information comes from. They are not two fixed browser passes that always run in sequence. A layout algorithm may measure content, assign space, and repeat those steps when one result depends on a value that has not yet been computed.

Width and height can affect each other during layout. When the text area is narrower, the product name wraps onto more lines, and each extra line makes the card taller. Increasing the card's horizontal padding leaves less room for the same text, so a spacing decision can change the resulting height as well. The browser must know the available width before it can determine how the text wraps and how much height the card uses.

The browser lays out each set of children using size information from the content and any author-declared constraints. It places the page regions, arranges the product cards within the catalog, and then lays out the image, name, price, and link inside each card.

CSS Boxes Provide the Measurements

The browser measures CSS boxes when it compares the space available from a parent with the size required by its children.

CSS usually represents an element with a rectangular CSS box whose content area is surrounded by padding, a border, and a margin. The four nested areas define the content box, the padding box, the border box, and the margin box, each with different dimensions. The phrase “the product card's width” is therefore incomplete until the relevant edge is known.

A box's edges do not always match what appears painted on screen. The border-radius property rounds the visible corners of the border. The clip-path property can clip the painted content to a circle, polygon, or another shape. A transform can rotate, scale, or move a box's rendered appearance. Regardless, the box underneath still reserves its full rectangular area among its siblings.

One element, multiple boxes

An element does not always generate exactly one such box. A paragraph usually generates a surrounding box that contains line boxes, while its text is split into inline fragments when it wraps across those lines. A list item, for example, generates a marker box for its bullet or number alongside the box that holds its content. CSS layout operates on these generated boxes rather than on a developer-defined visual group such as “product card.” That grouping exists only in the developer's markup and mental model. The element tree establishes the document structure, while the box tree is the set of boxes that CSS layout actually measures and positions.

The box-sizing property determines whether declared sizes apply to the content box or the border box. Its initial value is content-box where the declared width applies to the content area. With border-box, the same declared width includes the content, padding, and border. Margin remains outside both measurements.

The box-sizing value determines whether padding expands the declared width or reduces the space available to content. Consider a card with width: 20rem and box-sizing: content-box. Adding padding to it makes the card wider. The same card with border-box keeps a twenty-rem border box, so additional padding leaves less room for its content.

Applying box-sizing: border-box consistently can make component dimensions easier to reason about because padding and borders stay inside the declared size. It does not prevent overflow by itself. Content, minimum sizes, or margins can still make a box exceed the space available to it.

Document Flow Connects Neighboring Boxes

A box in normal flow participates in a shared layout and therefore affects the space available to nearby boxes.

Normal flow is the default layout for boxes that have not been taken out of flow. Block-level and inline-level boxes participate in normal flow differently. An ordinary non-replaced block-level box with an automatic width fills the available inline space. It is placed after the preceding block-level box along the block axis. It accepts a declared width, height, and vertical margin the same way the box model describes. An inline-level box instead participates in a line of text. In horizontal English text, it sits beside the inline-level box before it and moves to a new line when the current line has no more room. For an ordinary non-replaced inline box, width and height do not apply, and top and bottom margins do not change the line's layout. Its size follows its content, while left and right margins affect the surrounding inline content.

The product card contains both kinds of box. Its container and product-name heading are block-level boxes that stack vertically. A link in its description is an inline-level box that sits among the surrounding words in this horizontal writing mode.

Every element has a value for the CSS display property, which controls the boxes it generates and how they participate in layout. A <div>, a <p>, and an <h1> default to display: block. A <li> defaults to display: list-item, which gives it a block-level box for its contents and a marker box. A <span>, an <a>, and a <strong> default to display: inline. These defaults reflect the elements' usual roles. Headings begin a new block, while links and emphasized text remain within a line.

A box's size can also change the position of boxes that follow it. Each block-level box stacks below the one before it, so a taller heading pushes the paragraph after it further down the page. Each inline-level box sits in the same line as the one before it. A wider word or link therefore changes where the next fragment starts and can push later words onto a new line.

display: inline-block combines both behaviors. The box still sits inline with the surrounding content, but it accepts a width, a height, and vertical margin the way a block-level box does. A star rating badge placed next to the price is a common use, since it needs a fixed size without forcing a line break around it.

These three display values differ as follows:

  • display: block starts a non-replaced box on a new line and, with the default automatic width, fills the available inline space.
  • display: inline places a non-replaced box inside a line of surrounding content and sizes it from that content.
  • display: inline-block places the box inside a line like an inline box, but lets it accept a width, a height, and vertical margin like a block-level box.

A different value, display: none, does not generate a box at all. The element has no visual presence and no effect on the boxes around it, the same as if it had been removed from the HTML.

Other display values change how an element's children are laid out. With display: flex or display: grid, the children participate in Flexbox or Grid layout.

Top to bottom and left to right describe the common case in a horizontal writing system, but the direction itself can change. The inline axis is the direction along which inline-level boxes flow within a line. The block axis is the direction along which block-level boxes stack. English commonly uses a horizontal inline axis and a vertical block axis, while a vertical writing mode maps those same logical axes to different physical directions.

Logical properties express sizes and spacing through these axes. A declaration such as padding-inline applies padding on both sides of the inline axis, regardless of which physical edges correspond to those logical sides. Physical properties such as width and margin-left remain appropriate when the design depends on a physical dimension or edge.

Suppose the product card has width: 50%. Because it is a block-level box inside the catalog region, that percentage resolves against the catalog region's content box. An 800-pixel-wide catalog therefore gives the card a used width of 400 pixels, and resizing the catalog changes the card's width. CSS calls that reference box the containing block rather than simply the parent. In ordinary block layout the two are usually the same box, so the distinction rarely matters here. The distinction matters in positioned layout. An absolutely positioned box may use its nearest positioned ancestor as its containing block rather than its parent.

Positioned Layout Changes Participation

The position property can preserve a box's place in flow or remove the box so that it no longer reserves space.

By default, CSS places every box using normal flow. In normal flow, each box occupies space that affects where later boxes are placed. The position property can change that arrangement for an individual box. It can keep the box in normal flow while shifting where it is drawn, or it can remove the box from normal flow entirely, so that other boxes no longer make room for it.

The initial value, position: static, leaves a box in normal flow with no shift at all. Relative positioning with position: relative also preserves the box's original place in flow, but inset properties such as top and left can shift where it is drawn. The boxes that follow still use the unshifted position when they are laid out, so a visual offset does not create new space around the moved box.

Relative positioning can also establish the containing block for an absolutely positioned descendant. Absolute positioning, set with position: absolute, removes a box from normal flow, so it no longer reserves space among its siblings. The browser resolves its top, right, bottom, and left offsets and any percentage width or height against a containing block.

Positioning an ancestor is one way to establish that containing block. When position is the property that establishes it, the browser uses the nearest ancestor whose position value is not static. That ancestor's padding box becomes the reference, so top: 0 places the absolutely positioned box's top margin edge against the top edge of that padding box. If no ancestor establishes an absolute-positioning containing block, the browser falls back to the initial containing block, which for a page open in a browser window has the dimensions of the viewport.

Other ancestor properties can also qualify

A non-positioned ancestor can still become the containing block for an absolutely positioned box. A transform, filter, or perspective value other than none can do so, as can will-change when it names a qualifying property. Certain contain values such as contain: layout and a content-visibility value of auto can also establish a containing block.

The product-card badge shows how relative and absolute positioning work together. Without a positioned ancestor nearby, an absolutely positioned badge on a product card would be placed against the whole viewport instead of against its card. Giving the card position: relative establishes its padding box as the badge's containing block, even without inset values. The badge can then be pinned to a corner of the card instead of the page. The card itself remains in normal flow throughout.

Fixed positioning with position: fixed removes a box from normal flow like absolute positioning, but an ancestor's non-static position value alone does not establish its containing block. Its containing block is the viewport by default, which is what allows a notice to remain at the same viewport position while the document scrolls. An ancestor with a transform, filter, or another qualifying property can also establish the containing block for a fixed box, just as it can for an absolutely positioned box. Fixed positioning is therefore relative to the viewport only when no such ancestor intervenes.

Sticky positioning with position: sticky keeps a box in normal flow but shifts it within its nearest scrollport as the page or container scrolls. A scrollport is the visible area through which a scrolling box is viewed. The declared inset and the box's containing block limit how far it can move. A section heading can therefore remain visible during part of a scroll without giving up the space it occupies in the document.

The five position values differ as follows:

  • position: static is the initial value. The box stays in normal flow, and inset properties have no effect.
  • position: relative keeps the box in normal flow but lets inset properties shift where it is drawn, without changing the space reserved for it.
  • position: absolute removes the box from normal flow and positions it against its nearest positioned ancestor, or the initial containing block if there is none.
  • position: fixed removes the box from normal flow and positions it against the viewport, unless an ancestor establishes a different fixed-positioning containing block.
  • position: sticky keeps the box in normal flow but shifts it within a declared inset as the page or container scrolls, until the box's own containing block limits how far it can go.

Stacking Context Determines Paint Order

The browser paints overlapping boxes in a defined order, and z-index values are comparable only within the same stacking context.

Boxes can overlap after one is removed from flow or shifted from its original position. When boxes overlap, the browser uses the paint order to determine which content appears on top. The z-index property can assign a box a numeric stacking level, but those numbers are comparable only when the boxes participate in the same stacking context. A stacking context groups an element with its descendant boxes. Their z-index values are compared within that context rather than directly against every z-index on the page. Within a stacking context, a higher positive z-index paints after a lower positive level when both are compared in the same context. A descendant's own z-index cannot move it above a sibling stacking context that is painted later.

A positioned element with a z-index other than auto creates a stacking context rooted at that element. Fixed and sticky positioned elements also form stacking contexts. Properties such as opacity and transform can create a stacking context too, without requiring positioning at all, since each of those properties can already change how the element is composited on screen. The isolation: isolate declaration creates a stacking context without otherwise changing the element's appearance. It is useful when a component must contain its own z-index values without relying on an unrelated property. The element and its descendants are then painted together as one item in the parent stacking context.

The browser paints each stacking context as a single item among the sibling contexts in its parent. If the context-creating element has a z-index, that value ranks the whole context against its sibling contexts, the same way it would rank an ordinary descendant. When two sibling contexts have no distinguishing z-index, the one that appears later in the HTML paints on top of the other.

The Browser Resolves Size from Content and Context

The browser calculates a used size from the available space, the content's size, and limits declared in CSS.

If the product card has width: 50%, the browser resolves that percentage against the width of its containing block. Moving the unchanged card into a narrower container then results in a narrower used width. Extrinsic sizing describes sizing that depends on constraints outside the box.

Content also contributes intrinsic sizing information. A product name has widths at which its text can wrap, while an image may carry natural dimensions in its source data. Intrinsic sizing derives a size from the content itself, without regard to the space the surrounding layout would otherwise offer.

Text contributes two useful intrinsic widths. At its min-content width, the text wraps at every available opportunity and is roughly as wide as the longest word or other unbreakable run of characters. Its max-content width lays the text out on a single line instead, without wrapping at all. These values describe limits supplied by the content. They do not force the final box to use either width.

Images, video, and other embedded content contribute intrinsic dimensions differently from text because they do not wrap. An image may provide a natural width, a natural height, and a natural aspect ratio. When CSS determines one dimension and leaves the other automatic, the browser can use that ratio to calculate the automatic dimension.

The aspect-ratio property gives a box a preferred ratio for sizing. When one dimension is constrained and the other remains automatic, the ratio helps determine the automatic dimension. A full-width placeholder with aspect-ratio: 16 / 9 can therefore reserve space before its image or video arrives.

Authors can constrain the sizing calculation with width, min-width, and max-width. width provides a preferred width. min-width sets a lower bound, while max-width sets an upper bound. The layout algorithm resolves the used size from these declarations, the containing block, and the content's intrinsic contributions.

The fit-content calculation combines intrinsic sizes with available space. It uses the available space when that space falls between the intrinsic minimum and maximum. The result is limited by the min-content size on one side and the max-content size on the other. For example, a button can use width: fit-content. If the surrounding container offers more space than the button's label needs, the button shrinks to wrap the label snugly instead of stretching to fill the container. If the container is narrower than the label's min-content width, the button still uses that minimum, so an unbreakable run can overflow rather than make the button shrink further. The button's final width therefore depends on both its content and the available space.

Content or a declared minimum can make a box exceed the available space and overflow. A long unbreakable value may contribute more width than the parent can provide. Enforcing a declared minimum can create the same visible result, although the source of the constraint is different.

The overflow property controls what happens when content extends beyond a box's padding box. Depending on the chosen value and axis, the excess may remain visible, be clipped, or become reachable through a scrolling mechanism. The property controls how the excess is displayed.

Diagnosis should therefore begin with the box edge, intrinsic contribution, or declared minimum that led to the conflict. The appropriate correction depends on the relationship the layout must preserve. The content may be allowed to break, an unnecessary minimum may be relaxed, or the container may deliberately clip or scroll the excess.

Layout Algorithms Coordinate Children

At each nesting level, a container's layout algorithm determines how its children contribute size, share available space, and align with one another.

Ordinary block and inline layouts are suitable when content should follow the document's natural sequence. Setting a container to display: flex or display: grid gives its children a different layout algorithm. The container itself normally remains an in-flow box within its parent, so changing the algorithm for its children does not remove the container from the surrounding page layout.

Flexbox starts with a sequence along a main axis, while the perpendicular direction is the cross axis. These are not the same pair as the inline and block axes from earlier. The main axis follows the inline axis by default. With flex-direction: column, it follows the block axis instead. The writing mode alone therefore does not determine its physical direction. A toolbar can distribute actions along a horizontal main axis. Its items may grow or shrink as the container allocates the available space, and wrapping can create additional flex lines when one line is not enough.

Grid defines explicit rows and columns for layouts that need alignment in two dimensions. Grid declarations specify the sizes of those rows and columns, and the children are placed into that structure instead of simply following one after another. A child can also be given a specific row or column of its own, so its position does not have to follow the order it appears in the markup. In the catalog, Grid can align product cards across shared rows and columns. Flexbox does not provide the same cross-row alignment because each flex line is laid out independently.

The choice of algorithm depends on the required relationship. Flexbox suits a sequence distributed primarily along one axis, even when it wraps. Grid suits layouts that need alignment across rows and columns. Both algorithms still resolve sizes from available space, intrinsic contributions, and declared limits.

order changes visual order by default

The order property applies to flex and grid items. It can change an item's visual position without changing its place in the document. The CSS Flexible Box Layout specification states that style sheets that use order to perform logical reordering are non-conforming. With the default reading-flow: normal, order does not affect tab order or the sequence exposed to speech. CSS Display Level 4 defines reading-flow as a separate container property for setting a different order for speech and sequential navigation. Some reading-flow values take order into account. Without an explicit reading flow, a keyboard user's focus still follows the document, not the screen. If focusable items are visually reordered, keyboard focus may jump between distant positions because the tab order still follows the document. The source order should express the intended logical sequence, and order should be reserved for adjustments that are genuinely visual.

Flexbox and Grid provide separate properties for alignment, sizing, and placement. Detailed Flexbox and Grid properties are outside this article's scope.

Spacing Expresses Ownership and Grouping

Spacing affects both the room available in a layout and whether readers perceive neighboring content as a group.

Spacing changes both the room available to content and the relationships readers perceive. Readers group a label with a nearby value, while a larger distance separates that pair from the next group. UX Principles explains why proximity works this way. The element responsible for a relationship should also control the CSS declaration that creates the distance. A component therefore owns the spacing among its internal parts, while its parent owns the spacing between sibling components. Keeping each declaration with its owner preserves those relationships when content wraps, a component is reused, or the design changes.

Padding creates space between a box's content and its border. That space is entirely internal to the box. On the product card, the card's own styles therefore set the padding. With border-box, increasing padding inside a fixed width leaves less room for the content and can cause the text to wrap onto more lines.

The gap property creates gutters between grid tracks, between flex items or lines, and between columns in multi-column layout. This distance belongs to the container, since only the container's own layout determines how its children relate to one another. For example, the catalog can change the distance between cards without adding sibling-dependent rules to each card.

Margin creates space outside a box's border. Unlike gap, which belongs to a container's layout, a margin belongs to one edge of a specific box. A heading can use its bottom margin, for example, to contribute space before the paragraph that follows it.

Adjacent vertical margins can collapse in normal block layout. Consider a heading with margin-bottom: 2rem immediately followed by a paragraph with margin-top: 1rem. These margins do not create 3rem of space. The adjacent margins collapse to the larger value, producing 2rem. Margins on flex or grid items do not collapse, and collapsing never applies to the gap property, which creates space through a separate mechanism. For a known set of children, gap usually expresses the intended spacing more directly than margins on each child.

A spacing scale is a limited set of reusable distances. It reduces one-off values, but developers still decide which box should use each value. The catalog still owns the gap between cards, while the card owns its internal padding. Design Systems explains how token names can preserve these distinctions across a larger system.

Responsive Rules Follow Their Owner

Continuous changes in available space often need only flexible sizing. A media or container query is needed when the arrangement itself must change.

Responsive design allows a layout to adapt when its available space changes. Flexible sizing and wrapping can absorb some changes without switching to a different arrangement. When the navigation, catalog, and recommendations no longer fit beside one another, the page layout can stack those regions instead. The element that arranges a set of children should also own the rule that changes their arrangement. The page therefore controls changes among page regions, while a component controls changes among its internal parts.

Breakpoints and their owner

A breakpoint is the threshold at which a layout switches to a different arrangement, rather than simply reflowing within its current one. The new arrangement determines the threshold because it needs enough width to work. Nominal device categories do not determine that point. CSS can test a page-level breakpoint with a media query or a component-level breakpoint with a container query.

A viewport-width media query tests a condition against the width of the page's viewport, so it suits page-level changes such as switching the regions from a stacked column to a side-by-side arrangement. A container size query instead tests the size of a nearby ancestor declared as a query container. A descendant can then change its own styles according to the space that ancestor actually provides, regardless of where in the page that ancestor sits. This keeps the page responsible for allocating space to a region, the region is responsible for arranging the cards, and a card stays responsible for deciding how its own elements use whatever space it receives.

The card itself can act as that ancestor, establishing an inline-size query container with container-type: inline-size. The card layout starts with one grid column, and an @container rule can add an image column once the card's own content box has enough inline space. The query condition therefore depends only on the space needed by the card's two-column layout, not on the region that contains it.

Continuous adaptation

Some layouts need no breakpoint because their sizes and wrapping already respond continuously to available space. Text wraps as its available inline size narrows. A wrapping flex container moves items to another line when they no longer fit, while a grid with repeating columns reduces the number of columns. Minimum and maximum sizes define the useful range for that adaptation. A minimum keeps an item from becoming too narrow. Once items reach that limit, the flex or grid layout fits fewer of them on each line instead of shrinking them further. A maximum keeps an item from stretching beyond the width the design can use. These declarations stay with the box or layout whose size they constrain.

The clamp() function combines a preferred value with lower and upper bounds, as in clamp(1rem, 4vw, 2rem). The computed value can change continuously but never falls below 1rem or rises above 2rem. If the preferred value includes a viewport-percentage unit such as vw, the result follows the viewport width until it reaches one of those bounds. The clamp() declaration belongs to the element whose size it controls.

Choosing a unit

The appropriate unit depends on the measurement that should determine the value. The rem unit resolves against the root element's font size. The em unit resolves against the current element's font size, except when it sets font-size itself, where it resolves against the inherited font size. These units suit type and spacing that should scale with the corresponding text size. A viewport-relative unit such as vw resolves as a percentage of the viewport width, which suits page-level values but not measurements inside a nested container. A container query length unit such as cqi resolves against the inline size of the nearest ancestor established as an inline-size query container. If there is no eligible query container, cqi falls back to the small viewport's inline size. A px length represents CSS pixels rather than a percentage of a font size, viewport, or container, though browser zoom still scales the rendered page.

The same ownership rule applies to spacing, sizing, and responsive behavior. A continuous sizing rule belongs to the element it sizes. The element responsible for an arrangement should also define its breakpoint. The page owns breakpoints between page regions, while a component owns breakpoints within its own layout.

Composition Patterns Give Recurring Relationships a Name

A name gives a team a shared term for a recurring layout pattern. Teams can implement that pattern as a reusable primitive.

A layout primitive is a reusable implementation of a recurring spatial relationship without product meaning. Andy Bell and Heydon Pickering's Every Layout collects a well-known set of these, each named for the relationship it preserves. A Stack places children one after another along the block axis with a controlled gap, and a Cluster arranges children along the inline axis and lets them wrap. Sidebar, Switcher, and Center preserve three other useful relationships.

  • Sidebar pairs a fixed-width region with a flexible region. They share a row until the flexible region becomes narrower than a set threshold. When that happens, both regions stack at full width.
  • Switcher gives any number of children equal widths in a row, unlike Sidebar's asymmetric split. When the container is too narrow for those widths, all of the children stack.
  • Center sets a maximum width and uses automatic side margins to center the block. It switches to content-box sizing so side padding does not reduce that width.

Other primitives cover different layout relationships. Cover centers a piece of content vertically within a minimum-height container while pinning header and footer content to the top and bottom, which suits a full-height hero section. For a responsive multi-column layout, Grid adds or removes columns as space changes without an explicit breakpoint. Reel keeps its children in a single horizontally scrolling row instead of wrapping them. Imposter uses absolute positioning and the containing-block mechanism covered earlier to center an element over its nearest positioned ancestor.

These patterns do not replace the earlier ownership rule. Their names help a team recognize recurring relationships and reuse the same declarations instead of rebuilding them.

Where Layout Rules Belong

A layout rule should stay with the element that owns the relationship and become shared code only when that relationship recurs.

The catalog controls the grid and gaps between cards, while each card controls the arrangement and padding inside its border. The catalog should not position a card's product name, and the card should not add an outer margin that assumes which siblings surround it.

A primitive may be implemented as a CSS class or another small abstraction. It should contain only the declarations for its recurring layout behavior. The surrounding markup still determines which elements participate and what those elements mean. A Stack may control direction and gap, but it should not assume that its first child is a product name or that its last child is a purchase action.

A relationship that appears once can remain a local CSS rule. A shared rule becomes useful when the same Stack, Cluster, grid, or spacing relationship recurs and should change consistently. Design Systems explains how organizations package those rules alongside tokens and component libraries.

Each parent determines how its children share the available space, while the children's content affects their sizes. A recurring relationship may justify a shared abstraction. A one-off arrangement should remain local.
