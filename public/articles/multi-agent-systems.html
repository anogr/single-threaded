Multi-Agent Systems

What a second agent adds, the patterns that coordinate agent teams, and why the failures look like distributed systems.

Andreas Ögren
~11 min read
Last updated July 2026

Every agent in this series so far works alone. One agent holds one context window, and it does one thing at a time. Those two limits define a ceiling. A task too large to fit one window, or too slow to run serially, does not get easier with better prompting.

There are two ways past the ceiling. The first is a bigger window, and the LLM article covers why that route thins out well before it solves the problem. The second is more agents, and it is this article's subject. Adding agents buys capacity and parallelism, and it pays for them in the currency every distributed system pays. Coordination becomes part of the work, and eventually most of it.

Building on earlier articles

This article assumes the assistant/agent distinction from the assistants article and the context-window mechanics from how large language models work. The single-tool subagent covered earlier is the smallest version of what this article generalizes.

Why Multiple Agents

What a second agent adds is a second context window. Everything else follows from that.

The intuition to discard first is that several agents form a smarter collective. What splitting the work buys, mechanically, is independent context windows. Each agent reasons in its own window, uncluttered by the others' reading, tool output, and dead ends. Total working context stops being capped by any single request. That fact, more than any notion of collective intelligence, is what every pattern in this article exploits.

Splitting pays off under three conditions, and reliably only under them. The first is specialization. An agent with a narrow objective and a clean window outperforms a generalist working in a crowded one. The second is parallelism. Sub-tasks that do not depend on each other can run at the same time, which shortens wall-clock time even as total compute rises. The third is critique. A reviewer agent whose context holds none of the author's reasoning catches what self-review misses, for the same reason a fresh human reviewer does.

Underneath specialization sits an older idea, bounded responsibility. A worker with a small, clearly stated objective has a small prompt surface, an output that can be judged against the objective, and a role that can be rewritten or reassigned without touching the rest of the system. The architecture articles on this site make the same case for single responsibility in code and for team-sized ownership of frontends. Agents behave better under bounded responsibility for the same reasons modules and teams do.

The price arrives in three dimensions, and the failure modes later in the article map onto the same three. Compute multiplies, since every handoff repeats context and every aggregation re-reads results. Anthropic's engineering account of its own orchestrated research system, the best-documented production example, reports token consumption around an order of magnitude beyond an ordinary chat interaction. Latency stacks, because handoffs and aggregation are serial steps wrapped around the parallel work. Reliability drops, because each added agent, handoff, and merge is one more part that can fail.

Orchestrator and Workers

One agent plans, the others execute, and the planning is the hard part.

The pattern most production systems converge on has one coordinating agent, the orchestrator, and a set of workers it creates per task. The orchestrator's job runs in a sequence that looks the same across frameworks:

  1. Decompose the task into pieces that are independent, evaluable, and together sufficient.
  2. Assign each piece to a worker as a narrow, self-contained objective.
  3. Isolate each worker in its own clean context window.
  4. Aggregate the results as they return.
  5. Re-plan when a result changes the picture, spawning or redirecting workers.

Decomposition is where quality is won or lost. Cutting a task into truly independent, checkable pieces is the same skill as decomposing any system, and a bad cut cannot be rescued downstream. Workers handed overlapping pieces duplicate effort or contradict each other. Workers handed a piece with a hidden dependency stall or guess. Spawning a worker takes a fraction of a second. Deciding what the worker should do is the engineering, which is why the human gate, when there is one, belongs at this step.

Aggregation is where the independent-windows insight becomes visible in the data flow. Workers report results, never transcripts. A worker may read fifty files and reason at length, and what returns to the orchestrator is a summary sized for the orchestrator's budget. The coordinating window holds the plan and the findings, not the full working state of every agent. Anthropic's research system follows this shape, a lead agent decomposing a question and merging what parallel searchers bring back, and its published gains came specifically from spreading reasoning across separate windows.

Pipelines, Swarms, and Debates

The alternatives earn a paragraph each, and a reason to pick them.

A pipeline chains agents so that each one's output is the next one's input, a drafting agent feeding an editing agent feeding a fact-checking agent. It fits work that is naturally staged, where each stage transforms the whole artifact. Its weakness is that stages run serially, so latency adds up, and a defect introduced early flows through everything downstream.

A swarm drops the coordinator. Peer agents pull work from a shared queue and handle items independently. The shape fits high volumes of homogeneous, separable items, such as triaging a backlog or processing documents. Without a coordinator there is no single place where a plan lives or a mistake gets caught, so the shape suits work where any single item is cheap to redo.

A debate sets agents to argue opposing positions, with a judge, often a human, deciding. It is the critique condition from earlier run in both directions, and it can raise quality on judgment-heavy questions at a steep multiple of the token cost. As a standing pattern it is rarer than the other two, and closer to a deliberate quality gate than a way of producing work.

Orchestrator-worker remains the reference point, and most production systems either are one or contain one. The alternatives are worth reaching for when the work visibly has their shape, staged transformation, an embarrassingly parallel queue, or a decision worth the cost of structured disagreement.

Workspace Isolation

Two writers, one file, no lock. The oldest concurrency bug applies to agents too.

Independent context windows do not imply independent workspaces. Two agents editing one repository checkout collide the way two processes writing one file always have. One agent's half-finished refactor becomes another's confusing input. A test run picks up a mixture of both agents' changes and fails in ways neither can explain. The failure is worse than it was for processes, because an agent does not crash on inconsistent state. It reads the wreckage as context and carries on, confidently.

Git worktrees are the lightweight answer, giving each agent a separate working copy backed by the same repository, with results merged deliberately afterward. Containers and sandboxes are the heavier answer, isolating processes, dependencies, and network access along with the files. The harness tools named in the workflows article, Claude Squad at the light end and Gas Town at the heavy end, are to a large extent machinery for this, keeping parallel sessions from touching each other's state.

Isolation solved creates the next problem. Agents that cannot touch each other's state still need to hand work to each other.

Agent-to-Agent Communication

Inside one product, a handoff is an implementation detail. Across products, it needs a protocol.

Within a single framework, communication is internal plumbing. The orchestrator invokes its workers the way a program calls functions, and no standard is needed. The problem changes when the agents belong to different vendors. A company's procurement agent delegating to a supplier's support agent shares no runtime with it, and every pair of products wiring up a bespoke integration recreates the N×M problem that MCP solved for tools, one level up.

Agent2Agent (A2A) is the protocol emerging to fill that slot. An agent publishes an agent card, a machine-readable description of what it can do and where to reach it. Another agent discovers the card, delegates a task, and receives results, with the protocol handling the exchange in between. The division of labor between the two protocols is clean and worth memorizing. MCP connects an agent to tools and data. A2A connects agents to each other.

Where A2A stands

A2A reached version 1.0 under the Linux Foundation in 2026, with over 150 backing organizations and support landing across the major cloud platforms. That is real momentum, and it is still young next to MCP, which has years of deployment and tooling behind it. Treat A2A as the emerging standard for agent interoperability rather than a settled one, and check current client and platform support before designing around it.

Failure Modes

Every classic distributed-systems failure has an agent-shaped version, and one is new.

Coordination fails first. A handoff is a summary, and a summary is lossy. The detail a worker judged irrelevant and dropped is sometimes the detail the next agent needed, and no error is raised when it vanishes. The tighter the coupling between sub-tasks, the more each handoff loses, which is the mechanical reason decomposition quality dominates everything downstream.

State consistency fails quietly. Two agents acting on different pictures of the world, one having read the repository before the other's merge landed, produce work that is individually correct and jointly wrong. Practitioner post-mortems repeatedly name context inconsistency, rather than the choice of pattern, as the leading cause of production failures. It is the other face of the isolation the whole approach depends on. Independent windows mean independent views, and independent views drift. The same mismatch between plan and reality appears in single-agent form as context blindness, and the grounding step described there applies here per agent.

Errors cascade. A wrong intermediate result does not sit inert, it gets built upon, and by the time the flaw surfaces in the final output several agents have compounded it. Checks belong at the seams, validating a worker's result before the orchestrator builds on it, because the final artifact no longer reveals where things went wrong.

Which is the observability failure in miniature. A five-agent run cannot be debugged from its final answer. Without a record of which agent did what, with which input, and what came back, there is nothing to inspect, and the trail has to be designed in rather than reconstructed later. The shape is the one the MCP gateway section describes for tool calls, applied to every handoff.

Cost fails loudest and last. Orchestration calls stack on top of every worker call, so spend grows faster than agent count, and a workflow that looked cheap in a pilot behaves differently multiplied across a team's daily volume. The three dimensions from the start of this article, compute, latency, and reliability, are the budget lines to watch, and none of them improves with scale.

One documented anti-fit deserves its own mention. Tightly interdependent work, where each step needs the full nuance of the step before it, loses more through lossy handoffs than it gains from parallelism. Much of coding has that character, and Anthropic's account draws the same line, strong results on parallelizable research, weaker fit for interdependent implementation work. The multi-agent coding setups that do work concentrate on the separable parts, such as parallel exploration, isolated subtasks, and review passes, rather than splitting one feature across five authors.

When to Reach for It

One agent, engineered well, is the default. The escalation has a checklist.

The default remains a single agent with disciplined context engineering, because every cost in the previous section arrives the moment there is a second node. Escalate when the task decomposes into independent parts and at least one of the three conditions from the start of this article holds. A specialist would beat the generalist, the parts can run in parallel, or an independent critic would catch what self-review misses. If none of them holds, a second agent adds coordination cost and nothing else.

Where a team does escalate, the human gate from the workflows article moves to the decomposition step. A flawed plan costs minutes to correct before any worker runs, and multiplies across every worker after. Reviewing five workers' output without having reviewed the plan that produced it is diff review at its most expensive.

The discipline for running all of this already exists, because the thing being run is older than it looks. A multi-agent system is not a smarter language model, but a distributed system whose nodes happen to be language models. It rewards the instincts distributed systems have always rewarded, such as explicit contracts between parts, isolation by default, checks at the seams, and a record of what happened. Teams that bring those instincts keep the capacity and the parallelism. Teams that skip them rediscover, at token prices, why the instincts exist.
