Multi-Agent Systems

How separate agents divide work, exchange results, and introduce the coordination problems of a distributed system.

Andreas Ögren
~11 min read
Last updated July 2026

A single agent works through one primary task thread and a sequence of model requests. For each request, its harness assembles instructions, selected history, and tool results within the model's context window. The harness may run tool calls concurrently, but their results return to the primary task thread. Some tasks benefit from separate workers that can reason and execute independently.

A multi-agent design gives each worker a separate task thread with its own selected history. Products may still let workers share a filesystem, credentials, or other execution state. Independent workers can run in parallel or focus on specialized work. The orchestrator must then duplicate shared instructions, coordinate shared state, and evaluate results passed across handoffs. A task benefits only when the independent work saves more time or improves quality enough to cover this coordination.

This coordination resembles a distributed system even when every worker runs on one machine. Work crosses a message boundary, delivery can be delayed or repeated, and each participant may observe a different version of shared state. Familiar controls such as version identifiers, idempotent operations, timeouts, and audit records apply because the failure shapes are similar.

Additional Workers

Each additional agent provides a separate task thread and execution path that the system must coordinate.

Multiple agents add working capacity by separating a task into bounded objectives. Each worker receives the context and tool output needed for its objective. The orchestrator sees the combined work only after workers return summaries and evidence.

A clean decomposition can be seen in a dependency audit. One worker can inspect application imports while another checks container images because neither result changes the other's evidence. Implementing a database schema and updating every caller is more coupled. The caller work depends on the exact schema produced by the first worker, so serial work or a shared contract may be safer than parallel edits.

Teams usually add workers for specialization, parallel execution, or independent critique. A specialist can receive a narrow objective and focused context. Independent subtasks can run concurrently when they do not depend on one another. A critic can review an artifact without sharing the full reasoning path of its author. Each use requires an assignment whose result can be evaluated on its own.

A specialist needs a responsibility narrow enough to exclude irrelevant context and define a useful output contract. Single-responsibility design and team-sized frontend ownership use similar boundaries to make work and failures easier to locate.

Each worker receives the shared instructions relevant to its assignment, and the orchestrator must process each returned result. These extra requests raise total token use. Parallel execution can shorten the worker phase. Decomposition and aggregation happen in sequence and limit the time saved. Each worker and handoff can time out, use stale state, or return an incomplete summary. Teams should compare these costs with a single-agent run.

Orchestrator and Workers

The orchestrator divides the task, assigns workers, and evaluates their results.

A common pattern has one coordinating agent, the orchestrator, and a set of workers assigned to parts of the task. The five steps below show how the orchestrator assigns and evaluates their work.

  1. Decompose the task into pieces that are independent, evaluable, and together sufficient.
  2. Assign each piece to a worker as a narrow, self-contained objective.
  3. Bound each worker's task context and give it only the tools and state it needs.
  4. Aggregate the results as they return.
  5. Re-plan when a result changes the picture, spawning or redirecting workers.

The orchestrator must divide the task into assignments that do not overlap or hide dependencies. Overlap wastes effort and can produce conflicting results. A hidden dependency forces a worker to wait or make an unsupported assumption. Each assignment needs a bounded objective, known inputs, and a result that can be checked before aggregation. Reviewing the decomposition early avoids reconciling several incompatible results later.

A worker should return its result with supporting evidence and known uncertainty. Returning the full transcript can consume much of the orchestrator's context and include details irrelevant to the decision. The orchestrator compares the result with the assignment before accepting it, requesting more work, or revising the plan. The output contract must therefore specify enough evidence for this check.

The orchestrator needs durable task state when work can outlive one process or network request. A task identifier ties retries and late results to the original assignment. State transitions can distinguish queued work from active, completed, failed, or cancelled work. The orchestrator should accept a result only from the expected assignment version so an older worker cannot overwrite a newer decision.

Retries are safe only when the assigned operation is idempotent or carries a deduplication key. Repeating a read-only analysis wastes resources but usually preserves state. Repeating a request to publish a release or issue a refund can perform the external action twice. The worker contract has to say whether an operation can be retried and how the receiving system recognizes a duplicate.

Pipelines, Shared Queues, and Debates

The dependencies between tasks determine how agents should exchange work.

A pipeline chains agents so each output becomes the next input. A drafting agent may feed an editing agent, whose output then goes to a fact-checking agent. Tasks where each stage transforms the whole artifact can use this topology. The stages run serially, so their latency accumulates. Later stages may build on a defect introduced near the start.

A shared-queue topology lets peer workers claim items and handle them independently. Some products call this topology a swarm, although the label refers to several coordination models. A shared queue can distribute a high volume of similar, independent items such as backlog tickets or documents. Global planning and cross-item consistency need a separate owner because no worker sees the whole queue by default.

A debate asks agents to develop competing positions for a judge to compare. Competing analyses can expose assumptions in judgment-heavy work. Agreement provides no independent proof, and disagreement gives the judge more claims to evaluate. Because debate requires several extra model calls, it is most useful for selected decisions where competing analyses improve the review.

An orchestrator-worker topology can change the decomposition as results arrive. A pipeline processes ordered stages, and a shared queue distributes many independent items. Debate adds competing analyses for selected decisions. The task's dependencies should determine which topology is used.

Workspace Isolation

Agents that edit one checkout concurrently encounter the shared-state conflicts faced by any parallel writers.

Separate task threads do not separate files. Two agents editing one checkout can overwrite one another, read half-finished changes, or run tests against a mixture of both branches. The model may then interpret inconsistent state as valid evidence and continue. Parallel writers therefore need isolated workspaces and an explicit merge step.

Git worktrees give each agent a separate working tree while sharing the repository's object store. Containers or sandboxes can isolate the process and its dependencies from the host. They can restrict access to credentials and the network as well. The harness should choose the boundary from the risk of the tools involved, then merge results through the checks used for concurrent human work.

Separate working trees prevent direct interference while the agents edit. Conflicts can still appear when branches are merged, and workers may share remote services, credentials, or generated outputs outside those trees. Results therefore need an explicit handoff and the established integration checks used for concurrent human work.

A worktree isolates repository files. Package caches, local databases, ports, and cloud accounts sit outside that boundary. Containers can separate more process state, yet two containers may still call a shared test tenant. Isolation design begins by listing every writable resource, then deciding which resources can be shared safely and which need a per-worker namespace.

Agent-to-Agent Communication

A product can use private APIs for internal delegation. Delegation between products needs a shared protocol.

Within one framework, the orchestrator can invoke workers through private APIs. Products from different vendors do not share a runtime, so each pair would otherwise need a separate integration. Pair-specific integrations create the N×M problem that MCP addresses for tools, now at the agent boundary.

Agent2Agent (A2A) is an open protocol for that cross-system boundary. An agent can publish an agent card describing its interfaces and capabilities. Another system uses the card to choose an interface and send a message. The remote agent may answer with a message when it can respond immediately or create a stateful task for longer work. Tasks can exchange later messages and produce artifacts while reporting their status. In broad terms, MCP exposes tools and context to a host, while A2A coordinates work between independently operated agents.

An agent card advertises capability. It does not prove that the remote agent is trustworthy, authorized for a task, or accurate. Deployments still need authenticated transport, authorization for the requested work, and a policy for accepting artifacts from another organization. A remote result should enter the orchestrator as untrusted evidence until its provenance and content have been checked.

A2A governance

Google donated A2A to the Linux Foundation in 2025, where it is developed as a vendor-neutral project. Implementations and protocol versions continue to evolve. Teams should test interoperability with the specific products and versions they plan to use.

Failure Modes

Every handoff can omit information, use stale state, or pass an incorrect result to later workers.

A handoff usually summarizes the worker's context. The worker may omit a detail that the next agent needs, and the system raises no error for missing context. Tightly coupled subtasks depend on more shared detail, so they are more likely to fail across a summary boundary.

State consistency can fail without an obvious error. Two agents may act on different repository revisions or snapshots of an external system, producing results that are correct in isolation and incompatible together. Their task histories then describe different states unless the system records versions and revalidates assumptions. The grounding step used for one agent applies before each worker starts and again before its result is merged.

An incorrect intermediate result can be used as input by several later agents before the flaw appears in the final output. Checks therefore belong at the handoff boundaries, where the orchestrator can validate a worker's result before building on it. The final artifact may no longer reveal where the error began.

Timeouts create an ambiguous state when the orchestrator does not know whether the worker failed or merely replied late. Cancelling locally may not stop an external action already in progress. A worker protocol should expose cancellation when possible and let the orchestrator query task status before retrying. Late results need a rule as well, since accepting one after replacement work has started can reintroduce stale state.

Observability must cover every handoff because the final answer cannot show where an earlier error began. Debugging a five-agent run requires the assignment and input given to each agent and the result it returned. The system must record this trail during the run. The MCP gateway section describes a similar audit record for tool calls.

A small pilot may hide the full operating cost. Orchestration calls add to worker calls, every worker receives shared context, and retries repeat both kinds of work. Teams should compare total tokens and elapsed time with the single-agent path. Completion rate and the amount of human correction show whether the additional work improved the result.

Tightly interdependent work passes many details from one step to the next and is therefore a poor fit for separate task threads. Coding tasks often mix independent and coupled work. Exploration or independent review may separate cleanly. Several workers editing one tightly coupled feature may spend more time reconciling assumptions than parallel execution saves.

Choosing Multiple Agents

A multi-agent design should begin with one well-controlled agent and add workers for a specific need.

A single agent with disciplined context engineering avoids handoff and coordination costs. Add a worker when a specialist can handle one bounded responsibility better, independent work can finish sooner in parallel, or a separate critic provides a valuable independent check. The task must separate cleanly enough for the worker's result to be evaluated on its own.

Before workers start, a person should review the decomposition as described by the human gate in the workflows article. Correcting an overlapping assignment or hidden dependency takes little time at this point. After five workers have followed the flawed plan, reviewers must reconcile every result built on it.

A multi-agent system is a distributed workflow that needs explicit assignments and handoff contracts. Versioned state and isolated workspaces keep workers consistent, while timeouts and safe retries limit failures. Audit records let operators inspect each run. Independent work or critique must improve the result enough to justify this coordination. Other tasks are simpler with one well-controlled agent.
