Multi-Agent Systems

How separate agents divide work, exchange results, and introduce the coordination problems of a distributed system.

Andreas Ögren
~9 min read
Last updated July 2026

The agents described so far work through one primary context window and one sequence of decisions. That arrangement becomes limiting when a task contains independent work that could run in parallel or when exploration would crowd the main context with unrelated detail. Better prompting cannot create another workspace or make two tool calls finish at the same time.

Multiple agents offer another option by giving separate workers their own context and execution paths. That can add parallelism and keep specialized work isolated. It also adds handoffs, duplicated context, state coordination, and new failure modes. The architecture is useful only when those costs are smaller than the bottleneck it removes.

Building on earlier articles

This article assumes the assistant/agent distinction from the assistants article and the context-window mechanics from how large language models work. The single-tool subagent covered earlier is the smallest version of what this article generalizes.

Why Multiple Agents

What a second agent adds is a second context window. Everything else follows from that.

Several agents do not automatically form a smarter collective. Their concrete advantage is separation. Each worker can hold a narrow objective, its own context, and the tool output relevant to that objective. The system gains aggregate working capacity, although no individual agent can see all of it unless results are summarized and handed back.

Splitting work can help in three distinct ways. A specialist receives a smaller objective and only the material needed for it. Independent subtasks can run concurrently, reducing elapsed time while increasing total compute. A separate critic can approach an artifact without inheriting every assumption from the authoring path. Each benefit depends on a boundary that can be described and evaluated clearly.

Specialization rests on bounded responsibility. A worker with a narrow objective receives less irrelevant context, and its output can be judged against a clearer contract. The same principle appears in single-responsibility design and team-sized frontend ownership: boundaries make both work and failure easier to locate.

The costs appear in compute, latency, and reliability. Workers repeat shared instructions and the orchestrator must read their results, so total token use rises. Parallel work can shorten one phase, but decomposition and aggregation remain serial. Every worker and handoff also creates another place for timeouts, stale state, or a misleading summary. These costs should be measured against a single-agent baseline.

Orchestrator and Workers

One agent plans, the others execute, and the planning is the hard part.

The pattern most production systems converge on has one coordinating agent, the orchestrator, and a set of workers it creates per task. The orchestrator's job runs in a sequence that looks the same across frameworks:

  1. Decompose the task into pieces that are independent, evaluable, and together sufficient.
  2. Assign each piece to a worker as a narrow, self-contained objective.
  3. Isolate each worker in its own clean context window.
  4. Aggregate the results as they return.
  5. Re-plan when a result changes the picture, spawning or redirecting workers.

Decomposition determines whether the pattern works. Overlapping assignments waste effort and can produce conflicting results. Hidden dependencies force a worker either to wait or to guess. Each assignment therefore needs a bounded objective, the inputs it may rely on, and a result that can be checked before aggregation. Reviewing this plan is usually cheaper than reconciling several workers built on a poor split.

Aggregation keeps those independent contexts from flooding the coordinator. A worker should return a result, supporting evidence, and any uncertainty rather than its full transcript. The orchestrator can then compare the output with the assignment and decide whether to accept it, request more work, or revise the plan. A summary that omits evidence saves tokens but makes verification harder, so the output contract matters as much as the task description.

Pipelines, Swarms, and Debates

Different dependency shapes call for different coordination patterns.

A pipeline chains agents so that each one's output is the next one's input, a drafting agent feeding an editing agent feeding a fact-checking agent. It fits work that is naturally staged, where each stage transforms the whole artifact. Its weakness is that stages run serially, so latency adds up, and a defect introduced early flows through everything downstream.

A swarm drops the coordinator. Peer agents pull work from a shared queue and handle items independently. The shape fits high volumes of homogeneous, separable items, such as triaging a backlog or processing documents. Without a coordinator there is no single place where a plan lives or a mistake gets caught, so the shape suits work where any single item is cheap to redo.

A debate asks agents to develop competing positions for a judge to compare. It can expose assumptions in judgment-heavy work, but agreement between agents is not proof and disagreement does not identify the truth. The pattern is best treated as an expensive quality gate for selected decisions rather than a default production workflow.

Orchestrator-worker is the general pattern when the task must be decomposed dynamically. A pipeline suits ordered transformation, while a shared queue suits many independent items. Debate is useful only when competing analyses add enough value to justify the extra calls. Choosing from the dependency structure is more reliable than beginning with a preferred topology.

Workspace Isolation

Two writers, one file, no lock. The oldest concurrency bug applies to agents too.

Separate context windows do not separate files. Two agents editing the same checkout can overwrite one another, read half-finished changes, or run tests against a mixture of both branches. The model may then interpret inconsistent state as valid evidence and continue. Parallel writers therefore need isolated workspaces and an explicit merge step.

Git worktrees give each agent a separate working tree while sharing the repository's object store. Containers or sandboxes can also isolate processes, dependencies, credentials, and network access. The harness should choose the boundary from the risk of the tools involved, then merge results through the same checks used for concurrent human work.

Isolation solved creates the next problem. Agents that cannot touch each other's state still need to hand work to each other.

Agent-to-Agent Communication

Inside one product, a handoff is an implementation detail. Across products, it needs a protocol.

Within one framework, the orchestrator can invoke workers through private APIs. Cross-vendor delegation has no shared runtime, so each product pair otherwise needs a bespoke integration. That recreates the N×M problem that MCP addresses for tools, but at the agent boundary.

Agent2Agent (A2A) is an open protocol for that cross-system boundary. An agent can publish an agent card describing its endpoint and capabilities. Another system can then discover the card, create a task, exchange messages or artifacts, and receive status updates. In broad terms, MCP exposes tools and context to a host, while A2A coordinates tasks between independently operated agents.

Where A2A stands

Google donated A2A to the Linux Foundation in 2025, where it is developed as a vendor-neutral project. Implementations and protocol versions continue to evolve, so interoperability should be tested with the specific products involved rather than inferred from a shared label.

Failure Modes

Lossy handoffs, stale state, cascading errors, and weak observability all become harder to diagnose once several agents participate.

Coordination fails first. A handoff is a summary, and a summary is lossy. The detail a worker judged irrelevant and dropped is sometimes the detail the next agent needed, and no error is raised when it vanishes. The tighter the coupling between sub-tasks, the more each handoff loses, which is the mechanical reason decomposition quality dominates everything downstream.

State consistency can fail quietly. Two agents may act on different repository revisions or different snapshots of an external system, producing results that are correct in isolation and incompatible together. Independent windows create independent views, and those views drift unless the system records versions and revalidates assumptions. The grounding step used for one agent applies before each worker starts and again before its result is merged.

Errors cascade. A wrong intermediate result does not sit inert, it gets built upon, and by the time the flaw surfaces in the final output several agents have compounded it. Checks belong at the seams, validating a worker's result before the orchestrator builds on it, because the final artifact no longer reveals where things went wrong.

Which is the observability failure in miniature. A five-agent run cannot be debugged from its final answer. Without a record of which agent did what, with which input, and what came back, there is nothing to inspect, and the trail has to be designed in rather than reconstructed later. The shape is the one the MCP gateway section describes for tool calls, applied to every handoff.

Cost is easier to see after deployment than during a small pilot. Orchestration calls add to worker calls, shared context is repeated, and retries multiply both. Measure total tokens, elapsed time, completion rate, and human correction against the single-agent path. More agents are worthwhile only when they improve the outcome that matters after all four costs are counted.

One documented anti-fit deserves its own mention. Tightly interdependent work, where each step needs the full nuance of the step before it, loses more through lossy handoffs than it gains from parallelism. Much of coding has that character, and Anthropic's account draws the same line, strong results on parallelizable research, weaker fit for interdependent implementation work. The multi-agent coding setups that do work concentrate on the separable parts, such as parallel exploration, isolated subtasks, and review passes, rather than splitting one feature across five authors.

When to Reach for It

One agent, engineered well, is the default. The escalation has a checklist.

The default remains a single agent with disciplined context engineering, because every cost in the previous section arrives the moment there is a second node. Escalate when the task decomposes into independent parts and at least one of the three conditions from the start of this article holds. A specialist would beat the generalist, the parts can run in parallel, or an independent critic would catch what self-review misses. If none of them holds, a second agent adds coordination cost and nothing else.

Where a team does escalate, the human gate from the workflows article moves to the decomposition step. A flawed plan costs minutes to correct before any worker runs, and multiplies across every worker after. Reviewing five workers' output without having reviewed the plan that produced it is diff review at its most expensive.

A multi-agent system is best treated as a distributed workflow whose nodes happen to use language models. Explicit contracts, versioned state, isolation, timeouts, idempotency, checks at handoffs, and an audit trail all matter. Add the second agent when independent work or critique earns back that machinery. Until then, one well-controlled agent remains the simpler and usually more reliable design.
