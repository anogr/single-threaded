Accessibility and Rendering Architecture

How routing, streaming, and hydration choices quietly remove behavior browsers provide for free, and what it takes to rebuild it.

Andreas Ögren
~13 min read
Last updated July 2026

Every rendering strategy covered in this site's rendering strategies article trades away something. Most of those tradeoffs are about speed. One of them is about accessibility, and it's rarely named as a tradeoff at all.

A traditional multi-page app (MPA) gives a specific accessibility contract for free, without anyone on the team writing a line of code for it. Every navigation is a full page load: the browser throws away the old document, requests a new one, and starts over. That reset means focus returns to the top of the document, the page title updates, and a screen reader announces the arrival of a new page automatically. From the browser's perspective, a new page is exactly what happened. None of this is a feature a team built. It's a side effect of how document navigation has always worked.

Client-side routing, the mechanism behind every single-page app (SPA) and behind most metaframework apps once their first load has finished, breaks that contract silently. The URL changes, the DOM gets patched with new content, but nothing about a JavaScript-driven route change resembles a real navigation from the browser's point of view. Focus stays wherever it already was, usually on the link that triggered the change. The document title doesn't update unless something explicitly sets it. No announcement happens, because nothing that would normally trigger one occurred. A sighted mouse user sees the new content and moves on without noticing anything unusual. A keyboard or screen reader user gets no signal at all that a navigation happened.

Every strategy covered in this article follows the same shape. A rendering or hydration decision buys something real, such as faster subsequent navigations, a page that streams instead of blocking, or a component that ships without its own JavaScript. In exchange it quietly removes a piece of behavior the platform used to provide automatically. None of that is a reason to avoid the technique. It's a reason to know exactly which piece of behavior disappeared, so a team can decide to rebuild it on purpose rather than finding out about the gap from a user.

Client-Side Routing Breaks Focus

Restoring what the browser no longer does on navigation is the routing layer's job, whether the router ships it or the team builds it.

The fix is well established and doesn't require much code, only the discipline to apply it on every route change:

  • Move focus to a sensible landing point, usually the page's own <h1>, made programmatically focusable with tabindex="-1" since headings aren't focusable by default.
  • Update document.title to match the new page.
  • Announce the change through an aria-live="polite" region, which lets a screen reader report the update without requiring focus to physically land inside the region for the announcement to fire.

The three pieces work together. Focus gives a keyboard user a sensible place to start reading and interacting, and the live region gives a screen reader user the announcement an MPA would have produced automatically. The title update keeps browser history and screen reader page-summary features accurate on top of that.

This is a real evaluation criterion when choosing or building a router. Coverage varies by framework and by version, so check directly against whichever router a project is evaluating rather than assuming. Some routers ship this behavior close to automatically, restoring scroll position and moving focus to a sensible default on route change. Others leave it entirely to application code, treating focus and announcement as a concern for whoever builds each page rather than something the router itself owns. Knowing which camp a router falls into before committing to it saves a retrofit later. Accessibility as an Architecture Decision discusses these kinds of gaps that cost a line of code early and a migration project once a hundred routes have shipped without it.

Streaming SSR and Server Components

A newer, narrower version of the same underlying problem shows up wherever content resolves out of document order.

Streaming server-side rendering and React Server Components send a page's markup to the browser in pieces rather than all at once. Independent Suspense boundaries resolve whenever their data happens to be ready, not in the order they appear on the page, a mechanism covered in depth in the React Server Components article's section on Suspense and arrival order. That's what makes streaming fast: a slow, personalized section of a page doesn't hold up the fast, static parts around it. It's also the source of a specific accessibility risk. A screen reader can announce newly streamed content in the order it arrives rather than the order it reads in the document, so a boundary that resolves last can get announced after content that logically follows it. Focus can be lost the same way. If it was set on an element inside a boundary still showing its loading fallback, that element disappears the moment the boundary resolves, and focus silently lands nowhere. The user is left with no clear sense of where they are on the page.

Neither failure is unique to React Server Components. Both apply to any streaming SSR implementation, since the underlying mechanism, independently resolving chunks sent as they finish, is the same regardless of framework. What's specific to Server Components is that the pattern encourages wrapping more of a page in independent boundaries than teams typically used with plain streaming SSR. That increases how often a boundary sits near something interactive enough to matter. The practical guidance isn't to avoid streaming. Any boundary near a focusable element, such as a button or a form field, needs a specific manual check. Focus the element, trigger the boundary's resolution, and confirm focus survives or is deliberately redirected somewhere sensible.

A "skip to main content" link, the common pattern that lets a keyboard user bypass repeated navigation and jump straight to a page's primary content, runs into a related version of the same timing question on a streamed page. If the skip link's target is itself inside a boundary that hasn't resolved yet, activating it lands focus on an empty placeholder rather than real content, and the user has to try again once the boundary finishes. It's a small case, but one that only shows up when someone tests the interaction on a slow or throttled connection rather than the fast local network a development environment usually runs on.

Islands, Resumability, and the Interactive Gap

Partial hydration solves a performance problem and introduces a narrower, timing-shaped accessibility one.

The hydration, islands, and resumability section of the rendering strategies article covers the performance case for partial hydration. A page ships as mostly static HTML, and only the components explicitly marked interactive load and run JavaScript, each hydrating independently instead of the whole page hydrating as one unit. The gap between a component's HTML painting on screen and its JavaScript finishing download and execution is sometimes called partial hydration's uncanny valley: the content is visibly present, but nothing about it responds yet. For a purely decorative island, such as a hero animation or a related-articles widget, that gap is invisible to everyone. For an island holding an interactive control, such as a quantity stepper or an add-to-cart button, that gap is not invisible. A keyboard user who tabs to it, or a screen reader user who activates it, gets no response and no explanation why during that window. The failure looks identical to a broken component, because from the user's side, it briefly is one.

Qwik's resumability, also covered in the rendering strategies article, sidesteps this specific gap rather than shrinking it. Because it serializes event listener references into the HTML at build time instead of shipping a component tree to re-execute, there's no hydration pass to wait for at all. The tradeoff is adopting a different framework with a different mental model rather than applying a drop-in optimization. Even so, it's a real point of comparison for pages where above-the-fold interactivity matters enough that even a brief unresponsive window is worth designing around.

The practical takeaway carries over from the streaming section. Islands and partial hydration remain a legitimate and often correct way to ship less JavaScript. What deserves deliberate design attention is the above-the-fold interactive islands, the ones most likely to get a keyboard or screen reader interaction in that narrow window. A visible loading or disabled state on an unhydrated interactive island, rather than a control that looks ready but silently does nothing, closes most of the practical gap even without eliminating the underlying timing window.

Live Regions Beyond Routing

Anything that changes content without a navigation, not just a route change, needs the same announcement treatment.

A toast notification, an inline validation error appearing under a form field, and an optimistic update from a Server Action all change what's on screen without anything resembling a navigation. All of them need an aria-live region to be announced to a screen reader the same way a route change does. The choice between aria-live="polite" and aria-live="assertive" should be made deliberately rather than defaulting to whichever one shows up first in a tutorial. Polite waits for a natural pause before announcing, which fits most route changes and status updates. Assertive interrupts whatever the screen reader is currently saying, useful for time-sensitive cases such as a session about to expire or a failed payment. Overusing it for routine updates trains users to tune out the interruption entirely.

The Server Action case has a specific wrinkle, covered from the state-management side in the React Server Components article. useOptimistic's rollback only happens automatically when an action throws. If an action instead follows the typed-result convention and returns something like { ok: false }, there's no thrown error for useOptimistic to react to, and the optimistic UI keeps showing its predicted state until something else updates it. When that reversal does eventually happen, it's a second content change with no navigation and no user-initiated trigger behind it. It needs its own announcement just as much as the original optimistic update did. A UI that silently reverts a predicted success into a failure, with no live region covering either transition, leaves a screen reader user believing an action succeeded when it didn't.

Baking It Into the Design System

Focus styles, contrast, and motion fallbacks are design-system decisions, which makes them the cheapest accessibility work in this article.

A focus-visible outline style, a minimum contrast ratio, and a motion-reduction fallback belong at the shared token layer of a design system, not re-solved inside each component. That's the same reason a correct native <button> belongs in a shared component library. Get it right once, and every consumer of the design system inherits it without having to think about it again. Get it wrong once, at the token layer, and every consumer inherits that too.

The cross-document View Transitions that give multi-page apps animated navigation without JavaScript are a concrete case where this matters. A page transition animation that ignores the prefers-reduced-motion media query is a real regression for users with vestibular disorders, for whom large-scale motion can trigger dizziness or nausea. The fix costs only a few lines of CSS: wrap the transition's animation rules in a media query that swaps them for an instant, non-animated cross-fade whenever the visitor has requested reduced motion. Done at the design-system level, once, it protects every page that opts into cross-document transitions automatically. Done per page, it's one more thing to remember and one more thing that eventually gets missed.

Two WCAG 2.2-specific success criteria land squarely on decisions a rendering architecture and its design system make together, rather than on individual page content. Focus not obscured requires that a focused element isn't hidden behind a sticky header, a fixed banner, or a cookie-consent bar. That's a real risk in any layout with persistent chrome, where a page can scroll a focused element toward it. Target size sets a minimum tappable area for interactive controls. That matters most for whichever component library renders every button and link across a product, since a token-level fix there reaches every consumer at once rather than needing to be patched control by control.

Testing This Category of Bug

Generic accessibility scanning is bad at catching any of the failures described in this article, because none of them are static markup problems.

An automated scanner like axe-core, discussed in more general terms in the foundations article's testing section, inspects a single rendered snapshot of a page. Every failure covered here (a route change that doesn't move focus, a Suspense boundary that steals it, an island that looks ready before it is) is timing-dependent and interaction-dependent rather than something visible in one static snapshot. A scan of the finished DOM after everything has settled can look completely clean while the transition getting there was inaccessible the entire time.

The workable approach is treating each distinct route-change and streaming scenario a rendering architecture introduces as its own scripted keyboard pass: trigger the navigation or the boundary resolution, then check where focus ended up and what, if anything, got announced. This is testing work that belongs to whoever owns the rendering architecture decision, not a separate accessibility-only pass bolted on afterward. The failure modes are specific to the rendering choices covered in this article, and they don't show up in a generic component-level accessibility audit at all.

Tooling can carry some of this load once the scenarios are named. A Playwright script can drive a route change, or wait for a specific Suspense boundary to resolve, then assert on document.activeElement and on the contents of a live region. That turns a manual keyboard check into a regression test that runs on every pull request. It doesn't replace a real screen reader pass entirely, because announcement behavior varies enough between NVDA, VoiceOver, and JAWS that an assertion on DOM state alone can miss real differences. But it cheaply and automatically catches the most common regression where focus silently landing on <body> after a navigation.

None of this is an argument against SPAs, streaming, or islands. Each strategy trades away a specific piece of behavior a plain MPA gave for free. Naming which piece (focus reset, announcement, or interactive readiness) is what lets a team rebuild it deliberately instead of discovering the gap from a support ticket.
