React Antipatterns

A field guide to the state, rendering, and data-fetching habits that look fine in one component and turn into architectural debt across a whole app.

Field guide
~17 min read
React
July 2026

How not to structure React components. Antipatterns are built from choices that compile without complaint, look correct inside the one file they're written in, and still turn into real cost once the app is bigger than a page or two. Every example below runs. The problem shows up one level up, in how many components re-render on a single state change, how many network requests fire before anything paints, and how much of the codebase has to understand one component's internal state to stay correct.

A prop-drilling shortcut or a fetch dropped into useEffect rarely fails code review, because reviewing one component at a time is exactly the vantage point that hides the cost. The cost only becomes visible at the level of the whole tree. A re-render that should have touched one badge touches the entire page. A detail view that should load in one round trip loads in four, one after another. Eight habits follow, grouped by what they actually break: who owns a piece of state, what effects are for, how data gets fetched, and how a component's size compounds over time.

Context as a global store

One provider holding everything isn't a shortcut around prop drilling. It's a subscription list every consumer joins whether it wants the next update or not.

Prop drilling gets tedious fast, and a single context that holds the current user, the theme, the shopping cart, and a notifications list looks like it solves that in one move. Every component below the provider can reach in and grab whatever it needs. No intermediate component has to forward a prop it doesn't use. It's the same shortcut Software Design Principles warns about from the code side, a shared abstraction pulled together because the pieces sat near each other, not because they were ever the same piece of knowledge. The problem is what a context actually is under the hood. It's one value, plus a list of every component that called useContext on it. React doesn't know which field inside that value a given consumer cares about. It only knows the value changed, so every subscriber re-renders, including the one that reads theme when what actually changed was cart.

app-context.tsx TSX 
type AppContextValue = {
  user: User | null;
  setUser: (user: User | null) => void;
  theme: string;
  setTheme: (theme: string) => void;
  cart: CartItem[];
  setCart: (cart: CartItem[]) => void;
};

const AppContext = createContext<AppContextValue | null>(null);

function AppProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [theme, setTheme] = useState('dark');
  const [cart, setCart] = useState<CartItem[]>([]);

  return (
    <AppContext value={{ user, setUser, theme, setTheme, cart, setCart }}>
      {children}
    </AppContext>
  );
}

ThemeToggle only ever reads theme. Avatar only ever reads user. Neither cares about cart, but both are subscribed to the same context object as CartBadge, so adding an item to the cart re-renders all three. On a small page that's invisible. On a real layout with a header, a sidebar, and a dozen widgets all reading from the same provider, one cart update walks the entire subscriber list every time. None of that work shows up as a bug. It shows up as the app feeling slower than its actual amount of changed state should explain.

What this costs

The re-render blast radius grows with how many things the context holds, not with how much actually changed. The fix that costs almost nothing is splitting state from the functions that change it, and splitting unrelated concerns into separate contexts entirely, covered in the context selectors section of the patterns article. Past a certain size, a store library with slice-level subscriptions, covered in the client state article, replaces context for shared state entirely rather than patching around its all-or-nothing re-render model.

Lifting state too early

Moving state up "in case a sibling needs it later" turns a local decision into an architectural one that every future contributor has to route around.

Lifting state to a shared ancestor is the correct move once two siblings genuinely need to read or change the same value. The mistake is doing it by default, keeping a piece of state at the top of whatever component contains the feature, even when nothing outside that feature ever reads it. A boolean for whether a confirmation modal is open doesn't need to live in the page component that also renders a product gallery and a details panel. It only needs to live next to the button that opens the modal and the modal itself, the two things that actually use it. Placed at the page level anyway, every open and close re-renders the page and everything else the page renders alongside the button. That's not because the architecture required it, but because the state was declared one level higher than the components that use it.

product-page.tsx TSX 
function ProductPage({ product }: { product: Product }) {
  const [isModalOpen, setIsModalOpen] = useState(false);

  return (
    <div>
      <ProductGallery images={product.images} />
      <ProductDetails product={product} />
      <button onClick={() => setIsModalOpen(true)}>Add to cart</button>
      {isModalOpen && <ConfirmationModal onClose={() => setIsModalOpen(false)} />}
    </div>
  );
}

ProductGallery and ProductDetails read nothing from isModalOpen, but both sit under ProductPage, so both re-render every time the modal opens or closes, an image carousel repainting for a state change that has nothing to do with it. Moving the state down into a component that owns just the button and the modal keeps that re-render contained to the one place it actually happens.

product-page.tsx TSX 
function AddToCartButton({ product }: { product: Product }) {
  const [isModalOpen, setIsModalOpen] = useState(false);

  return (
    <>
      <button onClick={() => setIsModalOpen(true)}>Add to cart</button>
      {isModalOpen && <ConfirmationModal onClose={() => setIsModalOpen(false)} />}
    </>
  );
}

function ProductPage({ product }: { product: Product }) {
  return (
    <div>
      <ProductGallery images={product.images} />
      <ProductDetails product={product} />
      <AddToCartButton product={product} />
    </div>
  );
}

Neither ProductGallery nor ProductDetails re-renders when the modal opens now, because ProductPage itself never re-renders for that state change. Only AddToCartButton does. The general rule holds up well in practice. State starts as low in the tree as it can, in the smallest component that owns both the state and the thing reading it. It moves up only when a second, currently existing consumer needs it, never in anticipation of one.

The same mistake, one level up

The identical trade-off shows up with global stores. Reaching for a shared store the moment two components need to agree on something is the store equivalent of lifting state to the nearest common ancestor. Reaching for it before that need exists, "so it's there when we need it," produces the same speculative coupling, just with a bigger blast radius once it happens.

Derived state stored as state

If a value's answer is always a formula of state you already have, storing it separately just gives the two copies room to drift.

A filtered list, a computed total, a boolean for whether a form is valid: none of these are facts about the world that need their own slot in state. Each is a pure function of state that already exists elsewhere in the component. Storing it separately, then using an effect to keep it in sync whenever the source state changes, is derived state treated as if it were independent state. It's one of the most common ways useEffect gets misused. The dependency array has to list every value the calculation touches, and forgetting one produces a component that renders a stale answer for exactly one render before the effect catches up.

product-list.tsx TSX 
// Antipattern: a second state slot, synced by an effect
function ProductList({ products, query }: { products: Product[]; query: string }) {
  const [filtered, setFiltered] = useState<Product[]>([]);

  useEffect(() => {
    setFiltered(products.filter((p) => p.name.includes(query)));
  }, [products, query]);

  return <List items={filtered} />;
}

This renders ProductList twice for every change to query. It renders once with the stale filtered from before the effect ran, then again once setFiltered lands. The fix removes the second state slot entirely and computes the value in the render body, where it can never be out of sync with products and query because it's calculated from them directly, every time.

product-list.tsx TSX 
function ProductList({ products, query }: { products: Product[]; query: string }) {
  const filtered = products.filter((p) => p.name.includes(query));
  return <List items={filtered} />;
}

No effect, no second render pass, and no dependency array to keep correct by hand. A filter over a short array is cheap enough that wrapping it in useMemo would cost more in dependency-comparison overhead than it saves. The React Compiler now handles memoization automatically for components it can statically analyze, so adding it by hand has become the exception rather than the default. Reaching for useMemo still earns its keep in a few cases. For example, a genuinely expensive computation, a value handed to a third-party library that compares by reference, or a value used as another effect's dependency are still valid cases.

Effects as event handlers

An effect that only ever fires in response to a click is a click handler wearing a disguise, and it inherits none of the click handler's guarantees about when it runs.

useEffect exists to synchronize a component with something outside React. For example, a subscription, a DOM measurement, or a connection that needs to open and close as the component mounts and unmounts. It isn't meant to react to a specific user action. A common way this gets confused in practice is a boolean flag set inside an onClick handler, watched by an effect that performs the actual work once the flag flips.

checkout-button.tsx TSX 
// Antipattern: a flag routes a click through an effect
function CheckoutButton({ cart }: { cart: CartItem[] }) {
  const [submitted, setSubmitted] = useState(false);

  useEffect(() => {
    if (submitted) {
      trackEvent('checkout_started', { cart });
      setSubmitted(false);
    }
  }, [submitted, cart]);

  return <button onClick={() => setSubmitted(true)}>Checkout</button>;
}

This adds a full render-and-effect round trip between the click and the tracking call. It also makes submitted a piece of state that exists purely to be reset a moment after it's set. Worse, it quietly re-fires if cart changes for any other reason while submitted happens to still be true. None of that machinery is needed. The click is already an event. Calling trackEvent directly inside the handler runs it exactly once, exactly when the user clicked, with no extra state and no dependency array to get wrong.

checkout-button.tsx TSX 
function CheckoutButton({ cart }: { cart: CartItem[] }) {
  function handleClick() {
    trackEvent('checkout_started', { cart });
  }

  return <button onClick={handleClick}>Checkout</button>;
}
A quick test for any effect

Ask what would happen if the effect's dependency array were deleted and it ran on every render instead. If the answer is "it would do the same user-triggered thing over and over for no reason," the logic belongs in a handler, not an effect. If the answer is "it would keep some external system correctly in sync," it's a legitimate effect.

Fetching inside component effects

A fetch dropped into useEffect looks like data loading. Structurally, it's a hidden dependency the component now owns end to end, race conditions, caching, and all.

Fetching a resource on mount is one of the oldest useEffect habits in React, and it's also the one with the most invisible failure modes. Done properly it needs an ignore flag or an abort controller to stop a slow, stale response from overwriting a newer one if the component's props change and re-trigger the effect before the first request finishes. Done without that guard, a component whose id prop changes quickly, a user clicking through a list of records, for instance, can render the response to an old request after a new one has already started.

user-profile.tsx TSX 
// Antipattern: fetch in an effect, race condition included for free
function UserProfile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then(setUser);
  }, [userId]);

  return user ? <Profile user={user} /> : <Spinner />;
}

Even fixed for that race, this version still fetches on every mount with no cache. Navigating away and back re-requests data the component already had, and two sibling components that both need the same user re-request it independently rather than sharing one in-flight request. None of that is specific to this component. It's exactly the job of a query layer, and by 2026 most apps don't hand-roll one. A hook from TanStack Query or SWR covers it for most apps. Where the framework supports it, fetching in a Server Component or a route loader that runs before the component tree renders works just as well, a pattern covered in the Server Components article.

user-profile.tsx TSX 
function UserProfile({ userId }: { userId: string }) {
  const { data: user, isLoading } = useQuery<User>({
    queryKey: ['user', userId],
    queryFn: () => fetch(`/api/users/${userId}`).then((res) => res.json()),
  });

  return isLoading ? <Spinner /> : <Profile user={user} />;
}

The race condition, the cache, and the request deduplication between two components asking for the same userId all come from the library rather than from hand-written effect code. None of it has to be re-verified per component. useEffect is still the right tool for the cases a query layer doesn't cover, such as subscribing to a WebSocket or a browser API. It's just not the right tool for the specific case of "load this data when the component appears."

Request waterfalls

A tree where every level fetches only after it mounts turns one page load into a relay race, each leg waiting on the one before it.

Fetching in effects has a second cost beyond the one above, and it shows up even after caching and race conditions are handled correctly. Picture a parent that fetches a user, waits for it to resolve, and only then renders a child that fetches the user's orders. That child in turn renders a grandchild that fetches order details. The three requests run one after another, even though only the second and third actually depend on data from the one before. This is a request waterfall, and it's a structural property of where the fetches sit in the tree, not something a faster network connection fixes.

The fix isn't a faster individual request. It's issuing the independent requests together instead of nesting them inside the components that need their results. When orders only needs a userId that's already known before the user record resolves, it can be requested in parallel with Promise.all. Or it can be hoisted to a route loader that starts every request the page needs before rendering any component that depends on the results. Only a request that genuinely can't start without a value from an earlier one, order detail needing an order ID that only exists inside the orders response, has to wait. Everything else waiting is a tree shape problem, not a data dependency.

God components

A component that grew a prop, a hook, and a conditional branch for every case it's ever had to handle is easier to spot from its import list than from its size.

A god component is one that has quietly absorbed data fetching, permission checks, layout, and several unrelated feature branches into a single file, usually a few additions at a time, none of which looked wrong in isolation. Nobody sets out to write one. It's what a Dashboard component becomes after eighteen months of "just add one more if" for a new plan tier, a new role, a new widget. The result is a file every reviewer is nervous to touch, because a change meant for one feature can silently affect three others sharing the same render function. It's also a file that's effectively impossible to unit test in isolation, because testing any one branch means standing up everything the whole component depends on.

Symptom
Blast radius grows with unrelated work

A change for one customer segment risks breaking a code path for a completely different one, because both live in the same function.

Symptom
Untestable without the whole tree

Exercising one branch means mocking every dependency the entire component uses, not just the ones that branch touches.

The way out is the same set of moves covered in the composition half of this series. Pull data fetching and business logic into a custom hook so the component's job shrinks to rendering. Split visually or behaviorally distinct sub-parts into their own components using the compound component pattern instead of a growing prop list. And treat a new conditional branch as a signal to ask whether this is really the same component anymore, or two components that have been sharing a file.

Cargo-cult memoization

Wrapping every value in useMemo and every function in useCallback used to be defensive. With the compiler doing that work now, it's mostly noise, and occasionally a bug.

For years, the safe habit on any team worried about performance was to memoize liberally. That meant wrapping expensive-looking calculations in useMemo, wrapping every function passed as a prop in useCallback, and treating both as a kind of insurance. The React Compiler, a build-time tool that statically analyzes component code and inserts the equivalent memoization automatically, changes the trade-off. On components it can fully analyze, it already does this work. Doing it by hand on top adds a dependency array to keep correct for no benefit, plus the small but real cost of comparing that array on every render.

Hand memoization can also actively mislead. A useCallback with a stale dependency array doesn't fail loudly. It just hands out an old closure that quietly reads outdated props or state, a bug that's harder to spot than the unnecessary re-render it was meant to prevent. In a codebase leaning on the compiler, treat both hooks as escape hatches, not defaults. Reach for them when integrating with a third-party library that compares props by reference instead of value, when a value feeds another effect's dependency array, or when a calculation is expensive enough that profiling confirms it matters. That holds regardless of the compiler. Profiling comes first, before reaching for either hook. Otherwise, you're just optimizing a number nobody measured.

Not every codebase has the compiler yet

Teams on an older React version, or one that hasn't adopted the compiler, still need manual memoization as the working default in hot paths. The direction of travel matters more than the exact cutover date. Treat new manual memoization as something to justify, not something to reach for automatically, and let the compiler take over incrementally as the codebase upgrades.

When antipatterns compound

Any one of the habits above is survivable alone. A single overly broad context costs a handful of unnecessary re-renders. A single derived-state effect costs one extra render pass. Production slowdowns that show up as "the app just feels slow," with no one obvious line of code to blame, are usually several of these stacked on top of each other. A cart update in a shared context re-renders a dozen consumers, each of which happens to compute a derived value in an effect, so each one renders twice. Two of those consumers each independently fetch the same resource in their own effect, because there's no shared cache between them. None of that shows up in a single profiler snapshot as one bug. It shows up as a page that takes a beat too long to feel responsive, for reasons that only become visible by tracing the whole path a state change takes through the tree.

Server Components and a proper query layer remove entire categories of this by construction. A component that never runs in the browser can't misuse an effect, and a cache-aware query hook can't create a waterfall between two siblings that ask for the same data. Neither removes the need to know who owns a given piece of state and why a specific component re-renders when it changes. That discipline is what every fix in this article actually comes down to, and it's the same discipline the patterns in the companion article are built on top of.
