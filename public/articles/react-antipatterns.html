React Antipatterns

A field guide to the state, rendering, and data-fetching habits that look fine in one component and turn into architectural debt across a whole app.

Field guide
~17 min read
React
July 2026

A companion article in this series covers six patterns for structuring React components. This one covers the opposite case. It's built from choices that compile without complaint, look correct inside the one file they're written in, and still turn into real cost once the app is bigger than a page or two. None of what follows is a syntax error. Every example below runs. The problem shows up one level up, in how many components re-render on a single state change, how many network requests fire before anything paints, and how much of the codebase has to understand one component's internal state to stay correct.

That's what makes these worth an architect's attention specifically. A prop-drilling shortcut or a fetch dropped into useEffect rarely fails code review, because reviewing one component at a time is exactly the vantage point that hides the cost. The cost only becomes visible at the level of the whole tree: a re-render that should have touched one badge touches the entire page, or a detail view that should load in one round trip loads in four, one after another. Eight habits follow, grouped by what they actually break: who owns a piece of state, what effects are for, how data gets fetched, and how a component's size compounds over time.

Context as a global store

One provider holding everything isn't a shortcut around prop drilling. It's a subscription list every consumer joins whether it wants the next update or not.

Prop drilling gets tedious fast, and a single context that holds the current user, the theme, the shopping cart, and a notifications list looks like it solves that in one move. Every component below the provider can reach in and grab whatever it needs, no intermediate component has to forward a prop it doesn't use. The problem is what a context actually is under the hood: one value, and a list of every component that called useContext on it. React doesn't know which field inside that value a given consumer cares about. It only knows the value changed, so every subscriber re-renders, including the one that reads theme when what actually changed was cart.

app-context.jsx JSX 
const AppContext = createContext(null);

function AppProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const [cart, setCart] = useState([]);

  return (
    <AppContext value={{ user, setUser, theme, setTheme, cart, setCart }}>
      {children}
    </AppContext>
  );
}

ThemeToggle only ever reads theme. Avatar only ever reads user. Neither cares about cart, but both are subscribed to the same context object as CartBadge, so adding an item to the cart re-renders all three. On a small page that's invisible. On a real layout with a header, a sidebar, and a dozen widgets all reading from the same provider, one cart update walks the entire subscriber list every time. None of that work shows up as a bug. It shows up as the app feeling slower than its actual amount of changed state should explain.

What this costs

The re-render blast radius grows with how many things the context holds, not with how much actually changed. The fix that costs almost nothing is splitting state from the functions that change it, and splitting unrelated concerns into separate contexts entirely, covered in the context selectors section of the patterns article. Past a certain size, a store library with slice-level subscriptions, covered in the client state article, replaces context for shared state entirely rather than patching around its all-or-nothing re-render model.

Lifting state too early

Moving state up "in case a sibling needs it later" turns a local decision into an architectural one that every future contributor has to route around.

Lifting state to a shared ancestor is the correct move once two siblings genuinely need to read or change the same value. The mistake is doing it speculatively, before any sibling exists that needs it, on the theory that it might save a refactor down the line. A search input's typed value doesn't need to live in the page component that renders both the search box and the results list. It only needs to live there once the results list actually has to react to it. Placed there anyway, every keystroke re-renders the page and everything else the page renders alongside the search box, not because the architecture required it, but because the state was put one level higher than the problem it was solving.

search-page.jsx JSX 
function SearchPage() {
  const [query, setQuery] = useState('');

  return (
    <div>
      <SearchBox value={query} onChange={setQuery} />
      <FiltersPanel />
      <RecentSearches />
      {/* query isn't read here yet, no results list exists to consume it */}
    </div>
  );
}

FiltersPanel and RecentSearches read nothing from query, but both sit under SearchPage, so both re-render on every character typed. Keeping the input's value inside SearchBox itself, and lifting it only once a results list is added that actually needs to read it, keeps that re-render contained to the one component that changes. The general rule holds up well in practice: state starts as low in the tree as it can, and moves up only when a second, currently existing consumer needs it, never in anticipation of one.

The same mistake, one level up

The identical trade-off shows up with global stores. Reaching for a shared store the moment two components need to agree on something is the store equivalent of lifting state to the nearest common ancestor. Reaching for it before that need exists, "so it's there when we need it," produces the same speculative coupling, just with a bigger blast radius once it happens.

Derived state stored as state

If a value's answer is always a formula of state you already have, storing it separately just gives the two copies room to drift.

A filtered list, a computed total, a boolean for whether a form is valid: none of these are facts about the world that need their own slot in state. Each is a pure function of state that already exists elsewhere in the component. Storing it separately, then using an effect to keep it in sync whenever the source state changes, is derived state treated as if it were independent state, and it's one of the most common ways useEffect gets misused. The dependency array has to list every value the calculation touches, and forgetting one produces a component that renders a stale answer for exactly one render before the effect catches up.

product-list.jsx JSX 
// Antipattern: a second state slot, synced by an effect
function ProductList({ products, query }) {
  const [filtered, setFiltered] = useState([]);

  useEffect(() => {
    setFiltered(products.filter((p) => p.name.includes(query)));
  }, [products, query]);

  return <List items={filtered} />;
}

This renders ProductList twice for every change to query: once with the stale filtered from before the effect ran, then again once setFiltered lands. The fix removes the second state slot entirely and computes the value in the render body, where it can never be out of sync with products and query because it's calculated from them directly, every time.

product-list.jsx JSX 
function ProductList({ products, query }) {
  const filtered = products.filter((p) => p.name.includes(query));
  return <List items={filtered} />;
}

No effect, no second render pass, and no dependency array to keep correct by hand. A filter over a short array is cheap enough that wrapping it in useMemo would cost more in dependency-comparison overhead than it saves, and with the React Compiler now handling memoization automatically for components it can statically analyze, adding it by hand has become the exception rather than the default: a genuinely expensive computation, a value handed to a third-party library that compares by reference, or a value used as another effect's dependency are the remaining cases where reaching for useMemo still earns its keep.

Effects as event handlers

An effect that only ever fires in response to a click is a click handler wearing a disguise, and it inherits none of the click handler's guarantees about when it runs.

useEffect exists to synchronize a component with something outside React: a subscription, a DOM measurement, a connection that needs to open and close as the component mounts and unmounts. It isn't meant to react to a specific user action. A common way this gets confused in practice is a boolean flag set inside an onClick handler, watched by an effect that performs the actual work once the flag flips.

checkout-button.jsx JSX 
// Antipattern: a flag routes a click through an effect
function CheckoutButton({ cart }) {
  const [submitted, setSubmitted] = useState(false);

  useEffect(() => {
    if (submitted) {
      trackEvent('checkout_started', { cart });
      setSubmitted(false);
    }
  }, [submitted, cart]);

  return <button onClick={() => setSubmitted(true)}>Checkout</button>;
}

This adds a full render-and-effect round trip between the click and the tracking call, makes submitted a piece of state that exists purely to be reset a moment after it's set, and quietly re-fires if cart changes for any other reason while submitted happens to still be true. None of that machinery is needed. The click is already an event. Calling trackEvent directly inside the handler runs it exactly once, exactly when the user clicked, with no extra state and no dependency array to get wrong.

checkout-button.jsx JSX 
function CheckoutButton({ cart }) {
  function handleClick() {
    trackEvent('checkout_started', { cart });
  }

  return <button onClick={handleClick}>Checkout</button>;
}
A quick test for any effect

Ask what would happen if the effect's dependency array were deleted and it ran on every render instead. If the answer is "it would do the same user-triggered thing over and over for no reason," the logic belongs in a handler, not an effect. If the answer is "it would keep some external system correctly in sync," it's a legitimate effect.

Fetching inside component effects

A fetch dropped into useEffect looks like data loading. Structurally, it's a hidden dependency the component now owns end to end, race conditions, caching, and all.

Fetching a resource on mount is one of the oldest useEffect habits in React, and it's also the one with the most invisible failure modes. Done properly it needs an ignore flag or an abort controller to stop a slow, stale response from overwriting a newer one if the component's props change and re-trigger the effect before the first request finishes. Done without that guard, a component whose id prop changes quickly, a user clicking through a list of records, for instance, can render the response to an old request after a new one has already started.

user-profile.jsx JSX 
// Antipattern: fetch in an effect, race condition included for free
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then(setUser);
  }, [userId]);

  return user ? <Profile user={user} /> : <Spinner />;
}

Even fixed for that race, this version still fetches on every mount with no cache, so navigating away and back re-requests data the component already had, and two sibling components that both need the same user re-request it independently rather than sharing one in-flight request. None of that is specific to this component. It's exactly the job of a query layer, and by 2026 the answer for most apps is to not hand-roll it: a hook from TanStack Query or SWR, or, where the framework supports it, fetching in a Server Component or a route loader that runs before the component tree renders at all, covered in the Server Components article.

user-profile.jsx JSX 
function UserProfile({ userId }) {
  const { data: user, isLoading } = useQuery({
    queryKey: ['user', userId],
    queryFn: () => fetch(`/api/users/${userId}`).then((res) => res.json()),
  });

  return isLoading ? <Spinner /> : <Profile user={user} />;
}

The race condition, the cache, and the request deduplication between two components asking for the same userId all come from the library rather than from hand-written effect code, and none of it has to be re-verified per component. useEffect is still the right tool for the cases a query layer doesn't cover, subscribing to a WebSocket or a browser API, for instance, just not for the specific case of "load this data when the component appears."

Request waterfalls

A tree where every level fetches only after it mounts turns one page load into a relay race, each leg waiting on the one before it.

Fetching in effects has a second cost beyond the one above, and it shows up even after caching and race conditions are handled correctly. If a parent fetches a user, waits for that to resolve, and only then renders a child that fetches the user's orders, and that child in turn renders a grandchild that fetches order details, the three requests run one after another even though only the second and third actually depend on data from the one before. This is a request waterfall, and it's a structural property of where the fetches sit in the tree, not something a faster network connection fixes.

The fix isn't a faster individual request. It's issuing the independent requests together instead of nesting them inside the components that need their results. When orders only needs a userId that's already known before the user record resolves, it can be requested in parallel with Promise.all, or hoisted to a route loader that starts every request the page needs before rendering any component that depends on the results. Only a request that genuinely can't start without a value from an earlier one, order detail needing an order ID that only exists inside the orders response, has to wait. Everything else waiting is a tree shape problem, not a data dependency.

God components

A component that grew a prop, a hook, and a conditional branch for every case it's ever had to handle is easier to spot from its import list than from its size.

A god component is one that has quietly absorbed data fetching, permission checks, layout, and several unrelated feature branches into a single file, usually a few additions at a time, none of which looked wrong in isolation. Nobody sets out to write one. It's what a Dashboard component becomes after eighteen months of "just add one more if" for a new plan tier, a new role, a new widget. The result is a file every reviewer is nervous to touch, because a change meant for one feature can silently affect three others sharing the same render function, and a file that's effectively impossible to unit test in isolation, because testing any one branch means standing up everything the whole component depends on.

Symptom
Blast radius grows with unrelated work

A change for one customer segment risks breaking a code path for a completely different one, because both live in the same function.

Symptom
Untestable without the whole tree

Exercising one branch means mocking every dependency the entire component uses, not just the ones that branch touches.

The way out is the same set of moves covered in the composition half of this series: pull data fetching and business logic into a custom hook so the component's job shrinks to rendering, split visually or behaviorally distinct sub-parts into their own components using the compound component pattern instead of a growing prop list, and treat a new conditional branch as a signal to ask whether this is really the same component anymore, or two components that have been sharing a file.

Cargo-cult memoization

Wrapping every value in useMemo and every function in useCallback used to be defensive. With the compiler doing that work now, it's mostly noise, and occasionally a bug.

For years, the safe habit on any team worried about performance was to memoize liberally: wrap expensive-looking calculations in useMemo, wrap every function passed as a prop in useCallback, and treat both as a kind of insurance. The React Compiler, a build-time tool that statically analyzes component code and inserts the equivalent memoization automatically, changes the trade-off. On components it can fully analyze, it already does this work, and doing it by hand on top adds a dependency array to keep correct for no benefit, plus the small but real cost of comparing that array on every render.

Hand memoization can also actively mislead. A useCallback with a stale dependency array doesn't fail loudly. It just hands out an old closure that quietly reads outdated props or state, a bug that's harder to spot than the unnecessary re-render it was meant to prevent. In a codebase leaning on the compiler, both hooks work best treated as escape hatches rather than defaults: keep them for integrating with a third-party library that compares props by reference instead of value, for values used as another effect's dependency, or for the rare calculation expensive enough to measure and confirm makes a difference. That last part matters regardless of the compiler. Reaching for either hook without first checking, in the profiler, that the component in question is actually a re-render problem, is optimizing a number nobody measured.

Not every codebase has the compiler yet

Teams on an older React version, or one that hasn't adopted the compiler, still need manual memoization as the working default in hot paths. The direction of travel matters more than the exact cutover date. Treat new manual memoization as something to justify, not something to reach for automatically, and let the compiler take over incrementally as the codebase upgrades.

When antipatterns compound

Any one of the habits above is survivable alone. A single overly broad context costs a handful of unnecessary re-renders. A single derived-state effect costs one extra render pass. Production slowdowns that show up as "the app just feels slow," with no one obvious line of code to blame, are usually several of these stacked on top of each other. A cart update in a shared context re-renders a dozen consumers, each of which happens to compute a derived value in an effect, so each one renders twice, and two of those consumers each independently fetch the same resource in their own effect because there's no shared cache between them. None of that shows up in a single profiler snapshot as one bug. It shows up as a page that takes a beat too long to feel responsive, for reasons that only become visible by tracing the whole path a state change takes through the tree.

Server Components and a proper query layer remove entire categories of this by construction. A component that never runs in the browser can't misuse an effect, and a cache-aware query hook can't create a waterfall between two siblings that ask for the same data. Neither removes the need to know who owns a given piece of state and why a specific component re-renders when it changes. That discipline is what every fix in this article actually comes down to, and it's the same discipline the patterns in the companion article are built on top of.
