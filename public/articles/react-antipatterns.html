React Antipatterns

Eight habits that obscure state ownership, repeat work, or turn a component tree into a request chain.

Andreas Ögren
~9 min read
Last updated July 2026

React antipatterns rarely look broken in isolation. The code renders the right interface and may pass its tests. The cost appears as the component tree grows: unrelated components update together, requests wait on rendering order, and state gains more than one source of truth.

Each section asks what larger relationship a local choice creates. Some entries are firm mistakes, such as storing a value that can be calculated during render. Others are warnings whose severity depends on update frequency, framework support, and the size of the tree.

Context as a global store

One provider for unrelated, frequently changing values gives every consumer the same subscription boundary.

Context removes the need to forward a prop through intermediate components. That convenience can encourage one application-wide value containing the account, theme, cart, and notifications. Those values happen to be available in the same part of the tree, but they do not share a reason to change.

A component that reads context subscribes to the complete value. When the provider receives a different value, React updates every consumer of that context. It does not observe that one consumer read theme while another read cart.

app-context.tsx TSX 
type AppContextValue = {
  user: User | null;
  setUser: (user: User | null) => void;
  theme: string;
  setTheme: (theme: string) => void;
  cart: CartItem[];
  setCart: (cart: CartItem[]) => void;
};

const AppContext = createContext<AppContextValue | null>(null);

function AppProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [theme, setTheme] = useState('dark');
  const [cart, setCart] = useState<CartItem[]>([]);

  return (
    <AppContext value={{ user, setUser, theme, setTheme, cart, setCart }}>
      {children}
    </AppContext>
  );
}

ThemeToggle, Avatar, and CartBadge all subscribe to AppContext. Replacing its value after a cart update therefore schedules all three consumers. The extra work may be irrelevant in a small tree, but it becomes easier to notice when the provider contains fast-changing state and many consumers.

What this costs

Group a context by responsibility and update pattern, not by convenience. The patterns article shows how to separate state from stable commands. When consumers need slice-level subscriptions across a large shared model, Client State explains when an external store is the clearer boundary.

Lifting state too early

State placed above all of its consumers makes a wider part of the tree depend on each update.

Lifting state to the closest shared parent is correct when separate branches need the same value. The antipattern is lifting it before that relationship exists. A confirmation dialog's open state can live beside its trigger if no other branch reads or changes it.

Ownership is the useful question, as explained in Client State. A page component that owns unrelated modal state renders again whenever the dialog opens. Its child components may render again as a consequence, even though the value is absent from their props.

product-page.tsx TSX 
function ProductPage({ product }: { product: Product }) {
  const [isModalOpen, setIsModalOpen] = useState(false);

  return (
    <div>
      <ProductGallery images={product.images} />
      <ProductDetails product={product} />
      <button onClick={() => setIsModalOpen(true)}>Add to cart</button>
      {isModalOpen && <ConfirmationModal onClose={() => setIsModalOpen(false)} />}
    </div>
  );
}

ProductGallery and ProductDetails do not use isModalOpen, yet the parent calls them again when that state changes. Moving the state into AddToCartButton keeps the update inside the feature that owns it.

product-page.tsx TSX 
function AddToCartButton({ product }: { product: Product }) {
  const [isModalOpen, setIsModalOpen] = useState(false);

  return (
    <>
      <button onClick={() => setIsModalOpen(true)}>Add to cart</button>
      {isModalOpen && <ConfirmationModal onClose={() => setIsModalOpen(false)} />}
    </>
  );
}

function ProductPage({ product }: { product: Product }) {
  return (
    <div>
      <ProductGallery images={product.images} />
      <ProductDetails product={product} />
      <AddToCartButton product={product} />
    </div>
  );
}

Opening the dialog now updates AddToCartButton without updating ProductPage. Start state with the smallest owner that can serve its real consumers. Move it when sharing, persistence, or coordination creates a concrete reason.

The same mistake, one level up

A global store can create the same speculative coupling at a larger scale. Shared state is justified by shared ownership or synchronization requirements, not by the possibility that another component may need the value later.

Derived state stored as state

A value that can be calculated from current props and state does not need a second source of truth.

Filtered items, totals, and validation results are often derived values. Their inputs already contain everything needed to calculate them. Storing the result separately creates another state slot that must be synchronized with those inputs.

product-list.tsx TSX 
// Antipattern: a second state slot, synced by an effect
function ProductList({ products, query }: { products: Product[]; query: string }) {
  const [filtered, setFiltered] = useState<Product[]>([]);

  useEffect(() => {
    setFiltered(products.filter((p) => p.name.includes(query)));
  }, [products, query]);

  return <List items={filtered} />;
}

After query changes, the first render still sees the previous filtered value. The effect then updates state and causes another render. Computing the list during render keeps it aligned with products and query in the same pass.

product-list.tsx TSX 
function ProductList({ products, query }: { products: Product[]; query: string }) {
  const filtered = products.filter((p) => p.name.includes(query));
  return <List items={filtered} />;
}

The simpler version needs no effect or duplicate state. If the calculation is measurably expensive, useMemo can cache it between renders. Projects using React Compiler can usually rely on its automatic memoization for compiled components and hooks, while retaining manual memoization where identity is part of an external contract.

Effects as event handlers

Logic caused by one user action belongs with that action, not in a later synchronization pass.

Effects synchronize rendered state with an external system. Event handlers perform work caused by a particular interaction. A boolean set in a click handler and observed by an effect separates the cause from the work for no benefit.

checkout-button.tsx TSX 
// Antipattern: a flag routes a click through an effect
function CheckoutButton({ cart }: { cart: CartItem[] }) {
  const [submitted, setSubmitted] = useState(false);

  useEffect(() => {
    if (submitted) {
      trackEvent('checkout_started', { cart });
      setSubmitted(false);
    }
  }, [submitted, cart]);

  return <button onClick={() => setSubmitted(true)}>Checkout</button>;
}

The flag adds a render before the tracking call and must be reset afterward. Changes to another dependency can also run the effect again while the flag remains true. Calling trackEvent in the click handler keeps the work tied to the interaction that caused it.

checkout-button.tsx TSX 
function CheckoutButton({ cart }: { cart: CartItem[] }) {
  function handleClick() {
    trackEvent('checkout_started', { cart });
  }

  return <button onClick={handleClick}>Checkout</button>;
}
A quick test for any effect

Ask why the code runs. If a particular click or submission caused it, keep it in that event path. If the component must stay synchronized while it is displayed, an effect may be appropriate. Data fetching for the current route or query can fit the second case, although a framework or query library often provides a better implementation.

Hand-written fetching in effects

A request effect is valid, but it also makes the component responsible for races, caching, and server rendering.

Fetching in an effect is appropriate when the rendered component must stay synchronized with a remote resource. The small example is incomplete, however. If userId changes before the first request finishes, an older response can arrive last and overwrite the newer result.

user-profile.tsx TSX 
// Antipattern: fetch in an effect, race condition included for free
function UserProfile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then(setUser);
  }, [userId]);

  return user ? <Profile user={user} /> : <Spinner />;
}

Cleanup can ignore the stale result or abort the obsolete request, but the component still has no shared cache. Remounting requests the same resource again, and separate consumers cannot reuse an in-flight request. A query library can own those concerns. A framework route loader or Server Component can also fetch before the client component renders.

user-profile.tsx TSX 
function UserProfile({ userId }: { userId: string }) {
  const { data: user, isLoading } = useQuery<User>({
    queryKey: ['user', userId],
    queryFn: () => fetch(`/api/users/${userId}`).then((res) => res.json()),
  });

  return isLoading ? <Spinner /> : <Profile user={user} />;
}

The query hook centralizes race handling, caching, and deduplication. An effect remains useful when no data layer owns the synchronization, including subscriptions to browser APIs or a WebSocket. The antipattern is rebuilding a partial query system in every component, not the presence of fetch inside an effect by itself.

Request waterfalls

Requests coupled to nested mounts run in sequence even when their data dependencies do not.

A request waterfall appears when a parent waits for data before mounting a child that starts the next request. The child may then gate a grandchild in the same way. Rendering order has become network order, whether or not the requests truly depend on one another.

Start independent requests together. If the user and order requests both know their identifiers at route entry, a loader can begin both before rendering their consumers. A detail request that needs an identifier from the order response must remain sequential. The useful distinction is data dependency versus accidental nesting.

God components

A component becomes difficult to change when unrelated features share one render function and dependency set.

A god component accumulates concerns that change for different reasons. Data access, permissions, layout, and unrelated feature branches end up in one function. Its size is a symptom; the deeper problem is that every change shares the same imports, render path, and test setup.

Symptom
Blast radius grows with unrelated work

A change for one customer segment risks breaking a code path for a completely different one, because both live in the same function.

Symptom
Untestable without the whole tree

Exercising one branch means mocking every dependency the entire component uses, not just the ones that branch touches.

Split by responsibility, not by line count. A feature component can own its data boundary and render states together when they change together. Reusable stateful behavior may belong in a custom hook, but moving code into a hook does not reduce coupling by itself. A new branch is a prompt to ask whether the variants still share one responsibility.

Cargo-cult memoization

Memoization without a measured goal adds dependencies and can preserve stale closures without improving useful work.

useMemo caches a calculated value, and useCallback caches a function definition. Neither hook makes its work free. React still evaluates dependencies, and the cached identity only helps when some consumer can use it to skip work or preserve a required reference.

React Compiler can apply memoization automatically to the components and hooks it compiles. That makes routine defensive memoization less useful in projects that have adopted it. The compiler is a build-time choice, though, rather than behavior every React application receives automatically.

An incomplete dependency list can preserve a closure that reads old props or state. Correct manual memoization still has valid uses, such as stabilizing an effect dependency, serving a memoized child, or caching a calculation that profiling identifies as expensive. State the reason at the call site and verify that the downstream work is actually skipped.

Not every codebase has the compiler yet

React Compiler supports incremental adoption and can compile applications on React 17, 18, or 19. Existing memoization should not be removed mechanically because doing so can change compiler output or performance. In uncompiled code, profile first and add memoization where it protects a known expensive path or identity contract.

When antipatterns compound

These habits become expensive through composition. A broad context can update consumers that each maintain derived state in an effect. Some of those consumers may also request the same resource without a shared cache. No single line explains the delay because the repeated work follows several ownership and subscription boundaries.

Trace the path from a state change or navigation to the work it triggers. React DevTools can reveal repeated renders, while the browser network panel exposes sequential requests and duplicate fetches. A query layer or Server Components can remove some failure modes, but neither decides state ownership or component boundaries. Those remain design decisions.
