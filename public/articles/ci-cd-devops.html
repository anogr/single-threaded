CI/CD and DevOps

How a change moves from integration to release, and how teams control deployment risk along the way.

Andreas Ögren
~11 min read
Last updated July 2026

DevOps, CI/CD, and deployment pipelines often appear in the same conversation, but they describe different parts of software delivery. DevOps concerns how people share responsibility for a service. Continuous integration and continuous delivery are engineering practices, while a pipeline is one way to automate them.

The distinction matters because automation cannot create shared ownership on its own. The sections below begin with the working practices, then follow a change through a pipeline and into production. The final sections cover deployment control, GitOps, infrastructure as code, and the amount of machinery a team may need.

DevOps vs. CI/CD

DevOps changes who owns an outcome. CI/CD changes how software moves toward that outcome.

DevOps is a way of organizing software delivery around shared responsibility for the service in production. Developers, operations specialists, testers, security practitioners, and other contributors work across the delivery path instead of handing a finished build from one silo to another. The goal is to make delivery speed and operational reliability concerns of the same team.

CI/CD covers the technical practices that shorten and stabilize that path. Continuous integration combines frequent integration with automated feedback. Continuous delivery extends the automation far enough that a tested change can be released on demand. Pipelines support these practices, but a pipeline file alone does not establish DevOps. Ownership, feedback, and day-to-day collaboration still have to change.

Continuous Integration

Frequent integration keeps the distance between a developer's work and the shared codebase small enough to reason about.

Continuous integration (CI) means that every developer integrates with the shared codebase at least daily, and often more frequently. Each integration triggers an automated build and a useful set of tests. The short interval is the essential part. Conflicts and incompatible assumptions surface while the change is still small and fresh in the developer's mind.

Kent Beck developed continuous integration as an Extreme Programming practice in the 1990s. Its value does not depend on adopting the rest of that methodology. A team can use any branching and review workflow that still permits frequent integration, provided the shared branch stays healthy and failures receive prompt attention.

Continuous Delivery vs. Continuous Deployment

Both practices keep software releasable. They differ in what happens after a change has proved ready.

Continuous delivery keeps the software in a deployable state and makes production deployment available on demand. A release may still wait for a business decision, a scheduled window, or an explicit approval. Continuous deployment goes further by sending every change that satisfies the automated release criteria to production without a manual gate. Both are shortened to “CD,” so the surrounding context has to supply the meaning.

Continuous deployment is not a higher maturity level that every team must reach. It requires automated release criteria, production monitoring, and a recovery path that make unattended deployment acceptable for the service. Continuous delivery leaves the release decision outside the pipeline. That choice can reflect regulation, product coordination, or risk tolerance rather than a weakness in the automation.

Anatomy of a Pipeline

A pipeline arranges feedback so that cheap, fast checks fail before slower or riskier work begins.

A commit or merge starts a typical pipeline. The build stage compiles or packages the source into a deployable artifact, such as a binary, a web bundle, or a container image. Container image construction is covered in Containers and Orchestration. Fast automated tests then check the change before the pipeline spends time on broader system tests. Testing Strategy explains how unit, integration, and end-to-end tests divide that work.

Static analysis, linting, and security checks can run in parallel when they do not depend on one another. Security checks may inspect source, dependencies, build provenance, or the finished artifact. The wider supply-chain problem belongs to Web Security Principles. Once the required gates pass, the pipeline publishes the artifact to a registry or repository. Later stages should identify that artifact by an immutable version or digest.

Deployment is a path through environments rather than one final command. A continuous-delivery pipeline can deploy automatically to test environments and then expose a controlled production action. A continuous-deployment pipeline runs the production step when its release criteria pass. Environments and Promotion

Promotion gains its meaning from moving the tested artifact forward without rebuilding it.

Teams choose environment boundaries according to their product and risk model. A pipeline might use short-lived test environments, a persistent staging environment, production, or some combination of them. Whatever the names, the artifact that passed one stage should move unchanged into the next. Rebuilding from the same source can still resolve a mutable dependency or base image differently, leaving production with bytes that staging never tested.

Runtime configuration may differ across environments. Connection endpoints, credentials, and feature settings belong outside the artifact and are supplied during deployment or startup. Keeping code and environment-specific configuration separate lets one immutable artifact move through the delivery path while preserving the settings each environment needs.

Deployment Strategies

Which strategy fits is a question about acceptable risk and acceptable downtime, not a technical preference.

A rolling update replaces old instances in batches while some capacity stays available. It can avoid release downtime when the application supports mixed versions and the rollout settings preserve enough healthy instances. A blue-green deployment prepares a second environment and redirects traffic after it has been verified. Switching traffic back can be quick, although state and database changes may complicate recovery. A canary deployment exposes the new version to a limited share of traffic first, then expands or stops the rollout according to observed results.

RequirementStrategyTradeoff
Preserve availability with modest extra capacityRolling updateOld and new versions coexist during the rollout, and reversal is another rollout.

The patterns can be combined. A team might direct a small share of traffic to the green environment before completing a blue-green cutover. Kubernetes supplies useful rollout primitives, but weighted traffic and progressive analysis require additional components. Containers and Orchestration covers that boundary. The same deployment concepts also apply outside Kubernetes.

A feature flag separates deployment from release. The code can be present in production while the capability stays hidden or limited to a selected audience. Flags support product experiments and staged exposure, but they create temporary branches in runtime behavior. Each flag therefore needs an owner and a removal plan.

GitOps and Pull-Based Reconciliation

GitOps records desired state in a versioned source and lets software agents reconcile the running system toward it.

In a push-based deployment, the pipeline authenticates to the target environment and applies a change. GitOps uses a different control loop. Desired state is expressed declaratively, stored with version history, pulled automatically by an agent, and continuously reconciled with the running system. A Kubernetes deployment repository might declare an image digest, replica count, and configuration. An in-cluster controller such as Argo CD or Flux observes those declarations and applies the required changes.

The pull model can remove production credentials from the CI system because the reconciler already runs with the permissions needed inside the target environment. It does not make repository access harmless. A credential that can alter an automatically reconciled production branch may still authorize a production change. Protected branches, review rules, signed commits or artifacts, and narrowly scoped reconciler permissions stay part of the security boundary.

GitOps fits systems whose desired state can be represented declaratively and reconciled repeatedly. Kubernetes resources match that model well. Imperative operations with important intermediate steps need more care because their outcome cannot always be recovered from a final state declaration. In those cases, a conventional deployment job may stay clearer than hiding a sequence of commands behind a declarative wrapper.

Infrastructure as Code

Infrastructure as code brings version control and repeatable change to the resources beneath an application.

Infrastructure as code (IaC) represents resources such as networks, compute instances, and managed databases in versioned files. A tool such as Terraform, OpenTofu, Pulumi, or a cloud-native template system compares that definition with the provider and plans or applies the change. The underlying services are introduced in Cloud Computing. Code review and change history become possible, although safe operation still depends on state management, access control, and review of the generated plan.

IaC and GitOps overlap without being synonyms. IaC often provisions the cluster, network, and managed services. GitOps commonly reconciles application and platform configuration inside that infrastructure. Both use desired-state descriptions, but they may use different controllers, permission models, and change cadences.

Rollbacks and Pipeline Health

Recovery works only when the team has preserved a known-good artifact and rehearsed how to restore service.

Redeploying a previous artifact can be the quickest response to a stateless application regression, but some failures need more than a redeployment. Database migrations, external side effects, and incompatible protocols may require a forward fix or a separate recovery procedure. Immutable artifact promotion still helps because it preserves the exact application version that passed through the earlier environments.

The pipeline needs its own operational care. Rising execution time delays feedback, while flaky tests train developers to distrust failures. Teams should track queue time, stage duration, failure causes, and the rate of reruns or overrides. Production diagnosis belongs to observability, but the deployment record should still connect each release to its artifact, configuration, and source revision.

Choosing How Much Pipeline to Build

Everything in this article is available to any team. Not all of it is worth building on day one.

Multi-environment promotion, progressive delivery, and GitOps reconciliation all carry implementation and maintenance costs. They earn their place when release frequency, coordination needs, or production risk makes the extra control valuable. A smaller service may need only a reliable build, focused tests, and one repeatable deployment path.

TierWhat it looks likeFits
MinimalAutomated build and focused tests, followed by a documented manual deploymentA small service released infrequently, while deployment stays simple and low risk.

Large repositories face a related problem when CI work grows with the whole codebase instead of the affected change. Monorepos covers incremental builds and shared caching for that case. Pipeline controls should answer an observed cost or risk. Once added, they still need periodic review to confirm that they earn their place.
