Cascade and Inheritance

How a browser chooses among competing declarations and supplies values through inheritance.

Andreas Ögren
~18 min read
Last updated August 2026

Two stylesheets can assign different values to the same property on the same element. A base stylesheet might set a card's text to a neutral gray, and a theme stylesheet might set the same card's text to the brand's navy color. The browser must therefore choose which value becomes the card's color.

For a given property on an element, CSS may provide zero, one, or several applicable declarations. When no declaration applies, CSS obtains the value through inheritance or from the property's initial value. When exactly one declaration applies, the browser uses its value for the property. When several declarations compete, the cascade applies a fixed precedence order and selects one.

The Cascade

The browser resolves conflicts among declarations through an ordered sequence of comparisons.

A stylesheet can contain style rules, and each style rule can contain declarations. A style rule combines a selector with a block enclosed in braces. The selector determines which elements the rule can match. Each declaration in the block pairs a property with a value.

base.css + theme.css CSS 
/* base.css */
.card {
  color: gray;
  padding: 1rem;
}

/* theme.css, linked after base.css */
.card {
  color: navy;
}

Each block in the example is a style rule. .card is the selector, while color: gray and color: navy are declarations. Within the first color declaration, color is the property and gray is the value. The cascade considers each declaration separately. The card can therefore take color from the second rule while keeping padding from the first because the browser resolves those properties separately.

Before comparing precedence, the browser determines which declarations apply. A declaration in a style rule must be valid, and the rule's selector must match the element. If the rule is inside a condition such as @media, that condition must also match. Declarations that pass these checks become candidates in the cascade.

After filtering, the browser compares candidate declarations in the cascade order. It stops when one declaration has higher precedence. If the candidates tie, the browser moves to the next comparison.

The cascade compares declarations in this order.

  1. Origin and importance rank declarations by where they come from and whether they use !important.
  2. Encapsulation context decides between declarations from the document and its shadow trees.
  3. Style attributes take precedence over style rules when the earlier comparisons tie.
  4. Cascade layers set precedence among groups of declarations.
  5. Specificity favors the declaration whose selector is more specific.
  6. Scoping proximity favors the declaration whose scoping root is closest to the element.
  7. Source order lets the declaration that appears later win.

Origins and Importance

Origins identify who supplied a declaration. Importance changes which origins outrank others.

An origin identifies who supplied a declaration. The user-agent (UA) origin gives HTML elements usable default styles. The user origin represents styles chosen by the reader. The author origin contains linked stylesheets, <style> elements, and other styles supplied by the page.

For normal declarations, the site's author styles outrank user styles, and user styles outrank browser defaults. That order lets the page provide its design without requiring every browser default to be reset. In the example, both card declarations are normal author declarations, so neither gains precedence from origin.

Adding !important marks a declaration as important. Important declarations beat normal declarations, and the order of the three origins reverses. Important user-agent declarations outrank important user declarations, which outrank important author declarations. Reversing the origin order lets a reader's important font-size or color declaration override the site's important styles.

The origin-and-importance comparison also includes animation and transition declarations. While a CSS animation is running, the value it produces for an animated property outranks normal declarations for that property. Any important declaration still outranks the animated value. An active CSS transition outranks all of them for the property being transitioned. While active, an animation or transition can therefore replace the value the property would otherwise use.

!important as a last resort

In author CSS, !important should be reserved for a declaration that must outrank normal author declarations. It is unnecessary when changing layer order or selector matching can resolve the conflict. Once an author declaration is important, another author declaration normally needs !important to override it. A normal declaration cannot override an important one.

Encapsulation Contexts

A shadow tree creates a separate styling context attached to a host element.

A shadow tree is a separate Document Object Model (DOM) tree attached to a host element. Ordinary selectors in the page cannot match elements inside the shadow tree, and ordinary selectors inside the shadow tree cannot match elements in the page. The document tree and its shadow trees form separate encapsulation contexts for the cascade.

Special selectors allow limited styling across the shadow boundary. A :host rule inside the shadow tree and a rule in the outer document can both style the host element. When those rules set the same property, the cascade compares their encapsulation contexts after origin and importance. If both declarations are normal, the outer declaration wins, allowing the page to override a normal host default from the shadow tree. If both are important, the shadow-tree declaration wins. These precedence rules do not change which elements each selector can match.

The two card declarations come from page stylesheets, so both belong to the document context and remain tied at this comparison. The browser next checks whether either declaration comes from a style attribute.

Style Attributes

A declaration in a style attribute applies directly to one element and has no selector. If it competes with an author declaration from a style rule, it wins when both declarations have the same importance and encapsulation context. Important author declarations outrank normal declarations in style attributes.

A style attribute is useful when runtime code supplies a value for one element, such as a width calculated after measuring that element. Static styles shared by several elements are better expressed as style rules. One rule can apply to several elements. When another rule supplies a different value, the cascade chooses between the declarations.

The two card declarations both come from style rules, so they remain tied.

Cascade Layers

Layers give groups of declarations an explicit priority before specificity is compared.

A cascade layer groups related declarations and gives the group a position in the layer order. A project might place site defaults and third-party CSS in early layers, base components in the next layer, application styles in a later layer, and exceptions in a final layer. Declarations in the same layer remain tied at this comparison. When declarations come from different layers, layer order decides the winner before specificity.

Normal declarations outside a named layer belong to an implicit final layer, so they outrank normal declarations in every named layer. Normal declarations in an existing unlayered stylesheet can therefore outrank matching normal declarations in a layered default or third-party stylesheet. Moving only some rules into named layers can lower their normal precedence relative to rules left unlayered.

Important declarations reverse the layer order. An important declaration in an earlier layer outranks an important declaration in a later layer, and important declarations in named layers outrank important unlayered declarations. The reversed order protects important declarations in earlier layers when later layers add their own important declarations.

Layers are useful when groups of declarations need a stable priority that does not depend on selector weight. The layer order expresses that priority directly, so selectors do not need extra IDs or ancestors merely to win conflicts. Layers do not change which elements a selector matches. A small stylesheet with no recurring priority conflicts may not need named layers, while a larger project can define one layer order across its stylesheets as part of its CSS architecture.

If @layer base, theme; appears before either layer has been declared, it establishes base before theme. For normal declarations, a later layer has higher precedence. If the gray card declaration belongs to base and the navy declaration belongs to theme, the theme declaration wins at the layer comparison. If both .card rules remain unlayered, their color declarations tie at the layer comparison.

Specificity

The browser compares selector specificity only after the earlier cascade comparisons tie.

Specificity is a weight calculated from a selector's structure. The browser compares it only when declarations from style rules remain tied after the earlier cascade comparisons. Style attributes have no selectors, so specificity does not apply to them. Greater specificity cannot overcome a declaration that won an earlier comparison.

A selector's specificity is represented by three counts for IDs, classes, and types. The browser compares the counts from left to right and moves to the next count only when the earlier counts tie.

  1. The ID count comes first. Each ID selector contributes one.
  2. The class count comes second. Each class selector and attribute selector contributes one. Most pseudo-classes, including :hover, also contribute one.
  3. The type count comes last. Each type selector contributes one. A pseudo-element such as ::before also contributes one.

The selectors below show why one ID outweighs three classes.

specificity.css CSS 
#save-btn { color: navy; }
/* Specificity is (1, 0, 0) because the selector contains one ID. */

.card .actions .save-button { color: gray; }
/* Specificity is (0, 3, 0). Three classes still lose to the ID above. */

The universal selector and combinators add no specificity. The descendant combinator, written as a space, and the child combinator > describe relationships without increasing any of the three counts. The :where() pseudo-class also contributes zero, regardless of its argument, so :where(#save-btn) has (0, 0, 0). A default stylesheet can use :where() to match a precise set of elements without making later overrides harder.

The :is(), :has(), and :not() pseudo-classes take the specificity of their most specific selector argument. The selector :is(.save-button, #save-btn) therefore has (1, 0, 0), even when it matches an element through the class argument.

The :nth-child() and :nth-last-child() pseudo-classes each contribute one to the class count. An of clause adds the specificity of its most specific selector, so :nth-child(2n of .featured) has a specificity of (0, 2, 0). The nesting selector & follows the same maximum rule as :is(). It has the specificity of the most specific selector in the parent rule's selector list.

Specificity should follow from the selector needed to identify the intended elements. Adding an ID or ancestor only to win a conflict makes later overrides harder. When a selector matches the intended elements but still loses, an earlier cascade comparison may already have decided the winner. More specificity cannot change the result of an earlier comparison.

Scope Rules

A scope limits selector matching to a document region. If scoped declarations otherwise tie, the browser also compares their distance from the scoping root.

A scope rule begins with @scope and groups style rules that share a matching region. The first selector in parentheses identifies one or more scoping roots, which form the upper boundary of each scope. An optional selector after to identifies the lower boundaries. Enclosed selectors can match descendants of a scoping root, but not a lower-boundary element or any of its descendants.

scope.html + scope.css HTML + CSS 
<!-- scope.html -->
<article class="article">
  <header>
    <h2 class="title">
      Cascade and inheritance
    </h2>
  </header>
  <section class="comments">
    <h2 class="title">Comments</h2>
  </section>
</article>

/* scope.css */
@scope (.article) to (.comments) {
  .title { color: navy; }
}

The article title is inside .article and outside .comments, so the scoped rule gives it navy text. The comments heading is a descendant of the lower-boundary element and therefore outside the scope. Wrapping the article title in <header> does not change the match because .title can appear at any descendant depth between the boundaries.

A scope keeps the shared boundary separate from the selectors that style individual elements. When several rules belong to the article region, each enclosed selector can describe the element it styles without repeating .article or an exclusion for .comments. Changing the region later requires changing the @scope prelude rather than every enclosed selector. The block also keeps rules for the same region together in the stylesheet.

Descendant and child combinators express one relationship within one selector. The selector .article .title matches both headings because both are descendants of the article. The selector .article > .title matches neither heading because each one is wrapped in another element. The scope allows the article title to appear at any depth between the two boundaries while excluding the entire comments subtree.

Scope boundaries do not add specificity to enclosed selectors. The scoped .title selector remains (0, 1, 0), whereas .article .title has (0, 2, 0). Specificity therefore reflects the enclosed selector rather than the selectors that define the region.

If declarations remain tied after specificity, the browser compares scoping proximity. It counts the parent or sibling steps between the matched element and each scoping root. The declaration from the nearest root wins. A declaration from an unscoped rule has no scoping root, so it loses to an otherwise tied scoped declaration.

Source Order

If scoping proximity ties, or both rules are unscoped, source order is the final comparison. The later declaration wins whether it appears later in the same stylesheet or in a stylesheet linked afterward.

These comparisons form the complete cascade order. The browser moves down the order only when declarations tie. The two card declarations reach source order because they tie at every earlier step.

Inheritance

The cascade may provide a value for a property. If it does not, defaulting uses inheritance or the property's initial value.

Every applicable declaration contributes a declared value for its property. If the cascade supplies no value, defaulting uses inheritance or the property's initial value. Each property's definition states whether the property inherits. An inherited property then receives its parent's value, while a non-inherited property uses its initial value. The root element has no parent, so an inherited property on the root also uses its initial value.

Text-related properties such as color, font-family, and line-height usually inherit because nested text should normally keep the surrounding text style. Authors can set these properties on a container instead of repeating them for every descendant that contains text.

Properties that control an element's box usually do not inherit. A border, margin, or width belongs to the box on which it is set. If those values inherited, every nested element would receive the same box styling unless another declaration replaced it.

A card with a nested <em> shows both behaviors.

inheritance.html + inheritance.css HTML + CSS 
<!-- inheritance.html -->
<div class="card">
  Card text with <em>emphasis</em>.
</div>

/* inheritance.css */
.card {
  color: #1a1a1a;
  border: 1px solid;
}

The <em> has no color declaration, so it inherits the card's color. It also has no border declaration, but border properties do not inherit. Its border properties take their initial values, including none for border-style, so the browser draws no border around the emphasized text.

Inheritance uses the parent's computed value, which is the value after CSS has resolved dependencies such as relative units. If a parent declares font-size: 1.25em, the browser first resolves that size against the font size inherited by the parent. A child that inherits font-size receives the resolved size, so the 1.25 factor is not applied again at each descendant level.

A property's initial value comes from the property's specification, not from the browser's user-agent stylesheet. The initial value of display is inline, for example, even though the browser's stylesheet normally gives a <div> block layout. In normal flow, display: initial therefore makes a <div> inline rather than restoring its familiar browser styling.

Custom properties (CSS variables) inherit by default. A descendant can use the inherited value in another declaration with var(). A design-token value declared on an ancestor is available to descendants that do not override it. An @property rule can register the custom property with inherits: false when the value should not pass to descendants.

A CSS-wide keyword can be used as the complete value of any property. CSS defines five such keywords.

  • inherit uses the inherited value even if the property does not normally inherit. That value is the parent's computed value, or the property's initial value on the root element.
  • initial takes the property's initial value even if the property normally inherits.
  • unset acts like inherit on an inherited property and like initial on a non-inherited property.
  • revert rolls author styles back to the user origin and user styles back to the user-agent origin. In a user-agent stylesheet, it behaves like unset.
  • In a style rule, revert-layer acts as if declarations in the current cascade layer did not apply to that property. The cascade checks lower-priority layers in the same origin and can continue to an earlier origin if none supplies a value.

The first three keywords determine the specified value directly. Because color is inherited, color: unset gives the card its parent's computed color.

With revert and revert-layer, the browser continues at lower precedence to find another declaration. If @layer base sets the card's color to gray and a later @layer theme declares color: revert-layer, the browser disregards the theme layer for that property and uses the gray declaration from base. If a normal theme rule uses color: revert, the browser disregards author-origin declarations for that property and checks the user and user-agent origins before defaulting.

In this example, .card__highlight is a child of .card. Its color would inherit without an explicit declaration, while its border would not. The inherit keyword changes the border behavior but leaves the resulting color unchanged.

inheritance.css CSS 
.card {
  color: #1a1a1a;
  border: 1px solid;
}

.card__highlight {
  color: inherit;  /* Color already inherits, so this does not change the result. */
  border: inherit; /* The highlight receives the card's border values. */
}

Tracing a Property

A property trace follows one property from applicable declarations to its specified and computed values.

The :root selector matches the document root. The :root rule sets a color that the save button would inherit if no declaration set color on the button itself. The two button rules set color directly, so both declarations enter the cascade. The selector in base contains one ID and three classes, while the selector in components contains one class.

resolution.css CSS 
:root { --accent: #9a5a22; color: #1a1a1a; }

@layer base, components;

@layer base {
  #page .sidebar .card .save-button { color: red; }
  /* Specificity is (1, 3, 0), but this rule is in the earlier layer. */
}

@layer components {
  .save-button { color: var(--accent); }
  /* Specificity is (0, 1, 0). Layer order makes this declaration win. */
}

Both declarations are normal author declarations in the same encapsulation context. They tie at the origin-and-importance and encapsulation-context comparisons. Neither declaration comes from a style attribute, so they also tie at the style-attribute comparison. The components layer was declared after base, so its declaration wins at the layer comparison. The cascade stops there without comparing specificity, scoping proximity, or source order. Because a declaration supplies the button's color, the button does not inherit color from :root.

A property trace follows one property from applicable declarations to its computed value in four stages.

  1. Candidate collection gathers valid declarations for that property that apply to the element. A candidate may come from a matching style rule or a style attribute. If a style rule is inside a condition such as @media, that condition must match.
  2. Cascade comparison orders the candidates by precedence and chooses at most one cascaded value. revert-layer can make the cascade continue in a lower-priority layer, and revert can make it continue at a lower-priority origin. If no declaration remains, there is no cascaded value.
  3. Defaulting produces the specified value. It normally uses the cascaded value. The inherit, initial, and unset keywords instead determine the specified value according to their rules. If there is no cascaded value, an inherited property receives its parent's computed value, or its initial value on the root element. A non-inherited property receives its initial value.
  4. Computation resolves dependencies in the specified value that do not require layout, producing the computed value.

A property trace shows why the browser chose an unexpected value. Selector matching decides which declarations participate. Layer order sets precedence among groups of declarations, while a scope limits selector matching to a region. Increasing specificity cannot change layer order, and !important cannot make a declaration apply when its selector does not match.

Low-specificity selectors make declarations within the same layer easier to override without adding IDs solely for that purpose. Layer order controls precedence between layers independently of selector specificity. Block Element Modifier (BEM), for example, uses class-based names for blocks, elements, and modifiers. Combining BEM selectors with an explicit layer order makes precedence easier to trace across a CSS codebase.
