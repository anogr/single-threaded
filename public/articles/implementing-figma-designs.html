Implementing Figma Designs

How frames, variants, variables, and inspected values inform implementation without becoming the DOM or component API directly.

Andreas Ögren
~11 min read
Last updated July 2026

A Figma frame captures one example of an interface. Implementation has to recover the rules that make the interface work beyond that example.

A button that measures 140 pixels may be fixed at that width, or it may have grown around the label used in the mock. Five visible navigation items may represent a product rule or one account's permissions. The interface still has to work with longer text, missing data, and different content. Reading the file well means separating intended constraints from measurements that belong only to the example.

This article is not a guide to operating Figma. Comments, branches, libraries, version history, and prototypes all support the wider workflow, but the focus here is the implementation artifact. That artifact consists mainly of containers, reusable components, component properties, variables, and the values exposed for inspection.

UX Principles explains the usability and interaction reasoning behind the design. The discussion here begins at handoff. It follows the file into markup and component code, then identifies the points where the file cannot supply a complete answer.

Frames, Auto Layout, and Components

Frames, Auto Layout, components, instances, and variants carry most of the structural information needed during implementation.

A frame is a Figma container with dimensions, layout properties, and child layers. Frames can nest, so their hierarchy may resemble a DOM tree at first glance. The resemblance is useful for finding groups, but it does not determine the eventual markup. Pages organize material within the file and usually have no direct equivalent in the product.

Auto Layout arranges children using a vertical, horizontal, or grid flow. It also records spacing, padding, alignment, and resizing behavior such as hug, fill, and fixed dimensions. Horizontal and vertical flows often suggest flexbox, while grid flow may suggest CSS grid. The correspondence is still interpretive. Code should use the layout model that expresses the component's behavior, even when the design reached the same appearance through a different flow.

For example, a horizontal Auto Layout frame with a 16-pixel gap and children that hug their contents closely resembles display: flex with gap: 16px. That is useful evidence, not generated architecture. Wrapping behavior, minimum sizes, and the semantics of each child still have to come from the design's intent and the surrounding product.

A component is a reusable definition, and an instance is a placed copy that exposes selected properties for customization. A variant is one member of a component set, identified by property values such as size or state. These ideas resemble component definitions, rendered instances, and props in code, but their boundaries do not match every frontend framework exactly.

The layer tree should not be copied into the DOM one node at a time. Some layers exist only to position or annotate the design. A spacer rectangle becomes a gap in CSS, and a frame used for alignment may disappear when its relationship can be expressed on the parent. Keep a wrapper only when it represents a meaningful group, layout boundary, or reusable component.

Element choice requires information that the layer panel does not encode. A control that performs an action belongs in a native <button>, even if the design represents it as a rectangle and a text layer. Markup should describe the interface's meaning. CSS should reproduce its layout and presentation.

Variants and Component Props

Variant properties are evidence for a component API, but their names and combinations still need to be interpreted.

A mutually exclusive property often maps cleanly into code. If a component has small, medium, and large variants, a string union can express that choice. Other differences may represent independent conditions or editable content. Copying every Figma property into one variant prop hides those distinctions and makes invalid combinations easier to create.

Figma may show default, hover, disabled, and loading as separate variants so each appearance can be inspected. A literal translation produces values such as primary-loading and secondary-disabled, causing the union to grow with every combination. In code, hover normally comes from the browser's interaction state. Disabled and loading are independent conditions that may coexist with an intent such as primary or secondary.

button.tsx TSX 
// One identity axis, two independent conditions layered on top.
type ButtonProps = {
  variant: 'primary' | 'secondary';
  disabled?: boolean;
  loading?: boolean;
};

Separating intent and size from temporary state keeps the prop model understandable as the component grows. The exact split depends on whether combinations are valid and who owns each state. React Patterns & Component Design develops the same question at the code-component boundary.

Name Variants by Intent, Not Appearance

Names such as Primary and Secondary can survive a rebrand because they describe roles. Names such as Blue and Gray become misleading when the palette changes. The component prop should preserve the same semantic distinction. This applies the consistency heuristic from UX Principles to the component API.

Dev Mode and the Inspect Panel

Inspection provides exact values for the selected object. It does not decide which values are rules, tokens, or measurements of one instance.

Dev Mode provides a developer-focused view of a Figma file. For a selected object, its Inspect panel exposes layout, spacing, color, typography, component properties, styles, variables, and prototype interactions where they apply. It can also show autogenerated code whose language and output depend on the selected settings and any code-generation plugins.

Each reported value still needs interpretation. A 24-pixel gap may be the resolved value of spacing.lg, and a fill may come from a semantic color variable. Dev Mode can expose applied variables and suggest matching variables for some raw values. When the project already has a token, use its name instead of copying the resolved number and creating a second source of truth.

Dimensions require the same reading. A layer that currently measures 200 pixels may be fixed, or it may be filling a container that happens to be 200 pixels wide. Resizing properties such as hug, fill, fixed, minimum, and maximum reveal how the dimension should behave beyond the selected frame.

A selection that reports Mixed does not share one value for that property. Multiple layers may differ, or one object may use separate values on individual sides or corners. Inspect the relevant layer or sub-property more narrowly instead of treating Mixed as an implementation value.

Dev Mode's Export Isn't a Drop-In

Generated code describes the current selection and context. It may include Figma variables, but it cannot know the architecture, responsive rules, or unselected states of the application. Use it to inspect how Figma resolved a property, then express the same intent through the codebase's components and tokens.

Pasting a generated block can preserve structural choices that only made sense on the canvas. Review every declaration against the component's intended layout, responsive behavior, and existing token system.

Figma Variables as Design Tokens

Figma variables, design tokens, and CSS custom properties overlap, but each belongs to a different layer of the delivery pipeline.

A Figma variable stores a color, number, string, or boolean value. Collections and modes let the value change with a context such as a light or dark theme. Variables can also alias other variables, which makes semantic naming possible. A design token carries that named decision across tools, while a CSS custom property is one possible runtime representation of the token.

The mapping is not necessarily one to one. A local variable may exist only to maintain a particular file, while code can need tokens for concerns the design never models, such as stacking order. Promote a value into the shared token system when several consumers need to agree on its meaning. Tool symmetry is not a goal by itself.

CSS at Scale covers token tiers, theming, and the tooling that keeps names and types aligned. During handoff, shared semantic names matter more than identical storage. They let the developer trace a design value to an existing token instead of negotiating the meaning of another raw number.

What Auto Layout Doesn't Capture

Auto Layout can model resizing and reflow, but it only communicates the responsive decisions that someone explicitly encoded and checked.

A 16-pixel gap records a relationship between two elements. On its own, it does not say whether the gap changes on a narrow screen or whether the elements should wrap, stack, or disappear. Auto Layout supports responsive behavior, including wrapping, grid flow, and size constraints. Those capabilities only help when the file uses them to express the intended transition.

Files often show a few representative widths rather than every point in a continuous range. The examples reveal where the layout was reviewed, not necessarily where CSS breakpoints should be placed. Implementation must interpolate between them and test beyond the narrowest and widest examples, using the content and component constraints to decide where a change is needed.

One Frame's Measurements Aren't a Responsive Spec

A component that looks correct at the one width its frame was drawn at can still be missing every decision that matters at the widths nobody checked. Confirming behavior at the extremes, not just the one width in the file, is implementation work a design file can't do on its own.

Content creates another range that a single frame cannot cover. A short name does not reveal truncation or wrapping behavior, and five list items do not explain empty or long lists. Translated strings add further variation, but no one language provides a reliable worst case. Test realistic extremes and decide which content may wrap, truncate, scroll, or change the surrounding layout.

States a Static Frame Can't Show

A frame renders one state. The others still have to exist somewhere before code can be written against them.

A component may pass through default, hover, focus, active, disabled, loading, and error states. Interaction States and Feedback explains what those states mean in the finished interface. In Figma, they may appear as variants, prototype interactions, documentation, or examples in a library. If the file shows only the default, implementation should follow an established component pattern or ask for the missing behavior rather than inventing each state independently.

Focus is easy to overlook because it is encountered through keyboard navigation in the product, not by pointing at a static frame. Its absence from the file should not be read as a decision to remove it or reuse hover styling. Confirm the treatment and preserve a visible indicator. Accessibility as an Architecture Decision covers the underlying keyboard and semantic requirements.

The Handoff Conversation

Most of what a static file can't answer gets resolved fastest by asking, not by guessing and hoping the guess survives review.

Not every gap needs another frame. An established component or design-system pattern may already provide the answer, and small low-risk details can often be resolved by following it. The important step is to notice the gap and choose deliberately. Otherwise the browser, a library default, or an incidental implementation detail makes the decision.

  • Behavior — What does this look like while it's loading, and what happens on screen if the action fails outright?
  • Behavior — Is this update optimistic, applied immediately and rolled back on failure, or does it wait for confirmation first?
  • Layout — What happens at the widths this file doesn't show, particularly the narrowest one a real user might actually have?
  • Layout — What does this look like with no content in it at all?
  • Content — What's the longest realistic value this label or field needs to hold, not just the one used in the mock?
  • Content — Does this string still fit once it's translated, and does the layout assume a length that won't hold in every locale?
  • Interaction — Does this work end to end from a keyboard alone, with a visible focus indicator at every step?
  • Interaction — What replaces this on a touch device, if the design depends on hover to reveal it?

These questions turn handoff into a shared interpretation of the interface rather than a transfer of pixel measurements. The file remains essential evidence, but it is one set of examples within a larger specification made of product rules, component conventions, content, and accessibility requirements.
