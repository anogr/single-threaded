Implementing Figma Designs

How a Figma file's frames, variants, and inspector values map onto the DOM, and where a static design stops being enough to build from.

Practical guide
~13 min read
Design handoff
July 2026

A Figma frame captures one instance of an interface. Turning it into working software means deciding which parts of that instance are meant to hold as a rule, and which parts just happened to be true of the single example on screen.

A button drawn at 140 pixels wide isn't a specification for a 140-pixel button. It's an example of a button, sized to fit whatever label the designer typed into it that day. A navigation frame showing five menu items isn't declaring that the product will always have exactly five. Both are snapshots of a system that has to keep working once a label runs longer, a list comes back shorter, or an account carries more permissions than the one used to build the mock. Reading a Figma file well means noticing which numbers on screen are load-bearing and which ones are incidental.

Figma itself is mostly out of scope here. Comments, branching, shared libraries, version history, and prototyping are all real parts of working in the tool, and none of them are covered in what follows. What matters for implementation is the artifact a file produces once a design is ready to build: frames, components, variants, and the values an inspector panel reports for each one.

UX Principles covers the heuristics, structure, and interaction states that explain why a design looks the way it does. This article assumes that reasoning already happened and picks up where the file lands on a developer's desk, covering how its structure maps onto a DOM, where that mapping runs out, and what to ask when it does.

Frames, Auto Layout, and Components

Five vocabulary terms account for nearly everything worth reading in a design file. A sixth, pages, is mostly filing.

A frame is Figma's container element, the rough equivalent of a <div> with a fixed or flexible size. Frames nest inside each other the way DOM elements do, and a full screen is usually one large frame holding many smaller ones. Pages, the tabs along the top of a Figma file, just group frames for the designer's own organization. They rarely carry any meaning that needs to survive into code.

Auto Layout maps most naturally onto flexbox: a frame with Auto Layout enabled arranges its children in a row or column, with a defined gap and padding, and each child can be set to hug its content, fill the available space, or stay a fixed size. That mapping is close enough to be genuinely useful during implementation, not just a teaching analogy, but it isn't automatic. The layout model that belongs in code follows the component's actual behavior, not whichever tool produced the mock. A wrapping grid of cards still belongs in CSS grid, even when the frame specifying it only used Auto Layout to approximate the effect. A frame with Auto Layout, a 16-pixel gap, and three children set to hug their content is describing display: flex, gap: 16px, and no flex-grow on any child, almost directly.

A component is a reusable definition, the Figma equivalent of a component definition in code. An instance is a placed copy of that component, configurable only within the constraints the main component allows, the same relationship a rendered <Button /> has to its source file. A variant is one of several predefined states of a component, grouped into a variant set with one or more named properties, such as size or intent, that a designer switches between using a dropdown instead of manually restyling each instance.

None of this structure is meant to be copied one to one into the DOM. Figma's layer tree exists to help a designer position and organize things, and it routinely contains frames, groups, and empty rectangles that have no reason to exist as elements once the design becomes code. A rectangle sitting between two fields to hold a gap open is a spacer layer, and it becomes a gap value in a flex or grid container, not an empty <div>. A frame that exists only to let a designer nudge two elements together doesn't need a wrapper element in the DOM unless that grouping is also a real, reusable unit. The question worth asking of every layer is whether it represents a genuine structural or semantic boundary, or whether it's an artifact of how the design tool happens to model positioning. The target is markup that reflects the interface's meaning and component boundaries, not one shaped like the layer tree, which is also why element choice matters as much as structure. A component instance that behaves like a button belongs in a <button> element, not a styled <div> with a click handler, even though nothing in Figma's layer panel distinguishes between the two.

Variants and Component Props

A variant set looks like it wants to become a prop. Whether it should become one prop or several is a judgment call the file itself doesn't make.

The direct move is to turn a Figma variant property into a matching prop, and for something like size, small, medium, large, that's usually correct: a component only ever needs one of those at a time, so a string union models it exactly. The mistake is applying the same move to every variant property a design file happens to define, including ones that aren't mutually exclusive at all.

A button component in Figma often carries separate variants for its default appearance, its hover state, its disabled state, and a loading state, because a designer needs to see and edit each one individually. Translated literally, that becomes a prop like variant="primary-loading" alongside variant="primary-disabled", variant="secondary-loading", and so on, a union that grows by multiplication every time either dimension gains a new value. Hover in particular shouldn't become a prop at all: a browser already provides that state for free through :hover, and nothing needs to pass it down.

button.tsx TSX 
// One identity axis, two independent conditions layered on top.
type ButtonProps = {
  variant: 'primary' | 'secondary';
  disabled?: boolean;
  loading?: boolean;
};

loading and disabled aren't variations of what the button is, they're temporary conditions layered on top of it, and a design file usually shows them as separate variants only because that's the easiest way to let a designer preview each one. Splitting a variant set into an identity axis, usually intent or size, and a set of independent boolean conditions keeps the resulting prop type from growing combinatorially. The same judgment call, deciding what belongs on a component's identity versus what's just its current state, comes up throughout React Patterns & Component Design.

Name Variants by Intent, Not Appearance

A variant named Primary and Secondary survives a rebrand that changes which color counts as primary. One named Blue and Gray doesn't, and neither does a prop copied from that naming. Matching a variant's name to what a component means, not what it currently looks like, is the same consistency heuristic covered in UX Principles, applied one level down into the component's own API.

Dev Mode and the Inspect Panel

The values an inspector reports are measurements of one specific frame, not necessarily the values a component should ship with.

Dev Mode is Figma's inspection surface for a selected layer: spacing, color, typography, and border values on the right-hand panel, along with a generated code snippet in CSS, iOS, or Android that approximates the same layer. It's the fastest way to get an exact number out of a design file, and also the easiest way to end up with a codebase full of numbers nobody chose on purpose.

The question worth asking of every value Dev Mode reports is whether it's intentional or incidental: does this specific gap, color, or size mean something the same way everywhere it appears, or is it just what the tool calculated for this one layer? A gap of 24 pixels between two elements is often really spacing.lg from an existing scale, present in this particular frame because that's what Auto Layout happened to compute once the surrounding content was in place. A fill of #1976D2 is often really color.primary, the same accent used everywhere else in the file, picked from a shared swatch rather than mixed fresh for this one button. Copying the literal number in either case works today and quietly reintroduces the drift a token system exists to prevent.

The same distinction applies to size, not just spacing and color. A layer reporting a width of 200 pixels might be genuinely fixed, meant to stay that size regardless of context. It might also be a child set to fill its container, currently measuring 200 pixels only because that's how wide the container happens to be in this particular frame. Auto Layout's hug, fill, and fixed settings, visible in the same inspector panel as the raw number, say which one is true. The number by itself doesn't.

A selection that reports Mixed instead of a value is the same problem in a different shape. It shows up when a multi-layer selection, or a shape with a different corner radius on each corner, doesn't share one consistent value for whatever property is being inspected. That's a statement about the current selection, not a value to carry into code: the fix is selecting more narrowly until each layer reports one real number, not writing something in its place to paper over the ambiguity.

Dev Mode's Export Isn't a Drop-In

A generated CSS snippet is scoped to the one instance selected, at the one width the frame happens to be. It won't reference the project's actual token names, won't include the states that aren't currently selected, and won't say anything about what happens outside that width. Treat it as a fast way to confirm a value, not as code to paste directly into a component.

The same caution applies to anything Dev Mode exports as a snippet, not just raw values. Pasting an entire generated CSS block copies whatever structural choices produced the file's current layer tree, including the spacer layers and wrapper frames covered above, straight into the codebase.

Figma Variables as Design Tokens

A Figma variable, a design token, and a CSS custom property describe the same value at three different points in its life, and the mapping between them isn't guaranteed to be 1:1.

A Figma variable is a named value, color, number, string, or boolean, that can be swapped per mode, such as a light and dark theme or a set of regional brands, without touching every layer that references it. Functionally, it's the same idea a design token is built around: define a value once, reference it everywhere, change it in one place. The token itself is the semantic layer worth keeping stable. A CSS custom property is one common way to expose that token in code, not the only one, and a token system built on a plain object or a theming library follows the same pipeline without a CSS variable ever entering the picture.

The three stages don't map onto each other one to one in practice. A designer might define a Figma variable purely to make a file easier to maintain, a spacing value used in exactly one layout, that never needs to exist as a token because no other component references it. In the other direction, a codebase often has tokens with no Figma equivalent at all, a z-index scale or an animation-duration set, because they solve a purely implementation-level problem a static design file was never going to specify. Expecting every variable to become a token, or every token to trace back to a variable, is the same mistake as expecting a Figma frame's layer tree to become the DOM directly.

How these tokens actually get organized once they exist in code, tiers of variables, theming, and the tooling that keeps a token's name and its type in sync, is covered in CSS at Scale. What matters on the Figma side is naming a variable to match the token it's meant to become before implementation starts, so the mapping is a lookup instead of a negotiation.

What Auto-Layout Doesn't Capture

Auto Layout describes how elements relate to each other at one width. It doesn't say what happens at any other width, because it was never asked to.

A 16-pixel gap that Auto Layout maintains between two elements is a real, useful fact about the relationship between them. It says nothing about whether that gap should shrink at 375 pixels wide, whether the two elements should stack instead of sitting side by side, or whether one of them should disappear entirely. Auto Layout keeps recalculating the same relationship at whatever width the frame is resized to, which can look like responsive design inside the editor without actually specifying any of the decisions responsive design requires.

Most Figma files show two or three representative widths for a given screen, not a continuous range. Whatever happens between those points, and past the narrowest or widest one shown, is a decision that gets made during implementation whether or not anyone consciously makes it. Treating the widths that were drawn as the full set of breakpoints a product needs is a common enough shortcut that it's worth naming directly: a design file's breakpoints are examples of where the layout was checked, not a specification of every width it needs to hold up at.

One Frame's Measurements Aren't a Responsive Spec

A component that looks correct at the one width its frame was drawn at can still be missing every decision that matters at the widths nobody checked. Confirming behavior at the extremes, not just the one width in the file, is implementation work a design file can't do on its own.

The same limitation applies to content, not just width. A frame showing a name field filled with a short example name says nothing about what happens at forty characters. A list shown with five items says nothing about what a product does with fifty, or with none. Localization multiplies this problem rather than introducing a new one: a string that fits comfortably in English routinely runs thirty percent longer in German, and a layout that only holds up around the one example string it was built with was never actually specifying a layout, just describing what that particular string looked like.

States a Static Frame Can't Show

A frame renders one state. The others still have to exist somewhere before code can be written against them.

A single interactive component can pass through default, hover, focus, active, disabled, loading, and error states, and the six-state matrix that matters for implementation, along with the case for reaching for a native control to get several of them for free, is covered in full in Interaction States and Feedback. What's worth adding here is where those states live, or fail to live, inside the file itself. A well-maintained design system ships each state as its own labeled variant, so the states exist as artifacts before a single line of code gets written. A file built under deadline pressure more often shows only the default, and the rest get inferred from a component library's existing patterns, or requested from the designer directly once the gap is noticed.

Focus is the state most likely to be missing entirely, rather than just unshown. Hover is usually visible somewhere in an existing design system. Focus often isn't, in part because a mouse-driven design tool has no native way to trigger it. A frame with no visible focus treatment isn't a decision that focus should look like hover, it's usually a state nobody got around to designing at all. The visible indicator itself, and the accessibility tree it plugs into, is covered in Accessibility as an Architecture Decision.

The Handoff Conversation

Most of what a static file can't answer gets resolved fastest by asking, not by guessing and hoping the guess survives review.

Not every gap needs a new frame. A reasonable default, extrapolated from how the rest of the design system already handles the same situation, resolves most of these faster than waiting on a design change. What's worth protecting is the habit of noticing the gap in the first place, since an unnoticed gap doesn't get a default, it gets whatever the implementation happened to produce.

  • Behavior — What does this look like while it's loading, and what happens on screen if the action fails outright?
  • Behavior — Is this update optimistic, applied immediately and rolled back on failure, or does it wait for confirmation first?
  • Layout — What happens at the widths this file doesn't show, particularly the narrowest one a real user might actually have?
  • Layout — What does this look like with no content in it at all?
  • Content — What's the longest realistic value this label or field needs to hold, not just the one used in the mock?
  • Content — Does this string still fit once it's translated, and does the layout assume a length that won't hold in every locale?
  • Interaction — Does this work end to end from a keyboard alone, with a visible focus indicator at every step?
  • Interaction — What replaces this on a touch device, if the design depends on hover to reveal it?

None of these questions require design training to ask, and most of them take less time to raise than to implement a guess and unwind it later. What they require is treating the file in front of a developer as one instance of the interface, worth reading carefully, and not the whole specification of it.
