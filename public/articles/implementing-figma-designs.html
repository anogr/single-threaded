Implementing Figma Designs

How to read frames, variants, variables, and inspected values as evidence for production markup, components, and styles.

Andreas Ögren
~13 min read
Last updated August 2026

Implementing a Figma design means recovering the rules behind the screens, states, and values shown in the file.

Figma is an interface design and prototyping tool that product teams use to work through the structure and appearance of an interface. Designers arrange screens in a workspace, compose them from reusable interface parts, and connect screens to demonstrate a flow. The work is saved in a Figma file and presented to developers so that they can implement that interface. During handoff, the developer can examine how the design is structured, which parts are reused, and which layout or visual values were applied. The file therefore communicates more than a screenshot.

The file still shows the interface through selected examples. A button that measures 140 pixels may have a fixed width, or it may have grown around the label in that example. A screen may show five links in a navigation menu, but it does not tell the developer whether every user sees the same links or if permissions determine which links appear. In both cases, the visible result may come from a fixed product rule or from the content and state used in the example. Implementation requires the rule, not only the example.

Teams can publish reusable design assets in a Figma library so that many files use the same decisions. Production applications need corresponding code components and tokens rather than the design assets themselves. Design Systems explains the contract between those representations. This article concentrates on reading a Figma file during handoff and deciding what its contents mean for production code.

Reading a Figma File

A Figma file organizes design work into pages. Each page contains the objects that make up screens and reusable interface parts.

A Figma file is a saved design document. A file can contain several pages, which designers use to separate areas such as current screens, early explorations, and component documentation. Each page provides a canvas, which is the workspace on which design objects are placed. Every object on that canvas is a layer, including text, shapes, images, and frames. The Layers panel displays those objects as a hierarchy.

A frame is a container with its own dimensions and layout properties. A frame might represent a complete screen, a region within a screen, or the boundary of a reusable interface part. Frames can nest, which produces the hierarchy shown in the Layers panel. A group keeps several layers together for selection and movement, while a frame can define how its children are sized and arranged.

Figma and the browser use hierarchies for different purposes. Figma's design workspace is optimized for composing, comparing, and reviewing visual states on a canvas. Its layers reflect what a designer needs to select, position, reuse, or annotate. HTML describes the meaning and relationships of content and controls. CSS lays those elements out from rules that respond to content and available space, while application code supplies data and behavior. A Figma frame may resemble a DOM subtree, but the two structures answer different questions.

Auto Layout arranges a frame's child layers using a vertical, horizontal, or grid flow. Figma currently labels grid flow as an open beta. Auto Layout records the gap between children, the padding inside the frame, and how the children are aligned. Its resizing settings describe whether a layer keeps a fixed dimension, hugs its contents, or fills the space offered by its parent.

Horizontal and vertical flows often suggest flexbox, while grid flow may suggest CSS grid. The visual match is not enough to choose an algorithm. The code needs to preserve the intended relationship as content and available space change. For example, a horizontal Auto Layout frame with a 16-pixel gap and children that hug their contents closely resembles display: flex with gap: 16px. The resemblance gives the developer a starting point. The implementation must still determine whether the row wraps, how small each child can become, and whether the gap changes with the available space.

Figma represents reusable structure through components. A component is the reusable definition, while an instance is a placed copy that exposes selected properties for customization. A component set groups related versions of a component. Each version is a variant, identified by property values such as size or state. A Figma library makes published components and other shared design assets available for reuse in other files. These concepts resemble component definitions, rendered instances, and props in code, but their boundaries do not match every frontend framework exactly.

A prototype adds interactions that connect frames or change properties in response to an action. For example, a designer can connect a Continue button to a confirmation frame so reviewers can step through the intended flow. The prototype communicates navigation and interaction ideas, but it does not run the application's data access, validation, permissions, or error handling.

Because the layer tree records visual composition rather than document semantics, some layers do not need a DOM element. A spacer rectangle becomes a gap in CSS, and a frame used for alignment may disappear when its relationship can be expressed on the parent. Keep a wrapper only when it represents a meaningful group, layout boundary, or reusable component.

The Layers panel does not tell a developer which HTML element to use. A control that performs an action belongs in a native <button>, even if the design represents it as a rectangle and a text layer. The HTML should describe what the control means and does, while CSS reproduces its layout and appearance.

Variants and Component Props

Variant properties are evidence for a component API, but their names and combinations still need to be interpreted.

A Figma component property may describe one mutually exclusive choice. If a component has small, medium, and large sizes, a string union can express that choice in code. Other properties may control independent conditions or editable content. Combining every Figma property into one variant prop hides those distinctions and makes invalid combinations easier to create.

Figma may show default, hover, disabled, and loading as separate variants so each appearance can be inspected. A literal translation produces values such as primary-loading and secondary-disabled, causing the union to grow with every combination. In code, hover normally comes from the browser's interaction state, while disabled and loading belong to component state, and primary and secondary describe the button's visual role.

button.tsx TSX 
// One visual role and two independent state conditions.
type ButtonProps = {
  variant: 'primary' | 'secondary';
  disabled?: boolean;
  loading?: boolean;
};

Separating the component's visual role from temporary states keeps the prop model understandable as the component grows. The exact API depends on which combinations are valid and whether the component or its caller owns each state. React Patterns & Component Design explains how a code component can enforce those boundaries.

Name Variants by Intent, Not Appearance

Names such as primary and secondary describe the choice a caller makes. Names such as blue and gray bind that choice to the current palette and become misleading when the theme changes. The component prop should preserve the semantic distinction, while the component and its tokens determine the appearance. Design Systems applies this separation to token architecture.

Dev Mode and the Inspect Panel

Inspection provides exact values for the selected object. It does not decide which values are rules, tokens, or measurements of one instance.

Dev Mode provides a developer-focused view of a Figma file. For a selected object, the Inspect panel exposes layout, spacing, colors, applied styles and variables, and prototype interactions where they apply. The panel can show autogenerated code whose language and output depend on the selected settings and code-generation plugins.

Each reported value still needs interpretation. A 24-pixel gap may be the resolved value of spacing.lg, and a fill may come from a semantic color variable. Dev Mode can expose applied variables and suggest matching variables for some raw values. When the project already has a token, its name should be used instead of copying the resolved number and creating a second source of truth.

A reported dimension may describe a fixed rule or the result of a resizing rule. A layer that measures 200 pixels may have a fixed width, or it may use Fill container inside a parent that happens to be 200 pixels wide. Hug contents, Fill container, fixed dimensions, and minimum or maximum constraints reveal how the layer should behave beyond the selected frame.

Generated Code Needs Interpretation

Generated code describes the current selection and context. It may include Figma variables, but it does not know the application's architecture, responsive rules, or unselected states. Generated code can be used to inspect how Figma resolved a property, but the intended behavior should be expressed through the codebase's components and tokens.

A generated snippet may reproduce a spacer as an empty element or fix a width that Figma resolved from Fill container. Copying either choice would turn a canvas detail into application behavior. Each declaration should be reviewed against the component's layout, responsive behavior, and existing token system.

Figma Variables as Design Tokens

A shared color, spacing value, or other design decision may need a corresponding name in the design file, token source, and production stylesheet.

A Figma variable stores a color, number, string, or boolean value. Variables are organized into collections, and each collection can have modes that provide context-specific values, such as light and dark themes. A variable can refer to another variable of the same type through an alias.

A design token gives a design decision a stable name that tools and platforms can share. A Figma variable may be the design representation of that token. Production code may receive the token as a CSS custom property, a TypeScript value, or another platform-specific format.

This mapping does not establish one universal source. A team may generate both Figma variables and CSS custom properties from token files. Another team may own selected values in Figma and export them to code. In either workflow, the team must name the canonical owner and define how the other representations stay synchronized.

The lists do not have to match one to one. A Figma file may contain a variable for a design-tool concern, such as a debugging grid, that production code never uses. Production code may need a token for a concern the design file does not model, such as stacking order. A value belongs in the shared token system when several tools or platforms need to agree on its meaning.

During handoff, a shared semantic name lets the developer trace a design value to an existing token instead of introducing another raw number. Design Systems explains token tiers and generated outputs, while Design System Governance explains canonical ownership and compatibility.

Responsive Rules Beyond Auto Layout

Auto Layout can model resizing and reflow, but it only communicates the responsive decisions that someone explicitly encoded and checked.

A 16-pixel gap records a relationship between two elements. On its own, it does not say whether the gap changes on a narrow screen or whether the elements should wrap, stack, or disappear. Auto Layout supports responsive behavior, including wrapping, grid flow, and size constraints. Those capabilities only help when the file uses them to express the intended transition.

A file may show a few representative widths rather than every point in a continuous range. Those frames show where someone reviewed the layout. They do not necessarily identify the widths where the implementation should change. Test between and beyond the examples to find where the current layout stops working, then decide which existing or new responsive rule should handle that transition. Layout, Spacing, and Sizing explains whether the design system, page shell, or component should own the rule.

A Failure Point Does Not Define the Rule's Scope

Content collisions or unusable controls show that the layout needs to change. First check whether a shared viewport breakpoint or layout primitive already defines that change. Use a component-specific container threshold when the component owns the transition and must adapt across different placements. The width of a supplied frame does not establish either rule.

Width is not the only variable that can break the layout. A short name does not reveal how a longer name should wrap or truncate, and a frame with five list items does not show how the component handles an empty or much longer list. Translated strings add another source of variation, but no single language provides a reliable worst case. Realistic content extremes can be used to test and decide which content may wrap, truncate, scroll, or change the surrounding layout.

Unspecified Interaction States

A frame renders one state, while component code must define every state that a user can reach.

A component may pass through default, hover, focus, active, disabled, loading, and error states. Interaction States and Feedback explains what those states mean in the finished interface. In Figma, they may appear as variants, prototype interactions, documentation, or examples in a library. If the file shows only the default, the implementation should follow an established component pattern or ask for the missing behavior rather than inventing each state independently.

A static frame often omits focus because focus appears while a person moves through the working interface with a keyboard. If the file does not show a focus treatment, do not remove the browser's indicator or substitute the hover style. Confirm the intended treatment and preserve a visible indicator. Accessibility as an Architecture Decision covers the underlying keyboard and semantic requirements.

The Handoff Conversation

Handoff should identify what the file specifies, what an existing component or product rule supplies, and what the team still needs to decide.

For each missing decision, start with the existing code component and design-system guidance. When an existing contract answers the question, it can be recorded as the source of the behavior. Otherwise, the designer, developer, and product owner need to decide what the product requires. Without an explicit answer, the implementation may inherit a browser or library default that nobody reviewed.

  • Behavior: What appears while the action is loading, and what replaces it if the action fails?
  • Behavior: Is this update optimistic, applied immediately and rolled back on failure, or does it wait for confirmation first?
  • Layout: What happens between the widths shown in the file and at the narrowest supported width?
  • Content: What appears when there is no content?
  • Content: What is the longest realistic value this label or field must hold?
  • Content: How does the layout handle translated strings of different lengths?
  • Interaction: Does this work end to end from a keyboard alone, with a visible focus indicator at every step?
  • Interaction: What replaces this on a touch device, if the design depends on hover to reveal it?

The answers create a shared interpretation of the interface. The file remains essential evidence, while the full specification combines that evidence with product rules, component conventions, content requirements, and accessibility behavior.
