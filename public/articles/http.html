HTTP

How the protocol behind every web interaction works, from methods and status codes to caching, cookies, CORS, and the evolution from HTTP/1.1 to HTTP/3.

Deep dive
~24 min read
Web fundamentals
June 2026

Every browser request, API call, and webhook delivery travels over the same protocol. Understanding it removes a layer of mystery from almost everything on the web.

HTTP (Hypertext Transfer Protocol) is the application-layer protocol that powers communication on the web. It operates on a simple model. A client sends a request, and a server sends back a response. That's it. Every browser page load, API call, and file download is one or more of these exchanges.

A request consists of a method (what action to perform), a URL (which resource), headers (metadata), and an optional body (data). A response consists of a status code (what happened), headers, and an optional body. In its plaintext form, a basic exchange looks like this.

# Request
GET /articles/http HTTP/1.1
Host: example.com
Accept: text/html
# Response
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 4821
 
<!DOCTYPE html>…

HTTP is stateless: each request is self-contained. The server has no memory of previous requests from the same client. State that needs to persist across requests (authentication, sessions, preferences) must be carried explicitly, typically in headers or cookies.

A Brief History

HTTP has gone through four major versions. Each solved a specific bottleneck of the one before it.

1991 · 1996
HTTP/0.9 & HTTP/1.0

HTTP/0.9 was a single line, just a GET request and plain HTML back. HTTP/1.0 introduced headers, status codes, and support for content types other than HTML. Each request required its own TCP connection, which was expensive.

1997
HTTP/1.1

Added persistent connections (reuse the same TCP connection for multiple requests), chunked transfer encoding, and mandatory Host headers (which enable virtual hosting). HTTP/1.1 ran the web for nearly two decades and remains widely supported.

2015
HTTP/2

Binary framing and multiplexing allow multiple requests over a single connection at the same time, with header compression via HPACK. This eliminated the need for many HTTP/1.1 performance workarounds like domain sharding and inlining assets.

2022
HTTP/3

Replaced TCP with QUIC, a UDP-based transport developed by Google. Eliminates TCP-level head-of-line blocking, supports connection migration across networks, and has faster connection setup with built-in TLS 1.3.

HTTP/1.1 is still everywhere. HTTP/2 is now the default for most browsers and servers. HTTP/3 adoption is growing rapidly. Today it handles a significant share of web traffic. More on the differences in the HTTP/2 & HTTP/3 section.

Methods

A method declares the intended action. Choosing the right one is not just convention, since it affects caching, retry behavior, and how intermediaries treat the request.

HTTP defines a small set of methods, each with a specified semantic. Two properties matter most. A method is safe if it has no side effects (calling it must not change server state). A method is idempotent if calling it multiple times produces the same result as calling it once. Safety implies idempotency, but not the reverse.

GET Retrieve a resource. Safe and idempotent. Must not modify state. Responses may be cached by browsers and intermediaries. The body is ignored by most servers.
POST Submit data for processing. Neither safe nor idempotent. Used to create resources, trigger operations, or submit forms. The server decides what to do with the body.
PUT Replace a resource entirely. Idempotent but not safe. The client provides the complete new representation. Repeated calls produce the same result.
PATCH Apply a partial update. Not idempotent by default (though specific patch formats can be). The body describes changes, not a full replacement.
DELETE Remove a resource. Idempotent in effect: the server state after repeated calls is the same, whether the resource existed or not.
HEAD Same as GET, but returns only headers. Useful for checking whether a resource exists or has been modified without downloading the body. Safe and idempotent.
OPTIONS Describe the communication options for a resource. Used by browsers to issue CORS preflight requests before a cross-origin request. Safe and idempotent.
QUERY Run a query with a request body, safely. 2026 Safe and idempotent, like GET, but carries a body, like POST. Defined in RFC 10008 for queries too large or too structured to fit in a URL.

Why do these properties matter in practice? Caches only store GET and HEAD responses. Browsers and proxies may automatically retry safe and idempotent requests after a network failure, but they will not retry a POST (which could charge a card or create a duplicate order). Middleware, load balancers, and API gateways all make decisions based on the method. Using GET for something that modifies state, or POST for something safe, breaks these assumptions.

The QUERY Method 2026

A method that closes a long-standing gap between GET and POST: a request body with the safety and cacheability guarantees of a read.

Search and filter operations often need more structure than a URL comfortably holds, such as nested filters, long lists of IDs, or a full-text query alongside facets and pagination. The usual way to express this is a query string.

GET /feed?q=foo&limit=10&sort=-published HTTP/1.1
Host: example.org

This works until the query grows past what a URL can carry comfortably. Intermediaries along the path don't all agree on a size limit, so there's no safe upper bound to design around. Structured data is awkward to encode as a flat string of characters. Query strings also end up in server logs, browser history, and bookmarks, which is unwelcome when the query itself contains something sensitive. And every distinct combination of parameters is technically a different URL, which defeats caching strategies that expect a stable set of resources.

The common workaround is to send the query as a POST body instead.

POST /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
 
q=foo&limit=10&sort=-published

This solves the size and encoding problem, but it introduces a new one. Nothing about a POST request tells a cache, proxy, or client library that the operation is actually safe and repeatable. POST is defined as neither safe nor idempotent, so intermediaries won't cache the response or retry it automatically after a dropped connection, even though this particular POST is just a read.

RFC 10008, published by the IETF in June 2026 as a Proposed Standard, defines a new method to sit in the gap, called QUERY. The request looks almost identical to the POST version above, but the method name tells every intermediary along the way that the operation is safe and idempotent, the same guarantee GET carries.

QUERY /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
 
q=foo&limit=10&sort=-published
HTTP/1.1 200 OK
Content-Type: application/json

The request content and its Content-Type together define the query. A server must reject the request if Content-Type is missing or doesn't match the body, since there's otherwise no way to know how to interpret it. The examples above use application/x-www-form-urlencoded because it's familiar, but QUERY doesn't prescribe a format. A resource can just as well accept application/sql, a GraphQL document, or a JSON body describing filters, as long as client and server agree on what it means.

GETQUERYPOST
Safeyesyesnot guaranteed
Idempotentyesyesnot guaranteed
Cacheableyesyesonly for the resulting GET/HEAD, not the POST itself
Bodyno defined meaningdefines the querydefines the operation

Because a cache can no longer key purely on the URL (two QUERY requests to the same URL with different bodies are different queries), servers that want QUERY responses cached correctly need to return a Vary header covering the request content, and caches need to support keying on it. This is a bigger change for HTTP cache implementations than it looks, and it's the main reason adoption is expected to be gradual, since the method existing in the spec doesn't mean every proxy, CDN, and client library handles it yet.

A server can advertise which query formats it accepts with the new Accept-Query response header, similar in spirit to how Allow advertises accepted methods.

Accept-Query: application/x-www-form-urlencoded, application/sql

As of today, QUERY is a Proposed Standard rather than an established convention. Expect to see it first in API frameworks and HTTP client libraries that add explicit support, with broad browser and intermediary support following over time, the same adoption curve every new method has followed.

Status Codes

The three-digit status code is the server's top-level answer to the request. The first digit indicates the class of outcome.

There are five classes. Most of what appears in practice falls into 2xx, 4xx, and 5xx. 3xx matters for redirects and caching. 1xx is mostly invisible, handled by the browser.

2xx · Success

200OK: The request succeeded. The response body contains the result.
201Created: A resource was created. Should include a Location header pointing to it.
202Accepted: The request was received but processing is not yet complete. Used for async operations.
204No Content: Succeeded with no body to return. Common for DELETE and some PATCH responses.

3xx · Redirection

301Moved Permanently: The resource lives at a new URL. Clients should update stored links.
302Found: Temporary redirect. The original URL remains valid.
304Not Modified: The cached version is still valid. No body returned. Used with conditional requests.
307Temporary Redirect: Like 302, but the original HTTP method must be preserved.
308Permanent Redirect: Like 301, but the original HTTP method must be preserved.

4xx · Client Error

400Bad Request: The request is malformed or contains invalid syntax.
401Unauthorized: Authentication is required but was not provided, or credentials are invalid. Despite the name, this means unauthenticated.
403Forbidden: The client is authenticated but does not have permission. The distinction from 401 matters: a 403 tells the client that authenticating differently won't help.
404Not Found: The resource does not exist at this URL. Sometimes returned intentionally in place of 403 to conceal existence.
409Conflict: The request conflicts with the current resource state, for example, a duplicate creation or a failed optimistic concurrency check.
422Unprocessable Entity: The request is syntactically valid but semantically incorrect. Typically used for domain validation failures.
429Too Many Requests: Rate limit exceeded. Should include a Retry-After header.

5xx · Server Error

500Internal Server Error: Something went wrong on the server. A catch-all for unhandled failures.
502Bad Gateway: An upstream server returned an invalid response. Common when a reverse proxy cannot reach the backend.
503Service Unavailable: The server is temporarily unable to handle requests. Should include a Retry-After header.
Error response bodies

HTTP status codes communicate the class of error, but not the detail. RFC 9457 (Problem Details for HTTP APIs) defines a standard JSON format for error bodies: a type URI identifying the error kind, a title, a status mirroring the code, and a human-readable detail. Use Content-Type: application/problem+json when returning this format.

Headers

Headers carry metadata about the message, the sender, the content, and the desired behavior. They are the control plane of HTTP.

Headers are key-value pairs sent before the body in both requests and responses. They control how the message is interpreted, what content is acceptable, how long a response can be cached, and who is allowed to read it. Header names are case-insensitive. Values are case-sensitive where the spec says so.

Content negotiation

HTTP has a built-in mechanism for clients and servers to agree on representation format. The client expresses what it can handle in the Accept header. The server responds with the chosen format in Content-Type. The same mechanism applies to encoding (Accept-Encoding / Content-Encoding) and language (Accept-Language / Content-Language).

# Client signals it prefers JSON but accepts anything
Accept: application/json, */*;q=0.8
 
# Server confirms what it actually sent
Content-Type: application/json; charset=utf-8

The q parameter (quality value) expresses preference on a 0–1 scale. application/json without a q value defaults to 1.0 (highest preference). This mechanism also underpins versioning via Accept headers and content-type-specific error formats like application/problem+json.

Caching

Caching is one of the most impactful and most misunderstood parts of HTTP. A well-cached API or site is dramatically faster. A badly cached one serves stale data or bypasses caching entirely.

HTTP caching works by storing responses and serving them without contacting the origin server. There are two kinds of cache to reason about, the private cache in the browser (one user's responses) and shared caches like CDNs and reverse proxies (responses served to many users). They behave differently and must be controlled independently.

Cache-Control

The Cache-Control header is the primary mechanism for controlling caching behavior. It appears in both responses (server instructs caches) and requests (client instructs intermediaries). The most important response directives follow.

DirectiveMeaning
max-age=NCache the response for N seconds from the time it was received
no-cacheCache the response, but always revalidate with the server before using it
no-storeDo not store the response at all (for sensitive data)
privateOnly the browser may cache this, CDNs and shared proxies must not
publicAny cache may store this, including CDNs
s-maxage=NLike max-age but applies only to shared caches
stale-while-revalidate=NServe a stale response for up to N seconds while fetching a fresh one in the background
immutableThe response will never change, skip revalidation even on explicit reload
no-cache does not mean "don't cache"

Cache-Control: no-cache means "store this, but check with the server before using it." To prevent storage entirely, use no-store. This is one of the most common sources of caching confusion.

A typical pattern for static assets with content-hashed URLs is Cache-Control: public, max-age=31536000, immutable, which caches forever and never revalidates, because the filename changes when content changes. For API responses that vary per user, Cache-Control: private, max-age=60 allows short-lived browser caching without exposing data to a shared cache.

Conditional requests and ETags

Once a cached response expires, the client can ask the server whether it has changed rather than fetching the full content again. The server includes an ETag (a version token, a hash or revision number) in the original response. On revalidation, the client sends that token in an If-None-Match header. If the resource hasn't changed, the server returns 304 Not Modified with no body, and the client uses its cached copy.

# First request, server returns content with a version token
GET /products/42
200 OK
ETag: "d4f8a2"
Cache-Control: max-age=300
# After 5 minutes, client revalidates
GET /products/42
If-None-Match: "d4f8a2"
304 Not Modified (no body, saves the bandwidth)

ETags are also used for optimistic concurrency in APIs. A client that wants to update a resource sends its ETag in an If-Match header, and the server rejects the update with 412 Precondition Failed if the resource has changed since the client last fetched it. This prevents last-write-wins data loss when multiple clients edit the same resource.

Cookies

Cookies are how HTTP bridges its own statelessness. They are the mechanism for sessions, preferences, and authentication state that persists across requests.

A cookie is a small piece of data the server sends to the browser in a Set-Cookie header. The browser stores it and includes it automatically in every subsequent request to that origin in the Cookie header, with no code required on the page.

# Server sets a cookie after login
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
 
# Browser sends it on every subsequent request to this origin
Cookie: session_id=abc123

Cookie attributes

The attributes attached to a cookie control how and when the browser sends it, and who can access it.

AttributeEffect
HttpOnlyJavaScript cannot read this cookie. Protects session tokens from XSS attacks, since a script that can't access the token can't steal it.
SecureThe cookie is only sent over HTTPS connections. Required for any cookie carrying sensitive data.
SameSiteControls when the cookie is sent on cross-site requests (see below).
Max-Age / ExpiresHow long the cookie lives. Without these, it is a session cookie, deleted when the browser closes.
PathLimits the cookie to a URL path prefix. Rarely needs to differ from /.
DomainExtends the cookie to subdomains. Omitting it scopes the cookie to exactly the origin that set it.

SameSite

Cookies were never covered by the same-origin policy. The browser decides whether to attach a cookie based only on the request's destination, not on who triggered the request or where they triggered it from, which is exactly the gap CSRF exploits. SameSite is what lets a server opt out of that default. It governs whether a cookie is sent when the request originates from a different site, for example, when a user clicks a link from one site that takes them to another, or when JavaScript on one site makes a request to another.

The attribute takes three values:

  • SameSite=Strict: the cookie is never sent on cross-site requests, even top-level navigations.
  • SameSite=Lax (the browser default since around 2020): sends the cookie on a cross-site request only if it's a top-level navigation using a safe method. Clicking a link is the common case. A cross-site POST, whether it's a form that navigates the page or a request made in the background by JavaScript, an image, or an iframe, doesn't qualify and gets no cookie.
  • SameSite=None: allows the cookie on all cross-site requests, but requires Secure, and it's the only setting that works with CORS requests that include credentials.
SameSite and CORS credentials

If an API relies on cookies for authentication and is called from a different origin, the cookie must be SameSite=None; Secure, the CORS response must include Access-Control-Allow-Credentials: true, and the client must set credentials: 'include' in the fetch call. All three are required.

Redirects

Redirects tell the client to look elsewhere. The choice of status code controls whether the redirect is permanent, temporary, and whether the HTTP method is preserved.

When a server responds with a 3xx status code and a Location header, the browser automatically makes a new request to that URL. For 301 and 302, browsers historically changed the method of the follow-up request to GET even if the original was POST. 307 and 308 were introduced specifically to prevent that.

Permanent
301 & 308

301 is a permanent redirect. The browser may change POST to GET on follow-up. 308 is the same but preserves the method. Both signal that the client should update stored URLs, and both are cached indefinitely by default.

Temporary
302 & 307

302 is a temporary redirect, method may change to GET. 307 preserves the method. Neither is cached by default. The original URL remains valid and should be used next time.

Reload & Resubmission

Reloading a page and reissuing its last request are the same thing to a browser. That's fine after a GET, but not always after a POST.

Reloading a page replays the request that produced it. If the last request was submitting a form, the replayed request will be a POST. Since POST is neither safe nor idempotent (see Methods above), replaying one can repeat a side effect like placing a duplicate order. F5 and Ctrl+F5 both re-invoke the same history entry with its original method and body, so either one triggers a "Confirm Form Resubmission" prompt on a POST-loaded page. Hard refresh only changes whether the cache is bypassed, not what gets resent. Enter in the address bar avoids the prompt because it starts a fresh navigation, and a typed navigation is always a GET.

ActionRepeats method & bodyResubmission warning
F5 / Ctrl+Ryesyes, if the entry was a POST
Ctrl+F5 / Ctrl+Shift+Ryes (cache bypassed)yes, if the entry was a POST
Enter in address barno, always GETno

Post-Redirect-Get

The fix is to never leave a POST as the current history entry. The server processes the POST, then responds with 303 See Other (see Redirects above) pointing to a result URL. The browser follows it with a GET, and it's that GET, not the POST, that any later reload replays.

POST /orders → form submission
303 See Other
Location: /orders/a3f9b2c1
GET /orders/a3f9b2c1 → browser follows automatically
200 OK

Compression

HTTP response bodies are compressed in transit. For text content, this typically reduces payload size by 70–90% with no effort from application code.

The client advertises the encodings it supports in the Accept-Encoding request header. The server picks one, compresses the body, and indicates the chosen encoding in the Content-Encoding response header. The client decompresses transparently.

Accept-Encoding: br, gzip, deflate
Content-Encoding: br

Gzip is universally supported and produces good compression. Brotli (br) achieves better compression ratios, typically 15–25% smaller than gzip for text, and is supported by all modern browsers. Servers should prefer Brotli when the client supports it. Compression is most valuable for text (JSON, HTML, CSS, JavaScript) and should generally be skipped for binary formats like images and video, which are already compressed.

In most deployment environments (NGINX, Caddy, cloud load balancers, CDNs), compression is configured at the infrastructure level and requires no application code.

File Uploads

Uploading files over HTTP is common but slightly awkward. There are two distinct approaches, and choosing the wrong one creates friction.

multipart/form-data

HTML forms use multipart/form-data when they include file inputs. The request body is divided into named parts separated by a boundary string, each with its own headers. This format can mix file data with regular text fields in a single request, which is natural for form submissions.

POST /uploads
Content-Type: multipart/form-data; boundary=----Boundary7MA4YWxk
 
------Boundary7MA4YWxk
Content-Disposition: form-data; name="description"
 
Product photo
------Boundary7MA4YWxk
Content-Disposition: form-data; name="file"; filename="photo.jpg"
Content-Type: image/jpeg
 
[binary data]
------Boundary7MA4YWxk--

Binary PUT

For APIs that upload a single file, PUT with the raw binary body is simpler and more efficient. There's no multipart overhead, the Content-Type describes the file directly, and the URL identifies where the file should live. This approach is used by object storage APIs like S3.

PUT /files/profile-photo.jpg
Content-Type: image/jpeg
Content-Length: 48291
 
[binary data]

A common architecture for large files skips uploading through the application server entirely. The client requests a short-lived pre-signed URL from the API, then uploads directly to object storage, so the application server never touches the binary data and storage scales independently.

CORS

Browsers block cross-origin requests by default. CORS is the mechanism that lets servers selectively open that boundary.

The same-origin policy

Browsers enforce a same-origin policy that prevents JavaScript on one origin to read responses from a different origin. An origin is the combination of scheme, host, and port (https://app.example.com:443 is a different origin from https://api.example.com:443, even though they share the same domain). For more information, see the same-origin policy and CORS section of the browser security article.

Relaxing the policy

CORS (Cross-Origin Resource Sharing) is the mechanism a server uses to relax the same-origin policy for a trusted origin so that JavaScript is allowed to read the responses. The mechanism differentiates between simple and non-simple requests. Simple requests are sent directly, with no permission asked in advance. They cover GET, HEAD, or POST with a limited set of content types, such as text/plain or application/x-www-form-urlencoded. The browser sends the request and checks the response headers afterward to decide whether JavaScript may read the result. Content-Type: application/json is not on that list, so a JSON request triggers a preflight instead.

Preflight requests

Anything beyond a simple request (a custom header, a JSON body, a method like PUT or DELETE) requires the browser to check first. It sends an OPTIONS request asking the server whether it allows this origin, method, and headers, and only sends the real request if the response says yes.

# Browser asks permission first
OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization
204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
# Browser sends the actual request
POST /orders
Origin: https://app.example.com
Content-Type: application/json

Access-Control-Max-Age caches the preflight result so the browser doesn't have to repeat it on every request. Set it to a reasonably high value (86400 seconds = 24 hours) for endpoints that don't change.

Credentials

By default, cross-origin requests do not include cookies or the Authorization header. The browser strips them. To send credentials, three things must align:

  • The server must respond with Access-Control-Allow-Credentials: true.
  • The server must also specify a concrete origin in Access-Control-Allow-Origin, since the wildcard * is not allowed when credentials are involved.
  • The client must opt in with fetch(url, { credentials: 'include' }).

Access-Control-Expose-Headers

By default, JavaScript can only read a small set of "safe" response headers, such as Content-Type and Content-Length. Other headers, including ETag, Location, and any custom headers, are hidden even if the request is permitted by CORS. To expose them, the server must list them explicitly.

Access-Control-Expose-Headers: ETag, Location, X-Request-Id
CORS is a browser constraint

CORS headers only affect browser JavaScript. curl, server-to-server calls, and tools like Bruno and Postman are not bound by the same-origin policy and will receive responses regardless of CORS headers. If an API call works in curl but not in the browser, CORS configuration is the first thing to check.

HTTP/2 & HTTP/3

Both versions solve performance problems that HTTP/1.1 couldn't address. They solve different problems at different layers of the network stack.

HTTP/2: multiplexing over TCP

HTTP/1.1 processes one request at a time per TCP connection. To work around this, browsers open up to six parallel connections per host, a hack that adds overhead and still limits parallelism. HTTP/2 replaces the text-based request/response format with a binary framing layer built around streams, multiple logical request/response exchanges multiplexed over a single TCP connection simultaneously. A slow response no longer blocks others in the queue.

HTTP/2 also compresses headers with HPACK, which matters because headers (including cookies) are repeated in full on every HTTP/1.1 request. The result is fewer connections, lower latency, and less need for the bundling and inlining tricks that HTTP/1.1 performance optimization required.

Server push, where the server could proactively send resources the client hadn't requested yet, was part of HTTP/2 but never saw wide adoption. Chrome removed support for it in 2022.

HTTP/3: QUIC over UDP

HTTP/2 multiplexing over TCP has a residual problem. TCP is a single ordered byte stream. When a packet is lost, TCP stalls the entire connection while waiting for retransmission, even streams that had no packet loss are blocked. This is TCP-level head-of-line blocking, and multiplexing can't fix it because multiplexing happens above the TCP layer.

HTTP/3 solves this by replacing TCP with QUIC, a transport protocol built on UDP that implements reliability and flow control per stream. A lost packet only affects the stream it belongs to. QUIC also bakes in TLS 1.3, enables connection migration (a connection survives a network change, such as switching from WiFi to mobile), and supports 0-RTT resumption for known servers.

HTTP/2 and HTTP/3 are mostly infrastructure concerns. Negotiation happens transparently via TLS ALPN during the handshake. The negotiated version can be inspected in the browser DevTools Network panel, in the Protocol column. Support for HTTP/3 depends on the server software and hosting environment, not the application code.

Tools

HTTP is easier to understand when it can be seen directly. A good set of tools allows inspecting, replaying, and crafting requests without writing code.

curl

curl is the universal baseline, present on virtually every system and used in almost every piece of documentation. The most commonly used flags are shown below.

Shell 
# GET request
curl https://api.example.com/orders

# Include response headers in output
curl -i https://api.example.com/orders

# Show full request and response headers (verbose)
curl -v https://api.example.com/orders

# POST with JSON body
curl -X POST https://api.example.com/orders \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"product_id": "abc", "quantity": 2}'

# Upload a file
curl -X PUT https://api.example.com/files/photo.jpg \
  -H "Content-Type: image/jpeg" \
  --data-binary @photo.jpg

HTTPie

HTTPie is a curl alternative designed to be readable. The default output is syntax-highlighted and formatted. JSON bodies are pretty-printed automatically, useful for quick exploration.

Shell 
# GET
http GET api.example.com/orders

# POST with JSON (key=value pairs become JSON automatically)
http POST api.example.com/orders product_id=abc quantity:=2

# Custom header
http api.example.com/orders Authorization:"Bearer <token>"

Bruno

Bruno is the leading GUI alternative to Postman. Its key difference is that collections are stored as plain files on disk in a readable format, so they can be committed to source control alongside the code they test. There's no mandatory cloud account or sync. The UI resembles VS Code. Bruno is a good default recommendation for teams that want a shared, version-controlled request collection.

VS Code REST Client

The REST Client extension for VS Code allows defining HTTP requests in .http files and running them with a click. Because they're plain text files, they live in the repository next to the code, which is useful for documenting API interactions and sharing reproducible examples with the team.

Authorization: Bearer {{token}}

Browser DevTools

The Network panel in browser DevTools is indispensable for understanding what's actually happening in a web application. Beyond the request and response headers, a few habits are worth building early:

  • The Timing tab shows connection setup, time-to-first-byte, and transfer time broken down by phase.
  • The Protocol column shows whether HTTP/2 or HTTP/3 was negotiated.
  • Filtering by type (XHR/Fetch, JS, CSS, Images) narrows the list to what matters for the task at hand.
  • "Preserve log" keeps requests visible across navigations, which matters when a redirect or reload would otherwise clear them.

HTTP underlies nearly everything that crosses the network in a web application: page loads, API calls, webhooks, and service-to-service calls inside a cluster. Methods and status codes, headers and caching, cookies and CORS, and the shift from HTTP/1.1 to HTTP/2 and HTTP/3 account for most of what shows up in a browser's Network panel or a server's access log. The RESTful API design and web application networking articles build directly on these mechanics.
