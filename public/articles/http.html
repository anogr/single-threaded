HTTP

How requests and responses work, from methods and status codes to caching, cookies, CORS, HTTP/2, and HTTP/3.

Andreas Ögren
~24 min read
Last updated July 2026

Every browser request, API call, and webhook delivery travels over the same protocol. Understanding it removes a layer of mystery from almost everything on the web.

HTTP (Hypertext Transfer Protocol) is the application-layer protocol used for communication on the web. It follows a request-response model in which a client sends a request and a server returns a response. Page loads, API calls, and file downloads all consist of one or more of these exchanges.

The request carries a method that describes the intended action and a URL that identifies the target. Its headers provide metadata, while an optional body carries content. The response has a status code, its own headers, and sometimes a body. In the text-based syntax used by HTTP/1.1, a basic exchange looks like this.

# Request
GET /articles/http HTTP/1.1
Host: example.com
Accept: text/html
# Response
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 4821
 
<!DOCTYPE html>…

HTTP is stateless, which means that the protocol does not give one request implicit access to the context of an earlier one. Applications may still keep server-side state. They connect a request to that state through information carried with the request, often a session cookie or authorization header.

A Brief History

HTTP has evolved in several stages. Each revision addressed limits that became visible as the web grew.

1991 · 1996
HTTP/0.9 & HTTP/1.0

HTTP/0.9 supported a minimal GET exchange that returned HTML. HTTP/1.0 added headers, status codes, and other media types. Connections were normally closed after each response, so loading a page with many resources required repeated connection setup.

1997
HTTP/1.1

HTTP/1.1 made persistent connections the default, allowing several exchanges to reuse one TCP connection. It also added chunked transfer coding and required the Host header, which lets one server distinguish sites that share an IP address.

2015
HTTP/2

HTTP/2 introduced binary framing, multiplexed streams, and HPACK header compression. Several exchanges can share one connection without waiting in an HTTP-level queue, removing much of the rationale for workarounds such as domain sharding.

2022
HTTP/3

HTTP/3 carries HTTP over QUIC instead of TCP. QUIC provides independent streams, integrates TLS 1.3, and can preserve a connection when the client changes networks. Packet loss on one stream no longer stalls every other stream at the transport layer.

HTTP/1.1, HTTP/2, and HTTP/3 all remain in use. Applications usually rely on clients and infrastructure to negotiate the best option they share. The HTTP/2 and HTTP/3 section explains how the two newer versions differ.

Methods

A method declares the intended action, giving clients and intermediaries semantics they can use for caching and retries.

HTTP defines a small set of methods, each with specified semantics. Two properties shape how generic software handles them. A method is safe when the client does not request a state change. It is idempotent when several identical requests have the same intended effect as one. Every safe method is idempotent, but an idempotent method can still change state.

GET Retrieve a representation. Safe and idempotent, which means the client does not ask for a state change. A GET request has no generally defined meaning for request content, so clients should not send a body without an explicit agreement with the origin.
POST Submit data for processing. Neither safe nor idempotent. Used to create resources, trigger operations, or submit forms. The server decides what to do with the body.
PUT Replace a resource entirely. Idempotent but not safe. The client provides the complete new representation, and repeated identical requests have the same intended effect.
PATCH Apply a partial update. Not idempotent by default (though specific patch formats can be). The body describes changes, not a full replacement.
DELETE Remove a resource. Idempotent in effect: the server state after repeated calls is the same, whether the resource existed or not.
HEAD Same as GET, but returns only headers. Useful for checking whether a resource exists or has been modified without downloading the body. Safe and idempotent.
OPTIONS Describe the communication options for a resource. Used by browsers to issue CORS preflight requests before a cross-origin request. Safe and idempotent.
QUERY Run a query with a request body, safely. 2026 Safe and idempotent, like GET, but carries a body, like POST. Defined in RFC 10008 for queries too large or too structured to fit in a URL.

These properties give clients and intermediaries a basis for decisions about caching and retries. GET and HEAD dominate ordinary HTTP caching, although HTTP also defines narrower caching semantics for POST. An idempotent request may be retried after a connection failure because repeating it has the same intended effect. A client cannot make that assumption for POST unless the application supplies another guarantee, such as an idempotency key.

Method semantics are therefore part of the contract with infrastructure as well as application code. A GET endpoint that changes state can be triggered by prefetching, crawling, or an automatic retry. Using POST for a read is valid, but it gives up the safety and idempotency guarantees that generic HTTP software understands.

The QUERY Method 2026

QUERY fills the gap between GET and POST by giving a body-bearing request safe, idempotent, and cacheable semantics.

Search and filter operations often need more structure than a URL comfortably holds, such as nested filters, long lists of IDs, or a full-text query alongside facets and pagination. The usual way to express this is a query string.

GET /feed?q=foo&limit=10&sort=-published HTTP/1.1
Host: example.org

Query strings work well until the query becomes large or deeply structured. Servers and intermediaries impose different URL-length limits, so applications cannot rely on one universal maximum. Encoding nested data into a flat string also becomes cumbersome. URLs commonly appear in browser history and server logs, which makes them a poor place for sensitive query values.

The common workaround is to send the query as a POST body instead.

POST /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
 
q=foo&limit=10&sort=-published

A POST body removes the URL constraint, but the method no longer tells generic HTTP software that the operation is safe and repeatable. POST responses can be cached under limited conditions, though most cache implementations do not support that path. Automatic retries are also unsafe unless the client knows more about the operation than the method reveals.

RFC 10008, published on the IETF Standards Track in June 2026, defines the QUERY method for this case. The request resembles the POST version above, but its method explicitly promises safe and idempotent processing.

QUERY /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
 
q=foo&limit=10&sort=-published
HTTP/1.1 200 OK
Content-Type: application/json

The request content and its Content-Type together describe the query. A server must reject a QUERY request when the media type is missing or inconsistent with the content. The method does not prescribe one format, so a resource may accept form data, JSON, SQL, or another media type whose query semantics it defines.

GETQUERYPOST
Safeyesyesnot guaranteed
Idempotentyesyesnot guaranteed
Cacheableyesyesyes, but only for later GET or HEAD requests
Bodyno defined meaningdefines the querydefines the operation

Two QUERY requests to the same URL may describe different operations, so a cache key must incorporate the request content and the metadata that affects its interpretation. Existing caches were largely designed around URL-keyed GET requests. Supporting QUERY therefore requires implementation work across clients, proxies, and CDNs. Publication of the RFC does not make that support immediate.

A server can advertise QUERY support and the accepted media types through the Accept-Query response header. The header plays a role similar to Allow, but describes query formats rather than methods.

Accept-Query: application/x-www-form-urlencoded, application/sql

QUERY entered the standards track in June 2026, so deployment is still at an early stage. An application must confirm support in every client and intermediary on its request path before depending on the method or its caching semantics.

Status Codes

The three-digit status code is the server's top-level answer to the request. The first digit indicates the class of outcome.

HTTP defines five classes. Application code encounters 2xx, 4xx, and 5xx most often. The 3xx range controls redirection and participates in caching, while clients commonly handle informational 1xx responses below the application layer.

2xx · Success

200OK: The request succeeded. The response body contains the result.
201Created: One or more resources were created. A Location header can identify the primary new resource.
202Accepted: The request was received but processing is not yet complete. Used for async operations.
204No Content: Succeeded with no body to return. Common for DELETE and some PATCH responses.

3xx · Redirection

301Moved Permanently: The resource lives at a new URL. Clients should update stored links.
302Found: Temporary redirect. The original URL remains valid.
304Not Modified: The cached version is still valid. No body returned. Used with conditional requests.
307Temporary Redirect: Like 302, but the original HTTP method must be preserved.
308Permanent Redirect: Like 301, but the original HTTP method must be preserved.

4xx · Client Error

400Bad Request: The request is malformed or contains invalid syntax.
401Unauthorized: The request lacks valid authentication credentials. The response includes a WWW-Authenticate challenge.
403Forbidden: The server understood the request but refuses to fulfil it. Different credentials may be insufficient, or the resource may be prohibited for another reason.
404Not Found: The resource does not exist at this URL. Sometimes returned intentionally in place of 403 to conceal existence.
409Conflict: The request conflicts with the current resource state, for example, a duplicate creation or a failed optimistic concurrency check.
422Unprocessable Content: The server understands the content type and syntax but cannot process the instructions. Domain validation failures often use this code.
429Too Many Requests: The client sent too many requests within a period. Retry-After can tell it when to try again.

5xx · Server Error

500Internal Server Error: Something went wrong on the server. A catch-all for unhandled failures.
502Bad Gateway: A gateway or proxy received an invalid response from an upstream server.
503Service Unavailable: The server is temporarily unable to handle requests. It may include Retry-After when the recovery time is known.
Error response bodies

HTTP status codes communicate the class of error, but not the detail. RFC 9457 (Problem Details for HTTP APIs) defines a standard JSON format for error bodies: a type URI identifying the error kind, a title, a status mirroring the code, and a human-readable detail. Use Content-Type: application/problem+json when returning this format.

Headers

Headers carry metadata about the message, the sender, the content, and the desired behavior. They are the control plane of HTTP.

Headers are key-value pairs sent before the body in both requests and responses. They control how the message is interpreted, what content is acceptable, how long a response can be cached, and who is allowed to read it. Header names are case-insensitive, though values are case-sensitive where the spec requires it.

Content negotiation

HTTP has a built-in mechanism for clients and servers to agree on representation format. The client expresses what it can handle in the Accept header. The server responds with the chosen format in Content-Type. The same mechanism applies to encoding (Accept-Encoding / Content-Encoding) and language (Accept-Language / Content-Language).

# Client signals it prefers JSON but accepts anything
Accept: application/json, */*;q=0.8
 
# Server confirms what it actually sent
Content-Type: application/json; charset=utf-8

The q parameter (quality value) expresses preference on a 0–1 scale. application/json without a q value defaults to 1.0 (highest preference). This mechanism also underpins versioning via Accept headers and content-type-specific error formats like application/problem+json.

Caching

Caching is one of the most impactful and most misunderstood parts of HTTP. A well-cached API or site is dramatically faster. A badly cached one serves stale data or bypasses caching entirely.

HTTP caching stores responses for reuse on later equivalent requests. A private cache, such as a browser cache, is dedicated to one user agent. Shared caches, including CDN and proxy caches, can reuse responses for several users. A response served from either cache may avoid contacting the origin, but shared reuse requires stricter separation of user-specific content.

Cache-Control

The Cache-Control header is the primary mechanism for controlling caching behavior. It appears in both responses (server instructs caches) and requests (client instructs intermediaries). The most important response directives follow.

DirectiveMeaning
max-age=NCache the response for N seconds from the time it was received
no-cacheCache the response, but always revalidate with the server before using it
no-storeDo not store the response at all (for sensitive data)
privateOnly the browser may cache this, CDNs and shared proxies must not
publicAny cache may store this, including CDNs
s-maxage=NLike max-age but applies only to shared caches
stale-while-revalidate=NServe a stale response for up to N seconds while fetching a fresh one in the background
immutableThe response will not be updated while fresh, so clients need not revalidate it during that period
no-cache does not mean "don't cache"

Cache-Control: no-cache means "store this, but check with the server before using it." To prevent storage entirely, use no-store. This is one of the most common sources of caching confusion.

A common pattern for static assets with content-hashed URLs is Cache-Control: public, max-age=31536000, immutable. The one-year freshness lifetime is safe because changed content receives a new URL. For a user-specific API response, Cache-Control: private, max-age=60 permits brief storage in a private cache while excluding shared caches.

Conditional requests and ETags

Once a cached response expires, the client can ask the server whether it has changed rather than fetching the full content again. The server includes an ETag (a version token, a hash or revision number) in the original response. On revalidation, the client sends that token in an If-None-Match header. If the resource hasn't changed, the server returns 304 Not Modified with no body, and the client uses its cached copy.

# First request, server returns content with a version token
GET /products/42
200 OK
ETag: "d4f8a2"
Cache-Control: max-age=300
# After 5 minutes, client revalidates
GET /products/42
If-None-Match: "d4f8a2"
304 Not Modified (no body, saves the bandwidth)

ETags also support optimistic concurrency in APIs. A client sends the version it read through If-Match when updating the resource. If that version is no longer current, the server rejects the update with 412 Precondition Failed. The stale client cannot silently overwrite a newer change.

Cookies

Cookies are how HTTP bridges its own statelessness. They are the mechanism for sessions, preferences, and authentication state that persists across requests.

A cookie is a small piece of data delivered in a Set-Cookie response header. The browser stores it and later includes it in matching requests through the Cookie header. Domain, path, security, expiry, and same-site rules determine which requests match.

# Server sets a cookie after login
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
 
# Browser sends it on every subsequent request to this origin
Cookie: session_id=abc123

Cookie attributes

The attributes attached to a cookie control how and when the browser sends it, and who can access it.

AttributeEffect
HttpOnlyJavaScript cannot read this cookie. Protects session tokens from XSS attacks, since a script that can't access the token can't steal it.
SecureThe cookie is only sent over HTTPS connections. Required for any cookie carrying sensitive data.
SameSiteControls when the cookie is sent on cross-site requests (see below).
Max-Age / ExpiresHow long the cookie lives. Without either attribute, it is a session cookie whose lifetime is controlled by the browser session.
PathLimits the cookie to a URL path prefix. Rarely needs to differ from /.
DomainAllows the cookie to match the named domain and its subdomains. Omitting it creates a host-only cookie.

SameSite

Cookie matching is separate from the same-origin policy. Historically, a browser could attach a matching cookie to a cross-site request even though the initiating page could not read the response. That behavior enables cross-site request forgery (CSRF). The SameSite attribute limits when a cookie accompanies a request initiated from another site.

The attribute takes three values:

  • SameSite=Strict: the cookie is never sent on cross-site requests, even top-level navigations.
  • SameSite=Lax: permits cookies on same-site requests and on cross-site top-level navigations that use a safe method. Browsers commonly apply a Lax-like default when the attribute is omitted.
  • SameSite=None: permits the cookie on cross-site requests and requires Secure. Browser privacy policy may still block the cookie in a third-party context.
SameSite and CORS credentials

A cross-site API that relies on cookies generally needs SameSite=None; Secure. Its CORS response must allow credentials for the calling origin, and the fetch request must use credentials: 'include'. Cookie rules and CORS rules are evaluated separately, so satisfying only one side is insufficient.

Redirects

Redirects tell the client to look elsewhere. The choice of status code controls whether the redirect is permanent, temporary, and whether the HTTP method is preserved.

When a server responds with a 3xx status code and a Location header, the browser automatically makes a new request to that URL. For 301 and 302, browsers historically changed the method of the follow-up request to GET even if the original was POST. 307 and 308 were introduced specifically to prevent that.

Permanent
301 & 308

301 marks a permanent move and permits a user agent to follow a POST with GET. 308 preserves the method. Both are heuristically cacheable unless cache controls say otherwise.

Temporary
302 & 307

302 marks a temporary move and permits POST to become GET. 307 preserves the method. Clients continue using the original URL for later requests. Explicit cache controls should define any temporary caching.

Reload & Resubmission

Reloading a page and reissuing its last request are the same thing to a browser. That's fine after a GET, but not always after a POST.

Reloading revisits the current history entry, including the method that produced it. If that method was POST, replaying the entry can repeat an effect such as creating an order. Browsers therefore ask for confirmation before resubmitting form data. A cache-bypassing reload changes cache behavior but does not turn the history entry into GET. Starting a fresh navigation from the address bar creates a GET request instead.

ActionRepeats method & bodyResubmission warning
Reload current entryyesbrowser confirms a form resubmission
Reload while bypassing cacheyesbrowser confirms a form resubmission
Start a new address-bar navigationno, sends GETno resubmission

Post-Redirect-Get

The Post-Redirect-Get pattern avoids leaving a POST as the current history entry. After processing the POST, the server returns 303 See Other with a result URL. The browser follows that URL with GET, so a later reload revisits the GET result rather than resubmitting the operation.

POST /orders → form submission
303 See Other
Location: /orders/a3f9b2c1
GET /orders/a3f9b2c1 → browser follows automatically
200 OK

Compression

Content coding reduces the bytes transferred for compressible response bodies, often without changes to application handlers.

The client advertises supported encodings through Accept-Encoding. The server may choose one, compress the body, and name that encoding in Content-Encoding. HTTP clients normally decompress the representation before exposing it to application code.

Accept-Encoding: br, gzip, deflate
Content-Encoding: br

Gzip has broad client and server support. Brotli (br) can produce smaller text responses, usually at a higher compression cost. The server chooses only an encoding advertised by the client. Compression helps text formats such as JSON, HTML, CSS, and JavaScript, while already-compressed images and video usually gain little.

Compression is often configured in a reverse proxy, load balancer, or CDN. Central configuration keeps the content-coding policy consistent across application handlers.

File Uploads

Uploading files over HTTP is common but slightly awkward. There are two distinct approaches, and choosing the wrong one creates friction.

multipart/form-data

HTML forms use multipart/form-data when they include file inputs. The request body is divided into named parts separated by a boundary string, each with its own headers. This format can mix file data with regular text fields in a single request, which is natural for form submissions.

POST /uploads
Content-Type: multipart/form-data; boundary=----Boundary7MA4YWxk
 
------Boundary7MA4YWxk
Content-Disposition: form-data; name="description"
 
Product photo
------Boundary7MA4YWxk
Content-Disposition: form-data; name="file"; filename="photo.jpg"
Content-Type: image/jpeg
 
[binary data]
------Boundary7MA4YWxk--

Binary PUT

For an API that uploads one file to a known resource URL, PUT with the raw binary body can be simpler. The Content-Type describes the file directly, and no multipart envelope is needed. Object-storage APIs commonly support this shape.

PUT /files/profile-photo.jpg
Content-Type: image/jpeg
Content-Length: 48291
 
[binary data]

A common architecture for large files skips uploading through the application server entirely. The client requests a short-lived pre-signed URL from the API, then uploads directly to object storage, so the application server never touches the binary data and storage scales independently.

CORS

The same-origin policy limits what browser code can read across origins, while CORS lets a server grant selected access.

The same-origin policy

Browsers enforce a same-origin policy that prevents JavaScript on one origin from reading responses returned by a different origin. An origin is the combination of scheme, host, and port (https://app.example.com:443 is a different origin from https://api.example.com:443, even though they share the same domain). For more information, see the same-origin policy and CORS section of the browser security article.

Relaxing the policy

CORS (Cross-Origin Resource Sharing) lets a server authorize browser code from another origin to read selected responses. Some requests meet the rules for a CORS-safelisted request. They use GET, HEAD, or POST and stay within a limited set of fields and content types, including text/plain and application/x-www-form-urlencoded.

The browser sends a safelisted request without asking permission first, then checks the response fields before exposing the result to JavaScript. Other requests need a preflight. A request declared as application/json, for example, falls outside the safelist.

Preflight requests

A request outside the CORS safelist requires the browser to check permission first. Common triggers include a non-safelisted field, JSON content, or a method such as PUT or DELETE. The browser sends an OPTIONS request naming the intended origin, method, and fields. It sends the actual request only when the response grants that combination.

# Browser asks permission first
OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization
204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
# Browser sends the actual request
POST /orders
Origin: https://app.example.com
Content-Type: application/json

Access-Control-Max-Age lets the browser reuse a successful preflight for a period. Browser-specific caps can shorten the configured value. Choose a duration that balances fewer preflights against the time required for a changed CORS policy to take effect.

Credentials

The default fetch credentials mode does not send cookies on cross-origin requests. A script may set an Authorization header separately, subject to the usual CORS preflight and header checks. Cookie-based credentialed requests require three pieces to align:

  • The server must respond with Access-Control-Allow-Credentials: true.
  • The server must also specify a concrete origin in Access-Control-Allow-Origin, since the wildcard * is not allowed when credentials are involved.
  • The client must opt in with fetch(url, { credentials: 'include' }).

Access-Control-Expose-Headers

By default, JavaScript can only read a small set of "safe" response headers, such as Content-Type and Content-Length. Other headers, including ETag, Location, and any custom headers, are hidden even if the request is permitted by CORS. To expose them, the server must list them explicitly.

Access-Control-Expose-Headers: ETag, Location, X-Request-Id
CORS is a browser constraint

CORS headers only affect browser JavaScript. curl, server-to-server calls, and tools like Bruno and Postman are not bound by the same-origin policy and will receive responses regardless of CORS headers. If an API call works in curl but not in the browser, CORS configuration is the first thing to check.

HTTP/2 & HTTP/3

Both versions solve performance problems that HTTP/1.1 couldn't address. They solve different problems at different layers of the network stack.

HTTP/2: multiplexing over TCP

HTTP/1.1 responses on one connection remain ordered. Browsers work around that constraint by opening several parallel connections to an origin, which adds setup cost and still caps parallelism. HTTP/2 introduces a binary framing layer built around streams. Frames from several request-response exchanges can be interleaved on one TCP connection, so one slow response does not hold up an HTTP-level queue.

HTTP/2 also compresses header fields with HPACK. Repeated fields such as cookies no longer need their full HTTP/1.1 text representation on every request. Fewer connections and multiplexed streams reduce the value of older bundling, inlining, and domain-sharding workarounds.

Server push, where the server could proactively send resources the client hadn't requested yet, was part of HTTP/2 but never saw wide adoption. Chrome removed support for it in 2022.

HTTP/3: QUIC over UDP

HTTP/2 multiplexing over TCP has a residual problem. TCP is a single ordered byte stream. When a packet is lost, TCP stalls the entire connection while waiting for retransmission, so even streams that had no packet loss get blocked. This is TCP-level head-of-line blocking, and multiplexing can't fix it because multiplexing happens above the TCP layer.

HTTP/3 solves this by replacing TCP with QUIC, a transport protocol built on UDP with reliability and flow control for independent streams. Missing data blocks only the streams that depend on it rather than the entire connection. QUIC integrates TLS 1.3, supports connection migration across network changes, and can use 0-RTT data when resuming a previous connection.

HTTP/2 and HTTP/3 are usually configured in servers, proxies, and hosting platforms rather than application handlers. TLS handshakes use Application-Layer Protocol Negotiation (ALPN) to select a supported protocol. Browser developer tools expose the result in the Network panel, often through a Protocol column.

Tools

HTTP is easier to understand when it can be seen directly. A good set of tools allows inspecting, replaying, and crafting requests without writing code.

curl

curl is a widely available command-line client and a common language for reproducible HTTP examples. The following commands cover the options used most often during inspection and testing.

Shell 
# GET request
curl https://api.example.com/orders

# Include response headers in output
curl -i https://api.example.com/orders

# Show full request and response headers (verbose)
curl -v https://api.example.com/orders

# POST with JSON body
curl -X POST https://api.example.com/orders \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"product_id": "abc", "quantity": 2}'

# Upload a file
curl -X PUT https://api.example.com/files/photo.jpg \
  -H "Content-Type: image/jpeg" \
  --data-binary @photo.jpg

HTTPie

HTTPie is a curl alternative designed to be readable. The default output is syntax-highlighted and formatted, and JSON bodies are pretty-printed automatically, which helps for quick exploration.

Shell 
# GET
http GET api.example.com/orders

# POST with JSON (key=value pairs become JSON automatically)
http POST api.example.com/orders product_id=abc quantity:=2

# Custom header
http api.example.com/orders Authorization:"Bearer <token>"

Bruno

Bruno is a desktop API client that stores collections as readable files on disk. Teams can commit those files beside the code they exercise and review request changes through the normal source-control workflow. A cloud account is not required for local collections.

VS Code REST Client

The REST Client extension for VS Code allows defining HTTP requests in .http files and running them with a click. Because they're plain text files, they live in the repository next to the code, which is useful for documenting API interactions and sharing reproducible examples with the team.

api.http HTTP 
### Get all orders
GET https://api.example.com/orders
Authorization: Bearer {{token}}

### Create an order
POST https://api.example.com/orders
Content-Type: application/json

{
  "product_id": "abc",
  "quantity": 2
}

Browser DevTools

The Network panel in browser developer tools shows what a web application sends and receives. Beyond inspecting request and response headers, several views are useful:

  • The Timing tab shows connection setup, time-to-first-byte, and transfer time broken down by phase.
  • The Protocol column shows whether HTTP/2 or HTTP/3 was negotiated.
  • Filtering by type (XHR/Fetch, JS, CSS, Images) narrows the list to what matters for the task at hand.
  • "Preserve log" keeps requests visible across navigations, which matters when a redirect or reload would otherwise clear them.

The protocol choices in this article explain most entries in a browser's Network panel or a server's access log. The RESTful API design article applies those semantics to API contracts, while web application networking follows requests through the infrastructure around an application.
