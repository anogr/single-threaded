CSS at Scale

How teams keep CSS maintainable as codebases, component counts, and contributor lists grow.

Andreas Ögren
~24 min read
Last updated July 2026

A ten-file CSS project barely needs an architecture. One stylesheet holds a handful of classes, and nobody steps on anybody else's rules. The trouble starts later, once a project reaches fifty components, three contributing teams, and a design system that's only half-adopted. At that point nobody can predict what changing one class name will do to a screen they've never opened. That's the moment CSS architecture stops being a preference and starts being a requirement.

This article covers the mechanisms that cause CSS to break down as projects grow and the pain points teams actually run into. It then surveys the current landscape built to address them, covering methodologies, preprocessors, CSS-in-JS libraries, utility frameworks, and native browser features. The platform itself has closed a lot of that gap since 2020. Cascade layers, @scope, and container queries now do natively what frameworks used to exist purely to work around. The result today is less a single winning approach than a set of tradeoffs. Most of them come down to how much a team is willing to trade authoring convenience for runtime cost, and how much they trust native CSS to keep closing the remaining gaps.

Why CSS Breaks Down at Scale

Three ordinary CSS mechanisms, useful at small scale, turn into liabilities once enough people are writing rules against the same page.

CSS was built around a small number of mechanisms. Selectors share a single global namespace, and a cascade resolves conflicting rules by specificity and source order. Inheritance then lets computed values flow from parent elements to children. Every one of those mechanisms is exactly what makes a small stylesheet pleasant to write, and exactly what turns a large one into a maintenance problem.

Take the global namespace first. Every class selector in a page's CSS lives in one shared space, regardless of which file, which team, or which component it was written for. A .card class in a checkout component and a .card class in a marketing component are the same selector as far as the browser is concerned. Whichever rule loads last, or whichever rule carries higher specificity, wins. Neither team necessarily knows the other one exists.

That collision risk feeds directly into the second mechanism: specificity. The cascade resolves competing rules using a scoring system built from ID selectors, class selectors, and element selectors, with source order as a tiebreaker when scores are equal. It's a reasonable way to prioritize a hundred rules. Across ten thousand rules written by rotating contributors over several years, nobody remembers the specificity of a selector they wrote eight months ago. The fix for "my rule isn't applying" becomes adding another selector segment, or reaching for !important. Each fix raises the bar the next override has to clear.

The third mechanism, cascade dependency, is the quietest one and the most expensive over time. Any rule's effect depends on every other rule that could apply to the same element. Deleting a rule requires knowing, with confidence, that nothing else in the codebase relies on the cascade resolving the way it currently does. Almost nobody has that confidence in a codebase past a certain size, so the safe move is never deleting anything. Stylesheets in mature products routinely carry years of rules nobody is willing to remove, not because the rules are useful, but because removing them is the one action nobody can prove is safe.

The Pain Points

Every architecture covered later in this article is really an attempt to close one or more of six recurring failure modes.

The three mechanisms above don't cause problems directly. They cause the six symptoms below, and those are the symptoms a team experiences day to day. This table works as the rubric for everything that follows. Every methodology, preprocessor, or framework in the next section gets measured against how many of these six it actually closes, not how many it claims to.

Pain pointWhat it looks likeRoot cause
Global namespace collisions Two unrelated components pick the same class name, one silently overrides the other's styles after a merge. Single global selector namespace, no built-in scoping.
Specificity wars Overrides pile up as extra selector segments, then ID selectors, then !important, because normal class rules keep losing to something written earlier with a higher score. The cascade resolves by specificity and source order, not by authorial intent.
Dead, unremovable CSS Stylesheets only grow. Nobody deletes a rule because nobody can prove another rule doesn't depend on it still being there. Cascade dependency: any rule's effect depends on every other rule that could match the same element.
Selector and paint performance Deeply nested selectors and oversized stylesheets slow down style recalculation, especially on large, frequently updated DOM trees. Selector matching cost scales with both selector complexity and DOM size.
Theming inconsistency Two teams both implement "the primary brand colour" with a slightly different value, because nothing enforces a single source of truth. Custom properties and design tokens are conventions, not types, nothing stops drift.
Build/tooling coupling A one-line style change forces a full rebuild, or a runtime styling bug in one component slows down pages that don't even render it. Some architectures tie style computation to the bundler or the JS runtime instead of resolving independently.

Each row in that table has a cost attached, and the cost is rarely the CSS itself. A namespace collision usually surfaces as a bug report two weeks after the merge that caused it, once someone finally notices a marketing page's .card quietly restyled a checkout component nobody thought to test. Specificity wars show up as onboarding time: a new contributor spends their first weeks learning which classes are safe to edit and which ones are load-bearing for reasons no comment explains. Dead CSS is a tax paid continuously, in bundle size that only grows and in the extra seconds a build step spends parsing rules nothing on the page still matches. Theming inconsistency turns a rebrand into an archaeology project, grepping for every hardcoded hex value that was supposed to be a token. None of these costs are dramatic on any single day. They compound, which is why a codebase that felt fine at year one can feel unworkable by year three without anyone being able to point to the one change that broke it.

Architectures and Tools

With the mechanisms and their symptoms established, every approach below can be measured against the same six-item rubric.

None of the approaches below eliminates all six pain points. That's the point of laying out the rubric first. A methodology like BEM never touches build tooling because it isn't tooling, while a runtime CSS-in-JS library can solve namespace collisions and make the tooling-coupling problem worse in the same move. The useful read on each entry is which specific pain points it closes, not whether it's "good" in the abstract.

Methodologies

Block, Element, Modifier (BEM) is a naming convention, not a tool. A component gets a block name, its internal parts get block__element names, and variations get block--modifier names, all as flat, single-class selectors with no nesting. .card__title--highlighted is unambiguous about what it styles and carries a specificity of exactly one class, the same as every other BEM selector in the codebase.

card.html HTML 
<div class="card card--highlighted">
  <h3 class="card__title">Title</h3>
  <p class="card__body">…</p>
</div>

That flatness is the entire mechanism. Because every BEM selector has identical, minimal specificity, two rules can only conflict based on source order, never on an escalating specificity score. That's what ends the specificity wars from the previous section. BEM does nothing for namespace collisions on its own. Two teams can still pick the same block name, so .card in one component collides with .card in another. It does nothing for dead CSS or theming either. It's a naming discipline, not an isolation mechanism.

Scalable and Modular Architecture for CSS (SMACSS) and Object-Oriented CSS (OOCSS), both from the early 2010s, layer additional rules on top of a BEM-like naming approach. OOCSS separates structure from skin, so a button's layout and its colour can be reused independently. SMACSS categorizes rules into base, layout, module, state, and theme buckets, to keep authors from mixing concerns in one file. Neither sees much greenfield adoption today. Inverted Triangle CSS (ITCSS) stands out from the other two: it orders a stylesheet from generic, low-specificity rules such as resets and element defaults down to specific, high-specificity rules such as utilities and overrides, so that source order and specificity increase together instead of fighting each other. That's precisely the ordering problem cascade layers now solve natively, which is why ITCSS reads less like a dated methodology today and more like a preview of @layer.

ApproachSolvesDoesn't solveBest fit
BEM Specificity wars, via flat, equal-weight selectors Namespace collisions, dead CSS, theming Teams without a build step, or as naming discipline layered on top of any other approach
SMACSS / OOCSS Some organizational discipline through file structure Namespace collisions, specificity wars, performance Legacy codebases already organized this way
ITCSS Specificity wars, via deliberate low-to-high ordering Namespace collisions, dead CSS Large stylesheets that need cascade layers but don't have them adopted yet

Preprocessors

Sass and its SCSS syntax add variables, nesting, mixins, functions, and file partials to plain CSS, then compile down to a single flat stylesheet before it ships. None of that touches the underlying cascade. A compiled Sass file has exactly the same specificity and namespace behaviour as if it had been hand-written, which is why Sass alone doesn't solve namespace collisions or specificity wars. What it solves instead is authoring ergonomics, things like a $breakpoint-tablet variable reused across forty files, a @mixin for a repeated flex pattern, or nesting that keeps a component's related rules visually together in the source.

Native CSS nesting, standardized and broadly supported since 2023, now covers a meaningful slice of what Sass nesting used to be needed for, and native custom properties cover a slice of what Sass variables used to be needed for. That overlap hasn't killed Sass. Teams with existing Sass codebases have no urgent reason to migrate, and Sass still has capabilities native CSS doesn't, such as real functions, loops, and mixins with logic. What has changed is Sass's role, from "the only way to get this" to "a mature, still-convenient way to get part of this."

Less occupies roughly the same space as Sass but with a smaller feature set and a shrinking ecosystem. New projects essentially never start on it today. It appears here only because it's still running in older codebases.

ToolSolvesDoesn't solveBest fit
Sass / SCSS Authoring ergonomics: variables, mixins, nesting, partial organization Namespace collisions, specificity wars, dead CSS, tooling coupling Existing Sass codebases, or projects needing real functions and loops native CSS still lacks
Less Same category as Sass, narrower feature set Same as Sass, plus a shrinking ecosystem Maintaining legacy projects only

CSS-in-JS

CSS-in-JS covers two genuinely different implementation strategies that happen to share a name. The runtime kind, most widely represented by styled-components and Emotion, writes styles as JavaScript template literals or objects. It then generates scoped class names and injects the resulting CSS into the page at render time, in the browser. JSS pioneered that same runtime idea even earlier, in the mid-2010s. It still exists as a library and as the styling engine some older Material-UI installs still carry, but it sees essentially no adoption on new projects today. Zero-runtime libraries such as Vanilla Extract, Panda CSS, StyleX, and Linaria generate that same scoped CSS at build time instead. They ship a static stylesheet and leave nothing but plain class name strings in the JavaScript bundle.

That distinction matters more today than it did five years ago, mostly because of React Server Components. A runtime library needs to execute JavaScript to know what styles to inject. That's awkward in a rendering model built around components that may never run any client-side JavaScript at all. It's specifically hard for styled-components and Emotion, whose runtime relies heavily on React's Context API, a feature Server Components don't support. styled-components' maintainer put the library into maintenance mode in March 2025 for exactly that reason. New work is limited to security patches and compatibility fixes rather than features, though the project has kept shipping fixes for things like React 19 hydration and Shadow DOM server-side rendering since then. That's a fair signal for new projects to look elsewhere, though it doesn't mean existing codebases are stranded. Zero-runtime tools sidestep the problem entirely, because the CSS is already a static file by the time any component renders, server or client. There is no runtime step that needs JavaScript execution to produce styles.

The zero-runtime tools aren't equally popular. Vanilla Extract's adoption has largely plateaued rather than grown, mostly because Tailwind absorbed much of the audience that might otherwise have picked up a new utility-adjacent tool. Panda CSS is smaller but has been growing quickly off a lower base. StyleX, Meta's atomic zero-runtime library, started as Meta's internal tool for Facebook, Instagram, WhatsApp, and Messenger before its December 2023 open-source release. It has since been adopted by outside companies including Figma, Snowflake, and HubSpot, and its team has explicitly demonstrated Server Components compatibility. The pattern across all three is similar: real but comparatively small usage next to Tailwind's, concentrated in TypeScript-heavy teams that want a typed design system more than they want utility classes in markup.

Zero-runtime tools also close a pain point runtime CSS-in-JS never touched: theming inconsistency. Vanilla Extract and Panda CSS both let a team define a theme contract, a TypeScript type describing exactly which tokens exist and what shape their values take. A typo'd token name then fails at compile time, instead of silently rendering as an unstyled default. That's a genuinely different guarantee than a Sass variable or a CSS custom property, both of which happily accept a misspelled name and give back nothing, silently.

theme.css.ts TypeScript 
import { createTheme } from '@vanilla-extract/css';

export const [themeClass, vars] = createTheme({
  color: {
    brand: '#3a6ea5',
    text: '#1a1a1a',
  },
  space: {
    sm: '8px',
    md: '16px',
  },
});

// vars.color.brnad would fail to compile: no such token exists

The values inside a theme contract, such as a type scale, a spacing scale, or color reserved for meaning rather than decoration, come from a design question before they come from a tooling one. UX Principles covers that side of the same system.

ToolEraSolvesDoesn't solveBest fit
styled-components / Emotion Runtime Namespace collisions, via generated scoped class names Tooling coupling, RSC compatibility, theming type-safety Existing codebases already built on them, not recommended for new work
Vanilla Extract / Panda CSS Zero-runtime Namespace collisions, theming inconsistency, tooling coupling (static output) Still requires a build step TypeScript codebases with a design system to enforce
StyleX / Linaria Zero-runtime Namespace collisions, tooling coupling, some specificity via atomic output Smaller ecosystems, steeper adoption curve Large orgs (StyleX, from Meta) or teams wanting near-zero-cost atomic styles

Utility-First CSS

Utility-first frameworks invert the usual authoring model. Instead of writing a .card class and defining its properties, a component applies dozens of small, single-purpose classes directly in markup, such as flex items-center gap-4 rounded-lg border, with each one mapping to exactly one CSS declaration. Tailwind is the framework that made this mainstream. Tailwind v4 is the default utility framework for most new projects today, and it backs the default styling choice in shadcn/ui and most AI code generation tools. The 2025 State of CSS developer survey ranked Tailwind as the most actively used CSS framework by a wide margin, well ahead of Bootstrap in second place.

Version 4 rebuilt Tailwind's engine in Rust, internally called Oxide, and folded in Lightning CSS for the underlying transforms. That's what let it drop the old JavaScript configuration file for plain CSS. A project now configures itself with @import "tailwindcss" and a handful of @theme variables instead of a tailwind.config.js. Tailwind's own benchmarks put full rebuilds at up to five times faster than v3. Incremental builds that don't introduce any new utility classes come in over a hundred times faster, since Oxide only has to re-check what changed rather than rescanning the whole project.

Utility classes solve namespace collisions and specificity wars structurally, not by convention. Every utility class has identical low specificity. There's nothing to collide with either, since flex means the same thing everywhere it's used. They also solve dead CSS almost by accident. An unused utility class in markup is trivially detectable by static analysis, and Tailwind's build step already strips anything that doesn't appear in scanned source files. What they don't solve is co-locating complex, conditional styling logic. A component with a handful of responsive, hover, and dark-mode variants can end up with a class attribute running to several hundred characters. Reading that line back for intent takes real practice compared to a semantic name like .card--highlighted. That readability cost is the most consistent criticism of the approach. It's a genuine tradeoff rather than a solved problem, and most teams accept it in exchange for never touching a separate stylesheet.

Tachyons pioneered the same idea years earlier and still exists, but has no meaningful adoption on new projects today. Most of what it offered is now just what Tailwind does, with a larger ecosystem around it.

ToolSolvesDoesn't solveBest fit
Tailwind v4 Namespace collisions, specificity wars, dead CSS Tooling coupling still ties styling to a build step, plus markup density Fast-moving teams, component frameworks, AI-generated code
Tachyons Same mechanism as Tailwind Everything Tailwind now covers better, plus no active development Legacy maintenance only

Scoped & Hashed CSS

CSS Modules take a different route to the same namespace problem. A stylesheet is written as ordinary CSS, one file per component. The build step then rewrites every class name into something globally unique, so .card becomes .Card_card__a3f9k before the browser ever sees it. The component only references the original, human-readable name through an imported object, styles.card, so authoring still looks like normal CSS while the actual selector on the page is guaranteed unique.

That hashing is also what bundlers do under the hood for any component-scoped styling approach. Webpack's [hash:base64] class name pattern and Vite's equivalent are the same mechanism CSS Modules is built on, just exposed more directly. The guarantee is purely mechanical, uniqueness rather than intent. Two components can still write conflicting layout assumptions about a shared child element. CSS Modules only promises the class names themselves won't collide, not that the cascade behaves predictably everywhere.

CSS Modules solve namespace collisions completely and specificity wars partially, since most authors write flat, low-specificity selectors by convention even though nothing enforces it. They don't touch theming or tooling coupling. Dead CSS detection depends entirely on whether the bundler's tree-shaking can prove a given CSS Module import is unused. It usually can for components, but not always for shared partial stylesheets. Next.js's own documentation still lists CSS Modules alongside Tailwind as the two most common ways teams style a Next.js application. That says something about how far "plain CSS with guaranteed unique class names" still goes, even in a utility-first, zero-runtime-heavy landscape.

ToolSolvesDoesn't solveBest fit
CSS Modules Namespace collisions, via guaranteed unique class names Theming, tooling coupling, specificity wars if authors nest deeply Component-per-file frameworks without a full CSS-in-JS or utility system
Bundler hash classes (Webpack / Vite) Same mechanism as CSS Modules, without the authoring layer Same gaps as CSS Modules Teams that want scoping without the CSS Modules import convention

Native Component Scoping

Two native browser mechanisms scope styles without any build step at all, and they solve the namespace problem in genuinely different ways.

Shadow DOM, part of the Web Components spec, gives an element its own isolated DOM subtree with its own stylesheet. Styles defined inside a shadow root simply don't apply outside it, and outside styles don't leak in, by default, not by convention. That's a real boundary enforced by the browser, not a naming discipline or a build-time rewrite, which makes Shadow DOM the strongest isolation on this list. The cost is that the same boundary keeping styles out also keeps a design system's shared tokens out, unless they're deliberately piped in. That's usually done through CSS custom properties, which do cross shadow boundaries by inheritance even though most other styles don't.

@scope takes a lighter approach that needs no Shadow DOM and no JavaScript at all. Chrome and Safari supported it from 2023 and early 2024 respectively, but it only became usable without a fallback once Firefox shipped support in Firefox 146, released in December 2025. That closed out cross-browser availability heading into 2026. It's the most direct native competitor to CSS Modules and BEM. It needs no build step, no hashed class names, and no naming convention to enforce by hand, just a scoping boundary declared where the styles are written.

card.css CSS 
@scope (.card) to (.card-actions) {
  .title { font-weight: 600; }
  .body  { color: var(--text-dim); }
}
/* .card-actions and anything inside it fall outside the scope */
ToolSolvesDoesn't solveBest fit
Shadow DOM Namespace collisions completely, specificity wars (outside styles can't reach in) Theming requires deliberate custom-property piping, adds a real DOM boundary Web Components, design systems distributed outside a single framework
@scope Namespace collisions, specificity wars, no build step required Requires a current-generation browser support matrix Projects with a build step already, wanting to shed CSS Modules or BEM discipline

Modern Trends

Four shifts define today's CSS landscape more than any single new framework does.

The clearest trend is the one already threaded through the sections above: zero-runtime CSS-in-JS has overtaken runtime CSS-in-JS for new projects. It isn't a marginal preference. styled-components and Emotion's maintenance-mode status is a direct consequence of React Server Components making runtime style injection awkward, while Vanilla Extract, Panda CSS, and StyleX sidestep that problem by construction. A team picking CSS-in-JS today for a new project has very little reason to reach for the runtime era.

Second, co-location versus global stylesheets stopped being a binary decision. Early framework opinions pushed hard toward one extreme or the other, either one global stylesheet for the whole app or one scoped stylesheet per component with nothing shared. In practice, most codebases today land somewhere in between. Global cascade layers handle resets, tokens, and typography. Co-located, scoped styles, whether CSS Modules, @scope, or a zero-runtime CSS-in-JS library, handle anything component-specific instead. The two aren't competitors. They're different layers of the same stylesheet doing different jobs.

Third, tooling underneath CSS authoring changed more than the authoring syntax did. Lightning CSS, originally built for Parcel, ships with Vite by default for one specific job, minifying the final CSS output, and Tailwind v4's own Oxide engine uses it internally for the same reason. Replacing PostCSS entirely for the rest of the pipeline, such as nesting, autoprefixing, and custom media queries, is still an opt-in setting in Vite rather than the default. Most projects, as a result, are running a mix of the two without necessarily knowing it. That inverts a pattern from a few years earlier, when picking a CSS approach also meant picking a build tool. Today, the build tool underneath a given authoring syntax is more often a replaceable implementation detail than a permanent commitment.

The fourth and most structural shift is how much native CSS now does on its own. Cascade layers let a stylesheet declare explicit priority groups that resolve before specificity ever gets consulted. A reset layer always loses to a base layer, which always loses to a components layer, which in turn always loses to an overrides layer. That ordering holds regardless of how many selectors or IDs any individual rule inside those layers uses.

app.css CSS 
@layer reset, base, components, overrides;

@layer reset {
  #app button { all: unset; }
}

@layer overrides {
  button { color: var(--accent); }
  /* wins over the ID selector above, not because it's more
     specific, but because @layer overrides was declared later */
}

That directly ends the specificity wars from section one, natively, without BEM's naming discipline or ITCSS's manual file ordering.

Container queries, stable across major browsers since early 2023, and @scope, stable across all of them since Firefox caught up in December 2025, round out the same story. A component can now respond to its container's size and stay visually scoped to its own subtree using nothing but CSS. Neither replaces a framework outright. A large team still benefits from Tailwind's utility vocabulary or Vanilla Extract's typed tokens. Both, though, meaningfully shrink the amount of isolation and responsiveness work a framework used to be the only way to get. The practical result for architecture decisions is to evaluate what native CSS already does before reaching for a tool to do it, because the list of things only a tool can do keeps getting shorter.

Tradeoffs

No single architecture closes all six pain points from earlier in this article, so the real differences between them are which problems each one leaves for something else to solve.

Four factors explain why two teams looking at the same six pain points end up choosing differently. Team size changes how much a naming convention like BEM can be trusted to hold without tooling enforcement in a small group, but discipline scales worse than a compiler error does as more contributors join. The second is whether a project renders with SSR or React Server Components, which rules runtime CSS-in-JS in or out fairly directly, since a component that might never execute in a browser can't rely on JavaScript to produce its styles. That's the exact issue that pushed styled-components and Emotion into maintenance mode. The third is design system maturity, which decides whether a typed theme contract, the kind Vanilla Extract or Panda CSS provide, is closing a pain point a team already feels or adding structure ahead of need. The fourth is whatever a codebase is already built on, which sets the real cost of getting from here to any alternative, a cost that exists independently of how good the alternative is on paper.

None of the approaches from the previous sections closes every pain point alone. That's why most production codebases today combine two of them, not out of indecision, but because each layer addresses a different row of the pain points table from earlier. A few combinations show up often enough to name directly, alongside what each one still leaves unsolved.

CombinationPain points it closesPain points it leaves open
Tailwind + CSS Modules Namespace collisions, specificity wars, dead CSS (Tailwind), plus scoped component styles for anything too conditional for utility classes (CSS Modules) Theming still depends on convention rather than a typed contract, tooling coupling remains
Vanilla Extract or Panda CSS + @scope Namespace collisions, theming inconsistency (typed tokens), tooling coupling (static output), plus scoping for markup that isn't authored through the theme system Requires both a build step and a current browser support matrix
Sass + cascade layers Authoring ergonomics (Sass), specificity wars (layer ordering resolving before specificity) Namespace collisions and dead CSS remain unaddressed by either half

The throughline across every section of this article is how much of that second and third column used to require a framework and now doesn't. Cascade layers close the specificity-wars gap without BEM's naming discipline or ITCSS's manual file ordering. @scope closes a meaningful part of the namespace-collision gap without CSS Modules' build step or Shadow DOM's isolation boundary. Container queries close a responsiveness gap that used to require JavaScript or a component library. None of the six pain points from earlier in this article has fully moved to the native platform. Theming in particular still leans on typed tooling, but the boundary between what only a framework can do and what CSS now does on its own has moved further in the last few years than in the decade before it. The remaining choice between Tailwind, Vanilla Extract, Sass, or any other combination increasingly comes down to authoring ergonomics and team fit rather than raw capability. That's a different, and in most cases easier, decision to make than it was when this article's earlier methodologies were first written.
