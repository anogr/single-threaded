CSS at Scale

How teams keep CSS maintainable as codebases, component counts, and contributor lists grow.

Andreas Ögren
~17 min read
Last updated July 2026

A small stylesheet rarely needs much architecture. Its authors can remember the selectors, understand their order, and see where a change will land. That shared context fades as components and contributors multiply. Eventually, changing one class can affect a screen its author has never opened. CSS architecture exists to make those effects predictable again.

These problems arise because selectors share a global namespace, rules compete in the cascade, and inheritance crosses component boundaries. CSS architectures address the problems caused by these mechanisms in different ways.

Native CSS now covers more of the architecture than it once did. Cascade layers make priority explicit, @scope limits selector reach, and container queries let a component respond to its own available space. Tooling still shapes authoring constraints and team workflow.

The Scaling Problem

Three ordinary CSS mechanisms, useful at small scale, turn into liabilities once enough people are writing rules against the same page.

Selectors in an ordinary document share one global namespace. When several declarations set the same property on the same element, the cascade chooses one according to a defined order. Through inheritance, some property values pass from ancestors to descendants. These mechanisms make CSS expressive, but their effects become harder to predict when many authors work against the same document.

The browser does not associate a class name with the component that introduced it. A class selector can match elements throughout the document, regardless of which file, team, or component it was written for. A .card class in a checkout component and a .card class in a marketing component are the same selector as far as the browser is concerned. A rule written for either .card can therefore style both components. Neither team necessarily knows the other one exists.

Collisions often lead to specificity escalation. Specificity is a weight calculated from a selector. An author whose rule loses may add another class or an ID to increase that weight. Marking a declaration !important changes its cascade importance rather than its specificity. The immediate problem disappears, but the next override must clear a higher bar. Over time, local fixes create a stylesheet whose effective priority is difficult to understand from any one file.

The third problem is proving that a rule is dead. A declaration that loses in one page, viewport, or component state may still apply elsewhere. Before removing a rule, an author must know which pages and component states rely on that interaction. If tests do not exercise those cases, deleting the rule is risky, so unused CSS tends to remain.

The Pain Points

The available architectures can be compared against six recurring failure modes.

The symptoms below result from the namespace, cascade, and inheritance described in the previous section. The rest of the article uses them as a consistent comparison. An approach is useful when it addresses the failure modes a team experiences without introducing a larger cost elsewhere.

Pain pointWhat it looks likeRoot cause
Global namespace collisions Two unrelated components pick the same class name, one silently overrides the other's styles after a merge. Ordinary class names are not locally scoped.
Specificity wars Overrides pile up as extra selector segments, then ID selectors, then !important, because class rules keep losing to higher-priority declarations. The cascade uses its defined priority order. It cannot infer which declaration an author meant to win.
Dead, unremovable CSS Stylesheets only grow. Nobody deletes a rule because nobody can prove another rule doesn't depend on it still being there. Whether a rule affects an element can depend on other rules that match the same element.
Selector and style performance Deeply nested selectors and oversized stylesheets can increase style-recalculation work, especially on large, frequently updated DOM trees. Selector matching cost depends on selector complexity and the affected elements.
Theming inconsistency Two teams both implement "the primary brand colour" with a slightly different value, because nothing enforces a single source of truth. Custom properties and design tokens remain conventions unless tooling enforces them.
Build/tooling coupling A style change requires a rebuild, or style generation adds client work as components render. Some architectures tie styling to the bundler or the JavaScript runtime.

The larger cost is uncertainty. A namespace collision may surface on a page that was never exercised during the original change. Specificity debt slows new contributors because selector priority is learned through trial and error. Uncertain ownership keeps dead rules in the bundle, while inconsistent tokens turn a visual change into a repository-wide search. Each failure may look minor on its own. Together they make routine styling work progressively harder.

Architectures and Tools

The following sections compare each approach against the same six failure modes.

No approach removes all six failure modes. BEM cannot affect build tooling because it is a naming convention. Runtime CSS-in-JS can prevent class collisions while adding client-side style work. Each option should therefore be judged against the particular problem it is meant to solve.

Methodologies

Block, Element, Modifier (BEM) is a naming convention. A component gets a block name, its internal parts get block__element names, and variations get block--modifier names, all as flat, single-class selectors with no nesting. .card__title--highlighted is unambiguous about what it styles and carries a specificity of exactly one class, the same as every other BEM selector in the codebase.

card.html HTML 
<div class="card card--highlighted">
  <h3 class="card__title">Title</h3>
  <p class="card__body">…</p>
</div>

BEM relies on flat selectors. Rules written as single classes have equal specificity, leaving source order to resolve conflicts instead of encouraging escalation. The convention does not guarantee unique block names, remove unused rules, or enforce theme tokens. It organizes a shared namespace without isolating it.

Scalable and Modular Architecture for CSS (SMACSS) and Object-Oriented CSS (OOCSS) add organizational rules. OOCSS separates reusable structure from visual skin. SMACSS groups rules into categories such as base, layout, module, state, and theme. Both remain useful when maintaining codebases already organized around them.

Inverted Triangle CSS (ITCSS) focuses on order. Generic, low-specificity rules appear first, followed by increasingly specific components, utilities, and overrides. Later rules therefore also tend to have higher specificity. Cascade layers now express that priority directly in the platform, but the organizing principle remains useful.

ApproachSolvesDoesn't solveBest fit
BEM Specificity wars, via flat, equal-weight selectors Namespace collisions, dead CSS, theming Teams without a build step, or as naming discipline layered on top of any other approach
SMACSS / OOCSS Some organizational discipline through file structure Namespace collisions, specificity wars, performance Legacy codebases already organized this way
ITCSS Specificity wars, via deliberate low-to-high ordering Namespace collisions, dead CSS Large stylesheets that need cascade layers but don't have them adopted yet

Preprocessors

Sass and its SCSS syntax add variables, nesting, mixins, functions, and modules before compiling to CSS. The output still participates in the ordinary cascade, so Sass alone does not prevent namespace collisions or specificity escalation. Its value lies in authoring tools such as reusable calculations, parameterized mixins, and source organization.

Native CSS now provides nesting and custom properties, so those features no longer require a preprocessor. Sass still provides compile-time functions, loops, mixins, and a mature module system. Existing codebases can keep those capabilities without treating Sass as an architectural boundary.

Less is another CSS preprocessor with different syntax. It remains relevant where an existing project or dependency already uses it.

ToolSolvesDoesn't solveBest fit
Sass / SCSS Authoring ergonomics: variables, mixins, nesting, partial organization Namespace collisions, specificity wars, dead CSS, tooling coupling Existing Sass codebases, or projects needing compile-time functions, loops, or mixins
Less The same authoring category as Sass The same namespace, cascade, dead-CSS, and build-coupling gaps as Sass Legacy projects already using Less

CSS-in-JS

CSS-in-JS covers two different implementation strategies. Runtime libraries such as styled-components and Emotion evaluate style definitions and coordinate generated class names while the application renders. Build-time libraries, often called zero-runtime CSS-in-JS, extract CSS ahead of execution. Vanilla Extract, Panda CSS, StyleX, and Linaria use this strategy. The browser receives a static stylesheet while application code refers to generated class names.

The code for React Server Components is not sent to the browser. A runtime CSS-in-JS library therefore needs framework support to collect styles during server rendering and to manage styles when interactive components run in the browser. Extracted CSS avoids that coordination because the stylesheet exists before either server or client components render. Existing runtime CSS-in-JS applications can continue to work, but new architecture decisions should account for that execution model.

Build-time tools differ in their authoring models and generated CSS. Vanilla Extract emphasizes typed theme contracts and CSS authored from TypeScript. Panda CSS generates utilities and recipes from a token system. StyleX produces atomic CSS and is designed for large codebases. Linaria extracts styles written with CSS-in-JS syntax. Their common property is static output.

Some build-time tools also type the theme contract. Vanilla Extract and Panda CSS can make token names part of the TypeScript program, so an unknown token fails during development instead of becoming a missing CSS value. Sass variables are checked while Sass compiles, but CSS custom-property references remain strings unless another tool validates them.

theme.css.ts TypeScript 
import { createTheme } from '@vanilla-extract/css';

export const [themeClass, vars] = createTheme({
  color: {
    brand: '#3a6ea5',
    text: '#1a1a1a',
  },
  space: {
    sm: '8px',
    md: '16px',
  },
});

// vars.color.brnad would fail to compile: no such token exists

A design system defines the values inside a theme contract, including type scales, spacing scales, and colors assigned to interface meanings.

ToolEraSolvesDoesn't solveBest fit
styled-components / Emotion Runtime Namespace collisions, via generated scoped class names Tooling coupling, server-rendering integration, theming type-safety Existing codebases, or products that need runtime-dependent style generation
Vanilla Extract / Panda CSS Zero-runtime Generated class names, typed theme contracts, no runtime style generation Still requires a build step and tool integration TypeScript codebases with a design system to enforce
StyleX / Linaria Zero-runtime Generated class names and static CSS output Tool-specific constraints, a required extraction step, and varying theme guarantees Codebases that want static CSS with CSS-in-JS authoring

Utility-First CSS

Utility-first frameworks invert the usual authoring model. Instead of defining a semantic .card selector, a component applies small classes such as flex items-center gap-4 rounded-lg border. Each class represents a narrow styling decision, and the repeated vocabulary is shared across the project. Tailwind is the most prominent implementation of this approach.

Tailwind v4 introduced a new engine, integrated Lightning CSS, and moved common configuration into CSS. A basic project can begin with @import "tailwindcss" and define design tokens through @theme. JavaScript configuration remains available for compatibility, but it is no longer the center of the default authoring model.

A generated utility vocabulary avoids local class-name collisions and keeps selector specificity low. Tailwind also emits CSS from the candidates it discovers in source files, which limits unused output. Utility classes put more styling information in markup. Responsive states, interaction variants, and conditional classes can make a component's visual intent difficult to scan. Component helpers can keep long utility combinations out of repeated call sites. Teams must then maintain those helpers as an additional convention.

Tachyons established many of the same functional-CSS ideas earlier. It remains useful in existing projects, while Tailwind offers the larger contemporary ecosystem and a more extensive variant system.

ToolSolvesDoesn't solveBest fit
Tailwind v4 Namespace collisions, specificity wars, dead CSS Tooling coupling still ties styling to a build step, plus markup density Teams using component frameworks and a shared utility vocabulary
Tachyons Same mechanism as Tailwind Smaller vocabulary and ecosystem than Tailwind Existing functional-CSS codebases

Scoped & Hashed CSS

CSS Modules address the same namespace problem during the build. A stylesheet is written as ordinary CSS, one file per component. The build step rewrites every local class name into a generated name, so .card might become .Card_card__a3f9k before the browser sees it. The component references the original name through an imported object, styles.card, so authoring still looks like normal CSS while the page uses the generated selector.

Generated names prevent local class-name collisions. Two components can still make incompatible layout assumptions about shared markup, and global selectors can still match elements in either module. CSS Modules therefore do not make every interaction in the cascade predictable.

CSS Modules solve local class-name collisions and encourage component-sized stylesheets. Flat selectors can also keep specificity manageable, although the format does not enforce that discipline. Theming still needs tokens, and unused CSS depends on what the build tool can eliminate. Authors write ordinary CSS while the build supplies generated local names.

ToolSolvesDoesn't solveBest fit
CSS Modules Class-name collisions between modules, via generated local names Theming, tooling coupling, specificity wars if authors nest deeply Component-per-file frameworks without a full CSS-in-JS or utility system
Bundler hash classes (Webpack / Vite) Same mechanism as CSS Modules, without the authoring layer Same gaps as CSS Modules Teams that want scoping without the CSS Modules import convention

Native Component Scoping

Two browser mechanisms constrain style reach without generated class names, although they create different kinds of boundary.

Attaching a shadow root to an element creates an isolated subtree with its own style scope. Selectors inside the shadow root do not match elements outside it, and document selectors do not normally cross into the shadow tree. Inherited properties, including CSS custom properties, can still cross the host boundary. Design systems can use inherited custom properties as a deliberate channel for tokens while keeping ordinary selectors isolated.

@scope limits a group of selectors to a DOM subtree and can define a lower boundary where that scope stops. The feature reached Baseline newly available status in December 2025, so projects supporting older browser releases may still need a fallback. Unlike Shadow DOM, @scope does not create a separate DOM tree or block outside styles.

card.css CSS 
@scope (.card) to (.card-actions) {
  .title { font-weight: 600; }
  .body  { color: var(--text-dim); }
}
/* .card-actions and anything inside it fall outside the scope */
ToolSolvesDoesn't solveBest fit
Shadow DOM Selector collisions across the shadow boundary, because outside selectors do not normally reach in Specificity conflicts inside the shadow tree, a deliberate theming API, and DOM integration costs Web Components, design systems distributed outside a single framework
@scope Selector reach within a subtree, with no build step required Class names remain global, and document rules can still match elements within the scope. Older browsers may need a fallback. Projects whose browser support range includes @scope

Modern Trends

Four shifts matter more than any individual styling library.

Static extraction lets teams use CSS-in-JS authoring without generating styles at runtime. Some components in a server-first application never execute in the browser, so they cannot generate styles there at runtime. The extracted stylesheet exists before those components render. Runtime libraries remain viable where their dynamic behavior and existing ecosystem justify the client work.

Global styles and co-located component styles can be used together. Global layers can define resets, tokens, typography, and shared utilities. Component-level styles can then use CSS Modules, @scope, or static extraction. Global and component-level styles handle different responsibilities within one cascade.

CSS processing can be chosen independently of authoring syntax. Tools such as Lightning CSS can transform and minify output regardless of whether the source came from plain CSS, a utility framework, or generated styles. PostCSS remains common where plugins provide project-specific transforms. A team can often change this processing layer without rewriting the styling model used by components.

Native CSS gives authors more control over cascade order. Cascade layers declare priority groups that resolve before specificity within those groups. If the order is reset, base, utilities, components, and overrides, a normal rule in the later overrides layer can outrank a more specific rule in reset.

app.css CSS 
@layer reset, base, utilities, components, overrides;

@layer reset {
  #app button { all: unset; }
}

@layer overrides {
  button { color: var(--accent); }
  /* wins over the ID selector above because @layer overrides
     was declared later */
}

Cascade layers set priority between architectural groups before specificity is compared within a group. Specificity still matters between competing rules inside the same layer. The example and figure use normal declarations. Important declarations reverse the order of named layers, while normal declarations outside any layer outrank layered normal declarations.

Container queries and @scope extend that native toolset. A component can respond to the size of its container and limit selectors to its subtree without JavaScript. Frameworks and build tools still add shared vocabularies, typed tokens, extraction, and compatibility transforms. The architecture decision should begin with the platform boundary and add tooling for constraints CSS does not enforce on its own.

Tradeoffs

No single architecture addresses all six pain points from earlier in this article. Each leaves some problems unresolved.

Teams choose differently because four project constraints vary. Naming discipline becomes harder to enforce as the contributor count grows. Runtime style generation must fit the application's rendering model. Typed tokens help when a team already maintains a governed token vocabulary in its design system. Migration cost depends on the existing codebase and often matters more than a cleaner architecture on paper.

Combinations are common because each layer can address a different failure mode. A project may use cascade layers for priority, CSS Modules for local names, and custom properties for shared tokens. The useful question is whether every added mechanism has a distinct responsibility.

CombinationPain points it addressesPain points it leaves open
Tailwind + CSS Modules Namespace collisions, specificity wars, dead CSS (Tailwind), plus scoped component styles for anything too conditional for utility classes (CSS Modules) Theming still depends on convention rather than a typed contract, tooling coupling remains
Vanilla Extract or Panda CSS + @scope Generated names, typed tokens, static output, and bounded selectors Build coupling remains; older browsers may need a scoping fallback
Sass + cascade layers Authoring ergonomics (Sass), specificity wars (layer ordering resolving before specificity) Namespace collisions and dead CSS remain unaddressed by either half

Native CSS now addresses more of the original scaling problem. Cascade layers define architectural priority, @scope limits selector reach, and container queries provide component-level responsiveness. Tooling still adds valuable guarantees around token types, generated vocabularies, extraction, and compatibility.

Teams usually need only enough mechanisms to make ownership and priority obvious. A team that values utility composition may prefer Tailwind. A typed design system may justify Vanilla Extract or Panda CSS. An established Sass codebase can adopt cascade layers without rewriting its authoring model. The durable architecture is the one contributors can understand and enforce.
