Testing Strategy

The testing pyramid, what's worth automating, and when manual testing still earns its place.

Deep dive
~19 min read
Automated & manual testing
July 2026

A testing strategy is a deliberate plan for where testing effort goes, based on the risk a piece of code carries, the cost of testing it, and how quickly a test gives feedback. It is not a rule that says write more tests. A team can have excellent coverage on the wrong layer and still ship regressions weekly, because the tests that exist run slowly, cover the wrong paths, or duplicate each other at three different levels.

This article covers the shapes tests come in, what separates code that's easy to test from code that fights back, and where mocking and manual testing fit around the automated core.

The Testing Pyramid

Three layers, each trading speed for realism.

The testing pyramid groups automated tests into three layers by how much of the system they exercise. Unit tests sit at the base, checking one function or module in isolation. Integration tests sit in the middle, checking that several pieces work together. End-to-end tests sit at the top, driving the whole system the way a real user would. The pyramid shape is the point: many cheap, fast tests at the bottom, fewer slow, expensive ones at the top.

A common way teams misread the pyramid is treating it as a ratio to hit, aiming for roughly even counts across the three layers, or a fixed percentage split. The shape isn't a target to engineer toward. It's a description of where confidence is cheapest to buy. The right question for any given piece of code is which layer catches its most likely failure for the least cost, not which layer is under-represented in this week's coverage report.

Unit Tests

A unit test calls one function or one small module directly and checks its output against an expected value, without starting a server, hitting a network, or touching a real database. That isolation is what makes unit tests fast enough to run in the hundreds on every save and cheap enough to write in bulk. Their blind spot is exactly what they exclude. A unit test can pass on every function in a request-handling path and still miss a bug that only shows up once those functions are wired together in the wrong order.

For UI code specifically, the unit under test is often a single component rendered in isolation with mocked props and dependencies. It's checked with a tool like Testing Library rather than by calling a plain function directly, but it's still the same layer: no real server, no real network, no real backing store.

Integration Tests

An integration test exercises more than one piece at once, such as a function together with a real database, or two internal modules calling each other without any mocks between them. It answers a question a unit test can't: not just whether each piece works alone, but whether they still work once they're connected. Integration tests run slower than unit tests because they touch more real infrastructure, so a team typically writes fewer of them and reserves them for the seams between components rather than every internal detail.

A contract test checks that one side's requests and the other side's responses still agree on shape. The boundary it checks sits between two services owned by different teams, or between a frontend and a backend built on separate schedules. It's commonly grouped with integration testing, since it targets the same kind of boundary. Many practitioners still treat it as its own technique, because a contract test usually runs without both sides live at the same time, checking each one independently against a shared, agreed-upon schema instead. This is the same territory covered by OpenAPI's mock and contract tooling in RESTful API Design. A published schema lets each side generate a mock of the other and test against it independently, catching a breaking change before it reaches a shared environment.

Consumer-driven contract testing tools such as Pact take a related but distinct approach. Instead of validating against a shared schema, the consumer records the exact requests it expects to make. That recording is replayed later against the real provider, independently of the consumer, to verify the provider still honors it.

End-to-End Tests

An end-to-end test drives the full system through a real interface, typically a browser automated with a tool like Playwright, clicking through the same flow a person would. It's the closest an automated test gets to proving a feature actually works. It's also the slowest and most fragile layer, because it depends on UI timing, network latency, and whatever state the environment happens to be in when the test runs. A layout change, a slow API response, or a leftover row from a previous test run can all fail an end-to-end test without the underlying feature being broken at all.

That fragility is usually called a flaky test: one that fails intermittently for reasons unrelated to the code under test. The fix is rarely to write more end-to-end tests and hope. Seeding deterministic test data instead of relying on whatever the environment already contains removes one common source. Retrying a failed run once before marking it broken absorbs transient network or timing noise. And a test that keeps failing without a clear cause is better quarantined into a separate, tracked bucket than left in the main suite, where it trains a team to ignore red builds.

Because each end-to-end test is expensive to write and run, it's worth reserving for critical paths: flows such as sign-up, checkout, or anything that risks corrupting a user's data if it silently breaks. A secondary settings page that's easy to click through and easy to spot when broken is a weaker candidate for this layer than a payment flow nobody looks at until it fails in production.

Writing a Good Test

The pyramid says which layer to test at. These three habits apply no matter which layer you're writing for.

Most tests, at any layer, follow the same three-part shape known as AAA: Arrange, Act, Assert. Arrange sets up whatever the test needs, the inputs, the initial state, any fakes standing in for a dependency. Act runs the one thing under test. Assert checks that the result is what it should be. Structuring a test this way, even with comments marking the three parts, makes it easy to scan later and easy to tell which part broke when it fails.

discount.test.ts TS 
test("applies the holiday discount", () => {
  // Arrange
  const total = 100;
  const isHoliday = true;

  // Act
  const result = calculateDiscountedTotal(total, isHoliday);

  // Assert
  expect(result).toBe(80);
});

A second habit is independence: a test should pass or fail the same way no matter which other tests ran before it, or in what order. A test that relies on a row another test happens to have left in a shared database, or on a module-level variable a previous test set, is not independent. It works until someone reorders the suite or runs a single test in isolation. At that point it fails for reasons that have nothing to do with the code being tested. Each test should set up the state it needs itself and leave nothing behind for the next one to trip over.

The third habit is writing from the right perspective. A unit test should exercise a function the way its caller actually uses it, through the same arguments and return value the rest of the codebase relies on. It shouldn't reach into private internals the function is free to change tomorrow without breaking that contract. An end-to-end test should go further and take a human's perspective specifically. It should click, type, and read the screen the way a person actually would. What it shouldn't do is reach into implementation details like a CSS class name or an internal component name, since a person testing the app by hand would never see either one. That distinction is also the design philosophy behind Testing Library, covered next.

Testability: What Makes Code Hard or Easy to Test

The pyramid describes the shapes tests come in. This is about why some code accepts any of those shapes easily, and some resists all of them.

A pure function always returns the same output for the same input and has no effect on anything outside itself. That makes it trivial to test: call it, check the return value, done. Nothing needs to be set up first and nothing needs to be cleaned up afterward. React relies on this property directly, since a component's rendered output is meant to depend only on its props and state, which is also what makes it testable and predictable in the first place.

A side effect is anything a function does beyond computing and returning a value. Writing to a database, calling fetch, reading or writing localStorage, and triggering a React state update as a byproduct of running are all side effects. None of these are mistakes on their own; software needs to read files and talk to networks to be useful. The problem shows up when a side effect is buried inside a function that looks like it should be a simple calculation. A test of that function then has to somehow deal with a network call or a browser API it didn't ask for.

A concrete version of this shows up often in React. A component that reads directly from localStorage inside its render logic is hard to test, since a test would have to seed that storage first just to render the component at all. Passing the stored value in as a prop moves that same side effect to the edge instead of burying it in render. A context provider a test can substitute a fake value into works the same way.

The other common failure is a unit with too many dependencies, or dependencies it never admits to. A function that reaches into a module-level singleton, calls a static method on some shared class, or imports three levels deep into another feature's internals is fine to call in production. All of that machinery is already wired up there. In a test, every one of those reached-for pieces has to exist too, even though the test only cares about the one calculation the function is actually responsible for.

Easy to test
Explicit, self-contained

Pure functions, dependencies passed in as parameters, no reach into globals, singletons, or the DOM.

Hard to test
Buried, far-reaching

Side effects mixed into calculations, module-level singletons, static methods, or deep imports into unrelated modules.

The usual fix for both problems is the same: separate deciding what to do from doing it, and hand a function its dependencies instead of letting it go find them. The code below shows the difference. The first version computes a discount and also reaches for the database, the system clock, and an email service, all inside one function. The second version only computes, and takes exactly the values it needs as arguments.

discount.ts TS 
// Hard to test: hidden dependencies and a side effect, all in one function.
async function applyDiscount(orderId: string): Promise<number> {
  const order = await db.orders.find(orderId);   // hidden dependency: a real database
  const discounted = order.total * (isHoliday(new Date()) ? 0.8 : 1);
  await emailService.send(order.customerEmail, `New total: ${discounted}`); // side effect
  return discounted;
}

// Easy to test: a pure function, every dependency passed in explicitly.
function calculateDiscountedTotal(total: number, isHoliday: boolean): number {
  return total * (isHoliday ? 0.8 : 1);
}

Neither the database call nor the email send disappeared. They moved to the edges of the code instead. That move is dependency injection: a function receives its dependencies as parameters instead of constructing or reaching for them internally. It's what makes it possible to swap in a fake version for a test without touching the calculation itself. A component that reaches for the whole tree to answer one narrow question suffers from the same root issue at a different scale.

Mocking

Once a dependency is passed in rather than reached for, a test can hand it something fake.

Mocking replaces a real dependency with a fake stand-in that a test controls completely. A mock database returns exactly the row a test asks it to, instantly, without a network round trip or any data left behind for the next test to trip over. Continuing the discount example, once emailService is a parameter instead of a reached-for import, a test can substitute a fake one and check that it was called correctly, without ever sending a real email.

discount.test.ts TS 
interface EmailService {
  send(to: string, body: string): Promise<void>;
}

const fakeEmailService: EmailService = { send: vi.fn().mockResolvedValue(undefined) };

test("notifies the customer with the new total", async () => {
  await notifyCustomer(order, fakeEmailService);
  expect(fakeEmailService.send).toHaveBeenCalledWith(
    order.customerEmail,
    expect.stringContaining("New total")
  );
});

Mocking makes otherwise untestable code testable, but it has a failure mode of its own. A test suite that mocks aggressively can end up checking that a function called a fake in the expected way. That's a slightly different claim from checking that the function behaves correctly against something real. If the real email service changes its interface and the mock isn't updated to match, every test built on that mock keeps passing while the actual integration is broken.

Keeping mocks honest

A few habits keep over-mocking in check. Prefer a real dependency over a mock inside integration tests, saving mocks for the unit-test layer where isolation is the point. Reserve mocking for dependencies genuinely external to the code under test, such as a third-party API or a payment provider, rather than mocking internal collaborators out of convenience. Revisit a long-lived mock's shape periodically against the real dependency's current interface, so the fake doesn't quietly drift out of sync with the thing it's standing in for. And in frontend code specifically, prefer intercepting at the network level with a tool like Mock Service Worker over hand-mocking fetch directly. A network-level mock stays honest against the same request and response shapes the real backend actually uses.

Unit and Component Tools

A test runner, a query philosophy, and one technique worth using carefully.

Jest and Vitest are the two dominant test runners for JavaScript and TypeScript, and both bundle a test runner, an assertion library, and mocking support into one tool rather than requiring three separate packages. Jest, built at Facebook for React, has the longer track record and the larger ecosystem of plugins and prior art to search when something goes wrong. Vitest is built on top of Vite, reuses a project's existing Vite configuration instead of needing a separate transform pipeline, and runs faster in a Vite-based project as a result. Vitest's API is close enough to Jest's that most teams can read one having only used the other.

Testing Library (React Testing Library, Vue Testing Library, and similar bindings for other frameworks) is not a test runner. It's a set of query functions layered on top of one, built specifically around the user-perspective habit described earlier. Instead of selecting an element by a CSS class or a component's internal name, a test asks for the button a user would see. It can query by accessible role, by visible label, or by other text and attributes an actual user would perceive on screen. That constraint is deliberate. If a query is hard to write because the markup has no discernible role or label, that's usually a sign the markup itself is missing something. A real user, including one relying on a screen reader, would be missing that same thing.

Both Jest and Vitest support snapshot testing: rendering a component or serializing a data structure to a file once, then failing any future run whose output no longer matches what's saved. It's a cheap way to catch an unintended change to something tedious to assert on by hand, such as a large rendered tree. The habit that undermines it is approving a failed snapshot without reading the diff first. Reviewing a change on faith replaces the saved snapshot with whatever the code now produces, even if that's the bug, and the test goes back to passing having caught nothing. Snapshot testing earns its keep only on output small enough that a person will actually read the diff before approving it.

Playwright and Cypress also support component testing, mounting a single component in isolation the way Testing Library does, but inside a real browser rather than a simulated DOM like jsdom. That trades some raw speed for catching real rendering and layout behavior a simulated DOM doesn't reproduce.

End-to-End Tools

Three tools, three different ways of getting a browser to do what the test says.

Selenium is the oldest of the three and, since version 4, drives a real browser through the W3C WebDriver protocol, a standard implemented natively by every major browser vendor. That standardization is its strength: Selenium supports the widest range of browsers and has bindings for the most programming languages, which is why large cross-browser compatibility matrices and long-lived enterprise suites still lean on it. The tradeoff is more setup and more code per test than the two newer tools below.

Cypress runs its test code inside the browser, alongside the application under test, rather than remote-controlling the browser from the outside. That architecture is what gives Cypress its well-regarded developer experience, including a time-travel debugger that lets a developer step back through a failed test's commands. It also historically limited Cypress to a single origin per test, a constraint later worked around with an explicit cy.origin() command for the cases that need to cross into a second origin. The underlying difference is still visible next to a tool that drives the browser from entirely outside it.

Playwright automates Chromium, Firefox, and WebKit through each browser's own remote-debugging protocol, out-of-process, behind one shared API. It waits automatically until an element is actionable, meaning visible, stable, and able to receive input, before interacting with it. That removes a common source of flaky end-to-end tests: a click that fires before the button has actually finished appearing and settling into place. That combination has made Playwright the common default for new end-to-end suites, without erasing Selenium's advantage in raw browser and language coverage or Cypress's advantage in in-browser debugging feel.

What's Worth Automating

The pyramid already answers most of this, layer by layer.

Unit and integration tests are worth automating almost without exception. They're cheap enough to run on every commit, and any regression they'd catch is worth catching before a person ever has to notice it manually. End-to-end automation is worth it selectively, aimed at the critical paths described earlier, and not stretched to cover every screen just because the tooling makes it possible.

Manual testing still earns its place in what's left over. A person can explore a new feature and deliberately try to break it in ways no one thought to script in advance. Visual review of a redesign is another case, since "does this look right" doesn't reduce to an assertion. Tools like Percy or Chromatic can automatically flag a pixel-level difference, but a person still has to judge whether the new appearance is actually correct or just different. Usability judgment is a third case: whether a flow that technically works is actually pleasant to use. None of that is a gap in the automation strategy. It's work that doesn't automate well, because the thing being checked isn't a fixed expected output but a judgment call a person is better positioned to make.

Coverage tooling reports what percentage of lines or branches a test suite executed, and it's tempting to treat that number as the goal itself. It isn't. A line can run during a test without the test ever checking what that line produced, which is enough to count as covered while catching nothing. Full coverage is achievable and still not the same thing as a correct program. An untested edge case, such as an empty input, a boundary value, or an error path, can sit right next to a hundred well-covered lines that never exercise it. Coverage is worth watching as a rough map of what's untested at all, not as a percentage to chase for its own sake.

Local Dev and CI

The same tests run in two different places, for two different reasons.

On a developer's own machine, a test runner's watch mode re-runs automatically on every save, often re-running only the tests affected by whatever file just changed rather than the entire suite. That narrower, near-instant loop is what makes writing a test alongside the code it covers practical instead of a chore saved for the end. Some teams add a pre-commit hook, commonly wired up with a tool like Husky, that runs the fastest subset of checks, lint plus the affected unit tests, before a commit is even created. It catches an obvious mistake a few seconds after it's made, well before it reaches a shared branch.

Once a change is pushed, the full suite runs again, this time in a continuous integration pipeline, where automated tests act as a gate a change can't pass without, covered in CI/CD and DevOps. This second run matters even though the developer's machine already passed the same tests, since it removes any doubt about whether the change also works outside that one machine's particular setup. The most expensive end-to-end suites are sometimes pulled out of that per-change gate entirely. They run instead on a schedule, overnight or a few times a day, when their cost would otherwise slow down every push. This article is about which tests earn a place in that gate and why. The CI/CD article is about what happens once they do.
