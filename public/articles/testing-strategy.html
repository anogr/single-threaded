Testing Strategy

How risk, test levels, automation, and specialist tools combine into a testing strategy from local feedback to production.

Andreas Ögren
~30 min read
Last updated July 2026

A testing strategy is a plan for building confidence in software quality. It directs testing effort toward failures with meaningful consequences and ensures useful evidence is available when decisions need to be made. An extensive test suite can still leave important risks unexamined, particularly when its tests do not reflect how the software is expected to behave or fail.

Testing takes many forms, from automated checks to human evaluation. Developers and testers contribute different kinds of evidence throughout delivery, often at different stages and with different strengths. A coherent strategy brings that evidence together while making clear what each method can reveal and where its limits lie.

The goal is not to test everything in every possible way. It is to choose methods that address meaningful risks and provide evidence when it can still influence a decision. A good strategy makes those choices deliberate.

A Map of Software Testing

Four independent questions describe a test more clearly than one label can.

Terms such as unit test, automated test, and acceptance test describe different aspects of testing. A clearer description asks how the test is performed, how much of the system participates, what the test is intended to establish, and where it provides feedback in the delivery process.

Execution method

Execution method describes how evidence is obtained. Dynamic testing runs software and observes its behavior. Most dynamic testing in software development is automated. Automated tests supply inputs, observe results, and compare them with programmed expectations. They support repeatable testing throughout development and delivery, from fast checks of isolated code to tests that exercise complete workflows. Dynamic testing can also be performed by a person. Scripted manual testing follows prepared procedures and expected results, while exploratory testing combines learning, test design, and execution as a person investigates the software. Other methods do not execute the software. Reviews rely on human examination of requirements, designs, or code, while static analysis tools such as type checkers and linters inspect artifacts automatically.

Scope

Scope describes how much of the system participates in a test. A test might exercise a small piece of logic in isolation, several collaborating components, or a complete workflow across system boundaries. Scope affects which failures a test can expose, how easily a failure can be isolated, and how much surrounding infrastructure the test depends on.

Purpose

Purpose describes what the testing is intended to establish. A test might examine functional behavior, accessibility, security, performance, recovery, or another property that matters to the system. The purpose determines which risk or quality concern the evidence is meant to address.

Placement

Placement describes where testing provides feedback in the delivery process. The same behavior can be examined while code is being written, during continuous integration, before release, or in a production-like environment. Earlier feedback can make defects cheaper to correct, while later evaluation can reveal behavior that depends on integration, configuration, infrastructure, or realistic use.

The same workflow can be tested in different ways for different purposes. An automated checkout test might add a product, enter payment details, and confirm that an order is created. A person could exercise the same workflow using only a keyboard to evaluate its accessibility. Both tests may cover much of the same system and run at the same point in delivery while differing in execution method and purpose.

Every dynamic test needs a basis for deciding whether the observed result is acceptable. This basis is the test oracle. If a test checks an invoice total, for example, it needs an independent basis for determining what the total should be. That basis might come from a business rule or a calculation performed separately from the implementation. If the test calculates the expected total using the same incorrect rule as the application, both can agree while still producing the wrong result.

Scope How much of the system participates? Isolated logic, component, connected components, complete system

Risk-Based Test Selection

A testing strategy starts with significant risks and the evidence needed to detect them.

Risk-based testing gives more attention to failures that are likely or would have serious consequences. A failed payment, for example, can lose revenue or charge a customer incorrectly. Risk can be higher where software changes frequently, depends on an unreliable boundary, or has failed before. Identifying these risks gives the team a reason for each test before choosing how to perform it.

Consider the risk of charging a customer twice when a payment request is retried. Evidence that a normal payment succeeds is insufficient. The team needs to observe what happens when the first request succeeds but its response is lost and the request is sent again. A test can reproduce that condition and verify that only one charge is created. A different payment risk, such as an incorrect total, requires different inputs and a different oracle. No single payment test provides evidence about every important failure.

A test condition makes this reasoning explicit by stating the situation to examine and the result that should be observed. “The customer is charged once when a successful payment request is retried” is more useful than “test payment retries.” It identifies the relevant state and expected result clearly enough to guide the design of the test.

A lightweight test plan collects the important test conditions for a change and identifies which evidence is needed before release. Writing these conditions early can expose missing requirements and risky assumptions while there is still time to change the design. The plan makes uncovered risks visible so the team can decide whether further testing or another form of mitigation is needed.

Testing in Development and Collaboration

Tests and examples can clarify expected behavior before and during implementation.

Test-driven development (TDD) is a programming practice in which a developer writes a small failing test, writes enough code to pass it, and then improves the design while keeping the tests passing. This short cycle uses tests to guide implementation and creates focused regression checks as the code develops. TDD has had considerable influence on software development practice, particularly the idea that tests can help shape code rather than merely check finished code. Teams may adopt that idea without consistently following the full TDD cycle.

Acceptance test-driven development (ATDD) uses examples to establish the conditions for accepting a change before implementation begins. Business, development, and testing perspectives contribute to those examples so that important expectations become explicit. Selected examples can become automated acceptance tests through an interface that provides reliable evidence. The main contribution of ATDD is establishing a shared understanding of acceptance before implementation makes assumptions more expensive to change.

Behavior-driven development (BDD) uses concrete examples to discover and describe how a system should behave. Business and technical participants develop those examples together to resolve ambiguity and build a shared understanding of the required behavior. The words Given, When, and Then can give an example a readable structure. Given a payment has succeeded, when the request is retried, then the customer is not charged again. Selected examples can be connected to automated tests. BDD puts the discussion of observable behavior at the center of development rather than treating examples primarily as test cases.

These practices use tests and examples at different points in development, but they share an emphasis on making expectations concrete. For a payment retry, the expected outcome might be that the customer is charged exactly once even when a successful request is repeated. Product knowledge establishes that expectation, implementation knowledge identifies where duplicate processing can occur, and testing knowledge helps reproduce the interruption and observe the result. The result is a specific condition that can guide implementation and later provide evidence that the expected behavior holds.

Test Levels from Units to Complete Systems

Test level describes the boundary around the software that participates in a test.

A test level describes how broadly a test exercises the system. A narrow boundary supports fast feedback and makes failures easier to locate. A wider boundary includes interactions that narrower tests deliberately exclude. The useful boundary depends on the risk and the evidence needed.

Teams use different names for the same kind of tests. We will use unit, component, integration, and system to describe increasingly broad test boundaries. Other common labels describe something different. An API test identifies the entry point, a contract test examines an agreement at a boundary, an end-to-end test emphasizes a complete journey, and acceptance testing describes whether the result is fit for stakeholder use.

Unit and Component Tests

A unit test exercises a small, deliberately isolated part of the software. The unit may be a function, class, module, or another boundary chosen by the codebase. Unit tests usually control dependencies that would make execution slow, unpredictable, or difficult to reproduce. Their narrow scope supports fast feedback and precise failures.

A component test exercises a larger part of the software while controlling systems outside its boundary. For example, a frontend component test might render a page with its real routing and state management while supplying controlled responses for external requests. Component tests allow related parts to interact without requiring the complete system to be deployed.

Unit and component tests are useful when the important behavior fits inside a narrow boundary. Tests with wider boundaries are needed when the risk depends on collaboration between parts.

Integration, API, and Contract Tests

An integration test examines whether parts work together through a real connection between them. Application code running against a real database is one example. Dependencies outside the integration being examined can be controlled so that the test focuses on the connection.

An application programming interface (API) test enters the system through a programmatic interface. The label identifies the entry point, not the scope. A test of one HTTP handler with controlled collaborators may have component scope, while a request sent to a deployed service with its real database may have system scope.

A contract test checks whether software on either side of a boundary agrees about their interaction. It can verify that requests, responses, or messages conform to an agreed structure and meaning. Consumer-driven contract testing derives those expectations from the interactions required by a consumer and verifies that the provider continues to satisfy them. Contract tests are especially useful for detecting incompatible changes between independently developed services.

System, End-to-End, and Acceptance Tests

In this article, a system test exercises the complete integrated system against specified behavior. The entry point can be a browser, API, command line, message, or device interface. A system test can examine a narrow rule or a longer workflow. Its defining property is the complete system boundary.

An end-to-end test follows a journey through the participating system from an external interface. System and end-to-end boundaries may coincide, but end-to-end emphasizes the path through them. A browser test might sign in, add an item, pay, and verify the resulting order. This provides evidence that the parts required for that journey are assembled and configured well enough for the journey to succeed.

Acceptance testing evaluates whether stakeholders can accept a feature or system. Acceptance criteria may be checked at unit, API, or browser level, while user acceptance testing may involve business representatives working through realistic scenarios. Fitness for use defines the acceptance decision, while the technical boundary can vary.

Functional Behavior and Quality Attributes

Testing checks both what the system does and how well it behaves.

Functional testing checks whether the system behaves according to its rules and user needs. A test might verify that a discount is calculated correctly, an unauthorized action is rejected, or an order is created after payment. Functional tests can run at any test level. The useful boundary depends on where the behavior is implemented and which interactions could cause it to fail.

A quality attribute describes how well a system behaves under a relevant condition. Performance under peak traffic, protection against unauthorized access, keyboard operation, and recovery from a failed dependency are examples. Testing a quality attribute requires an observable expectation, such as a response-time threshold, an accessibility requirement, or a recovery target. Without such an oracle, a broad goal such as “the system should be fast” cannot produce a meaningful test result.

Performance

Performance testing measures behavior under a defined workload. Response time and throughput might be checked at expected traffic, while heavier workloads can reveal where capacity begins to fail. Longer runs can expose gradual degradation such as resource exhaustion. Tools such as k6 generate controlled workloads and evaluate performance thresholds.

Security

Security testing examines whether the system protects data and operations against misuse. Automated analysis can detect known weaknesses in source code, dependencies, configuration, or a running application. For web applications, tools such as ZAP probe a running application for common vulnerabilities. Other security testing exercises abuse cases derived from the system's design and threat model. Security testing therefore combines repeatable automated checks with investigation of how the application could be misused.

Accessibility

Accessibility testing examines whether people with disabilities can perceive, operate, and understand the interface. Automated tools such as axe-core can detect many rule-based problems in rendered markup. Other requirements depend on interaction and meaning, so keyboard operation, screen-reader use, zoom and reflow, and human evaluation provide important evidence.

Other Quality Risks

Other risks require targeted testing when they can affect the application. Compatibility testing checks behavior in supported browsers, devices, and operating systems where platform differences could affect the result. Resilience and recovery testing introduces failures and observes whether the system stays safe and recovers correctly. Applications with important state transitions may need tests for concurrency, data integrity, and migrations. Locale, time zone, and visual rendering deserve similar attention when they can change an important outcome. These tests should be selected because a specific risk requires their evidence, not because every application needs every testing category.

Tests for Changes and Releases

After a change, testing provides evidence that the change works and that the software is ready to move forward.

Tests used after a change often reuse the same levels and quality checks described earlier, but serve a different purpose. Confirmation testing repeats the condition that exposed a defect to verify that the correction works. Regression testing checks previously working behavior for unintended effects of the change. A test created to confirm a defect correction often remains as a regression test when the same failure could return.

A smoke test is a small set of broad checks used to decide whether a build or environment is stable enough for further testing. For a web application, it might confirm that the application starts and that a user can sign in. Teams sometimes use sanity check for a narrower check of the area that changed. Because these terms vary between teams, the important information is what is checked and which decision the result supports.

The testing required before release should follow the risks introduced by the change. A copy change might need a focused check of rendering and accessibility, while a payment migration needs evidence that existing data is converted correctly and customers cannot be charged twice. A fixed release suite can still provide a useful baseline, but risk determines which additional evidence a particular change requires.

The Test Portfolio

A useful portfolio combines fast feedback with evidence from the boundaries where important failures can occur.

A test portfolio is the combination of tests and other evaluation activities used to provide evidence about a system. For automated functional testing, the testing pyramid offers a useful economic model. It favors many narrow tests because they are usually fast to run and make failures easier to locate. Fewer tests exercise broader boundaries where setup, execution, and diagnosis cost more.

The useful shape depends on the architecture and its risks. A frontend application, for example, may place substantial testing at component boundaries because much of its behavior emerges there. Another system may need more evidence at service or data boundaries. The goal is not to reproduce a geometric shape but to obtain useful coverage while keeping feedback fast and failures diagnosable.

Human evaluation complements the automated portfolio. Exploratory testing can investigate unexpected behavior, usability evaluation can reveal whether a workflow supports real users, and security review can challenge assumptions about how the system might be abused. Automation is effective when a check needs to run repeatedly and has an oracle that software can evaluate. A testing strategy combines these forms of evidence according to the risks the system faces.

Effective Test Design

A useful test has a trustworthy oracle, representative inputs, and one clear, decision-relevant claim.

A test technique guides the selection of test conditions and cases. Specification-based techniques derive cases from required behavior, structure-based techniques use the internal structure of the software, and experience-based techniques draw on domain knowledge and likely failures. These approaches are complementary rather than competing ways to find useful tests.

Oracles and Inputs

A test needs a trustworthy basis for deciding whether its observation is acceptable. The test oracle should come from a requirement, business rule, or another source outside the implementation being checked. Repeating the implementation's reasoning inside the test can reproduce the same mistake and allow both to agree on a wrong result. Inputs should concentrate on places where behavior changes. For a discount that starts at €100, values immediately below, at, and above €100 are usually more informative than several arbitrary totals.

Coverage as Evidence

Code coverage reports which parts of the implementation executed during testing. Line or branch coverage can reveal code that no test reaches, but execution alone does not show that the behavior was meaningfully checked. Coverage is therefore most useful for finding gaps rather than establishing quality. Mutation testing goes further by deliberately changing program behavior and checking whether the tests detect the change. A surviving mutation can reveal a weak input or assertion even when code coverage is high.

Experience provides another source of test cases. Defects seen in similar systems, knowledge of the domain, and observations made while exploring the application can reveal conditions absent from a specification or coverage report. Exploratory testing and error guessing formalize this kind of learning without requiring every useful case to be known in advance.

Generated Inputs

Property-based testing generates many inputs and checks that an invariant continues to hold. A pricing test, for example, might require every valid discounted total to stay between zero and the original total. Fuzz testing supplies unexpected or malformed inputs to expose crashes, unsafe parsing, and unhandled states. Both techniques extend testing beyond a small set of examples chosen by hand.

Readable Automated Tests

Many automated tests can be read as Arrange, Act, Assert (AAA). Arrange establishes the relevant state and inputs, Act performs the behavior under examination, and Assert compares the observation with the oracle. Keeping those parts visible makes the claim of the test easier to understand when it passes, fails, or needs to change.

discount.test.ts TypeScript 
test("applies the holiday discount", () => {
    const total = 100
    const holidayDiscount = 0.2

    const result = calculateDiscountedTotal(total, holidayDiscount)

    expect(result).toBe(80)
  })

Repeatability and Observable Behavior

A reliable automated test produces the same result when the relevant conditions are the same. Tests should create the state they need rather than depend on execution order or state left by another test. Time, randomness, network responses, and asynchronous work need control when they affect the result. This makes failures reproducible instead of dependent on hidden conditions.

Tests should usually make assertions about observable behavior rather than incidental implementation details. A unit test can check the result of an exported function, while a browser test can interact with a control and verify what the user can observe. A test that asserts private state, exact internal call order, or unnecessary markup structure can fail after a harmless refactoring even though the required behavior is unchanged. The opposite problem occurs when a test observes too little and continues to pass despite incorrect behavior. Structure-based techniques such as code coverage and mutation testing can help find these gaps without making the assertions depend on the implementation.

Testability in Software Design

Testable software makes relevant conditions easy to create and meaningful outcomes easy to observe.

Testability describes how easily software can be tested under relevant conditions. Controllability means a test can provide inputs and establish relevant state. Observability means it can inspect the resulting behavior. When important inputs are hidden or outcomes are difficult to observe, tests require more setup and failures become harder to understand.

Software design determines much of that control and observation. A pure function is an especially simple example where the same inputs produce the same output without reading or changing external state. A pricing calculation expressed as a pure function can be tested directly without touching side effects such as a database, network, or clock. Real applications still need those external interactions, but keeping decisions separate from infrastructure often makes both easier to test.

Frontend code has the same design pressure. A component that reads directly from localStorage during rendering requires storage to be prepared before each relevant state can be tested. Passing the stored value as an argument separates the storage from the behavior. The application can still read localStorage at its outer boundary, while the component concentrates on rendering and interaction.

Code reads global state, constructs dependencies, and mixes decisions with external work.

The following example shows the difference. applyDiscount combines a pricing decision with database access, the current time, and email delivery. Testing the calculation therefore requires dealing with dependencies unrelated to the calculation itself. calculateDiscountedTotal receives the values it needs and exposes the result directly. A coordinating function can perform the external work and use the calculation.

discount.ts TypeScript 
  // The pricing decision is mixed with external work.
  async function applyDiscount(orderId: string): Promise<number> {
    const order = await db.orders.find(orderId)
    const discount = isHoliday(new Date()) ? 0.2 : 0
    const total = order.total * (1 - discount)
    await emailService.send(order.customerEmail, `New total ${total}`)
    return total
  }

  // The pricing decision has explicit inputs and an observable result.
  function calculateDiscountedTotal(
    total: number,
    discount: number
  ): number {
    return total * (1 - discount)
  }

A boundary where a test can control an input or substitute an external dependency is sometimes called a test seam. Dependency injection is one way to create such a boundary by supplying a dependency from outside the code that uses it. A clock, repository, or service client can then use the real implementation in production and a controlled implementation when a test needs specific behavior.

Test Doubles and Controlled Dependencies

A test double controls a dependency so that a test can create specific conditions or observe an interaction.

A test double stands in for a dependency during a test. Different names describe the role it plays. A stub supplies predetermined results, a fake provides a simplified working implementation, and a spy records interactions. A mock defines expected interactions and checks whether they occur. Testing libraries often use mock as a general term, so what the substitute does matters more than what the API calls it.

Double Primary job Example
Stub Supply a result Return a fixed exchange rate
Fake Provide a lightweight implementation Store orders in memory
Spy Record an interaction Capture an email request
Mock Check an expected interaction Require one payment request

Suppose a test needs to check that an order confirmation requests the correct email. A spy can record the recipient and message passed to the email gateway without sending a real message. This gives the test evidence about the application’s request to the gateway, but not about whether the production gateway can communicate with the email provider. That connection requires evidence from a test that includes the real adapter or provider boundary.

This limitation applies to every test double. A substitute controls part of the test by replacing real behavior, so the test cannot establish that the replacement still matches the real dependency. If a payment provider changes its response format, tests using an old stub may continue to pass. Integration or contract tests can detect that disagreement at boundaries where compatibility matters.

Web applications often use Mock Service Worker (MSW) to intercept network requests and return controlled responses. Because the application still uses its normal HTTP client and response-handling code, these tests exercise more of the request path than replacing the client itself. The simulated response can still drift from the real API, so contract or integration testing should provide evidence about that external agreement.

Automation Decisions

Automation is most valuable when useful evidence needs to be produced repeatedly and quickly.

A strong automation candidate has a trustworthy oracle that software can evaluate, repeatable setup, and enough regression risk to justify repeated execution. A payment calculation fits because every run can compare the result with an expected value. Usability evaluation is different because judging whether an interaction works well requires human observation. Automation can still prepare accounts, data, and environments so that the person can concentrate on the evaluation.

Frequency and timing determine much of automation's value. A check that runs on every change can detect a regression minutes after it is introduced and provide evidence before the change moves forward. A condition examined once during a migration may be cheaper to test manually when automation would require substantial setup that has little future use.

Maintenance is part of the cost of automation. Brittle selectors, shared state, fixed delays, and duplicated setup make tests fail for reasons unrelated to the behavior they protect. Repeated unreliable failures reduce trust and encourage people to ignore results. A test should be repaired when it still supplies useful evidence and removed when it no longer supports a decision.

Testing Tools by Job

Choose testing tools by the job they perform, not by expecting one framework to cover every kind of evidence.

A web testing stack usually has several layers. A test framework discovers and runs tests, an assertion expresses the expected result, and an execution environment supplies Node.js, simulated DOM APIs, or a real browser. Other tools can control network responses or automate browser interaction. Understanding these responsibilities makes tool choices easier and prevents the name of a tool from being confused with the scope or purpose of a test.

Vitest and JavaScript Test Frameworks

Vitest is a test framework designed around Vite and is a common choice for many modern TypeScript and frontend projects. It provides a runner, assertions, test doubles, and coverage while using Vite's transformation and configuration ecosystem. Its API is familiar to developers who have used Jest, which can reduce the work needed to migrate tests or share conventions.

Jest provides a similarly integrated testing stack for JavaScript and TypeScript projects. Mocha takes a more composable approach in which surrounding libraries provide more of the stack, while the Node.js test runner provides testing directly through Node.js. The choice depends less on feature counts than on how well the runner fits the project's build system, environment, and existing tests.

Testing Library

Testing Library provides queries and interaction helpers for testing user interfaces. It is not a test runner, so it is commonly used with Vitest or Jest. Its queries encourage tests to find controls similar to how users do, such as reading labels or accessible roles and names, rather than by CSS classes or component internals. This supports tests that describe observable behavior and are less coupled to implementation details. Testing Library can run against a simulated DOM such as jsdom for fast feedback or as part of a stack that uses a real browser.

Selenium, Cypress, and Playwright

Selenium automates browsers through the WebDriver ecosystem and supports several programming languages. It has a long-established browser and infrastructure ecosystem, including remote execution with Selenium Grid. Selenium supports projects that need broad language support, existing WebDriver infrastructure, or a large browser matrix. A separate test framework commonly supplies the surrounding suite structure and assertions.

Cypress provides an integrated JavaScript and TypeScript environment for browser end-to-end and component testing. Its interactive runner, automatic retry behavior, and debugging tools help developers inspect a test as it executes. Cypress combines browser automation with much of the surrounding testing experience rather than treating browser control as a standalone library.

Playwright provides browser automation together with an integrated test framework for Node.js projects. It supports isolated browser contexts, automatic waiting for actionable elements, tracing, parallel execution, and control of multiple pages and browser contexts. These capabilities support end-to-end tests that need isolation and detailed failure diagnostics.

Selenium, Cypress, and Playwright overlap, but their emphasis differs. Selenium offers a mature, protocol-based ecosystem across languages and browser infrastructure. Cypress provides a tightly integrated development and debugging experience for JavaScript and TypeScript teams. Playwright combines browser automation with isolation and diagnostic tooling suited to complex browser workflows. A small trial using one representative journey usually reveals more about setup, reliability, and failure diagnosis than a long feature comparison.

Other Specialized Tools

Other tools fill narrower roles in the same testing strategy. Supertest can exercise Node.js HTTP applications, while Pact supports consumer-driven contract testing. Performance, security, and accessibility tools such as k6, ZAP, and axe-core address the quality attributes discussed earlier. These tools add particular forms of evidence rather than defining the level or purpose of the tests that use them.

Feedback Loops from Local Development to Production

Testing is most useful when evidence arrives soon enough to influence the next decision.

A feedback loop connects a change with evidence and a corrective action. A focused test can expose a defect while the changed code is still fresh in the developer's mind. Tests that require databases, browsers, external services, or deployed environments usually take longer and make failures harder to isolate. A testing strategy places each check in the earliest feedback loop that can produce credible evidence for the risk.

Moving useful feedback earlier is often called shift-left testing. During development, type checking and focused automated tests can detect problems within seconds. Continuous integration repeats fast checks in a clean environment and can then run tests that require real connections or broader system boundaries. Fast failures arrive first, while more expensive environments are used where their additional evidence matters.

Tests around deployment need an environment that represents the release being evaluated. The application, database migrations, configuration, and test data must agree closely enough for a failure to mean something. Smoke tests can check a newly deployed version, while broader browser or performance testing can run when the risk justifies its cost.

Shift-right testing extends evaluation into deployed and production environments. Synthetic transactions can exercise selected workflows with controlled data, while telemetry shows how the application behaves across real requests and operating conditions. This evidence can reveal failures that earlier environments do not reproduce and can feed what the team learns in production back into requirements, tests, and design.

Putting the Strategy Together

A testing strategy works when the team knows which evidence it needs and where that evidence should come from.

For a frontend web application, testing usually starts close to the code and expands where the risks require more of the system. A calculation may need a unit test, an interactive view may need component tests, and an important checkout journey may need a real browser and connected services. The aim is not to repeat the same behavior at every level, but to place each test where it provides useful evidence with reasonable cost and diagnostic value.

Developers keep feedback close

Developers need fast feedback while changing the application. Type checking and focused automated tests catch many problems locally or in continuous integration. Component tests can be valuable in frontend applications because they exercise rendering, state, interaction, and accessibility without requiring a complete deployment. When a defect is found at a wider boundary, a focused regression test can often reproduce it closer to the code.

Testers investigate what automation does not know

Automated checks are strongest when the condition and oracle are already understood, but testers also investigate uncertainty. Exploratory testing can follow unusual states and transitions, while accessibility and usability evaluation examine behavior that requires human judgment. Findings from this work can reveal missing requirements, expose new risks, and identify cases worth preserving as automated regression tests.

Architects identify important boundaries

Architecture determines where important failures can emerge. A frontend that depends on several services needs evidence that their contracts remain compatible. Authentication, caching, asynchronous processing, and other architectural boundaries can introduce failures that isolated frontend tests cannot expose. Architects help identify which connections need direct testing and which operating conditions need a representative environment.

The balance changes as the application changes. A new dependency can make contract testing more important, a production incident can expose a missing condition, and an unreliable test can stop providing useful feedback. The strategy should change with that evidence rather than preserve a fixed distribution of tests.

One question ties the strategy together. What do we need to know about this software, and what evidence would give us a reliable answer?
