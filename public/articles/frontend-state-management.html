Frontend State Management

How to decide what a frontend should remember and where each value belongs.

Andreas Ögren
~36 min read
Last updated August 2026

A storefront product screen can show a price loaded from a server, a filter encoded in the URL, an unsaved quantity entered by the user, and a cart total calculated from the price and quantity. Each value can change, but for a different reason. The seller changes the price, browser navigation changes the filter, the user edits the quantity, and the total changes because its inputs changed. Problems begin when the application stores these values as though they were interchangeable or keeps several writable copies that can disagree.

Frontend state is a changing value that the interface must read again to render correctly or respond to an interaction. Frontend state management decides which values must be remembered, where the current value comes from, how long it must survive, which changes are allowed, and which parts of the interface must respond after a change. This work covers values created by the application, values controlled by the browser, and local copies of data held by a server. A library can store and distribute values, but the product's requirements determine what those values mean.

The storefront in the first paragraph is the example this article returns to throughout. Its product data comes from a server, its search filter participates in browser navigation, its cart holds a quantity the visitor is still editing, and its total is calculated rather than stored. Understanding why each of these values behaves differently is the foundation for every decision that follows, including which framework feature or library ends up managing it.

Authority and Lifetime

The first distinction is not where a value is stored, but who can settle the value.

Server and client authority

Authority identifies the source or set of rules allowed to read and update a value. A product price, account balance, and shipping status are normally controlled by a server. The browser can display a local copy, but another person or process may change the server's value without changing that copy. A snapshot records a value at one point in time. A cache keeps a snapshot so that it can be reused instead of loaded again. The snapshot becomes stale when the authoritative source holds a newer value.

Changing the browser's copy does not transfer authority from the server. Suppose the cart contains one item and the user changes the quantity to two. The interface may show two immediately while the request is still pending, but that value is only a prediction. The server may accept two, replace it with a permitted quantity, or reject the request. The frontend therefore needs rules for each outcome before it presents a pending value as though it were confirmed. Synchronization is the work of bringing a local copy back into agreement with its authority after either one changes.

Client-owned state describes a value whose current truth does not depend on a server response. Whether a disclosure is open, which tab is active inside a widget, and what the user has typed into an unsent form can all be decided in the browser. A theme preference or guest cart is client-owned when the product deliberately keeps it on that device.

Lifetime and product boundaries

Lifetime describes which event ends a value and which boundaries it must survive. The open state of a disclosure may end when that component is removed from the page. A filter in the URL survives a reload and becomes part of browser history. A preference saved in the browser local storage can survive a later visit, while a preference saved to an account can follow the user to another device. A value kept longer than the interaction requires creates extra work because old copies must eventually be expired or removed.

The same feature can have different authority in different products. A guest cart may belong to one browser, while a signed-in cart may be controlled by the server so that it follows the account across devices. Product requirements establish that difference.

Canonical State and Derived Values

Once the source and lifetime are known, the application can decide which facts must be stored and which values can be calculated from them.

One canonical representation

A canonical representation is the one writable form of a value the application treats as the current fact within a boundary. A quantity and unit price may be canonical inputs to a cart row. The displayed line total is not another fact. It is a view of those inputs.

Derived state is calculated from canonical values rather than updated through a separate write. A cart total comes from its lines, and a filtered product list comes from the products and the current filter. Validation summaries and indicators that show which actions the user may request can be calculated in the same way. Such an indicator only controls what the frontend presents. The server must still authorize every protected operation. Cheap calculations can run whenever the interface renders. Memoization retains the result of an expensive calculation and reuses it only while the inputs are unchanged.

Duplicate writable representations create a synchronization problem because either copy can change first. If a filter is stored both in component memory and in the URL, Back navigation can change the URL while the component still holds the previous filter. A server record copied into another writable object has the same problem after a later request returns newer data or a write succeeds. Without a rule that chooses which copy wins, both copies can look valid to the code that owns them while showing different facts to the user.

Intentional working copies and forms

An edit buffer is different from an accidental duplicate, because the application creates it on purpose and knows exactly when it starts and ends. A form is a common example. It begins by copying a server snapshot into a local draft that the visitor can freely change. Submitting the form sends that draft back to the server as a write.

A form does not require a second application-held value for every control. In an uncontrolled control, the value held by the browser is the live draft. The application can supply an initial value, then read the current value when it handles submission or another relevant event. In a controlled control, the application-held draft is canonical for the interaction, and the application writes that value back to the control after each edit. A controlled value is useful when validation, calculated output, or another part of the interface must respond to every change. An uncontrolled value avoids a synchronized copy when the browser's form behavior already meets the requirement.

Form state includes the draft together with information about the interaction around it. A touched field commonly records that the visitor has focused and left it, while a dirty field records that the visitor has edited it. Validation results are derived from the current draft and validation rules. Submission status records whether a write has not started, is pending, succeeded, or failed. Keeping these values in one form model does not make them the same kind of state. Each should change only in response to its own source. If a newer server snapshot arrives while the draft is open, the form needs a product rule that keeps the draft, resets it, merges compatible changes, or asks the visitor to resolve the conflict.

Every writable copy needs a synchronization rule

A copy may be useful for editing, immediate feedback, continuing work without a network connection, or avoiding repeated calculation. Its design is incomplete until the application defines when the copy is created, what can change it, which source wins when the values differ, and when the copy is removed.

State Placement and Reset

Placement chooses the boundary that holds a value or one of its copies.

Component and subtree placement

Placement is the choice of which application boundary holds a value or one of its copies. A server record, navigation entry, browser storage area, component instance, and component subtree are different placements with different lifetimes and readers. Component placement narrows that decision to the component or subtree that owns a client-side value. State used by one component can stay with that component. When two branches of the component tree must change together, their shared value moves to the closest common owner that can update both. Component frameworks often call this movement lifting state. The state moves only as far as coordination requires, because a higher owner affects unrelated descendants.

Context is React's mechanism for making a value available to descendants without every intermediate component forwarding it. Other frameworks provide mechanisms with the same purpose. A provider establishes the subtree that can read the value. Context solves distribution, but it does not define which writes are allowed or let each reader subscribe to only part of one context value. One provider works well for a stable theme, locale, or coordinated screen state. A frequently changing object with unrelated readers may need a notification mechanism that can update one reader without updating them all.

Initialization, preservation, and reset

State identity connects a local value to one particular owner instance. A framework preserves the value as long as it considers the owner to be the same instance. Otherwise, it will replace the instance and initialize a new one with a fresh value. A reset deliberately ends the old instance or restores its initial snapshot. In React, a component's type and position provide its default identity, while a key can distinguish two instances rendered in the same position.

Initialization chooses the snapshot an owner starts with. Copying a value supplied by a parent or server into local state only during initialization creates a copy that will not follow later updates. If the local value should always follow that input, it should be derived. If it is an edit buffer, the application needs the draft rule defined earlier, including what happens when a newer source value arrives. Initialization and reset are therefore part of the value's lifetime rather than incidental framework behavior.

Browser State and Persistence

The browser both controls live interface values and offers storage that can outlive the page.

Browser-controlled state

Browser-controlled state is a value that can change through browser behavior rather than only through an application write. Back and Forward navigation can replace the current URL. A CSS media query is a condition based on properties such as viewport width or a device preference, and the browser reevaluates it when that property changes. The browser also tracks focus, text selection, scroll position, and native form-control values. The Document Object Model (DOM), which exposes the current document structure and element properties, makes many of these values available to application code. The frontend reads the browser's current value or subscribes to the relevant browser event when the interface must respond to a change.

Browser-controlled state is different from client-owned state stored in the browser. The browser controls the current focus and navigation entry even when application code can request a change. A guest cart saved in browser storage is controlled by the application's cart rules. Mirroring either kind of value in another store creates a synchronization obligation, but the direction differs. A browser-controlled value must be reread after browser events, while a persisted client-owned value needs rules for loading, saving, converting old stored formats, and resolving conflicts between copies.

URL and navigation

Values that identify a navigable view often belong in the URL. A search term, sort order, page number, or selected tab can then survive a refresh, participate in browser history, and travel in a shared link. The application should read the current URL as the canonical representation after every navigation. If it copies the same filter into component state, it needs a rule for Back and Forward navigation and for links opened with a different filter.

Browser persistence and server boundaries

Persistence retains a value after the code that created it has stopped running. Client-owned state can therefore outlive a page without becoming part of navigation. Web Storage retains small string values such as preferences or drafts, while IndexedDB stores larger structured records and data needed without a network connection. The stored value is another copy that can disagree with the value the application starts with. On startup, the application must decide which copy wins. When the stored format changes, older records must be converted to the new format or discarded, and another open tab may need to receive changes. A server-rendered page cannot read browser-only storage before it reaches the browser, so the initial server output needs a deliberate fallback.

A cookie fits a value that the browser must send with matching requests. A session cookie commonly contains a random identifier that the server uses to find a server-side session. The identifier itself need not reveal the session data. The cookie stays in the browser that stores it, while account data on the server can follow a signed-in user across devices after each device creates its own session. Browser storage that application code can read should not be the authority for sensitive credentials or shared records. Keeping a value in the browser makes it durable, but it does not make the browser an authority the server can trust.

The placements covered across the last two sections can now be compared by the boundary each one serves. Component and provider placement coordinate live interface code. The URL, browser storage, and a cookie-backed server session preserve values across navigation, reload, later visits, or server requests in different combinations.

Modeling State Changes

State should never be allowed to be set to invalid values.

Setters, events, and reducers

Everything so far has been about what a snapshot contains and where it lives. The next question is how the application gets from one valid snapshot to the next, a change called a state transition. The simplest way to make one is a setter, a function that just replaces one value with another. A setter is all a disclosure needs in order to open, because that changes one value that nothing else depends on. Several fields that must change together need one operation that calculates their next values as a unit. If a change is valid only after an earlier one, the current state must determine whether the change is allowed. Both cases need an explicit transition rule rather than independent setters.

An event describes something that happened, such as the user changing a quantity. A reducer is a function that receives the current snapshot and an event, then returns the next snapshot. An event named quantityChanged describes the occurrence rather than naming individual fields to set. Because one reducer handles the related fields, it can update the quantity, pending status, and validation message as one transition without exposing an intermediate combination. A reducer can belong to one component, a provider, or a shared application store. The explicit transition rule provides the benefit at each of those scopes.

Representing legal modes

The shape of the snapshot can prevent invalid combinations before any transition runs. Four booleans named isIdle, isSaving, isSaved, and hasError allow the interface to be idle and saving at the same time. One status field can instead select exactly one mode, and each mode can contain only the data it needs. A TypeScript union type describes a value that may have one of several defined shapes. The union below gives each save mode its own shape, so the state cannot contain fields that belong to two modes at once.

cart-save-state.ts TypeScript 
type SaveState =
  | { status: 'idle' }
  | { status: 'saving'; requestId: string }
  | { status: 'saved'; confirmedAt: number }
  | { status: 'failed'; message: string };

A state machine defines the available modes and specifies which events are allowed in each mode. A reducer explains how an event produces the next snapshot. A state machine also makes the legal event sequence part of the model. A checkout can accept payment only after it has a valid address, and a media player can pause only while it is playing. The machine does not replace the address, payment details, or media data. It organizes the control state that determines which step can happen next.

A state-machine diagram draws each mode as a node and each legal transition as an arrow. A filled circle points to the initial mode. The arrow's label begins with the event that requests the transition. A guard is a condition in square brackets that must be true before the transition can run. Text after a slash names an action performed when the transition is taken. An event with no arrow from the current mode is not a legal transition from that mode.

Asynchronous work and side effects

Asynchronous work can complete in a different order from the events that started it. Suppose the user searches for “shoe” and then immediately searches for “shirt.” If the shoe request finishes last, blindly accepting its result replaces the newer shirt results with older work. The application can cancel the first request, attach an identifier to each request, or compare a version before accepting a response. A library that manages overlapping requests makes the same decision through its cancellation or replacement policy.

A state transition and a side effect have different jobs. A side effect communicates with or changes something outside the calculation of the next snapshot. For example, network code can send a save request while a reducer can move the save state from idle to saving. This separation lets the reducer be tested with plain inputs and outputs, while retry and cancellation are part of the network policy.

Server State Synchronization

Server-owned data turns frontend state management into synchronization between an authoritative value and one or more local snapshots.

Queries and cache freshness

A query is a read of server-owned data described by its inputs, such as a product identifier or a set of search filters. A server-state cache stores the latest query result so that another consumer can reuse it. The result is stored under a query key that represents every input capable of changing the result. A filtered product list and an unfiltered list therefore need different keys even if the same server function handles both reads.

A server-state cache has to track more about each query than just its most recent result. For a given query key, it separately records whether any data exists yet, whether a request for it is currently running, whether the data it already has might be out of date, and whether the entry is still worth keeping around at all. These facts genuinely overlap in practice. A screen can be showing data that loaded successfully, and is still perfectly renderable, while being stale in the sense defined earlier, with a background request already underway to replace it. Invalidation is the act of marking a stored result as needing to be checked against the server again. Invalidating an entry does not have to mean deleting it. The visitor can keep looking at the old result right up until the new one arrives.

Freshness is the period during which the product is willing to use cached data without checking the server again. A currency quote may need a short period, while a country list can stay current for much longer. Revalidation runs the query again to check whether the server has a newer result. It can happen after time passes, when the window regains focus, when the network reconnects, or after a related write. If several consumers request the same key at the same time, the cache can send one network request and share its result. This behavior is called request deduplication.

Query results and record identity

A query-keyed cache treats each result as the snapshot for one query key. The same product can therefore appear in a search result, a category result, and a product-detail result. A successful price change does not automatically identify every cached result that contains that product. The application or library must update those results, invalidate the affected keys, or revalidate a broader key group defined by the cache.

A normalized cache separates records from the query results that refer to them. It gives a record a stable cache identifier, stores one cached record under that identifier, and lets several query results point to it. A later response for the same identifier can merge fields into that record and notify readers that depend on it. This model reduces duplicate cached records, but it requires identity and field-merge rules.

Mutations and concurrency

A mutation is a request intended to change server-owned data. The browser can wait for confirmation before changing the interface, or it can use an optimistic update when immediate feedback is valuable and failure can be handled safely. An optimistic update shows the expected result locally, keeps enough information to recover, and then sends the mutation. The temporary value is an optimistic overlay placed over the last confirmed snapshot. If the server accepts the mutation, its response confirms or replaces the overlay and related queries can be invalidated. If the server rejects the mutation, the browser removes the overlay or replaces it with the value returned by the server, then presents an error.

A race condition occurs when the result depends on which of two overlapping operations reaches the server last. Suppose two devices load cart version 10 and both send a new quantity. If the server accepts both writes without checking what each edit was based on, the later request silently replaces the earlier change. This is a lost update. Ignoring an old response in one browser can prevent that browser from displaying stale data, but it cannot protect the server record. Version-based optimistic concurrency control adds that protection. Each write includes the version it edited, and the server applies the write only if that version is still current. After the first write advances the record to version 11, the server rejects the second write based on version 10. The frontend can then reload the current value, merge compatible edits, or ask the user to resolve the conflict.

Data loading and rendering boundaries

A query library automates loading, retaining, refreshing, and writing cached server data without changing who owns that data. The application defines how cached entries are identified and when queries, mutations, and revalidation should run. GraphQL lets a client describe the fields it wants from a server, and GraphQL clients can apply similar cache policies to those results. Some application frameworks treat each navigable URL pattern as a route. They can attach a loader to that route so that navigation runs the required reads, and an action that handles writes submitted through it. React Server Components provide another boundary by rendering selected components in a server environment before their output reaches the client tree. A client query cache is useful when data must refresh without navigation, support an optimistic interaction, or stay synchronized while the route stays open.

Server rendering can create the initial snapshot for a client cache. Hydration is the step in which client code attaches behavior to server-rendered output. The server output and the first client render must use the same snapshot during that handoff. Afterward, one policy must determine how the data is revalidated. If a client cache refreshes independently, server-rendered output that summarizes the same record can stay older until that server content is rendered again.

Live, offline, and local-first synchronization

Live updates and offline writes extend the same synchronization problem. In a live connection, the server can send an event without waiting for a new browser request. The event can mark a cached result as out of date or provide data that updates the local snapshot. When the browser is offline, a mutation queue records intended writes and sends them after the server becomes reachable.

A local-first design gives the device's copy a different role. Each device can accept writes while disconnected, and synchronization merges the device copies later. The merge rules must ensure that devices reach the same result after they have received the same edits. A server may help exchange and back up those edits, but it does not have to confirm every write before the interface treats it as complete. Local-first state therefore replaces single-server authority with explicit rules for copying edits between devices and merging concurrent changes.

Shared Client State

Once server data, URL values, persistent browser data, and calculated values have their own homes, fewer values need a general mechanism for sharing client-owned state.

Narrow ownership boundaries

Shared client state is client-owned state that more than one part of the application must read or change. The value can still stay in local framework state when those parts share a nearby component owner. A product filter panel, for example, can keep its temporary expanded sections inside the panel even if several child components render them. The state needs to move higher only when components outside that boundary must coordinate the same interaction.

A reducer and Context can manage a complex screen when its readers fit one subtree. The reducer owns the transition rules, while Context gives descendants the current snapshot and update functions. In React, a consumer receives a new context value whenever its provider's value changes. If one provider object contains both a stable theme and a frequently changing cart, a cart change can therefore give theme readers work they do not need. Splitting unrelated values into separate contexts or using reader-specific notification mechanisms creates narrower update boundaries.

Stores, atoms, and machines

An external store keeps state outside the component tree and exposes operations for reading, writing, and observing it. A subscription registers code to run when the store changes. Some stores route named events through reducers. They may also run middleware, code that observes an event, starts asynchronous work, or prevents work from reaching another step. Other stores expose direct update functions instead. In either style, a selector reads one chosen part of the store so that a consumer does not need the whole snapshot.

An atom is a named unit of state that can be read, written to, or calculated from other atoms. An atom library exposes those units and their dependency relationships directly, while a store exposes a snapshot and usually lets consumers select parts of it. One atom might hold the cart's lines while a second calculates the total from them. A store can represent the same design with a cart snapshot and a total selector. Either approach can hold one small value or a whole feature, and either can be limited to a subtree or shared more widely. The architectural difference lies in how the values, calculations, and subscriptions are addressed rather than how large the state must be.

The method should match the kind of coordination the state requires. A cart that must change its lines, pending status, and error state together fits a reducer or one store. Independent preferences and calculations that depend on selected preferences can fit atoms because each relationship can be expressed separately. A checkout whose steps allow different events fits a state machine because legal order is the main problem. The remaining choice depends on how the team needs to inspect and test changes and whether code outside the component tree must read the state.

Propagation and Rendering

After deciding what a value means and where it lives, the remaining question is which readers must run when it changes.

Notification boundaries

A propagation mechanism connects a changing source to the code that reads it and determines which readers are notified after a change. A component subscribed to the entire cart receives a notification when any cart field changes, even if it renders only the total. A selective subscription can instead observe only the calculated total which may reduce rendering work.

React rendering and external stores

React schedules the component that owns changed state or subscribes to a changed external snapshot. During rendering, React calls components to calculate the next interface output. During the commit phase, it applies the required changes to the DOM. A memoized component can reuse earlier work when its inputs have not changed. React Compiler is a build-time tool that can add similar reuse automatically. React still organizes the update around component rendering and subscriptions.

React's useSyncExternalStore connects an external store through two functions. A snapshot function returns the current immutable snapshot, and a subscription function tells React when to read it again. Repeated reads must return the same snapshot until the store changes. This base contract observes the returned snapshot as a whole. A selector-aware store binding can add a selector and equality check so that one consumer renders again only when its selected value changes.

A React Transition marks an update as non-urgent so that React can prepare it without blocking urgent input. Before React commits a Transition update that read from an external store, it reads the store snapshot again. If the value changed during that work, React restarts the update as blocking and uses the latest snapshot. The snapshot and subscription contract therefore prevents the committed interface from combining two versions of the external store.

Signals and fine-grained updates

A signal is a reactive value that tracks which computations or UI regions read it. When it changes, the framework can update those dependents directly instead of beginning at a component boundary. The Solid framework uses those recorded dependencies to update the affected output, Angular records signal reads while evaluating a component template, then marks that component to be evaluated again after a change, and Svelte achieves similar read/write tracking through compiler-recognized runes and reactive proxy objects. All three track dependencies through reads, but each framework schedules the resulting work and updates the DOM in its own way.

Signals can hold local or shared state, and a store can expose equally selective subscriptions. Selective notification therefore does not answer the earlier ownership questions. A product record represented by a signal is still controlled by the server. A URL filter represented inside a store still needs to follow browser history, so the store cannot silently replace the URL as its canonical representation.

Once ownership and state transitions are correct, propagation becomes a performance question. Selective subscriptions reduce the number of notified readers. Memoization avoids repeating a calculation or component render when its inputs are unchanged. Fine-grained reactivity records dependencies at individual value reads rather than at a larger component or store boundary. A profiler records how much rendering work an update performs and how long that work takes. Its measurements show which updates cost enough to justify a narrower mechanism.

State Management Libraries

Libraries package different combinations of the mechanisms above, so they are easier to compare after authority, lifetime, transitions, and propagation are understood.

A state management library can provide a place to keep values, rules for changing them, and a way to notify readers. It cannot decide whether a value belongs to the server, the URL, persistent browser storage, or the current interface. That decision comes first. The comparisons below cover active, established choices that represent the main architectural models.

What UI libraries already manage

A UI library already provides state for the interface it renders. Its primitives usually cover component-owned values, calculated values, and sharing within a component subtree. They differ most in where reactive dependencies are recorded and how an update reaches the DOM. An external state library becomes useful when the required lifetime crosses that natural owner, non-component code needs the same state, transitions need stronger conventions, or the state is a server cache with its own synchronization policy.

Vue, Angular, Svelte, and Solid can create reactive state outside a component without another package. React has no equivalent built-in primitive outside its component tree, so an external React store connects through the snapshot and subscription contract described earlier.

Client-state libraries

Client-state libraries manage values whose transition rules belong to the frontend. A reducer store emphasizes named events and one explicit transition path. A direct store exposes update functions, while an atom library makes independently addressable values and their dependencies the primary interface. State-machine libraries add legal event order. These models differ in which rules they make explicit and which conventions the team must supply.

Server-state libraries

Server-state libraries manage cached snapshots whose authority stays on a server. Their job includes request coordination, freshness, invalidation, retries, and mutation outcomes rather than the frontend's general transition rules. An application can therefore use one of these caches alongside local framework state or a client-state library.

Redux became the de facto general state layer for many React applications because it provided one inspectable model for shared snapshots, events, reducers, middleware, selectors, and debugging. Its popularity as the automatic default declined as UI libraries handled more local and subtree state and specialized libraries such as Apollo, React Query, SWR, and Urql took responsibility for server-data fetching and caching. Redux Toolkit still fits applications that benefit from a consistent event vocabulary, centralized transition rules, middleware shared across features, and one inspectable action history.

Choosing an Approach

The questions below put the earlier decisions in dependency order. One screen can still use several state mechanisms.

The first question is whether a value must be stored at all. A value that can be calculated from current inputs should be derived. Values that must be stored needs an authority and a required lifetime, which narrow its placement. The next question identifies which readers and writers must change together. Only after those questions are answered do transition complexity and rendering cost determine whether a reducer, store, atom, machine, or more selective subscription is useful.

  1. Representation: Is this a canonical fact, an intentional temporary copy, or a derived view?
  2. Authority: Which system or set of rules may confirm, replace, or merge it?
  3. Lifetime: Should it survive a component reset, navigation, reload, later visit, or device change?
  4. Coordination: Which consumers read it, and which actor is allowed to change it?
  5. Transitions: Are direct writes sufficient, or do events, rules that must always hold, and asynchronous outcomes need an explicit model?
  6. Propagation: Which consumers must run after a change, and is the measured cost large enough to require narrower subscriptions?

The storefront example uses several answers at once. The current URL is the canonical representation of the search filter. A query cache or route loader holds product snapshots controlled by the server. One component owns an unsaved quantity. A signed-in cart combines a server-controlled record with a temporary optimistic overlay in the browser. The total is calculated from whichever cart snapshot the interface is currently presenting.

The screen therefore needs several state mechanisms, each with a different responsibility. Every value has an explicit authority and lifetime, and every additional copy is either temporary or synchronized through a stated rule. Each mechanism can then be tested against that responsibility. A library implements one part of the design instead of becoming the default location for every changing value.
