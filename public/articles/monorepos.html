Organization · Repository Strategy

Monorepos

How teams decide between one repository and many, and the workspace, caching, and orchestration layers that keep a large one fast.

Andreas Ögren
~18 min read
Last updated July 2026

A design-system team publishes @acme/ui to a private registry, and three product repositories depend on it. Fixing a spacing bug changes only the published package. Each product team must still upgrade on its own schedule, so the correction reaches consumers at different times. Until then, one source version contains the fix while deployed products continue to show the old behavior.

A monorepo closes that gap by allowing a shared package and its consumers to change in one commit. The shared boundary also connects build failures, slow tests, dependency upgrades, and access decisions that separate repositories would isolate. Repository strategy is therefore an organizational tradeoff. Atomic changes and unified tooling must be valuable enough to offset the autonomy, permission boundaries, and release independence that separate repositories provide.

The distinction between repository layout and build infrastructure comes first. A monorepo describes where code lives; workspaces, orchestrators, caches, and build systems determine whether that arrangement remains usable as it grows.

Repository Organization vs. Build Infrastructure

A monorepo is where code lives. An orchestrator, a build system, and a package manager are separate decisions about how that code gets built.

Repository organization answers whether several projects share one version-control repository. It does not imply workspace linking, caching, or a build graph. Projects in one Git repository can still install, build, and test independently with no knowledge of their neighbors. That arrangement is a valid monorepo, although it captures few of the coordination benefits.

Additional layers solve different problems as the repository grows.

Monorepo layerWhat it solvesRepresentative tools
Package managementResolving dependencies, including linking one in-repo package to another without publishing itnpm workspaces, pnpm, Yarn
Task orchestrationDeciding what to build or test, and in what order, based on what actually changedNx, Turborepo
Build systemsExecuting a build deterministically, often across several languagesBazel, Buck2, Pants
Continuous integration platformRunning all of the above on every push, at whatever scale the repository has reachedGitHub Actions, GitLab CI, Azure DevOps

Each layer is an independent choice. A small repository may need only a workspace-aware package manager, while a large multi-team repository may justify orchestration, caching, and dedicated build infrastructure. Without selective execution, continuous integration (CI) tends to perform work for the whole repository rather than the projects a change can affect. The sections below follow that progression from local linking to governance.

Where Scale Appears

The bottleneck in a large repository is almost never Git itself.

Repository size can slow cloning, checkout, status, and history operations, but Git provides tools that reduce the local footprint. A partial clone can omit selected objects until they are needed. Sparse checkout limits the files present in the working tree, and a sparse index can reduce work on excluded paths. These features have tradeoffs and server requirements, so they mitigate repository scale rather than making it disappear.

The larger cost often sits above version control. Every change can trigger dependency analysis, builds, tests, and linting across many projects. If the tooling cannot narrow that work, CI duration grows with the repository and local feedback slows with it. Monorepo infrastructure exists mainly to preserve short feedback loops as the project graph expands.

Large-Scale Precedents

The organizations that pioneered this at scale weren't running Git at all.

Google's large internal repository uses a proprietary version-control system called Piper and a build system called Blaze; Bazel grew from the same build model. Meta has used Mercurial with EdenFS and developed Buck2 as a build system. These examples are unusual in scale and infrastructure, but they establish a general lesson: version control alone does not make a large shared repository workable. Build graphs, reproducibility, caching, and selective execution do most of that work.

Most organizations do not need those custom systems. Workspace-aware package managers and general-purpose orchestrators now provide local linking, dependency graphs, affected-project analysis, and remote caching as ordinary tools. They apply the same principle at a smaller scale: avoid work whose declared inputs have not changed.

Local Package Linking: Workspaces

Before a repository needs a build graph or a cache, it needs a way for one package to depend on another without publishing it.

Suppose app-web and app-mobile both depend on a local ui package. Publishing ui to a registry after every edit would recreate the coordination delay that the shared repository was meant to remove. Local development needs package resolution to connect consumers directly to the package in the working tree.

Workspace tooling supplies that connection by letting npm, pnpm, and Yarn recognize several packages in one repository and link local dependencies during installation. The exact configuration and whether a consumer resolves source or built output depend on the package manager and package layout. Uncommitted local changes become available without publishing a registry version first.

package.json (repository root) JSON 
{
  "name": "acme",
  "private": true,
  "workspaces": ["packages/*"]
}

Workspace linking resolves packages; it does not decide how to build or test them. Dependency graphs, task ordering, and caching are separate layers built on top of that local package structure.

A shared working tree can also improve code navigation. Editors may lead from a consumer into the local package implementation instead of a published artifact, depending on exports and source maps. Developers can inspect and change both sides of an interface in one checkout.

Dependency Graph vs. Build Graph

The project graph describes relationships, while the task graph turns those relationships into an execution order.

An orchestrator can derive a dependency graph from package manifests, configuration, and sometimes source analysis. In the example, app-web depends on ui and api-client, which both depend on core. The graph records project relationships but does not yet describe a particular build.

A task graph combines those project relationships with the tasks being requested. If consumers build from dependency outputs, core must finish before ui and api-client. Those two can run in parallel because neither depends on the other. The applications can begin after their prerequisites complete. Task configuration matters here because not every repository requires dependencies to build first.

Computing the graph from declared relationships removes most manual scheduling. Its accuracy still depends on the declarations. Hidden dependencies or incomplete tool configuration can produce an incorrect order or an unsafe cache hit, which is why dependency hygiene matters as much as the orchestrator.

Only Rebuild What Changed

Selective execution keeps a local change from triggering unrelated work elsewhere in the repository.

The task graph determines order, but it does not prove that a task needs to run. Incremental computation reuses a previous result when every input relevant to that result is unchanged. Safe reuse depends on identifying source files, dependency outputs, configuration, environment, and tool versions that can influence the task.

Making that safe requires a few pieces working together:

  • Task hashing fingerprints declared inputs and uses the result as a cache key.
  • Content-addressable caching stores task outputs under that fingerprint, locally or in a shared remote cache.
  • Affected-project analysis combines changed files with the dependency graph to find projects whose results may have changed.

Change one file inside core, and everything downstream of it needs checking. Change one file inside a leaf package nothing else depends on, and the rest of the graph, however large, can be skipped entirely.

These mechanisms decouple CI work from total repository size. A narrow change can run tasks only for the projects it affects, and a matching cache entry can replace execution with artifact retrieval. Changes to widely shared code may still invalidate much of the graph.

An undeclared environment variable, external file, or tool version can make the fingerprint incomplete. A hermetic build reads only declared inputs and runs with controlled tools and environment. Bazel is designed around that property. Without it, a cache can return an artifact produced under conditions the key did not capture, making an apparently successful hit less trustworthy than a redundant rebuild.

Monorepo Tools

Task hashing, caching, and affected-project analysis are concepts. Monorepo tools are where a JavaScript or TypeScript team goes to get them.

Nx builds project and task graphs, caches task results locally, and can visualize project relationships. Nx Cloud adds managed remote caching and distributed CI execution. Framework plugins can infer tasks, provide generators, and integrate migrations or lint rules. JavaScript and TypeScript repositories can enforce tag-based module boundaries through ESLint. Teams can adopt the task runner incrementally, although deeper plugin use introduces more Nx-specific configuration and conventions.

Turborepo, maintained by Vercel, focuses on task orchestration and caching for package-manager workspaces. A turbo.json file describes tasks, dependencies, inputs, and outputs. Local caching works without a service, while remote caching requires configuration and can use Vercel's service or a compatible implementation. Turborepo leaves code generation and architectural enforcement to the repository's other tools, which keeps its scope narrow.

Rush, maintained by Microsoft, combines monorepo installation and task tooling with release and policy features. Its change-file workflow records version intent for published packages, and its installation model helps prevent a package from relying on dependencies it did not declare. Rush supports large repositories well, but adopting its conventions is a broader commitment than adding a task runner to an existing workspace.

Versioning

Internal source dependencies may follow the repository tip, while published packages still need an explicit release policy.

Under an always-at-tip policy, internal consumers build against the library source on the same revision. There is no registry version between a change to ui and applications in the repository. A single-version policy goes further by allowing only one active version of a dependency across the codebase. The ideas are related but not identical, because a repository can build from source while still carrying parallel APIs during a migration.

The policy prevents dependency drift, in which consumers remain on different releases of a shared package. Deferred upgrades accumulate breaking changes and make later migrations harder to plan. Keeping one active version moves that work to the change that introduced it, while the producing team still has the necessary context.

The cost becomes visible when an API breaks. Without version pins, a change to core must either update its consumers in the same revision or preserve the old API during a migration. The dependency graph identifies the affected consumers, but ownership and review boundaries still determine how quickly the change can land.

Atomic updates work best with a small blast radius. Widely used APIs need migration techniques that let many owners move safely without freezing the repository. The four approaches below can be combined.

Small blast radius
Atomic change

The library and every consumer it affects land in one commit. It's simple, and still the default whenever the affected set is small enough for one person to fix by hand.

Large blast radius, gradual
Two-phase migration

Also called expand and contract, it ships the new behavior alongside the old one first. Consumers migrate on their own schedule. The old behavior is only deleted once nothing depends on it anymore.

Large blast radius, mechanical
Automated migration

A codemod rewrites every call site across the repository in one pass, turning a change that would take months of manual edits into a single generated commit. Google's internal large-scale change tooling is the best-known example.

Isolating the change
Feature branch

The change develops away from main until it's ready, then merges in one step. It trades the always-latest model's simplicity for however much the branch drifts from main while it's open. That's usually a last resort rather than a default choice.

The migration approach follows the size and shape of the change. A small signature update may fit one commit, while a mechanical rename suits a codemod. A redesigned shared API usually needs an expand-and-contract migration so consumers can move before the old surface disappears.

Published packages still need versions because external consumers cannot move atomically with repository source. Some internal consumers may also remain deliberately on different releases. Those boundaries reintroduce compatibility promises and release coordination.

Lockstep versioning gives related packages one version and releases them as a set. Compatibility is easy to communicate because matching versions belong together. The cost appears when packages change at different rates, since a small update can advance the version of packages whose contents did not change.

Independent versioning lets each package advance on its own release cadence. Changesets records the affected packages and intended semantic-version changes in small files committed with the code. Release automation can combine those records into version updates and changelogs. Consumers gain smaller releases but must determine which combinations of related package versions are compatible. Rush change files support a similar workflow within Rush's release policy.

Releasing

Whether or not a package carries a version number, something still has to decide what changed, what ships, and how an already-shipped release keeps getting fixed.

Versioning assigns compatibility labels; releasing turns a repository change into published packages or deployed applications. The pipeline must identify affected artifacts, produce them, publish or deploy them, and record the result. Tools such as semantic-release can derive release intent from structured commit messages, while Changesets and Rush use explicit change files.

Deployed services can usually move forward from the main branch, but installed software may require support for an older release. Mobile applications and customer-pinned software development kits cannot be upgraded on the producer's schedule. A release branch preserves the source for a supported line so selected fixes can be backported without including unrelated work from main. Teams need an explicit policy for which versions receive fixes and how those changes return to other branches.

Monorepos Come in Different Shapes

A monorepo isn't synonymous with a JavaScript workspace, and what it holds looks different depending on who's using it.

Directory structure often reflects how the organization draws ownership and deployment boundaries.

Frontend-heavy
apps/ and packages/

The common shape for a single product team: a handful of deployable apps alongside shared UI, config, and utility packages they all pull from.

Platform team
services/, libraries/, tools/

Splits by role rather than by app, covering backend services, the libraries those services and others share, and internal developer tooling that doesn't ship to users at all.

Whole organization
frontend/, backend/, mobile/, infra/

The broadest version: an entire company's codebase organized by platform, common at the scale where Bazel-class build systems and dedicated platform teams tend to show up.

No directory shape is universally correct. Product boundaries, platform responsibilities, languages, and access requirements should determine the layout. Workspace and orchestration tools can operate beneath several of these arrangements.

Governance

The advantages of a shared repository disappear quickly if nobody knows who's allowed to change what.

A shared repository removes repository-level isolation between teams. Architectural boundaries must therefore become explicit in package exports, dependency rules, and automated checks. Lint or graph constraints can reject imports that cross a prohibited boundary before review. These controls protect design boundaries even though every developer may be able to read the surrounding source.

Automated rules still need human owners behind them. Ownership files can request reviews from the responsible team, and protected paths can require approval for high-risk changes. A platform team may own shared build infrastructure, while an API review process prevents accidental contracts from spreading widely. These mechanisms make responsibility visible inside a repository whose physical boundary no longer expresses it.

Levels of Monorepo Infrastructure

Repository scale and feedback time determine how much build infrastructure is justified.

Placing a repository on this scale is a useful gut check before reaching for the heaviest tooling by default.

Moving between levels usually means adding a layer rather than reorganizing every project. An orchestrator can sit above existing workspaces, and stricter build isolation can follow later. Measured feedback time, cache correctness, and platform workload are better triggers than package count alone.

Choosing a Repository Strategy

Repositories can share code through publication or pinned source without placing every project in one version-control boundary.

A monorepo and fully independent repositories are the endpoints of a wider set of strategies. With an internal package registry, projects remain separate and consume versioned packages through the normal dependency workflow. A Git submodule instead records a commit from another repository and checks that source out beneath the parent repository. Both preserve repository boundaries, but publication and pointer updates prevent atomic cross-repository changes.

Reaches for one repository
Shared libraries and coordinated refactors

Teams whose APIs evolve together, who refactor across package boundaries often, and where organization-wide standards matter more than any single team's independence. It also suits organizations where consumers benefit from reading a dependency's actual source rather than working against a published artifact.

Reaches for separate repositories
Independent products and boundaries

Fits products that are genuinely independent, or teams that need isolated permissions or open-source visibility. It also fits when release cycles diverge substantially, or when a compliance boundary separates what two teams are allowed to see of each other's code.

No repository strategy is correct by default. Shared ownership and frequent cross-project changes favor a shared repository. Independent release authority, restricted access, or genuinely separate products favor distinct repositories. Tool preference should follow that boundary decision.

Which Monorepo, Though

Repository strategy and infrastructure level remain separate decisions. A one-team workspace and an organization-wide codebase are both monorepos, but they need different controls. The infrastructure table relates tooling to scale, while the repository shapes show how ownership affects layout.

Begin with the smallest setup that preserves an acceptable feedback loop and clear ownership. Add affected-project analysis when unnecessary work becomes visible, remote caching when repeated work dominates, and hermetic or distributed builds when correctness and scale justify the platform cost. The repository should earn each layer through measured need.
