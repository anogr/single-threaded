Organization · Repository Strategy

Monorepos

How teams decide between one repository and many, and the workspace, caching, and orchestration layers that keep a large one fast.

Deep dive
Andreas Ögren
~24 min read
Repository architecture
Last updated July 2026

A design system team publishes @acme/ui to a private registry. Three product teams depend on it, each in its own repository. When the design system team fixes a spacing bug, they cut a new version, publish it, then wait for pull requests bumping the dependency to land in three unrelated repositories on three unrelated schedules. One team merges the bump the same day. Another sits on the old version for two months because nobody prioritized it. The bug is fixed in exactly one place and unfixed everywhere that hasn't updated yet.

That gap between fixing something once and having it actually take effect everywhere is the clearest case for a monorepo. It isn't free. The moment several teams' code sits in one repository, a change to a shared package can reach every consumer atomically. So can everything else, such as one team's broken build, one team's slow test suite, or one team's decision to bump a dependency nobody else wanted yet. The real question an architect is answering isn't whether to use a monorepo. It's whether this organization's shared code, atomic changes, and unified tooling are worth more than the team autonomy, isolated permissions, and independent release schedules that come more easily when repositories stay separate.

Neither side of that tradeoff is free, and the rest of this article works through what actually makes the shared-repository side viable once an organization grows past a handful of packages. That starts by separating what a monorepo is from the tools people reach for to make one work at scale.

Repository Organization vs. Build Infrastructure

A monorepo is where code lives. An orchestrator, a build system, and a package manager are separate decisions about how that code gets built, and conflating the two is the most common confusion in this space.

Repository organization answers one question: does code for multiple projects live in a single repository, or is it spread across many. That's the whole decision. Nothing about workspaces, caching, or build graphs is implied by it. A team can put every project in one Git repository and still build each one exactly as it would if the projects lived apart. Each package runs its own independent install step and its own independent test command, knowing nothing about its neighbors. That's a monorepo in name only, and it's a real, if uncomfortable, starting point for a lot of organizations.

What actually makes a large monorepo pleasant to work in is a stack of separate technologies sitting on top of that repository choice, each one solving a distinct problem.

Monorepo layerWhat it solvesRepresentative tools
Package managementResolving dependencies, including linking one in-repo package to another without publishing itnpm workspaces, pnpm, Yarn
Task orchestrationDeciding what to build or test, and in what order, based on what actually changedNx, Turborepo
Build systemsExecuting a build deterministically, often across several languagesBazel, Buck2, Pants
Continuous integration platformRunning all of the above on every push, at whatever scale the repository has reachedGitHub Actions, GitLab CI, Azure DevOps

Each layer is a separate decision, and a repository can stop at any point in that stack depending on how large it actually is. A five-package repository shared by one team probably only needs the first layer, a workspace-aware package manager. A thousand-package repository shared by dozens of teams usually needs all four. Without an orchestrator deciding what actually needs to run, continuous integration (CI) time grows with the size of the whole codebase instead of the size of whatever changed. The rest of this article follows that same progression, from workspaces down through the caching and governance layers that keep a large repository usable.

What "Scale" Means

The bottleneck in a large repository is almost never Git itself.

The instinctive worry about combining many projects into one repository is that Git will buckle under the weight. Cloning years of history for ten thousand packages sounds like it should take an hour, with every command crawling after that. In practice, modern Git handles repositories of that size reasonably well. Partial clone and sparse checkout let a developer fetch only the history and files they actually need instead of the entire tree. Both features exist because a handful of very large organizations hit this problem years ago and pushed fixes upstream. Git's scaling story isn't perfect at the extreme end, but for most organizations considering a monorepo, raw repository size isn't where the pain actually shows up.

The real constraints sit one layer up, in how much work has to happen on every change. A dependency graph with thousands of packages takes real computation just to reason about. The build graph derived from it gets more expensive to compute as that graph grows. CI time climbs if every push rebuilds and retests the whole repository rather than the part a change actually touches. The same problem shows up again in how long the test suite itself takes to run. The slowest-feeling consequence of all of this lands on a developer directly: how long they wait between saving a change and finding out whether it worked. Solving that chain of problems, not Git performance, is what the rest of this article is about.

Where This Came From

The organizations that pioneered this at scale weren't running Git at all.

Google's internal repository, known as Piper, holds most of the company's source code and predates any of today's open-source tooling. It runs on Google's own storage infrastructure rather than Git, and the build system that made a repository that size usable, Blaze, was later open-sourced as Bazel. Meta runs a similar setup: a single repository backed by Mercurial and a virtual filesystem called EdenFS, paired with its own build system, Buck, now in its second major version, Buck2. Neither company solved this by choosing a version control system. They solved it by building a custom build system whose entire job was avoiding repeated work, the same idea today's orchestrators are now reimplementing for everyone else.

What changed recently isn't the underlying idea. It's that the surrounding ecosystem finally caught up to it for ordinary organizations. CI got cheap enough to run per package rather than per repository. Cloud-hosted remote caching became a practical default instead of custom infrastructure. And the orchestrators from the table above matured enough to compute what actually changed reliably, without a dedicated platform team hand-tuning it. A monorepo built around those pieces today looks less like a smaller copy of Google's setup and more like a lightweight version of the same principle. It arrived roughly a decade later, because the surrounding infrastructure needed that long to become affordable outside a handful of the largest tech companies.

Local Package Linking: Workspaces

Before a repository needs a build graph or a cache, it needs a way for one package to depend on another without publishing it.

The most basic question a monorepo has to answer is deceptively simple. If app-web and app-mobile both need code from a shared ui package, and all three live in the same repository, how does app-web actually get ui's code into its build? The naive answer, publish ui to a registry and have app-web install it like any external dependency, defeats the entire point. It reintroduces a publish step for a change sitting a few folders away.

Workspace tooling solves exactly this. Rather than fetching a package from a registry, a workspace-aware package manager links the package's own folder directly into place. npm, pnpm, and Yarn all support this, so app-web resolves ui to the exact source sitting in the repository, uncommitted changes included. A one-line declaration in the repository's root manifest is usually all it takes to opt every package in a given folder into this linking.

package.json (repository root) JSON 
{
  "name": "acme",
  "private": true,
  "workspaces": ["packages/*"]
}

That's the whole mechanism. There's no build step involved yet, no cache, no orchestration, just a dependency resolution rule that treats sibling packages as already-installed local code instead of registry downloads. Everything covered in the rest of this article, the dependency graph, the build graph, incremental caching, sits on top of this one piece of plumbing.

The same linking that lets a build resolve ui to real source also changes what a developer sees while working. Jumping to a dependency's definition lands in its actual implementation, not a published package's type declarations or a compiled bundle. Understanding exactly what a shared function does, or why it behaves a certain way, doesn't require finding a separate repository and checking out whatever version happens to be pinned.

Dependency Graph vs. Build Graph

One graph describes relationships. The other describes what actually has to run, and in what order.

Once packages can depend on each other locally, an orchestrator can read every package's manifest and construct a dependency graph. app-web depends on ui and api-client, both of which depend on a shared core package, and so on across however many packages the repository holds. That graph describes relationships. It says nothing yet about building anything.

The build graph is what an orchestrator derives from that dependency graph in order to run a build. Because core has no dependencies of its own, it can build first. Because ui and api-client both depend on core but not on each other, they can build in parallel once core finishes. Because app-web and app-mobile depend on both ui and api-client, they wait for both before they can start. The dependency graph says what depends on what. The build graph turns that into a schedule. It determines which stage runs first, which packages run in parallel within a stage, and which packages have to wait.

This derivation is mechanical enough that an orchestrator can do it correctly for a graph with thousands of packages, which is exactly the point. A human reasoning about build order by hand doesn't scale past a few dozen packages before mistakes creep in. A graph computed from the manifests themselves stays correct as the repository grows, because it's recomputed from each package's current declared dependencies rather than maintained by hand.

Only Rebuild What Changed

A repository with thousands of packages can still run CI in minutes, as long as a change only touches the part of the graph it actually reaches.

The build graph from the previous section answers what order things run in. It doesn't answer whether they need to run at all. The idea that makes a large monorepo fast rather than merely organized is incremental computation. If a package's inputs, meaning its source files and the packages it depends on, haven't changed since the last time it was built, there's no reason to rebuild or retest it. The output from last time is still correct.

Making that safe requires a few pieces working together. Task hashing computes a fingerprint from a package's source files, its dependencies' outputs, and its build configuration, then uses that fingerprint as a cache key. Content-addressable caching stores build outputs keyed by that same fingerprint, whether on a developer's own machine or in a shared remote cache the whole team and every CI run can read from. Affected-project analysis walks the dependency graph backward from whatever files a commit actually touched, to work out exactly which packages could possibly be affected. Change one file inside core, and everything downstream of it needs checking. Change one file inside a leaf package nothing else depends on, and the rest of the graph, however large, can be skipped entirely.

This is why CI time doesn't have to grow linearly with repository size. A push that only touches a handful of packages only rebuilds and retests that handful. If any of them were already built with the same inputs elsewhere, even that work turns into a cache lookup instead of real computation.

None of this works if a build secretly depends on something it never declared, such as a stray environment variable, a file outside the package's own folder, or a mismatched tool version between two machines. A hermetic build is one that depends only on its explicitly declared inputs, the property Bazel is built around and enforces strictly. Hermeticity is what makes a cache key trustworthy in the first place. Without it, a cache hit might quietly reuse output computed against an input the build system never saw, which is a subtler and more dangerous failure than simply rebuilding too often.

Monorepo Tools

Task hashing, caching, and affected-project analysis are concepts. Monorepo tools are where a JavaScript or TypeScript team actually goes to get them.

Nx, built by the company Nrwl, is the most opinionated of the three. It computes the dependency graph covered earlier and renders it as an actual interactive diagram a developer can browse, not just an internal data structure the orchestrator consults. Its caching works locally by default and extends to Nx Cloud for a shared remote cache and distributed task execution across CI machines. What sets Nx apart is its plugin ecosystem. Plugins for React, Angular, Next.js, and other frameworks add code generators that scaffold a new component, library, or app with the repository's own conventions already applied. They also add lint rules that enforce the module boundaries described in the governance section above. That depth comes with a learning curve. Adopting Nx fully usually means adopting its configuration format and its way of describing tasks, not just pointing it at an existing repository.

Turborepo, originally an independent project later acquired by Vercel, takes the opposite bet. A single turbo.json file describes each task and what it depends on, and Turborepo handles hashing, local caching, and remote caching from there. Remote caching points at Vercel's infrastructure by default, though it can be pointed elsewhere. There's no generator system and no plugin ecosystem to learn. A team already running plain npm, pnpm, or Yarn workspaces can usually add Turborepo in an afternoon and get most of the caching win covered in the rebuild section without restructuring anything else. The tradeoff is that Turborepo assumes a team's existing tools already cover code generation and lint enforcement, because it doesn't try to.

Rush, built by Microsoft, solves a narrower problem than the other two. It targets very large enterprise repositories where policy matters as much as speed. It pairs tightly with pnpm and enforces rules Nx and Turborepo leave optional. A change that affects a published package must come with a change file describing the version bump. A package also can't import a dependency it never declared in its own manifest, a restriction that catches what's commonly called a phantom dependency. That policy layer is also why Rush's independent-versioning approach, mentioned in the versioning section below, comes with more built-in structure than Changesets does. The cost is flexibility. Rush is a heavier commitment upfront, and it shows up mostly in organizations already running dozens of teams through one repository rather than in a five-package startup monorepo.

ToolOriginCode generationVersioning policyBest fit
NxNrwlExtensive plugin and generator ecosystemBring your own, commonly ChangesetsMulti-framework repositories that want scaffolding and enforced module boundaries
TurborepoVercelNoneBring your own, commonly ChangesetsLeaner JS or TypeScript repositories wanting fast caching without an added framework
RushMicrosoftNoneBuilt in, enforced change filesLarge enterprise repositories where strict policy matters as much as speed

A newer entrant is moonrepo, a Rust-built task runner that applies the same hashing and caching ideas language-agnostically rather than tying itself to the JavaScript ecosystem specifically. It's less established than the three above, but it's often mentioned alongside them in repositories that mix a JavaScript frontend with services written in other languages.

Versioning

The most native monorepo answer to versioning is to skip it, and have every consumer simply depend on whatever is currently on the main branch.

Under a single-version policy, no internal package is versioned at all. Every consumer simply depends on whatever is currently committed to the main branch. There's no ui@2.3.1 to install, because there's no registry step between a change to ui and every app that already uses it. This is close to the model Google's Piper runs on, mentioned earlier. At any moment there's exactly one copy of a given library in existence, because every consumer builds directly from its source rather than from a published artifact.

Single-version policy exists to head off a specific failure mode common in polyrepos, sometimes called dependency drift. Updating a dependency competes with a team's own roadmap, and it usually loses, because staying on an old version carries no visible cost until it suddenly does. A team defers the bump through one sprint, then several, while the producing team keeps shipping changes on top of a version nobody else is tracking anymore. By the time the consuming team is finally forced to update, so many changes have accumulated that the migration is no longer a version bump. It's a multi-week project. The producing team has often moved on by then too, so the people who understand why each change happened aren't available to help the team doing the catch-up. A single-version policy removes the deferral option entirely. There's no old version left to sit on. Each update lands in small increments as part of whatever change introduced it, rather than arriving all at once as an overdue migration nobody remembers the reasoning behind.

Single-version policy has a real cost the moment a change isn't backward compatible. There's no version pinning to shield a consumer from it. A breaking change to core has to update every one of its consumers in the very same commit, even ones owned by a different team. The affected-project analysis covered earlier is exactly the graph a developer walks by hand to find those consumers. Under the always-latest model, walking that graph isn't just how the orchestrator decides what to retest. It's a manual obligation on whoever is making the breaking change, because merging it without also fixing every caller would leave the main branch broken for every team depending on it.

Landing every fix in the same commit works when a library has a handful of consumers. It stops being realistic once a core package has hundreds of them, spread across dozens of teams who can't all review and merge a change on the same afternoon. Four techniques cover most of what large single-version monorepos actually do. They aren't mutually exclusive.

Small blast radius
Atomic change

The library and every consumer it affects land in one commit. It's simple, and still the default whenever the affected set is small enough for one person to fix by hand.

Large blast radius, gradual
Two-phase migration

Also called expand and contract, it ships the new behavior alongside the old one first. Consumers migrate on their own schedule. The old behavior is only deleted once nothing depends on it anymore.

Large blast radius, mechanical
Automated migration

A codemod rewrites every call site across the repository in one pass, turning a change that would take months of manual edits into a single generated commit. Google's internal large-scale change tooling is the best-known example.

Isolating the change
Feature branch

The change develops away from main until it's ready, then merges in one step. It trades the always-latest model's simplicity for however much the branch drifts from main while it's open. That's usually a last resort rather than a default choice.

Which of these applies depends on the size and shape of the change, not on a fixed policy. A one-line signature fix is atomic by default. A repository-wide rename is a job for a codemod. A redesign of a core system's public API is usually a two-phase migration, sometimes developed behind a short-lived feature branch until the new shape is stable enough to expose.

Not every monorepo works this way. Versioning still has to come back the moment a package is meant to be consumed outside that always-latest world. That happens when it's published to a public registry, installed by an external customer, or deliberately meant to let two internal consumers sit on different releases at once.

Lockstep versioning gives every package in the repository the same version number and ships them together, as one release with one changelog and one version bump across the board. It's simple to reason about, and it's how several well-known monorepos, Babel among them historically, have operated. The cost shows up the moment packages have genuinely different release cadences. A one-line documentation fix in a rarely touched package still forces a version bump, and often a republish, of every other package in the repository, whether or not anything in them actually changed.

Independent versioning lets each package track its own version, so a change to one package doesn't force a bump anywhere else. It's the more common choice than lockstep specifically for monorepos publishing several related packages that don't actually share a release cadence, and Changesets is the tool most associated with it. A contributor drops a small markdown file into the pull request naming which packages changed and whether the change is a patch, a minor, or a major bump. A release step later collects every pending file and works out exactly which packages need a new version and what that version should be. It then opens a single pull request that applies all the bumps and rewrites each package's changelog at once. Merging that pull request is what actually triggers the publish. The tradeoff is that nothing guarantees two independently-versioned packages are compatible when installed together. A consumer has to work that out from the changelogs rather than from a shared version number, which is why some tools default to lockstep instead even though it forces unrelated packages to bump together. Rush takes a similar independent-versioning approach but bundles it with a stricter, built-in policy around what's allowed to ship together.

Releasing

Whether or not a package carries a version number, something still has to decide what changed, what ships, and how an already-shipped release keeps getting fixed.

Versioning only decides the number. Releasing still has to answer which packages actually changed, which of those need publishing somewhere such as a registry, and which already-deployed applications need a fresh build and rollout because a dependency they consume moved. The tool semantic-release automates that last mile by deriving a version and a changelog directly from commit messages, then publishing without a human triggering it. It fits well once affected-project analysis can already answer the underlying question of what changed reliably.

That covers shipping forward. Shipping backward, keeping an already-released version alive, is a separate problem. This works cleanly for anything that deploys straight from the main branch, such as a backend service or a website redeployed on every merge. It breaks down for anything with an install base that can't be forced to update on the organization's own schedule. A mobile app already on a user's phone, or a software development kit a customer has pinned to a specific release, are common examples. Supporting a version that's already shipped still needs bug fixes, without dragging in whatever unrelated work has landed on main since it went out. The standard answer is a release branch, cut from main at the moment of release and updated only by cherry-picking already-reviewed commits onto it, rather than developing directly on the branch itself.

Monorepos Come in Different Shapes

A monorepo isn't synonymous with a JavaScript workspace, and what it holds looks different depending on who's using it.

The shape a repository takes says something about the organization drawing its boundaries, not just about which packages happen to exist.

Frontend-heavy
apps/ and packages/

The common shape for a single product team: a handful of deployable apps alongside shared UI, config, and utility packages they all pull from.

Platform team
services/, libraries/, tools/

Splits by role rather than by app, covering backend services, the libraries those services and others share, and internal developer tooling that doesn't ship to users at all.

Whole organization
frontend/, backend/, mobile/, infra/

The broadest version: an entire company's codebase organized by platform, common at the scale where Bazel-class build systems and dedicated platform teams tend to show up.

None of these shapes is more correct than another. Each reflects how a specific organization has chosen to draw boundaries around ownership, and the same technical stack from earlier in this article, workspaces, a dependency graph, an orchestrator, works underneath any of them.

Governance

The advantages of a shared repository disappear quickly if nobody knows who's allowed to change what.

Putting every team's code in one repository removes the natural boundary a separate repository used to provide for free. Without something replacing it, nothing stops a change in one team's package from quietly reaching into another team's internals, and the module boundaries that were supposed to make refactoring safer end up meaning nothing. Enforcing those boundaries has to become explicit. For example, lint rules or graph-level constraints can reject an import that crosses a line the organization has decided shouldn't be crossed, checked automatically on every pull request rather than relying on someone noticing in review.

The organizational side of governance matters just as much and gets discussed far less. That includes ownership files mapping a folder to the team responsible for it, and review requirements on the folders that carry the most risk. It also means a platform team responsible for the shared infrastructure everyone else builds on, plus a lightweight process for reviewing a new shared API before it spreads to a dozen consumers. None of this is an optional extra bolted onto a mature monorepo. It's what makes ownership explicit instead of implicit, arguably the single biggest organizational advantage a well-run monorepo offers over a sprawl of separate repositories where ownership is whatever each repository's access list happens to say.

Modern Monorepo Architectures

There isn't one "monorepo." There are roughly three generations, and most real repositories sit clearly in one of them.

Placing a repository on this scale is a useful gut check before reaching for the heaviest tooling by default.

GenerationWhat it hasTypical fit
SimpleVersion control plus workspace-aware package linking, no orchestratorA handful of packages, one team, builds fast enough without caching
IntermediateWorkspaces plus an orchestrator computing affected projects, with local and remote cachingMost organizations once several teams and dozens to low hundreds of packages share a repository
Large-scaleHermetic builds, remote build execution, and distributed caching across the whole organizationThousands of packages, often multiple languages, usually paired with a dedicated platform team

Moving from one generation to the next is rarely a rewrite. It's usually adding one layer from the table back in the second section of this article, an orchestrator on top of workspaces, then a proper build system underneath that. The trigger is simply the previous generation's approach no longer being fast enough for the repository's actual size.

Choosing a Repository Strategy

The full comparison isn't monorepo against polyrepo. There are at least four real options, and the middle two are where most enterprises actually end up.

The two extremes usually discussed are a single monorepo on one side and a polyrepo with no required coordination on the other. Two more setups sit between them, and both are common enough in practice that leaving them out misses how most large organizations actually operate. A polyrepo paired with an internal package registry keeps every project in its own repository but shares code the ordinary way. One team publishes a versioned package to a private registry the organization runs, and other repositories install it like any external dependency. Git submodules reach the same middle ground a different way. One repository embeds a pointer to a specific commit of another repository, checked out into a subdirectory, so pulling in a change means deliberately updating that pointer rather than running an install.

Teams whose APIs evolve together, who refactor across package boundaries often, and where organization-wide standards matter more than any single team's independence. Fits products that are genuinely independent, or teams that need isolated permissions or open-source visibility. It also fits when release cycles diverge substantially, or when a compliance boundary separates what two teams are allowed to see of each other's code.

None of the four options in the table above is the default correct answer. The organizational shape a company already has, not a preference for one tool over another, is what decides which of these actually reduces friction rather than adding a new kind of it.

Which Monorepo, Though

Choosing to share a repository is a separate decision from choosing how much infrastructure that repository needs. A five-package repository shared by one team and a thousand-package repository shared by dozens of teams are both monorepos, but almost nothing else about how they operate is the same. The generations table earlier in this article maps that range, from simple repositories that stop at workspace linking, to intermediate repositories that add an orchestrator and caching, to large-scale repositories that add hermetic builds and distributed execution. The shapes section covers the organizational side of the same question, how ownership and package boundaries get drawn once several teams share one repository. Between those two, most of what determines whether a monorepo actually works for a given organization is already answered.

The starting generation matters more than it looks. Adopting the large-scale stack before the repository or the team is anywhere near that size adds every layer from the table in the second section without any of the payoff. None of it earns its cost until CI time or dependency-graph size actually demands it. The safer default is starting at whichever generation the current package count and team count actually justify, and moving up only once that generation measurably stops being fast enough.
