Governing AI-Written Code

How to combine deterministic checks, model-based review, and accountable human approval at the merge boundary.

Andreas Ögren
~9 min read
Last updated July 2026

AI assistants let a team produce first drafts faster than reviewers can understand them. Faster drafting does not reduce the evidence needed for a safe merge. Teams must therefore direct limited review time toward the mistakes with the greatest consequences.

Software teams already split review between automated checks and people. Compilers, linters, and test suites reject properties that can be checked repeatedly. People examine intent, design, and operational consequences. Model-based review adds a probabilistic check between these layers. It can read relationships expressed in ordinary code, but it does not turn those relationships into a proof.

At the merge boundary, the team should assess what a change can affect and which evidence can reveal a mistake. Earlier articles covered configuring assistants and producing a reviewable change through a controlled workflow. Deterministic tools, model-based review, and people can provide different kinds of evidence for the merge decision.

From Writing Bottleneck to Review Bottleneck

When drafting accelerates, the review queue grows unless the team changes how it checks and routes proposed changes.

An agent can turn one task description into a multi-file pull request in the time a developer might previously have spent understanding the first file. Fast generation does not reduce the reviewer's responsibility. The reviewer needs to confirm the intended behavior, check how the change fits the surrounding architecture, and inspect what happens outside the happy path.

Parallel agents can produce several changes without increasing the number of maintainers who know the affected code. Large diffs take time to understand regardless of who wrote them. A team that measures only generation speed may miss a longer review queue and slower delivery.

Rule-Based, AI, and Hybrid Review

Rule-based tools find violations expressed in their configuration. Model-based reviewers can examine relationships that no rule represents.

Rule-based review applies explicit checks with compilers, linters, and other analysis tools. A fixed configuration produces repeatable findings for a given input. Rule-based tools work well when a property can be encoded precisely. They cannot report a concern that no rule or analysis represents.

Model-based review can inspect a diff together with selected repository context and describe relationships that were never encoded as rules. It may notice a new helper that duplicates an existing abstraction or a caller written for the old shape of an interface. Its findings are probabilistic and depend on which files reached the model. A plausible comment may be wrong or may miss the relevant code entirely.

In a hybrid pipeline, deterministic checks run first and reject known violations without spending model time. A model-based pass then examines the change for context-dependent concerns. Human reviewers receive the findings and their supporting evidence before deciding whether the change can merge.

Suppose a change adds a field to an API response. A type checker may confirm that the server and generated client agree on its type. A contract test can verify a recorded response. A model reviewer may notice that a hand-written mobile client still assumes the old payload size, provided that caller enters its context. The service owner decides whether the compatibility risk is acceptable. The checks overlap, but each supplies a different kind of evidence.

Generated tests deserve a separate check because passing tests may exercise code without protecting behavior. Mutation testing deliberately alters the implementation and checks whether the suite fails. Coverage shows which code ran during a test, while mutation testing shows whether selected code changes can escape the assertions. The team must evaluate the specification separately.

Rule-based
Fixed rulebook

Rule-based checks run quickly and produce repeatable results for a given input. They catch known patterns reliably but cannot reason about anything outside the rulebook or the supplied analysis.

AI-based
Infers from selected context

Model-based review can flag breaking changes, duplicated logic, and architectural drift when the necessary context is available. Its findings need supporting evidence because they may be incomplete or wrong.

Hybrid
Rules first, AI second

A hybrid review runs deterministic checks first. The model then examines context-dependent issues that the encoded rules do not cover.

Precision, Recall, and Reviewer Attention

Reviewers need checks that catch consequential defects without overwhelming them with false warnings.

Precision measures how many flagged findings are real problems. Recall measures how many real problems the tool managed to flag. Lowering a detection threshold can improve recall by reporting more candidates, but it usually reduces precision by admitting more false positives. Neither measure is sufficient on its own because findings consume finite reviewer attention.

The acceptable tradeoff depends on the finding. A missed authorization flaw can cost more than investigating several plausible warnings, so a security check may favor recall. Repeated low-value warnings slow review and encourage people to skim later findings. Many review products do not expose a numeric detection threshold. A team can still change what reaches reviewers by combining detectors, filtering categories, and setting different escalation rules.

The pipeline should separate detection from presentation. Broad checks may collect many candidates, so filters and category-specific thresholds determine what reaches a reviewer. Each reported finding should name the affected code and explain the concern. Deterministic tools can enforce style rules, which lets model-based review focus on relationships that are difficult to encode.

Measuring precision and recall requires a labeled evaluation set in which the expected findings are known. The set can combine historical defects with carefully constructed changes that represent the repository's risks. Precision can then be calculated from the tool's reported findings, while recall uses the full set of known defects as its denominator. The evaluation should be repeated as the repository and models change. A model reviewer will miss some defects and produce some incorrect findings, so its additional findings must justify the time spent investigating them.

The unit of evaluation has to be defined before the numbers can be compared. Two comments about one faulty authorization check may count as one underlying defect, while a vague warning with no actionable location may count as no useful finding. Severity belongs beside precision and recall because catching ten minor naming issues does not compensate for missing the security case the review was introduced to detect.

An offline evaluation measures known cases under repeatable conditions. Production review supplies a different signal through accepted comments, dismissed findings, review time, and defects discovered after merge. Acceptance alone does not prove that a comment was correct, and a low acceptance rate may reflect poor presentation or an unsuitable threshold. Teams need both forms of evidence when a model, prompt, or context-selection method changes.

Risk-Tiered Review

Review tiers let a team spend more time on changes whose failure would be harmful or difficult to reverse.

Generated fixtures or internal documentation are often easy to validate and replace. Code that controls access or handles financial and personal data needs more scrutiny because a subtle defect can create lasting harm. Destructive data operations need similar care because recovery may be slow or impossible.

The review tier should depend on the change's possible effect, the difficulty of rollback, and the available verification. A small authorization change may need more review than a large generated test fixture. A generated refactor may need less when types and tests constrain its behavior closely.

Risk can change across the delivery path. A database migration may be easy to review as SQL but difficult to reverse after production data has changed. A feature behind a server-side flag may have a safer rollback path than a client release that takes days to reach users. The tier should reflect the deployed effect rather than the size or apparent simplicity of the diff.

Each tier can require a different combination of automated evidence and human approval, as the following example shows.

Model-based review can contribute findings in the high tier. A named human reviewer must examine the evidence and approve the change because an error may affect users, data, or legal obligations.

Review Policy and Attribution

A written policy defines permitted agent use, required evidence, and the person who approves each review tier.

A short policy can identify high-risk areas and state which checks and approvals each tier requires. Applying the tiers to all changes keeps authorship from becoming a substitute for risk assessment. AI attribution can tell reviewers how a diff was produced, but the possible impact should determine its review path.

A usage guideline defines which work may be delegated and which actions require approval. It should identify areas where an agent needs a named owner. A team might allow autonomous updates to generated fixtures while requiring a security owner for any password-reset change. Human-written changes should follow the risk tier as well.

The approval process can build on existing pull-request checks and deployment gates. The policy adds the evidence required for each tier, such as mutation results for generated tests or a threat-model review for a new authorization path. Reviewers then know what must be present before they begin reading the diff.

Attribution records how the change was produced. A pull request can name the contributing tool, describe the developer's review, and record the checks used to validate the result. The record helps later audits and supports the mixed-authorship questions covered in Data and IP in AI Tooling. The review policy should state what evidence the submitter provides and which approver or system owner accepts the risk of merging and operating the change.

A team can begin with a short policy that defines risk tiers, required evidence, and approval owners. Pull requests can record AI contribution when the provenance is useful. Review outcomes and defects found after release should inform later policy changes.

Human Approval

A model reviewer cannot approve risks that depend on business commitments or organizational responsibility.

A model reviewer sees only the context supplied by the system. It may receive the diff and nearby code but miss an earlier decision or incident that explains the current design. Customer commitments and operational constraints may be absent as well. A human reviewer can identify missing context and seek it out before approving the change.

Human approval is useful only when the reviewer can inspect the evidence and has authority over the affected system. A mandatory click from someone unfamiliar with the service creates a record without adding much judgment. High-risk paths should route the change to an owner who understands the failure modes and can request another test, a narrower rollout, or a redesign.

People who own a system must decide its architecture and product tradeoffs. They approve security boundaries and compliance obligations on behalf of the organization. Deterministic tools can enforce known rules, and a model can search for context-dependent defects. A person must make the final decision when an error could create significant harm.
