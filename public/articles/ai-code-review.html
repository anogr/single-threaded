Governing AI-Written Code

How to combine deterministic checks, model-based review, and accountable human approval at the merge boundary.

Andreas Ögren
~8 min read
Last updated July 2026

AI assistants reduce the time needed to produce a first draft, but they do not reduce the care required to merge it. A team can therefore generate changes faster than its reviewers can understand them. The practical question is no longer only how to create code efficiently. It is how to direct limited review attention toward the changes where a mistake would matter most.

This article focuses on that merge boundary. Earlier articles covered configuring assistants and producing a reviewable change through a controlled workflow. Once the diff exists, its origin matters less than its risk. The sections below separate deterministic checks from model-based review, then turn that distinction into review tiers, approval rules, and a clear role for human judgment.

From Writing Bottleneck to Review Bottleneck

Faster drafting moves work into review unless the rest of the delivery system changes with it.

An agent can turn one task description into a multi-file pull request in the time a developer might previously have spent understanding the first file. The review cost does not fall by the same amount. Someone still has to confirm that the change solves the right problem, respects the surrounding architecture, and behaves safely outside the happy path.

The queue becomes especially visible when agents produce several changes in parallel. More proposals do not create more maintainers with domain knowledge, and a large diff remains difficult to review regardless of who authored it. Teams that measure only generation speed can therefore report a local productivity gain while lead time and reviewer load worsen elsewhere.

Rule-Based, AI, and Hybrid Review

A linter and an AI reviewer aren't competing at the same job. They're catching different classes of mistake.

Rule-based review applies explicit checks through compilers, linters, type systems, security scanners, and policy engines. The same input produces the same finding under the same configuration. These tools are strong at properties that can be encoded precisely, but they cannot flag a concern no rule or analysis represents.

Model-based review can inspect a diff together with selected repository context and describe relationships that were never encoded as rules. It may notice that a new helper duplicates an existing abstraction or that a caller still assumes the old shape of an interface. Its findings are probabilistic, however, and depend on which files reached the model. A plausible comment may be wrong or may miss the relevant code entirely.

A hybrid pipeline gives each kind of tool the work it suits. Deterministic checks run first and reject known violations without spending model time. A model-based pass can then examine the remaining change for context-dependent concerns. Human reviewers receive both sets of findings, along with the evidence needed to accept or dismiss them.

Generated tests deserve a separate check because passing tests may exercise code without protecting behavior. Mutation testing can deliberately alter the implementation and confirm that the suite detects the change. It does not prove the specification is correct, but it gives stronger evidence than coverage alone that the assertions can fail when behavior changes.

Rule-based
Fixed rulebook

Fast, deterministic, the same result every time. Catches known patterns reliably. Blind to anything outside the rulebook or dependent on the rest of the codebase.

AI-based
Reasons over context

Understands how a change relates to the rest of the repository, catching breaking changes, duplicated logic, and architectural drift. Slower and less predictable than a fixed rule.

Hybrid
Rules first, AI second

A deterministic pass catches what it reliably can, before an AI pass spends its effort on the context-dependent issues the rule engine was never going to find.

Recall Over Precision

The design principle behind a review tool you can trust at the point where code merges.

Precision and recall pull in different directions. Precision measures how many of the things a tool flagged were real problems. Recall measures how many of the real problems the tool managed to flag. A traditional linter tends to optimize for precision, minimizing false alarms, because it isn't the last line of defense and a missed issue elsewhere still has other chances to get caught.

At the merge boundary, that calculation flips. A false positive costs a developer a moment's attention and gets filtered out before anything ships. A missed real vulnerability rides straight through to production, where the cost of finding out is dramatically higher than the cost of a little extra noise during review. A review tool tuned for recall accepts more false alarms in exchange for catching more of what matters. It pushes the job of filtering that noise to a separate pass, rather than asking the reviewer itself to be conservative about what it flags.

Noise still matters because reviewers learn to ignore a tool that comments on everything. A practical pipeline can separate detection from presentation: broad checks collect candidates, then deduplication and confidence thresholds decide which findings deserve attention. High-risk categories can keep a lower threshold, while style preferences should usually remain deterministic or silent.

Recall is valuable at the merge boundary because the pipeline is meant to compensate for rushed or inconsistent manual checking. It cannot provide perfect coverage, and a model reviewer should never be described as a guarantee. Its role is to add another chance to catch a defect before production, especially where a deterministic rule is unavailable.

A Risk-Based Review Strategy

More code arrives than anyone has time to read with equal care, so decide in advance what deserves that care.

Review effort should follow consequence and reversibility. Generated fixtures or internal documentation are often cheap to validate and cheap to replace. Authentication, payment handling, authorization, destructive data operations, and personal-data processing deserve more scrutiny because a subtle defect can create lasting harm even when the code looks conventional.

Authorship alone is a poor risk signal. A small human-written authorization change may deserve more attention than a large generated test fixture, while a generated refactor can be low risk if behavior is strongly constrained by types and tests. The tier should therefore be assigned from what the change can affect, how easily it can be rolled back, and which controls can verify it.

A workable version of this routes each tier to a different review path, rather than applying the same process to everything and hoping reviewers naturally spend more attention where it matters:

The model-based review still contributes in the high tier, but a clean result is insufficient on its own. A named human reviewer must examine the evidence and accept the risk because an error in this category has consequences beyond redoing a test fixture.

The Governance Decisions

A strategy nobody wrote down is a preference. Three decisions turn the tiers into policy.

The review tiers need to be written down because deadline pressure otherwise turns them into suggestions. A short policy can identify the high-risk areas, state which automated checks are mandatory, and name the approval required for each tier. It should apply to all changes. AI attribution can inform the reviewer about how the diff was produced, but it should not excuse weak review of human-authored code or replace an assessment of impact.

The first decision is a usage guideline. It states which work may be delegated, which actions require approval, and which areas an agent must not change without a named owner involved. A team might allow autonomous updates to generated fixtures while requiring a security owner for any password-reset change. The rule governs the path to merge rather than pretending that human first drafts are automatically safe.

The second decision is the approval process. Existing pull-request checks and deployment gates usually remain the right foundation. The policy adds the evidence required for each tier, such as mutation results for generated tests or a threat-model review for a new authorization path. Reviewers then know what must be present before they begin reading the diff.

The third decision is attribution. A pull request can record which tool contributed, what the developer reviewed, and which tests or checks validated the result. That information helps later audits and supports the mixed-authorship questions covered in Data and IP in AI Tooling. Attribution should provide provenance, not act as a substitute for ownership by the person submitting the change.

None of this requires elaborate tooling to start. A short usage policy and a habit of flagging AI-authored changes in pull request descriptions cover most of what a team needs before scaling further.

Where Human Review Stays Non-Negotiable

Even a very good AI reviewer has a blind spot no amount of codebase context fixes.

A model reviewer sees only the context the system supplies. It may receive the diff and nearby code but miss the decision record, incident history, customer commitment, or operational constraint that explains why the code has its present shape. A human reviewer can recognize that missing context and seek it out before approving the change.

Architecture, security boundaries, compliance obligations, and product tradeoffs remain decisions for accountable people. A model can surface questions and compare a change with repository conventions, but it cannot accept organizational risk. The useful arrangement is therefore layered: deterministic tools enforce known rules, a model broadens the search for context-dependent defects, and a human signs off where the cost of error is high.
