Governing AI-Written Code

The review bottleneck AI coding created, a risk-based way to decide what needs a human, and the policy that makes the answer stick.

Andreas Ögren
~10 min read
Last updated July 2026

Not long ago, the bottleneck in software delivery was writing code. For teams that adopted AI coding assistants seriously, that bottleneck has since moved one step to the right, to reviewing it. More code gets proposed than any team has time to read line by line. The sheer volume has forced a rethink of what review is supposed to catch, and who or what should be catching it.

This article covers the last gate in the series. Earlier articles covered configuring assistants, the workflows that get code to a reviewable state safely, and what an agent can reach once it's connected to real systems. What remains is the merge boundary. Once a diff shows up for review, human-authored or not, how does a team decide what needs a person's full attention and what doesn't? And once decided, what gets written down so the answer survives contact with a deadline?

From Writing Bottleneck to Review Bottleneck

Time-to-first-draft collapsed, but that didn't make review faster. It moved the queue.

A couple of years ago, an AI-authored pull request was a rounding error on most teams. A large and growing share of code reviews on GitHub now involve an agent, and on the most aggressively AI-adopting teams, AI-assisted code accounts for a substantial fraction of committed lines. First drafts arrive far faster than they used to.

It hasn't translated into faster delivery in any simple sense, because the review step didn't get faster along with it. AI-generated pull requests wait considerably longer to get picked up for review than human-written ones. When someone does look, they're accepted far less often than human-authored ones. The bottleneck didn't disappear when writing got faster. It moved to whoever has to read the result, and that person is now reading a lot more of it.

Rule-Based, AI, and Hybrid Review

A linter and an AI reviewer aren't competing at the same job. They're catching different classes of mistake.

Traditional static analysis, the kind tools like SonarQube have done for years, works off a fixed rulebook of known patterns, checked the same deterministic way every time. It's fast, predictable, and blind to anything the rulebook doesn't cover, including anything that depends on how a change relates to the rest of the codebase rather than how the changed lines look in isolation.

AI-based review works from the opposite direction. Rather than matching a diff against a fixed rule set, it reasons over the change in the context of the surrounding repository. Qodo is one concrete example of a tool built around that kind of understanding. Tools in this category catch a breaking change to a function other services still call the old way, logic that already exists somewhere else in the repo under a different name, or a new pattern that quietly drifts from an established convention. None of that is a rule that can be written down in advance. It depends entirely on what the rest of the codebase looks like right now.

More pipelines now run both rather than choosing one. DeepSource is a concrete example of the shape this takes. A deterministic rule engine, with thousands of rules across dozens of languages, runs first and catches everything it structurally can. Only after that does an AI pass, working with full codebase context, look for the issues the rule engine can't be written to find.

What gets reviewed has widened too. A diff that includes new tests raises a question neither a linter nor an ordinary reading catches reliably. Does the new test verify anything, or does it merely execute the code and pass? Some review pipelines now run a mutation-testing pass specifically against AI-generated tests, deliberately breaking the code under test and confirming the suite notices, the same check covered in more depth in the workflows article. A test suite that passes without ever failing on a genuine bug is a coverage number with nothing behind it.

Rule-based
Fixed rulebook

Fast, deterministic, the same result every time. Catches known patterns reliably. Blind to anything outside the rulebook or dependent on the rest of the codebase.

AI-based
Reasons over context

Understands how a change relates to the rest of the repository, catching breaking changes, duplicated logic, and architectural drift. Slower and less predictable than a fixed rule.

Hybrid
Rules first, AI second

A deterministic pass catches what it reliably can, before an AI pass spends its effort on the context-dependent issues the rule engine was never going to find.

Recall Over Precision

The design principle behind a review tool you can trust at the point where code merges.

Precision and recall pull in different directions. Precision measures how many of the things a tool flagged were real problems. Recall measures how many of the real problems the tool managed to flag. A traditional linter tends to optimize for precision, minimizing false alarms, because it isn't the last line of defense and a missed issue elsewhere still has other chances to get caught.

At the merge boundary, that calculation flips. A false positive costs a developer a moment's attention and gets filtered out before anything ships. A missed real vulnerability rides straight through to production, where the cost of finding out is dramatically higher than the cost of a little extra noise during review. A review tool tuned for recall accepts more false alarms in exchange for catching more of what matters. It pushes the job of filtering that noise to a separate pass, rather than asking the reviewer itself to be conservative about what it flags.

The two goals don't have to trade off as sharply as they first appear to. Recent hybrid approaches, combining a language model's judgment with deterministic static analysis, have reported eliminating the large majority of false positives while keeping recall high. Catching broadly and staying quiet about noise turn out to be a solvable combination, not an inherent tradeoff.

The reason recall matters this much isn't hypothetical. Most developers say they don't fully trust that AI-generated code is functionally correct, yet many admit they don't always check it before committing. That gap, distrust that doesn't translate into a matching habit of verification, is precisely what a recall-oriented tool sitting in the merge path is meant to close. It doesn't require every developer to close the gap themselves through discipline, but closes it structurally, by catching what a rushed or skipped check would have missed.

A Risk-Based Review Strategy

More code arrives than anyone has time to read with equal care, so decide in advance what deserves that care.

Not all code carries the same cost if something slips through. Scaffolding, test fixtures, boilerplate, and documentation are quick to verify by running rather than reading closely, and cheap to redo if something's wrong. Authentication logic, payment handling, data validation, and anything touching personally identifiable information sit at the other end, not because an assistant writes obviously worse code there, but because a mistake is both harder to spot in review and far more expensive once it ships.

Audits of production codebases give that high tier a sharper edge than intuition alone would. They have found privilege-escalation paths and architectural design flaws showing up far more often in AI-generated code than in comparable human-written code. None of that shows up by skimming a diff. It shows up by specifically looking for it, which is the argument for routing this category to a named human rather than trusting a generally clean-looking review.

A workable version of this routes each tier to a different review path, rather than applying the same process to everything and hoping reviewers naturally spend more attention where it matters:

LowScaffolding, test fixtures, boilerplate, docsAI review only
Auto-merge OK
MediumEveryday feature code, most bug fixesAI review, plus one human approver
HighAuth, payments, data validation, PII handlingAI review as a first pass only

The point of the high tier isn't that the AI's review gets ignored. It's that a clean AI review is never sufficient on its own to merge, regardless of how thorough that review looks, because the cost of being wrong there is categorically different from being wrong in a test fixture.

The Governance Decisions

A strategy nobody wrote down is a preference. Three decisions turn the tiers into policy.

The case for writing any of this down is largely a maintainability argument. Analyses of real commit histories have found AI-assisted code carrying measurably more of the problems that surface months later. Two stand out. The first is duplicated logic where an existing function should have been reused. The second is a rising share of code smells, the kind of structural issue that doesn't break a build today but makes the next change harder than it should be. None of that means the code doesn't work. It means unreviewed volume compounds into the kind of debt a written policy exists to catch before it accumulates.

The first decision is a usage guideline, and the tier table above is most of one. Written down, it says which categories of work an assistant may touch freely and which need a human writing the first draft. In concrete terms, a team might let an agent generate the fixtures for a new test suite and merge them without a second thought. A change touching a password reset flow, by contrast, is written by a human first and refined with an assistant's help afterward. A named reviewer signs off before merge regardless of who authored the diff.

The second decision is an approval process, covering what has to happen before agent-authored code reaches production. For most teams this is closer to their existing pull request process than a new invention. The same review, the same tests, and the same deploy gate still apply. What changes is applying them knowing the author might be an agent rather than a person, which shifts what a reviewer should look for.

The third decision is about attribution, and whether a pull request should note which parts were agent-generated. This isn't about assigning blame, but information a reviewer can use. A diff flagged as agent-authored in an unfamiliar part of the codebase deserves a closer read than one a senior engineer wrote by hand in code they already own. The same record has a use beyond review, since mixed human-and-machine authorship is what code-ownership questions turn on, covered in Data and IP in AI Tooling.

None of this requires elaborate tooling to start. A short usage policy and a habit of flagging AI-authored changes in pull request descriptions cover most of what a team needs before scaling further.

Where Human Review Stays Non-Negotiable

Even a very good AI reviewer has a blind spot no amount of codebase context fixes.

An AI review tool reads the diff and the repository around it, but not the linked ticket, the Slack thread where a workaround got debated, or the reason a particular tradeoff was accepted six months ago and never revisited. It reviews code without knowing why the code exists, which is the kind of context a human reviewer on the team already has, or can go find.

Architectural decisions fall firmly in this category, along with anything where a team's specific risk appetite matters more than a general best practice a model has absorbed from countless other codebases. The most reliable setups treat an AI reviewer's output as one more input into a human's judgment, not a replacement for it, and reserve unconditional human sign-off for the risk tier where being wrong is expensive. None of this replaces reading the code that matters. It changes how much of it a human needs to read first.
