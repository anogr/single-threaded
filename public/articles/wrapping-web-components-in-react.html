Wrapping Web Components in React

A thin typed wrapper for a custom element, including React 19 properties, refs, and custom events.

Andreas Ögren
~5 min read
Last updated July 2026

The companion article builds BaseButton as a custom element with shadow DOM, reflected properties, and a custom event. Its public contract is the DOM, so React can render it without a framework-specific implementation.

React 19 handles custom-element properties and events directly. A wrapper is therefore an API choice rather than a runtime requirement. It can present familiar React prop names, translate a custom event into a typed callback, and expose the element instance through ref.

The example keeps the wrapper narrow. TypeScript describes the intrinsic element, one hook bridges the namespaced custom event, and the component passes ordinary properties straight through.

React 19 and custom elements

React 19 added full custom-element support. During client rendering, a prop is assigned as a property when that name exists on the element instance; otherwise React writes an attribute. Custom events can be subscribed to with an on-prefixed JSX prop, preserving the event's case and dashes.

React 19 property/attribute strategy

During SSR, strings, numbers, and true render as attributes. React omits non-primitive values and false from the HTML. On the client, complex values work when the custom element exposes a matching property during construction. The element should also define sensible attribute behaviour for primitive values emitted by SSR.

TypeScript does not infer a project's custom tags from the browser registry. A declaration is needed before <base-button> receives project-specific prop types in JSX. A wrapper can then add a conventional onButtonClick callback and centralise any compatibility policy.

React 19 lets function components receive ref as a prop, so new wrappers no longer need forwardRef. The API remains available and is scheduled for deprecation in a future React release.

TypeScript global declarations

Register the tag in HTMLElementTagNameMap for typed DOM queries. Augment React.JSX.IntrinsicElements so TypeScript can validate the same tag in JSX.

base-button.d.ts TypeScript 
import { BaseButton } from './base-button';

declare global {
  // Allows: document.querySelector('base-button') → BaseButton
  interface HTMLElementTagNameMap {
    'base-button': BaseButton;
  }

    // Adds standard HTML props and ref, then the element's own properties.
  namespace React {
    namespace JSX {
      interface IntrinsicElements {
        'base-button': React.DetailedHTMLProps<
          React.HTMLAttributes<BaseButton>,
          BaseButton
        > & {
          variant?: BaseButton['variant'];
          size?: BaseButton['size'];
          type?: BaseButton['type'];
          disabled?: boolean;
        };
      }
    }
  }
}

The custom-event bridge

React can subscribe to custom events declaratively, but a namespaced event such as base-button:click is awkward to expose as a conventional React prop. A small hook maps that DOM event to a typed callback.

An imperative property hook is unnecessary for BaseButton. Its properties exist on the constructed instance, so React 19 detects and assigns them. They also reflect to attributes, which matches the primitive values produced during SSR.

useCustomElementEvent uses the DOM event name internally and gives the wrapper a CustomEvent<D>. It removes the listener whenever the element, event name, or callback changes.

useCustomElementEvent.ts TypeScript 
import { RefObject, useEffect } from 'react';

export function useCustomElementEvent<
  El extends HTMLElement,
  D = unknown
>(
  ref: RefObject<El | null>,
  eventName: string,
  handler: ((e: CustomEvent<D>) => void) | undefined
): void {
  useEffect(() => {
    const el = ref.current;
    if (!el || !handler) return;

    const listener = (e: Event) =>
      handler(e as CustomEvent<D>);

    el.addEventListener(eventName, listener);
    return () => el.removeEventListener(eventName, listener);
  }, [ref, eventName, handler]);
}

The event hook needs an internal ref, while callers may also request the element instance. useMergedRefs assigns the same node to both. React 19's RefObject type exposes a mutable current property, so the older MutableRefObject name is no longer needed here.

useMergedRefs.ts TypeScript 
import { Ref, useCallback } from 'react';

type AnyRef<T> = Ref<T> | undefined | null;

export function useMergedRefs<T>(
  ...refs: AnyRef<T>[]
): (node: T | null) => void {
  // eslint-disable-next-line react-hooks/exhaustive-deps
  return useCallback((node: T | null) => {
    for (const ref of refs) {
      if (!ref) continue;
      if (typeof ref === 'function') {
        ref(node);
      } else {
        (ref as React.RefObject<T | null>).current = node;
      }
    }
  }, refs); // stable as long as the refs array members don't change
}
Why useCallback here?

When a callback ref changes, React cleans up the previous ref and calls the new one with the node. Memoising the merged callback avoids that cycle while its input refs are unchanged. The dependency list uses the rest-array members directly; the lint suppression is limited to the case the rule cannot verify statically.

The wrapper component

The wrapper accepts ref as a normal React 19 prop. Its internal ref serves the event subscription, and the merged callback exposes the same BaseButton instance to the caller.

Button.tsx TypeScript · React 19 
export function Button({
  variant = 'primary',
  size = 'md',
  type = 'button',
  disabled = false,
  onButtonClick,
  children,
  className,
  style,
  ref: externalRef,
}: ButtonProps) {
  // The event hook and the caller both need the same element.
  const innerRef = useRef<BaseButton | null>(null);
  const mergedRef = useMergedRefs(innerRef, externalRef);

  // Translate the DOM event into the wrapper's callback prop.
  useCustomElementEvent<BaseButton, BaseButtonClickDetail>(
    innerRef,
    'base-button:click',
    onButtonClick ? (e) => onButtonClick(e.detail) : undefined
  );

  return (
    <base-button
      ref={mergedRef}
      variant={variant}
      size={size}
      type={type}
      disabled={disabled}
      className={className}
      style={style}
    >
      {children}
    </base-button>
  );
}

The JSX uses className. Custom elements inherit the className DOM property from HTMLElement, so React 19 can assign it in the same form used for built-in elements.

variant, size, type, and disabled are passed directly to the custom element. The declaration file gives those props their precise types, while the element's reflected properties keep client assignments and server-rendered attributes aligned.

Callers now use the wrapper like any other typed React component.

App.tsx TypeScript · React 
import { useRef } from 'react';
import { Button } from './Button';
import { BaseButtonClickDetail } from './base-button';

function App() {
  const btnRef = useRef<BaseButton | null>(null);

  const handleClick = (detail: BaseButtonClickDetail) => {
    console.log('clicked', detail.variant);
  };

  return (
    <Button
      ref={btnRef}
      variant="primary"
      size="lg"
      onButtonClick={handleClick}
    >
      Save changes
    </Button>
  );
}

BaseButton owns rendering and DOM behaviour. The wrapper owns React naming, typing, and event translation. Changes to the custom element's public properties or events still require a wrapper update; internal shadow DOM and styling changes do not.

A wrapper earns its place when it improves the consuming API. If the bare tag already has good JSX types and its event names fit the codebase, use it directly. Add a wrapper when the design system needs consistent prop names, defaults, logging, or event translation.

Custom elements are widely available across modern browsers, but specific features around them can have different support. Check the requirements of the element and its chosen authoring library. The companion article covers the platform contract that this wrapper depends on.
