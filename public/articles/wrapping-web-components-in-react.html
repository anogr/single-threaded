Wrapping Web Components in React

How to wrap a custom element in a first-class React component, with TypeScript types, a forwarded ref, and a typed custom event callback.

Andreas Ögren
~10 min read
Last updated July 2026

The companion article built BaseButton from scratch: a custom element with an encapsulated shadow DOM, a shared stylesheet, typed properties, and a custom click event. That component runs anywhere custom elements are supported. No React required.

Dropping it into a React codebase as-is already works, but a thin wrapper is still worth writing for a design system: typed props, a forwarded ref, and a callback mapped to the right event detail type. The gap being bridged is the one covered previously: React manages a virtual DOM, while a custom element is real DOM that the browser manages directly, so React only ever sees it as an opaque node.

This article writes that wrapper: three small generic hooks and one thin component, with full TypeScript safety.

React 19 and custom elements

React 19 (released December 2024) brought long-overdue improvements to custom element support. On the client, React now checks whether a prop name matches a property on the custom element instance, and if so, sets it as a JavaScript property rather than an HTML attribute. It also added declarative event listener support: passing on + the event name as a JSX prop makes React call addEventListener automatically. These two changes mean that for simple use cases, dropping a custom element into a React tree just works.

React 19 property/attribute strategy

On the client, props matching a property on the custom element instance are set as JS properties. The rest become attributes. On the server (SSR), primitive props (string, number, true) render as attributes, but non-primitive props are omitted to avoid hydration mismatches. This means complex props like objects still require the imperative ref approach when SSR is involved.

Despite these improvements, a typed wrapper component is still the right call for a design system. Using <base-button> bare in JSX provides no TypeScript safety on props, no onButtonClick callback mapped to the right detail type, and no forwarded ref for the consumer to rely on. The wrapper layer is thin, but it converts a loosely-typed DOM element into a properly-typed React component.

In React 19, forwardRef is deprecated. ref is now a plain prop on function components, so the wrapper is written accordingly.

TypeScript global declarations

Before writing the component, register the custom element with TypeScript so that document.querySelector('base-button') returns a typed BaseButton instance, and so JSX knows what props the bare tag accepts.

base-button.d.ts TypeScript 
import { BaseButton } from './base-button';

declare global {
  // Allows: document.querySelector('base-button') → BaseButton
  interface HTMLElementTagNameMap {
    'base-button': BaseButton;
  }

  // Allows JSX: <base-button ...>. Use React.HTMLAttributes as the base,
  // then add the element's own props. 'ref' is handled by React itself.
  namespace React {
    namespace JSX {
      interface IntrinsicElements {
        'base-button': React.HTMLAttributes<BaseButton> & {
          variant?: BaseButton['variant'];
          size?: BaseButton['size'];
          type?: BaseButton['type'];
          disabled?: boolean;
        };
      }
    }
  }
}

Helper hooks

Three small hooks do the heavy lifting for the wrapper. They are generic enough to be reused across any custom element in the system.

useCustomElementProperty sets a DOM property imperatively whenever its value changes. This is useful for non-primitive props (objects, arrays, complex types) that React 19 would otherwise omit during SSR or fail to set correctly.

useCustomElementProperty.ts TypeScript 
import { RefObject, useEffect } from 'react';

export function useCustomElementProperty<
  El extends HTMLElement,
  K extends keyof El
>(
  ref: RefObject<El | null>,
  property: K,
  value: El[K]
): void {
  useEffect(() => {
    const el = ref.current;
    if (el !== null) {
      el[property] = value;
    }
  }, [ref, property, value]);
}

useCustomElementEvent subscribes to a DOM custom event on the element and calls a React callback, cleaning up automatically on unmount or when the handler reference changes. Even though React 19 can wire up on-prefixed JSX props to addEventListener, doing so via a hook keeps the event strongly typed against CustomEvent<D> and keeps the wrapper's internal logic explicit.

useCustomElementEvent.ts TypeScript 
import { RefObject, useEffect } from 'react';

export function useCustomElementEvent<
  El extends HTMLElement,
  D = unknown
>(
  ref: RefObject<El | null>,
  eventName: string,
  handler: ((e: CustomEvent<D>) => void) | undefined
): void {
  useEffect(() => {
    const el = ref.current;
    if (!el || !handler) return;

    const listener = (e: Event) =>
      handler(e as CustomEvent<D>);

    el.addEventListener(eventName, listener);
    return () => el.removeEventListener(eventName, listener);
  }, [ref, eventName, handler]);
}

useMergedRefs combines multiple refs into a single callback ref. This lets the wrapper hold an internal RefObject for imperative DOM access, while simultaneously forwarding a ref to the consumer, all without either ref interfering with the other. The cast inside the loop targets RefObject rather than the older MutableRefObject: React 19's types deprecated MutableRefObject since RefObject is mutable by default now.

useMergedRefs.ts TypeScript 
import { Ref, useCallback } from 'react';

type AnyRef<T> = Ref<T> | undefined | null;

export function useMergedRefs<T>(
  ...refs: AnyRef<T>[]
): (node: T | null) => void {
  // eslint-disable-next-line react-hooks/exhaustive-deps
  return useCallback((node: T | null) => {
    for (const ref of refs) {
      if (!ref) continue;
      if (typeof ref === 'function') {
        ref(node);
      } else {
        (ref as React.RefObject<T | null>).current = node;
      }
    }
  }, refs); // stable as long as the refs array members don't change
}
Why useCallback here?

React calls a callback ref every render if its function identity changes, triggering unnecessary detach/re-attach cycles. useCallback memoises the merged ref so it only changes when the incoming refs themselves change. Note that the eslint exhaustive-deps rule would flag this. The disable comment is intentional since refs is a rest argument spread, not a stable array reference.

The wrapper component

With the hooks in place, the wrapper itself is simple. Since forwardRef is deprecated in React 19, the wrapper accepts ref as a plain prop. The internal useRef is needed to drive the imperative hooks, and useMergedRefs unifies it with whatever the consumer passes.

Button.tsx TypeScript · React 19 
export function Button({
  variant = 'primary',
  onButtonClick,
  children,
  className,
  style,
  ref: externalRef,
}: ButtonProps) {
  // Internal ref for imperative hooks, merged with whatever the consumer passed in
  const innerRef = useRef<BaseButton | null>(null);
  const mergedRef = useMergedRefs(innerRef, externalRef);

  // Set the DOM property directly. size, type, and disabled work the same way
  useCustomElementProperty(innerRef, 'variant', variant);

  // Subscribe to the custom event, strongly typed against its detail payload
  useCustomElementEvent<BaseButton, BaseButtonClickDetail>(
    innerRef,
    'base-button:click',
    onButtonClick ? (e) => onButtonClick(e.detail) : undefined
  );

  return (
    <base-button ref={mergedRef} class={className} style={style}>
      {children}
    </base-button>
  );
}

A few things stand out here. The JSX element uses class not className. It is a native element, not a React component, so React's aliasing does not apply. The wrapper still accepts className as a prop and passes it through as class to give consumers the familiar React API.

None of variant, size, type, or disabled appear as props on the JSX element itself. Each one goes through useCustomElementProperty via the ref instead, which sets the DOM property directly and triggers the element's own setters. This sidesteps React 19's SSR/attribute ambiguity entirely and makes the prop-to-DOM mapping explicit and testable. The full ButtonProps interface and all four property calls are in the full source at the end.

Using the wrapper looks exactly like any other React component:

App.tsx TypeScript · React 
import { useRef } from 'react';
import { Button } from './Button';
import { BaseButtonClickDetail } from './base-button';

function App() {
  const btnRef = useRef<BaseButton | null>(null);

  const handleClick = (detail: BaseButtonClickDetail) => {
    console.log('clicked', detail.variant);
  };

  return (
    <Button
      ref={btnRef}
      variant="primary"
      size="lg"
      onButtonClick={handleClick}
    >
      Save changes
    </Button>
  );
}

The BaseButton custom element owns rendering and its own lifecycle. The Button React wrapper owns the React integration surface. Neither knows too much about the other: the component's internals (new slots, tweaked styles, additional properties) can evolve without touching the wrapper, and the wrapper's React patterns can be refined without touching the element class.

Web Components are not trying to compete with React. They live at a lower layer, the browser platform, and that is exactly what makes them useful as a foundation for design systems that need to outlast any particular framework. The wrapping pattern built here applies to any custom element: three small generic hooks, one thin wrapper component, and the result is a first-class React citizen with full TypeScript safety.

The APIs are stable, the browser support is universal, and the tooling (Lit, FAST, Stencil, or the vanilla approach used in the companion article) is mature. It is a good time to know how they work.

Button.tsx TypeScript · React 19 
import { useRef, Ref } from 'react';
import { BaseButton, BaseButtonClickDetail } from './base-button';
import { useCustomElementEvent } from './useCustomElementEvent';
import { useCustomElementProperty } from './useCustomElementProperty';
import { useMergedRefs } from './useMergedRefs';

export interface ButtonProps {
  variant?: BaseButton['variant'];
  size?: BaseButton['size'];
  type?: BaseButton['type'];
  disabled?: boolean;
  onButtonClick?: (detail: BaseButtonClickDetail) => void;
  children?: React.ReactNode;
  className?: string;
  style?: React.CSSProperties;
  // React 19: ref is a plain prop, no forwardRef needed
  ref?: Ref<BaseButton>;
}

export function Button({
  variant = 'primary',
  size = 'md',
  type = 'button',
  disabled = false,
  onButtonClick,
  children,
  className,
  style,
  ref: externalRef,
}: ButtonProps) {
  // Internal ref for imperative hooks
  const innerRef = useRef<BaseButton | null>(null);

  // Merge the internal ref with any ref the consumer passed in
  const mergedRef = useMergedRefs(innerRef, externalRef);

  // Set properties directly on the DOM element.
  // For primitives React 19 handles this via JSX, but doing it here
  // is explicit, SSR-safe, and works regardless of React version.
  useCustomElementProperty(innerRef, 'variant', variant);
  useCustomElementProperty(innerRef, 'size', size);
  useCustomElementProperty(innerRef, 'type', type);
  useCustomElementProperty(innerRef, 'disabled', disabled);

  // Subscribe to the custom event via the DOM, strongly typed
  useCustomElementEvent<BaseButton, BaseButtonClickDetail>(
    innerRef,
    'base-button:click',
    onButtonClick ? (e) => onButtonClick(e.detail) : undefined
  );

  return (
    <base-button
      ref={mergedRef}
      class={className}
      style={style}
    >
      {children}
    </base-button>
  );
}
