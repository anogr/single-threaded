Frontend Routing and URL Architecture

How a public URL becomes matched application behavior while navigation, data, and history stay consistent.

Andreas Ögren
~30 min read
Last updated August 2026

A developer opens an issue in a project tracker and copies its URL. A colleague who follows the link should reach the issue. Reloading the page should open it again. Navigating elsewhere should update the address when the new view has its own URL. Using the Back button should return to the previous view. These are different ways to enter and navigate through the application, but each way depends on a URL having a stable meaning.

Frontend routing determines how an application responds to the browser's current URL. URL architecture determines which parts of an application have URLs, how those URLs are structured, and what they mean. A good URL structure keeps these meanings understandable as the application changes. Routing code applies the structure when a user follows a link, reloads the page, or navigates within the application.

This article explains routing by following a URL from the browser into an application. The goal is to show what happens along the way, which layer handles each step, and how one routing decision leads to the next.

The URL as Public Application State

A navigable view needs a stable address.

A URL represents a navigable view when the application can rebuild that view from the address. Reloading, opening another tab, or sharing the address should reach an equivalent destination. Component state does not provide this durability unless the relevant value is encoded in the URL. A URL therefore becomes part of the application's public state when navigation depends on it.

Different parts of the URL provide different kinds of input. The origin identifies the server and establishes the browser's security boundary. The path identifies a location within the application. The query can refine how a location is viewed. The fragment identifies a position or target inside the loaded document. The URL Standard defines the syntax of these parts. The application decides what its own paths and query values mean.

Consider a project tracker. /workspaces/acme/issues can identify the issue list for one workspace. /workspaces/acme/issues/1842 can identify one issue within it. Adding ?view=comments can show the comments tab. Adding #results can point to the results region inside the loaded document. The browser keeps the fragment out of the HTTP request, so a server cannot use it when selecting a response.

Durable and temporary state

Some interface state should appear in the URL because another person may need to reproduce the view. An issue identifier is a clear example because it selects a navigable resource. A status filter can qualify for a similar reason when sharing the filtered view is useful. Temporary interaction state usually does not need an address. An open tooltip or an unfinished field value can disappear when the view closes without changing what location the user was visiting.

Public URLs should describe product concepts that are expected to survive implementation changes. Moving a component to another source directory should not force every link to an issue to change. A route based on a stable issue identifier can survive such a refactor because the public address describes the issue rather than the code used to render it. Consistent casing and a predictable trailing-slash policy reduce unnecessary alternate forms. Redirects can later provide a transition from an old address to a preferred one.

Treat URL values as external input

Route values arrive as input from outside the application. A path parameter can contain an unexpected identifier, and a query value can contain an unsupported value. Routing code therefore needs to parse incoming values before application logic uses them. Validation can reject malformed input, while authorization decides whether the current user may access the requested resource.

URLs should not carry secrets. Addresses can be stored in browser history and recorded by servers or monitoring tools, and they can be copied into messages or exposed through referrer information.

Routes Turn URLs into Application Behavior

A router compares the current path with route patterns and determines which route matches.

A router reads the browser's current location and compares its path with the routes defined by the application. Each route connects a URL pattern to application behavior. When a pattern matches, the router selects the route and extracts any values encoded in the path. The result is a route match.

Static, dynamic, and catch-all segments

The simplest route patterns contain only fixed text. A pattern such as /workspaces/new matches one specific path. A dynamic segment replaces one fixed segment with a named placeholder. In /workspaces/:workspaceId/issues/:issueId, the names workspaceId and issueId mark values supplied by the URL. Matching /workspaces/acme/issues/1842 therefore produces acme for workspaceId and 1842 for issueId.

Some routers support a catch-all pattern for paths with an unknown number of segments. A file browser can use one when the route needs to capture a nested file path. Catch-all patterns accept a much wider range of URLs than ordinary dynamic segments, so they are usually reserved for routes where a variable-length path is intentional.

Overlapping route patterns

Route patterns can overlap. For example, /workspaces/new can overlap with a dynamic route such as /workspaces/:workspaceId because the dynamic segment can match new. The router needs a predictable rule for selecting one route. React Router ranks route branches and selects the static route in this case. Other routing systems define their own matching rules, so application code must follow the behavior of the selected system.

Routes can be declared directly in configuration or derived from a file structure. Both approaches eventually give the router enough information to match URLs with application behavior. File-based routing can make route organization visible in the source tree, but moving files should not unintentionally change public URLs. Public URLs should follow the product's navigation model even when the implementation is reorganized.

routes.ts TypeScript 
import { index, route, type RouteConfig } from "@react-router/dev/routes";

export default [
  route("workspaces/new", "./new-workspace.tsx"),
  route("workspaces/:workspaceId", "./workspace.tsx", [
    route("issues", "./issues.tsx", [
      index("./issue-list.tsx"),
      route(":issueId", "./issue.tsx"),
    ]),
  ]),
] satisfies RouteConfig;

This configuration uses React Router as a concrete example. A parent route contributes part of the path, and a child contributes the next part. The nested :issueId route therefore produces a URL such as /workspaces/acme/issues/1842. The router can then use the matched route to select the code responsible for the issue view.

A URL Matches a Route Branch

A URL can activate a sequence of nested routes, with each route contributing part of the resulting view.

Nested routing changes what a successful match looks like. For /workspaces/acme/issues/1842, the router can match a root route, then a workspace route, an issues route, and finally the issue route where 1842 is captured. Together these matches form a route branch from the root to the selected issue. Thinking in branches is important because later responsibilities such as layout and failures can be attached at different levels of the same branch.

Layouts follow the matched branch

The routes in a branch do not compete to render one page. A parent can provide structure around its matched child. The workspace route, for example, can render workspace navigation while leaving space for the selected workspace view. The issues route can add another layer inside this space before the issue route renders the selected issue.

A nested route usually renders its matched child through an outlet. The outlet marks the position where the child view appears. When navigation moves from one issue to another, the workspace and issues layouts can stay mounted while the content in the innermost outlet changes. This structure lets routing preserve interface regions shared by nearby URLs.

An index route handles the parent URL without adding another path segment. At /workspaces/acme/issues, an index route can render the issue list inside the issues outlet. Navigating to /workspaces/acme/issues/1842 selects the :issueId child instead. Both are children of the issues route, but only the issue route adds another segment to the URL.

A pathless layout route works differently. It can introduce another level of interface structure without contributing text to the URL. This is useful when several routes need a shared layout but the layout has no useful meaning in the public address.

Route boundaries follow behavior

Each route in the matched branch creates a route boundary. The boundary is a level where the application can attach behavior to one part of the route hierarchy. A route can provide a layout, load data needed by its children, or handle failures from its part of the branch.

A parent route can provide a shared layout for its child routes. The workspace route, for example, can render the workspace header and navigation around an outlet. Every child rendered in that outlet then appears inside the same workspace interface. Moving from the issue list to an individual issue changes the child view while the workspace layout stays in place.

A parent route can also own data needed throughout its branch. The workspace route can load the selected workspace once and make it available to its children. Farther down, the issue route can load the selected issue. Placing each responsibility at the route where it becomes relevant keeps broader responsibilities higher in the branch and more specific ones closer to the leaf.

Failure handling can use these boundaries as well. If an issue cannot be found, the issue route can handle the failure at its own boundary. The issue region can then show an error without replacing the workspace layout around it. A failure higher in the branch can replace a larger part of the interface because more child routes depend on that level.

Not every component needs to become a route. An issue badge can appear throughout the application without having its own URL or position in the route graph. Route boundaries are useful where navigation introduces a meaningful level of application behavior, such as a directly reachable view, a layout shared by several child routes, data needed throughout a branch, or a region with its own failure handling. The route hierarchy therefore reflects navigation and these shared responsibilities rather than copying the component tree.

Document and Client Routing

A URL can be reached by loading a new document or by navigating within the active document.

A document navigation asks the browser to load a URL as a new document. The request reaches the server where routing determines how the URL should be handled. The response includes an HTTP status and usually HTML. The browser replaces the current document with the response, and the application's JavaScript starts again in the new document.

A client navigation keeps the current document alive. When an eligible link is activated, a client router can handle the navigation instead of letting the browser load another document. The router coordinates matching, route code, data, browser history, and the interface update. Network requests may still occur during this process, but the browser does not replace the active document.

Direct visits still reach the server

The client router cannot handle a URL before its document exists. Opening a bookmarked application URL therefore begins with a document navigation. Reloading a client-routed page has a similar effect because the browser requests its current URL from the hosting layer. The server must know how to resolve every application URL a user can enter directly.

This requirement is easy to miss in a client-rendered application. A hosting layer can send the application shell for URLs handled later by the client router. Once the shell loads, the router can inspect the requested path and select the appropriate route. Unknown URLs need different treatment. If the hosting layer returns the application shell with a successful HTTP status for every path, an invalid URL can appear successful to software observing the HTTP response even when the application later shows a not-found view.

A hash router avoids this requirement by storing the client route after #. For /app#/issues/1842, the server receives /app and the browser-side router reads the fragment. This can support static hosting that cannot route different application paths to the same document. The tradeoff is that the fragment no longer acts only as an in-document target, and the server cannot return route-specific HTML, redirects, or status codes for the hash route.

An application can use document navigation for its initial entry and client navigation after JavaScript starts. Server-rendered applications can use a similar transition when later navigation is enhanced in the browser. Routing therefore has to give a public URL a consistent destination regardless of which kind of navigation reaches it. How the destination HTML is produced is a separate rendering decision.

Client routing preserves link behavior

A normal link lets the browser decide how to navigate. A client router can intercept an ordinary click on a link within the application and perform the navigation without loading a new document. Other uses of the link should continue to work as the browser defines them. A modified click can open the destination in another tab, a link with target can open another browsing context, and a download link can start a download. Links to destinations outside the application should follow normal browser navigation as well. The client router therefore handles only the in-app navigations intended to stay within the current document.

Keeping the document alive changes the accessibility work around a route. A document navigation loads a new document, including its title. Client navigation reuses the existing document, so the application must update the title and handle focus or announcements where needed to make the new view clear to the user. Accessibility in Rendering Architecture discusses these behaviors.

Loaders Align Reads with Navigation

A data router can start the reads required by a destination as part of navigation.

Matching a route often reveals which data the destination needs. Navigating to /workspaces/acme/issues/1842 identifies a workspace and an issue before either view renders. A data router can use this information to begin loading data during navigation. A route loader performs the read associated with one matched route and makes its result available to the route component.

A loader receives information from the navigation, including values captured from the URL. Data used by several child routes can be loaded by their parent route. The workspace loader can use workspaceId to read the acme workspace. Farther down the branch, the issue loader can use issueId to read issue 1842. Each loader is placed near the route whose behavior depends on its result.

A loader needs to account for every URL value that changes the data it reads. If ?status=open selects a different issue list, changing the status needs another read or a distinct cached result. Routers differ in how they detect these dependencies.

Start independent reads together

One navigation can activate several loaders. Because the router knows the matched branch before rendering begins, it can start independent reads at the same time. Loading data only after components render can create a sequence when a child cannot render until its parent has finished loading. The parent first renders and starts its request. Once its data arrives, the child can render and start another request. Route loaders let the router start independent reads earlier because matching the destination tells it which loaders to run before their components render.

Cancel obsolete work

The destination can change before a loader finishes. Suppose the user opens issue 1842 and immediately navigates to issue 1843. The first read may still be running when the second navigation begins. A router can provide an abort signal so the loader can cancel supported work. A late result for issue 1842 must not replace the data for the newer destination.

Mutations and Route Actions

Some data routers can connect a write to the route where the user performs it.

Loaders read server-owned data during navigation. Applications need to create, update, and delete server-owned data as well. These changes are often called mutations. A form can send a mutation directly to a server endpoint without involving a client router. Some data routers provide another option by associating the submission with a route. The router can then coordinate the write with navigation and with data previously loaded for the route.

React Router calls the handler for such a submission a route action. An action is the write-side counterpart to a loader. A loader reads data for a route, while an action handles a submission associated with one. For an issue edit, the action can identify the issue from the route, validate the submitted input, check whether the operation is allowed, and attempt the update. Other architectures place these responsibilities in a separate data or service layer.

Actions handle different submission outcomes

An action can produce different outcomes which the application handles differently. Invalid input can return validation information to the issue route so the user can correct the form. A successful edit can leave the user on the issue. Creating a new issue can redirect to the URL of the new record. The action handles the write and returns the information needed for the appropriate navigation or interface update.

Writes make loaded data stale

A successful write can make previously loaded data stale. Suppose the issue loader returned the title Broken search before an action changed it to Search returns no results. The loader result still contains the old title. React Router can revalidate loader data after the action completes by running the relevant loaders again. The issue route then receives the current server value.

Some writes should happen without navigating to another URL. Changing the status of an issue from a list is one example. React Router provides a fetcher for calling route actions without navigation. The issue row can submit the change while the user stays on the list URL. Since no navigation occurs, the submission does not add a history entry.

Mutation handling does not have to live in the router. An application can send writes through another data layer and refresh route data after the server accepts a change. The data layer can then control caching and mutation behavior. The application must still connect a successful write with any loaded route data which is now stale.

An interface can show a change before the server confirms it. This is an optimistic update. An issue row, for example, can show a newly selected status while the update is still in flight. If the write fails, the interface can restore the previous value or show the failure. If it succeeds, fresh server data can confirm the result. Routing can coordinate this process when the mutation and subsequent reads belong to routes.

Navigation Is a State Transition

Client navigation takes time when the destination needs code or data, so the application needs to represent the period before the destination is ready.

A navigation transition begins when client navigation starts and ends when the destination can be shown or the navigation fails. During this period, the router matches the destination and runs the work required by the matched routes. The current view may still be visible while the next one is being prepared.

Show pending UI where work is happening

Routers expose transition state so the interface can show useful feedback while navigation is in progress. Route boundaries provide natural places for this feedback because different parts of the matched branch can be waiting for different work. If issue details are loading, the workspace layout can stay visible while the issue region shows a pending state. If navigation changes the workspace itself, a larger part of the interface may need to show that it is waiting.

Prefetching prepares a likely destination

Prefetching can start code or data work before navigation begins when a destination is likely to be used. For example, an application can prefetch an issue when its link receives pointer or keyboard intent. Prefetching does not navigate to the issue or change the current URL. If the user later follows the link, the router can reuse prefetched data when it is still valid instead of starting the work again.

A newer navigation supersedes an older one

A new navigation can begin before an earlier transition finishes. Suppose the user selects issue 1842 and then selects issue 1843 before the first issue loads. The second navigation becomes the current destination. A late result for issue 1842 must not replace the view for issue 1843.

Writes require a different precaution. Stopping a client while a mutation is in progress does not reverse work already accepted by the server. If an update reaches the server before the user navigates elsewhere, the update may still complete. The server therefore needs its own rules for concurrent writes even when the router can cancel or supersede client-side transitions.

Browser History Is a User-Facing Contract

Every navigation decision affects what the user will encounter later when using Back and Forward.

A browser tab keeps a sequence of session history entries. Each entry records a location the browser can revisit. Back moves to an earlier entry, while Forward moves toward a later one. During client navigation, the router can add or replace these entries. When the user later returns to one, the application uses its URL to show the corresponding view.

Push, replace, or keep the current entry

Opening issue 1842 from an issue list normally creates a new history entry. The list is an earlier stop, so Back can return to it. The History API calls this operation a push. A push is appropriate when the destination should become another meaningful stop in the user's navigation path.

A replace changes the current history entry instead of creating another one. This is useful when the previous address should not become a stop of its own. If an obsolete issue URL is corrected to its current address, replacing the obsolete entry prevents Back from returning immediately to an address which only redirects forward again.

URL changes inside one view require a product decision about what Back should restore. Consider a search field which stores its value in the query string. The user probably should not step backward through every value they typed, so intermediate query changes can replace the current history entry. A completed search or selected filter may be worth returning to later, so that change can create a new entry. The desired Back behavior determines whether a URL change should push or replace an entry.

State associated with a history entry

A history entry can carry additional data through history.state. This data is associated with the entry without appearing in the visible URL. It can help restore temporary interface details while the user moves through history in one tab. A copied URL does not include history.state, so information another person needs to reproduce the view must be available elsewhere.

History traversal can restore scroll position as well as location. Document navigation receives browser scroll restoration behavior directly. Client routing may need to coordinate restoration with rendering because the target position can depend on content which has not appeared yet. The HTML Standard defines the browser APIs and behavior used for history traversal and scroll restoration.

Redirects and Failures Happen at Different Layers

The reason for a redirect or failure determines which layer can handle it.

A request can pass through infrastructure and application routing before reaching a route. Each layer knows something different about the destination. Infrastructure can know that a public host has been replaced. Application routing can know that an old product URL has a new address. After a route matches, an issue loader can discover that issue 1842 does not exist. These are different routing outcomes even though each can change what the client eventually receives.

Redirects preserve URL rules

A redirect tells the client to use another URL. During a document request, the server communicates a redirect with a 3xx HTTP status and a Location header. Redirect statuses distinguish permanent from temporary moves and determine how the client handles the request method when following the new URL.

Consider an issue which moved from an old public path to a new one. A direct request for the old URL can receive a redirect from the server. If the application is already running, its router can apply the public URL rule during client navigation. In either case, visiting the old address leads to the new one. The behavior belongs to the public URL regardless of how the user reached it.

Redirect destinations sometimes come from URL input such as ?returnTo=.... Allowing this value to name any destination can create an open redirect, where a trusted application sends the user to an attacker-controlled site. Applications can avoid this by accepting only known destinations or by validating allowed redirect targets before using them.

Matching and lookup fail at different stages

A request for /unknown can fail because no route pattern accepts the path. No application resource needs to be looked up because routing cannot select a route. During a document request, the server can return a 404 response. During client navigation, the router can show the corresponding not-found view.

A URL can match a route and still select a resource which does not exist. The path /workspaces/acme/issues/9999 can match the issue route before its loader discovers that issue 9999 cannot be found. The first case is a failure to find a route. The second is a failure to find the resource identified by a valid route. Both can produce a 404 response, but they arise at different stages of routing.

Error boundaries control the visible scope

Other failures do not mean anything is missing. A database error while reading an existing issue, for example, means the application could not complete the operation. The interface can show a fallback for the affected region while the application records information needed to investigate the failure. Treating the error as a 404 would incorrectly describe an operational failure as an absent route or resource.

A route error boundary determines how much of the current interface is replaced when route work fails. If loading issue details fails, an issue-level boundary can replace the detail region while leaving the surrounding workspace interface available. A boundary higher in the route branch can replace a larger region when the failure prevents its children from being used.

Failures do not generally require navigation to an error URL. A validation error can stay with the form where the user can correct the input. A missing issue can be represented at the issue route. A temporary service failure can offer another attempt inside the affected region. A redirect is appropriate when the request should lead to a different destination.

Routing Frameworks Package Different Responsibilities

Routing responsibilities can belong to a router, a separate data layer, or a broader application framework.

The routing model developed so far does not depend on a particular framework. URLs still match routes, routes form branches, navigation interacts with browser history, and routes may need data before they can render. Frameworks differ in which of these responsibilities they coordinate and which they leave to other parts of the application. React Router, TanStack Router, and Next.js illustrate three ways to divide this work.

Matching, reads, and writes

React Router can take responsibility for progressively more of the routing lifecycle. Declarative Mode provides route matching and navigation. Data Mode adds loaders for route reads and actions for route submissions. The router can start loaders during navigation and revalidate loaded data after an action. Framework Mode builds on this model with route modules, code splitting, and rendering features.

TanStack Router connects route matching closely with TypeScript types, search parameter validation, and data loading. Information from the route tree flows through parameters, navigation APIs, and loaders with types derived from the route definitions. Route loaders can read data before rendering and cache their results for later navigation. Writes are handled outside the router, so mutation code is responsible for invalidating route data which needs to be read again.

Next.js includes routing as part of a broader application framework. In the App Router, folders and special files define the route tree, layouts, loading states, and error boundaries. Server Components can read data while rendering a route, so route reads do not require a separate loader API. Writes can use Server Functions, including Server Actions bound to forms, or Route Handlers. Routing is therefore closely connected to the framework's rendering and server model.

The responsibilities still exist

These designs put familiar responsibilities in different places. React Router can coordinate matching, route reads, writes, and later revalidation through the router. TanStack Router coordinates matching and route reads while another data layer owns writes. Next.js places routing, server rendering, and much of the data lifecycle inside the framework. A concept such as loading data for a destination exists in all three designs even though only some expose it as a route loader.

Nested layouts and error handling are expressed differently as well. React Router and TanStack Router attach these responsibilities to routes in the route tree. Next.js uses files such as layout, loading, and error at different levels of its route hierarchy. In each case, the hierarchy determines which interface is shared by child routes and how much of the interface is affected when route work fails.

Routing can belong to a larger framework

React Router can be used primarily as a router or extended into a broader application framework through Framework Mode. TanStack Router can stay in the routing layer while TanStack Start provides server and application framework features around it. Next.js starts with the broader framework and includes its router as part of that model. These choices affect where developers configure rendering, data access, and builds.

A routing-system review can locate how URLs become route matches, where destination data is read, which layer handles writes, how stale data is refreshed, and how nested routes divide the interface. The API names and framework boundaries differ, but each system has to account for these navigation problems.

Designing a Routing Architecture

A routing design starts with the locations users need to reach and follows each location through the application.

Routing design begins with the views which need public URLs. An issue list needs an address because a user may want to return to it or share it. An individual issue needs another address because it can be visited independently of the list. A temporary tooltip has no comparable navigation role, so it can stay outside the URL. Starting from user navigation keeps the public address structure independent of the component tree.

Trace reads and writes

Once the public URLs are clear, one URL can be traced through its route branch. For /workspaces/acme/issues/1842, the trace identifies the patterns which match the path and the places where acme and 1842 are validated and used. It then follows the branch to the workspace and issue loaders. If the issue cannot be found, the trace identifies which route handles the failure.

The next trace follows a write which changes data used by the route. For an issue edit, it identifies where submitted values are validated, where the server update happens, and which loaded data becomes stale. It then shows how fresh data reaches the interface after the update. If success leads to another URL, the trace includes the layer which produces the redirect. This sequence shows which layer owns the write and how its result reaches the routes which depend on it.

Test every entry path

The URL needs to survive different forms of navigation. A direct request should let the server resolve the destination, and a reload should reconstruct it without hidden client state. An in-app link should reach an equivalent destination without replacing the document. Back and Forward should revisit useful stops rather than expose incidental URL updates.

An application deployed below the origin root needs one more alignment check. The router's base path, generated links, asset URLs, and hosting rewrites all need to agree on a prefix such as /tracker. A direct request, a reload, and generated links should preserve this prefix at the deployed location.

Plan for old and invalid addresses

Old and invalid addresses deserve deliberate behavior as well. An old URL with a known replacement can redirect to its current location. A malformed parameter can fail validation before application code treats it as a valid identifier. A well-formed identifier for a missing issue can reach the issue route and produce a not-found result. These cases exercise different parts of the routing design even when users experience each one as a failed attempt to reach a page.

Public URLs can outlive the implementation which first introduced them. Components may move and route modules may be reorganized while existing links continue to circulate in bookmarks, documentation, messages, and external systems. Changing an established address therefore requires a migration plan when old links still need to work. Redirects provide a way to move those links toward the current address without requiring every stored copy to change at once.

A routing review checklist

A review can summarize the design by asking a small set of questions after the route has been traced in detail.

  1. Does each public URL identify a view which can be reloaded, bookmarked, and shared without hidden client state?
  2. Do path and query values have explicit parsing, validation, defaults, and authorization?
  3. Do direct visits and client navigations reach equivalent content while preserving the correct HTTP status?
  4. Is data loaded at the route level where it is needed, and do writes refresh any data they make stale?
  5. Can pending and failed route work be shown in the appropriate part of the interface?
  6. Do push, replace, Back, Forward, scroll restoration, title updates, and focus behavior match the navigation users experience?
  7. Do the router base path, generated links, server rules, and redirects agree in the deployed environment?

A routing architecture is in good shape when each public URL has a predictable meaning however the user reaches it. The route branch determines how the application interprets the address and which work belongs to the destination. Reads and writes connect the route to server data, while browser history records the navigation steps users can return to. Frameworks provide different ways to implement these responsibilities, but the design begins with the URLs users need to reach.
