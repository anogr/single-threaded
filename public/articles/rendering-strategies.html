Rendering Strategies

How navigation, HTML generation, hydration, and speculative loading combine into a rendering architecture.

Andreas Ögren
~19 min read
Last updated July 2026

Traditional web navigation loads a separate HTML document for each page. Following a link requests the destination and replaces the current document with the response. Single-page apps introduced a second model in which JavaScript owns routing and updates the existing document. Frameworks can now combine these behaviors, even within one application.

The HTML itself may be generated during a build, refreshed in the background, rendered for each request, or created in the browser. These choices solve different problems, so a product rarely needs one answer everywhere. A public landing page and an account dashboard can belong to the same application while using very different rendering paths.

Rendering architecture becomes easier to reason about when it is separated into four questions. Navigation determines whether a link loads a document or updates the current one. Timing covers when HTML is produced and how long it can be reused. Hydration determines how existing HTML becomes interactive. Speculation concerns work the browser may perform before a likely navigation.

Multi-page apps (MPAs) and single-page apps (SPAs) describe navigation. Static site generation (SSG), incremental static regeneration (ISR), partial prerendering (PPR), and server-side rendering (SSR) describe when HTML is produced. Hydration, islands, and resumability describe client activation. The Speculation Rules API can accelerate navigation without changing the choices on those other axes.

Options on different axes combine freely. A route can use server rendering for its initial response, client-side routing for later navigation, and islands for selected interactive regions. Labels on the same axis need more care because frameworks can blend them. PPR, for example, combines a prerendered shell with request-time regions rather than occupying one simple point between static and dynamic rendering.

Out of scope: WebAssembly

WebAssembly can support compute-heavy browser work such as media processing or machine-learning inference. It does not determine who owns navigation, when HTML is produced, or how that HTML becomes interactive, so it sits outside this comparison.

Multi-Page Apps

A full document load remains useful when pages do not need to preserve in-memory state across navigation.

In a multi-page app (MPA), each navigation loads a new document. The browser requests a URL, receives HTML, and replaces the previous document. A client-side router does not need to preserve the old component tree or its in-memory application state.

A document replacement interrupts continuity that client-side routing can preserve. Persistent interface elements render again, and state held only in JavaScript disappears. Applications built around continuous playback, ongoing gestures, or long-lived workspaces may therefore benefit from keeping one document alive.

Cross-document view transitions can soften that visual break in supporting browsers. Same-origin pages opt in with the @view-transition rule. The browser supplies a default cross-fade, while matching view-transition-name values can animate selected elements between documents. Support is not universal, so the transition should remain a progressive enhancement.

During the transition, the browser captures images of the old and new states and animates their corresponding pseudo-elements. The documents still load through normal navigation. The API changes the presentation of the handoff rather than its underlying lifecycle.

A view transition does not preserve JavaScript memory. Durable state must come from the next response, the URL, browser storage, or another persistent source. That clean lifecycle suits content-led sites whose pages stand on their own and need little client-side coordination.

MPA describes navigation, not the source of the HTML. Each document may come from a static file, a regenerated cache entry, or a request-time render. Its interactive regions can ship no JavaScript, hydrate as one application, or activate as separate islands.

Single-Page Apps

One document gives the browser control of routing and rendering after the application starts.

A single-page app (SPA) keeps one document alive and lets JavaScript handle navigation. A purely client-rendered SPA may initially send little more than a mounting element and script references. The browser must then download and execute the application before it can render the route's main content. Later navigations update the interface and URL without loading another document.

The shell can have a low time to first byte (TTFB) without containing useful content. Its scripts still travel over the network and consume processing time on the visitor's device. The effect of this JavaScript bundle cost on Largest Contentful Paint (LCP) depends on the bundle, network, device, data dependencies, and loading strategy. The SPA label alone does not predict the result.

An empty shell also gives non-executing clients little content to inspect, including some link-preview services and specialized crawlers. Search engines vary in how they process JavaScript, so server-produced metadata and content remain the safer choice when discovery matters. A client-rendered SPA can still suit long-lived, authenticated tools where users accept an application startup cost and then move through many screens without document reloads.

Framework applications often mix navigation modes

Many framework applications sit between the two ends of this axis. A direct visit receives server-produced HTML, while later link clicks use client-side routing. The initial rendering method and the navigation model are separate decisions, even when a framework presents them as one application mode.

Static Site Generation

Build-time rendering moves work out of the request path and produces files that caches can serve directly.

Static site generation (SSG) renders HTML before requests arrive, usually during a build. The resulting files can be deployed to static hosting and cached by a content delivery network (CDN). A cache hit avoids application rendering and data access on the request path.

A cache hit needs no application rendering, which makes the request path predictable and inexpensive. Builds, storage, cache fills, and bandwidth still carry costs, while a miss may reach the origin. Static output nevertheless gives shared public content a comparatively simple delivery path.

Static output works best when many visitors can share the same representation. Articles, documentation, and marketing pages often fit that condition. Personalized or rapidly changing regions need another path, such as client-side data fetching, request-time rendering, or a hybrid that leaves only those regions dynamic.

Server-Side Rendering

Request-time rendering can use fresh data and visitor context, but it puts application work back on the response path.

Server-side rendering (SSR) generates HTML while handling a request. The renderer can use cookies, headers, and data fetched for that response. Personalization and request-level freshness can therefore appear in the initial HTML instead of waiting for client-side rendering.

With blocking SSR, TTFB includes the work that must finish before the server can send the response. Sequential data calls, a slow database, or saturated compute can therefore delay the whole page. Caching and parallel data access may reduce that delay, but they do not remove the request-time dependency.

Streaming SSR lets the server flush completed regions before the entire render has finished. A slow region sits behind a boundary whose fallback can appear in the initial HTML. When its data resolves, the server sends the remaining markup over the open response. A product page might show its description and price while reviews continue rendering, so one dependency no longer delays every visible region.

What "streaming" means on the wire

A server can begin a response before it knows the final body length. HTTP/1.1 can delimit such a body with chunked transfer encoding, while HTTP/2 and HTTP/3 use their own framing. Browsers parse HTML as bytes arrive. Frameworks add render boundaries and instructions that place later markup into the same response.

SSR may run in a regional origin or on a distributed edge runtime. An edge location can shorten the network path to the renderer, although the benefit depends on where its data lives and what the runtime supports. Edge-side rendering is therefore a deployment choice within SSR, not a separate rendering mechanism.

Incremental Static Regeneration

A cached page can be refreshed without making every request wait for a new render.

Incremental static regeneration (ISR) reuses generated output while allowing it to be replaced after deployment. A framework may consider an entry stale after a configured interval or invalidate it in response to an application event. Either trigger can refresh one page or a related set of cached results without rebuilding the entire site.

Many ISR implementations use stale-while-revalidate behavior. A request can receive the stale entry while regeneration runs in the background, and a later request receives the replacement. Exact semantics differ by framework and hosting platform, particularly after failures or concurrent requests, so ISR is best understood as a family of regeneration policies rather than one universal cache algorithm.

Regenerating the origin isn't the same as refreshing the edge

Replacing an origin entry does not guarantee that every cache immediately serves the new version. Purge behavior and propagation depend on the platform, so freshness must be considered across each caching layer.

On-demand invalidation ties freshness to a content event instead of a timer. A publishing webhook can invalidate tagged entries as soon as content changes, while unrelated pages remain cached.

Partial Prerendering

A prerendered shell can arrive first while request-dependent regions finish separately.

Partial prerendering (PPR) combines a prerendered shell with regions deferred to request time. The cacheable shell contains fallbacks for those regions. Dynamic regions render behind their own boundaries and stream into the response as they complete. Shared page structure can therefore avoid request-time rendering while personalized content still arrives as HTML.

A cached shell lets the server begin the response without waiting for dynamic regions, which can reduce TTFB compared with a blocking render of the same page. The deferred regions still carry their own data and rendering latency, so the complete page arrives later.

Useful dynamic regions include a session-aware cart, recommendations, or an experiment variant. Their presence no longer forces the shared shell onto the same request-time path. The visitor can see stable page structure first, followed by content whose value depends on the request.

PPR exposes a limitation in the simple timing axis: one response can contain output produced at different times. Its boundaries describe when markup becomes available. Islands answer a later question about which regions need client-side JavaScript. A request-time region may remain non-interactive, while a component already present in the shell may hydrate as an island.

Hydration, Islands, and Resumability

Once HTML reaches the browser, a separate choice determines how much JavaScript is needed to make it interactive.

Navigation and HTML generation do not determine how interactivity starts. A statically generated page and a server-rendered page can use the same hydration model. Conversely, two regions in one PPR response may use different amounts of client-side JavaScript.

Server-produced HTML can display controls before their application logic is active. Hydration connects that existing DOM to client-side component state and event handling. In frameworks such as React, the client evaluates a corresponding component tree and reconciles it with the server output instead of intentionally replacing all of the markup. A well-matched render becomes interactive without a visible rebuild.

Monolithic hydration treats the application as one hydration root. A large root can delay interaction while its code and dependencies become available. Progressive hydration changes the schedule by activating selected regions first and deferring others until visibility, idle time, or interaction. Deferral may postpone some downloads when paired with code splitting, but it does not guarantee less JavaScript overall.

Islands architecture, a term coined by Katie Sylor-Miller and popularized more widely by Jason Miller in 2020, is where the payload actually shrinks. A page is treated as mostly static HTML with small, independent islands of interactivity dropped in, and each island hydrates on its own rather than as part of one shared tree. Astro is the framework most associated with this pattern. It ships a page as plain HTML by default, and a component only gets a JavaScript bundle if it's explicitly marked as interactive. A product image carousel might hydrate immediately, while a comment form further down the page might not hydrate until it scrolls into view. Neither one waits on the other, and neither one requires the rest of the page to ship any JavaScript at all.

Qwik addresses startup work through resumability. The server serializes application state and references that let the client continue from the rendered result. Qwik can then load code for an interaction when it is needed instead of eagerly re-executing the component tree to reconstruct listener placement. Some client initialization may still be necessary for code or state that cannot be serialized, so resumability reduces the default startup path rather than abolishing all client work.

Hydration mismatches

Hydration relies on compatible server and client output. Values derived from a timezone, Math.random(), or a browser-only API can produce a mismatch when evaluated in both environments. Framework responses differ: they may warn, patch text or attributes, or replace an affected subtree. The durable fix is to keep the initial render deterministic or move browser-dependent output to a later client phase.

Islands and resumability both try to avoid paying client startup costs for static content, but their boundaries differ. An Astro island is an independent client root, so framework context does not automatically cross between separate islands. A React 'use client' boundary marks modules that enter the client graph within one React application. Client components can share context beneath a common client provider, and server-rendered elements can be passed through client components as children.

Speculation Rules API

The browser can prepare likely destinations without changing how those pages are rendered.

The Speculation Rules API lets a document identify likely future navigations. A supporting browser may prefetch a destination's resources or prerender the page in a hidden context before the visitor opens it. If the prediction is correct, activation can be much faster than starting the navigation from nothing.

Rules appear as JSON in a <script type="speculationrules"> element. They can list URLs or select links from the document, then assign an eagerness level. conservative waits for a strong interaction signal. moderate and eager allow earlier heuristics, while immediate starts speculation as soon as possible.

The browser may decline or limit speculation according to its own policies and resource constraints. Prefetching retrieves resources without rendering the destination. Prerendering goes further by loading the document in a hidden browsing context, where its scripts may execute before activation. Pages must therefore treat prerendering as real execution and avoid premature side effects.

Browser support remains uneven, which makes speculation a progressive enhancement. The destination must behave correctly when no speculative work occurs, and the rule should avoid wasting bandwidth or running sensitive actions for navigations that never happen.

Framework Support

Frameworks expose similar building blocks, but their defaults and deployment-dependent features differ.

Next.js App Router supports prerendering, request-time rendering, streaming, and cache revalidation. In Next.js 16, the opt-in Cache Components model unifies earlier PPR and caching flags. With cacheComponents enabled, cacheable work is marked with 'use cache', while uncached request-time regions sit behind Suspense boundaries and stream into a prerendered shell. React Server Components keep selected component code off the client, and 'use client' defines the client module boundary. That boundary is not an islands architecture because the client components still belong to a shared React tree.

A recent name change

Current Next.js documentation presents Partial Prerendering as the behavior produced by Cache Components. Older experimental PPR configuration was removed in Next.js 16, so examples using experimental_ppr describe the previous interface.

Nuxt applies prerendering, server rendering, client rendering, and caching to route patterns through routeRules. Its swr and platform-specific isr rules differ in where regenerated output is stored. SvelteKit exposes page-level prerender, ssr, and csr options. Regeneration beyond HTTP caching depends on the deployment adapter or host. SolidStart supports prerendering and streaming SSR, while Solid hydrates existing DOM through its fine-grained runtime.

Astro renders static output by default and ships no client JavaScript for a framework component unless a client:* directive opts it into hydration. An adapter can add on-demand rendering, and server islands let selected server-rendered components load independently of the surrounding page. These server islands concern request-time HTML, while client islands concern browser interactivity.

Qwik and Qwik City use resumability as their application model. Serialized state and lazy code references reduce the JavaScript needed during startup, while code is fetched as interactions and rendering require it. The actual payload depends on the application and any eager client work it introduces.

React Router framework mode supports server rendering and streaming. Its build configuration can prerender selected URLs, including routes discovered by a prerender function. A single deployment can therefore serve generated HTML for some URLs and render others per request.

Angular supports per-route client rendering, SSR, and prerendering through its server route configuration. Hydration reuses server-rendered DOM, while incremental hydration can leave @defer regions inactive until configured triggers fire. Angular's built-in rendering modes do not provide an ISR-style background regeneration policy. Hosting or cache infrastructure would need to supply that behavior.

Mixing Strategies by Default

Routes and regions can use different strategies while remaining part of one application.

A marketing route might be pure SSG, a product listing might use ISR to stay roughly fresh, and a checkout flow might be SSR end to end because every byte of it has to reflect the current session. That's ordinary route-by-route variation within a single axis, no different in kind from picking different page layouts per route.

Separately, and this is the more important point, any single route can combine its own timing-axis answer with its own navigation-axis and hydration-axis answers, because those are different questions with independent answers. A checkout route can be SSR on the timing axis, sit inside an app whose navigation is client-routed after the first load, and hydrate only its payment form as an island rather than the whole page, and none of those three decisions constrains either of the other two.

A documentation site built with Astro often combines document navigation, static generation, and a few client islands. A dashboard might begin with SSR, switch to client routing, and hydrate one application root. A commerce page can combine a cached shell, streamed request-time regions, and selected interactive boundaries. Each architecture follows from the route's content and interaction needs rather than a framework-wide label.

Per-route and per-region choices now appear across framework ecosystems. The framework still matters because its cache semantics, deployment adapters, and boundary model determine which combinations are practical.

Choosing a Strategy

Cost, freshness, and personalization pull in different directions, and the right answer is usually route-specific, not site-wide.

Rendering labels do not predict a performance ranking

A cached static response usually removes application compute from TTFB, but interactivity may still wait for JavaScript. Streaming SSR can reveal useful content before a slow region finishes. A small client-rendered tool can outperform a poorly cached server-rendered page. Compare architectures with measurements from the routes, devices, and networks that matter.

Cost follows the work performed at each stage. Static output moves compute to builds and leaves storage, cache traffic, and bandwidth on the request path. Regeneration adds rendering and invalidation work when cached entries refresh. Uncached SSR consumes compute with request volume, although response caching can change that shape. A client-rendered SPA is inexpensive to serve as static files, but its JavaScript still consumes network and processing resources on each visitor's device.

Begin with the content boundary. Shared content that changes with a release is a strong candidate for SSG. Content with an independent publishing lifecycle may benefit from regeneration or HTTP caching. Visitor-specific content needs request context somewhere, although only the affected region must be dynamic.

Choose navigation and hydration from the interaction requirements. Long-lived workspaces benefit more from client routing than self-contained content pages do. A few isolated controls rarely justify hydrating an entire document.

Where this connects

Core Web Vitals include LCP, Interaction to Next Paint (INP), and Cumulative Layout Shift (CLS). Rendering choices influence those metrics, but they do not determine them without the page's code, data, network, and device context. Service workers form another independent layer for caching, offline behavior, and request handling. Client routing, streaming updates, and deferred hydration also introduce accessibility responsibilities covered in Accessibility and Rendering Architecture.
