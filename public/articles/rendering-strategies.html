Rendering Strategies: Where and When HTML Gets Built

How SPA, MPA, SSR, SSG, ISR, and PPR differ in where HTML gets built and when JavaScript takes over, and how to pick the one that fits.

Deep dive
~25 min read
Rendering architecture
July 2026

Ask a few frontend engineers when a page's HTML actually gets built and the answers start to disagree, because for a long stretch of the 2010s the question had one obvious answer: the browser builds it, after JavaScript runs. That's no longer true for most production sites, and the reasons it stopped being true are what this article is about.

A page's HTML can be built once at deploy time and served unchanged for months. It can be built fresh on every request. It can be built once and quietly rebuilt in the background while stale copies keep serving traffic. Or it can be built almost entirely in the browser, starting from an empty shell that JavaScript fills in after the page has already loaded. None of these ideas are new on their own. What changed is how many of them a single product now uses at once, often on different routes of the same app.

This article treats rendering as one axis: when HTML gets produced, and when the JavaScript that makes a page interactive takes over. Six points along that axis get their own section (multi-page apps, single-page apps, static generation, server rendering, incremental static regeneration, and partial prerendering), followed by two ideas that cut across all of them rather than adding a seventh point: islands architecture and the browser's own speculative prefetching.

Out of scope: WebAssembly

WebAssembly speeds up specific, compute-heavy code paths in the browser: image and video processing, in-browser machine learning inference, codec work. It doesn't change when or where HTML itself gets produced, which is the axis this article is actually about, so it's left out of the comparison entirely.

MPA: The Full Reload, Reconsidered

The oldest rendering strategy on this list just got a reason to look modern again.

A multi-page app does exactly what the phrase says. Every navigation is a full page load: the browser requests a URL, the server renders that page's complete HTML, and the browser throws away the previous page's DOM and starts over. There's no client-side router, no persistent JavaScript application state, no virtual DOM diffing against a previous render. Each page is its own self-contained document.

For most of the 2010s, this reload was the reason teams reached for a single-page app instead. A full navigation meant a blank white flash between pages, no way to keep a header or sidebar mounted across routes, and no smooth transition between one screen and the next. Avoiding that flash was, for a lot of products, the actual justification for shipping a large client-side JavaScript framework, rather than a specific technical need for one.

That justification has weakened considerably. Cross-document View Transitions, a browser-native API that animates the swap between two full page loads, reached roughly 92% combined global browser coverage as of May 2026, with Chrome and Edge supporting it since mid-2024, Safari since late 2024, and Firefox closing the gap in December 2025. Turning it on takes two declarative pieces and no JavaScript animation library at all: a site-wide rule that opts every cross-document navigation into a transition, and, optionally, a shared view-transition-name on one element, a product image, a page title, so the browser morphs that element between pages instead of just cross-fading everything at once.

The browser captures a snapshot of the outgoing page, waits for the new page's HTML, and cross-fades or slides between them, all coordinated by the browser's own compositor rather than JavaScript juggling DOM nodes mid-transition.

None of this makes an MPA behave like an SPA. State still resets on every navigation, so anything that needs to persist, a shopping cart drawer, an audio player, an open modal, has to be re-derived from the server response or from storage rather than kept in memory. But the specific complaint that drove teams toward client-side routing, the visual jank of a reload, no longer has to be one of the tradeoffs. An MPA today gets a smooth transition from a few lines of CSS, which makes it a genuinely reasonable default for content-first sites: marketing pages, blogs, documentation, catalogs, anything where each page is mostly self-contained and doesn't need to survive a navigation in memory.

SPA: Client-Rendered, Client-Owned

A single-page app trades a slow first paint for a fast every-paint-after-that.

A single-page app ships one HTML document, almost empty, and lets JavaScript take over from there. The initial response is a shell: a <div id="root"> and a set of <script> tags. The browser has to download that JavaScript, parse it, execute it, and only then does the application render anything a visitor can actually see. Every subsequent navigation happens client-side, swapping components and updating the URL through the History API, without another full page load.

The real cost of this approach isn't any single number, it's two separate costs stacked on top of each other. The first is time to first byte for a blank shell, which is fast (there's nothing to render server-side), but that speed is deceptive, because the shell isn't the content. The second, larger cost is the JavaScript bundle tax: the total size of the framework, the application code, and every dependency that has to download, parse, and execute before the page becomes interactive. Published comparisons put largest contentful paint around 1.1 to 1.8 seconds for SSR or SSG pages against roughly 2.8 to 3.5 seconds for a CSR-only SPA rendering equivalent content, and that gap is almost entirely the bundle tax, not server speed.

That gap is the reason "SPA for the whole product" stopped being the default today for anything public-facing or SEO-dependent. A search crawler or a social-media unfurler that doesn't execute the client bundle sees an empty shell, and a visitor on a slow connection or an older device pays the parse-and-execute cost in full before anything appears. None of that makes the pattern wrong, it makes it situational. Behind an authentication wall, where there's no crawler to satisfy and the visitor has already committed to loading the tool, a pure SPA is often still the right call: internal dashboards, admin panels, and data-heavy tools where the first paint happens once per session and every screen after that benefits from never touching the network for a full document reload.

SSG: Built Once, Served Forever

If the content doesn't change per visitor, there's no reason to compute it per visit.

Static site generation renders every page's HTML at build time, before any visitor ever requests it, and uploads the finished files to a CDN. When a request comes in, the edge node closest to the visitor just returns a file it already has. There's no server-side rendering step at request time, no database query, no template execution, just a static asset being served the same way an image would be.

This is the cheapest rendering strategy to run, by a wide margin. The cost shape is storage and bandwidth only: no compute happens per request, so traffic spikes don't translate into server load the way they would for a strategy that renders on demand. It's also the fastest strategy in the ordinary sense, since serving a pre-built file from a nearby edge node is about as fast as HTTP gets.

The tradeoff is that SSG only fits content that's the same for every visitor, or close to it. A blog post, a documentation page, a product marketing page: all of these render once and stay correct until the next deploy. Anything that needs to reflect a specific visitor, a personalized recommendation, a logged-in user's name in the header, live inventory counts, doesn't fit the model without falling back to client-side fetching layered on top of the static shell. That's exactly the seam that incremental static regeneration and partial prerendering exist to smooth over, both covered further down.

SSR: Rendered Per Request

Server rendering buys freshness and personalization, and pays for it in time-to-first-byte.

Server-side rendering runs the same rendering work SSG does at build time, but on every incoming request instead. The server, or an edge function, more on that in a moment, executes the page's rendering logic, fetches whatever data the page needs, and returns fully formed HTML. Because it runs per request, SSR can read the actual visitor's session, personalize content, and reflect data that changed a second ago, none of which a purely static build can do.

The cost is that time-to-first-byte is now tied directly to how long the server takes to fetch data and render, and if a page waits on three sequential API calls before it can produce any HTML, the visitor waits on all three before seeing anything. Traditional, blocking SSR sends nothing until the entire page is ready, which turns a single slow dependency into a slow page.

Streaming SSR fixes that specific failure mode of "wait for everything, then send everything." The server marks which regions of the page are allowed to render independently of the rest. A data dependency that resolves quickly is awaited normally and included in the first flush of HTML. A slower one gets its own boundary with a placeholder, so the server can send the fast parts of the page the moment they're ready and keep the connection open for the slow part rather than buffering the entire response until every dependency has settled. A product page can send its header, price, and description within that first flush, while a slower reviews section streams in a beat later inside its own boundary and patches into place once it arrives, without a second round trip and without blocking anything else on the page.

What "streaming" actually means on the wire

A normal HTTP response declares its size upfront in a Content-Length header, which forces the server to know the whole body before it writes the first byte. Streaming responses use chunked transfer encoding instead, sending the body as a sequence of chunks over the same open connection without ever committing to a total size. The browser's HTML parser has always been able to consume a document incrementally as bytes arrive rather than waiting for the end of the stream, which is why even old-fashioned, non-streaming SSR pages painted progressively long before any framework offered a streaming API. What a streaming boundary adds on top of that is control over ordering: the placeholder markup goes out in the first chunk, and once the slow data resolves, the server writes the real markup into a later chunk on that same connection, alongside a small inline script that swaps it into the placeholder's position and removes the placeholder. Nothing about this needs a second request, because the connection never closed.

One more variable belongs in this section rather than getting its own heading: where SSR actually executes. Running it on an edge runtime, Cloudflare Workers or Vercel Edge Functions, instead of an origin Node server trades some compute headroom for near-instant cold starts and lower network latency, since the code runs physically closer to the visitor. This is what "edge-side rendering" means in practice: it's still SSR, just relocated. It's not a different rendering strategy, it's a deployment decision about where the SSR strategy runs.

ISR: Static, With a Background Refresh

Incremental static regeneration keeps SSG's speed and adds a way to keep the content from going stale.

Incremental static regeneration starts from the same place as SSG, a page built once and cached, but adds a mechanism for regenerating that cache without a full redeploy. A page can be marked to revalidate after a fixed window (regenerate this page in the background if it's more than sixty seconds old) or on demand, by tagging a specific piece of content so a single API call can invalidate exactly the pages that depend on it, without waiting for a timer or rebuilding anything unrelated.

The behavior underneath both approaches is stale-while-revalidate: the visitor who happens to trigger a regeneration still gets the old, cached page instantly, while the new version renders in the background and replaces the cache for the next visitor. Nobody waits on a rebuild. This is the detail that makes ISR feel like SSG in terms of speed while behaving more like SSR in terms of freshness, without fully paying either strategy's cost.

Regenerating the origin isn't the same as refreshing the edge

Revalidating the origin cache doesn't automatically mean every visitor sees fresh content immediately. The CDN's edge caches have to actually receive and honor the purge, and if that propagation is slow or misconfigured, a regenerated page can sit correctly rebuilt at the origin while edge nodes keep serving the old copy a while longer.

SSG, ISR, and SSR are really the same rendering operation with different caching rules attached, which is why most metaframeworks expose all three through one setting rather than three separate systems: fetch once and cache indefinitely (SSG), fetch and cache with a revalidation window measured in seconds (ISR), or skip the cache entirely and fetch on every request (SSR). On-demand invalidation is a fourth option layered on top of the same knob, tagging a specific piece of content so one call from a webhook can invalidate exactly the pages that depend on it, without waiting for the timer to expire.

PPR: Static Shell, Dynamic Holes

Partial prerendering treats a page as two different rendering strategies stitched into one response.

Partial prerendering serves a page's static shell from the edge, the same way SSG would, and leaves gaps, holes, for the parts of the page that genuinely need to be computed per request. Those holes stream in after the shell has already reached the browser, each one resolving independently inside its own boundary, similar to how streaming SSR resolves slow sections without blocking the rest of the page. The difference is that with PPR, most of the page never needed a server render at request time in the first place, only the holes do.

That distinction shows up directly in time-to-first-byte. When the static shell serves from an edge cache, PPR moves TTFB from something in the 350 to 550 millisecond range, typical for a fully dynamic SSR response, down to roughly 40 to 90 milliseconds, because the browser is receiving a cached file rather than waiting on a server to render anything before the first byte goes out.

The holes themselves are ordinary dynamic content: a personalized recommendation strip, a cart icon reflecting the visitor's actual session, an A/B test variant. What PPR changes is that none of that dynamic content forces the rest of the page to wait. A visitor's browser paints the static shell almost immediately, then fills in the personalized pieces a moment later, a meaningfully different experience from either a fully static page (fast, but can't personalize) or a fully dynamic SSR page (can personalize, but the whole response waits on it).

Hydration, Islands, and Resumability: A Different Axis

Everything above is about when HTML gets built. This section is about how much JavaScript ships once it does, and how a static-looking page becomes interactive at all.

Every strategy covered so far answers the same question: when does rendering happen. Hydration, islands, and resumability answer a different one: how much of the page needs JavaScript at all, and at what granularity. It's worth treating as a separate axis rather than a seventh point on the same timeline, because a page can combine, say, SSG with islands, or PPR with islands. The two ideas aren't mutually exclusive.

Start with hydration itself, since the other three ideas in this section are all reactions to it. Any page whose HTML was produced ahead of time, by SSG, SSR, or ISR, arrives in the browser already looking correct, but that HTML is inert: none of its buttons respond to a click yet, because no JavaScript has run. Hydration is the step that fixes this. The browser downloads the same component code the server used, runs it again against the DOM that's already sitting on the page, and uses that second pass to attach event listeners and wire up internal state, rather than throwing the existing markup away and rebuilding it from scratch. Done correctly, hydration is invisible: the visitor never sees a flash of rebuilt content, only a page that goes from static to responsive.

The default version of this, sometimes called monolithic hydration, treats the whole page as one unit. The browser can't attach a single event listener until it has downloaded, parsed, and re-executed the entire component tree, even for the ninety percent of the page that has nothing to do with the one button a visitor is about to click. Progressive hydration narrows that cost without removing it: the framework still ships and eventually runs the same component tree, but it prioritizes the order, hydrating whatever's visible in the viewport first and deferring the rest until it's needed or until the browser is idle. It reduces how long a visitor waits for the important part to become interactive, but the total JavaScript payload doesn't shrink.

Islands architecture, a term coined by Katie Sylor-Miller and popularized more widely by Jason Miller in 2020, is where the payload actually shrinks. A page is treated as mostly static HTML with small, independent pockets of interactivity dropped in, and each pocket hydrates on its own rather than as part of one shared tree. Astro is the framework most associated with this pattern: a page ships as plain HTML by default, and a component only gets a JavaScript bundle if it's explicitly marked as interactive. A product image carousel might hydrate immediately, while a comment form further down the page might not hydrate until it scrolls into view. Neither one waits on the other, and neither one requires the rest of the page to ship any JavaScript at all. Astro's server islands, added in late 2024 and carried forward through Astro 6 in 2026 via the server:defer directive, extend the same idea to server-rendered content: a slow, personalized fragment can render on the server independently of the static parts around it, without holding up the page.

Qwik takes a more radical approach to the same underlying problem, one that skips hydration entirely rather than shrinking its footprint. Instead of shipping a component tree for the browser to re-execute, Qwik serializes the listener references themselves into the HTML at build time. The browser never re-runs any component logic to become interactive. It resumes from exactly where the server left off, downloading the handler code for a specific interaction only when that interaction actually happens. This is why the pattern is called resumability rather than hydration: there's no re-execution step to skip past, because nothing needs to be reconstructed in the first place.

Hydration mismatches

Hydration assumes the HTML the browser downloaded matches what the component tree would produce if it rendered again right now. When it doesn't, because a value depends on the visitor's timezone, on Math.random(), or on browser-only APIs that weren't available during the server render, the framework detects the mismatch and either patches the DOM or, in stricter setups, throws a warning and re-renders the affected subtree from scratch. It's a common source of console warnings in server-rendered React and Vue apps, and the fix is almost always to make the mismatched value deterministic or to defer it until after hydration completes.

Islands and resumability both converge on the same result: near-zero JavaScript shipped by default, with more added only for the specific pieces of a page that need it. It's worth naming one callback explicitly, because it recurs elsewhere in this series: a 'use client' component inside a server-rendered React tree is structurally the same shape as an Astro client island, a small, independently hydrated pocket of interactivity inside an otherwise static or server-rendered page.

Speculation Rules API: The Browser Prefetches for You

None of the strategies above account for the browser guessing where a visitor is headed next.

Every rendering strategy on this list still has to serve the current navigation. The Speculation Rules API sits on top of all of them and handles a different problem: prefetching or fully prerendering a page the browser predicts a visitor is about to navigate to, before they click anything.

A page declares its intent with a small, declarative block inside a <script type="speculationrules"> tag rather than any JavaScript: a URL pattern to match, and an eagerness level ranging from conservative (prerender only on a strong signal, like a pointer press) to eager (prerender as soon as a matching link scrolls into view).

The browser decides whether to actually honor that hint based on conditions no application code has visibility into: available memory, network type and speed, and current CPU load. On a resource-constrained device or a slow connection, the browser can simply decline to prerender, and the app never knows or needs to know. Nothing in the application runs speculatively, the meaningful difference from a JavaScript-driven prefetch library: this is a browser-native decision, not a heuristic the application team has to tune and maintain.

The caveat is worth stating plainly rather than glossing over: as of today, Speculation Rules support is Chromium-only, Chrome, Edge, and Opera, with no shipped support in Firefox or Safari. That makes it a progressive enhancement layered on top of whichever rendering strategy a page already uses, not something to design an architecture around. A site should work identically with the feature entirely absent, because for a meaningful share of visitors, it will be.

Where the Popular Frameworks Land

None of the strategies above are theoretical. Here's what today's frameworks actually ship, and where they differ from each other.

Next.js's App Router covers most of the ground in this article inside one framework. Static pages render at build time for SSG, a revalidate window plus tag-based invalidation covers both timed and on-demand ISR, and streaming SSR is the default for anything dynamic. Partial prerendering, introduced experimentally in 2023, was folded into what Next.js 16 calls Cache Components in late 2025: a page opts in with a "use cache" directive rather than a separate feature flag, but the underlying idea, a static shell with dynamic holes, is the same one covered earlier in this article. React Server Components give the framework its island-like boundary too, since a component stays server-only unless it's explicitly marked with 'use client'.

A name change worth knowing

Readers researching PPR today will often land on Next.js documentation that talks about Cache Components instead. It's the same static-shell-plus-dynamic-holes model this article describes under PPR, repackaged under a broader caching API rather than deprecated.

Nuxt, SvelteKit, and SolidStart all take the same structural approach: pick a rendering mode per route rather than committing an entire app to one strategy. Nuxt's routeRules config is the most explicit about it, with dedicated settings for prerendering, server rendering, and a built-in stale-while-revalidate cache that behaves like ISR without any extra setup. SvelteKit exposes the same per-route choice through page-level prerender and ssr options, though ISR-style background regeneration there comes from the deployment adapter rather than the framework itself, Vercel's SvelteKit adapter is the common way to get it. SolidStart, built on the same underlying server engine as Nuxt, offers the same spread of SSR, streaming, and prerendering, and Solid's fine-grained, signal-based reactivity means hydration attaches listeners directly to existing DOM nodes rather than re-running a full render pass, which lowers the cost of hydration without removing it as a step.

Astro remains the clearest expression of islands architecture: static by default, with on-demand rendering and server islands available once an adapter is added for a specific host. A team can run an entire Astro site as SSG, flip individual routes to server rendering, or leave most of a page static while a handful of components hydrate independently, all in the same project.

Qwik and Qwik City build resumability in as the default rather than an opt-in, so every page effectively serves near-zero JavaScript until a visitor actually interacts with something. The tradeoff is ecosystem size: Qwik's adoption remains modest next to the frameworks around it, worth weighing alongside the technical benefit before committing a large team to it.

React Router v7, the result of Remix merging into React Router in late 2024, defaults to server rendering with streaming built in, but a route can also be pre-rendered at build time through a prerender config function that returns the list of URLs to generate, covering the SSG case for routes that don't need per-request data. Mixing rendered-per-request routes with pre-rendered ones inside the same app is a normal pattern here, not an exception.

Angular's story is SSR and SSG rather than ISR. Non-destructive hydration, stable since Angular 17, means the framework reuses server-rendered DOM instead of discarding and rebuilding it, and incremental hydration, added in Angular 19, extends that to hydrate parts of a page on demand rather than the whole tree at once, the same progressive-hydration idea covered earlier in this article. What Angular doesn't have today is a native background-regeneration mechanism equivalent to ISR: static routes are rebuilt at deploy time, not revalidated on a timer.

Mixing Strategies by Default

Almost no serious product today picks one rendering strategy for the whole site.

The strategies above read like a menu of mutually exclusive choices, but most production apps today mix several of them across different routes, and increasingly across different components on the same route. A marketing homepage might be pure SSG. A product listing page might use ISR, regenerating every few minutes as inventory changes. A checkout flow might be SSR end to end, because every byte of it needs to reflect the current session. And within any one of those routes, specific widgets might hydrate as independent islands rather than as one large client-rendered tree.

A concrete version of this: a route rendered with PPR for its shell, with a handful of genuinely interactive pieces inside that shell, a quantity selector, a "save for later" button, a live chat widget, hydrated independently, island-style, rather than shipped as part of one monolithic client bundle that has to hydrate all at once before any of it responds to a click. The shell handles when the HTML arrives. The islands handle how much JavaScript any given piece of it needs.

This isn't unique to the React ecosystem, either. As the framework rundown above shows, per-route mixing is closer to the default assumption across the field than a Next.js-specific trick.

Choosing a Strategy

Cost, freshness, and personalization pull in different directions, and the right answer is usually route-specific, not site-wide.

Cost is easy to leave out of a purely technical comparison, but it belongs in the decision, because the strategies scale differently under load. SSG costs close to nothing beyond storage and bandwidth, since there's no compute per request. ISR's cost scales with how often content actually regenerates, not with traffic, a page that revalidates every hour costs the same whether it gets ten visitors or ten million. SSR, and edge-SSR alongside it, scale with request volume directly, because every request triggers real compute. An SPA is the cheapest strategy to host, in the narrow sense that a static JS bundle on a CDN costs about the same as any other static file, but that's because the strategy pushes its real cost onto the visitor's device, in the form of JavaScript parse and execute time that never shows up on a hosting bill.

None of this reduces to a single rule, but a few questions narrow it quickly. Does the page need to reflect a specific visitor at request time, or is the same content correct for everyone? That's the line between SSG or ISR and SSR. Does the content change often enough that a background regeneration window matters, or is a full rebuild on deploy good enough? That's SSG versus ISR. Is the page public-facing, where a slow first paint or an empty shell for crawlers is a real cost, or is it behind an authentication wall where a visitor has already committed to loading the tool? That's usually where an SPA remains defensible today, and where it doesn't.

Where this connects

Core Web Vitals today track INP, which replaced FID as the responsiveness metric, alongside CLS and LCP, and every strategy above moves those numbers differently. The mechanics of each metric belong to a dedicated Core Web Vitals article rather than here. Service Workers are a separate, orthogonal caching layer for offline and fallback behavior, not a rendering strategy, and get their own treatment in a future PWA article.

Migrating an Existing App

The realistic path off a legacy CSR-only SPA is route by route, not a rewrite.

A product that's been a pure client-side SPA for years rarely gets rebuilt from scratch to adopt a different rendering strategy, and trying to do so is usually the wrong call anyway. The practical default is incremental: most modern meta-frameworks let a team mix rendering modes per route within the same app, which means a route can move from client-side rendering to SSR, SSG, or PPR on its own schedule, without touching the routes around it.

The routes worth migrating first are usually the ones where the SPA's weaknesses are most visible: a marketing or landing page that needs to be crawlable and fast on first load, a product or content page where LCP directly affects conversion, anything currently paying the full JavaScript bundle tax just to render text that never changes per visitor. Routes that are genuinely dashboard-like, authenticated, and update-heavy can reasonably stay client-rendered indefinitely, because that's the situation the strategy actually fits.

This route-by-route approach is also why the earlier framing, rendering as a spectrum rather than a single site-wide choice, matters practically and not just conceptually. A migration doesn't need a target architecture where every route ends up using the same strategy. It needs each route ending up using the strategy that fits what that route actually does.
